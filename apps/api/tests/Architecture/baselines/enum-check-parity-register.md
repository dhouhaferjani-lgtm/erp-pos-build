## Divergences vs the §#26 hand census (2026-08-23 state-machine sweep)

The sweep put the population at **90 status columns, 76 uncovered, 14 constrained**. That census was
grep-based over the migration tree and it is wrong in both directions. Recorded here because the
burn-down denominator has to be the mechanical number, not the remembered one:

- **It missed every `$table->enum()` column.** Laravel renders `enum()` on PostgreSQL as a varchar plus
  an auto-named `{table}_{column}_check`, which no grep for `ADD CONSTRAINT … CHECK` finds. So
  `pos_receipts.fiscal_status` (constrained since `tenant/2026_05_01_000001_prepare_pos_receipts_for_pending_seal.php`)
  and the whole `impersonation_*` family were filed as uncovered when they are covered.
- **It counted a different population.** The register above is every column an `app/**/Domain/Enums/*`
  enum GOVERNS, not every column named `*status*`: 244 tenant columns, not 90. Restricted to
  `*status`-suffixed columns the count is 74, of which 15 are covered — close to the sweep's 76/14 but
  not equal, and the gap is columns with no enum cast at all (below).
- **`bank_reconciliations.status` cannot be asserted at all.** The table carries
  `bank_reconciliations_status_check` but has NO Eloquent model, so there is no enum to compare it to.
  The sweep counted it among the 14 constrained; this gate cannot see it. Same class:
  `fiscal_event_quarantine.payload_parse_status` is `$fillable` and documented `string|null` while its
  sibling `fiscal_events.payload_parse_status` IS cast — a missing cast, not a missing CHECK.
- **One column is already DIVERGENT, not merely uncovered:** see the NARROWER row above. A CHECK that
  is narrower than its enum is a write bomb, not debt.
