## Findings

### Important / MAJOR

1. **[IMPORTANT] `apps/api/app/Modules/Treasury/Application/Projections/TreasuryReceiptBridge.php:428-431` + `apps/api/app/Modules/Treasury/Infrastructure/EloquentPaymentMethodResolver.php:38-41` — the new company-scoped method gate sits on top of a company-ambiguous resolver; multi-company tenants can hard-fail the projection.**
   The diff adds `->where('company_id', $event->company_id)` to the `PaymentMethod` load and throws on null (`TreasuryReceiptBridge.php:435-442`). But `resolveByCode()` filters by tenant only, with an unordered `first()`, and its docblock's uniqueness claim is **stale**: the `(tenant_id, code)` unique was replaced by `(company_id, code)` in `2025_12_30_195300_fix_multi_company_unique_constraints.php:26-29`, so a tenant may legitimately hold one `CARD` method **per company** (the diff's own test builds exactly that shape, `PaymentMethodRepositoryRoutingTest.php:611-621`). When the resolver returns the *other* company's method id, the new gate throws → `ApplyFiscalEventProjectionJob` retries indefinitely for every sale of that company.
   *Why it's not a blocker:* the pre-diff behavior was strictly worse — `find($paymentMethodId)` with no scoping silently bound a foreign-company `payment_method_id` onto the Payment row, and would now have routed money via the wrong company's `default_repository_id` mapping. Fail-closed is the correct posture (mirrors the Task 22 Opus F1 repository gate) and the fail mode is loud, not wrong-money. Single-company tenants are unaffected.
   *Required follow-up (pre-⑤b-cutover, ticketed):* company-scope the resolution — either extend `PaymentMethodResolver::resolveByCode` with `companyId` (Shared/Contracts change) or filter/order deterministically in `EloquentPaymentMethodResolver` — and fix its stale docblock (`EloquentPaymentMethodResolver.php:14-16`).

## Test-quality and replay/idempotency assessment

**Test quality: good.** Real models + `RefreshDatabase`, a full 27-key canonical payload with genuine `canonical_bytes`/hash (`persistEvent`, `canonicalEncode` — no faked projection inputs), `CompanyContext` cleared before `apply()` (worker reality honored), fixed UUIDs (`...101` < `ffffff...102`) making the ordered-by-id fallback assertion deterministic rather than accidental, and API tests using the real endpoint with `RolesAndPermissionsSeeder` conventions inherited from `PaymentMethodTest`. Money stays in strings (`bcadd(...,2)` is test-local EUR fixture math, out of the production guards' scope). Gaps: finding 2 (non-GL/foreign mapping arms untested at the bridge), and no test for the partial-write replay permutation (Payment+GL landed, movement missing, mapping changed) — though the code path is provably safe since the replay branch feeds the stored repository into the same idempotency key.

**Replay/idempotency: this was the whole gate, and it holds.** The Codex plan-review finding 8 resolution is implemented exactly: resolver receives the resolved `PaymentMethod`, the per-leg `Payment` probe runs *before* any mapping read, and replays derive the repository from immutable history rather than mutable operator policy. Defense in depth is real, not incidental — even if the bridge ordering regressed, `handleIdempotentHit`'s repository comparison (`TreasuryMovementService.php:512`) converts a re-routed replay into a loud `IdempotencyConflictException` instead of a second movement. A mapping change can neither create a movement in another repository nor move history.
