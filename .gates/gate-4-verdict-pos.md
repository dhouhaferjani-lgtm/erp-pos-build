## Findings

**[Critical] Empty effective-scope fails OPEN → full-company takings leak** — `PosAnalyticsService.php` (every `->when($locationIds !== [], …)`, e.g. `getSalesSummary`, and 7 sibling methods) and `ReportController.php:271` (`if ($locationIds !== []) { … whereIn … }`). When `LocationScopeResolver::resolve()` returns `[]` — which it does for a user whose effective allowed set is empty (`LocationScopeResolver.php:37-39` returns `effectiveAllowed`; `LocationContext.php:198-200` returns `[]` for no active membership, and `effectiveAllowedIds` returns `array_intersect([], …) = []` for a membership with `allowed_location_ids = []`) — the `!== []` guard **skips the predicate entirely**, so the query returns the **whole company's** analytics / Z-reports. This is reachable: `CreateUserRequest.php:53` / `UpdateUserRequest.php:61` validate `allowed_location_ids` as `['sometimes','nullable','array','list']` with **no `min:1`**, so a user can be provisioned with `allowed_location_ids = []` (intended "no location access") and, given `pos.view_reports`, will see every location's fiscal takings instead of nothing. The sibling surfaces fail CLOSED for this case — `CashPositionController.php:89-94` applies `whereIn('location_id', $effectiveLocationIds)` **unconditionally** (empty → `0=1` → no rows) and only adds `orWhereNull` when `LocationScopeBoundary::isUnrestricted()` is true; Expense/Maturing/Accounting controllers do the same (`ExpenseAnalyticsController.php:33`, `MaturingInstrumentsController.php:57-66`, `ReportsController.php:866`). The POS surfaces are the only ones that guard the predicate with `!== []`. **Fix:** drop the `!== []` guard and apply the location predicate unconditionally (empty set → empty result), deriving inclusion via `LocationScopeBoundary::isUnrestricted()` exactly like the sibling surfaces — inject `LocationScopeBoundary`, and add `orWhereNull` only when unrestricted (see next finding for the nullable column).

**[Important] Plan-mandated scope-enforcement tests are absent — the leak above is unverified** — `ZReportListTest.php` contains **1** test (unfiltered, unrestricted admin) of the **5** the plan required for Task 5 (`docs/superpowers/plans/…-multiloc-4-…md:344`): missing (b) `terminal_id` narrowing, (c) `location_ids[]` narrowing, (d) out-of-scope ⇒ 403, (e) restricted-user/no-param ⇒ own-location-only. `AnalyticsTest.php` covers unrestricted-subset narrowing (`:169`) and cross-company 403 (`:197`) but has **no restricted-membership test** — every acting user has `allowed_location_ids = null` (unrestricted; `AnalyticsTest.php:447-451` creates a membership with no `allowed_location_ids`, and `ZReportListTest.php:30` an `admin`). Consequently the "restricted user with no `location_ids` still narrows" guarantee (plan Task 1 step (c) / Task 5 step (e)) and the Critical empty-set path are both untested — the suite stays green even though a zero-allowed user sees everything. **Fix:** add feature tests using a membership with an explicit subset (`allowed_location_ids = [L1]`) asserting a bare request returns only L1's totals/Z-reports, an out-of-scope in-company id ⇒ 403, and a user with `allowed_location_ids = []` receives an **empty** result (not company-wide) — the last will currently fail and pin the Critical fix.

**[Minor] F&B "Unattributed" orders silently dropped for an unrestricted owner** — `PosAnalyticsService::getFnbMetrics` adds `->when($locationIds !== [], … whereIn('location_id', …))` on `pos_orders`, whose `location_id` **is nullable** (`create_pos_orders_table.php:20`). For an unrestricted owner the resolver returns the concrete list of all location ids, so `whereIn` excludes any closed order with `location_id = NULL`, diverging from the spec ("unrestricted may include Unattributed") and from the sibling `isUnrestricted() + orWhereNull` pattern. Severity Minor because `getFnbMetrics` returns operational metrics (table time, items/order, peak hours, order modes), not a revenue total — no money is undercounted. Note the receipt-based money surfaces are unaffected: `pos_receipts.location_id` (`create_pos_receipts_table.php:29`) and `pos_terminals.location_id` (`create_pos_terminals_table.php:29-31`) are **NOT NULL**, so no takings are dropped there. **Fix:** fold into the isUnrestricted refactor above (add `orWhereNull('location_id')` when unrestricted for the `pos_orders` queries).

**[Minor] PG invariant lane gap for the join-qualified filters** — `ci.yml` adds `ZReportListTest` to the PG allowlist but not `AnalyticsTest`, so the join-qualified predicates in `getSalesByCategory`/`getSalesByProduct`/`getDiscountAnalysis`/payments (all filtering `pos_receipts.location_id` across a join) run only on SQLite. Additionally, `ZReportListTest`'s single test never passes `location_ids`, so the `whereIn('pos_terminals.location_id', …)` branch of the `whereHas` (`ReportController.php:271-273`) is never executed on PostgreSQL. Low risk (columns are unambiguously qualified), but the location branch is unexercised on the target engine. **Fix:** add `AnalyticsTest` to the PG allowlist and add a `?location_ids[]=` assertion to `ZReportListTest`.

## VERDICT: REJECT

What to fix before merge: apply the location predicate unconditionally (fail closed on an empty effective set, using `LocationScopeBoundary::isUnrestricted` + `orWhereNull`-when-unrestricted, matching the sibling controllers) in `PosAnalyticsService` and `ReportController::listZReports`, and add the plan-mandated restricted-user / zero-allowed / 403 / location-filter tests to `AnalyticsTest` and `ZReportListTest` (with a zero-allowed case asserting an empty result) to pin it.
