## Executive Summary

The system has **foundational pieces** for stock lifecycle management, but **significant gaps** exist that prevent proper stock tracking across the document lifecycle.

**Key Findings:**
- ✅ StockMovement and StockLevel models exist with good structure
- ⚠️ Missing 5 critical document types (GoodsReceipt, Returns, Adjustments, Transfers)
- ❌ No listeners connect documents to stock movements
- ❌ Missing MovementReason granularity (only has generic types)
- ⚠️ Missing GL service methods for inventory transactions

## Part E: Decision Points

### Decision 1: MovementType vs MovementReason

**Current:** Generic MovementType (Receipt, Issue, Adjustment)
**P0.5:** Granular MovementReason (GOODS_RECEIPT, DELIVERY, CUSTOMER_RETURN, etc.)

**Recommendation:** **Create MovementReason enum, keep MovementType**
- MovementType: High-level (IN/OUT/ADJUSTMENT)
- MovementReason: Specific business reason
- StockMovement has both fields

**Pros:** Better audit trail, easier reporting
**Cons:** One extra field

---

### Decision 2: Document Reference Structure

**Current:** Single `reference` string field
**P0.5:** Polymorphic `reference_type` + `reference_id`

**Recommendation:** **Add both fields, keep reference for legacy**
- Add reference_type (string) - "delivery_note", "goods_receipt", etc.
- Add reference_id (UUID)
- Keep reference (string) for backward compatibility

---

### Decision 3: COGS Timing

**Current:** COGS created on InvoicePosted
**P0.5:** COGS created on DeliveryNoteConfirmed

**Recommendation:** **Move COGS to DeliveryNoteConfirmed**
- More accurate (stock leaves when delivered, not invoiced)
- Aligns with perpetual inventory accounting
- Matches Tunisia compliance expectations

**Migration:** Update PostCOGSOnInvoice to listen to DeliveryNoteConfirmed instead

---

### Decision 4: Credit Note Returns

**Current:** No distinction between refund-only vs physical return
**P0.5:** Separate ReturnNote document OR flag on CreditNote

**Recommendation:** **Create separate CustomerReturn document type**
- Cleaner separation of concerns
- Return can exist before/without credit note
- Credit note references return (optional)

**Flow:**
1. Customer initiates return
2. Create CustomerReturn document (physical)
3. Confirm return → stock increases
4. Issue CreditNote (financial) → AR decreases
5. Link credit_note.return_note_id = return.id
