## 3. Ground rules (non-negotiable — from CLAUDE.md and `apps/erp/.claude/context/*`, violations block merge)

1. TDD both layers: failing test first (PHPUnit backend, Vitest frontend), red → green → refactor.
2. Strict typing: PHP no `mixed` (DTOs for the validator result), TypeScript no `any` (`unknown` + type guards). New JSONB/DTO shapes need a corresponding PHP DTO.
3. **Module boundaries (rule 6) — this is the point of the whole design.** Validator lives in `app/Shared/Banking/Domain/BankAccountValidator.php` + `app/Shared/Banking/Contracts/BankAccountValidatorInterface.php` + `app/Shared/Banking/Domain/ValueObjects/{RibValidationResult,IbanValidationResult}.php`. `Partner` module code must depend on the **interface**, never import Treasury internals, and never import the `Bank` model directly across a module boundary without going through a public service/contract. Existing pattern to mirror: `app/Shared/Contracts/`, `app/Shared/Precision/` (constructor-injected interfaces, see rule 13).
4. Constructor injection ONLY (`private readonly`), never `app()` helper — this includes wherever the validator or bank lookup is injected into controllers/services.
5. Enums for status/type columns — `is_active`/`is_custom` on `banks` are plain booleans per the design (not enums; that's correct, they're not status/type columns), but if `PaymentRepository`'s `type` column pattern is touched, do not regress it off its existing enum.
6. Route middleware (rule 12): `['api', 'auth:sanctum', SetPermissionsTeam::class, EnforceTokenTenantClaim::class]` for `GET /api/v1/banks` (see §2.3 above — no `can:` gate, matches `categories`/`attachments/config` precedent). Banks/treasury reference data is universal (both IziPOS and Otospex per the design doc §6) — do **not** add a `module:` gate either.
7. Types flow from backend (rule 7): after adding the `BankAccountValidator` result DTO, the `Bank` DTO, and the `PartnerBankAccount` DTO, run `php artisan typescript:transform` (needs `CACHE_STORE=array` in the worktree's `.env` — known gotcha, see `apps/api/.env` if transform silently no-ops). Never hand-edit `packages/shared/types/`.
8. Frontend API handling (rule 14): `apiGet`/`apiPost` already unwrap `response.data.data` — do not double-unwrap in the new `useBanks`/`useBankAccountValidation` hooks.
9. Design tokens (rule 18): `BankPicker.tsx` is a new component in a new directory — use tokens from `@/lib/designTokens` exclusively, zero hardcoded Tailwind colors, from day one (it's a "new feature directory" per rule 18, so this is a hard requirement, not a migrate-as-you-touch one).
10. **Monetary/quantity precision (rule 19) — the validator is the highest-stakes surface in this track.** RIB clé and IBAN check-digit computation are **mod-97 big-integer math — bcmath (`bcmod`, `bcadd`, `bcmul` as needed) or GMP, never float, never `intval`/`(int)` cast on a 20+-digit string** (a PHP int overflows past ~18-19 digits on 64-bit; this is not optional precision hygiene, it's correctness — a float or overflowed int will silently produce wrong check digits on real RIBs). PHPStan's `ForbidFloatCastOnDecimalProperty`/`ForbidHardcodedBcmathScale` guards may not fire here since RIB/IBAN aren't `decimal` currency columns — enforce this by code review + the unit-test fixtures in §5, not by relying on the static-analysis guard alone. RIB/IBAN/BIC are stored and passed as **strings** everywhere, never through `MoneyInput`/numeric coercion.
11. i18n (rule 11): every new label (`BankPicker` search placeholder, "bank not listed" fallback link, validation warning text, bank-accounts section headers in `B2BFieldsSection`) via `t()`, en + fr. Check the 3-place `i18n.ts` wiring (import, resources, ns array) if a new namespace file is needed — more likely this reuses the existing `treasury` and `partners` namespaces; only add a new namespace if genuinely warranted, and note the choice in the progress file.
12. Tests **by path**, never the full suite: `./vendor/bin/phpunit <path>` per test class/file; `pnpm vitest run <path>`. NEVER run the full PHPUnit suite (crashes the machine) and never run vitest unbounded — if a run hangs, `ps aux | grep 'node (vitest'` and kill worker processes.
13. Tenant migrations must be **re-runnable-safe**: use `Schema::hasTable`/`hasColumn` guards consistent with the recent migrations in `apps/api/database/migrations/tenant/2026_07_08_*` (spine columns, repository_movements) — these all guard against re-running against an already-migrated tenant DB. `BanksSeeder` must be idempotent (`updateOrCreate` keyed on `(tenant_id, company_id or country_code, name)` or the unique `(tenant_id, country_code, rib_bank_code)` index from the design) — this is directly tested in §5.
14. Preflight-equivalent before declaring any phase done: `pnpm typecheck`, `pnpm lint`, targeted `pnpm vitest run <paths>`; backend `./vendor/bin/phpunit <path>`, `./vendor/bin/phpstan` on touched modules (level 8, zero errors on new code), `./vendor/bin/pint`.

## 5. Verification (all three phases)

- **Seeder idempotency test:** feature test that runs `BanksSeeder` twice against the same tenant/company and asserts row count is unchanged (no duplicates) and `updateOrCreate` semantics hold on a re-run with a changed `name`/`bic` for an existing `rib_bank_code` — model this on `apps/api/tests/Feature/Seeders/PaymentRepositorySeederTest.php` if it has an idempotency assertion, otherwise on the `PaymentMethodSeeder` test suite.
- **Validator unit tests with real TN fixtures** straight from the design doc: known-valid vector `07040005810111129653 → TN59 0704 0005 8101 1112 9653` (Amen Bank, `rib_bank_code = 07`), plus corrupted-key (flip the last 2 digits), wrong-length (19 or 21 digits), non-numeric-input, and a foreign/non-TN IBAN case (validator should reject cleanly, not throw). Assert on bcmath/GMP-computed values, not hardcoded expected strings copy-pasted without re-deriving the math — the point of the test is to catch a float/overflow regression, so at least one fixture should use a RIB large enough that naive `(int)` casting would silently corrupt it (any 20-digit RIB already exceeds safe 64-bit signed int range for some inputs — verify this is actually exercised, not just theoretically true for the chosen fixture).
- **Playwright-checkable acceptance for the picker:** open `AddRepositoryModal`, select `type=bank_account`, type into the bank search, select a TN bank from the dropdown, assert `bic` field autofills, type a valid RIB into the account/IBAN field, assert a green/valid indicator appears without blocking the Save button; repeat with an invalid RIB and assert a warning indicator appears while Save remains enabled (warn-but-allow, never blocks per design §6). Second flow: partner edit page, add a bank account row via `B2BFieldsSection`, same picker/validator behavior, save succeeds.
- Backend: `./vendor/bin/phpstan` level 8 zero errors on `app/Shared/Banking/**`, `app/Modules/Treasury/**` (touched files), `app/Modules/Partner/**` (touched files); `./vendor/bin/pint`.
