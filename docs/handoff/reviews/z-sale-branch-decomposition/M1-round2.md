**2. P2 — CONFIRMED — §1.3 does not state that the fix inverts which intra-payload identity holds; the gate needs this for ruling question 3 (F-2 sequencing).**
Memo `:77-98` (§1.3 "what a verifier comparing an old and a new event would see"), `:390-423` (F-2), `:538-539` (ruling question 3).
`net_sales` is `Σ receipt.subtotal` (`zReportService.ts:900`), and `subtotal` is `Σ line_total` = gross (`receiptService.ts:153`, stored `:547`). So on a one-line 12.00-gross / 2.00-VAT sale shift: **today** `net_sales 12.00 == Σ vat_breakdown.net_amount 12.00` ✓ while `gross_sales 12.00 ≠ Σ gross_amount 14.00` ✗; **after the fix** `Σ gross_amount 12.00 == gross_sales` ✓ but `Σ net_amount 10.00 ≠ net_sales 12.00` ✗ — off by exactly the shift's VAT. The memo says the fix changes two numeric strings per rate row and stops there; it never says the fix *moves* the payload's internal contradiction from the gross column to the net column. This is operator- and server-visible, not theoretical: `apps/pos/src/components/pos/ZReportModal.tsx:158-159` renders `gross_sales`/`net_sales` directly above the per-rate table at `:176-193`, and the server projection copies both into one row (`ZReportProjection.php:149` vs `:154`). It also matters that the codebase treats the analogous identity as canonical elsewhere — `Σ vat_breakdown[].net_amount == subtotal` is a **hard server-enforced invariant** for `SALE_RECEIPT` (`FiscalPayloadConstraintValidator.php:1097-1098`, enforced `:1139-1166`); the Z family escapes it only because `validateZReportFamilyPayload` (`:764-771`) never iterates the breakdown.
**Failure scenario:** the gate answers ruling question 3 with "F-2 out of scope, ticket it" believing the Z is otherwise coherent post-fix, and M2 ships a signed Z whose headline and per-rate rows disagree by the full VAT — a state the memo's own §1 was commissioned to make visible.
