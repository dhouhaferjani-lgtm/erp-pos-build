### Register

**1 — P1 — `apps/api/app/Modules/CountryDefaults/Presentation/Controllers/DefaultsEditorController.php:34-37, 151-153, 185-187` — CONFIRMED — the `/editors` lifecycle reaches `support_approver` accounts and breaks four-eyes**

Spec §7 F-17 scopes these endpoints to "`defaults_editor` accounts" and states in the same section that "`support_approver` four-eyes semantics [are] untouched" (spec `:206`, `:214`; brief `:382`). The implementation scopes them to **every non-`super_admin` account**: `index()` selects `where('role', '!=', SuperAdminRole::SuperAdmin->value)` (`:35`), and both `updateEditor()` (`:151`) and `resetEditorCredentials()` (`:185`) guard *only* against `role === super_admin`. A `support_approver` is therefore a first-class target of list / rename / disable / role-change / **reset-credentials**.

Failure scenario (each step verified in code): super-admin A wants to impersonate a tenant without a second human. `approveSecond()` requires `$grant->operator_id !== $approver->id` **and** `ConfiguredApproverSet::allows($approver)` — role `support_approver`, active, and email in the `support_access.four_eyes.approver_emails` deploy allowlist (`GrantLifecycleService.php:245`, `ConfiguredApproverSet.php:36-42`). A calls `GET /api/v1/admin/country-defaults/editors`, which now enumerates every allowlisted approver with `id` + `email` (`DefaultsEditorResource.php:17-21`). A calls `POST /editors/{approverId}/reset-credentials` with no body: the account's password is overwritten and the **plaintext is returned to A** in `meta.generated_credential` (`:182`, `:188`, `:91`). The approver's email is unchanged, so it is still allowlisted; `support_approver` login is not flag-blocked (`SuperAdminAuthController.php:40`, and `DefaultsEditorLoginFlagTest.php:20` asserts 200 for that role). A logs in as the approver and self-approves the grant. The audit trail attributes the approval to the approver. `PUT /editors` with `is_active:false` or `role:'defaults_editor'` gives the cheaper denial-of-approval variant.

This capability did **not** exist before M3: `grep -rn "SuperAdmin::query()->create\|password" app/Http/Controllers/Api/Admin/ app/Modules/` finds no other admin-account CRUD or password-mutation path anywhere in the codebase — the only pre-existing use of `SuperAdmin.password` is the `Hash::check` in `login()`. The behavior is not accidental: `DefaultsEditorLifecycleTest.php:45-49` explicitly asserts that `role: 'support_approver'` is accepted, and `UpdateDefaultsEditorRequest.php:26-29` explicitly whitelists it. Minimum fix: restrict every `/editors` selector and lock to `role === defaults_editor` (list, update, reset), and drop `SupportApprover` from the `Rule::in` on `role`.

**2 — P2 — `apps/api/app/Http/Controllers/Api/Admin/SuperAdminAuthController.php:40-45` with `apps/api/app/Modules/CountryDefaults/Presentation/routes.php:11-18` — CONFIRMED — the `external_editors_enabled` kill switch is login-only, never re-checked at the request boundary**

The wave's standing owner constraint is "`defaults_editor` stays FEATURE-FLAGGED OFF until the central-admin MFA lane lands" (`progress.yaml`, `defaults-editor-activation`), and brief `:409` frames the flag as blocking `defaults_editor` **authentication**. It is enforced at exactly one point — the login credential path. Neither `EnsureCentralAdmin` nor `central_admin_role:super_admin,defaults_editor` consults it, and flipping the flag off does not revoke existing tokens (contrast the explicit `tokens()->delete()` on disable/role-change at `DefaultsEditorController.php:160-162`).

Failure scenario: staging sets `COUNTRY_DEFAULTS_EXTERNAL_EDITORS_ENABLED=true` for a demo; an external accountant logs in and receives a Sanctum PAT. Ops flips the flag back off. `config/sanctum.php:53` sets `'expiration' => 43200` (30 days), so that token keeps passing the whole M3 middleware stack for up to 30 days and can continue to create drafts, upsert rows, publish, and re-point country assignments — the inputs that M5 turns into company provisioning. Turning the flag off is the documented control and it does not close the door. A `is_active`/role-scoped `defaults_editor` check inside `EnsureCentralAdmin` (or a dedicated middleware on the group), plus a token sweep when the flag goes false, makes the switch fail-closed.

**3 — P2 — `DefaultsEditorController.php:102-107` and `TemplateRowController.php:46-51` — CONFIRMED — blanket `QueryException` → 409 masks unrelated infrastructure failures**

Both handlers catch `QueryException` unconditionally and return a typed lifecycle-conflict 409. This is the exact defect a prior review round already forced out of the sibling controller: `AssignmentController::update()` now narrows to SQLSTATE `23505`/`23000` on the *named* `country_template_assignments_country_domain_unique` constraint and **rethrows everything else** (`AssignmentController.php:83-107`), with a trigger-based test proving propagation (`AssignmentApiEndpointTest.php:143-162`). The two siblings were left unnarrowed and have no equivalent test.

Failure scenario: a deadlock (`40P01`), statement timeout (`57014`), or dropped central connection during `PUT /editors` returns `409 EDITOR_CONFLICT` — "The editor account operation conflicts with its current state." The operator retries, gets 409 again, and concludes the account is in a bad lifecycle state. No 5xx reaches monitoring or Sentry, so a live central-DB incident is invisible. Identical for a 5000-row `PUT /templates/{id}/rows` failing on disk-full or timeout mid-transaction, where the operator is told their draft is in conflict.

### Bypasses attempted that FAILED (the code held)

- **`defaults_editor` reaching `/editors` through middleware dedup.** Laravel keeps both `central_admin_role:super_admin,defaults_editor` and the nested `central_admin_role:super_admin` (different parameters → distinct strings in `gatherMiddleware()`); both execute, and `RequireCentralAdminRole.php:26` uses strict `in_array`. `CentralAdminRouteInventoryTest.php:74-81` asserts 403 on every `/editors` verb.
- **Tenant-user token authenticating on the admin guard.** `config/auth.php:50-53` pins `sanctum-admin` to the `super_admins` provider, and Sanctum's `Guard::isValidAccessToken()` calls `hasValidProvider($accessToken->tokenable)` (`vendor/laravel/sanctum/src/Guard.php:130,140`), so a tenant `User` token cannot resolve there. `EnsureCentralAdmin.php:19-21` is a second `instanceof` layer.
- **SuperAdmin token reaching tenant routes.** Mirror check: `sanctum` is pinned to the `users` provider, so a `defaults_editor` PAT cannot authenticate on `auth:sanctum`. The `super-admin` ability that `EnforceTokenTenantClaim.php:78` honors is therefore unreachable from a central token on a tenant route — the escalation I was hunting does not exist.
- **Deactivated central admin slipping through.** `EnsureCentralAdmin.php:22-24` and `RequireCentralAdminRole.php:22-24` both check `is_active`; `AdminAuthRouteBoundaryTest.php:36-43` proves `ACCOUNT_DEACTIVATED` on `/admin/auth/me`.
- **Widening the full-admin group.** `routes/api.php:57-58` is byte-identical to base (`git diff` on the file shows only the `super_admin` → `central_admin` swap at `:44`), and `CentralAdminRouteInventoryTest.php:47-51` asserts the exact four-element list on every route carrying the `super_admin` alias — a fifth entry or a reorder fails.
- **Creating a privileged account through `POST /editors`.** `CreateDefaultsEditorRequest.php:28` marks `role` `prohibited`, and the controller hardcodes `SuperAdminRole::DefaultsEditor` at `:129`; `DefaultsEditorLifecycleTest.php:79-83` covers it. (The *update* path is a different story — finding 1.)
- **Duplicate-email account through a wrong-connection validator.** `Rule::unique(SuperAdmin::class, 'email')` derives both table and pinned central connection from the model (`CreateDefaultsEditorRequest.php:26`), proven by the `DB::listen` connection-name assertion at `DefaultsEditorLifecycleTest.php:86-104`.
- **Stealing another template's rows via a supplied `id`.** `TemplateRowController.php:66-71` rejects any `rows.*.id` not present in the locked template's own `$existing` set before any delete runs.
- **Editing a published template through any HTTP verb.** `updateDraft()` (`:229`), `replaceDraftRows()` (`:61`) both re-read under `lockForUpdate()` and reject non-`Draft`, on top of the M2 model hooks; `TemplateApiEndpointTest.php:88-89` asserts the 409.
- **Escaping the audit inside the HTTP layer.** Every mutating path (`TemplateController.php:204,227`, `TemplateRowController.php:59`, `DefaultsEditorController.php:124,149,183`) wraps the write and its `AdminAuditService::log()` in one `$connection->transaction()` on the central connection.
