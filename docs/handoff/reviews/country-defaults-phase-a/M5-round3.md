## Findings register

**1. P2 — `apps/api/tests/Feature/CountryDefaults/FrozenSeederProvisioningIsolationTest.php:114-126` — CONFIRMED.** The F-6 static guard is bypassable and does not cover the scope the brief assigns it. `codeNames()` only inspects `T_STRING`/`T_NAME_QUALIFIED`; a string-literal FQCN is `T_CONSTANT_ENCAPSED_STRING` and is invisible to it. **Failure scenario:** a later commit writes `$this->call('Database\Seeders\TunisiaChartOfAccountsSeeder')` (or `app('Database\Seeders\FranceChartOfAccountsSeeder')`, or a `match` returning a class-string) inside `CompanyController` or `TenantInitializationService`; a frozen seeder is back in the flag-true provisioning path and the guard stays green. Separately the walk is limited to `app/` + `database/` (`:81`), so the brief's "plus **explicitly labeled** historical-compat tests" carve-out is unenforced — and this milestone's own `ExpenseCategorySeederLoudFailureTest.php:14,40,56` imports `GenericChartOfAccountsSeeder` with **no** `#[Group('historical-compat')]`, unlike the correctly-labeled `DemoSeedersTaxTest.php:39,63,90`.

**2. P2 — `apps/api/app/Console/Commands/SeedChartsCommand.php:87-93` — CONFIRMED.** The new fail-closed guard is evaluated *before* `$dryRun` is read (`:95`), so it blocks the read-only inspection mode too, and it retires the only existing-company chart-repair path with no replacement and no runbook line. **Failure scenario:** after the Release-2 flip, an operator responding to a treasury incident cannot even run `accounting:seed-charts --dry-run` to enumerate which existing companies are missing the portfolio/fee accounts the command's own docblock (`:19-27`, citing `docs/handoff/treasury-phase2-deploy-checklist.md §2`) exists to add; the documented procedure becomes inoperable with no successor named. Failing closed for the *write* mode is correct under N-C — over-blocking the dry run is not.

**3. P2 — `apps/api/app/Modules/CountryDefaults/Application/Services/CountryTemplateResolver.php:30,36,58,62` + `bootstrap/app.php:883-891` — CONFIRMED.** Platform-configuration failures are surfaced to tenant end users as untranslated English `422 BUSINESS_ERROR`. **Failure scenario:** a tenant admin submits `POST /api/v1/companies` for `TN` before the super-admin has made the exact assignment and receives `{"code":"BUSINESS_ERROR","message":"Timbre-capable country TN requires an exact template assignment."}` — internal template/certification vocabulary, no `fr`, presented as a business rule the user could fix, when in fact nothing the user can do resolves it. Same for `"No pinned wildcard assignment exists for chart_of_accounts."` (`:36`) and `"Assignment TN does not reference a published template."` (`:58`). This is the single most likely Release-2 failure mode and it has no typed code, no translation, and no operator-vs-user distinction.

**4. P3 — `apps/api/database/seeders/ExpenseCategorySeeder.php:76-111` + `apps/api/app/Modules/Company/Presentation/Controllers/CompanyController.php:156` — CONFIRMED.** The D-5 loud failure and the catch removal are **not** gated by `provisioning_enabled`, so "Release 1 … readers stay legacy" (brief §5.5) is not behaviorally inert: from Release 1 onward, a chart gap that previously degraded to `GeneralExpense` aborts company creation. This is brief-sanctioned (D-5 is explicitly assigned ungated) and I verified no live country breaks today, but the release note must say Release 1 carries a behavior change, because the flag-matrix test suite implies it does not.

**5. P3 — `apps/api/config/country_defaults.php:6` — CONFIRMED.** Under the standard production `php artisan config:cache`, `config('country_defaults.provisioning_enabled')` returns the value baked at cache time. The brief's "Release 2 **is** a deployment configuration change setting it true. Rollback = restore false" therefore requires an explicit `config:cache` rebuild + app/Horizon restart on both the flip and the rollback. No runbook line was added. The code-level requirement (no boot capture, no memoization) is satisfied.

**6. P3 — `apps/api/app/Modules/CountryDefaults/Infrastructure/Seeders/TemplateChartOfAccountsSeeder.php:40-58` — CONFIRMED.** Divergence from the "reproduce the **actual** current semantics" instruction: a row matched by `system_purpose` rather than `code` falls into the same branch as a code match and gets its `is_system` promoted (`:50-56`). Legacy takes the purpose match and `continue`s without promotion (`GenericChartOfAccountsSeeder.php:58-70`). Benign and arguably better, but it is an unpinned divergence — no test covers the purpose-match branch at all.

**7. P3 — `apps/api/database/seeders/CountryDefaultsChartOfAccountsSeeder.php:26-29` — CONFIRMED.** `Company::query()->when($tenantId !== null, …)->findOrFail($companyId)` performs an unscoped global company lookup when the optional `$tenantId` is omitted, which the contract permits (`ChartOfAccountsSeederContract.php:30`). Seeder-only surface and the id is an unguessable UUID, so impact is negligible in shared-DB compat mode, but the tenant filter should not be optional on a class whose whole job is picking a provisioning target.

**8. P3 — `apps/api/app/Modules/CountryDefaults/Infrastructure/Seeders/TemplateChartOfAccountsSeeder.php:74` — CONFIRMED.** `'balance' => '0.000'` is a hardcoded scale-3 literal. No float is involved and it matches `Account::$attributes['balance']`, so this is a style nit against Rule 19's "scale comes from the resolver", not a defect.

**9. P3 — commit `5adb98de8`, scope creep — CONFIRMED.** Edits unrelated to M5 rode along: `ParapharmacySeeder.php:960` (`is_physical` removed), `:1299` (new null guard), four docblock `@param` additions; `CoffeeShopSeeder.php:307` (`started_at` removed); `TunisianParapharmacySeeder.php:464` (`is_physical` removed). **10. P3 — `apps/api/tests/Feature/CountryDefaults/ProvisioningFlagMatrixTest.php:41,52,271` — CONFIRMED.** The "additional company" leg of the brief's required *both flag values × both provisioning paths* matrix is a direct `ChartOfAccountsService::seedForCompany()` call, not `POST /api/v1/companies`. No test asserts a **successful** additional-company creation with the flag true. This is transitively de-risked: `test_registration_path_uses_template_when_flag_is_true` (`:83-93`) drives the full `initializeForNewRegistration`, which includes step 3.5 expense categories and step 8 payment repositories against a template-provisioned chart — so a template missing `6130`/`GeneralExpense`/a treasury purpose would already fail there.

**11. P3 — `apps/api/app/Modules/Company/Domain/Company.php:141-154` + `app/Modules/Progression/Infrastructure/Listeners/RegisterCompanyWithGrowthAdvisor.php:19-31` — PLAUSIBLE.** New cross-boundary partial write introduced by making COA failure roll back. `CompanyCreated` fires from `static::created` **inside** the controller transaction; `RegisterCompanyWithGrowthAdvisor` is synchronous (no `ShouldQueue`) and posts an external registration. When the resolver or expense seeder now throws, the DB rolls back but the external Growth Advisor registration does not, leaving a phantom company id registered outside the system. Marked PLAUSIBLE because the listener swallows all throwables and the impact depends on `GrowthAdvisorClientInterface` being live in the target environment, which I did not verify.

**12. P3 — evidence, commit `5adb98de8`.** No red-first artifact exists for M5: implementation and all eight test files landed in one commit with no captured failing output, and `M5-round1.md`/`M5-round2.md` are tool-error stubs. This matches the accepted pattern for M0–M4 in this wave (e.g. `cd73d36fd`), so I am not treating it as blocking — but the standing red-first check is not satisfiable from the record, and I ran no tests (read-only mandate), so every green claim in this review is static-analysis-based.

## Bypasses I attempted that FAILED (i.e. the implementation held)

- **Boot-time flag capture.** Tried to find a constructor-captured or `once()`/`static`-memoized read of `provisioning_enabled` — none; `ChartOfAccountsService.php:42` reads per call, proven by `ProvisioningNoCacheTest.php:25-41`.
- **Resolver reading the tenant connection.** Tried the default-connection swap — the `CentralConnection` trait on all three models pins it; `CountryTemplateResolverTest.php:119-137` already tests exactly this.
- **Archived/unpublished template reaching provisioning.** `verifiedTemplate` (`CountryTemplateResolver.php:53-57`) rejects any non-`Published` status; `TemplateChartOfAccountsSeeder.php:20-22` rejects again at the seam.
- **Domain mismatch / out-of-scope certification via a stale assignment row.** Blocked upstream at `TemplateAssignmentService.php:69-100` (domain match, capability version, content-hash re-verification, `CertificationScope::allowsAssignment`), and published templates are immutable (`AdminTemplate.php:47-52`), so a validated assignment cannot rot into an invalid one.
- **Cross-company write from the template seeder.** All four statements are scoped `tenant_id` + `company_id` (`TemplateChartOfAccountsSeeder.php:33-36,42-45,51-55,94-98`), with a `$updated !== 1` tripwire at `:99-101`; `TemplateChartOfAccountsSeederSemanticsTest.php:71-93` pins it.
- **Duplicate `system_purpose` insert via the code-then-purpose two-key lookup.** Walked the pass-1 ordering: the purpose probe at `:41-46` runs against rows already inserted earlier in the same loop, so the second definition maps onto the first row rather than inserting a colliding purpose.
- **Orphaned tenant database on db-per-tenant registration failure.** `TenantProvisioningService.php:203-207` catches `\Throwable` and compensates (drops the DB, deletes central rows), so the new `DomainException` is covered by the existing mechanism despite the test running only the compat branch.
