### 1. P2 — the capability *version* is not coupled to the capability *set*, and the test that claims to catch exactly that does not · CONFIRMED
`apps/api/tests/Unit/CountryDefaults/CountryAccountingCapabilitiesServiceTest.php:26` + `apps/api/app/Modules/CountryDefaults/Application/Services/CountryAccountingCapabilitiesService.php:11,14`

The test comment reads *"Production break caught: the capability set changes without the certification version changing with it."* It catches no such thing. `test_only_tunisia_is_stamp_duty_capable_after_normalization` asserts five fixed inputs (`' TN '`, `'tn'` true; `'FR'`, `'zz'`, `''` false); `test_capability_version_is_the_stable_v1_scalar` pins `'v1'` independently. Adding `'MA'` to `STAMP_DUTY_COUNTRIES` (`:14`) changes none of those five values and leaves `CAPABILITY_VERSION` at `'v1'`. I swept every guard for a contents pin: `CapabilityAuthoritySingularityTest.php:43,46` only `str_contains` the *constant names* to locate the file, never their values; `test_tax_seeder_stamp_capability_and_country_authority_agree` (`:135-155`) iterates only `['TN','FR']`. Repo-wide grep for `STAMP_DUTY_COUNTRIES` / `CAPABILITY_VERSION` / `->version()` returns no other assertion.

**Failure scenario:** a later lane makes Morocco timbre-capable and adds `'MA'` to the set. No test reds, so the version literal stays `'v1'`. Per spec §3.1 (`2026-08-08-country-defaults-super-admin-design.md:79`), `capability_registry_version` is stamped at publish and the resolver refuses any assignment whose stored version differs from the current one — that equality is the *entire* recertification tripwire. A template published under old-v1 with exact scope `["MA"]` was, at publish time, forbidden by the non-timbre negative rule from carrying a `SalesStampDutyPayable` row. After the set change it is still assigned, still stamped `v1`, and the version check passes. MA companies are provisioned from a chart with no stamp-payable account; the first MA credit note bearing timbre hits `getAccountByPurpose($companyId, SystemAccountPurpose::SalesStampDutyPayable)` at `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:292` and the GL posting throws. The wildcard direction is genuinely fail-closed (a timbre country never falls back to `*`), but the exact-scope direction is not.

This is the milestone's own named invariant — *"one [production place] answers what is the capability version"* — present but vacuous on the half that matters: the version authority is not tied to what it versions. **Minimum acceptable fix is small:** pin the full capable-country set alongside the version in the existing M1 test (so any set edit reds until the version literal is bumped), or, at absolute minimum, delete the comment that asserts a guarantee the suite does not provide and add this as an explicit acceptance criterion on the carry-forward ticket. Leaving a green test that misdescribes its own coverage will mislead the M2 reviewer who is asked to trust the stored version.
