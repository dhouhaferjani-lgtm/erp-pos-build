## Register

**1. P1 — CONFIRMED — `apps/api/app/Modules/Accounting/Presentation/Console/CheckCogsCoverageCommand.php:283-302` — D-f's POS arm still reports a by-design no-movement population: sale lines whose product has no `stock_levels` row at the sale location.**
Both POS receipt-line writers return without writing any movement when the location's `stock_levels` row is absent, and both document it as intended: `ReceiptCreationService.php:911-913` (*"No stock record — skip stock decrement for products without inventory tracking"*) and `PosCoreReceiptProjection.php:1940-1957` (product-level lines *"are normal (non-inventory / service items) and stay silent to avoid log noise"*). `stock_movement_expected` is hard-coded `true` for every non-Return line (`PosCoreReceiptProjection.php:1243-1251` gates the computation on `$receiptType === ReceiptType::Return`), and the column default is `true` for `ReceiptCreationService`'s lines, which never set it. The round-2 filter at `:295` therefore does not touch this population.
*Failure scenario:* a product is added to the catalogue and sold before its first goods receipt posts, or a second terminal/location has no `stock_levels` row for a product stocked elsewhere. The receipt is above the watermark, the line is physical with `quantity > 0`, and no `('pos_receipt', receipt_id, product_id)` movement exists. D-f logs and the command exits `FAILURE` every night, with no grace window and no watermark protection (the receipts are new). `stock_levels` rows are only created by `OpeningBalancePostingService:141`, `WeightedAverageCostService:178/515` and `StockAdjustmentService:1578` — nothing creates one at product creation, so the population is not hypothetical. Note the brief's D-f contract scopes the population to *"physical **+ stock-tracked** products"* (`:452`); "stock-tracked" is unimplemented — `is_physical` is the whole predicate — and "has a `stock_levels` row at this location" is precisely the de-facto stock-tracked signal both writers use. Either that predicate joins D-f, or these lines get the same explicit `stock_movement_expected = false` treatment the refund dispositions got. As shipped, neither a positive nor a negative was constructed for this lane, so M3's evidence contract ("stays silent on a constructed negative") is not discharged for the **sale** path — only the refund path.

**2. P2 — CONFIRMED — `CheckCogsCoverageCommand.php:283-302` vs `PosCoreReceiptProjection.php:2109-2124` — a SCRAP refund of a product archived between sale and refund writes neither leg, is `stock_movement_expected = true`, and fires D-f forever.**

**4. P3 — CONFIRMED — `PosCoreReceiptProjection.php:1281` — writing the raw canonical `disposition` string into an enum-cast column gives a projector a way to reject an already-sealed event.**
`ReceiptLine::casts()` now maps `disposition => ReturnLineDisposition::class` (`ReceiptLine.php:132`), so Laravel's enum cast calls `ReturnLineDisposition::from($value)` on assignment and throws `ValueError` for any out-of-domain string. Thirty-eight lines above, the same value is read defensively with `tryFrom` (`:1245`), and `applyScrapDisposition`'s docblock states the doctrine outright: *"A projector may never REJECT an already-signed event (Model 1, §4.1)"*. Today the value is constrained at ingest (`FiscalPayloadConstraintValidator.php:1999`, domain `['restock','scrap','not_received']`), so the population is empty — but the column write converts a previously-tolerated bad value (which fell through `tryFrom → null` to unconditional restock) into a hard projection failure. Cheap fix: write `ReturnLineDisposition::tryFrom(...)?->value`. Also note no consumer reads `pos_receipt_lines.disposition` — the write is currently observability-only, so it carries risk without a reader.

**5. P3 — CONFIRMED — `CheckCogsCoverageCommand.php:296` vs `ReceiptReturnService.php:1018` — the interactive return path's new `stock_movement_expected` write is dead for D-f, and interactive returns are entirely outside D-f's coverage.**
