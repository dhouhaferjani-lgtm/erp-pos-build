## 1. What exists (facts)

- **Transfers**: `Inventory` module; `TransferStatus` draft → in_transit → completed | cancelled (`Domain/Enums/TransferStatus.php:17-21`); intercompany rejected at runtime. Idempotency at initiate only (`StockTransferService.php:195-203`). In-transit quantity is *derived* from `stock_transfers.status = in_transit` in three query services (`LocationStockQueryService.php:144,228`, `StockMatrixQueryService.php:402`, `WeightedAverageCostService.php:124`). Events `StockTransferInitiated/Completed/Cancelled` are plain `Dispatchable`, **not stored** (`DomainEvent`/Spatie). `StockTransferCompleted` has **no listener**. Web pages exist; **no mobile screen**.
- **Replenishment requests**: `pending → in_progress → fulfilled | rejected | cancelled`, no approval step; request → transfer via `ReplenishmentFulfillmentService::createTransfers()` with derived idempotency key (`:83`); settlement by listener on `StockTransferInitiated` (`SettleRequestsOnTransferInitiated`), reopen on cancel. POS capture exists; **no mobile screen**.
- **Goods receipts**: from a confirmed PO or standalone (Procurement policy); **never from a transfer**. Status draft | posted; PO carries partial/full. Over-receipt hard refusal, batch/expiry policies, `GoodsReceived` is a stored DomainEvent with exactly one listener (GR-IR posting, pinned by test).
- **Blind counting pattern to mirror**: counter-facing endpoints omit `theoretical_qty` by construction (`InventoryCountingController.php:376` guard comment), access by assignment not permission (`isUserAssigned()`), separate supervisor reconciliation (`CountingDiscrepancyReportService.php`), mobile types mirror the omission (`countingApi.ts:171-197`).
- **Notifications**: Laravel DB notifications + web bell only; 13 notification classes, none for stock; mobile push absent.
- **Mobile**: counting (blind, offline queue), receiving (PO only, **no offline queue**, non-blind), placements, scanning, expenses. No transfers, no replenishment.

## 2. Gaps ranked

1. Transfer completion is all-or-nothing, quantity-less, no discrepancy path, not event-sourced, no completion listener.
2. No receipt document for transfers → nothing to make blind; no receiver assignment concept for POs or transfers.
3. No notification on any stock event; no push channel.
4. No concurrency test on `complete()`; no negative-stock test on the transfer path beyond initiate; replenishment partial-fulfilment/bump paths thin at the UI level.
5. Mobile: receiving has no offline queue; no transfer/replenishment screens.

**M-1 — Mobile: incoming transfers (receive, blind) and replenishment capture.** After T-2/T-3 APIs land: "Réceptions" list gains a *Transferts entrants* tab; blind receive flow = scan → count → submit, using the counting offline-queue pattern (`pendingCountSyncService.ts`) so receiving finally gets an offline queue too.
