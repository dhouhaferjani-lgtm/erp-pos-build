# Ruling + plan addendum — W-LOT-A-1a, legacy NULL-team roles (2026-09-09, paste into the `W-LOT-A-1a permissions/roles/web gating` thread)

**Decision: NO ownership adoption. Do not re-home legacy roles.** Legacy roles created by `RolesAndPermissionsSeeder` via `Role::firstOrCreate(['name', 'guard_name'])` (`apps/api/database/seeders/RolesAndPermissionsSeeder.php:567`) carry `tenant_id = NULL`. Under Spatie teams (`config/permission.php:99,134`) a NULL-team role is matched by every lookup — `Role::findByParam` selects `whereNull(tenant_id) OR tenant_id = getPermissionsTeamId()` (`apps/api/vendor/spatie/laravel-permission/src/Models/Role.php:174-180`). In this database-per-tenant deployment every row of a tenant database already belongs to that tenant, so a NULL team is not an ownership ambiguity; it is the shipped shape of every seeded role in every tenant. Setting `tenant_id` on those rows would (a) make them invisible to any context where `getPermissionsTeamId()` is null — console commands and queued jobs run without `SetPermissionsTeam` (CLAUDE.md rule 20) — and (b) change a lookup contract the whole application relies on, far outside §2's hard scope. That is the ownership migration §8.4 deliberately does not define; it stays undefined.
