## Findings (all LOW; none blocking)

1. **LOW — immediate-excess advance-JE timing change is real but unpinned** (concur with Opus RC2 LOW-1). `createCustomerAdvanceJournalEntry` defaults to `PostingMode::AfterCommit` (`GeneralLedgerService.php:341`); the diff passes `SynchronousInTransaction` unconditionally (`PaymentController.php:1057`), changing the immediate path too. The direction is safe — the movement's `journal_entry_id` now references a POSTED entry atomically, closing a latent crash window between commit and after-commit posting — and it is recorded, but the only immediate-path pin (`DeferredTenderPaymentTest.php:185`) has no excess leg, so nothing pins the new immediate-excess behavior. Add a pin (immediate payment with excess: advance JE posted in-transaction, movement linked) in Wave E/F.
2. **LOW — legacy deposit wrapper posts remittance GL under the weaker permission** (concur with Opus RC2 LOW-2). `POST /payment-instruments/{id}/deposit` keeps `can:instruments.transfer` (`routes.php:105-107`) but now wraps createDraft→addLine→remit (`InstrumentLifecycleService.php:164-180`), which for an effet posts the §7 remise JE (Dr 5113 / Cr 413) — an action the canonical route gates behind `instruments.remit`. Seeded roles hold both, so exposure is custom-roles only. Either move the wrapper to `instruments.remit` or record the asymmetry as intended URL-compatibility behavior.
3. **LOW — supplied-instrument partner check is stricter than spec §8 and the delta is unrecorded.** Spec §8 allows an instrument "owned by the same partner-or-null"; plan Task 13 says "partner-matching"; the code enforces exact equality (`PaymentController.php:590 / :720`), so a null-partner manually-registered instrument is 422'd until its partner is set via PATCH. Fail-closed with a workaround, but the spec/plan discrepancy and the chosen (stricter) reading should be one line in the progress file — or relax to partner-or-null per spec.
4. **LOW — new `payment_method_id` rule lacks `uuid` before `ScopedExists`.** `MultiPaymentController.php:453-456` (`recordPaymentOnAccount`): `ScopedExists` is a bare `Rule::exists` (`ScopedExists.php:34-37`), so a non-UUID string reaches a PG `uuid` column comparison and 500s (SQLSTATE 22P02) instead of 422. Matches the file's pre-existing idiom (`:136-139`, `:269-272` share the gap), and the deferred guards themselves are safe (they run post-validation) — a blemish, not a money bug, but new code shouldn't replicate it. Add `'uuid'`; sweep siblings opportunistically.
5. **LOW — instrument-eligibility amount equality compares at company scale, not payment-currency scale.** `PaymentController.php:591 / :723` use `bccomp(..., $this->scale())` (no-arg company resolution, `:68-71`). When the payment currency's scale exceeds the company's, amounts differing in the extra decimals compare equal, admitting an instrument whose nominal differs from the payment by up to one company-scale ulp — a future reconcile-#4 drift seed. Unreachable in single-currency tenants; use `getScale($paymentCurrency)` when next touching the block.
