## 1. Findings to fix (priority order)

### M-1 · P0 · `GET /inventory/zones` does not exist (404) — zone-scoped drafts and the zone label are broken
- Mobile: `src/features/counting/api/countingApi.ts:213-227` (`getZones`), `src/features/counting/api/queries.ts:83` (`useInventoryZones`), consumers `app/(app)/counting/create-draft.tsx:96` and `app/(app)/counting/[id]/index.tsx:44-62`. Test pinning the wrong URL: `src/features/counting/__tests__/countingApiZoneScope.test.ts`.
- Server: the flat zones API was replaced on 2026-07-07 (`f6d84c08d`) by the placement-node hierarchy. Replacement: `GET /inventory/locations/{locationId}/nodes` (`can:inventory.view`; optional `?include_deleted=1`). Response `{ data: LocationNodeDto[] }` with `id, location_id, parent_id, node_type ('zone'|'aisle'|'rack'|'shelf'|'bin'|'section'), code, name, path, depth, sort_order, is_active, updated_at, deleted_at`. The mobile placements feature already consumes it: `src/features/placements/api/placementApi.ts:48-54` — reuse that call.
- Counting-scope contract: `scope_filters.zone_ids[]` must be ids from `location_nodes` of `scope_filters.location_id` (any node type; soft-deleted nodes are refused with 422 VALIDATION_ERROR on `scope_filters.zone_ids.*`).
- Fix: `getZones(locationId)` → call the nodes endpoint, keep `deleted_at === null && is_active`, map to `InventoryZone` (`id, locationId: location_id, name, code, sortOrder: sort_order, isActive: is_active, createdAt/updatedAt`). Show `path` or indent by `depth` so a shelf under an aisle is readable. Update the test.
- Acceptance: create a zone draft on a location that has nodes → the picker lists them → activation succeeds → session screen shows the zone names in the label.

### M-2 · P1 · `warehouse` scope type does not exist server-side; `zone` label missing

- Fix: remove `warehouse` from the union and the picker; add `zone` to `scopeLabel`.

### M-3 · P0 · `product_location` drafts never carry `location_id` → the count silently spans every location
- Mobile: `createDraftScopeFilters` (`countingApi.ts:99-110`) and `scopeFiltersForDraft` (`src/features/counting/services/draftSyncService.ts:59-72`) send `{ product_ids: [] }` for every non-zone scope; `CreateDraftInput` has no `locationId` for `product_location`; the create-draft screen shows the location picker only for zone scope (`create-draft.tsx:95`).
- Live evidence: a mobile-shaped `product_location` draft with two products was activated into **7 items across 4 locations** (STORE-SFA, WH-01, STORE-TUN1, STORE-SOU). A `product_location` counting with a null location also never matches `CountingBlockService::scopeCoversLocation()` and escapes the per-location terminal-sync-health gate.
- Server change coming with lane N-1 (ERP): `POST /inventory/countings/{id}/activate-draft` refuses a `product_location` draft with no `scope_filters.location_id` → **422 `{"error":"A location must be selected before activation"}`**; `POST /inventory/countings/drafts` validates `scope_filters.location_id` (`required_if:scope_type,product_location`, company-scoped) → 422 `{error:{code:'VALIDATION_ERROR', message, errors:{'scope_filters.location_id':[...]}}}`; `POST /inventory/countings/drafts/batch` keeps its per-row contract: a `product_location` (or `zone`) draft without `scopeFilters.location_id`, or with a location that does not belong to the company, is NOT persisted and comes back in `errors[]` as `{localId, error:'A location must be selected for this scope'}` (or `'Location not found for the current company'`) while the other drafts in the batch succeed (201). An unknown `scopeType` (e.g. `warehouse`) now fails validation for the whole batch (422 VALIDATION_ERROR on `drafts.N.scopeType`) — never enqueue one. Activating a draft whose scope matches no stock rows is refused with 422 `{error:{code:'BUSINESS_ERROR', message:'Nothing to count in this scope — no stock rows matched'}}` — surface that message on the draft screen. `scope_filters` cannot be changed by `PATCH …/draft`, so it must be right at creation. Zone drafts need `location_id` too (already sent today).
- Fix: `CreateDraftInput` for `product_location` requires `locationId`; show the location picker for `product_location` (same component as zone); batch payload `scopeFilters: { product_ids: [], location_id }`; parked-draft error surfacing (M-5) shows the server message. Tests: `draftSyncServiceZoneScope.test.ts` sibling for product_location; `createDraftZoneScopeScreen.test.tsx` sibling.
- Acceptance: a product_location draft created on mobile, activated, shows only items at the chosen location in counter-view.

### M-4 · P1 · no lifecycle awareness — the session screen never reads `counting.status`, and a closed counting parks offline counts forever
- Mobile: `app/(app)/counting/[id]/index.tsx` never inspects `session.counting.status` (scan CTA at :181-187 and every row stay tappable after `pending_review` / `finalized` / `cancelled`); `src/features/counting/lib/taskView.ts:22-26` knows `*_in_progress`, `scheduled`, `activated` only; `pendingCountSyncService.ts:10-15` parks every 4xx as `sync_error` with no bulk discard.
- Server truth: `GET /inventory/countings/my-tasks` returns ONLY statuses `count_1_in_progress | count_2_in_progress | count_3_in_progress` (controller :539-543) — the task disappears from the list the instant the last item is counted (status auto-transitions to `count_1_completed` → `pending_review` when `requires_count_2=false`). Counter-view still answers 200 for the assigned counter with `counting.status`. Submitting a count on a finalized/cancelled counting returns **422 `{error:{code:'COUNTING_TRANSITION_REFUSED', message, counting_id, current_status, attempted_status}}`** (since 2026-08-23); the `message` is server-localised (Accept-Language) — never string-match it.
- Fix: (a) session screen: if `status` is not one of the three in-progress values, hide the scan CTA and row taps and show a terminal banner (`pending_review` → "Comptage transmis pour vérification", `finalized` → "Comptage finalisé", `cancelled` → "Comptage annulé", other → generic); (b) `useSubmitCount` + `pendingCountSyncService`: on a 422 whose `error.code === 'COUNTING_TRANSITION_REFUSED'`, park **all** pending rows of that `countingId` with a "counting closed" reason (one server round-trip, not one per row); (c) `sync-errors.tsx`: add "Supprimer tout pour ce comptage" grouped by countingId; (d) `taskView.ts`: treat `pending_review` as a distinct "en vérification" bucket on the home screen (optional, P2) — do not put it in `isPendingTask`.
- Tests: `pendingCountSyncService.test.ts` (typed 422 → whole-counting park), `countingSessionScreenLiveInventory.test.tsx` (terminal banner), `syncErrorsScreen.test.tsx` (bulk discard).

### M-5 · P1 · error-envelope parsing misses two server shapes
- Mobile: `src/lib/api.ts:66-82` (`getErrorMessage` reads `response.data.error.message`, then `response.data.message`); `app/(app)/counting/draft/[id]/index.tsx:46-48` (`errorMessage()` shows the raw axios text "Request failed with status code 422").
- Server truth (verified): the draft-lifecycle endpoints use a **bare string** — `add-product` 409 `{"error":"Product already added to this count"}`, 404 `{"error":"Product not found with barcode: X"}`, 422 `{"error":"Can only add products to draft counts"}`; `activate-draft` 422 `{"error":"At least one product must be added before activation"}` / `"Primary counter must be assigned before activation"` / (N-1) `"A location must be selected before activation"`; `update-draft` 422/403 same shape. Validation failures use `{error:{code:'VALIDATION_ERROR', message, errors:{field:[msg]}}}`. `abort(403)` on counter routes renders `{error:{code:'FORBIDDEN', message, ability:null}}` (custom message discarded). Lookup miss is `404 {found:false, message}`.
- Fix: `getErrorMessage` handles `typeof body.error === 'string'`, and when `body.error.errors` is an object appends the first field message; draft detail uses `getErrorMessage`. Tests in `src/lib/__tests__/api.test.ts:70-90`.

## 2. Contract facts verified live on 2026-09-02 (use these as fixtures)
- Auth: `POST /auth/login {email,password}` → `{data:{token, tokenType, deviceId, user}}`; `GET /user/companies` → `{data:[{id, name, is_primary, currency, locale, timezone, …}]}`; every request carries `X-Company-Id`.
- `GET /inventory/countings/my-tasks` → `{data:[{id, status, my_count_number, instructions, deadline, progress:{count_1:{counted,total,percentage}, count_2|null, count_3|null, overall}}]}` — in-progress statuses only.
- `GET /inventory/countings/{id}/counter-view` → `{data:{counting:{id,status,instructions,deadline,block_sales,ambiguity_window_minutes,includes_zero_stock}, my_count_number, items:[{id, product:{id,name,sku,barcode}, location:{id,code,name}, is_counted, my_count, my_count_at}], progress:{counted,total}}}` (no `percentage`, no scope fields, never a theoretical quantity).
- `GET /inventory/countings/{id}/lookup?barcode=` → 200 `{found:true, data:{id, product:{id,name,sku,barcode}, location:{id,code}, is_counted, my_count}}` or 404 `{found:false, message}`.
- `POST /inventory/countings/{id}/items/{item}/count` body `{quantity:"6", notes?, counted_at_device?, device_now?}` (ISO-8601 with `Z` or offset) → 200 `{message, data:{item_id, quantity:<echo of the raw input>, count_number}}`. After N-1: `quantity` must match `^-?\d+(\.\d{1,4})?$` else 422 VALIDATION_ERROR.
- Draft path: `POST /inventory/countings/drafts` (requires role manager/admin on top of `inventory.adjust`) → 201 `{data:{id, counting_number, status:'draft', scope_type, scope_filters, …}}` (no `title`); `POST …/add-product {barcode|product_id}` → 201 `{data:{product_id, product:{id,name,sku,barcode}, added_at}}`; `POST …/add-products/batch {products:[{barcode|productId}]}` → 200 `{data:{success:[{productId,status}], errors:[{data, code:'PRODUCT_ALREADY_IN_COUNT'|'PRODUCT_NOT_FOUND'|'INVALID_BARCODE', error}], total_products}}`; `GET …/my-drafts` → `{data:[{id, uuid, title, status, scope_type, product_count, created_at, last_modified_at}]}`; `PATCH …/draft {count_1_user_id, requires_count_2, execution_mode, …}` → 200 `{data:{…}}`; `POST …/activate-draft {activate_immediately:true}` → 200 `{data:{status:'count_1_in_progress', …}}`.
- Batch endpoints are camelCase (`localId, scopeType, requiresCount2, count1UserId, scopeFilters`) with a snake_case `scopeFilters` value — unchanged; keep it.
- Sales-block semantics: only `POST /inventory/countings` (the web wizard) can set `block_sales` / `ambiguity_window_minutes`; mobile drafts always get `block_sales=false`, window 15. The block is enforced on the POS device via the terminal payload (`GET /pos/terminals/{id}` → `active_counting_block:{counting_id, counting_number, started_at}|null`, `counting_zone_advisories:[{zone_name, counting_number}]`), from `count_1_in_progress` through `pending_review` inclusive; the server never refuses a sale, it flags late sales on the counting. The mobile's only surface for the mode is the counter-view banner (`block_sales` true → "Ventes suspendues", false → "Comptage en direct ±N min"), which is correct today.
- Receiving: `GET /purchase-orders?status=confirmed`, `GET /purchase-orders/{id}` (lines now DO carry `quantity_received`), `GET …/receipt-status` (now also `free_quantity_ordered/received/remaining` per line — additive), `POST …/receive {quantities:{lineId:"1"}, batches?:{lineId:{batch_number, expiry_date, manufacturing_date?}}}` → 200 with `meta.receipt_status` (verified: mobile's `meta ?? root ?? data` lookup works). New server-side `ReceiveGoodsRequest` (2026-09-01) enforces scale-4 strings on `quantities.*` — the mobile already sends digit strings.
- Expenses, dashboard, placements, onboarding-worklist, nodes: all 200 with the shapes the mobile expects (probed).
