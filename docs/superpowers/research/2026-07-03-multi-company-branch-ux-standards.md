# Multi-Company / Multi-Location Management — Industry Standards Research

> Research date: 2026-07-03. Scope: how mature ERP/POS products model and expose company (legal entity) vs branch/location (operational unit) — entity model, switcher UX, settings scoping, branch editing surface, country-aware defaults, per-branch tax identity. Sources: vendor docs + reputable partner writeups, cited per section.

---

## 1. Odoo (v17+ branches feature)

**Entity model.** One `res.company` model serves both roles. A "branch" is a company record with a **Parent Company** set; hierarchy can be multi-level. Branches **inherit and share the parent's chart of accounts, taxes, and fiscal positions** — they are NOT separate books. A full sibling company (no parent, or a different localization) gets its own CoA/taxes. Warning in docs: a parent cannot later be converted into a branch (access-rights corruption). Branch records carry the full company field set: name, address, **Tax ID + Company ID (registry number)**, currency, phone/mobile/email, website, email domain, **logo and color scheme** — so a branch can present its own identity on documents while sharing the parent's fiscal configuration.
**Switcher UX.** Single top-bar company selector with **checkboxes (multi-select) + one "active" company**. Selecting a parent auto-links (checks) all its branches; selecting a branch scopes to that branch only. Active company is what new records get stamped with (`company_id` auto-filled and shown in a Company field on quotations/invoices/bills); checked companies define the visibility set for lists. Switching is a scoped-query refresh, not a session change.
**Settings scoping.** The Settings app is company-scoped: when multi-company is on, a company dropdown appears at the top of Settings ("settings apply to company X"). Records that can differ per company (e.g., product sales price in some configs) rely on `company_dependent` fields — same record, per-company value.
**Where edited.** Settings → Users & Companies → Companies → list + detail form; branch creation = new company with Parent Company set, and the parent form shows a **Branches tab**.
**Country defaults.** **Fiscal localization packages** (`l10n_*`): country-specific modules auto-installed from the company's country at database/company creation — pre-configured taxes, fiscal positions, CoA, legal statements, e-invoicing certificates. Package can be swapped only until the first journal entry is posted (Accounting → Configuration → Settings → Fiscal Localization).
**Per-branch tax identity.** Yes — branch has its own Tax ID field while sharing the parent CoA; documents issued from a branch carry the branch's header/identity.
Sources: [Odoo 18 Companies doc](https://www.odoo.com/documentation/18.0/applications/general/companies.html), [Fiscal localizations doc](https://www.odoo.com/documentation/18.0/applications/finance/fiscal_localizations.html), [Technaureus Odoo 17 branch concept](https://www.technaureus.com/blog-detail/odoo-17-branch-concept-multi-company-management), [ERPixel branch management](https://erpixel.com/odoo-branch-management/).

## 2. ERPNext (Frappe)

**Entity model.** `Company` is the legal entity: own abbreviation, tax ID, default currency, country, own CoA (validated against parent when in a **company tree** — parallel/parent-child structures allowed for consolidation). Below Company, "branch" is NOT one entity — it is decomposed: **Warehouse** (stock), **Cost Center** (P&L dimension, tree-structured), **Branch** (a thin HR master used mainly for employee assignment), and **Address** records linked to the company. All company-scoped masters (accounts, cost centers, warehouses, tax templates) are suffixed with the company abbreviation.
**Switcher UX.** No persistent switcher — every document has a `company` field (defaulting from user defaults/session defaults); list views filter by it. Multi-company is a per-document dimension, not a UI mode.
**Settings scoping.** Company-level settings live on the Company doctype itself (default accounts, default cost center, round-off account, etc.). Branch-level behavior is achieved by defaults on Warehouse/Cost Center/POS Profile (the **POS Profile** is effectively ERPNext's "location settings" object for retail: per-store warehouse, cost center, payment methods, print format).
**Where edited.** Masters each have their own list+form (Company, Warehouse, Cost Center, Branch, Address); no unified "Locations" page.
**Country defaults.** At company creation the setup wizard asks for country and installs a **country-specific CoA template**; regional apps (e.g., India Compliance) add fields like GSTIN, GST categories, e-invoicing.
**Per-branch tax identity.** Yes, via **addresses**: "update your company's branch wise Address with appropriate GSTIN" — each branch address carries its own GSTIN; on an invoice the user picks the company branch address, and Tax Categories (with a Source State) + per-category Sales/Purchase Tax Templates auto-select intra-state vs inter-state GST. Tax identity is address-borne, not company-borne, for branches.
Sources: [ERPNext Company setup](https://docs.frappe.io/erpnext/company-setup), [GST for multiple branches](https://docs.frappe.io/erpnext/user/manual/en/gst-for-multiple-branches), [Cost Center](https://docs.erpnext.com/docs/v13/user/manual/en/accounts/cost-center).

## 3. SAP Business One (Multiple Branches)

**Entity model.** One company database = one legal entity's books; **branches are units within the DB** (Administration → System Initialization → Company Details → Basic Initialization → "Enable Multiple Branches" — **irreversible**). Precondition: inventory managed by warehouse; each warehouse is assigned to a branch. Branch record (Administration → Setup → Financials → Branches): mandatory **Branch Name, Default Warehouse, Default Resource Warehouse, Country**; plus address and a **tax registration number per branch** — on activation with existing transactions a "Branch Registration Number" window forces entering the main branch's registration number (immutable afterwards). Users and business partners can be shared across or assigned to specific branches.
**Switcher UX.** No global mode switch — users are *authorized* to branches; every marketing document gets a branch (derived from the user's default/authorized branch and the warehouse); reports filter by branch. UI = branch field on documents + branch-filtered reporting.
**Settings scoping.** Company Details stays company-wide (one CoA, one posting system); branch differences are captured on the branch record (registration number, default warehouses) and via per-branch G/L determination.
**Country defaults.** Localization is chosen at company-database creation (localization pack determines CoA templates, tax system, statutory fields); cannot be changed later.
**Per-branch tax identity.** Yes — explicit per-branch registration number, designed for jurisdictions where each establishment has a filing number.
Sources: [SAP Help — Enabling Multiple Branches](https://help.sap.com/docs/SAP_BUSINESS_ONE/68a2e87fb29941b5bf959a184d9c6727/fc161d0bfa894ad4a0670dd7df8205af.html), [SAP B1 tips — activation walkthrough](https://www.sap-business-one-tips.com/en/activated-the-multiple-branches/), [Vina System — Multiple Branches](https://www.vinasystem.com/en/blogs/customers/multiple-branches-in-sap-business-one), [SAP B1 Multi-Branch ebook](https://help.sap.com/doc/download_multimedia_ebooks_businessone91_multiplebranches_story_html/9.1/en-US/story_content/external_files/B1_91_Multi_Branch.pdf).

## 4. Microsoft Dynamics 365 Business Central

**Entity model.** **Company = fully separate books** (own Company Information: name, address, VAT registration no., bank details, logo). Below a company, two orthogonal units: **Location** (physical inventory: warehouses, plants, showrooms, service vehicles; stockkeeping units = item@location with per-location replenishment/addresses/posting info) and **Responsibility Center** (administrative unit: sales office, purchasing dept — carries its own **address and contact info that override the document header**: "When you enter a responsibility center code on a document, it affects the address, dimensions, and prices on the document").
**Switcher UX.** **Company switcher pane** in the app bar (top-right, near search) listing all companies across environments, open-in-same-or-new-tab. Plus the **Company Badge**: a configurable colored badge with short text pinned to the top-right of every page identifying the current company (round = production, square = sandbox). Switching company is a full context change (different books). Responsibility centers are not "switched" — users get default RC filters in User Setup (separate Sales/Purchase/Service RC filters) and see only documents of their center.
**Settings scoping.** Per-company: Company Information page. Per-RC: the RC card (address/contacts). Per-location: the Location card (address, warehouse policies, bins). Inheritance: document RC defaults from user → customer/vendor → Company Information's default RC.
**Where edited.** Dedicated list+card pages ("Locations", "Responsibility Centers"), found via Tell Me search; Company Information under settings.
**Country defaults.** BC ships **country localization apps** per market (base application + localization layer: local VAT statements, tax fields like SIRET/Intrastat, local formats); a company's localization is fixed by the environment's country.
**Per-branch tax identity.** Not really — VAT registration lives on Company Information (one per company). Multi-establishment tax identity requires separate companies or ISV extensions.
Sources: [Responsibility centers](https://learn.microsoft.com/en-us/dynamics365/business-central/inventory-responsibility-centers), [Switching company/environment](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-organization-switch), [Company Information](https://learn.microsoft.com/en-us/dynamics365/business-central/admin-company-information), [Company badge](https://yzhums.com/29665/).

## 5. NetSuite OneWorld

**Entity model.** **Subsidiary = legal entity**, arranged in a strict tree rolling up to a root subsidiary (max 250; elimination subsidiaries extra). Each subsidiary: own base currency, country (drives edition + first **nexus** = tax jurisdiction, auto-assigned from the subsidiary address country; multiple nexuses per subsidiary e.g. US states), own tax registrations per nexus, own logo/forms branding. **Location** is a subsidiary-scoped record for physical sites — "Each subsidiary has one or more locations unique to that subsidiary, which enables you to administer location-based tax and regulatory requirements." Transactions carry both subsidiary and location.
**Switcher UX.** No free company switcher — **access is role-based**: each role has Subsidiary Restrictions (All / Selected); users switch context by switching roles. Session-level narrowing via Home → Set Preferences → Restrict View, or the **Subsidiary Navigator** dashboard portlet (click a node in the subsidiary tree → all portlets re-scope for the session; resets next login).
**Settings scoping.** Subsidiary record holds entity-level settings; a **Subsidiary Settings Manager** centralizes per-subsidiary preferences. Accounting books/preferences can vary per subsidiary; shared masters (items, customers) are tagged with the subsidiaries they're available to.
**Where edited.** Setup → Company → Subsidiaries (tree list + record); Setup → Company → Locations.
**Country defaults.** Subsidiary country determines edition behavior and auto-creates the first nexus; tax schedules/codes are generated per nexus (Advanced Taxes, mandatory in OneWorld).
**Per-branch tax identity.** Per-subsidiary and per-nexus tax registration; locations support "location-based tax and regulatory requirements" but a location is not itself a filing entity.
Sources: [OneWorld Overview](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N266701.html), [Subsidiaries in OneWorld](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N268563.html), [Nexuses and Taxes in OneWorld](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N269581.html), [Restricting role access to subsidiaries](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/bridgehead_N286421.html), [Subsidiary Navigator](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/bridgehead_3808545097.html).

## 6. QuickBooks Online (Locations/Classes)

**Entity model.** One QBO company file = one legal entity (multiple entities = multiple subscriptions). Within a file: **Location** = whole-transaction dimension (one per transaction — stores/offices/regions); **Class** = line-level dimension (product lines/departments). Plus/Advanced only (Plus caps 40 classes+locations combined).
**Switcher UX.** None — location is a field on each transaction; reports (P&L by Location) do the segmentation. Multi-entity users switch company files entirely.
**Settings scoping / inheritance — the notable pattern.** Sales forms default to the company-level name/address, but a Location record has **opt-in override checkboxes**: "This location has a different title for sales forms", "…a different company name", "…a different address where customers contact me or send payments", "…a different email/phone". Unchecked = inherit from company; checked = reveal the per-location field. This is the cleanest inherit-with-override UX in the group.
**Where edited.** Settings → Advanced → Categories → Track locations (enable); Settings → All Lists → Locations (list + new/edit dialog).
**Country defaults.** Regional QBO editions (tax module = VAT/GST/sales tax per country); no per-location tax identity.
**Per-branch tax identity.** No — single tax registration per company file.
Sources: [Set up and use location tracking](https://quickbooks.intuit.com/learn-support/en-us/help-article/track-location/set-use-location-tracking/L2raFkEBC_US_en_US), [Customise sales forms by location](https://quickbooks.intuit.com/learn-support/en-global/help-article/customise-forms/customise-sales-forms-location/L4qhdiNE2_ROW_en), [Class vs location tracking](https://paygration.com/class-and-location-tracking-in-quickbooks-online-explained/).

## 7. Lightspeed Retail & Square POS (multi-location retail)

**Lightspeed (R-Series).** One account = one business; **Settings → Locations** list + form. Per-location fields: name, description, **address/phone/email/website — all printed on that location's receipts**, operating hours, and a per-location sales tax (each location's tax must be set explicitly — "a drawer per location in a filing cabinet"). Catalog and customers are shared; inventory quantities, taxes, and (optionally) prices are per-location. Registers belong to a location; sales can start at one location and complete at another. Location count is a plan/billing limit.
**Square.** Account & Settings → My business → **Locations** (limit 300). Per-location: **business name (appears on card statements + digital receipts)** vs internal **nickname**, description, address, timezone, business hours, contact email/phone/socials, **logo + brand color**, receipt language, and **its own bank account for transfers**. Devices bind to a location via device codes; POS app switches location via ☰ More → Switch location (blocked when signed in with a device code — i.e., a register is pinned to its location). Dashboard reports filter by location; team permissions gate location creation. Receipt option "Show location" toggles the location name on receipts.
**Country defaults / tax identity.** Both are account-country based (tax engine per country); no per-location tax registration — location identity is presentational (receipt header, bank account) not fiscal.
Sources: [Lightspeed — Adding locations](https://retail-support.lightspeedhq.com/hc/en-us/articles/360034072574-Adding-locations), [Lightspeed — Taxes in multi-location accounts](https://retail-support.lightspeedhq.com/hc/en-us/articles/360033998214-Setting-taxes-in-multi-location-accounts), [Square — Manage multiple locations](https://squareup.com/help/us/en/article/5580-manage-multiple-locations-with-square), [Square — Customize receipts](https://squareup.com/help/us/en/article/5424-customize-digital-receipts-and-invoices).

## Convergent industry patterns

1. **Two-tier model is universal; the split is books vs operations.** Company/subsidiary = own tax registration, own currency, own (or shared-template) chart of accounts, own fiscal calendar. Branch/location = operational scoping (inventory, documents, users, receipt identity) that **posts into the parent's books**. Nobody makes a branch keep separate books; when separate books are needed, every product says "make it another company."
2. **Branches still get an identity block.** Across Odoo, SAP B1, BC responsibility centers, Square, Lightspeed: the branch record carries name, address, phone/email, and (Odoo/Square) logo/brand color — because **the document/receipt header must come from the branch, not the company**. This is presentational identity, distinct from fiscal identity.
3. **Per-branch tax/establishment numbers exist in ERPs that serve establishment-registration jurisdictions.** Odoo (Tax ID on branch), SAP B1 (branch registration number, forced at activation), ERPNext (GSTIN per branch address), NetSuite (nexus/registration per jurisdiction). POS products (Square/Lightspeed/QBO) don't do fiscal identity per location at all. Sharing the CoA while differing on tax ID is the established pattern (Odoo branches, SAP B1 branches).
4. **Every transaction is stamped with its unit** (`company_id` + branch/location/RC code) at creation from context defaults; reporting = filter on the stamp. The stamp is user-editable on the document in ERPs, fixed by device in POS.
5. **Switcher: one selector for the books context, defaults (not a switcher) for the operational unit.** Odoo: single company/branch selector where picking a parent implies its branches. BC: company switcher pane + persistent **company badge**; responsibility center comes from user defaults, not a switcher. NetSuite: role-based access + session-scoped Subsidiary Navigator. POS: the device/register is pinned to a location; explicit "Switch location" is a deliberate, rare action. Persistent on-screen indication of current context (badge/selector label) is standard.
6. **Inheritance is opt-in override, blank = inherit.** QBO's checkboxes ("this location has a different X") are the most explicit; BC (document RC overrides header address only when set), Odoo (branch fields fall back to parent behavior for accounting config), Lightspeed/Square (receipt fields per location, account-level elsewhere) all follow inherit-unless-overridden.
7. **Country is chosen once, at entity creation, and seeds everything.** Odoo l10n packages (auto-installed from company country: taxes, CoA, fiscal positions, legal reports; swappable only before first posting), ERPNext wizard country → CoA template + regional app fields, NetSuite country → edition + first nexus, SAP B1/BC localization fixed at DB/environment creation. Country-specific labels/fields (SIRET, GSTIN, VAT no.) come from the localization layer, not from generic settings.
8. **Irreversibility warnings around structure changes** are common: SAP B1 multi-branch activation is irreversible; Odoo parent→branch conversion is forbidden; Odoo localization locked after first posting. Products protect the books' integrity by locking structural choices early.

## Recommendations — Laravel+React ERP (company → locations, sellable branches with own tax ID)

Context: Synerivia ERP already has tenant → company → branches/locations; sellable branches (e.g., Tunisian *établissements* with their own Matricule Fiscale suffix, French SIRET per establishment) need their own tax identity on receipts/invoices while posting into the company's books.

**1. Entity model.** Keep two tables, not a self-referencing tree: `companies` (legal: tax ID, currency, CoA, fiscal calendar, country) and `locations`/`branches` (operational, FK to company). On the location: name, address, phone/email, **`tax_id` (nullable = inherit company's)**, establishment/registry number, receipt header/footer text, logo override, default warehouse, optional bank account (Square precedent). Follow the industry line: a location never has its own CoA or fiscal year; "needs own books" = create a company. The location's tax ID must be part of the signed fiscal payload (aligns with the existing `project_branch_tax_id` decision: per-branch tax ID in signed SALE_RECEIPT bytes).

**2. Switcher design.** Two-level, one control: a single header selector showing `Company · Location` (BC-style badge with company color/short code), opening a **hierarchical picker** — companies as group headers, locations nested under them (Odoo pattern: picking the company = all-locations view for reporting; picking a location = scoped operational context). Persist selection per user (server-side, like BC user setup), stamp `company_id` + `location_id` on every created record from this context, and treat switch as a scoped-query refresh (invalidate React Query caches keyed by company/location), not a reload. POS devices/registers are pinned to a location (Square model); switching there is a settings action, not a header control. Most single-company tenants should see no switcher at all until a second company/location exists.

**3. Settings information architecture.** Split by ownership, not by feature: an **Organization** section with `Companies` (list → company detail: legal identity, fiscal/localization, CoA linkage) and inside each company a **Locations tab/list → location detail form** (SAP B1 / Lightspeed / Square all use a dedicated Locations list+form — do the same; do not scatter branch fields across settings pages). Any settings page whose values are company- or location-scoped must show an explicit scope banner/selector at the top: "Editing settings for **Pharmacie Bio — Lac 2**" (Odoo Settings company dropdown + BC badge precedent). Never let a user edit a scoped setting without the scope being visible on screen.

**4. Inheritance/override pattern.** Copy QBO's explicit opt-in overrides — it is the clearest UX in the field. On the location form, group inheritable fields ("Receipt identity", "Tax identity", "Contact") each with a toggle: *"This location has a different tax ID"* → reveals the field; off → show the inherited company value read-only with an "Inherited from {company}" hint. Storage: nullable columns, `NULL = inherit`; resolve with a single `LocationProfileResolver` (company value ⟵ overridden by location value) so receipts, invoices, and the fiscal payload all resolve through one path — never duplicate company values into location rows (stale-copy trap).

**5. Country-profile seeding.** Adopt the Odoo l10n architecture at data scale, not module scale: a `country_profiles` registry (config or seeded table) keyed by ISO country, providing — tax-ID **label + validation regex + placeholder** (`Matricule Fiscale — 0000000A/A/M/000` for TN, `SIRET — 14 digits` for FR establishments, `VAT Reg No` UK…), secondary establishment-number semantics (FR: SIREN on company / SIRET per location; TN: MF with establishment suffix), address field order/format, phone prefix, default currency, default tax rates/stamp duty, rounding/scale (ties into `CurrencyScaleResolver`), and receipt legal mentions. Apply it at **company creation** (seed taxes/labels, set currency/scale) and let locations inherit; re-resolve labels per location's own country only if you ever allow cross-border locations (NetSuite does; Odoo branches share the parent's fiscal country — recommend the latter: **location country = company country, enforced**). Lock the profile after first fiscal posting (Odoo/SAP precedent), and surface labels through i18n keys parameterized by country profile rather than hardcoded per-locale strings.

**6. Guardrails.** Make structural rules explicit and validated: a location cannot move between companies once it has fiscal documents; company country/currency immutable after first posting; deleting a location = soft-archive only. Show these as disabled-with-tooltip, not hidden.
