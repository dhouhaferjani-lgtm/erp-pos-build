# RBAC Wave 0b — new permissions for the remaining ungated writes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Declare the nineteen permission keys that do not exist yet, gate the twenty-five live write routes and sixteen read routes that need them, and ship the three pieces of machinery those keys cannot reach a live tenant without — `PermissionWriteLock` (adopting `lane/w-lot-a-1a`'s advisory key and row order), `TenantFleetRunner` (the one fleet iterator) and `permissions:ensure` / `permissions:ensure-fleet`. Plus the five items wave 0a had to defer for file-overlap reasons, the **four Identity read-route gates and their page guards** relocated here by plan gate r1 (task **0b-15**), and the CI `env:` line that switches on wave 0a's anti-growth direction.

**Architecture:** Wave 0b still writes the catalogue through `RolesAndPermissionsSeeder`'s two arrays — the registry is wave 1 — but it stops *deploying* through `tenants:seed`, because after `lane/w-lot-a-1a` merges that seeder writes **nothing at all** on a marked tenant with `LOT_ACTION_PERMISSIONS_ENFORCE=false` (its shipped default). The wave therefore ships a small additive command, `permissions:ensure`, whose per-tenant routine runs on the shared `TenantFleetRunner`, whose grants are equality-guarded by `LegacyRoleBaseline::matchesPreWave0b()`, and whose whole run sits inside one transaction holding the **same** per-tenant advisory lock the incoming lane's `LotActionPermissionDelta` already takes. Every other runtime role-grant writer is wired into that lock in the same commit, because an equality check that is not serialized against the operator edit path is not a guard.

## Global Constraints

- [ ] **Entry condition is a merge, not a hope.** `lane/w-lot-a-1a` must be an ancestor of local `dev` before Task 1 starts. The exact check is in Phase 0 and is `git merge-base --is-ancestor`, not a `branch --merged` grep — a grep matches a substring and a deleted-then-recreated branch name.
- [ ] **Middleware set (CLAUDE.md rule 12):** every module `routes.php` group keeps `['api', 'auth:sanctum', SetPermissionsTeam::class, EnforceTokenTenantClaim::class]` plus whatever `module:<Name>` gate it already carries. This wave **adds** `can:` to existing routes; it never rewrites, reorders or removes an existing middleware.
- [ ] **`can:` only.** The action gate is `can:` (or `require.any.permission:` for an any-of). Never `permission:` — that alias has never existed in this repository. Never a controller check or a FormRequest `authorize()` as the *only* gate (spec §4.4.1 E-2/E-4).
- [ ] **A flag-conditional middleware is not a gate.** `BatchActionAccess` returns `$next($request)` with no check at all while `LOT_ACTION_PERMISSIONS_ENFORCE` is false (`lane/w-lot-a-1a:apps/api/app/Modules/BatchExpiry/Presentation/Middleware/BatchActionAccess.php:18-20`, default `false` at `lane/w-lot-a-1a:apps/api/config/lot_action_permissions.php:5`). 0b-5 adds a real `can:` **beside** it, never instead of it.
- [ ] **Nineteen keys, and not a twentieth.** The key list is fixed by §8 and by `LegacyRoleBaseline`'s v0 arithmetic (§4.3.0a rule 1: `admin` gets all 19, `manager` and `general_manager` get **seven**, every other 0b key is `admin`-only). Adding a key means editing `wave0bAdditions`, the deploy `--keys` list and `Wave0bAdditionConstantTest` in the same commit — see **Q-0b-2**.
- [ ] **The lock key is `lane/w-lot-a-1a`'s, adopted verbatim: `'wlota1a:'.$tenantId`, hashed with `hashtextextended(?, 0)`** (`lane/w-lot-a-1a:apps/api/app/Modules/Identity/Application/Services/LotActionPermissionDelta.php:131-136`). Row order is **`roles.name` ASC, then `roles.id` ASC** (`lane/w-lot-a-1a:…/LotActionPermissionDelta.php:111-116`). Two advisory namespaces are two serialization domains, i.e. no serialization at all; two row orders are a deadlock. Never invent a second key or a second order.
- [ ] **NULL-team tolerance everywhere.** Every role lookup in this wave resolves `guard_name = 'sanctum' AND name IN (…) AND (tenant_id IS NULL OR tenant_id = :tenantId)`, preserves `tenant_id` **as found**, orders by `name` then `id`, and takes `lockForUpdate()`. Two matching rows for one name is `ambiguous_legacy_role_collision`; an unmarked `general_manager` is `unmarked_general_manager_collision`. This is `LotActionPermissionDelta::resolveCatalogueRoles()` verbatim (`lane/w-lot-a-1a:…/LotActionPermissionDelta.php:111-129`). **No role is ever re-homed.**
- [ ] **Constructor injection only** (`private readonly`), never the `app()` helper in production code. **Strict types** (`declare(strict_types=1);` in every new PHP file), no `mixed`, no `any`. Enums for every status/type value this wave introduces.
- [ ] **PHPUnit by path only.** The full backend suite is never run locally (laptop rule). Every command in this plan names a file or a directory.
- [ ] **PG lane env — this wave has real PostgreSQL legs.** Six of its tests are PG-only by construction (two-connection races, two real tenant databases, advisory locks). Use a **private per-session** database and override **both** variables:

### Q-0b-1 — the `permissions_ensure` status file has a named reader in the deploy checklist, **not** in `HealthCheckService`

Spec §4.3.3's table is explicit: the ensure status file *"is read by the **wave-0b deploy checklist**, not by `HealthCheckService`: that service's `permissions_sync` check ships in wave 1 with `permissions:sync-fleet`, and adding a second key for a command wave 1 deletes would be a health check with a one-wave lifetime."*

**This plan implements the spec:** `permissions:ensure-fleet` writes `/var/run/autoerp/permissions-ensure.status` on **both** arms, and the wave-0b deploy checklist row reads it. `HealthCheckService` is **not** touched in 0b.

**If the orchestrator wants the admin health reader in 0b** (so the ensure deploy is observable at `GET /api/v1/admin/monitoring/health` rather than only in a shell), the bounded edit is: add a fifth check `permissions_ensure` to the array at `apps/api/app/Modules/Admin/Application/Services/HealthCheckService.php:19-24` reading that file with the same three-state rule wave 1 will use for `permissions_sync` (absent ⇒ healthy, `=ok` ⇒ healthy, `=failed` ⇒ unhealthy with an `error` string), plus one test; and wave 1 must then **delete** that key in the same commit that deletes `EnsurePermissions`. It is ~30 lines in and ~30 lines out. **Ask before adding it.**

### Q-0b-2 — which three `services.*` keys, and what gates the two DELETE routes

Spec §8 pins **three** `services.*` and **three** `service-categories.*` keys (and §4.3.0a's v0 table pins **seven** manager additions in total), while §4.4.4 counts *"six routes"* for the pair and §4.5.4 item 1 says the FE alias file's keys *"become real permissions in wave 0b"*. The alias file declares exactly `services.view`, `services.create`, `services.edit` (`apps/web/src/hooks/uiAliasPermissions.ts:8-10`), and `MODULE_PERMISSIONS.services` is `['services.view']` (`apps/web/src/hooks/usePermissions.ts:80`) under a **fail-closed** contract — so a wave-0b catalogue without `services.view` makes the `/services` nav entry vanish for everyone the moment wave 2a deletes the fallback.

**This plan implements** `services.{view,create,update}` and `service-categories.{view,create,update}` — the alias map's three, with `edit` canonicalised to `update` per D5 — which keeps §4.5.4 item 1 true and keeps the seven-key arithmetic exact. **`DELETE /services/{service}` and `DELETE /service-categories/{category}` are gated on `can:services.update` / `can:service-categories.update`**, on the ground that retiring a service catalogue row is the same authority as editing it, and that a fourth key would change three counts the spec pins in three different places.

**If the owner rules that deletion is its own authority**, the bounded edit is: add `services.delete` and `service-categories.delete` (21 keys total, **nine** manager additions), change those two route gates, and update `LegacyRoleBaseline::wave0bAdditions()`, the deploy `--keys` list and `Wave0bAdditionConstantTest` in the same commit. Nothing else moves.

### Q-0b-3 — the four `channels.*` verbs

Spec §8 pins **four** `channels.*` keys and names no verbs. The tenant-facing group has ten routes: four reads (`index`, `orders` all, `{id}/sync-operations`, `{id}/orders`) and six writes (`store`, `{id}/test-connection`, `{id}/resync`, `{channelId}/orders/{orderId}/promote`, `{channelId}/products/{productId}/publish`, `{channelId}/products/{productId}/unpublish`).

**This plan implements** `channels.view` (the four reads), `channels.create` (`store`), `channels.update` (`test-connection`, `resync` — configuration writes on an existing channel), `channels.operate` (`promote`, `publish`, `unpublish` — the day-to-day channel operations, and `Operate` is a case of the closed verb enum wave 1 introduces). If the orchestrator prefers `promote` under a fifth key (it converts a channel order into a sales order), that is one key and one route gate.

### Q-0b-4 — the 0b deploy is **two** invocations of `permissions:ensure-fleet`, not one

Spec §8's deploy row says *"one command over the whole fleet, with the 0b key list and the template roles each key is declared for"*. The signature it specifies cannot express that: `--keys=*` and `--grant-to=*` are two flat lists, and the contract of `--grant-to` is *"role names that must hold **every** named key"*. Twelve of the nineteen keys are `admin`-only, so a single invocation carrying all nineteen with `--grant-to=manager` would grant a manager twelve keys the spec says are admin-only.

**This plan implements two invocations** of the same fleet command — one carrying the twelve admin-only keys with **no** `--grant-to`, one carrying the seven with `--grant-to=manager --grant-to=general_manager`. The seven land in **one** run, which is what `EnsurePermissionsCustomisationGuardTest::all_seven_additions_land_on_a_pristine_manager_in_one_run` requires (the eligibility snapshot is taken once per role, before any of that role's additions are written). The alternative — a per-key role map on the command line — is more machinery than a command wave 1 deletes deserves.

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Domain\Authorization;

/**
 * The catalogue's permission-key rename map (owner ruling D5, spec 4.9.2).
 *
 * APPEND-ONLY and SHRINK-NEVER: an entry is removed only once
 * `permissions:sync --dry-run` reports it stale on every tenant, which is why
 * the sync reports staleness at all.
 *
 * Two invariants make the single-pass canonicalisation below a fixed point,
 * and both are asserted by PermissionRenameMapTest:
 *   - the map is acyclic;
 *   - the TARGET set and the SOURCE set are DISJOINT. Acyclicity alone is not
 *     enough: an acyclic map may still contain the chain a->b, b->c, under
 *     which one pass gives {b} and two passes give {c}, so the comparison's
 *     answer would depend on how many times it had been normalised.
 *
 * A rename is applied IN PLACE by the wave-1 sync (UPDATE permissions SET name),
 * so no grant pivot is ever rewritten. This class only names the pairs.
 */
final readonly class PermissionRenameMap
{
    /**
     * @return list<array{from: non-empty-string, to: non-empty-string, introducedIn: non-empty-string}>
     */
    public function entries(): array
    {
        return [
            // snake_case resource -> kebab-case resource (D5)
            ['from' => 'catalog_cart.view', 'to' => 'catalog-cart.view', 'introducedIn' => '2026.09'],
            ['from' => 'catalog_cart.create', 'to' => 'catalog-cart.create', 'introducedIn' => '2026.09'],
            ['from' => 'catalog_cart.convert_po', 'to' => 'catalog-cart.convert_po', 'introducedIn' => '2026.09'],
            ['from' => 'catalog_cart.convert_so', 'to' => 'catalog-cart.convert_so', 'introducedIn' => '2026.09'],
            ['from' => 'catalog_cart.marketplace_checkout', 'to' => 'catalog-cart.marketplace_checkout', 'introducedIn' => '2026.09'],
            ['from' => 'catalog_cart.manage_all', 'to' => 'catalog-cart.manage_all', 'introducedIn' => '2026.09'],
            ['from' => 'pos_held_orders.view', 'to' => 'pos-held-orders.view', 'introducedIn' => '2026.09'],
            ['from' => 'pos_held_orders.create', 'to' => 'pos-held-orders.create', 'introducedIn' => '2026.09'],
            ['from' => 'pos_held_orders.delete', 'to' => 'pos-held-orders.delete', 'introducedIn' => '2026.09'],
            // edit -> update verb normalisation (D5)
            ['from' => 'uom.edit', 'to' => 'uom.update', 'introducedIn' => '2026.09'],
            ['from' => 'deliveries.edit', 'to' => 'deliveries.update', 'introducedIn' => '2026.09'],
        ];
    }

    /** @return array<non-empty-string, non-empty-string> */
    public function map(): array
    {
        $map = [];
        foreach ($this->entries() as $entry) {
            $map[$entry['from']] = $entry['to'];
        }

        return $map;
    }

    /** @return list<non-empty-string> */
    public function sources(): array
    {
        return array_values(array_keys($this->map()));
    }

    /** @return list<non-empty-string> */
    public function targets(): array
    {
        return array_values($this->map());
    }

    public function to(string $key): ?string
    {
        return $this->map()[$key] ?? null;
    }

    /**
     * canonical(S) = { renameMap.to(k) ?? k : k in S }, applied in EXACTLY ONE
     * pass, deduplicated and sorted so the result is comparable as a set with
     * assertSame(). Total, order-free and — under the disjointness invariant
     * above — idempotent.
     *
     * @param  list<string>  $keys
     * @return list<string>
     */
    public function canonicalise(array $keys): array
    {
        $map = $this->map();
        $canonical = [];
        foreach ($keys as $key) {
            $canonical[$map[$key] ?? $key] = true;
        }
        $canonical = array_keys($canonical);
        sort($canonical);

        return $canonical;
    }
}
~~~

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Domain\Authorization;

use RuntimeException;

/**
 * The frozen version-0 baseline of the eight seeded role templates, and the TWO
 * equality oracles built on it. Ships in wave 0b (spec 4.3.5's rev-6 B-1
 * ruling); wave 1's adoption pass INHERITS it rather than introducing it.
 *
 * The two predicates measure the role at two DIFFERENT MOMENTS and must never
 * collapse into one:
 *
 *   matchesPreWave0b(k, S)  <=>  canonical(S) == canonical(postA1aGrants(k))
 *       "the role is still exactly what lane/w-lot-a-1a left it" — the ONLY
 *       oracle `permissions:ensure` may use, because it runs BEFORE the 0b
 *       additions are granted.
 *
 *   matchesVersion0(k, S)   <=>  canonical(S) == canonical(version0(k))
 *       version0 = postA1aGrants ∪ wave0bAdditions — the ONLY oracle wave-1
 *       adoption may use, because it runs AFTER them.
 *
 * Using matchesVersion0() inside `ensure` is unsatisfiable by construction: on a
 * pristine post-A-1a manager, current = P while version0 = P ∪ A, so the very
 * first wave-0b grant would be unreachable. LegacyRoleBaselinePredicateTest
 * pins that the pair does not collapse.
 *
 * Both normalise through PermissionRenameMap on BOTH sides, so neither the
 * mandatory wave-1 rename nor a legitimate 0b grant can make a pristine role
 * compare unequal.
 */
final readonly class LegacyRoleBaseline
{
    private const FIXTURE = 'tests/Fixtures/Identity/legacy-role-baseline-v0.json';

    /**
     * The EXACT `--grant-to` argument list wave 0b deploys, per template key.
     * A committed constant, not a computation: every element is known at the
     * moment 0b ships, which is what makes `version0 = postA1a ∪ additions`
     * safe. Wave0bAdditionConstantTest asserts it equals the deploy arguments.
     *
     * Twelve of the nineteen 0b keys are admin-only and therefore appear here
     * for NO template — `admin` is granted unconditionally by
     * EnsurePermissionsRunner and is re-derived to activeKeys() by wave 1's
     * sync step 8, so its row is never the deciding input.
     */
    public const WAVE_0B_ADDITIONS = [
        'manager' => [
            'credit-notes.cancel',
            'services.view',
            'services.create',
            'services.update',
            'service-categories.view',
            'service-categories.create',
            'service-categories.update',
        ],
        'general_manager' => [
            'credit-notes.cancel',
            'services.view',
            'services.create',
            'services.update',
            'service-categories.view',
            'service-categories.create',
            'service-categories.update',
        ],
    ];

    public function __construct(private PermissionRenameMap $renameMap) {}

    /**
     * The post-A-1a grant map, read from the committed fixture.
     *
     * @return array<string, list<string>>
     */
    public static function postA1aGrants(): array
    {
        $path = base_path(self::FIXTURE);
        if (! is_file($path)) {
            throw new RuntimeException('legacy role baseline fixture is missing: '.$path);
        }

        /** @var array<string, list<string>> $decoded */
        $decoded = json_decode((string) file_get_contents($path), true, 512, JSON_THROW_ON_ERROR);

        return $decoded;
    }

    /** @return list<string> */
    public static function wave0bAdditions(string $templateKey): array
    {
        return self::WAVE_0B_ADDITIONS[$templateKey] ?? [];
    }

    /**
     * version0(k) = postA1aGrants(k) ∪ wave0bAdditions(k), in the RAW
     * post-A-1a spelling. Normalisation happens on read, in the predicates.
     *
     * @return list<string>
     */
    public static function version0(string $templateKey): array
    {
        $base = self::postA1aGrants()[$templateKey] ?? [];

        return array_values(array_unique([...$base, ...self::wave0bAdditions($templateKey)]));
    }

    /** @param list<string> $currentKeys */
    public function matchesPreWave0b(string $templateKey, array $currentKeys): bool
    {
        $baseline = self::postA1aGrants()[$templateKey] ?? null;
        if ($baseline === null) {
            return false;
        }

        return $this->renameMap->canonicalise($currentKeys) === $this->renameMap->canonicalise($baseline);
    }

    /** @param list<string> $currentKeys */
    public function matchesVersion0(string $templateKey, array $currentKeys): bool
    {
        if (! array_key_exists($templateKey, self::postA1aGrants())) {
            return false;
        }

        return $this->renameMap->canonicalise($currentKeys) === $this->renameMap->canonicalise(self::version0($templateKey));
    }
}
~~~

## Task 2 (0b-9b): `PermissionWriteLock`

**What it is, and what it is not.** One transaction-scoped PostgreSQL advisory lock per tenant, serialising every writer of a `role_has_permissions` or `model_has_roles` row. It is **not** a table lock — ordinary reads are never blocked — and `pg_advisory_xact_lock` releases on commit **or rollback**, which is what makes a failed run safe to retry.

**The key is adopted, not invented.** `lane/w-lot-a-1a` already ships a role-grant writer that locks `'wlota1a:'.$tenantId` hashed with `hashtextextended(?, 0)` (`lane/w-lot-a-1a:apps/api/app/Modules/Identity/Application/Services/LotActionPermissionDelta.php:131-136`) and locks its roles by `name` then `id` (`:111-116`). A second namespace would be a second serialization domain — i.e. **no** serialization between the two writers — and for `manager` versus `general_manager` the `name` and `id` orders can be opposite, which is a deadlock rather than a race. The lane lands first, so this design **adopts**. The key string keeps the lane's name even after wave 3 retires the delta as dead code: an advisory key is an opaque token whose only property is that every writer computes the same one.

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Infrastructure\Locks;

use Illuminate\Support\Facades\DB;
use LogicException;

/**
 * Serialises every role-grant writer for ONE tenant, for the life of the
 * CURRENT transaction.
 *
 * The key and the hash function are lane/w-lot-a-1a's, adopted VERBATIM so that
 * LotActionPermissionDelta::apply() and every writer wired in wave 0b share ONE
 * serialization domain (see that class's acquireTenantLock()). Two advisory
 * namespaces would be two domains, i.e. no serialization at all.
 *
 * Companion obligations, on the CALLER (spec 4.3.2's five obligations):
 *   (i)   open a transaction;
 *   (ii)  call acquire() as its FIRST statement;
 *   (iii) SELECT ... FOR UPDATE the affected roles rows ordered by
 *         roles.name ASC, then roles.id ASC — the lane's order, because a
 *         deterministic order is only a deadlock cure when every participant
 *         uses the SAME one;
 *   (iv)  RE-READ the decision inputs (grant set, and from wave 1 customised_at)
 *         AFTER the lock is held, and decide from that read;
 *   (v)   write and commit.
 *
 * The ONE stated exception is RoleController::store, which creates a row that
 * does not yet exist: advisory lock -> INSERT -> initial grants, in one
 * transaction, with no FOR UPDATE and no prior grant set to re-read. A
 * post-insert FOR UPDATE on a row the same transaction just created adds no
 * serialization beyond the advisory lock it already holds, so it is not
 * required and must not be added as ritual.
 *
 * PostgreSQL: SELECT pg_advisory_xact_lock(hashtextextended(<key>, 0))
 * SQLite:     no-op (the fast lane is single-connection; the serialization
 *             property is asserted on the PG lane only — EC-20a/b/c).
 */
final readonly class PermissionWriteLock
{
    public static function key(string $tenantId): string
    {
        return 'wlota1a:'.$tenantId;
    }

    public function acquire(string $tenantId): void
    {
        if (DB::transactionLevel() === 0) {
            throw new LogicException(
                'PermissionWriteLock::acquire() must be called inside an open transaction — '
                .'a transaction-scoped advisory lock taken outside one is released immediately.',
            );
        }

        if (DB::getDriverName() !== 'pgsql') {
            return;
        }

        DB::select('SELECT pg_advisory_xact_lock(hashtextextended(?, 0))', [self::key($tenantId)]);
    }
}
~~~

## Task 3 (0b-9c, part 1): `TenantFleetRunner` — the one fleet iterator

**Why a class and not `tenants:run`.** Three defects rule `tenants:run` out (spec §4.3.3): child options must be forwarded as `--option=['k=v']` and a bare child flag errors; `tenants:run` **discards child exit statuses**; and the entrypoint additionally catches failures and keeps booting. A half-synced fleet would be logged as completed while the app started serving mixed authorization state. There is therefore **exactly one** runner, shared by `permissions:ensure-fleet` (this wave) and `permissions:sync-fleet` (wave 1), because the universe predicates, the failure semantics, the per-tenant marker shape and the exit contract are the parts a gate has to re-verify and they are written **once**.

**Gate r9 m-1 is applied here.** The start snapshot is `get(['id', 'slug'])`, **not** `pluck('id', 'slug')` — `pluck` collapses duplicate keys rather than preserving a match set, and it cannot represent a cross-column collision at all. `tenants.slug` **is** globally unique (`apps/api/database/migrations/2025_11_30_000001_create_tenants_table.php:19`), so the reachable ambiguity is a selector equal to tenant A's **UUID** and tenant B's **slug** — never two equal slugs, which the schema forbids.

- Create: `apps/api/app/Modules/Tenant/Domain/Enums/FleetOutcome.php`
- Create: `apps/api/app/Modules/Tenant/Application/DTOs/FleetTenantOutcome.php`
- Create: `apps/api/app/Modules/Tenant/Application/DTOs/FleetRunResult.php`

- The **command** — never the runner — renders the aggregate marker line and returns the process exit code.

**Contract, restated so a reviewer can check it against the code**

1. **One start read.** `$directoryAtStart = Tenant::query()->get(['id', 'slug'])`. This read is the run's clock; nothing later re-reads it except step 4.
2. **Selector resolution (step 1a).** Empty `$onlyTenants` ⇒ the whole snapshot. Otherwise each selector is matched against the snapshot on `id` (exact UUID) **or** `slug` (exact, case-sensitive) — one lookup, the **union** of matches, not a sequence with a fallback. Exactly one match contributes that tenant. Duplicates **collapse** (a tenant's id and its slug in one invocation yield one tenant, processed once, counted once). Zero matches ⇒ `FAILED`, `reason=tenant_selector_unmatched`, named by the **literal selector string**. More than one ⇒ `FAILED`, `reason=tenant_selector_ambiguous`, with the matched ids listed. Either failure counts in `failed=` and makes the run exit non-zero, and per-selector isolation matches per-tenant isolation — every selector that *did* resolve is still processed.
3. **Readiness, per tenant, at the moment of use.** (a) the database **physically exists** — the same check `TenancyResolver::initializeIfProvisioned()` performs (`apps/api/app/Modules/Tenant/Application/Services/TenancyResolver.php:90`); (b) after `tenancy()->initialize()`, the tenant's `migrations` table contains **every** file under `database/migrations/tenant`. A tenant failing either is **`FAILED` with `reason=tenant_not_ready`** (sub-reason `database_absent` or `migrations_behind`) and the run exits non-zero. It is *not* an informational skip: nothing observable to the runner distinguishes a tenant that is mid-provisioning from an established tenant whose rolling migration just failed, and the entrypoint makes the second case routine — `tenants:migrate-rolling --force` runs unconditionally and its failure is caught and logged (`apps/api/docker/entrypoint.sh:150-154`). A fleet run that cannot prove it synced a tenant must not report success for that tenant.
4. **Per-tenant failure isolation.** One tenant's `FAILED`/`BLOCKED` never stops the run.
5. **The closing population gauge.** `gauges.provisioned_during_run = |directory at end| \ |directory at start|`. It is a **pure population count** and asserts **nothing** about those tenants' catalogue state: the directory row is written *before* the database is created, migrated or initialised (`TenantProvisioningService`), so a row's appearance is equally consistent with a provisioning attempt that never reached its own sync. It exists so an operator reading the aggregate line can see the fleet grew mid-run.
6. **Exit rule.** Non-zero if any tenant or any selector is `BLOCKED` or `FAILED`.
7. **`--dry-run` is WRITE-free, not FAILURE-free.** It changes exactly one thing — what is written — and nothing else. Classification, per-tenant markers (`mode=DRY_RUN`), the aggregate line and the exit rule are identical to an applying run. That belongs to the **closure**, not the runner: the runner never writes anything itself.

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Tenant\Application\Services;

use App\Modules\Tenant\Application\DTOs\FleetRunResult;
use App\Modules\Tenant\Application\DTOs\FleetTenantOutcome;
use App\Modules\Tenant\Domain\Tenant;
use Closure;
use Illuminate\Support\Collection;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\File;
use Throwable;

/**
 * The ONE fleet iterator (spec 4.3.3, rev-8 gate r7 M-1).
 *
 * `tenants:run` cannot be one: it forces the --option=['k=v'] encoding on every
 * child flag, and it DISCARDS child exit statuses, so a half-applied fleet
 * would be reported as clean. This class calls the per-tenant closure DIRECTLY
 * and therefore holds the real result object.
 *
 * Shared verbatim by permissions:ensure-fleet (wave 0b) and
 * permissions:sync-fleet (wave 1). Only the closure, the marker prefix and the
 * status file differ.
 */
final readonly class TenantFleetRunner
{
    /**
     * @param  list<string>                          $onlyTenants ids or slugs; empty = every directory row
     * @param  Closure(Tenant): FleetTenantOutcome   $perTenant
     */
    public function run(array $onlyTenants, string $markerPrefix, Closure $perTenant): FleetRunResult
    {
        // 1. Read the directory ONCE. This read is the run's clock.
        /** @var Collection<int, Tenant> $directoryAtStart */
        $directoryAtStart = Tenant::query()->get(['id', 'slug']);
        $startIds = $directoryAtStart->pluck('id')->all();

        // 1a. Selector resolution against the START snapshot.
        [$selected, $selectorOutcomes] = $this->resolveSelectors($directoryAtStart, $onlyTenants);

        $outcomes = $selectorOutcomes;

        foreach ($selected as $tenantId) {
            /** @var Tenant|null $tenant */
            $tenant = Tenant::query()->find($tenantId);
            if ($tenant === null) {
                // The row vanished between the snapshot and now. Fail closed:
                // the run cannot prove it processed this tenant.
                $outcomes[] = FleetTenantOutcome::failed($tenantId, 'tenant_not_ready:directory_row_disappeared');

                continue;
            }

            $outcomes[] = $this->runOne($tenant, $perTenant);
        }

        // 4. Closing directory read — a pure population gauge.
        $endIds = Tenant::query()->pluck('id')->all();
        $provisionedDuringRun = count(array_diff($endIds, $startIds));

        return new FleetRunResult(array_values($outcomes), $provisionedDuringRun);
    }

    /**
     * @param  Collection<int, Tenant>  $snapshot
     * @param  list<string>             $onlyTenants
     * @return array{0: list<string>, 1: list<FleetTenantOutcome>}
     */
    private function resolveSelectors(Collection $snapshot, array $onlyTenants): array
    {
        if ($onlyTenants === []) {
            return [$snapshot->pluck('id')->all(), []];
        }

        $selected = [];
        $failures = [];

        foreach (array_values(array_unique($onlyTenants)) as $selector) {
            // A value is offered to BOTH columns and the UNION of matches is the
            // selector's match set — never a sequence with a fallback, which
            // would silently pick the id match and hide the collision.
            $matches = $snapshot
                ->filter(static fn (Tenant $t): bool => $t->getAttribute('id') === $selector || $t->getAttribute('slug') === $selector)
                ->pluck('id')
                ->unique()
                ->values()
                ->all();

            if ($matches === []) {
                $failures[] = FleetTenantOutcome::failed($selector, 'tenant_selector_unmatched');

                continue;
            }

            if (count($matches) > 1) {
                $failures[] = FleetTenantOutcome::failed(
                    $selector,
                    'tenant_selector_ambiguous:'.implode('|', $matches),
                );

                continue;
            }

            // Duplicates COLLAPSE: a tenant named twice (by id and by slug) is
            // processed once and counted once, or applied= would disagree with
            // the fleet size.
            $selected[$matches[0]] = true;
        }

        return [array_keys($selected), $failures];
    }

    /** @param Closure(Tenant): FleetTenantOutcome $perTenant */
    private function runOne(Tenant $tenant, Closure $perTenant): FleetTenantOutcome
    {
        $tenantId = (string) $tenant->getAttribute('id');

        try {
            // (a) the database physically exists — the same check
            // TenancyResolver::initializeIfProvisioned() performs.
            if (! $tenant->database()->manager()->databaseExists($tenant->getDatabaseName())) {
                return FleetTenantOutcome::failed($tenantId, 'tenant_not_ready:database_absent');
            }

            tenancy()->initialize($tenant);

            // (b) migrations are current.
            $pending = $this->pendingTenantMigrations();
            if ($pending !== []) {
                return FleetTenantOutcome::failed(
                    $tenantId,
                    'tenant_not_ready:migrations_behind:'.count($pending),
                );
            }

            return $perTenant($tenant);
        } catch (Throwable $exception) {
            return FleetTenantOutcome::failed($tenantId, 'exception:'.$exception->getMessage());
        } finally {
            if (tenancy()->initialized) {
                tenancy()->end();
            }
        }
    }

    /**
     * Files under database/migrations/tenant that the CURRENT (initialized)
     * tenant database has not recorded.
     *
     * @return list<string>
     */
    private function pendingTenantMigrations(): array
    {
        $path = database_path('migrations/tenant');
        if (! File::isDirectory($path)) {
            return [];
        }

        $onDisk = [];
        foreach (File::files($path) as $file) {
            if ($file->getExtension() === 'php') {
                $onDisk[] = $file->getFilenameWithoutExtension();
            }
        }
        sort($onDisk);

        /** @var list<string> $ran */
        $ran = DB::table('migrations')->pluck('migration')->all();

        return array_values(array_diff($onDisk, $ran));
    }
}
~~~

## Task 4 (0b-9c part 2 + 0b-14): `permissions:ensure`, `permissions:ensure-fleet`, and the lock wired into every runtime writer — **ONE commit**

> **This is one commit by spec ruling, not by preference.** §8's 0b-14 row: *"WIRING that lock into every runtime role-grant writer that exists at 0b, **in the same lane and the same commit as `EnsurePermissions.php`**"*. The 0b-window argument (§4.3.2, rev-7 B-1) is why: with every runtime writer serialized on the one advisory key, `ensure`'s post-lock eligibility check is decisive on its own — any operator change to a `--grant-to` role either commits **before** `ensure` acquires the lock (the post-lock re-read finds the role no longer equal to `postA1aGrants`, `matchesPreWave0b()` is false, and the role falls into `admin_only=`) or commits **after** `ensure` releases (and lands on top of a grant set `ensure` had already decided was eligible). There is no third interleaving **because there is no unlocked writer left to produce one**. Split the two and there is: for the whole 0b window `ensure` would be serialized against nothing, and the equality check would be a race with no detector.

### Why `permissions:ensure` exists at all

After `lane/w-lot-a-1a` merges, `php artisan tenants:seed --class=…RolesAndPermissionsSeeder` **writes nothing** on a marked tenant while `LOT_ACTION_PERMISSIONS_ENFORCE` is false — its shipped default. `run()` falls past the enforcement branch, hits `markedTenantCarriesWlota1aDelta()`, emits its `WLOTA1A-RESEED … marked_tenant_delta_preserved` marker and **returns** (lane `RolesAndPermissionsSeeder.php:52-55`, predicate at `:72-78`). That is *correct* for the lane, whose whole point is that a marked tenant is never re-seeded. The consequence for 0b is fatal: the nineteen keys would never reach a marked tenant while its routes are already gated on them, and Spatie fails closed — **403 for everyone, including `admin`**. That is the `credit-notes.cancel` failure mode reproduced on nineteen fresh keys.

### The contract, deliberately the smallest thing that closes the hole

- **Creates only.** `Permission::firstOrCreate(['name' => $key, 'guard_name' => 'sanctum'])`. Never renames, never deprecates, never deletes, never revokes.
- **Grants to `admin` unconditionally.** The registry-era rule is `admin = activeKeys()` and `admin` is not operator-editable at all, so granting `admin` a new key restores an invariant rather than widening a choice.
- **Grants a named `--grant-to` role only when `matchesPreWave0b()` is true**, evaluated **once per role, from the post-lock re-read, before any of that role's additions are written**, and the approved additions are then written as **one batch**. Evaluating per key would be the same defect at a smaller scale: the first granted key makes the role unequal and every subsequent key in the same invocation would be refused.
- **Otherwise: `admin` only, and say so.** The role is skipped, listed in `admin_only=`, and printed with the operator sentence. **A skip is not a failure** — the run still exits 0, because a tenant that customised its `manager` and therefore does not receive a new key is the correct outcome, not an incident.
- **Writes no marker.** It touches neither `provisioning_source` nor `general_manager`'s existence, which is exactly why it is safe where `tenants:seed` deliberately no-ops.
- **Team-bounded and NULL-team-tolerant.** `SetPermissionsTeam` is HTTP-only (`apps/api/app/Modules/Identity/Presentation/Middleware/SetPermissionsTeam.php:22-29`), and a console command has nothing to supply the team from. `ensure` therefore takes the identical boundary the lane ships — set before the transaction, restored in a `finally` on **every** path including failure — and resolves every role with the lane's NULL-or-tenant predicate. After the lane merges the legacy catalogue roles stay **NULL-team** while `general_manager` is **tenant-team-scoped**, so a lookup that ignores the team column would either miss `general_manager` entirely or resolve a different row than the `FOR UPDATE` that locked it — and a lock over one topology guarding a write over another is not serialization.

~~~php
/**
 * The wave-0b stopgap catalogue writer (spec 4.3.5).
 *
 * It exists because after lane/w-lot-a-1a merges, `tenants:seed
 * RolesAndPermissionsSeeder` writes NOTHING on a marked tenant while
 * LOT_ACTION_PERMISSIONS_ENFORCE is false (its shipped default) — correct for
 * that lane, fatal for a wave that gates live routes on nineteen new keys.
 *
 * permissions:sync SUPERSEDES it entirely in wave 1 (step 2 creates every
 * registry key and step 6 applies template grants, a strict superset), which is
 * why wave 1 deletes this class, both commands and their deploy rows in the
 * same commit that lands permissions:sync.
 */
final readonly class EnsurePermissionsRunner
{
    public function __construct(
        private PermissionRegistrar $permissionRegistrar,
        private PermissionWriteLock $writeLock,
        private LegacyRoleBaseline $baseline,
    ) {}

    /**
     * @param  list<string>  $keys
     * @param  list<string>  $grantTo
     */
    public function run(string $tenantId, array $keys, array $grantTo, bool $write): EnsurePermissionsResult
    {
        // The team boundary lane/w-lot-a-1a ships, adopted verbatim: set before
        // the transaction, restored in a finally that runs on EVERY path.
        $previousTeamId = $this->permissionRegistrar->getPermissionsTeamId();
        $this->permissionRegistrar->setPermissionsTeamId($tenantId);

        try {
            return DB::transaction(function () use ($tenantId, $keys, $grantTo, $write): EnsurePermissionsResult {
                // Obligation (ii): the lock is the FIRST statement in the transaction.
                $this->writeLock->acquire($tenantId);

                $created = 0;
                $granted = 0;
                $adminOnly = [];
                $missingRoles = [];

                // Obligation (iii): FOR UPDATE the affected roles, ordered by
                // roles.name ASC then roles.id ASC — the lane's order.
                $wanted = array_values(array_unique(['admin', ...$grantTo]));
                $roles = $this->resolveCatalogueRoles($tenantId, $wanted);

                // 1. Create-only.
                foreach ($keys as $key) {
                    $exists = Permission::query()
                        ->where('name', $key)
                        ->where('guard_name', 'sanctum')
                        ->exists();
                    if ($exists) {
                        continue;
                    }
                    $created++;
                    if ($write) {
                        Permission::create(['name' => $key, 'guard_name' => 'sanctum']);
                    }
                }

                // 2. admin — unconditional. Restores an invariant, never widens a choice.
                $admin = $roles->get('admin');
                if ($admin === null) {
                    $missingRoles[] = 'admin';
                } else {
                    $granted += $this->grantMissing($admin, $keys, $write);
                }

                // 3. Every other --grant-to role, equality-guarded, snapshot ONCE.
                foreach ($grantTo as $roleName) {
                    if ($roleName === 'admin') {
                        continue;
                    }
                    $role = $roles->get($roleName);
                    if ($role === null) {
                        $missingRoles[] = $roleName;

                        continue;
                    }

                    // Obligation (iv): the eligibility decision is made from the
                    // POST-LOCK read, once per role, BEFORE any of that role's
                    // additions are written. Per-key evaluation would refuse every
                    // key after the first in the same invocation.
                    $current = $this->currentKeys($role);
                    if (! $this->baseline->matchesPreWave0b($roleName, $current)) {
                        $adminOnly[] = $roleName;

                        continue;
                    }

                    $granted += $this->grantMissing($role, $keys, $write);
                }

                $outcome = ($created === 0 && $granted === 0)
                    ? EnsurePermissionsOutcome::AlreadyCurrent
                    : EnsurePermissionsOutcome::Applied;

                $result = new EnsurePermissionsResult(
                    $outcome,
                    $write ? 'ensure_applied' : 'dry_run',
                    $created,
                    $granted,
                    array_values(array_unique($adminOnly)),
                    array_values(array_unique($missingRoles)),
                );

                if (! $write) {
                    // Write-free, not failure-free: the classification above is
                    // identical to an applying run; only the rows are rolled back.
                    throw new DryRunRollback($result);
                }

                return $result;
            });
        } catch (DryRunRollback $rollback) {
            return $rollback->result;
        } catch (DomainException $exception) {
            return new EnsurePermissionsResult(
                EnsurePermissionsOutcome::Blocked,
                $exception->getMessage(),
                0,
                0,
                [],
                [],
            );
        } finally {
            $this->permissionRegistrar->setPermissionsTeamId($previousTeamId);
            $this->permissionRegistrar->forgetCachedPermissions();
        }
    }

    /**
     * lane/w-lot-a-1a's resolveCatalogueRoles() verbatim, minus the hard-coded
     * general_manager provisioning: NULL-or-tenant team predicate, tenant_id
     * PRESERVED as found, ordered name then id, lockForUpdate, and both refusals.
     *
     * @param  list<string>  $names
     * @return Collection<string, Role>
     */
    private function resolveCatalogueRoles(string $tenantId, array $names): Collection
    {
        $team = config('permission.column_names.team_foreign_key');
        /** @var Collection<int, Role> $roles */
        $roles = Role::query()
            ->where('guard_name', 'sanctum')
            ->whereIn('name', $names)
            ->where(fn (Builder $query): Builder => $query->whereNull($team)->orWhere($team, $tenantId))
            ->orderBy('name')
            ->orderBy('id')
            ->lockForUpdate()
            ->get();

        foreach ($roles->groupBy('name') as $name => $matches) {
            if ($name === 'general_manager' && $matches->contains(
                static fn (Role $role): bool => $role->getAttribute('provisioning_source') !== 'w-lot-a-1a',
            )) {
                throw new DomainException('unmarked_general_manager_collision');
            }
            if ($matches->count() !== 1) {
                throw new DomainException('ambiguous_legacy_role_collision');
            }
        }

        return $roles->keyBy('name');
    }

    /** @return list<string> */
    private function currentKeys(Role $role): array
    {
        /** @var list<string> $keys */
        $keys = $role->permissions()->toBase()->pluck('name')->all();

        return $keys;
    }

    /**
     * @param  list<string>  $keys
     * @return int the number of grants this call added (or would add, in a dry run)
     */
    private function grantMissing(Role $role, array $keys, bool $write): int
    {
        $existing = $this->currentKeys($role);
        $missing = array_values(array_diff($keys, $existing));
        if ($missing === []) {
            return 0;
        }
        if ($write) {
            // ONE batch per role — the snapshot was taken once, so the batch is
            // what the snapshot approved.
            $role->givePermissionTo($missing);
        }

        return count($missing);
    }
}
~~~

### Steps — part B: wire the lock into every runtime writer (0b-14)

> **The five obligations, per writer:** (i) open a transaction; (ii) `PermissionWriteLock::acquire($tenantId)` as its **first** statement; (iii) `SELECT … FOR UPDATE` the affected `roles` rows ordered by **`roles.name` ASC, then `roles.id` ASC**; (iv) **re-read** the decision inputs after the lock is held and decide from that read; (v) write and commit.
>
> **The one stated exception is `RoleController::store`.** It creates a row that does not yet exist, so there is nothing to `FOR UPDATE` and no prior grant set to re-read. Its obligation is exactly three steps in one transaction: **open the transaction; acquire the lock; INSERT the role, then apply its initial grant set.** A post-insert `FOR UPDATE` on a row the same transaction just created adds **no** serialization beyond the advisory lock it already holds — no other transaction can be between the two statements, because no other transaction holds the lock — so it is not required and **must not be added as ritual**. `PermissionWriteLockCoverageTest` asserts this as a **named property**, not as an exemption from the lock.

- [ ] **Step 4 — `RoleController`, five methods.** Lines re-derived in Phase 0; at lane tip `5d847b2ba` they are `store` `:213` (`Role::create`) / `:221` (`syncPermissions`), `update` `:241` (`findOrFail`) / `:265` (`syncPermissions`), `destroy` `:285` / `:312` (`$role->delete()`), `assignRole` `:373` (existing `DB::transaction`) / `:385`, `removeRole` `:430`.

      Constructor-inject the lock (rule 13 — never `app()`):
      ```php
      public function __construct(
          // …the controller's existing dependencies, unchanged…
          private readonly PermissionWriteLock $permissionWriteLock,
      ) {}
      ```

      **`store`** — the create-path exception:
      ```php
      $role = DB::transaction(function () use ($validated, $tenantId): Role {
          $this->permissionWriteLock->acquire($tenantId);
          $role = Role::create([/* …exactly the existing payload… */]);
          if (array_key_exists('permissions', $validated)) {
              $role->syncPermissions($validated['permissions']);
          }

          return $role;
      });
      ```
      **`update`**, **`destroy`**, **`assignRole`**, **`removeRole`** — the full five obligations. `assignRole` and `removeRole` additionally **re-count the admin population under the lock** rather than before it (that count becomes the wave-2a last-admin floor's input; 0b only moves *where* it is taken):
      ```php
      return DB::transaction(function () use (/* … */): JsonResponse {
          $this->permissionWriteLock->acquire($tenantId);
          $role = Role::query()
              ->where('id', $id)
              ->orderBy('name')->orderBy('id')
              ->lockForUpdate()
              ->firstOrFail();
          // …re-read the grant set / the admin population HERE, then decide…
      });
      ```
      **Do not change any response body, status code, validation rule, `CrossTenantRoute` annotation or audit dispatch in this task.** The only change is the transaction, the lock and the moved read.

- [ ] **Step 5 — `UserController`, two methods.** Both already open a transaction (`:217` for `store`, `:357` for `update`); the lock becomes the **first statement inside the existing closure**, and the role resolution moves inside it. `store`'s `assignRole` is at `:234`, `update`'s `syncRoles` at `:384`.

- [ ] **Step 6 — `ResetTenantCommand`.** Spec §4.3.2's rev-8 M-2 ruling moves it from INITIALIZATION-ONLY to **LOCKED**. The command refuses only in production (`:29-35`), `--force` skips the confirmation (`:59-63`), and it drops and recreates the live schema with no maintenance mode (`:65-71`) — staging and development tenants routinely have active operators, so "no operator can be concurrent" was simply false for this row.

      The correction is the small one: the `assignRole('admin')` loop at `:89-95` moves inside a transaction whose first statement is the lock, taken **after** the schema recreate and migrations:
      ```php
      $users = User::where('tenant_id', $tenant->id)->get();
      setPermissionsTeamId($tenant->id);
      DB::transaction(function () use ($tenant, $users): void {
          $this->permissionWriteLock->acquire($tenant->id);
          $admin = Role::query()
              ->where('guard_name', 'sanctum')
              ->where('name', 'admin')
              ->where(fn (Builder $q): Builder => $q->whereNull('tenant_id')->orWhere('tenant_id', $tenant->id))
              ->orderBy('name')->orderBy('id')
              ->lockForUpdate()
              ->firstOrFail();
          foreach ($users as $user) {
              $user->assignRole($admin);
              $this->line("  Assigned admin role to: {$user->email}");
          }
      });
      ```
      The explicit `setPermissionsTeamId($tenant->id)` the command already performs at `:91` **stays exactly where it is**.

      **Out of scope, deliberately and by name:** serialising the `DROP SCHEMA … CASCADE` itself. The lock cannot usefully span it — between the drop and the recreate the `roles` table does not exist, so no role-grant writer can be contending for anything the lock names, and holding one transaction across `DROP SCHEMA`, `CREATE SCHEMA` and a full migration run would block every other role writer in that tenant for the whole duration and would wrap DDL the migrator already transactions. This plan does **not** claim the reset is concurrency-safe as a whole; it claims only, and checkably, that the **role assignment** at the end can no longer interleave with another role-grant writer.

~~~php
        foreach ($finder as $file) {
            /** @var SplFileInfo $file */
            $source = (string) $file->getContents();
            foreach (self::WRITER_PATTERNS as $pattern) {
                if (str_contains($source, $pattern)) {
                    $writers[] = str_replace(base_path().'/', '', $file->getPathname());

                    break;
                }
            }
        }

        return array_values(array_unique($writers));
    }

    private function methodBody(string $source, string $signature): string
    {
        $start = strpos($source, $signature);
        $this->assertNotFalse($start, "method not found: {$signature}");
        $next = strpos($source, "\n    public function ", $start + 1);

        return substr($source, $start, $next === false ? strlen($source) : $next - $start);
    }
}
~~~
