You are the **POS Orchestrator session for T2.1** — catalog truthfulness + stranded-syncing recovery. Four bundled sub-steps that close the largest open functional gap in the POS desktop app + the highest-impact crash-safety durability gap.

**Your prime directive:** the cashier on a 5000-SKU parapharmacy or 10000-SKU autospecs tenant currently cannot see most of their catalog on cold start, cannot scan most of it via barcode/SKU even after the catalog hydrates, sometimes sees the visible subset disappear when they switch category tabs, and can lose a fiscal record if the device power-cuts mid-sync. Four bugs (3 truthfulness + 1 durability):

1. **`productStore.fetchProducts` hardcodes `limit: 500`** on the foreground cold-start path. The background `pullProducts` delta-sync flow (which DOES paginate via `updated_since` + chunked pulls) fires immediately on terminal activation (`syncScheduler.ts:27-35` — `void this.tick()` runs before the interval is installed) AND every 60 s thereafter. **The cold-start gap is therefore a foreground/background race against the IMMEDIATE first tick + the existing `isSyncing` guard at `syncScheduler.ts:69-70`**, NOT a "60s delayed" gap. On a 5000-SKU tenant on Slow-3G, the foreground 500-cap typically resolves first (faster API call, no backoff), then the background tick is debounced by `isSyncing` until the foreground completes, then catches up. The user-visible result is the cashier sees ~500 of 5000 products until the foreground 500-cap fetch returns AND the cashier reloads or the next tick (typically ~60 s later) overwrites the in-memory snapshot via `productStore.refreshFromSQLite()`. The functional gap is real even if the timing model is more nuanced than "5–10 minutes". Verified at `apps/pos/src/stores/productStore.ts:57`.

2. **HomePage barcode handler searches `productStore.products` only**, matching `p.barcode === scannedCode || p.sku === scannedCode` (verified `HomePage.tsx:231-235`). It never falls back to `getProductByBarcode(db)` from SQLite (which `productRepository.ts:44-49` already exports — and which already does the same `barcode = $1 OR sku = $1` matching), nor to the existing `fetchProductByBarcode(barcode)` API helper at `productApi.ts:16-18` (which calls `apiGet('/products', { barcode, per_page: 10 })`). Compounds bug 1: even when SQLite has the product post-tick, the in-memory store doesn't, so the scan returns "product not found" for ~90% of the catalog.

3. **Two filter-state regressions cause "products vanish on A→B→A"** — `selectedCategory` is local state in `ProductGrid` that doesn't invalidate when `products[]` is replaced (e.g. by a sync tick), so a tap on a category that no longer exists in the new list silently produces an empty grid. The virtualizer (`ProductGrid.tsx:148-153`, scroll container at `:311-315`, empty-state branch at `:300-309`) also doesn't reset its scroll position / re-measure when the filtered subset changes shape, so the visible window can hold a stale range after a category switch. Opus's 2026-04-30 catalog-state-deep-dive ranked this combination as the #1 root cause of the "products vanish" symptom.

4. **Stranded `'syncing'` rows are silently dropped from replay forever.** `syncService.ts:300` updates a receipt's status to `'syncing'` BEFORE the sync HTTP call completes; on success the response handler advances to `'synced'`, on failure to `'failed'`. A SIGKILL / power-cut between the status update and the response handler leaves the row at `'syncing'` permanently. `getPendingReceiptsForSync` filters `WHERE status IN ('pending', 'failed')` (`offlineReceiptRepository.ts:163`) — so the orphaned row is invisible to every subsequent sync attempt. This is a silent fiscal-record loss on power cut. Verified by grep across `syncService.ts`, `offlineReceiptRepository.ts`, `terminalStore.ts`, and `lib/db.ts` — no boot-time recovery `UPDATE` exists.

These four bugs collectively bound the cashier-facing surface: every product reachable, every category honest, every filter consistent, every fiscal record durably recoverable. T2.1 fixes all four so the catalog surface is the single truthful representation of what's in SQLite AND no fiscal record is lost to a crash.

## Section 3 — T2.1 scope (4 sub-steps in one PR — catalog truthfulness + stranded-syncing recovery)

### Why bundle these 4 sub-steps in one PR (not split further)?

The catalog surface is a single state machine. Step A makes coverage truthful (every product reachable on cold start); Step B makes lookup truthful (every barcode scan finds the product if SQLite has it); Step C makes filter truthful (every category tap shows the live subset). Splitting would force interim states where the catalog is partly truthful (e.g. coverage fixed but barcode still misses) — confusing for a reviewer, painful for a cashier mid-rollout. ### Step A — Foreground catalog warmup uses paginated delta pull (closes the 500-SKU cap)

**Files:**
- `apps/pos/src/stores/productStore.ts` (verify; `fetchProducts` at `:57` post-T2.2; `refreshFromSQLite` at `:161-175`; Menu guard at `:52-58` via `hasModule(config, 'Menu')`).
- `apps/pos/src/lib/sync/syncService.ts` (verify; `pullProducts(db)` at `:565-621`; `updated_since` + `deleted_ids` cursor logic; the cursor `products_last_sync` is persisted per-PULL at `:603-604`, NOT per-page; `pullProducts` swallows errors and returns `0` at `:616-620`).
- `apps/pos/src/pages/HomePage.tsx` (verify; the cold-start `fetchProducts` invocation in a `useEffect`).

**The bug (verify on dev tip):**
`productStore.fetchProducts` calls `fetchPOSProducts({ limit: 500 })` for the standard-retail (non-Menu) tenant path and writes the result to the store + SQLite (`productStore.ts:57`). On a 5000-SKU tenant the cashier sees the first 500 products immediately. The SyncScheduler's IMMEDIATE first tick (`syncScheduler.ts:27-35` — `void this.tick()` runs before the interval) calls `pullProducts(db)` which pages through the rest using `updated_since` + chunked pulls. Subsequent ticks call `productStore.refreshFromSQLite()` (via `syncScheduler.ts:78`), which DOES read all rows from SQLite and replace the in-memory snapshot. So the cashier eventually sees the full 5000 — but the foreground 500-cap typically wins the race against the immediate tick (faster API call), and the `isSyncing` guard at `syncScheduler.ts:69-70` debounces the background tick until the foreground 500-fetch completes. Net cashier experience: 500 of 5000 products until the next tick (~60 s later) reconciles via SQLite.

**Fix contract:**
- **Architectural change to `syncService.ts`** (Codex round-2 R2): the existing `pullProducts(db)` swallows all errors and returns `0` (`syncService.ts:616-620`). A wrapper that simply calls `pullProducts` cannot distinguish "timeout" from "HTTP 5xx" from "0 products legitimately". Step A therefore extracts the shared pagination into a NEW lower-level function `pullProductsCore(db, opts: { signal?: AbortSignal; timeoutMs?: number }): Promise<{ count: number }>` that THROWS typed errors (`FetchTimeoutError`, `PullProductsError` with `kind: 'http_5xx' | 'network' | 'parse'`). The existing `pullProducts(db)` is REFACTORED into a thin wrapper that calls `pullProductsCore(db)`, swallows errors via the existing `try/catch` (preserving the scheduler-side 0-on-error semantics bit-identically), and returns `count` or `0`. The scheduler-side observable behavior is unchanged. Verify post-refactor by spot-checking `pullProducts` against the pre-refactor call sites — same return shape, same error swallowing, same logging.
- **Replace the `fetchPOSProducts({ limit: 500 })` call in `productStore.fetchProducts`** (standard-retail / non-Menu branch only — see Menu-tenant note below) with a NEW free-function wrapper `pullProductsForeground(db, { timeoutMs: 30000 })` exported from `syncService.ts`. The wrapper:
  - Internally calls `pullProductsCore(db, { timeoutMs })` (NOT the swallowing `pullProducts`) so timeout/HTTP/network errors propagate as typed exceptions.
  - On success: returns `{ ok: true, count: number }`.
  - On `FetchTimeoutError`: rejects.
  - On `PullProductsError`: rejects with `kind` preserved.
- **After `pullProductsForeground` resolves**, call `productStore.getState().refreshFromSQLite()` once to read the now-complete catalog from SQLite into the in-memory store. **Spinner-then-full UX**: the cashier sees the loading spinner from `fetchProducts` entry to `refreshFromSQLite` resolution, then the full catalog appears in one re-render. NO incremental partial-then-full progression (per orchestrator decision; the page-commit callback architectural change is out of T2.1 scope).
- **`fetchProducts` rejection contract:** today `fetchProducts` swallows errors into store state (`isLoading: false, error: …`) per `productStore.ts:136-145` and never throws. Step A preserves that contract: the `pullProductsForeground` rejection is caught inside `fetchProducts`, written to `error` state with the typed error message, and surfaced in the UI as the existing error banner. **Tests assert against this store-state contract, NOT against `fetchProducts()` rejecting.** (This corrects v1's incompatible Test A.3.)
- **Preserve the SyncScheduler's tick-driven refresh.** Background ticks continue to call `pullProducts` directly (NOT `pullProductsForeground`, NOT `pullProductsCore`) — they keep the swallow-on-error semantics that are appropriate for silent retry.
- **Menu-tenant non-regression:** the Menu-mode branch in `productStore.fetchProducts` (guarded by `hasModule(config, 'Menu')` at `:52-58`) calls `fetchPOSMenu` + `flattenMenuToProducts` and is OUT OF T2.1 SCOPE. Step A's fix MUST NOT touch that branch. Add a regression test that the Menu-mode path still returns a flattened products array post-fix. **Otospex go-live impact:** Otospex uses Menu mode; T2.1 does NOT close the Menu-tenant catalog desync (C2 in the audit). If Otospex is a target launch tenant alongside parapharmacy, the Menu desync is an explicit pre-launch blocker tracked separately — surface to orchestrator if uncertain.

**Codex preempts (T1.x lessons + round-2 ricochet — pre-empt aggressively):**
- **Foreground/scheduler race is NOT debounced by `isSyncing`** (Codex round-2 R1 correction). The `useSyncStore.isSyncing` guard at `syncScheduler.ts:65-72` is set by `SyncScheduler.startSync` (a method on the scheduler instance) — NOT by a free-function `pullProductsForeground` call. The foreground wrapper does NOT touch `useSyncStore.isSyncing`. So the scheduler's immediate first tick CAN fire concurrently with a foreground pull. Both call into the same SQLite. **Acceptance contract** (revised from v2):
  - SQLite per-statement atomicity covers correctness — upserts on the same row are idempotent.
  - In-memory snapshot last-write-wins after both finish.
  - The cost of a rare benign double-pull is one extra HTTP round-trip + idempotent re-upserts of pages already in SQLite. Negligible compared to the user-facing benefit.
  - **Document this as the acceptance**, NOT "no double-pull". The earlier "no double-pull" framing in v2 was wrong.
  - **Optional follow-up (NOT in T2.1):** if the cost of the double-pull becomes user-visible (rare, only on Slow-3G + a 10K-SKU catalog where both pulls take >30s), a future architectural session can add a free-function-level mutex shared by the scheduler and the foreground wrapper. Out of T2.1 scope.
- **`pullProductsCore` extraction discipline.** The extraction is a refactor with strict bit-equivalent observable behavior for the scheduler-side path. Verify with at least one targeted test that pre-refactor scheduler tests still pass against the post-refactor `pullProducts` thin wrapper. If any scheduler test changes shape, the refactor went wrong.

### Step D — Boot-time stranded `'syncing'` row recovery (crash-safety durability)

**Files:**
- `apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts` (verify; `OfflineReceiptStatus` enum at `:4` includes `'syncing'`; `getPendingReceiptsForSync` at `:163` filters `WHERE status IN ('pending', 'failed')` — `'syncing'` is excluded, the bug).
- `apps/pos/src/stores/terminalStore.ts` (verify; `seedOfflineHashChain` declaration at `:98`, with a TODO docstring above at `:90-97`; the function is the canonical boot-time hook for SQLite hydrations; Step D adds the recovery `UPDATE` inside this function before scheduler.start at `:118-121`).
- `apps/pos/src/lib/sync/syncService.ts` (verify; `:300` is the `updateReceiptStatus(... 'syncing')` call site that creates the orphan-prone state).

**The bug:**
`syncService.ts:300` advances a receipt to `'syncing'` BEFORE the sync HTTP call. On success the response handler advances to `'synced'`; on failure to `'failed'`. A SIGKILL / power-cut / OS-level kill between the status update and the response handler (or its catch block) leaves the row at `'syncing'` permanently. `getPendingReceiptsForSync` at `:163` filters `WHERE status IN ('pending', 'failed')`, so the stranded row is invisible to every subsequent sync attempt. Net effect: a fiscal record with a hash-chain advance but no server-side counterpart, never retried, eventually visible only via `php artisan pos:verify-chains` as a chain-break — by which time the cashier has long moved on. **For a parapharmacy on shaky power infrastructure, this is a real go-live risk.**

**Fix contract:**
- **Add a boot-time recovery `UPDATE` inside `seedOfflineHashChain`** (or its sibling startup function — verify the canonical boot hook by re-reading T1.2's `seedOfflineHashChain` enhancements and T1.3's hydration additions). The new step:
  ```ts
  // T2.1 Step D: stranded-syncing recovery. A SIGKILL/power-cut between
  // syncService.updateReceiptStatus(... 'syncing') and the response handler
  // can strand a row at 'syncing' permanently. On boot, demote any such
  // row back to 'pending' so the next sync tick re-attempts it. Idempotent
  // by construction (the row is in the same state pre/post-send because
  // the response never landed).
  await db.execute(
    "UPDATE offline_receipts SET status = 'pending' WHERE status = 'syncing'"
  );
  ```
  - Wrap with `try/catch` + `serializeErrorForLog` per T0.1 contract. SQLite `UPDATE` against a missing row is a no-op (rowsAffected: 0); failure means SQLite is in a bad state and the boot hook should surface the error to the user via the existing chain-break recovery banner pattern (don't silently swallow).
  - Order this BEFORE the SyncScheduler `start()` call so the next tick sees the demoted rows in `getPendingReceiptsForSync`.
  - Log the row count when nonzero: `console.info('[T2.1 Step D] recovered N stranded syncing rows on boot')`. Production value: cashier-support-team can grep logs for "recovered N stranded" to detect power-cut frequency patterns.
- **Idempotency reasoning** (document in PR body): a row at `'syncing'` is in one of three states post-crash:
  1. The HTTP request never left the device (most common) → the server has nothing → demote to `'pending'`, retry → server processes the receipt fresh → done. ✓ Correct.
  2. The HTTP request succeeded server-side but the response was lost → demote to `'pending'`, retry → server detects via `idempotency_key` (T0.2 contract) and returns the prior result → client advances to `'synced'`. ✓ Correct.
  3. The HTTP request succeeded server-side AND the response landed but the local status update failed → demote to `'pending'`, retry → same as (2). ✓ Correct.
  All three converge to the right outcome thanks to T0.2's per-receipt idempotency keys. Step D's recovery is safe.
- **No PRAGMA changes in this step.** `busy_timeout` and explicit `journal_mode=WAL` assertion are deferred to T2.6 (separate session). Step D is the focused stranded-row recovery only.

**Codex preempts:**
- **Race against the SyncScheduler's immediate first tick (Codex M0 echoed).** The scheduler starts at `terminalStore.ts:118-121` and fires `void this.tick()` immediately. Step D's `UPDATE` MUST run BEFORE `scheduler.start()` so the first tick sees the demoted rows. Verify the ordering in `seedOfflineHashChain` after the fix.
- **Concurrency with an in-flight pre-crash request.** Edge case: a process running BEFORE the crash had a `'syncing'` row mid-send; the new process boots, demotes the row, attempts to send. If the old process's request lands on the server AFTER the new process's: idempotency key collapses both into one server-side receipt, second-arrival wins on the server (T0.2). The client sees one of the two responses; the row ends at `'synced'`. Document.
- **Multi-tenant isolation.** The `UPDATE` runs against the per-tenant SQLite DB (`getDatabase(companyId)`); only that tenant's rows are touched. Verify `seedOfflineHashChain` already operates within tenant scope (T1.1 + T1.2 work confirmed this).
- **Test honesty.** The RED test for this step seeds 1 `'syncing'` row + 1 `'pending'` row + 1 `'synced'` row pre-boot, calls `seedOfflineHashChain('term-1')`, asserts: `'syncing'` row is now `'pending'`, `'pending'` row stays `'pending'`, `'synced'` row stays `'synced'`. Pre-fix RED: the `'syncing'` row stays at `'syncing'`.
