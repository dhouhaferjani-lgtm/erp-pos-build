# T2.4 — Bootstrap Error Handling State Machine (Kickoff)

**Status:** Pending kickoff. Source: activation hardening plan §Phase 3 + Codex P1 audit finding (silent indefinite spinner mid-bootstrap).
**Estimated effort:** 2–3 days.
**Coordination risk:** Low–Medium. Touches `apps/pos/src/App.tsx` (`AppRouter`), all three init stores, and a new error screen. Refund flow may also touch App.tsx (to add a `/refund` route) — keep this scope to the bootstrap orchestration logic, not route definitions.

## Why this exists

The activation hardening plan §Phase 3 (`docs/superpowers/plans/2026-04-30-pos-activation-hardening.md` lines 111-153) describes the failure mode:

> Internet drops between the `/auth/login` call and the terminal/company hydration, leaving the cashier on a loading screen with no error message.

The plan's "Current state" section says the bootstrap is a sequential `await` chain in `AppShell.tsx`. **That's stale** — post-PR-#87 (T1.1 Phase 1, the auth-orphan boot fix), the orchestration was hoisted from `AppShell.tsx` into `App.tsx::AppRouter()`. The actual current shape is three independent `useEffect`s that fire serially based on Zustand store state:

```tsx
// apps/pos/src/App.tsx::AppRouter (the actual bootstrap orchestrator today)
useEffect(() => { void initAuth(); }, [initAuth]);

useEffect(() => {
  if (isAuthenticated && companyId) void initTerminal();
}, [isAuthenticated, companyId, initTerminal]);

useEffect(() => {
  if (isAuthenticated && companyId && terminal && hasPins === null) {
    void checkHasPins();
  }
}, [isAuthenticated, companyId, terminal, hasPins, checkHasPins]);
```

The render branches off `isInitialized`, `authLoading`, `terminalLoading`, etc. When any `initialize()` hangs or throws an unhandled error, the corresponding `*Loading` flag never flips to false — render gets stuck on the indefinite spinner at `<div className="...animate-spin..." />`. **No timeout. No retry. No user-facing error.**

T2.4 closes this with a unified bootstrap state machine that covers all three init paths plus the `companyRecovery` already-shipped recovery branch.

## Surface (estimated 2–3 days)

### New: `apps/pos/src/stores/bootstrapStore.ts`

```ts
type BootstrapPhase =
  | 'idle'
  | 'authenticating'
  | 'fetching-companies'
  | 'fetching-terminal'
  | 'checking-pins'
  | 'ready'
  | 'error';

type BootstrapError = {
  phase: BootstrapPhase;
  errorName: string;        // SAFE_ERROR_NAMES allowlist (mirrors App.tsx:161)
  recoverable: boolean;     // true if SQLite has a usable cached value
  retryCount: number;
};

interface BootstrapState {
  phase: BootstrapPhase;
  error: BootstrapError | null;
  lastSuccessfulPhase: BootstrapPhase | null;
  // actions
  start: () => Promise<void>;
  retry: () => Promise<void>;        // Re-runs from `lastSuccessfulPhase + 1`
  skipWithCache: () => Promise<void>; // Falls through to cached SQLite values
}
```

Each phase delegates to the existing store's initialize method, wrapped in `withTimeout`:

| Phase | Delegates to | Existing call site |
|---|---|---|
| `authenticating` | `authStore.initialize()` | `App.tsx:54` |
| `fetching-companies` | `authStore.fetchCompanies()` | `App.tsx:181` (recovery branch already shipped) |
| `fetching-terminal` | `terminalStore.initialize()` | `App.tsx:59` |
| `checking-pins` | `operatorStore.checkHasPins()` | `App.tsx:65` |

### New: `apps/pos/src/lib/bootstrap/withTimeout.ts`

Promise-with-timeout helper. **Inject the clock for testing** (see Risks below):

```ts
export class BootstrapTimeoutError extends Error {
  override name = 'BootstrapTimeoutError';
  constructor(public phase: BootstrapPhase, public timeoutMs: number) {
    super(`Bootstrap phase "${phase}" timed out after ${timeoutMs}ms`);
  }
}

export function withTimeout<T>(
  phase: BootstrapPhase,
  promise: Promise<T>,
  timeoutMs: number,
  signal?: AbortSignal,
): Promise<T> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(
      () => reject(new BootstrapTimeoutError(phase, timeoutMs)),
      timeoutMs,
    );
    signal?.addEventListener('abort', () => clearTimeout(timer));
    promise.then(
      (v) => { clearTimeout(timer); resolve(v); },
      (e) => { clearTimeout(timer); reject(e as Error); },
    );
  });
}
```

Default timeout: **15 seconds** per phase (configurable via Zustand state or settings store).

### New: `apps/pos/src/components/BootstrapErrorScreen.tsx`

Replaces the indefinite spinner branch in `AppRouter`. Renders:

- The failed phase name (i18n: `bootstrap.phase.<phaseName>`).
- The error name (from the SAFE_ERROR_NAMES allowlist — never raw `error.message`).
- **Retry** button → calls `bootstrapStore.retry()`.
- **Use cached data** button (only rendered when `error.recoverable === true`).
- **Sign out** secondary affordance (delegates to `authStore.logout()`).
- A "View details" expander showing `phase`, `errorName`, `retryCount`, and a timestamp — for engineering when a cashier reports a stuck terminal.

The visual style mirrors the existing `CompanyRecoveryScreen` (App.tsx:169-245) so the cashier sees a consistent recovery UX across all bootstrap-time failures.

### Refactor: `apps/pos/src/App.tsx::AppRouter`

Replace the three `useEffect` orchestration calls and the indefinite-spinner branches with a single `useEffect → bootstrapStore.start()` and one render branch on `bootstrapStore.phase === 'error'`. The downstream conditional renders (auth → companies → terminal → pins → operator) stay; the state machine just guards the **happy path** and surfaces failures.

The existing `CompanyRecoveryScreen` can be folded into `BootstrapErrorScreen` (both share the failed-phase + retry + signout pattern), but a low-risk first cut leaves it in place and lets `BootstrapErrorScreen` handle the other three phases.

## Tests

### Unit: `bootstrapStore.test.ts`

- Phase transitions: `idle → authenticating → fetching-terminal → checking-pins → ready` (happy path).
- `start()` halts on the first failing phase; `error.phase` matches the failing phase.
- `retry()` re-runs from `lastSuccessfulPhase + 1`, not from `idle`.
- `skipWithCache()` skips the failing phase and falls through to the next one when `recoverable === true`; throws when `recoverable === false`.
- `error.errorName` is always within the `SAFE_ERROR_NAMES` allowlist (regression guard for the T0.1 banner-opacity contract — never leak raw error text to UI).

### Unit: `withTimeout.test.ts`

- Resolves when the wrapped promise resolves before the timeout.
- Rejects with `BootstrapTimeoutError` when the timeout fires first.
- Cancels the timeout when the abort signal fires.
- Uses `vi.useFakeTimers()` everywhere — no wall-clock dependence (Risks below).

### Integration: `App.test.tsx` (extend existing harness)

- Mount `AppRouter` with mocked store init methods that throw a network-style error → assert `BootstrapErrorScreen` renders within one render pass after the timeout fires (advance fake timers).
- Click **Retry** → `bootstrapStore.retry()` is called, the mocked init re-runs.
- When recoverable, click **Use cached data** → falls through to the next phase.

### Manual smoke (audit phase / before merge)

- Cold install, kill API mid-`/auth/me` → confirm `BootstrapErrorScreen` appears within 15s.
- Cold install, kill API mid-`/user/companies` → confirm error screen with "Retry" + "Use cached data" (when SQLite has a cached company list).
- Cold install, kill API mid-`/terminals?company_id=...` → confirm error screen.
- Retry from each error state → confirm success after API returns.

## Risks

1. **Test flakiness from timing.** Wall-clock-dependent tests will flake on slow CI. **Mitigation:** every `setTimeout` goes through `withTimeout`'s clock injection; tests use `vi.useFakeTimers()` exclusively. No `await new Promise(r => setTimeout(r, n))` in production code — all delays gated by the abstraction.

2. **Coordination with refund-flow PR.** Refund flow may also touch `App.tsx` to add a `/refund` route. **Mitigation:** Keep this PR's diff scoped to the bootstrap useEffect orchestration + new render branch. **Don't refactor route definitions.** If refund-flow merges first, rebase. If T2.4 merges first, refund-flow's route additions land cleanly because the conditional render structure is unchanged.

3. **Coordination with T2.7 (training-aware receipts).** T2.7 backend changes touch `ReceiptSyncService` and `SyncReceiptPayload`; T2.7 frontend touches `createOfflineReceipt` and the `offline_receipts` SQLite schema. **Zero overlap with T2.4** — the bootstrap state machine doesn't touch sync ingestion. Both can land in either order.

4. **Backwards compat with `CompanyRecoveryScreen`.** The existing recovery branch already handles the `companies.length === 0` case. **Mitigation:** Phase 1 of T2.4 leaves it in place; the bootstrap state machine catches errors in `fetchCompanies()` itself, but the empty-companies render path stays as today. A Phase 2 follow-up (post-launch) can fold them.

5. **Stale plan reference.** The activation hardening plan says T2.4 touches `AppShell.tsx`. The current architecture is `App.tsx::AppRouter`. Update the plan's Phase 3 §Current state when this PR lands so future readers don't redo the audit.

## Open questions / spec decisions

1. **Timeout duration per phase.** 15s default per the activation plan. Should `fetching-companies` get a longer ceiling on slow networks (e.g., 30s), since it's the most network-heavy phase? **Recommendation:** start at 15s for all, monitor Phase 6 smoke results, adjust pre-merge if needed.

2. **What counts as `recoverable`?** Per phase:
   - `authenticating`: false (login token is the entry point; can't be cached).
   - `fetching-companies`: true if `localStorage` has a cached company list.
   - `fetching-terminal`: true if SQLite has a cached terminal record.
   - `checking-pins`: true (operator PIN check is a guard, not a hydration — falls through to PIN entry).

3. **Telemetry hook.** Should `bootstrapStore.error` events fire a telemetry beacon (Sentry / structured log) so engineering sees production retry-rate signals? **Recommendation:** yes; use the `serializeErrorForLog` helper at `apps/pos/src/lib/errorLogging.ts` to keep the payload shape consistent with the rest of T0.1.

4. **Should `BootstrapErrorScreen` show the actual phase name in plain English ("Loading your shop", "Setting up your terminal") or the technical phase ("fetching-companies")?** UX choice. **Recommendation:** plain English via i18n keys at `bootstrap.phase.<phaseName>`. Engineering can still see the technical phase in the "View details" expander.
