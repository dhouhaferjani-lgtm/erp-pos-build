# RBAC Wave 1 — catalogue as code Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the 871-line seeder array with a code-owned catalogue — per-module `PermissionManifest`s aggregated by a `PermissionRegistry` — and make a deploy apply an **additive template delta** that provably never touches a custom role or a customised system role. This is the wave that closes G3, the core gap: today the application never re-syncs an existing tenant, while staging runs a **destructive full reseed on every deploy** (I-20).

**Architecture:** A permission becomes a `PermissionDefinition` whose key is **derived** from `(resource, verb, qualifier)` and can therefore never disagree with its parts; verbs come from a **closed** `PermissionVerb` enum; each module owns a manifest in its `Domain/Authorization/` (a pure declaration with zero infrastructure dependency) and contributes it by **tagging** in its own service provider, which is the automatic-inclusion guarantee at the wiring level. `PermissionSyncService::sync()` runs nine steps in one transaction under the **wave-0b** `PermissionWriteLock`, with **adoption before any grant write**, and it never references a single symbol from `lane/w-lot-a-1a`. The seeder survives as a thin adapter, because two contracts (the exporter and that lane's staging protocol) name it.

**Tech Stack:** Laravel 12 / PHP 8.4 / Spatie laravel-permission 6.25 / Stancl Tenancy 3.10 / PHPUnit 11 / PHPStan L8 / Pint / nikic/php-parser / React 19 / Vitest

## Global Constraints

- [ ] **Nothing in this wave references a symbol from `lane/w-lot-a-1a`.** Not `LotActionPermissionDelta`, not `LotActionPermissionActivation`, not any `TemplateMigration*` class (there is none — the whole machinery is deleted from the design). `PermissionSyncServiceTest::sync_references_no_lot_action_symbol` is the mechanical form. The delta runs **once, at that lane's own activation deploy, before wave 1 exists**; the registry's `template_version = 0` snapshots are the *post-A-1a* state, so sync starts from what tenants actually hold and has nothing to re-apply.
- [ ] **Adoption runs before any grant write.** Steps are rename → create → orphan report → **adopt** → create missing template roles → template deltas → deprecation replacements → admin → after-commit cache. Running a role-mutating step first is what let rev 3 of the spec re-add a grant a tenant had removed, making a customised role compare equal and be adopted pristine.
- [ ] **The lock is 0b's, unchanged.** `PermissionWriteLock::acquire($tenantId)` on the key `'wlota1a:'.$tenantId`; `FOR UPDATE` ordered `roles.name` ASC then `roles.id` ASC. Wave 1 **adds three writers** to the LOCKED class — `PermissionSyncService::sync()`, `TemplateDeltaApplier::applyTo()` (including the *Re-apply template* caller) and the `customised_at` writer inside `RoleController::update` — and extends `PermissionWriteLockCoverageTest` accordingly. It does not redefine the key, the order or the helper.
- [ ] **Two tenant migrations, timestamped AFTER `2026_09_06_205000_add_provisioning_source_to_roles.php`.** Wave 1 ships **one** of them (`roles`); `users` is wave 2. Neither may write `tenant_id`, or the W-LOT CHECK's `tenant_id IS NOT NULL` clause interacts with a NULL-team legacy role.
- [ ] **`provisioning_source` is written in EXACTLY ONE case** and never cleared, changed or widened: when step 5 **creates** a missing `general_manager` on a tenant that carries no marker. `PermissionSyncMarkerTest` asserts the five negatives and the one positive.
- [ ] **A custom role (`is_system = false`) receives no template grant, ever, and never loses a key of any kind** — the sole exception being a `replacedBy` grant on a deprecation, which emits a `RoleSyncedV1` audit event so the exception is visible in the audit chain rather than being an invisible carve-out.
- [ ] **A customised system role (`customised_at IS NOT NULL`) receives nothing in either direction.** Not a grant, not a revocation.
- [ ] **An UNCUSTOMISED template-linked role is brought to set EQUALITY with its template** — every key the template declares and the role lacks is granted, and **every key the role holds that the template does not declare is revoked, deprecated or not**. That is safe *here and only here*: by construction such a role is its template plus whatever sync itself put there.
- [ ] **`admin` is a full replace to `registry->activeKeys()`**, and `admin` is implicit — a manifest that lists `'admin'` in `templateDefaults` is a build error.
- [ ] **Idempotency has two clauses, both mechanically checked:** every **`mutations`** counter zero **AND** zero database writes. The two **`gauges`** (`orphans`, `templates_skipped_customised`) report whatever is true of the tenant and are **unconstrained** on a re-run. `outcome=ALREADY_CURRENT` is defined as exactly that conjunction.
- [ ] **`--dry-run` is WRITE-free, not FAILURE-free.** It changes exactly one thing — what is written — and nothing else. A dry run that reaches `BLOCKED` still exits **2**; one that fails still exits **1**. On the per-tenant command and on the fleet runner alike.
- [ ] **Every wave from 1 onward deploys through `permissions:sync-fleet`** — never `tenants:run permissions:sync` (discarded child exit statuses), never the per-tenant `permissions:sync` without an explicit `--tenant=` in an operator-remediation context, and there is **no `--force`**.
- [ ] **Constructor injection only** (`private readonly`), never `app()` — with **one** sanctioned exception, named in Task 14: the two `public static` shims on `RolesAndPermissionsSeeder`, which have no constructor to inject into and exist purely to keep the exporter's and the lane's contracts intact. They carry an explicit `@internal` docblock and are listed among the PHPStan rule's allowed call sites.
- [ ] **Strict types** in every new PHP file, no `mixed`, no `any`. **Enums** for every status/type value.
- [ ] **PHPUnit by path only.** Never the full suite locally.
- [ ] **PG lane env:** `DB_DATABASE=autoerp_test_w1 DB_CENTRAL_DATABASE=autoerp_test_w1_central DB_CONNECTION=pgsql DB_HOST=127.0.0.1 DB_PORT=5433`. Both variables, always; never the shared default; never two PG legs in parallel.

### O-5 / OQ-3 — **owner-owed, and it blocks Task 13's baseline**

### O-6 / OQ-4 — **owner-owed at the END of this wave, not at its start**

Does `SYNC_PERMISSIONS_ON_BOOT` default to `true` in production after the soak? The applied default: **yes**, after a one-week staging soak with zero unintended diffs. The conservative alternative — leave it `false` and run `permissions:sync-fleet` as a named deploy step — is a real option and costs one runbook line. **This plan ships the flag's production default at `false` and the soak as Task 19's exit condition.** The flag name is **kept**: W-LOT-A-1a's evidence protocol asserts its value on staging in six places, and renaming it would invalidate that lane's evidence. What changes is only what the flag runs.

### OQ-1 and OQ-2 — **not blocking this wave**

### Q-w1-1 — the resource regex must admit `purchase-hub.orders`

§4.2.1's resource pattern is `^[a-z0-9]+(-[a-z0-9]+)*(\.[a-z0-9]+(-[a-z0-9]+)*)?$`, and the spec glosses the second dot segment as *"the two legitimate nested resources, `catalog.attributes` and `inventory.transfers`"*. Wave 0b declared **`purchase-hub.orders.create`**, whose resource is `purchase-hub.orders` — a third nested resource. It **matches the regex as written**; only the prose gloss is short.

**This plan implements the regex unchanged** and adds `purchase-hub.orders` to the docblock's list of nested resources, plus a registry test asserting all **three** construct through `make()`. No behaviour changes. Flagged so a gate does not read the gloss as a whitelist and reject a key wave 0b already deployed.

### Q-w1-3 — the seeder shim's `run()` KEEPS the lane's marked-tenant preservation branch

## Task 1: `PermissionVerb` — the closed verb enum

~~~php
<?php

declare(strict_types=1);

namespace App\Shared\Domain\Authorization;

/**
 * The CLOSED verb enum (owner ruling D5). Verbs are declared, not invented.
 *
 * Thirty-two cases: what the 304-key catalogue already used, plus the verbs the
 * accepted T-2/T-3 transfer spec needs. A key whose action is not one of these
 * is either a legacy() key (which decomposes into nothing and says so) or a
 * mistake — there is no third option, and that is the point.
 */
enum PermissionVerb: string
{
    // read / write lifecycle
    case View = 'view';
    case Create = 'create';
    case Update = 'update';
    case Delete = 'delete';
    case Restore = 'restore';

    // document lifecycle
    case Post = 'post';
    case Cancel = 'cancel';
    case Reverse = 'reverse';
    case Void = 'void';
    case Correct = 'correct';
    case Complete = 'complete';
    case Close = 'close';

    // workflow
    case Request = 'request';
    case Submit = 'submit';
    case Approve = 'approve';
    case Reject = 'reject';
    case Confirm = 'confirm';
    case Convert = 'convert';

    // operations
    case Receive = 'receive';
    case Transfer = 'transfer';
    case Adjust = 'adjust';
    case Reconcile = 'reconcile';
    case Allocate = 'allocate';
    case Refund = 'refund';
    case Pay = 'pay';

    // exceptions and IO
    case Override = 'override';
    case Print = 'print';
    case Export = 'export';
    case Import = 'import';

    // administration
    case Assign = 'assign';
    case Operate = 'operate';
    case Manage = 'manage';

    /** Verbs that mutate. Drives the write half of the §4.4 ratchet and the §4.6 denial audit. */
    public function isWrite(): bool
    {
        return match ($this) {
            self::View, self::Print, self::Export => false,
            default => true,
        };
    }

    /**
     * Verbs that make a FINANCIAL FACT REAL. Drives SoD-1 (§4.7).
     *
     * `confirm` is here because it is what makes a purchase order a commitment
     * and an order a promise; omitting it would have made the SoD test silently
     * vacuous on the purchase-order group it was written for. `pay` is here
     * because paying an expense is the moment money leaves.
     */
    public function isFinanciallyDecisive(): bool
    {
        return match ($this) {
            self::Post, self::Reverse, self::Void, self::Approve,
            self::Confirm, self::Refund, self::Allocate, self::Pay => true,
            default => false,
        };
    }
}
~~~

## Task 2: `PermissionDefinition` and the `PermissionManifest` contract

**The key is derived, never typed.** `make()` computes `key = "{$resource}.{$verb->value}" . ($qualifier !== null ? "_{$qualifier}" : '')` and throws `InvalidPermissionKey` on a malformed resource or qualifier. **The key can never disagree with its parts**, which is the whole reason the constructor is private.

**`$module` is deliberately independent of the key prefix.** Today the UI groups by `explode('.', $name)[0]` on both sides (`apps/api/app/Modules/Identity/Presentation/Controllers/RoleController.php:320-324`; `apps/web/src/features/settings/RolesPage.tsx:37-42`), which puts `catalog.attributes.view` under a group called `catalog` and `inventory.transfers.close` under `inventory`. Grouping by **declared module** fixes both without renaming either key.

**`$behavesAs` is a STORED readonly property, not a constructor-local.** Rev 3 of the spec accepted it as an argument to `legacy()` and then read it from a classification method that had no access to it — the object literally could not answer `isFinanciallyDecisive()` for `payments.pay-supplier`, so SoD-1's own baseline rows were unclassifiable and the SoD test could not be written at all.

**Files:** `PermissionDefinition.php`, `InvalidPermissionKey.php`, `apps/api/app/Shared/Contracts/Authorization/PermissionManifest.php`, `apps/api/tests/Feature/Authorization/PermissionDefinitionTest.php`.

**Steps**

- [ ] **Step 1 — the value object.**

~~~php
<?php

declare(strict_types=1);

namespace App\Shared\Domain\Authorization;

/**
 * One declared permission. The KEY IS DERIVED from its parts and can therefore
 * never disagree with them — which is why the constructor is private.
 */
final readonly class PermissionDefinition
{
    /** Resource: kebab segments, optionally ONE nested dot segment. */
    private const RESOURCE_PATTERN = '/^[a-z0-9]+(-[a-z0-9]+)*(\.[a-z0-9]+(-[a-z0-9]+)*)?$/';

    /** Qualifier: snake_case only. */
    private const QUALIFIER_PATTERN = '/^[a-z0-9]+(_[a-z0-9]+)*$/';

    /**
     * @param  non-empty-string        $key             canonical key, e.g. 'purchase-orders.approve'
     * @param  non-empty-string        $module          owning module, e.g. 'Procurement' — drives UI grouping and the
     *                                                  module gate, and is NOT derived from the key prefix
     * @param  non-empty-string        $resource        kebab-case resource. Three nested resources are legitimate today:
     *                                                  catalog.attributes, inventory.transfers, purchase-hub.orders
     * @param  ?PermissionVerb         $verb            NULL for a legacy() key, which does not decompose
     * @param  ?PermissionVerb         $behavesAs       STORED. null for make(); set only by legacy(), for SoD classification
     * @param  ?non-empty-string       $qualifier       snake_case narrowing of the verb, e.g. 'above_threshold'
     * @param  non-empty-string        $labelKey        i18n stem, always 'permissions.actions.<action>'. Keyed by
     *                                                  module+action ONLY, so resources sharing a verb share one generic
     *                                                  label. Intentional: it is what RolesPage.tsx already does, and a
     *                                                  per-permission label would be 304 strings x 3 locales to say
     *                                                  "Create" 34 times. A resource needing distinct wording carries a
     *                                                  $qualifier, which produces its own action key.
     * @param  list<non-empty-string>  $templateDefaults  system-role template keys that receive this by default.
     *                                                    'admin' is IMPLICIT and MUST NOT be listed.
     * @param  ?non-empty-string       $sodGroup        separation-of-duties group (§4.7)
     * @param  non-empty-string        $introducedIn    release tag, e.g. '2026.09'
     * @param  ?non-empty-string       $replacedBy      successor key when $deprecated is true
     */
    private function __construct(
        public string $key,
        public string $module,
        public string $resource,
        public ?PermissionVerb $verb,
        public ?PermissionVerb $behavesAs,
        public ?string $qualifier,
        public string $labelKey,
        public string $descriptionKey,
        public array $templateDefaults,
        public ?string $sodGroup,
        public string $introducedIn,
        public bool $deprecated,
        public ?string $replacedBy,
        public bool $legacyAction,
    ) {}

    /**
     * @param  list<non-empty-string>  $templateDefaults
     */
    public static function make(
        string $module,
        string $resource,
        PermissionVerb $verb,
        ?string $qualifier = null,
        array $templateDefaults = [],
        ?string $sodGroup = null,
        string $introducedIn = '2026.09',
    ): self {
        if (preg_match(self::RESOURCE_PATTERN, $resource) !== 1) {
            throw new InvalidPermissionKey("resource '{$resource}' is not kebab-case with at most one nested segment.");
        }
        if ($qualifier !== null && preg_match(self::QUALIFIER_PATTERN, $qualifier) !== 1) {
            throw new InvalidPermissionKey("qualifier '{$qualifier}' is not snake_case.");
        }
        if (in_array('admin', $templateDefaults, true)) {
            throw new InvalidPermissionKey("'admin' is implicit and must not appear in templateDefaults for '{$resource}'.");
        }

        $action = $verb->value.($qualifier !== null ? '_'.$qualifier : '');

        return new self(
            key: $resource.'.'.$action,
            module: $module,
            resource: $resource,
            verb: $verb,
            behavesAs: null,   // a decomposing key needs no shadow verb and MUST NOT carry one
            qualifier: $qualifier,
            labelKey: 'permissions.actions.'.$action,
            descriptionKey: 'permissions.descriptions.'.$action,
            templateDefaults: array_values($templateDefaults),
            sodGroup: $sodGroup,
            introducedIn: $introducedIn,
            deprecated: false,
            replacedBy: null,
            legacyAction: false,
        );
    }

    /**
     * Escape hatch for the pre-existing keys that do not decompose into
     * verb[_qualifier] — 'batches.traceability', 'pricing.sell_below_cost',
     * 'reports.operational'. Every call is counted against a SHRINK-ONLY
     * baseline (LEGACY_ACTION_CEILING); a NEW module may not use it at all,
     * because the baseline is keyed by permission key and a key absent from it
     * is growth regardless of the ceiling.
     *
     * @param  list<non-empty-string>  $templateDefaults
     * @param  ?PermissionVerb         $behavesAs  SoD classification only; REQUIRED when $sodGroup is set
     */
    public static function legacy(
        string $key,
        string $module,
        array $templateDefaults = [],
        ?string $sodGroup = null,
        string $introducedIn = '2026.09',
        ?PermissionVerb $behavesAs = null,
    ): self {
        $dot = strpos($key, '.');
        if ($dot === false) {
            throw new InvalidPermissionKey("legacy key '{$key}' has no resource segment.");
        }
        if (in_array('admin', $templateDefaults, true)) {
            throw new InvalidPermissionKey("'admin' is implicit and must not appear in templateDefaults for '{$key}'.");
        }

        $resource = substr($key, 0, $dot);
        $action = substr($key, $dot + 1);

        return new self(
            key: $key,
            module: $module,
            resource: $resource,
            verb: null,        // a key like batches.traceability genuinely HAS no verb from the closed enum
            behavesAs: $behavesAs,
            qualifier: null,
            labelKey: 'permissions.actions.'.$action,
            descriptionKey: 'permissions.descriptions.'.$action,
            templateDefaults: array_values($templateDefaults),
            sodGroup: $sodGroup,
            introducedIn: $introducedIn,
            deprecated: false,
            replacedBy: null,
            legacyAction: true,
        );
    }

    public static function deprecate(self $definition, ?string $replacedBy): self
    {
        return new self(
            key: $definition->key,
            module: $definition->module,
            resource: $definition->resource,
            verb: $definition->verb,
            behavesAs: $definition->behavesAs,
            qualifier: $definition->qualifier,
            labelKey: $definition->labelKey,
            descriptionKey: $definition->descriptionKey,
            // A deprecated key leaves EVERY template. Step 6's exact diff then
            // revokes it from every uncustomised template-linked role.
            templateDefaults: [],
            sodGroup: $definition->sodGroup,
            introducedIn: $definition->introducedIn,
            deprecated: true,
            replacedBy: $replacedBy,
            legacyAction: $definition->legacyAction,
        );
    }

    /** verb + optional '_' . qualifier, or the legacy suffix. */
    public function action(): string
    {
        if ($this->verb === null) {
            $dot = strpos($this->key, '.');

            return $dot === false ? $this->key : substr($this->key, $dot + 1);
        }

        return $this->verb->value.($this->qualifier !== null ? '_'.$this->qualifier : '');
    }

    /** Reads the STORED pair — this is why $behavesAs is a constructor property. */
    public function isFinanciallyDecisive(): bool
    {
        return ($this->verb ?? $this->behavesAs)?->isFinanciallyDecisive() === true;
    }

    /** The create-class half of SoD-1, on the same stored pair. */
    public function isCreateClass(): bool
    {
        return ($this->verb ?? $this->behavesAs) === PermissionVerb::Create;
    }

    public function isWrite(): bool
    {
        return ($this->verb ?? $this->behavesAs)?->isWrite() === true;
    }
}
~~~

## Task 3: `PermissionRegistry`, the tagging wiring, and the consistency test

**Tagging, not a hard-coded array.** Each module's existing service provider contributes its manifest with **one line in that module**:
```php
$this->app->tag([ProcurementPermissionManifest::class], 'permission.manifests');
```
and the registry resolves `$app->tagged('permission.manifests')`. That is the automatic-inclusion guarantee (§3.3) at the wiring level. `PermissionRegistryCoverageTest` asserts that **every** directory under `app/Modules/` owning at least one key in the parity baseline has a tagged manifest — so deleting the tag line fails CI rather than silently dropping a module's permissions.

~~~php
<?php

declare(strict_types=1);

namespace App\Shared\Domain\Authorization;

use App\Shared\Contracts\Authorization\PermissionManifest;

final class PermissionRegistry
{
    /** @var list<PermissionDefinition>|null */
    private ?array $definitions = null;

    /** @param list<PermissionManifest> $manifests */
    public function __construct(private readonly array $manifests) {}

    /** Ordered by module, then resource, then action — DETERMINISTIC. @return list<PermissionDefinition> */
    public function definitions(): array
    {
        if ($this->definitions !== null) {
            return $this->definitions;
        }

        $all = [];
        foreach ($this->manifests as $manifest) {
            foreach ($manifest->definitions() as $definition) {
                if ($definition->module !== $manifest->module()) {
                    throw new InvalidPermissionCatalogue(sprintf(
                        "definition '%s' declares module '%s' but lives in %s's manifest.",
                        $definition->key,
                        $definition->module,
                        $manifest->module(),
                    ));
                }
                $all[] = $definition;
            }
        }

        usort($all, static fn (PermissionDefinition $a, PermissionDefinition $b): int => [$a->module, $a->resource, $a->action()] <=> [$b->module, $b->resource, $b->action()]);

        return $this->definitions = $all;
    }

    /** Includes deprecated keys. @return list<non-empty-string> */
    public function keys(): array
    {
        return array_values(array_map(static fn (PermissionDefinition $d): string => $d->key, $this->definitions()));
    }

    /** Excludes deprecated. @return list<non-empty-string> */
    public function activeKeys(): array
    {
        return array_values(array_map(
            static fn (PermissionDefinition $d): string => $d->key,
            array_filter($this->definitions(), static fn (PermissionDefinition $d): bool => ! $d->deprecated),
        ));
    }

    public function get(string $key): ?PermissionDefinition
    {
        foreach ($this->definitions() as $definition) {
            if ($definition->key === $key) {
                return $definition;
            }
        }

        return null;
    }

    /** @return array<non-empty-string, list<non-empty-string>> module => keys */
    public function byModule(): array
    {
        $grouped = [];
        foreach ($this->definitions() as $definition) {
            $grouped[$definition->module][] = $definition->key;
        }

        return $grouped;
    }

    /**
     * templateKey => keys. 'admin' is activeKeys() by construction; every other
     * template is the union of the definitions naming it.
     *
     * @return array<non-empty-string, list<non-empty-string>>
     */
    public function templateGrants(): array
    {
        $grants = ['admin' => $this->activeKeys()];
        foreach ($this->definitions() as $definition) {
            if ($definition->deprecated) {
                continue;   // a deprecated key leaves every template
            }
            foreach ($definition->templateDefaults as $template) {
                $grants[$template][] = $definition->key;
            }
        }
        foreach ($grants as $template => $keys) {
            $unique = array_values(array_unique($keys));
            sort($unique);
            $grants[$template] = $unique;
        }

        return $grants;
    }

    /** @return array<non-empty-string, list<non-empty-string>> sodGroup => keys */
    public function sodGroups(): array
    {
        $groups = [];
        foreach ($this->definitions() as $definition) {
            if ($definition->sodGroup !== null) {
                $groups[$definition->sodGroup][] = $definition->key;
            }
        }

        return $groups;
    }

    /** The registry's catalogue version — bumped by the release process, asserted non-decreasing. */
    public function version(): int
    {
        return (int) config('permission_catalogue.version', 1);
    }

    /** @throws InvalidPermissionCatalogue on any §4.2.2 violation. */
    public function validate(): void
    {
        $seen = [];
        foreach ($this->definitions() as $definition) {
            if (isset($seen[$definition->key])) {
                throw new InvalidPermissionCatalogue("duplicate permission key '{$definition->key}'.");
            }
            $seen[$definition->key] = true;
            if ($definition->deprecated && $definition->templateDefaults !== []) {
                throw new InvalidPermissionCatalogue("deprecated key '{$definition->key}' still names templateDefaults.");
            }
            if ($definition->sodGroup !== null && $definition->verb === null && $definition->behavesAs === null) {
                throw new InvalidPermissionCatalogue("legacy key '{$definition->key}' joins SoD group '{$definition->sodGroup}' without declaring behavesAs.");
            }
        }
    }
}
~~~

## Task 7: the `roles` schema migration

**Timestamped after `2026_09_06_205000`**, and it must **not** write `tenant_id` — the W-LOT CHECK's `tenant_id IS NOT NULL` clause interacts with a NULL-team legacy role.

| Column | Type | Null | Default |
|---|---|---|---|
| `is_system` | `boolean` | NO | `false` |
| `template_key` | `varchar(64)` | YES | `NULL` |
| `template_version` | `integer` | YES | `NULL` |
| `customised_at` | `timestamptz` | YES | `NULL` |

**Two partial uniques, because one index cannot express both topologies.**
- `roles_tenant_template_key_unique ON roles (tenant_id, template_key) WHERE template_key IS NOT NULL` — *"at most one role per template **per tenant**"*, the real invariant in both topologies and the only one that holds in compatibility mode, where every tenant's roles share one physical table and two tenant-scoped `manager` rows are legal today (the existing Spatie unique is `(tenant_id, name, guard_name)`).
- `roles_global_template_key_unique ON roles (template_key) WHERE template_key IS NOT NULL AND tenant_id IS NULL` — the NULL-team half. PostgreSQL treats every NULL as distinct, so the first index alone would permit two adopted NULL-team `manager` rows; this second one forbids exactly that without touching the tenant-scoped rows.

**Three CHECKs** (PG, with SQLite triggers, following the pattern the lane established): `template_key IS NULL OR is_system`; `customised_at IS NULL OR is_system`; `template_version IS NULL OR template_key IS NOT NULL`. The third exists because the pair without it permits `template_version = 7, template_key = NULL, is_system = false` — a state that contradicts the column's own meaning. Normal sync never creates it; a CHECK that permits a meaningless state is one that will eventually be handed one.

**No value CHECK on `template_key`, and that is a decision, not an omission.** The eight-case list is expected to grow — a future vertical may ship a ninth template — and a value CHECK would make that growth a tenant migration on **every** database rather than an enum edit plus a sync, which is the whole point of Direction B. Validity is enforced where the value is written (`SystemRoleTemplate` is the only source of a `template_key` in production code; sync writes `$case->value` and never a string) plus a **schema-level ratchet test**, `RoleTemplateKeyDomainTest`, asserting over a live tenant database that `SELECT DISTINCT template_key FROM roles WHERE template_key IS NOT NULL` is a subset of `SystemRoleTemplate::cases()`.

**`down()` REFUSES while any row has `template_key IS NOT NULL`**, mirroring the lane's `down()` contract — so a rollback after a sync is a deliberate act that first requires clearing adoption, and never silently discards which roles were system roles.

## Task 8: `RoleMarkerRepository` and `TemplateDeltaApplier`

**The marker predicate is `private` on the lane's seeder** (`RolesAndPermissionsSeeder::markedTenantCarriesWlota1aDelta()`) and therefore uncallable. namespace App\Modules\Identity\Infrastructure\Repositories;

~~~php
use Illuminate\Support\Facades\Schema;
use Spatie\Permission\Models\Role;
~~~

**`TemplateDeltaApplier` is the ONE implementation of "apply a template to a role", with two callers** — sync's step 6 and `RoleController`'s *Re-apply template* action. That is what rev 2's deleted `syncRole()` was reaching for and what its signature could not deliver: `sync(string, bool)` and `syncRole(string, string, bool)` would have been two orderings of the same rules.

**It is an EXACT diff, not an add-plus-deprecation-sweep.** The role's grant set is made **equal** to the template's: every key the template declares and the role lacks is granted, **and every key the role holds that the template does not declare is revoked — deprecated or active.** That is safe **here and only here**: an *uncustomised* template-linked role is one whose grant set has never diverged from its template (`customised_at IS NULL` is written on adoption only when the role compared **equal** to v0, and is set to `now()` by the first operator edit), so by construction such a role *is* its template plus whatever sync itself put there, and every extra key is a key the platform added and has since retracted — never a tenant's choice.

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Domain\Authorization;

use App\Modules\Identity\Application\DTOs\TemplateDelta;
use Illuminate\Support\Facades\DB;
use Spatie\Permission\Models\Role;

/**
 * "Apply a template to a role", once, for two callers: PermissionSyncService's
 * step 6 and RoleController's Re-apply template action.
 *
 * CALLER OBLIGATION: this method assumes it is already inside a transaction
 * whose first statement was PermissionWriteLock::acquire(), and that $role was
 * read under FOR UPDATE ordered roles.name ASC, roles.id ASC. It does NOT take
 * the lock itself — a helper that took its own lock would let a caller believe
 * it was serialized when its OTHER reads were not.
 */
final readonly class TemplateDeltaApplier
{
    public function __construct(private PermissionRegistry $registry) {}

    public function applyTo(Role $role, int $registryVersion): TemplateDelta
    {
        $templateKey = $role->getAttribute('template_key');
        if (! is_string($templateKey) || $templateKey === '') {
            throw new \LogicException('TemplateDeltaApplier requires a template-linked role.');
        }

        /** @var list<string> $target */
        $target = $this->registry->templateGrants()[$templateKey] ?? [];
        /** @var list<string> $current */
        $current = $role->permissions()->toBase()->pluck('name')->all();

        $added = array_values(array_diff($target, $current));
        $removed = array_values(array_diff($current, $target));
        $from = $role->getAttribute('template_version');

        if ($added !== [] || $removed !== []) {
            // Set EQUALITY, in one call: syncPermissions replaces the pivot set.
            $role->syncPermissions($target);
        }

        DB::table('roles')->where('id', $role->getKey())->update(['template_version' => $registryVersion]);

        return new TemplateDelta(
            added: $added,
            removed: $removed,
            fromVersion: is_int($from) ? $from : null,
            toVersion: $registryVersion,
        );
    }
}
~~~

**One public method.** `sync(string $tenantId, bool $write): PermissionSyncResult`. There is no `syncRole()`: with the template-migration machinery retired there is no step 5 to run for one template, and the remaining single-role work is exactly the step-6 delta for one already-adopted role — which does not need a second public entry point, a second transaction shape, or a second set of counters.

**The team boundary is W-LOT-A-1a's, verbatim in shape**, and the lock is 0b's:

~~~php
$previousTeamId = $this->permissionRegistrar->getPermissionsTeamId();
$this->permissionRegistrar->setPermissionsTeamId($tenantId);
try {
    return DB::transaction(function () use ($tenantId, $write): PermissionSyncResult {
        $this->writeLock->acquire($tenantId);   // the SHARED PermissionWriteLock, 0b's
        // steps 1..9; step 6 SELECTs … FOR UPDATE by roles.name ASC, roles.id ASC
        // and re-reads customised_at and the grant set AFTER the lock is held
    });
} finally {
    $this->permissionRegistrar->setPermissionsTeamId($previousTeamId);
}
~~~

### The nine steps, in this order

1. **Rename.** For each `(from, to)` where a `permissions` row named `from` exists and none named `to` exists: `UPDATE permissions SET name = :to WHERE name = :from AND guard_name = 'sanctum'`. **In place** — the primary key never changes, so every `role_has_permissions` and `model_has_permissions` row survives untouched and **no grant is lost**. If **both** exist the run is `BLOCKED` with `reason=rename_target_exists` (a human must decide which grants win). If **neither** exists the entry is a no-op and is **reported as stale**, so the map can be trimmed. **A renamed key can never re-enter:** step 2 creates only `registry->keys()`, and `no_manifest_declares_a_rename_source_key` proves no manifest declares a `from`. There is **no** "renamed keys must not be re-created" exclusion list anywhere in this design, because there is no writer that could create one.
2. **Create.** `Permission::firstOrCreate(['name' => $key, 'guard_name' => 'sanctum'])` for every `registry->keys()`, **deprecated keys included** — a deprecated permission keeps its row for one release so a custom role referencing it does not break.
3. **Orphans.** A `permissions` row present in the database and absent from the registry is **reported, never deleted**. Deleting it would cascade its grants away, and a row can legitimately be a leftover from a tenant that has not yet received a deploy that removed a module. **This step writes nothing**, which is why it may sit before adoption. Its count is a **gauge**. `permissions:prune-orphans --confirm` is wave 3 and is a deliberate operator action.
4. **Adopt** — **the first step that touches `roles`, and it writes no grant.** For each **existing** role whose `name` matches a `SystemRoleTemplate` case (resolved with the NULL-team-tolerant predicate) **and whose `template_key IS NULL`**: compute its current grant set, compare through `LegacyRoleBaseline::matchesVersion0()`, and adopt with `is_system = true`, `template_key = <name>`, `template_version = 0`, and `customised_at = NULL` (equal) or `customised_at = now()` (different). Counted as `adopted_pristine` / `adopted_customised`, logged per role, listed in `--dry-run`. **Adoption is one-way and once**: a role that already carries a `template_key` is never re-classified. Roles whose name matches no template stay `is_system = false` and are never touched.

   > **`customised_at = now()` for the "different" branch is deliberately the CONSERVATIVE direction.** It can only ever *withhold* a delta from a tenant that had in fact not customised, which surfaces as a visible banner and a one-click *Re-apply template*. The opposite error — adopting a genuinely customised role as pristine and then silently re-granting what the tenant removed — is precisely I-20 in a new costume.

5. **Create missing template roles.** For each `SystemRoleTemplate` case with no resolvable role in this tenant, create it with `tenant_id = :tenantId`, `guard_name = 'sanctum'`, `is_system = true`, `template_key`, `template_version = <registry version>`, `customised_at = NULL`, and **no grants yet** — step 6 grants. Counted as `roles_created`. **`general_manager` is created here like any other template role, with one addition:** when `roleMarkers->tenantCarriesMarker('w-lot-a-1a')` is `false`, the insert **also** sets `provisioning_source = 'w-lot-a-1a'` and `marker_written` becomes 1. Every clause of the lane's CHECK holds by construction on this path — sync always sets a tenant id and always this name and guard — so the write cannot violate it, and the partial unique is satisfied because sync reaches this branch only when the tenant has no marked role.
6. **Template deltas — an EXACT diff on uncustomised template-linked roles.** For each **non-`admin`** template, through `TemplateDeltaApplier`: **lock and re-read first** (`FOR UPDATE`, `roles.name` ASC then `roles.id` ASC, then read `customised_at` and the grant set **from that locked read**); **skip** the role entirely if the re-read `customised_at IS NOT NULL` (counted in the `templates_skipped_customised` **gauge**, `template_version` left where it was, which is what lets the Roles UI say *"this role is 3 versions behind"*); otherwise make the grant set **equal** the template's; set `template_version`; emit one **`RoleSyncedV1`** per role whose grant set actually changed.
7. **Deprecation replacement grants** — **the one case in which sync writes a custom role.** For every deprecated definition naming a `replacedBy`, grant the successor to every role currently holding the deprecated key, **custom roles included**, and emit a `RoleSyncedV1` per affected role. A deprecation with `replacedBy: null` writes nothing anywhere. The reason it is not a carve-out: a deprecated key stops being granted by any template and will eventually be pruned, so a custom role not given the successor **loses the capability on prune day, silently**, which is exactly what D2 forbids.
8. **Admin.** The role whose `template_key = 'admin'` is set to exactly `registry->activeKeys()` with `syncPermissions()`. This is the one place a full replace is correct, and it is what replaces `Permission::all()` — after it, the catalogue is once again the boundary of what `admin` holds, and a stray row inserted out of band is no longer silently attached. Counted as `admin_changes`, **including removals**.
9. **Cache — AFTER commit.** `DB::afterCommit(fn () => $this->permissionRegistrar->forgetCachedPermissions())`, registered **inside** the transaction so it fires once the commit has landed, and it runs **while the permissions team id is still set to this tenant**, because the S-1 key scheme derives the cache namespace from it. A `finally` inside the transaction callback executes **before** Laravel commits, leaving a window in which another request rebuilds and re-caches the *old* snapshot which then outlives the commit — which is the defect this step's ordering exists to prevent.

### The result marker

```
PERMISSIONS-SYNC tenant=<uuid> mode=APPLY|DRY_RUN outcome=APPLIED|ALREADY_CURRENT|BLOCKED|FAILED
                 mutations: renamed=<n> created=<n> adopted_pristine=<n> adopted_customised=<n>
                            roles_created=<n> templates_applied=<n> templates_removed=<n>
                            replacements_granted=<n> admin_changes=<n> marker_written=<n>
                 gauges:    orphans=<n> templates_skipped_customised=<n>
                 reason=<token>
```

**Two kinds of number, and only one of them can be zero on a re-run.** The ten **`mutations`** counters are rows this run **wrote** — all zero, always, on a re-run. The two **`gauges`** are state this run **observed** — **unconstrained**; on a tenant with one customised `manager` and one orphan row, `orphans=1 templates_skipped_customised=1` is reported on **every** run forever, and that is not a failure. `outcome=ALREADY_CURRENT` is defined as *every `mutations` counter zero **AND** zero database writes*, so the marker's outcome token and its numbers cannot disagree.

**Why the second run is `ALREADY_CURRENT` — re-derived, not asserted.** **1** every `from` is gone and nothing re-created it → `renamed=0`; **2** every key exists → `created=0`; **3** the orphan set is a **read** and its count is a gauge; **4** every template-named role carries a `template_key` → `adopted_*=0`; **5** every case resolves → `roles_created=0`, `marker_written=0`; **6** every uncustomised template role already **equals** its template → `templates_applied=0`, `templates_removed=0`, while `templates_skipped_customised` reports the same non-zero number as the first run whenever the tenant has a customised role; **7** every role holding a deprecated key already holds its successor → `replacements_granted=0`; **8** `syncPermissions(activeKeys())` on a role that already equals that set writes no pivot row → `admin_changes=0`; **9** the flush is unconditional and is not a counter.

**Exit codes:** `0` applied or already-current, `1` failed (**nothing written** — the whole run is one transaction), `2` blocked (a rename collision, or compatibility mode with `--tenant`).

**Compatibility mode.** With `TENANCY_DB_PER_TENANT=false`, `permissions:sync` **refuses `--tenant`** (exit 2, `reason=compatibility_mode_is_global`) and runs **steps 1–4 only**, once globally, reporting `templates_applied=0 templates_removed=0 roles_created=0 marker_written=0`. **Adoption runs there too** — it is a DB-level classification of `roles` rows, not a template application, and skipping it would leave every system role at `is_system = false`, which is exactly the state wave 2's rename/delete protection and both floors depend on. **Step 5 in particular must NOT run there**: creating one tenant's `general_manager` in a shared `roles` table provisions it for everybody, and writing the marker there would additionally claim, falsely, that every tenant in the schema carries the lane's end state. This is **stated rather than silently degraded**, because a silent degrade is exactly how I-20 happened.

## Task 12: the `customised_at` writer and *Re-apply template*

**Why the writer cannot wait for wave 2.** Wave 1 already deploys and repeatedly runs sync, so during the soak the existing editor would keep calling `syncPermissions()` **without marking customisation**, and the next sync could add template grants to a role the tenant had just edited. The column and the writer that sets it **must not ship a wave apart**.

**The writer's transaction is the SAME transaction as its `syncPermissions()`, and it takes the shared lock.** Today `RoleController::update` resolves the role and later calls `syncPermissions()` with **no transaction and no lock at all**. The operator edit becomes, in one transaction: `PermissionWriteLock::acquire($tenantId)` → `SELECT … FOR UPDATE` the role (ordered `roles.name`, `roles.id`) → compute the audit diff → `syncPermissions()` → `customised_at = now()` → commit. The flag and the grant set it describes are then written **or rolled back together**, which is what lets step 6's post-lock re-read be trusted: there is no window in which the grants have changed and the flag has not.

**Set `customised_at = now()` only when a system role's permission set ACTUALLY CHANGES and `customised_at IS NULL`.** A no-op save must not mark a role customised — that would withhold every future delta from a tenant that changed nothing.

***Re-apply template* is a `RoleController` action over one role, not a sync mode.** In one transaction: (a) refuse unless the role is `is_system` **and** carries a `template_key`; (b) set `customised_at = NULL` **inside the lock**, so a sync cannot observe the half-state; (c) call `TemplateDeltaApplier::applyTo()`; (d) advance `template_version`; (e) emit the diff as `RoleSyncedV1` with `cause: 'template_reapply'` and a **non-null** `actorUserId`.

**Steps**

- [ ] **Step 1** — the `update` change and the re-apply action; both under 0b's lock, with the five obligations.
- [ ] **Step 2 — `PermissionWriteLockRaceTest` (EC-20a)**, two PG connections: operator edit versus sync. **The outcome contract, which is what a gate checks rather than the mechanism:** whichever order the two transactions serialize in, if the operator commits first, sync's post-lock re-read sees `customised_at IS NOT NULL` and **skips** the role into the `templates_skipped_customised` gauge; if sync commits first, it applies its delta to a then-pristine role and the operator's edit lands afterwards, setting `customised_at` on top. **There is no interleaving in which a write is lost, and none in which a role is left `customised_at IS NOT NULL` carrying a grant set the operator did not choose.**
- [ ] **Step 3 — `CustomisedAtWriterTest`**: a no-op save does **not** set the flag; a real change does; a second change does **not** move it (it records the **first** edit); a **custom** role is unaffected (it has no template to be customised against).

## Task 16: the static guards

### 16a — `ForbidPermissionStringLiteral` (PHPStan)

Flags **any** dotted lowercase string literal matching `^[a-z][a-z0-9-]*(\.[a-z][a-z0-9_.-]*)+$` when it appears as an argument to `->can()`, `->cant()`, `->hasPermissionTo()`, `->hasAnyPermission()`, `Gate::authorize()`, `Gate::allows()`, `Gate::denies()`, or inside a `->middleware([...])` / `middleware('can:…')` / `middleware('require.any.permission:…')` string.

**Two error classes, and the second is the important one.** Flagging only literals *already in* the registry lets the single most damaging mistake through: a typo such as `invoices.posst` is absent from the registry and would therefore **pass** — while at runtime Spatie swallows `PermissionDoesNotExist`, so the route **silently 403s for everyone including `admin`**.

| Literal | Verdict | Message |
|---|---|---|
| in the registry | **error**, use the enum | *"permission literal 'inventory.transfers.reconcile' — use `InventoryPermission::TransfersReconcile->value`."* |
| **not** in the registry | **error**, unknown key | *"unknown permission literal 'invoices.posst' — it is in no PermissionManifest, so this gate denies every caller including admin. Declare it, or fix the typo."* |

**Restricting the shape match to authorization CALL SITES** (rather than to any dotted string anywhere) is what keeps the rule free of false positives on config and i18n keys, so the registry lookup is no longer load-bearing for precision.

**Allowed call sites, encoded in the rule:** `app/Modules/*/Domain/Authorization/*PermissionManifest.php`, `app/Modules/*/Domain/Enums/*Permission.php`, `app/Shared/Domain/Authorization/*`, `database/seeders/RolesAndPermissionsSeeder.php` (the shim), `app/Console/Commands/SyncPermissions.php`, and everything under `tests/`.

**The ignore list is large, and that is the honest cost.** 608 route middleware strings and 309 call sites exist today, so the rule ships with a **generated shrink-only baseline**. What the baseline buys is that the **door closes behind** the existing sites: a *new* literal is an error on day one, and the list only shrinks (wave 3 empties it).

### 16b — `RoutePermissionLiteralTest` (AST, with constant-expression evaluation)

**PHPStan cannot see route files.** `apps/api/phpstan.neon:5-8` analyses `app/` only, so the rule reaches module `routes.php` under `app/Modules/*/Presentation/` but **not** the top-level `routes/` directory. Widening PHPStan's paths would pull unrelated files into level 8 and need its own baseline. So a companion architecture test parses every `app/Modules/*/Presentation/routes*.php` **and** every file under `routes/` with `nikic/php-parser` (already a PHPStan dependency), extracts each `can:` / `require.any.permission:` argument, and asserts every extracted key is in `activeKeys()`.

**It STATICALLY EVALUATES constant expressions and ACCEPTS them.** A guard that rejects the migration target is not a guard, it is a wall — and `'can:'.InventoryPermission::TransfersReconcile->value` is exactly the form this design prescribes:

| Expression in a route file | Handling |
|---|---|
| `'can:inventory.transfers.reconcile'` | plain `String_` — resolved, reported as a **literal** (use the enum) **and** checked against the registry |
| `'can:'.InventoryPermission::TransfersReconcile->value` | `Concat` of a `String_` and an enum-case `->value` — **evaluated and ACCEPTED**; the resolved key is checked against the registry |
| `implode(',', [Enum::A->value, Enum::B->value])`, or an array of such expressions inside `->middleware([...])` | **evaluated and ACCEPTED**, element by element, when every element is itself constant |

Resolution uses `nikic/php-parser`'s `ConstExprEvaluator` with an **enum-case fallback that reads the case's declared value from the module enum's own AST** — no autoloading, no reflection on a booted app, so the test stays a pure static walk. **Only a genuinely non-constant expression is reported** — a key built from a variable, a function call, a match arm on request data — with: *"route permission key at `<file>:<line>` is not statically resolvable; a route gate must be a constant expression so CI can verify it exists."* **There are zero such sites in the tree today.**

It is an **AST walk, not a grep**, so nothing is silently skipped: every extracted argument is either resolved and checked, or reported as non-constant.

**`permissions:sync` is additive**, so a rollback leaves extra `permissions` rows on every tenant. They are **inert** once no route and no template references them, and `permissions:prune-orphans` is **not** run as part of a rollback — it does not exist until wave 3, and it is a deliberate operator action even then.
