### Step 2.4 — Pre-warm payment config at terminal activation

**File:** `apps/pos/src/stores/terminalStore.ts` (verify; `seedOfflineHashChain` lives at `:83-110`).

**The bug (still present on dev):**
`seedOfflineHashChain` does the SQLite seed (terminal_state, Z-chain, image cache, scheduler start) but does NOT eagerly fetch payment config. The first call to `fetchPaymentConfig` happens lazily from `HomePage`'s `useEffect` once the cashier reaches the home screen. There's a small window where the cashier can interact with cart/checkout before payment config is loaded — Step 2.3's gate covers this, but Step 2.4 closes the window so the gate rarely triggers in practice.

**Fix contract:**
- After `scheduler.start()` (line ~106 post-T1.1), fire `void usePaymentStore.getState().fetchPaymentConfig()` (don't await — must NOT block the seed). The fire-and-forget pattern matches T0.5's scheduler hook.
- If `paymentConfig` already loaded in memory (e.g. from a prior session's `initialize()`), `fetchPaymentConfig` is idempotent — safe to call. Verify by reading `paymentStore.ts:331` (`fetchPaymentConfig` impl).
- The pre-warm runs from EVERY `seedOfflineHashChain` call site. Read all four (currently `:123, :140, :160, :191, :224` per kickoff Section 1's grep). Confirm that's the right behavior — yes: every terminal activation path benefits from pre-warm.

**Codex preempts:**
- **Race with `HomePage`'s lazy fetch.** `HomePage` calls `fetchPaymentConfig` on mount. If the pre-warm is still in flight when `HomePage` mounts, two concurrent `fetchPaymentConfig` calls race. Last-write-wins on identical data is safe (Phase-2 spec confirms). But verify: does `fetchPaymentConfig` have any side effect (e.g. SQLite write) that's NOT idempotent? Read the impl carefully.

### Step T0.5-residual — Equality-by-id skip-set in `paymentStore.refreshFromSQLite`

**File:** `apps/pos/src/stores/paymentStore.ts` (verify; `refreshFromSQLite` at `:680-705`).

**The bug (deferred from T0.5 round-1 Codex prompt 2.1 item 4):**
`refreshFromSQLite` calls `set({ paymentMethods: methods, paymentRepositories: repositories })` unconditionally on every 60 s tick. Zustand creates new array references even when contents are unchanged, so any subscriber that destructures `paymentMethods` or `paymentRepositories` re-renders 60 times per hour for no reason. `productStore.refreshFromSQLite` uses `diffProducts(...)` to skip set when unchanged; `paymentStore` does not.

**Fix contract:**
- Compute equality-by-id BEFORE the `set`. Compare each array's id-set against the current state's id-set.
- If BOTH `paymentMethods` AND `paymentRepositories` are unchanged-by-id, skip the `set` entirely. Do NOT do a deep-equal — id-equality is sufficient (Phase-2 spec wording: "skip set when arrays are equal-by-id").
- If only one changed, still do the atomic single-set (don't fire two separate `set` calls — that creates an intermediate state).
- Implementation idiom (verify against productStore's `diffProducts` for style):
  ```ts
  const current = get();
  const methodsUnchanged =
    current.paymentMethods.length === methods.length &&
    current.paymentMethods.every((m, i) => m.id === methods[i]?.id);
  const reposUnchanged =
    current.paymentRepositories.length === repositories.length &&
    current.paymentRepositories.every((r, i) => r.id === repositories[i]?.id);
  if (methodsUnchanged && reposUnchanged) return;
  set({ paymentMethods: methods, paymentRepositories: repositories });
  ```

**Codex preempts:**
- **Order sensitivity.** The id-equality check above is order-sensitive. If SQLite returns `[A, B]` once and `[B, A]` next (e.g. cursor ordering changed between syncs), a naive index-by-index compare would treat that as "changed" even though the set is equal. Two options:
  - (a) Sort both before comparing (overkill — `getAllPaymentMethods` already orders by `display_order`).
  - (b) Use Set semantics (`new Set(currentIds).size === currentIds.length` etc.). Cleaner.
  - **Recommended: option (b) using Set-equality.** Verify what `getAllPaymentMethods` actually orders by (`grep -n 'ORDER BY\|orderBy' apps/pos/src/lib/db/repositories/paymentMethodRepository.ts`); if the order is stable, option (a) suffices and is faster.
- **`is_active` toggle.** A method's `id` doesn't change when `is_active` flips, but the UI must re-render so the cash/card buttons update. **Equality-by-id is INSUFFICIENT — the skip-set must also detect `is_active` and other field changes.** Either widen the equality check to `id + is_active` OR fall back to a shallow per-row diff (compare every field). The Phase-2 spec wording said "equal-by-id" but the underlying intent is "no observable change" — surface to orchestrator if you think `is_active` warrants a wider check.
- **Test coverage.** A regression test must show that `set` is NOT called when both arrays are unchanged (use `vi.spyOn(zustand, 'setState')` or instrument via a subscriber count). Without this test, the perf optimization is untestable.
