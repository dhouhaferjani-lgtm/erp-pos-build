# Enrichment Image Persistence Plan Review

Adversarial read-only review against `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md`, the Rev 2 spec, and current code found **4 BLOCKER**, **12 MAJOR**, and **4 MINOR** findings. The highest-risk issues are a nonexistent relation in proposed production code, an SSRF fetcher that still buffers oversized bodies, DB tests that omit `RefreshDatabase`, and an end-to-end test that fakes away the only job that makes uploaded media visible.

## 1. Referenced Symbols, Signatures, FQCNs

- [BLOCKER] Proposed policy queries a nonexistent `asset` relation — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:942-948`; `apps/api/app/Modules/Media/Domain/Media/MediaAttachment.php:44-50`; `apps/api/app/Modules/Media/Infrastructure/Persistence/EloquentMediaAttachmentRepository.php:33-39` — the plan's `whereHas('asset', ...)` will fail because `MediaAttachment` exposes `mediaAsset()`, and current repository code consistently uses `mediaAsset`. Suggested fix: change the policy query to `whereHas('mediaAsset', ...)` and eager-load/reference `mediaAsset` everywhere.
- [MAJOR] Service provider paths are wrong — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:52`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:475`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1587-1588`; `apps/api/app/Modules/Product/ProductServiceProvider.php:5-16`; `apps/api/app/Modules/Media/MediaServiceProvider.php:5-19` — the plan names `app/Modules/Product/Providers/ProductServiceProvider.php` and `app/Modules/Media/Providers/MediaServiceProvider.php`, but the real providers are module-root classes. Suggested fix: patch/register commands and bindings in the real provider files/namespaces.
- [MAJOR] `RunEnrichmentCommand` filters a nonexistent product `vertical` column — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1665-1683`; `apps/api/database/migrations/tenant/2025_11_30_052910_create_products_table.php:16-40`; `apps/api/app/Modules/Product/Domain/Product.php:91-129`; `apps/api/app/Modules/Tenant/Domain/Tenant.php:57`, `apps/api/app/Modules/Tenant/Domain/Tenant.php:111`, `apps/api/app/Modules/Tenant/Domain/Tenant.php:128` — `vertical` lives on tenants, not products. Suggested fix: remove `Product::where('vertical', ...)`; derive the platform vertical from the initialized tenant or validate `--vertical` against tenant vertical.
- [MINOR] Current `uploadForProduct` has four parameters, so `sourceRef` calls depend on Task 2 landing first — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:206-210`; `apps/api/app/Modules/Media/Application/Services/MediaUploadService.php:217-231` — the proposed fifth arg is not present today; this is expected work, but any tests/tasks that call the fifth arg before Task 2 will fatal. Suggested fix: keep Task 2 as a hard dependency before persister tests.
- [MINOR] Demo verification references nonexistent `Product::primaryMedia` — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1889-1891`; `apps/api/app/Modules/Product/Domain/Product.php:211-437`; `apps/api/app/Modules/Catalog/Application/Queries/CatalogMediaQuery.php:35-72` — product media is resolved through `CatalogMediaQuery`, not a `primaryMedia` relation. Suggested fix: verify through `CatalogMediaQueryInterface::forProduct()` or the product/POS API payload.

## 2. SSRF-Safe Image Fetcher Design

- [BLOCKER] Size cap is enforced after full buffering, not while streaming — `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:59`, `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:146`; `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:670-686`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:726` — `stream => true` is set, but `$response->body()` reads the whole body before `strlen()` checks `MAX_BYTES`, so an oversized response can exhaust memory/disk before rejection. Suggested fix: use a real stream sink/progress callback or PSR stream loop that aborts once `MAX_BYTES + 1` is read.
- [MAJOR] Redirect handling contradicts the spec — `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:56`; `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:670-677`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:726` — `allow_redirects => false` is safe against redirect SSRF because redirects are denied, but it does not "re-run the full resolve->validate->pin on every redirect hop" or cap redirects. Suggested fix: either explicitly document "redirects are denied" as the chosen policy, or implement a manual redirect loop that re-guards each `Location`.
- [MAJOR] IP pinning is not tested by the proposed tests — `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:62`; `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:539-585`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:670-674`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:726` — every fetcher test uses `Http::fake()`, and the plan itself notes that this short-circuits before cURL applies `CURLOPT_RESOLVE`; Task 12 does not add the promised `CURLINFO_PRIMARY_IP`/`on_stats` assertion. Suggested fix: add a test seam around the HTTP client/options or an integration test that proves the connected peer IP equals the validated pinned IP.

## 3. Idempotency And Race Conditions

- [MAJOR] Checksum backstop misses same-bytes/different-URL concurrent uploads — `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:76`; `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1208-1215`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1287-1293` — the duplicate check runs before attach and only searches assets already attached to the product, so two workers uploading identical bytes under different URLs can both see no attached duplicate and then both attach. Suggested fix: serialize per product/checksum, or attach under a transaction/advisory lock and re-check attached assets before committing.
- [MAJOR] `attachIdempotentWithRole` swallows every `QueryException` — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1265-1271`; `apps/api/app/Modules/Media/Application/Services/MediaAttachmentService.php:57-78`; `apps/api/database/migrations/tenant/2026_06_12_100003_create_media_attachments_table.php:32-35` — not every `QueryException` means the new owner/asset unique index fired; it could be the one-primary index or another DB failure. Suggested fix: inspect SQLSTATE/index name and only no-op the intended owner/asset duplicate.

## 4. Migration Correctness

- [MAJOR] New owner/asset unique index can fail on existing duplicate data — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:291-297`; `apps/api/database/migrations/tenant/2026_06_12_100003_create_media_attachments_table.php:28-35`; `apps/api/app/Modules/Media/Application/Services/MediaAttachmentService.php:69-77` — current schema has only sort-order and one-primary indexes, while `attach()` blindly creates links; any historical duplicate `(tenant_id, owner_type, owner_id, media_asset_id)` rows will abort the migration. Suggested fix: add a preflight/dedupe migration step or fail-loud diagnostic query before creating the unique index.

## 5. Test Design Flaws

- [BLOCKER] Proposed DB tests omit `RefreshDatabase` — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:229-255`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1004-1072`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1348-1357`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1604-1620`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1753-1773`; `apps/api/tests/Feature/Modules/Catalog/Media/MediaUploadServiceTest.php:15-26`; `apps/api/phpunit.xml:41-42` — the snippets extend `TestCase` only, but the suite uses in-memory SQLite and existing DB tests opt into `RefreshDatabase`. Suggested fix: add `use RefreshDatabase;` and real tenant/company/product setup to every DB-backed test class.
- [MAJOR] Manual tenant migration command is incompatible with the test harness assumption — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:321-324`; `apps/api/phpunit.xml:41-46`; `apps/api/config/tenancy_resolver.php:30` — `php artisan migrate --database=tenant` outside PHPUnit will not populate the in-memory DB used by the test process, and default tests run with `TENANCY_DB_PER_TENANT=false`. Suggested fix: rely on `RefreshDatabase` for normal tests; only opt into db-per-tenant with explicit config and provisioning helpers.
- [BLOCKER] The E2E test fakes away the job that makes uploaded images visible — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1757-1771`; `apps/api/app/Modules/Media/Application/Services/MediaUploadService.php:155-159`; `apps/api/app/Modules/Media/Application/Jobs/GenerateRenditions.php:88-92`; `apps/api/app/Modules/Media/Infrastructure/Persistence/EloquentMediaAttachmentRepository.php:33-37` — uploaded images start as `UPLOADED`, `Bus::fake()` suppresses `GenerateRenditions`, and `CatalogMediaQuery` only returns `READY` assets, so `primary_image_url` remains null. Suggested fix: run `GenerateRenditions` inline, mark the asset `READY` intentionally in the fixture, or assert before/after visibility explicitly.
- [MAJOR] `Http::fake()` leaves cURL pinning and streamed caps untested — `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:136`, `docs/superpowers/specs/2026-07-08-enrichment-image-persistence-design.md:142`; `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:539-585`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:726` — the tests cover URL validation and response parsing, not `CURLOPT_RESOLVE`, connected peer IP, redirect hops, or incremental abort. Suggested fix: add a lower-level fake client/options assertion and at least one non-`Http::fake()` guarded integration.
- [MINOR] Queue-name assertions should use the queue fake used elsewhere — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1608-1618`; `apps/api/tests/Feature/Fiscal/RetryFiscalProjectionsCommandTest.php:128-152` — the plan uses `Bus::fake()` to assert `$j->queue`, while existing queue-name coverage uses `Queue::fake()`/`Queue::assertPushed()`. Suggested fix: use `Queue::fake()` for queue routing assertions and reserve `Bus::fake()` for command dispatch intent.
- [MINOR] Several test snippets call helpers that do not exist in `Tests\TestCase` — `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1456`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1523`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1609`, `docs/superpowers/plans/2026-07-08-enrichment-image-persistence.md:1762`; `apps/api/tests/TestCase.php:7-27` — implementer notes say to build them, but the provided snippets will fatal as written. Suggested fix: include concrete factory/setup helpers in the test classes or reference existing helpers by real name.
