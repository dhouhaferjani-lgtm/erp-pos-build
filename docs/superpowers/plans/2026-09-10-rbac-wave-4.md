# RBAC Wave 4 — the edge-case campaign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn spec §7's edge-case register from a table a reader agrees with into a **campaign that runs**. Every row gets an executable home in a named lane, every browser row gets a scripted Playwright scenario on the repo's own harness, and every row's outcome lands in one committed evidence document with a run id, an environment, a count and a timestamp. **Exit is the 2026-08-31 empirical-evidence rule satisfied for every row** — a row is done when a command was run and its output recorded, never when a reviewer read the expectation and nodded.

**Architecture:** Nothing is designed. Wave 4 is a **harness plus a ledger**. The harness is the one this repository already has (`scripts/campaign-onboarding.sh` → `pnpm --dir apps/web campaign:onboarding` → a Playwright config with serial legs and a `ledger.json`), extended with an RBAC campaign that follows the same shape: a fresh tenant, a **second company**, a **second `pos_enabled` location**, serial legs, a ledger, and — because this is an authorization campaign — a **deny assertion in every leg that has an allow assertion**. The ledger is what makes the exit checkable: promotion reads the ledger, not the exit code.

**Tech Stack:** PHPUnit 11 (PG + SQLite lanes) / Redis 7 / Vitest (`apps/web`, `apps/pos`) / Playwright (`apps/web/e2e`) / Laravel 12 / React 19 / Tauri 2.

**Spec:** `docs/superpowers/specs/2026-09-10-roles-permissions-catalogue-design.md` (rev 9, **ACCEPTED** — gate r9, register at `docs/superpowers/reviews/2026-09-10-rbac-spec-codex-gate-r9.md`). Wave 4's authoritative rows are **§7 in its entirety**, §6's wave-4 row, and §8's wave-4 row.

**Master plan:** `docs/superpowers/plans/2026-09-10-rbac-programme-execution-plan.md` — §2 "Wave 4". Its exit checklist is this plan's exit: *"a green campaign run **plus** a clean `tenant:census-day-one` — together the promotion precondition for the whole programme"*, and *"the campaign is re-run end to end on the same tenant, asserting the second pass creates no duplicate role, permission or membership row and that every counter in `permissions:sync-fleet` reports `ALREADY_CURRENT`"*.

## Decisions and open questions

Five. All are gaps this plan resolves; none is one of the spec's four OQs, all of which are settled or owner-owed by the time wave 4 runs.

### Q-w4-1 — the `Phase` ordinal

The programme's ordinals are 0a `0.1`, 0b `0.2`, wave 1 `0.3`, 2a `0.4`, 2b `0.5`, wave 3 `0.6`. **This plan implements `Phase 0.7.<task>`.** Phase 0 confirms it:
```
git -C /Users/houssamr/Projects/syneriva/apps/erp log dev --oneline --grep='^Phase 0\.' -60 | sed 's/.*\(Phase 0\.[0-9]*\)\..*/\1/' | sort -u
```
If an earlier wave took a different ordinal, take the next free one and record the shift.

### Q-w4-2 — the register is **58 rows** by the spec's count and **57 table rows** by grep

Spec §7's lead-in says *"Fifty-eight rows in rev 9"*. Enumerating the table's row ids mechanically at plan-writing time gives **57**:
```
awk 'NR>=2058 && NR<=2126' docs/superpowers/specs/2026-09-10-roles-permissions-catalogue-design.md \
  | grep -oE '^\| \*?\*?EC-[0-9]+[a-z]?' | tr -d '|* ' | sort -u | wc -l      # 57
```
The ids present are EC-1..EC-21 (with 4a, 4b, 9a, 9b, 9c, 15a, 16a, 18a, 20a, 20b, 20c, 21a, 21b), **EC-22 absent — withdrawn in rev 2 with its number retained**, then EC-23..EC-40 (with 32a, 32b, 32c, 32d, 37a, 37b).

**This plan implements the campaign against the enumerated ids, and Phase 0 reconciles the count before a single leg is written.** The likeliest explanations are that the spec's prose counts the retained-but-withdrawn EC-22, or that one row's id is formatted so the grep misses it. **Neither is assumed**: Phase 0 reads §7 and produces the authoritative id list into the evidence document's first column. **A campaign whose row count disagrees with its spec is a campaign nobody can audit**, so this is settled before, not during.

### Q-w4-3 — the campaign is a SECOND campaign, not legs appended to the onboarding one

`docs/qa/ONBOARDING-CAMPAIGN.md` is the fresh-tenant promotion gate, with legs L0a..L9 and its own known-red list; a red campaign blocks promotion and *"promotion reads the ledger, not the exit code"*.

**This plan implements a separate `scripts/campaign-rbac.sh` with its own config, ledger and runbook**, copying the onboarding campaign's shape verbatim. Three reasons: the onboarding campaign registers **one** tenant per run and is throttled (5 registrations per window per IP, ~576 migrations synchronously in-request, 20–60 s), so appending forty legs to it makes one run enormous and one red anywhere block both gates; its fixtures are **Tunisia/Parapharmacy-only** and this campaign needs a **second company and a second `pos_enabled` location**, which the onboarding fixtures do not create; and its known-red list is about product findings in the money path, which would drown an authorization finding.

**The bounded alternative** — one campaign, RBAC as legs L10+ — is a real option and costs less scaffolding; it is rejected because it couples two promotion gates whose failure modes are unrelated. **If the orchestrator prefers coupling, the edit is bounded**: move the ten browser legs into `apps/web/e2e/campaign/` as L10..L19, add their ledger definitions to the existing `journey.ts`, and drop `campaign-rbac.sh`. Nothing else changes.

### Q-w4-4 — the campaign's tenant is a **campaign tenant**, and there is no teardown

The onboarding campaign records this honestly and it applies identically here: **there is no teardown** — every run leaves its `tenant_<uuid>` database behind under db-per-tenant. `CAMPAIGN_KEEP_TENANT=1` only **prints** the credentials.

**This plan implements the same contract and states it in the runbook**: cleanup of accumulated campaign tenants is an **operator task** (`tenants:list` → delete the `rbac-campaign+…@test.otospex.dev` tenants), and the **push trigger stays INERT** — do not arm a push→dev trigger on a target you cannot clean. The bounded alternative — a teardown command — is genuinely useful and genuinely out of scope for a campaign wave; it is recorded as a residual.

### Q-w4-5 — which rows can be driven in a browser at all

Of the enumerated ids, only a minority have a **UI** that can express them. The rest are console, database-state or concurrency scenarios whose only honest home is a test lane.

**This plan implements the split by asking one question per row: *can an operator observe this in the product?*** If yes → a browser leg (and, where the underlying rule also needs a unit-level proof, **both**). If no → a lane test, and the evidence document records the **command and its output**, which is the same standard of proof. **What this plan refuses to do is invent a UI for a row so that it can be "campaigned"** — a screen that exists only to make an edge case observable is a second surface (convention 11) and a maintenance burden. The lane assignments below are the spec's own, with the browser column added.
