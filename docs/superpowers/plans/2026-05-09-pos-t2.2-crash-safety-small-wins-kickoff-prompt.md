### Step 5.1 — Move `scheduleDebouncedSync()` past `COMMIT`

**Files:**
- `apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts` (verify line range — Phase 5 spec cites `:88-91` but post-T1.3 merge may have shifted).
- `apps/pos/src/lib/offline/receiptService.ts` (verify line range — Phase 5 spec cites `:216-224`).

**The bug (verify on dev tip):**
`insertOfflineReceipt` calls `scheduleDebouncedSync()` from INSIDE the transaction (between `BEGIN` and `COMMIT`). The debounce window can fire and the scheduler can read SQLite before `COMMIT` durably persists. Under load (multiple receipts in quick succession + the OS deciding to defer fsync), the scheduler's first read may return N receipts when N+1 just landed in the in-flight transaction. The race is small in practice (debounce is typically tens of ms; SQLite COMMIT is usually <5 ms) but violates the ordering contract Phase 4 (T1.3) just stabilized.

**Fix contract:**
- Remove the `scheduleDebouncedSync()` call from inside `insertOfflineReceipt`. The repository function should be transactionally pure — DB work only, no side-effects on the scheduler.
- Move the call to `createOfflineReceipt` in `receiptService.ts`, *after* `db.execute('COMMIT')`. The service-layer wraps the repository's transactional unit and is the correct place to fire side-effects.
- **Audit every callsite of `insertOfflineReceipt`** to confirm `createOfflineReceipt` is the only caller that needs the trigger. If a different service-layer caller exists, add the call there too. Likely greps:
  ```bash
  grep -rn 'insertOfflineReceipt\b' apps/pos/src
  ```

**Codex preempts (T1.1+T1.2+T1.3 lessons — pre-empt aggressively):**
- **Caller audit must be exhaustive.** Phase 5 spec says "grep callsites of `insertOfflineReceipt`". Run the grep AND look at any test fixture that mocks the repository — those tests may have been asserting the in-transaction call as a contract; update them to assert the post-COMMIT call.
- **What if COMMIT throws?** If `db.execute('COMMIT')` fails (extremely rare — typically only on disk full or corruption), the receipt didn't durably persist. The fix should NOT call `scheduleDebouncedSync` after a failed COMMIT — wrap in a success-only branch. Otherwise the scheduler will tick, read empty, and the cashier will think the receipt synced when it didn't.
- **No new race introduced.** Moving the call past COMMIT means there's a window (post-COMMIT, pre-scheduleDebouncedSync) where another concurrent insert could race. SQLite's MVCC isn't an issue here (we're not reading), but the scheduler's debounce coalesces near-simultaneous calls anyway, so this is defensive-only.
- **Error logging.** If scheduler invocation throws (unlikely — it's just setTimeout), wrap in try/catch + `serializeErrorForLog` and don't propagate. The receipt is durably committed; a missing trigger just means the next interval-driven tick (~60 s) handles it.
