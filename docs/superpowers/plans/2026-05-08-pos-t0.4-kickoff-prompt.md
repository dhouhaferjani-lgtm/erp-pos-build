## Section 3 — T0.4 scope

### The bug (per Codex checkout audit + Opus sync audit)

When the server has advanced its hash chain past the client's local sequence (typically because a "failed" POST actually committed server-side and the client retried with a different idempotency key creating a duplicate receipt), the legacy code path treats this as a chain break and raises `ChainBreakAlert`. The cashier sees a persistent banner; the receipt loops in retry-failed state; subsequent receipts chain off a hash the server never accepted, amplifying the divergence with every sale.

### Critical analysis of the CURRENT post-T0.3 state — DO THIS FIRST

The previous session left an open question: **is T0.4 actually a new fix, or is the 'duplicate' branch on dev already correct and T0.4 is hardening + test coverage?**

Read `apps/pos/src/lib/sync/syncService.ts` around the `pushOfflineReceipts` function. The current shape:

- Line 266 (or nearby — verify): `if (resultItem.status === 'synced' || resultItem.status === 'duplicate')` — both treated identically (success path).
- Lines 281-306 (verify): if `terminal_last_hash` + `terminal_hash_sequence` present, call `advanceHashChain(db, terminal_id, server_last_hash, server_sequence)`. The catch block handles `FiscalRegressionError` (local AHEAD of server) by logging "reconcile skipped (local ahead)".
- Line 309 (verify): chain break ONLY raised when `resultItem.status === 'chain_broken'` OR `failed AND isChainBreakError(resultItem.error)`. `'duplicate'` does NOT trigger chainBreak.

So on the surface, the existing code MIGHT already handle the recovery for `status === 'duplicate'` correctly. Three load-bearing questions:

1. **Does the server actually populate `terminal_last_hash` + `terminal_hash_sequence` in a `'duplicate'` response?** If not, advanceHashChain is skipped and local stays at sequence N while server is at N+1 — silent divergence. This is the HIGH-RISK case T0.4 must verify.

2. **Does `advanceHashChain` correctly handle the case where local sequence < server sequence?** The catch handles local > server (FiscalRegressionError); the inverse is the T0.4 path. Read `advanceHashChain` in `apps/pos/src/lib/db/repositories/terminalStateRepository.ts` and confirm.

3. **What does the `'chain_broken'` server status mean operationally?** Is it raised when server is BEHIND local (FiscalRegressionError mirror), AHEAD of local (the T0.4 scenario but the audit's "broken in the field" framing), or for some other divergence? The current code at line 309 always increments retry_count + halts — that's the path T0.4 may need to soften.

The answer to these three questions determines T0.4's actual surface:

- **If the server reliably populates terminal_last_hash + terminal_hash_sequence on `'duplicate'`** AND **advanceHashChain handles local-behind-server cleanly**: T0.4 reduces to (a) explicit test coverage for the duplicate-with-server-advance path, (b) hardening the `'chain_broken'` branch to attempt reconcile before halting, (c) verifying the negative case (genuine chain break server-side) still raises alarm.
- **If the server does NOT populate those fields on `'duplicate'`**: T0.4 expands scope — the client needs a follow-up GET to fetch the existing receipt + its chain anchor. Backend coordination needed. Surface to orchestrator.
- **If advanceHashChain refuses to advance local sequence**: T0.4 needs to extend the helper or add a sibling `reconcileHashChainTo(db, terminalId, serverHash, serverSequence)` that allows local-behind-server advance. Carefully — the FiscalRegressionError guard exists for a reason.

**Your first concrete action after pre-flight is to write the EXPLORATORY test that probes the current behavior** (Section 5 below), not to write the implementation.

### Fix contract (T0.4 minimum-viable)

When the server returns `'duplicate'` status with `terminal_last_hash` + `terminal_hash_sequence` populated:
- Local hash chain advances to `(terminal_last_hash, terminal_hash_sequence)` if local is BEHIND server.
- Local receipt's `status` flips to `'synced'`.
- Local receipt's `server_receipt_id` populated from `resultItem.receipt_id`.
- No `chainBreak = true`, no entry in `errors[]`, no banner.

When the server returns `'chain_broken'` status:
- Attempt the same reconcile if `terminal_last_hash` is provided.
- If reconcile succeeds, treat as recovered: status='synced', no alert.
- If reconcile fails (genuine divergence, server BEHIND or fork), keep the existing alarm path.

When the server returns `'failed'` with a chain-break error message but no reconciliation data:
- Existing alarm path stands. T0.4 does NOT regress this.

## Section 4 — T0.3 integration (the architectural tie)

T0.3 merged the timeout-revert-to-pending contract: when `FetchTimeoutError` fires, the receipt status reverts to `'pending'` (not `'failed'`), no retry-count bump, no errors[] append. The next sync tick re-pushes via T0.2's stable idempotency key.

**T0.4's recovery path is the downstream consumer of this chain.** The end-to-end happy path for a transient timeout that actually committed server-side:

```
[Tauri POST] body sent + committed server-side, response dropped on wire
         ↓
[T0.3]   FetchTimeoutError thrown in fetchWithTimeout (Promise.race)
         ↓
[syncService catch] instanceof FetchTimeoutError branch:
         updateReceiptStatus(id, 'pending') + logSyncOperation 'success' "timeout — pending for retry" + continue
         ↓
[next sync tick]  pushOfflineReceipts re-runs; receipt is 'pending' again
         ↓
[T0.2]   processCash/Card/Advanced reuses pendingIdempotencyKey;
         createOfflineReceipt's early-return-existing branch returns the
         already-persisted SQLite row (no new INSERT, no UNIQUE collision)
         ↓
[apiPost] POST /pos/receipts/sync with the SAME idempotency_key as before
         ↓
[server]  Recognizes the key as the one whose response was previously dropped.
         Returns status='duplicate' with the existing receipt's terminal_last_hash + terminal_hash_sequence
         ↓
[T0.4]   pushOfflineReceipts duplicate-handling branch reconciles local
         to server's chain — local advances from N to N+1, no chain break
         alert, status='synced'.
```

**T0.4 is the last link in this chain.** Without T0.4, T0.3's timeout-revert-to-pending succeeds at unblocking the cashier UI but leaves a permanent local desync.
