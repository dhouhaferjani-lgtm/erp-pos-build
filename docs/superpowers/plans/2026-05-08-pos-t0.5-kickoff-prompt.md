### Critical pre-flight audit result — embedded inline (do NOT re-derive)

The previous session ran the load-bearing backend audit while authoring this kickoff. **The canonical pair is unambiguous: `/payment-methods` + `/payment-repositories` (the paymentApi.ts side).** The `/treasury/payment-methods` + `/treasury/payment-repositories` paths called by `syncService.ts:569-570` **DO NOT EXIST in the backend** — they 404, and `pullPaymentConfig`'s outer try/catch silently absorbs the failure (`syncService.ts:578-582` returns `false` and writes a sync_log error row).

The sync scheduler's pull leg has been a no-op for payment data. Any payment-method changes made on the platform side AFTER the cashier's last login will NOT propagate until the cashier re-logs in.

### Fix contract (T0.5 minimum-viable)

**Two changes, one PR:**

1. **Endpoint alignment.** Replace `syncService.ts:569-570`'s `/treasury/payment-methods` + `/treasury/payment-repositories` calls with `/payment-methods` + `/payment-repositories` (the canonical pair). This is a **bug fix** — the sync's pull leg was hitting 404; aligning fixes it.

2. **`paymentStore.refreshFromSQLite()` + scheduler hook.** Add a method on `paymentStore` analogous to `productStore.refreshFromSQLite()` (template at `apps/pos/src/stores/productStore.ts:161-175`). Wire it in `apps/pos/src/lib/sync/syncScheduler.ts` immediately after `useProductStore.getState().refreshFromSQLite()` (currently at line 77) so every successful sync tick rehydrates BOTH stores from SQLite.

The reference pattern from productStore (verbatim):

```ts

  try {
    const companyId = useAuthStore.getState().companyId;
```

**Note:** productStore's catch uses raw `console.error` with `error` reference — that's a T0.1 lapse (PII spread risk). T0.5's new `paymentStore.refreshFromSQLite` catch MUST use `serializeErrorForLog` per the T0.1 contract; do NOT propagate productStore's lapse. (Migrating productStore is OUT OF SCOPE for T0.5 — note as a follow-up TODO.)

The diff shape paymentStore needs:
- New action `refreshFromSQLite: () => Promise<void>` on `PaymentActions`.
- Implementation reads `getAllPaymentMethods(db)` + `getAllPaymentRepositories(db)` (both already exist in `apps/pos/src/lib/db/repositories/paymentRepository.ts` — verify line refs with `grep -n 'export async function getAll' apps/pos/src/lib/db/repositories/paymentRepository.ts`), then calls `set({ paymentMethods: ..., paymentRepositories: ... })` atomically.

- Wrap in try/catch using `serializeErrorForLog` for the error path.

The scheduler hook in `apps/pos/src/lib/sync/syncScheduler.ts:77` (currently):

### `apps/pos/src/stores/paymentStore.ts` (T0.2 — lifecycle gates)

```ts
export interface PaymentState {
  // ... pre-existing fields ...
  paymentMethods: PaymentMethod[];
  paymentRepositories: PaymentRepository[];
  pendingIdempotencyKey: string | null;  // T0.2 — in-memory only
  isProcessing: boolean;                  // T0.2 — concurrent-call gate
}
export interface PaymentActions {
  // ... pre-existing actions ...

  discardPendingSubmission: () => void;  // T0.2 narrow lifecycle reset

```

`discardPendingSubmission()` clears `pendingIdempotencyKey` ONLY — leaves print state intact. Already wired at `Header.handleSwitchOperator` + `holdStore.holdCurrentCart` + `CloseShiftModal.handleCloseShift`.

**Critical T0.5 lifecycle question:** if a sync tick fires DURING an in-flight checkout (paymentStore has `pendingIdempotencyKey` set + `isProcessing=true`), what happens when `refreshFromSQLite()` calls `set({ paymentMethods, paymentRepositories })`?

- Best case: the in-flight checkout completes against the OLD payment-method object (paymentStore's checkout flow reads `paymentMethods` once into a local at action-start), so the rehydrate is invisible.
- Risk case: if any in-flight checkout code reads `paymentMethods` AFTER the rehydrate window, it could observe a different `PaymentMethod` reference for the same id and break id-equality assumptions.

The scheduler currently fires `productStore.refreshFromSQLite()` mid-tick without checking `paymentStore.isProcessing` — that's a precedent. But productStore's data isn't read by the checkout flow; paymentStore's IS.

**Decision branch for T0.5:**
- **Option A (default):** `refreshFromSQLite()` is unconditional — same as productStore. Document the assumption that `paymentMethod.id` + `paymentRepository.id` are the load-bearing keys (not object reference) and that's already how the codebase reads them. Verify this by `grep -n 'paymentMethod === \|paymentMethods\[0\] === ' apps/pos/src/` before committing — if any `===` comparison on PaymentMethod *objects* exists, that's a callsite that breaks under rehydrate.
- **Option B (defensive):** `refreshFromSQLite()` short-circuits when `usePaymentStore.getState().isProcessing` is true. This avoids any in-flight risk but introduces a window where the cashier MIGHT see stale payment config if a checkout takes longer than a sync tick interval. Only choose this if Option A's grep finds an actual reference-equality callsite.

**Codex will probe this** — pick a side and document it. See Section 5.c.
