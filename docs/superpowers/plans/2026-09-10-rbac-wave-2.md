**Goal:** Make role management safe to operate — no tenant can lose its last admin, no `roles.manage` holder can empty the admin role, role reads are gated **and shaped**, every role mutation and every write-route denial lands on the audit chain with the acting principal and credential named — and make a service account a first-class principal whose MCP/API token can only ever **narrow**, never widen, its owner's permissions.

**Architecture:** One `users` table with two `principal_kind`s (convention 11 — a second `service_accounts` table would be a duplicate surface). The narrowing is enforced in exactly one place, `User::hasPermissionTo()`, which every permission-based idiom already routes through via Spatie's Gate callback — so 917 call sites inherit it with no edit; the eight **role-name** idioms that do not are converted in 2a and that conversion is a hard entry condition of token issuance in 2b. Status, tenant-claim and membership enforcement live in one middleware attached to the **global `api` group** (attachment, not merely priority), proven by a live-router coverage test with no allow-list. The last-admin rule is one domain service called by every writer, proven by a static census, and it takes its locks in a deterministic order.

**Tech Stack:** Laravel 12 / PHP 8.4 / Sanctum 4 / Spatie laravel-permission 6.25 / Stancl Tenancy 3.10 / PHPUnit 11 / PHPStan L8 / Pint / Redis 7 / React 19 / TanStack Query 5 / Vitest / Playwright.

## Decisions and open questions

Seven. Two are the spec's own **OQ-1** and **OQ-2**, both of which this wave **implements** and either of which the owner may still overrule; five are gaps this plan had to resolve, each with the default implemented and the bounded alternative.

### OQ-1 — do service accounts count toward the last-admin floor? **Implemented: NO.**

Spec §9.2's applied default, hard-coded here in three places: `LastAdminFloor`'s definition of *A* filters `principal_kind = human`; `LastAdminFloorTest::a_service_admin_does_not_satisfy_the_floor` (EC-4); and the glossary row Task 2a-1 does **not** touch (wave 3 owns the glossary sweep). **If the owner rules YES**, the bounded edit is exactly three: drop the `principal_kind = human` clause from *A*, delete EC-4's test method, re-word the Service-account glossary row. Nothing else moves. **Ask before merging 2b** — the floor is 2a's, but the `principal_kind` column it filters on is 2b's, so a YES ruling that arrives between the two merges costs one commit in 2b rather than a rework.

### OQ-2 — default TTL for a service-account token? **Implemented: service 365 d, human 90 d, POS 1 y unchanged.**

Spec §9.2's recommended default. Three facts make this a change to an existing policy, not a greenfield choice: `dev:apps/api/config/sanctum.php:43-53` sets a **global 30-day** expiration; `dev:apps/api/app/Providers/AppServiceProvider.php:201-219` makes a per-row `expires_at` **override** it; and POS terminal tokens already carry an explicit one-year `expires_at` (`dev:apps/api/app/Modules/Identity/Presentation/Controllers/AuthController.php:146-176,294-310`).

**All three are expressed as explicit per-row `expires_at` values and the global stays at 43 200 minutes**, so no existing token's lifetime changes retroactively and the override semantics already in `AppServiceProvider` keep working. **Human back-office tokens LENGTHEN, 30 → 90 days** — that is the half of this that is a real decision, and it is called out in the handback rather than buried in a constant. **If the owner rules differently**, the bounded edit is `TokenTtl`'s three constants plus `ServiceAccountTokenIssuanceTest`'s three assertions; the mechanism is unaffected. **There is no unlimited option on any of the three** — `IssueServiceAccountTokenRequest` rejects a null/absent `expires_at` by supplying the default, and rejects a value beyond the ceiling.

~~~php
/**
 * Floor F-2 — spec 4.6.3. The SOLE implementation; nine writers call it and
 * none re-implements it, because nine copies of a rule is how writer #5
 * (UserController::update's syncRoles) came to be missing for a whole revision.
 *
 * A = principals that are ALL of: principal_kind = human, status = active,
 *     holding the role whose template_key = 'admin', AND holding at least one
 *     ACTIVE user_company_memberships row.
 *
 * LOCK ORDER — inherited from wave 0b, NOT invented here (plan gate r1, B1-1
 * and cross-plan BLOCKER 1). Every assert* method MUST be called inside the
 * mutation's own transaction and takes its locks in exactly this sequence:
 *
 *   1. PermissionWriteLock::acquire($tenantId)   -- the SHARED advisory lock,
 *      key 'wlota1a:'.$tenantId, ALWAYS FIRST. pg_advisory_xact_lock is
 *      re-entrant within a transaction, so a caller that already holds it
 *      (RoleController::store/update/destroy/assignRole/removeRole are all
 *      wave 0b LOCKED_ENTRY_POINTS) is unaffected: the second take is free and
 *      the lock is released once, at commit. That is why this is unconditional
 *      rather than a branch that would have to be right at nine call sites.
 *   2. roles FOR UPDATE, ordered roles.name ASC then roles.id ASC -- wave 0b's
 *      order, over the admin-template role. A SECOND row order over `roles` is
 *      a deadlock rather than a race: for `manager` vs `general_manager` the
 *      name and id orders are opposite.
 *   3. users FOR UPDATE, ordered users.id ASC -- the floor's own candidate set.
 *   4. model_has_roles FOR UPDATE for those users, ordered (model_id, role_id).
 *      Rev 1 locked (3) and not (4), so a concurrent writer could detach the
 *      surviving admin's pivot between this read and the caller's write.
 *   5. Re-read A from committed state and decide.
 *
 * A floor that takes a different lock, or the same locks in a different order,
 * is not a stricter floor: it is a deadlock and an unserialised read.
 *
 * The `roles` lock at step 2 is SINGLE-ROW (one admin-template row), so wave 0b's
 * every_multi_row_roles_lock_uses_the_lane_row_order case does not demand an
 * order clause of it -- 0b rev 6 lists three multi-row locks and three single-row
 * exemptions, and this writer is new to both lists. The ORDER BY is written
 * anyway: a predicate that returns one row today returns two on a tenant that
 * carries BOTH a NULL-team legacy admin role and a tenant-scoped one, and an
 * unordered multi-row lock is exactly the deadlock the lane's order prevents.
 */
final readonly class LastAdminFloor
{
    public function __construct(
        private PermissionWriteLock $writeLock,
        private LastAdminFloorViolation $violationFactory,
    ) {}

    /** @throws LastAdminFloorViolation */
    public function assertRoleRemovalSurvives(User $target, string $roleName, string $tenantId): void
    {
        if (! $this->isAdminRole($roleName, $tenantId)) {
            return;
        }

        $this->assertPopulationSurvivesWithout($target, $tenantId, 'LAST_ADMIN_ROLE_REMOVAL');
    }

    /**
     * PATCH /users/{id} with a different `role` calls syncRoles(), which is a
     * WHOLESALE replacement: it removes the admin role without ever touching
     * removeRole(). Writer #5.
     *
     * @param  list<string>  $nextRoleNames
     * @throws LastAdminFloorViolation
     */
    public function assertRoleReplacementSurvives(User $target, array $nextRoleNames, string $tenantId): void
    {
        $adminRoleName = $this->adminRoleName($tenantId);

        if ($adminRoleName === null || in_array($adminRoleName, $nextRoleNames, true)) {
            return;   // the target keeps admin; the population cannot shrink
        }

        $this->assertPopulationSurvivesWithout($target, $tenantId, 'LAST_ADMIN_ROLE_REMOVAL');
    }

    /** @throws LastAdminFloorViolation */
    public function assertDeactivationSurvives(User $target, string $tenantId): void
    {
        $this->assertPopulationSurvivesWithout($target, $tenantId, 'LAST_ADMIN_DEACTIVATION');
    }

    /** @throws LastAdminFloorViolation */
    public function assertDeletionSurvives(User $target, string $tenantId): void
    {
        $this->assertPopulationSurvivesWithout($target, $tenantId, 'LAST_ADMIN_DELETION');
    }

    /**
     * Consumed by wave 2b's MembershipRevocationService. Removing a membership
     * only threatens the floor when it removes the principal's LAST active one
     * — the clause that makes A "principals who can actually get somewhere".
     *
     * @throws LastAdminFloorViolation
     */
    public function assertMembershipRemovalSurvives(User $target, string $companyId, string $tenantId): void
    {
        $remaining = DB::table('user_company_memberships')
            ->where('user_id', $target->id)
            ->where('company_id', '!=', $companyId)
            ->where('status', 'active')
            ->count();

        if ($remaining > 0) {
            return;
        }

        $this->assertPopulationSurvivesWithout($target, $tenantId, 'LAST_ADMIN_MEMBERSHIP_REMOVAL');
    }

    /** @throws LastAdminFloorViolationException */
    private function assertPopulationSurvivesWithout(User $target, string $tenantId, string $code): void
    {
        if (DB::transactionLevel() === 0) {
            throw new \LogicException(
                'LastAdminFloor must be called inside the mutation transaction — a floor evaluated '
                .'outside one is read against state the mutation has not yet taken locks on.',
            );
        }

        // STEP 1 — the SHARED lock, first, on wave 0b's key. Re-entrant, so a
        // caller that already holds it pays nothing.
        $this->writeLock->acquire($tenantId);

        // STEP 2 — the admin-template role row, in wave 0b's order.
        $adminRoleName = $this->lockAdminRole($tenantId);

        if ($adminRoleName === null) {
            // No admin-template role on this tenant: A is empty by definition and
            // every shrinking operation is refused. Fail closed and say why.
            throw $this->violationFactory->make($code);
        }

        // STEP 3 — the candidate users, id ASC. DETERMINISTIC: two concurrent
        // admins each removing the other take the same row locks in the same
        // sequence, so one blocks and re-evaluates against committed state (EC-19).
        $candidateIds = $this->candidateQuery($tenantId, $adminRoleName)
            ->orderBy('users.id')
            ->lockForUpdate()
            ->pluck('users.id')
            ->all();

        // STEP 4 — the pivots for those users, in a deterministic order. Without
        // this a concurrent writer can detach the surviving admin's role between
        // step 3 and the caller's own write.
        if ($candidateIds !== []) {
            DB::table('model_has_roles')
                ->whereIn('model_id', $candidateIds)
                ->where('model_type', $target->getMorphClass())
                ->orderBy('model_id')
                ->orderBy('role_id')
                ->lockForUpdate()
                ->get();
        }

        // STEP 5 — decide from the locked read.
        $survivors = array_values(array_filter(
            $candidateIds,
            static fn (string $id): bool => $id !== (string) $target->id,
        ));

        if ($survivors === []) {
            throw $this->violationFactory->make($code);
        }
    }

    /**
     * Locks the admin-template role in wave 0b's canonical order and returns its
     * name. The predicate is tenant-OR-NULL because the legacy NULL-team topology
     * can carry the row without a tenant_id, exactly as wave 1's sync resolves
     * roles (spec 4.3.0 clause 3).
     */
    private function lockAdminRole(string $tenantId): ?string
    {
        /** @var Role|null $role */
        $role = Role::query()
            ->where('template_key', 'admin')
            ->where(static fn (Builder $q): Builder => $q
                ->where('tenant_id', $tenantId)
                ->orWhereNull('tenant_id'))
            ->orderBy('name')          // wave 0b's order: roles.name ASC,
            ->orderBy('id')            //                  then roles.id ASC
            ->lockForUpdate()
            ->first();

        return $role?->name;
    }

    /**
     * A, as a query. OQ-1's applied default is the principal_kind clause: a
     * SERVICE principal does NOT count toward A, because a tenant whose only
     * administrator is a machine has nobody who can log in when the token is
     * lost, revoked or expired. Task 2a-0 landed the column, so this is a real
     * predicate and not a comment (Q-w2-4).
     *
     * @return Builder<User>
     */
    private function candidateQuery(string $tenantId, string $adminRoleName): Builder
    {
        /** @var Builder<User> $query */
        $query = User::query()
            ->select('users.id')
            ->where('users.tenant_id', $tenantId)
            ->where('users.principal_kind', PrincipalKind::Human->value)
            ->where('users.status', UserStatus::Active->value)
            ->whereExists(static fn ($q) => $q
                ->from('user_company_memberships')
                ->whereColumn('user_company_memberships.user_id', 'users.id')
                ->where('user_company_memberships.status', 'active'));

        return $query->whereHas('roles', static fn ($q) => $q->where('name', $adminRoleName));
    }

    private function isAdminRole(string $roleName, string $tenantId): bool
    {
        return $this->adminRoleName($tenantId) === $roleName;
    }

    /** The unlocked read, used ONLY by the two early-return predicates above. */
    private function adminRoleName(string $tenantId): ?string
    {
        /** @var Role|null $role */
        $role = Role::query()
            ->where('template_key', 'admin')
            ->where(static fn (Builder $q): Builder => $q
                ->where('tenant_id', $tenantId)
                ->orWhereNull('tenant_id'))
            ->orderBy('name')
            ->orderBy('id')
            ->value('name');

        return $role;
    }
}
~~~

      > **Why the two early-return predicates may read unlocked.** `assertRoleRemovalSurvives()` and `assertRoleReplacementSurvives()` call `adminRoleName()` **before** taking any lock, purely to answer *"is this operation even about the admin role?"*. A stale answer there can only be wrong in the direction of **doing more work** — it sends a non-admin operation into `assertPopulationSurvivesWithout()`, which then locks, re-reads and finds survivors. It can never skip the floor for an operation that *is* about the admin role, because the only way the admin-template role's **name** changes is `RoleController::update`, which Task 2a-1 refuses on `is_system`. The locked read inside `assertPopulationSurvivesWithout()` is the one the decision is made from.

      > **The two floors emit `RoleUpdateRefused`, not `AuthorizationDenied`.** Every refusal — F-2's five codes and F-1's one — dispatches `RoleUpdateRefused` with `role_id`, the `RoleUpdateRefusalReason` case, `principal_id` and `token_id`, which is EC-13's required stable event (spec §4.6.5). It is **not** a denial: the caller *is* authorized to reach the endpoint, so Task 2a-7's `authz.denied` rule must not fire, and `RoleUpdateRefusedTest` asserts a `RoleUpdateRefused` row lands **and** an `authz.denied` count of zero.

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Domain\Authorization;

/**
 * The ONE construction site for a floor refusal, so the 422 body is one shape
 * across nine call sites. Constructor-injected (CLAUDE.md rule 13); it dispatches
 * the audit event and returns the exception the caller throws, so a refusal can
 * never be audited without being raised or raised without being audited.
 */
final readonly class LastAdminFloorViolation
{
    /** @var array<string, RoleUpdateRefusalReason> */
    private const REASONS = [
        'LAST_ADMIN_ROLE_REMOVAL' => RoleUpdateRefusalReason::LastAdminRoleRemoval,
        'LAST_ADMIN_DEACTIVATION' => RoleUpdateRefusalReason::LastAdminDeactivation,
        'LAST_ADMIN_DELETION' => RoleUpdateRefusalReason::LastAdminDeletion,
        'LAST_ADMIN_MEMBERSHIP_REMOVAL' => RoleUpdateRefusalReason::LastAdminMembershipRemoval,
    ];

    public function __construct(
        private \Illuminate\Contracts\Events\Dispatcher $events,
        private \Illuminate\Contracts\Auth\Factory $auth,
        private CurrentAccessTokenId $tokenId,
    ) {}

    public function make(string $code, ?int $roleId = null): LastAdminFloorViolationException
    {
        $reason = self::REASONS[$code] ?? throw new \LogicException(
            "LastAdminFloor emitted an undeclared refusal code '{$code}' — add it to "
            .'RoleUpdateRefusalReason and to this map, so the audit chain carries a closed set.',
        );

        $this->events->dispatch(new RoleUpdateRefused(
            roleId: $roleId,
            reason: $reason,
            principalId: $this->auth->guard()->id() === null ? null : (string) $this->auth->guard()->id(),
            tokenId: $this->tokenId->current(),
            occurredAtIso: now()->toIso8601String(),
        ));

        return new LastAdminFloorViolationException($code, self::messageFor($reason));
    }

    private static function messageFor(RoleUpdateRefusalReason $reason): string
    {
        return match ($reason) {
            RoleUpdateRefusalReason::LastAdminRoleRemoval =>
                'This is the tenant\'s last active administrator. Grant the admin role to another '
                .'active user with a company membership before removing it from this one.',
            RoleUpdateRefusalReason::LastAdminDeactivation =>
                'This is the tenant\'s last active administrator and cannot be deactivated.',
            RoleUpdateRefusalReason::LastAdminDeletion =>
                'This is the tenant\'s last active administrator and cannot be deleted.',
            RoleUpdateRefusalReason::LastAdminMembershipRemoval =>
                'Removing this membership would leave the tenant with no administrator who has '
                .'access to any company.',
            default => throw new \LogicException('Unreachable: '.$reason->value),
        };
    }
}

/**
 * The thrown type. Rendered by the existing handler as 422 { code, message };
 * a controller may also catch it and return its own forbidden()-shaped 422. The
 * tests assert the CODE and the unchanged rows, never the rendering path.
 */
final class LastAdminFloorViolationException extends \RuntimeException
{
    public function __construct(
        public readonly string $errorCode,
        string $message,
    ) {
        parent::__construct($message);
    }
}
~~~

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Domain\Authorization;

use App\Modules\Identity\Application\DTOs\EffectivePermissionEntry;
use App\Modules\Identity\Application\DTOs\EffectivePermissionSet;
use App\Modules\Identity\Application\DTOs\TokenScopeData;
use App\Modules\Identity\Domain\User;
use App\Shared\Contracts\Authorization\EffectivePermissionResolverInterface;
use App\Shared\Domain\Authorization\PermissionRegistry;
use Laravel\Sanctum\PersonalAccessToken;

/**
 * Spec 4.1.3a (c). The ONE place that answers "what may this principal do",
 * with the two questions kept apart:
 *
 *   forSubject  -- owner grants INTERSECTED with the presented token's scope.
 *   forTarget   -- owner grants, optionally projected through ONE named token.
 *
 * It never authorizes. can: still does that, through User::hasPermissionTo(),
 * which is where the narrowing is ENFORCED (Global Constraints). This class is
 * the READ model over the same rule, and EffectivePermissionResolverTest
 * asserts the two agree key-for-key -- a read model that can disagree with the
 * enforcement point is worse than no read model.
 */
final readonly class EffectivePermissionResolver implements EffectivePermissionResolverInterface
{
    /** The one bridge between a catalogue key and a Sanctum ability string. */
    private const SCOPE_PREFIX = 'permission:';

    public function __construct(private PermissionRegistry $registry) {}

    public function forSubject(User $subject, ?PersonalAccessToken $token): EffectivePermissionSet
    {
        return $this->assemble($subject, $token);
    }

    public function forTarget(User $target, ?int $tokenId): EffectivePermissionSet
    {
        if ($tokenId === null) {
            return $this->assemble($target, null);
        }

        /** @var PersonalAccessToken|null $token */
        $token = $target->tokens()->whereKey($tokenId)->first();

        if ($token === null) {
            throw new TokenNotOwnedBySubject($tokenId, (string) $target->id);
        }

        return $this->assemble($target, $token);
    }

    /**
     * OWNER GRANTS -- deliberately the UNNARROWED set, read from the database
     * rather than from the request's subject.
     *
     * User::getAllPermissions() narrows only when the model IS the authenticated
     * subject carrying currentAccessToken() (dev:.../User.php:201-241). For
     * forTarget that model is NOT the authenticated subject, so the call returns
     * the full grants -- correct, and now correct BY DECLARATION. For forSubject
     * we must not let that accidental narrowing happen twice, so the owner set is
     * read through getUnfilteredPermissionsForSupportAccess() (dev:176-179), the
     * accessor that already means "grants before any token filter", and the
     * intersection below is the ONLY narrowing this class performs.
     *
     * @return array<string, list<string>>  permission key => role names granting it
     */
    private function ownerGrants(User $principal): array
    {
        $byKey = [];

        foreach ($principal->roles()->with('permissions')->get() as $role) {
            foreach ($role->permissions as $permission) {
                $byKey[$permission->name][] = $role->name;
            }
        }

        // D6: no direct principal->permission grants exist in this design. The
        // unfiltered accessor is nonetheless the oracle, so a future direct grant
        // cannot silently disappear from this panel: anything it returns that no
        // role explains is attributed to the principal itself.
        foreach ($principal->getUnfilteredPermissionsForSupportAccess() as $permission) {
            $byKey[$permission->name] ??= ['(direct grant)'];
        }

        foreach ($byKey as $key => $roles) {
            $byKey[$key] = array_values(array_unique($roles));
            sort($byKey[$key]);
        }

        ksort($byKey);

        return $byKey;
    }

    /**
     * PARSE the token's narrowing list.
     *
     * Returns null  -> the token does not narrow (no `permission:` ability at
     *                  all, or no token): the principal's full grants apply.
     * Returns list  -> the keys the scope names, INCLUDING ones the registry does
     *                  not know; splitting known from unknown is the caller's job
     *                  below, because "unknown" must be VISIBLE (rule 4) rather
     *                  than silently dropped here.
     *
     * `*` is NOT honoured: it is meaningful to Sanctum's tokenCan(), not to this
     * intersection. A token carrying BOTH `*` and a `permission:` ability is
     * rejected upstream by EnforceTokenScope with TOKEN_SCOPE_AMBIGUOUS (401), so
     * by the time this runs the combination cannot occur; we therefore ignore a
     * lone `*` rather than treating it as "everything", which would WIDEN.
     *
     * @return list<string>|null
     */
    private function scopeKeys(?PersonalAccessToken $token): ?array
    {
        if ($token === null) {
            return null;
        }

        /** @var list<string> $abilities */
        $abilities = $token->abilities ?? [];

        $keys = [];

        foreach ($abilities as $ability) {
            if (str_starts_with($ability, self::SCOPE_PREFIX)) {
                $keys[] = substr($ability, strlen(self::SCOPE_PREFIX));
            }
        }

        // No `permission:` ability => unscoped. An EMPTY list is impossible here
        // by construction (we would have returned null); a token whose scope
        // narrows to nothing is one carrying `permission:` abilities that name
        // only unknown keys, and that denies everything -- which is rule 2,
        // preserved rather than special-cased.
        return $keys === [] ? null : array_values(array_unique($keys));
    }

    private function assemble(User $principal, ?PersonalAccessToken $token): EffectivePermissionSet
    {
        $owner = $this->ownerGrants($principal);
        $scope = $this->scopeKeys($token);
        $known = $this->registry->keys();

        $granted = [];
        $unknown = [];

        if ($scope !== null) {
            foreach ($scope as $key) {
                if (! in_array($key, $known, true)) {
                    $unknown[] = $key;          // rule 4: dropped from the
                    continue;                    // intersection, but SURFACED

                if (array_key_exists($key, $owner)) {
                    $granted[] = $key;           // rule 1: NARROWING ONLY --
                }                                // a scope key the principal does
            }                                    // not hold grants nothing
        }

        $entries = [];

        foreach ($owner as $key => $grantedBy) {
            $definition = $this->registry->get($key);

            $entries[] = new EffectivePermissionEntry(
                key: $key,
                module: $definition?->module ?? '(retired)',
                granted_by: $grantedBy,
                in_token_scope: $scope === null || in_array($key, $granted, true),
            );
        }

        return new EffectivePermissionSet(
            principal: [
                'id' => (string) $principal->id,
                'kind' => $principal->principalKind()->value,
                'status' => $principal->status,
            ],
            roles: $principal->roles->map(static fn ($r): array => [
                'id' => $r->id,
                'name' => $r->name,
                'is_system' => (bool) $r->is_system,

                'template_version' => $r->template_version,
                'customised_at' => $r->customised_at?->toIso8601String(),
            ])->all(),
            permissions: $entries,
            token_scope: $token === null ? null : new TokenScopeData(
                token_id: (string) $token->id,
                token_name: (string) $token->name,
                granted: $granted,
                unknown: $unknown,
                expires_at: $token->expires_at?->toIso8601String(),
            ),
            company_scope: $principal->activeCompanyIds(),
            location_scope: $principal->allowedLocationIdsByCompany(),
            discount: $principal->discountLimits(),
        );
    }
~~~

~~~php
<?php

declare(strict_types=1);

namespace App\Modules\Identity\Infrastructure\Authorization;

use Illuminate\Contracts\Redis\Factory as RedisFactory;

/**
 * Spec 4.6.5's dedup/rate rule. TWO keys per (principal_id, permission, route_name):
 *
 *   authz:deny:lock:<hash>   emission lock, SET ... NX EX 300.
 *                            Acquired => "emit now". Not acquired => "suppress".
 *   authz:deny:count:<hash>  retained counter, INCR on every suppression, with a
 *                            ROLLING 24-HOUR TTL refreshed on each write so it
 *                            deliberately OUTLIVES the 5-minute lock.
 *
 * When the next emission wins the lock it ATOMICALLY reads and clears the counter
 * and carries its value as suppressed_count on the emitted event.
 */
final readonly class AuthorizationDenialRecorder
{
    private const LOCK_TTL_SECONDS = 300;
    private const COUNT_TTL_SECONDS = 86400;

    /**
     * GETDEL semantics with an explicit floor, executed as ONE Redis command.
     *
     * A MULTI/EXEC wrapping GET + DEL is an accepted equivalent (both are atomic
     * against other clients); Redis 6.2+ GETDEL is a third. The contract is ONE
     * ATOMIC OPERATION, not a particular spelling. Two round trips lose every
     * increment that lands between the GET and the DEL — under exactly the storm
     * this rule exists to describe — and always UNDERCOUNT, which is the failure
     * mode that makes an audit number untrustworthy.
     */
    private const READ_AND_CLEAR_LUA = <<<'LUA'
        local n = redis.call('GET', KEYS[1])
        if n == false then return 0 end
        redis.call('DEL', KEYS[1])
        return tonumber(n)
        LUA;

    public function __construct(private RedisFactory $redis) {}

    /** @return int|null suppressed_count when this call should EMIT; null when it should SUPPRESS */
    public function shouldEmit(string $principalId, string $permission, string $routeName): ?int
    {
        $hash = hash('sha256', $principalId.'|'.$permission.'|'.$routeName);
        $connection = $this->redis->connection();

        $acquired = $connection->set('authz:deny:lock:'.$hash, '1', 'EX', self::LOCK_TTL_SECONDS, 'NX');

        if (! $acquired) {
            $countKey = 'authz:deny:count:'.$hash;
            $connection->incr($countKey);
            $connection->expire($countKey, self::COUNT_TTL_SECONDS);   // ROLLING, refreshed each write

            return null;
        }

        /** @var int $suppressed */
        $suppressed = $connection->eval(self::READ_AND_CLEAR_LUA, 1, 'authz:deny:count:'.$hash);

        return $suppressed;
    }
}
~~~
