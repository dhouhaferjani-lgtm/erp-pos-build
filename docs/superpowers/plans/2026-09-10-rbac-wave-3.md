# RBAC Wave 3 — consistency sweep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One enforcement style everywhere, and every exception list emptied. Route middleware becomes the **only** action gate: the in-controller checks and the FormRequest-only gates move to `can:` / `require.any.permission:`, deleting ratchet baseline entries as they go. The POS legacy role ladder is removed now that `authority_stale` plus a permission payload can replace it. `MembershipRole` and Spatie roles stop being two vocabularies for one noun. And a per-role regression matrix asserts, for the first time, what each seeded role **cannot** do.

**Architecture:** Nothing new is designed. This wave is a **sweep with a ratchet**: each module's cluster is one commit, each commit lowers a ceiling, and the ceilings only fall. The one behavioural change is the POS ladder removal, which is gated behind a real offline test and a POS release. Everything else is a move of an existing check from one layer to another, proven by a per-route allow-and-deny assertion rather than by "it still compiles".

### Q-w3-3 — POS is 91 of the 127, and it is converted last, by controller

`Gate::authorize` in `apps/api/app/Modules/POS` is not one idiom in one place: at `dev:630afa86f` it appears in at least ten controllers (`AnalyticsController` ×8, `OrderController` ×9, `PosAuthController` ×5, `CashDrawerController` ×4, `KitchenDisplayController` ×4, and singles across the sync/replenishment/stock controllers). The POS also has the **most offline-sensitive** clients and the **most device-authored** contracts (CLAUDE.md rule 20).

**This plan implements POS last and splits it into one commit per controller**, each with its own allow/deny test and its own ceiling decrement, so a POS regression is revertable to a single controller rather than to "the POS". **The bounded alternative** — one POS commit — is rejected: 91 conversions in one diff is precisely the shape of change where a reviewer approves the pattern and misses the one route where the permission is subtly different.

### Q-w3-4 — the POS ladder removal needs `fetchDiscountPermissions` wired FIRST

Spec §4.10 item 4 says removing the ladder means *"the offline path must fall back to the last synced permission payload instead of to a role name"*. But the device's discount authority today has a **second** hole: `fetchDiscountPermissions` exists at `dev:apps/pos/src/api/discountApi.ts:14` and is **never called from the store** — `resolveOnlineDiscountPermissions` wraps the verify-pin response instead, so `pos_terminals.max_discount_percent` (the **terminal ceiling**) is ignored on the device. The recorded chain is `effective limit = min(terminal_limit, user_limit)`; only the user half is enforced client-side.

**This plan wires `fetchDiscountPermissions` (Task 3-3) BEFORE removing the ladder (Task 3-2 step POS-last).** The ordering is load-bearing: `operatorStore`'s ladder currently sets `can_discount: isAdmin` and `max_discount_percent: isAdmin ? 100 : null` (`dev:apps/pos/src/stores/operatorStore.ts:354-364`) — **deleting the ladder without a terminal-aware source would leave an admin's offline PIN setup with `can_discount: false` and no ceiling at all**, i.e. an admin who cannot discount. The bounded alternative — remove the ladder and accept the regression until a later POS release — is rejected; it is a visible till-side outage.

### Q-w3-5 — "after one release" is defined mechanically

Spec §8's wave-3 row says the 22 deprecated keys and `reports.view` are removed *"after one release"*. That is not a checkable condition as written.

**This plan implements it as three facts, all verifiable, all required:**
1. **Wave 1's deploy has been live in production for at least one full release cycle** — i.e. a **later, unrelated** production deploy has happened since it, so every tenant has been synced at least twice with the keys flagged deprecated.
2. **`php artisan permissions:report-dead` returns exactly the 22** on the current tree, scanning its four roots (`apps/api`, `apps/web/src`, `apps/pos/src`, and the generated map) under its two honesty rules — a hit in the **generated map alone** is not evidence of use, and a hit must be **permission-shaped** (`apps/pos/src/components/pos/TodaySalesPanel.tsx:308` is `t('reports.view')`, a translation key; counting it would keep a genuinely retired permission alive forever).
3. **A live-tenant orphan report** shows the keys are held by no **custom** role on any tenant — because sync's step 6 revokes them from uncustomised template roles but never from a custom one, and pruning a key a custom role holds silently removes a capability.

**If any of the three fails, Task 3-7 is DEFERRED and recorded as a residual** — not partially performed. Removing 21 of 22 is worse than removing none: it makes the set no longer authoritative. The bounded alternative — remove them now regardless — is rejected for exactly the reason the deprecation window exists.

### Q-w3-6 — the `Sidebar.permission` rename is `permission` → `moduleKey`, not the reverse

`dev:apps/web/src/components/organisms/Sidebar/Sidebar.tsx:110,120` declares `permission?: ModuleKey` on both the item and the group interfaces, and its own docblock at `:101` says *"`permission` — key into `MODULE_PERMISSIONS` (role gating)"*. The values in use are a mixture: `'services'`, `'purchases'`, `'dashboard'`, `'sales'` are `ModuleKey`s, while `'deliveries.view'` (`:170`), `'partners.view'`, `'goods-receipt.create-standalone'` (`:200`) and `'document-ingestions'` (`:201`) are **permission-shaped**, and `'nav.purchasesGroup'` / `'nav.purchaseOrders'` (`:187,196`) are neither.

**This plan implements the rename as `permission` → `moduleKey`, typed `ModuleKey`, and introduces a SECOND optional field `permission?: Permission`** typed against wave 1's generated union — so the mixed values separate into the two things they actually are, and the `nav.*` pseudo-keys become **explicit `MODULE_PERMISSIONS` entries** rather than strings that happen to resolve. Any value that is neither is a finding. **The bounded alternative** — rename the type instead of the field — is rejected: it would leave `'deliveries.view'` typed as a `ModuleKey`, which is the confusion, not the fix.

## Rollback

**Wave 3 has no migration and no destructive deploy step. Its rollback granularity is the per-module commit** — which is why the per-module commit boundary is a Global Constraint rather than a style preference.

| Revert | Effect | Must also revert |
|---|---|---|
| Task 3-9 (matrix) | the regression matrix disappears; nothing else changes | — |
| Task 3-8 (sidebar / marketplace) | `permission?: ModuleKey` returns; `marketplace.admin` returns to the tenant guard | — |
| Task 3-7 (key retirement) | the 22 keys return to the registry — **but the rows are already gone** if the prune was run | **re-run `permissions:sync-fleet`** to recreate the rows; a registry key with no row is a fail-closed 403 for everyone |
| Task 3-6 step 4 (prune command) | the command disappears; rows already deleted stay deleted | — |
| Task 3-6 step 3 (seeder shims) | the exporter's input returns to the statics | the statics must be restored **in the same revert commit**, or the exporter calls methods that do not exist |
| Task 3-6 step 2 (`LotActionPermissionDelta`) | the dead class returns; **no behavioural change either way** — sync never called it | — |
| Task 3-6 step 1 (literal baseline) | the PHPStan rule stops hard-failing | — |
| Task 3-5 (glossary) | documentation only | — |
| Task 3-4 (`MembershipRole` / enums) | `isOwner()` returns as an authz read; `SystemRoleName` returns | its callers, re-pointed in the same revert |
| **Task 3-3 (POS ladder)** | the ladder returns and the terminal ceiling is ignored again | **revert as a POS release**, and only as a whole: reverting the ladder deletion without reverting the `fetchDiscountPermissions` wiring leaves two authority sources, which is worse than either |
| **Task 3-2 (POS sweep)** | per controller — each is its own commit | each controller's ceiling decrement in the same revert |
| **Task 3-1 (non-POS sweep)** | per cluster — each is its own commit | each cluster's ceiling decrement and baseline entries in the same revert |

**A partial revert must restore its ceiling and its baseline entries in the SAME commit.** A reverted conversion whose baseline entry stays deleted makes the ratchet's **stale** direction fail on the next run, and a reverted conversion whose ceiling stays lowered makes the **anti-growth** direction fail — either way the build goes red for a reason that has nothing to do with the revert's intent, and someone "fixes" it by raising a ceiling. That is the failure this note exists to prevent.
