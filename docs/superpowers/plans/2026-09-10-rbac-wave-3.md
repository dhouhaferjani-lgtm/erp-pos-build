**Goal:** One enforcement style everywhere, and every exception list emptied. Route middleware becomes the **only** action gate: the in-controller checks and the FormRequest-only gates move to `can:` / `require.any.permission:`, deleting ratchet baseline entries as they go. The POS legacy role ladder is removed now that `authority_stale` plus a permission payload can replace it. `MembershipRole` and Spatie roles stop being two vocabularies for one noun. **Architecture:** Nothing new is designed. This wave is a **sweep with a ratchet**: each module's cluster is one commit, each commit lowers a ceiling, and the ceilings only fall. The one behavioural change is the POS ladder removal, which is gated behind a real offline test and a POS release. Everything else is a move of an existing check from one layer to another, proven by a per-route allow-and-deny assertion rather than by "it still compiles".

## Task 3-9: the per-role regression matrix

**Files:** `apps/api/tests/Feature/Authorization/RolePermissionMatrixTest.php`, `apps/api/tests/Feature/Authorization/matrix/README.md`

**Why it is last, and why it is the wave's real deliverable.** Today's `dev:apps/api/tests/Feature/Identity/RBACTest.php` acts as `admin` throughout: it proves an **allow** path and nothing else. After a sweep that moved 176 authorization checks between layers, the question a reviewer cannot answer by reading is *"does each seeded role still deny exactly what it denied before?"* — and only a matrix answers it.

**Steps**

**The registry decides the EXPECTATION. It cannot manufacture the REQUEST.** `PermissionRegistry::templateGrants()` maps a role to the keys it holds, so for a given (role, route) pair it says *"expect 2xx"* or *"expect 403"*. It does **not** know that `PATCH /work-orders/{id}` needs a work order in a particular state, that `{id}` must be a real UUID, or what a body that would have succeeded looks like. Without those, a "deny" cell cannot be distinguished from a 404 on a fabricated id, a 422 from validation, or a domain refusal — and an 8 × ~800 grid of indistinguishable failures proves nothing (plan gate r1, **BLOCKER B3-3**). Rev 1 promised the grid and supplied no request source.

**The fixture registry, `apps/api/tests/Architecture/fixtures/route-action-fixtures.json`.** One entry per gated route, giving the matrix everything the registry cannot: what to create first, what to put in the URI, what body to send, and **what row proves the action happened**.

~~~jsonc
// Schema. One object per entry; the file is a JSON array, sorted by `route`.
{
  "route":    "work-orders.update",        // the route NAME (unique; the router is the oracle)
  "method":   "PATCH",                     // must equal the router's method for that name
  "uri":      "api/v1/work-orders/{id}",   // the router's uri, for cross-checking only
  "setup":    "WorkOrderFixture::openForCompany",   // static factory: (Company, User) -> array
                                                    // returns the values `params` and `payload` interpolate
  "params":   { "id": "{work_order_id}" }, // {curly} tokens resolve from setup's return array
  "payload":  { "notes": "matrix probe" }, // a body that WOULD succeed for a holder; {} for none
  "expect": {                              // what proves the action happened, on the ALLOW cell
    "table":  "work_orders",               // and, negated, on the DENY cell
    "where":  { "id": "{work_order_id}" },
    "column": "notes",
    "value":  "matrix probe"
  },
  "notes": "row-level ownership is E-3 and is NOT asserted here"
}
~~~

**How the matrix uses it.** For each (template, entry): create the fixture through `setup`, act as a principal holding **exactly** that one template role, send `method` + interpolated `uri` + `payload`. If `templateGrants()` says the role holds the route's key → assert **2xx** *and* `expect` matches. If not → assert **403** *and* `expect` does **not** match, i.e. the row is unchanged. **The same payload is used on both cells**, which is what makes the deny meaningful: a 403 on a request that would have succeeded for a holder is an authorization denial and nothing else.

## Rollback

**Wave 3 has no migration and no destructive deploy step. Its rollback granularity is the per-module commit** — which is why the per-module commit boundary is a Global Constraint rather than a style preference.

| Revert | Effect | Must also revert |
|---|---|---|
| Task 3-9 (matrix) | the regression matrix disappears; nothing else changes | — |
| Task 3-8 (sidebar / marketplace) | `permission?: ModuleKey` returns; `marketplace.admin` returns to the tenant guard | — |
| Task 3-7 (key retirement) | the 22 keys return to the registry — **but the rows are already gone** if the prune was run | **re-run `permissions:sync-fleet`** to recreate the rows; a registry key with no row is a fail-closed 403 for everyone |
| Task 3-6 step 4 (prune command) | the command disappears; rows already deleted stay deleted | — |
| Task 3-6 step 3 (seeder shims) | the exporter's input returns to the statics | the statics must be restored **in the same revert commit**, or the exporter calls methods that do not exist |
| Task 3-6 step 2 (`LotActionPermissionDelta`) | the dead class returns; **no behavioural change either way** — sync never called it | — |
| Task 3-6 step 1 (literal baseline) | the PHPStan rule stops hard-failing | — |
| Task 3-5 (glossary) | documentation only | — |
| Task 3-4 (`MembershipRole` / enums) | `isOwner()` returns as an authz read; `SystemRoleName` returns | its callers, re-pointed in the same revert |
| **Task 3-3 (POS ladder)** | the ladder returns and the terminal ceiling is ignored again | **revert as a POS release**, and only as a whole: reverting the ladder deletion without reverting the `fetchDiscountPermissions` wiring leaves two authority sources, which is worse than either |
| **Task 3-2 (POS sweep)** | per controller — each is its own commit | each controller's ceiling decrement in the same revert |
| **Task 3-1 (non-POS sweep)** | per cluster — each is its own commit | each cluster's ceiling decrement and baseline entries in the same revert |

| Task 3-6 step 1 (literal conversions) | per module — each is its own commit | that module's regenerated baseline in the same revert; the baseline **file** returns if it had been deleted |
| The fixture registry (Task 3-9 step 1) | the matrix has no request source and cannot run | `unfixtured-routes.json` and `UNFIXTURED_ROUTE_CEILING` in the same revert — a registry reverted without its complement makes the ceiling assert against a set that no longer exists |

**A partial revert must restore its ceiling and its baseline entries in the SAME commit.** A reverted conversion whose baseline entry stays deleted makes the ratchet's **stale** direction fail on the next run, and a reverted conversion whose ceiling stays lowered makes the **anti-growth** direction fail — either way the build goes red for a reason that has nothing to do with the revert's intent, and someone "fixes" it by raising a ceiling. That is the failure this note exists to prevent.
