# T2.7 — Offline-First Training-Aware Receipt Path (Kickoff)

**Status:** Pending kickoff. Branched from PR #99 (T2.5 Training Mode UI) round-8 P1 finding.

## Why this exists

PR #99 surfaces the existing `terminals.is_training_mode` flag in the POS UI via a sticky banner. The backend's `ReceiptCreationService.php:466-485` already handles training mode correctly for the **online** receipt path: training receipts get a separate prefix via `generateTrainingReceiptNumber()` and skip the fiscal hash chain entirely (no `fiscal_hash`, no `previous_hash`, no `chain_sequence`). They are excluded from Z reports / NF525 exports / `Terminal::scopeProduction()`.

But the POS is **offline-first**: every sale goes through `createOfflineReceipt` → `ReceiptSyncService::ingestSingle()`, never `ReceiptCreationService`. Neither side consults `terminal.is_training_mode`. So training-terminal sales:

- Advance the local fiscal hash chain in SQLite (`advanceHashChain`).
- Sync via `ReceiptSyncService` as **production** receipts.
- Finalize through `ReceiptFinalizationService` — server-side chain advance, Z report inclusion, NF525 inclusion.

The compliance promise that "training receipts skip the fiscal chain" is silently broken on the offline path. PR #99's banner copy was softened from "Receipts excluded from Z reports and fiscal records" to "Test terminal — verify mode before each transaction" as a stopgap; the architectural fix lives here.

## Surface (estimated 2-3 days)

### Frontend (apps/pos)

1. **SQLite migration** — add `is_training INTEGER NOT NULL DEFAULT 0` to `offline_receipts`. Backfill existing rows to 0 (correct: production receipts on existing installs).
2. **`OfflineReceipt` repository type** — surface `is_training: boolean`.
3. **`createOfflineReceipt`** —
   - Read `terminal.is_training_mode` from `useTerminalStore` at the start of the function.
   - Branch the receipt-number generation: training receipts use a `FORM-` prefix (matching `generateTrainingReceiptNumber()` server-side).
   - Skip `advanceHashChain` for training receipts. Set `fiscal_hash`, `previous_hash`, `chain_sequence` to NULL (or sentinel values).
   - Persist `is_training=true` on the SQLite row.
4. **Sync payload** — extend the wire shape to include `is_training` (default false for backwards compat).
5. **Frontend tests** — (a) training-mode terminal + createOfflineReceipt → no chain advance + training prefix; (b) sync payload includes is_training when set.

### Backend (apps/api)

1. **`SyncReceiptPayload` DTO** — add `bool $isTraining` field (default false). Update `fromArray()` to read `is_training`.
2. **`SyncReceiptsRequest` validator** — accept optional `is_training: boolean`.
3. **`ReceiptSyncService::ingestSingle()`** — branch on `payload->isTraining`:
   - Skip `finalizationService->finalize()` — training receipts don't enter the chain.
   - Skip the `offlineFiscalHashMismatch` check (training receipts don't have a meaningful fiscal hash to compare).
   - Set `is_training=true` on the `Receipt` row.
   - Set `fiscal_status` to a training-appropriate value (probably a new `Training` enum case if it doesn't exist).
4. **Backend tests** — feature tests:
   - Training payload via SyncReceiptsRequest → receipt persisted with is_training=true, no chain advance.
   - Production payload (default) → unchanged behaviour (regression guard).
   - `Terminal::scopeProduction()` continues to exclude training receipts on the synced path.

## Test fixture coordination

The existing offline-flow integration tests use `is_training_mode: false` terminals. T2.7 adds at least one training-terminal fixture. The `Terminal` interface in `apps/pos/src/stores/terminalStore.ts` already has `is_training_mode: boolean` (added in PR #99); 3 existing test fixtures were updated to include it.

## Risk / scope clarifications

- **Backwards compat:** existing offline_receipts rows default to is_training=0. Existing sync payloads without the field are interpreted as production. No backfill needed; no breaking change.
- **Hash chain:** the local fiscal chain stays production-only. Training receipts don't enter ANY chain (matching the online ReceiptCreationService behaviour). If a single terminal alternates training/production mid-shift, the production chain advances normally over the training gap (training receipts are invisible to the chain).
- **Receipt numbering:** training receipts use a `FORM-` prefix, distinct from production. Production sequence counter is unchanged.

This decouples the backend correctness fix from the frontend schema change. A backend-only landing already prevents the bad behaviour at the sync ingest path, even if the frontend continues to send is_training=false (the default) until the frontend fix lands.
