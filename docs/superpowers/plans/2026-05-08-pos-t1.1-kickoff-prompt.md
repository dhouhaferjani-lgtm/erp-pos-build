The four failure modes:
1. **Auth persistence orphan.** A network drop AFTER `/auth/login` succeeds but BEFORE `/user/companies` resolves leaves TOKEN + USER persisted in Tauri Store and `isAuthenticated:true` in memory, but `companies:[]`. Next boot: cashier sees a broken TerminalSetupPage instead of LoginPage.
2. **Empty-companies router gap.** App.tsx has no branch for `isAuthenticated && companies.length === 0` — the user falls through to TerminalSetupPage which immediately throws because there's no companyId to scope the terminal pull.
3. **Connectivity-monitor sited on the wrong shell.** `connectivityStore.startMonitoring()` runs from AppShell (which only mounts inside the authenticated branch), so LoginPage NEVER sees connectivity state — the user can't tell whether their login is failing because of credentials or because the API is unreachable.
4. **LoginPage frozen-spinner trap.** When `/auth/login` hangs (server overloaded, captive portal half-broken), the cashier sees a frozen spinner with no escape — no cancel, no "still trying" sub-text, no recovery. T0.3's read-timeout caps the abort to 10s but for sub-10s slow-but-not-timeout paths the UX is opaque.

### Step 1.1 — Roll back persisted auth on `/user/companies` failure

**File:** `apps/pos/src/stores/authStore.ts` (verify line numbers; `login` action lives around `:130-186` post-T0.5).

**The bug (still present on dev — verified 2026-05-08):**
The current login flow at `authStore.ts:130+` does:
1. POST `/auth/login` → get token + user (line ~142).
2. **Persist TOKEN to Tauri Store** (line ~155).
3. **Persist USER to Tauri Store** (line ~156).
4. **Set `isAuthenticated:true` in memory** (line ~161).
5. GET `/user/companies` (line ~167).
6. Persist COMPANIES (line ~168).
7. Auto-select if single company.

If step 5 throws (transient network drop after the POST returned), the catch handler (around line ~178+) DOES NOT roll back the persisted TOKEN/USER or the `isAuthenticated:true` flag. Next boot: `initialize()` reads TOKEN+USER from Tauri Store, sees `isAuthenticated:true` with `companies:[]`, and routes to TerminalSetupPage which immediately throws.

**Fix contract:**
- Move `setStoredValue(TOKEN, ...)`, `setStoredValue(USER, ...)`, and `set({ isAuthenticated: true })` to **AFTER** the `apiGet<Company[]>('/user/companies')` resolves successfully.
- On companies-fetch failure, do not persist token/user, do not flip `isAuthenticated`, throw the original error so `LoginPage` shows it.
- Keep auto-select-on-single-company behavior untouched.

**Codex preempts (5-task pattern):**
- Race: two concurrent `login()` calls leaving inconsistent state. The current code doesn't gate concurrent calls — verify whether T0.2's `isProcessing` pattern (or a sibling) applies here. If not, document why.
- Cleanup on the catch path: any partial state that leaks between login() throws and the next attempt. Wrap any required cleanup in a `finally` block, NOT in catch.
- Token already persisted from a PRIOR successful login: the rollback on companies-failure must not wipe a previously-valid TOKEN that was already cached. The fix should ONLY refrain from PERSISTING the new login's token — not delete pre-existing data.

### Step 1.2 — Add `companies.length === 0 && isAuthenticated` recovery branch in router

**File:** `apps/pos/src/App.tsx` (verify; the auth/companies branch ladder lives around `:78-104` post-T0.5).

**The bug (still present on dev):**
Current branch ladder at `App.tsx:78-95`:
1. `if (!isAuthenticated)` → LoginPage routes (line ~78-86).
2. `if (companies.length > 1 && !companyId)` → company-selection LoginPage (line ~88-94).
3. `if (!terminal && !terminalLoading)` → TerminalSetupPage routes (line ~96-103).
4. Falls through to MainApp.

**MISSING branch:** `isAuthenticated && companies.length === 0` (with or without `companyId`). This state is reachable today via Step 1.1's bug, AND will remain reachable via legitimate edge cases (e.g. an admin removed the user from all companies between sessions). The user falls through to TerminalSetupPage which throws on the first `apiGet('/terminals?company_id=...')` because companyId is null.

**Fix contract:**
- Insert a new branch BEFORE the `!terminal` check that catches `isAuthenticated && companies.length === 0`. Render a recovery screen that re-runs `/user/companies` on a button press AND auto-runs once on mount.
- The recovery screen should also handle `companies.length === 0 && companyId === null` for users that previously had companies cached but now don't (e.g. admin revoked).
- Recovery screen design: simple full-page error state with a "Retry" button, an "Sign out" link, and the most recent error message (if any) in a small typed-fields-only diagnostic block.

**Codex preempts:**
- **Redirect loop:** the new branch must not interact with the existing `/login` and `/setup` Routes in a way that creates a redirect loop. Test the four states: `(isAuthenticated:true, companies:[], companyId:null)`, `(isAuthenticated:true, companies:[A], companyId:A.id)`, `(isAuthenticated:true, companies:[A,B], companyId:null)`, `(isAuthenticated:false)`.
- **Banner-opacity (T0.1/T0.3 contract):** the recovery screen's error-message rendering must use `serializeErrorForLog`'s typed fields, NOT the raw error message — a captive-portal HTML error page or backend stack trace must not leak to the cashier UI.

### Step 1.5 — `LoginPage` "still trying" affordance + cancel button

**File:** `apps/pos/src/pages/LoginPage.tsx` (136 lines as of dev tip; `login` action at `:10-23`, no AbortController, no cancel UI).

**The bug:**
