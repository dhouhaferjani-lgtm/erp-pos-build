You are the **POS Orchestrator session for T1.3** — sync indicator truthfulness. T1.3 is the last named Tier-1 task. Your job is to ship the three Phase-4 sub-steps with the same discipline T0.1 → T1.2 demonstrated.

**Your prime directive:** the sync indicator in the POS header lies to the cashier today. Three small but compounding bugs:

1. **`pendingReceiptCount` reads "receiptsFailed" from the most-recent SyncResult, not SQLite truth.** A cashier with 3 receipts in `status='pending'` from a tick that timed out sees the badge as "0" because the most-recent tick didn't itself fail any new receipts. Drift compounds across ticks; the badge cannot be trusted.
2. **`lastSyncAt` lives in memory only — not persisted.** Restart the app and the SyncButton's "X minutes ago" affordance is blank until the next tick fires. The cashier loses trust signal across every restart.
3. **The header doesn't differentiate "synced" from "synced with errors".** A tick that pushed 3 receipts but failed to pull payment config returns "success" to the UI — green dot, no warning. The cashier doesn't know payment config is stale until they hit the gate Step 2.3 just shipped.

These three bugs collectively bound the sync-state tristate: clean (green) → in-flight (spinner) → degraded (amber). T1.3 fixes all three so the header is the single truthful surface for sync health.

## Section 3 — T1.3 scope (3 sub-steps in one PR — sync indicator state machine)

### Why bundle these 3 sub-steps in one PR (not split further)?

The sync-indicator UI is a single state machine. Step 4.1 makes the count truthful; 4.2 makes the timestamp truthful across restarts; 4.3 makes the color truthful when partial-success ticks happen. Splitting would require two interim states where the indicator is partially fixed (e.g. count truthful but color still lying) — confusing for any reviewer trying to evaluate the surface. Matches T1.1's Phase-1 + T1.2's Phase-2 bundling rationale.

### Step 4.1 — `pendingReceiptCount` reads SQLite, not "receiptsFailed"

**Files:**
- `apps/pos/src/stores/syncStore.ts` (verify; `completeSync` at `:50-57` post-T1.2; `setPendingCount` at `:67-69`).
- `apps/pos/src/lib/sync/syncScheduler.ts` (verify; `completeSync` invocation at `:103` post-T1.2).
- `apps/pos/src/stores/terminalStore.ts` (verify; `seedOfflineHashChain` exported post-T1.2; `scheduler.start()` at `:106`; T1.2 added the `fetchPaymentConfig` pre-warm at `:117-130`).

**The bug (still present on dev — verified 2026-05-08):**
`syncStore.ts:56` writes `pendingReceiptCount: result.receiptsFailed` on every `completeSync`. `result.receiptsFailed` only counts the receipts that failed in the JUST-completed tick — not the running total of pending receipts in SQLite. After several ticks the in-memory count drifts from SQLite reality. Worse: on app boot, `pendingReceiptCount` defaults to 0 from `initialState` and stays at 0 until the first tick fires — so a cashier with 5 unpushed receipts from a previous session sees "0" in the header.

**Fix contract:**
- **Inside `syncScheduler.ts:103`'s `.completeSync(result)` call** OR right after it, read `getPendingReceiptCount(this.db)` and call `useSyncStore.getState().setPendingCount(count)` to overwrite the (now stale) `result.receiptsFailed`-derived value. The cleanest shape: keep `completeSync` accepting a `SyncResult` for the existing fields (lastSyncAt, lastError, etc.) but add a fresh SQLite-sourced count via `setPendingCount` immediately after.
- **In `syncStore.ts:56`'s `completeSync` reducer**, drop the `pendingReceiptCount: result.receiptsFailed` line. The count now comes ONLY from `setPendingCount`.
- **In `terminalStore.ts:seedOfflineHashChain`**, after `scheduler.start()` and after T1.2's `fetchPaymentConfig` pre-warm, fire a one-shot `getPendingReceiptCount(db)` and call `useSyncStore.getState().setPendingCount(count)`. This is the startup hydration — the badge shows the truth from boot, before any tick.
- **Optimistic increment on local insert (deferred):** the Phase-4 spec mentions "bump the count by 1 on insert". This requires hooking into every receipt-insert site. Defer to a follow-up — the post-tick hydration + startup hydration alone closes the visible drift; the optimistic-increment is a UX nicety, not a correctness requirement. Document the deferral in the PR body.

**Codex preempts (T1.1+T1.2 lessons — pre-empt aggressively):**
- **Race between two ticks firing setPendingCount.** Two scheduled ticks could overlap (despite the existing `isSyncing` guard) and call `getPendingReceiptCount` then `setPendingCount` concurrently. The reads against SQLite are atomic per-tick but the in-memory `set` could land in any order. Last-write-wins on a count that's monotonic-ish is acceptable, but document the rationale.
- **Startup hydration vs. first tick race.** `seedOfflineHashChain` fires the hydration AFTER scheduler.start. The scheduler's first tick (debounced or interval-driven) could fire before the hydration `await getPendingReceiptCount` resolves. Both call `setPendingCount`; the later one wins. If the hydration wins last the count reflects pre-tick state — slight UX issue but bounded (the next tick corrects it within ~60 s). Surface as a known acceptable race in the PR body.
- **SQLite read failure.** `getPendingReceiptCount` could throw if the DB is locked or the connection is dead. Wrap in try/catch with `serializeErrorForLog` (T0.1 contract) and DON'T propagate — leave the in-memory count at its prior value rather than crashing the tick.
- **Result.receiptsFailed still propagates to lastError.** The `completeSync` reducer also reads `result.errors[0]` for `lastError`. Don't accidentally drop the error-tracking when removing the count line.

### Step 4.2 — Persist `lastSyncAt` to `sync_metadata`

**Files:**
- `apps/pos/src/stores/syncStore.ts` (verify; `lastSyncAt` written at `:53` post-T1.2; new `setLastSyncAt` action needed).
- `apps/pos/src/lib/sync/syncScheduler.ts` (verify; `completeSync(result)` at `:103`; new `setSyncMetadata` write needed).
- `apps/pos/src/lib/db/repositories/syncLogRepository.ts` (existing helpers; no changes).
- `apps/pos/src/stores/terminalStore.ts` (verify; `seedOfflineHashChain`; new `getSyncMetadata + setLastSyncAt` hydration needed).

**The bug (still present on dev):**
`syncStore.ts:53`'s `completeSync` writes `lastSyncAt: Date.now()` to in-memory state. On app restart the state resets to `null` (initialState). The SyncButton's `formatTimeAgo` returns `null` for a null timestamp, so the cashier sees blank for "X minutes ago" until the next tick lands — typically ~60 s after boot. That's a long blank window, especially in flaky-network environments where the next tick may not land at all.

**Fix contract:**
- After `completeSync(result)` in `syncScheduler.ts:103`, call `setSyncMetadata(this.db, 'last_sync_at', String(Date.now()))`. Use the SAME timestamp the in-memory state got — don't call `Date.now()` twice (drift is negligible but consistency reads cleaner).
- Add a `setLastSyncAt(ts: number | null)` action to `syncStore.ts` that just calls `set({ lastSyncAt: ts })`. (Alternative: re-use the existing `completeSync` shape — but `completeSync` writes 5 fields and we want a hydration-only entry point. New action is cleaner.)
- **In `terminalStore.ts:seedOfflineHashChain`**, after `scheduler.start()` AND the T1.2 `fetchPaymentConfig` pre-warm AND the Step 4.1 `setPendingCount` hydration, read `getSyncMetadata(db, 'last_sync_at')`. If non-null, parse to number and call `useSyncStore.getState().setLastSyncAt(parsed)`. Skip if null or NaN.

**Codex preempts:**
- **Timestamp format.** Store as ms-since-epoch string (`String(Date.now())`). Parse with `Number(...)` and check `Number.isFinite` to reject corrupt values. Don't ship a `Date.parse` round-trip — that introduces locale ambiguity.
- **Hydration order.** In `seedOfflineHashChain`, read SQLite metadata BEFORE the scheduler ticks. If the scheduler ticks before hydration completes and writes a NEW timestamp, the hydration's older value would overwrite. Either await the hydration before scheduler.start (cleanest) OR skip the hydration write if `useSyncStore.getState().lastSyncAt` already has a fresher value (fallback). **Recommended: await the hydration before scheduler.start** — the read is fast (single SQLite query) and the ordering is explicit.
- **In-memory wins on conflict.** If the in-memory `lastSyncAt` is newer than the SQLite value (shouldn't happen, but defensive), don't overwrite. Compare and skip the `setLastSyncAt` if the in-memory value is fresher.
- **SQLite write failure.** `setSyncMetadata` could throw if the DB is locked. Wrap in `.catch(serializeErrorForLog wrapper)` and don't propagate — the in-memory state already has the truth; the next tick will retry the persistence.

### Step 4.3 — Differentiate "synced" from "synced with errors"

**Files:**
- `apps/pos/src/lib/sync/syncService.ts` (verify; `SyncResult` interface at `:185-205`; main sync impl returns the result).
- `apps/pos/src/components/atoms/SyncButton/SyncButton.tsx` (62 lines today; reads `isSyncing` + `lastSyncAt` from syncStore — needs to also read `lastSyncResult` for degraded check).

**The bug:**
The header has no signal for "tick completed but with errors". A cashier sees green dot + "5m ago" even when the most recent tick failed to push payment config or had 3 receipts fail. Step 2.3 (T1.2) gave them a downstream gate — but they don't know to look at PaymentSummary until they try to check out.

**Fix contract:**
- Add a `degraded: boolean` field to `SyncResult`. Compute it inside the sync function (`syncService.ts:1289-1321` — wherever the result object is assembled) as:
  ```ts
  const degraded =
    result.receiptsFailed > 0 ||
    result.zReportsFailed > 0 ||
    !result.paymentConfigPulled ||
    result.errors.length > 0;
  ```
  **Do NOT include `productsPulled === 0`** — the canonical playbook explicitly warns against false-positive on valid empty catalogs. The four conditions above are reliable.
- Update the SyncResult interface accordingly.
- In `SyncButton.tsx`, read `lastSyncResult` from the store (`useSyncStore((s) => s.lastSyncResult)`) and check `lastSyncResult?.degraded === true`. Render an amber dot inline when degraded:
  - Visual: a small amber circle (e.g. `<div className="h-1.5 w-1.5 rounded-full bg-amber-500" />`) inserted between the icon and the time-ago text.
  - Tooltip: `title={t('sync.degradedTitle')}` that lists the first error from `lastSyncResult?.errors[0]` if available, else a generic "Last sync had errors" translation.
  - Distinguishable from green/red — the spec says "amber" specifically, so use Tailwind `bg-amber-500` (NOT yellow which has a different connotation).
- Add `pos:sync.degradedTitle` (and any helper i18n keys) to BOTH `en/pos.json` and `fr/pos.json` (T1.1 round-2 lesson). Translated:
  - English: "Last sync had errors — click to retry"
  - French: "La dernière synchronisation a échoué — cliquez pour réessayer"

**Codex preempts:**
- **Empty catalog false-positive.** Confirm the heuristic doesn't include `productsPulled === 0` — a tenant with no products yet is a valid empty state, not a degraded one. Document the rationale in the PR body.
- **i18n keys must land in both en + fr** with translated values. Add a direct `i18n.t()` resolution check to the smoke test (matching T1.2 round-2's `paymentConfigReadyI18n.test.tsx` pattern).
- **Backwards compatibility of SyncResult.** Tests that mock SyncResult in fixtures need to be updated for the new `degraded` field. Run `grep -rn 'SyncResult\|receiptsPushed' apps/pos/src/__tests__ apps/pos/src/lib/sync/__tests__` to find them.
- **Aria + accessibility.** The amber dot should have `aria-label` describing the state, OR the surrounding button's aria-label should be updated to mention the degraded state. Visual-only signaling fails on screen readers.
- **Tooltip rendering on a button.** Browsers render `title` attributes only on hover. That's acceptable for a desktop POS but document that tap-to-show isn't free; if mobile becomes a concern later, a dedicated tooltip component is a follow-up.

- **Optimistic increment on local insert.** Step 4.1 spec calls for it; deferred to a future small PR after T1.3 ships.
- **Animated transition between states (green → amber).** Pure CSS, easy follow-up if the amber-on / amber-off transition feels jarring in real cashier use.
