## Ricochet Checks

### Check A — Recovery screen errorName allowlist: opaque label acceptable?
**Status: ACCEPTABLE**

When `errorName` falls outside `SAFE_ERROR_NAMES` (e.g. `NetworkError`, any vendor class name), `safeLabel = 'Error'` (`App.tsx:191`). The full structured payload including the real `errorName` is emitted to `console.error` at `App.tsx:184-187`, so devtools retains full diagnostics. The cashier UI intentionally shows only the class-bucket — this is correct per the T0.1 banner-opacity contract.

The allowlist itself is reasonable: `ApiRequestError`, `FetchTimeoutError`, `AbortError`, `TypeError`, `Error` cover all first-party error types. No vendor/API content can reach it. **Acceptable.**

### Check B — login() snapshot: missing fields?
**Status: ACCEPTABLE (with documentation note)**

The snapshot at `authStore.ts:183-189` captures 5 of 8 `AuthState` fields:
- Captured: `token`, `user`, `companies`, `companyId`, `isAuthenticated`
- NOT captured: `serverUrl`, `isLoading`, `isInitialized`

Why each missing field is safe:
- `serverUrl`: set at `authStore.ts:141` via `set({ isLoading: true, serverUrl })` BEFORE the snapshot is taken. Not reverting it is correct — `serverUrl` is re-derived from `getServerUrl()` and does not belong to the prior session identity. Restoring an old `serverUrl` would be wrong.
- `isLoading`: set to `true` at line 141, then reset to `false` in the `finally` block at line 229. Restoring `isLoading` from the snapshot (which captures it as `false`) would be redundant but harmless; the `finally` handles it either way.
- `isInitialized`: never changed during login; omitting it from the snapshot has no effect.

**No missing auth-identity fields. Acceptable.**

### Check C — userAbortPromise cleanup / memory leak
**Status: ACCEPTABLE**

On all three exit paths (success, timeout, user-abort):
- The `setTimeout` timer is cleared at `fetchWithTimeout.ts:166` via `clearTimeout(timer)`.
- The `userSignal` `abort` event listener is removed at line 168 via `userSignal.removeEventListener('abort', onUserAbort)`.
- The `userAbortPromise` and `rejectUserAbort` are local variables. When `fetchWithTimeout` returns (in `finally`), nothing outside the function holds a reference to either. Both become eligible for GC.

`Promise.race` does not pin the pending race legs after one settles; once no reference remains to `userAbortPromise`, it can be collected. On a successful fetch or timeout, `rejectUserAbort` is never called — the Promise stays "pending" but unreachable. This is a standard JavaScript pattern and not a structural leak.

Two `fetchWithTimeout` tests assert `vi.getTimerCount() === 0` after abort, confirming the timer side is clean.

**No leak. Acceptable.**

### Check D — fetchCompanies: null/undefined/empty companies guard
**Status: ACCEPTABLE**

`fetchCompanies` (line 255) calls `apiGet<Company[]>('/user/companies')`. The TypeScript type is `Company[]`, so the compiler requires an array.

- `companies` empty array (`[]`): `currentCompanyId !== null && [].some(...)` evaluates `false` → `stillValid = false` → `companyId` cleared. Safe.
- `currentCompanyId` already `null`: `null !== null` is `false` → `stillValid = false` → `companyId` cleared to `null` (no-op). Safe.
- `companies` is `undefined` (API contract violation, not typed): `undefined.some(...)` would throw. However, this requires an API regression outside T1.1 scope and is protected by TypeScript's strict mode at the call site. Not a T1.1 issue.

**Acceptable.**

## Preempt Re-probe

### E — AbortSignal lifecycle: Cancel-twice / Cancel-after-resolve / rapid-resubmit
**Status: NO REGRESSION**

- **Cancel-twice**: `userSignal.addEventListener(..., { once: true })` at `fetchWithTimeout.ts:132` ensures `onUserAbort` fires at most once. `rejectUserAbort` is idempotent after the first call (Promise already settled). `controller.abort()` is idempotent on `AbortController`. Safe.
- **Cancel-after-resolve**: In `LoginPage.tsx`, `abortControllerRef.current` is cleared when the login attempt settles (the ref cleanup path). A late `cancelButton` click calls `abortControllerRef.current?.abort()` on `undefined` — no-op. Safe.
- **Rapid-resubmit**: The submit button is `disabled={isLoading}` per `LoginPage.tsx`. While loading, no second submit is possible. Safe.

**Status: NO REGRESSION**

The fix-up commit does not touch `connectivityStore.ts` or `AppShell.tsx`. The `startMonitoring()` placement in `MainApp` (from the baseline commit) is unchanged. No regression observed.

### G — Test honesty (Cancel test)
**Status: IMPROVED, RESIDUAL MINOR CONCERN**

The mock at `LoginPage.test.tsx:135-145` now listens on `opts?.signal` and rejects with `AbortError` when it fires, and manually flips `isLoading: false` via `useAuthStore.setState`. This is more honest than the round-1 version.

Residual concern: the mock manually calls `useAuthStore.setState({ isLoading: false })` inside the signal listener. The real `authStore.login` resets `isLoading: false` in its `finally` block. A future integration test should cover the end-to-end abort path through the real store.

## New Findings

### Finding 6 — MAJOR: auth.companyRecovery.errorHint i18n key missing from all locales

**File:** `apps/pos/src/App.tsx:219`

```tsx
<div className="mt-1">{t('auth.companyRecovery.errorHint')}</div>
```

The key `auth.companyRecovery.errorHint` is called with `useTranslation('common')` (line 170). The `common` namespace maps to `apps/pos/src/locales/en/common.json` and `apps/pos/src/locales/fr/common.json`. Neither file contains any `auth` key or `companyRecovery` subtree. The `pos.json` namespace also has no `companyRecovery` section.

At runtime, `react-i18next` falls back to rendering the key string verbatim: `"auth.companyRecovery.errorHint"` appears in the red error banner in the cashier UI when `fetchCompanies` fails.

Additionally, ALL `auth.companyRecovery.*` keys used in `CompanyRecoveryScreen` (`title`, `message`, `retrying`, `retry`, `signOut`) are absent from the locale files. This means the entire recovery screen renders raw key strings, not translated text. This pre-existed in the baseline commit (`0fb3bbc4`) but the round-1 fix-up introduces `errorHint` without adding the key and without fixing the pre-existing gap.

**Remedy:** Add the `companyRecovery` subtree to both `apps/pos/src/locales/en/common.json` and `apps/pos/src/locales/fr/common.json`:

```json
"auth": {
  "companyRecovery": {
    "title": "Company Access Error",
    "message": "We couldn't load your companies. Please retry or sign out.",
    "retrying": "Retrying…",
    "retry": "Retry",
    "signOut": "Sign out",
    "errorHint": "Check your connection and try again."
  }
}
```

(French equivalent for `fr/common.json`.)

Note: the `useTranslation('common')` call on line 170 is correct — this namespace IS loaded. The locale files simply lack the keys.

### Finding 7 — NIT: priorAuth snapshot is spread-restored, not merged

**File:** `authStore.ts:201`

```ts
set(priorAuth);
```

`set(priorAuth)` merges only the 5 snapshot fields into the store (Zustand `set` is a shallow merge). Fields not in `priorAuth` retain whatever value they currently have (e.g., `isLoading: true` from line 141). This is safe because `isLoading` is reset to `false` in the outer `finally` at line 229. However, if the error propagation path ever changes and the outer `finally` were removed, `isLoading` would be stuck `true`. A comment noting this dependency would improve maintainability.

The entire `CompanyRecoveryScreen` renders raw i18n key strings at runtime because `auth.companyRecovery.*` does not exist in either locale file. Add a smoke test in `AppRouter.test.tsx` asserting the recovery screen renders a real string (not a key) for `data-testid="company-recovery-screen"` — or at minimum assert the translated title text. Finding 7 (NIT) does not block.
