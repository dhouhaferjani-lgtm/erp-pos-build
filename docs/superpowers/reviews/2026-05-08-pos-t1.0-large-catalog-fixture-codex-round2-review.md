## New Findings

### Finding 6 — MINOR: `whereNotNull('barcode')` guard may be redundant in the barcode uniqueness test

**File:** `apps/api/tests/Feature/Seeders/ParapharmacySeederTest.php:96`

```php
$distinctBarcodes = Product::whereNotNull('barcode')->distinct()->count('barcode');
```

**Analysis:** The `barcode` column in the products table is `NOT NULL` at the DB level (confirmed in the migration: `$table->string('barcode')->nullable(false)`... — see the existing product migration). The seeder always calls `generateBarcode($globalOrdinal)` and assigns the result to `barcode` with no nullable code path. PostgreSQL's `COUNT(column)` already excludes `NULL` rows, and `DISTINCT COUNT(column)` likewise excludes them, so `whereNotNull` is a no-op here.

The guard does no harm and adds intent documentation for future readers who might not know the schema. However, it creates a false safety net: if `barcode` were made nullable in a future migration, the `whereNotNull` filter would silently hide NULL barcodes instead of surfacing the regression. The cleaner approach would be `Product::count()` === `Product::distinct()->count('barcode')` (mirroring the SKU test at line 116).

**Recommendation:** Replace with a schema-consistent assertion in a follow-up (low urgency, does not block merge). No test logic error introduced.

### B. `distinct()->count('barcode')` + `whereNotNull` semantics

PostgreSQL: `COUNT(column_name)` — as opposed to `COUNT(*)` — already excludes NULL values. `DISTINCT COUNT(column)` also excludes NULLs. Therefore:

- `Product::whereNotNull('barcode')->distinct()->count('barcode')` is functionally identical to `Product::distinct()->count('barcode')` when `barcode` is NOT NULL at the DB level (which it is).
- If `barcode` were nullable, `whereNotNull` would hide the gap rather than expose it — see Finding 6.
- The test assertion `$totalProducts === $distinctBarcodes` would pass even if a small number of products had NULL barcodes (since `$totalProducts = Product::count()` counts all rows including NULLs but `$distinctBarcodes` would exclude them). This is a mild test-honesty gap, but not a correctness bug in the current schema.

**Conclusion:** No incorrect behavior in the current schema. Noted as Finding 6 (MINOR).

### C. Two-step `putenv` tearDown vs `Env::forget()`

The installed `Illuminate\Support\Env::forget()` (Laravel 12 / framework ~11) delegates to `phpdotenv`'s `PutenvAdapter::delete()` which calls:
1. `putenv($name)` — removes from the process env on POSIX.
2. `unset($_ENV[$name])`.
3. `unset($_SERVER[$name])`.

The new two-step tearDown does:
1. `putenv('PARAPHARMACY_SEEDER_SCALE=')` — clears to empty (Windows compat).
2. `putenv('PARAPHARMACY_SEEDER_SCALE')` — removes from process env (POSIX).
3. `unset($_ENV['PARAPHARMACY_SEEDER_SCALE'])`.
4. `unset($_SERVER['PARAPHARMACY_SEEDER_SCALE'])`.

The new pattern is a strict superset of `Env::forget()` on POSIX, and adds the Windows-compat step 1 that `Env::forget()` itself does NOT include. The only component `Env::forget()` touches that tearDown does not is `$_GET` — irrelevant for env vars. **No regression; the new tearDown is marginally more thorough than `Env::forget()` on Windows. Closed.**
