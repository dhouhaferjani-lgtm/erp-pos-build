## Summary

The claim — "payment-tolerance GL entries (close-with-tolerance + smart-payment allocation)
post when a real actor is available; actorless stays draft" — holds up under refutation. The
implementation threads an optional `postedByUserId` + `currencyCode` through
`PaymentToleranceService::applyTolerance()` and `CloseInvoiceWithToleranceService` into
`GeneralLedgerService::createPaymentToleranceJournalEntry()`, which performs the actor
lookup BEFORE creating the journal entry and posts via the shared
`postEntryAndDispatchPostedEventAfterCommit()` helper. Posting computes the fiscal hash chain,
validates double-entry balance with the resolver-derived scale (no float, no hardcoded scale),
and dispatches `JournalEntryPosted` after the outer transaction commits. Tests genuinely assert
Posted status + `posted_by` + `posted_at` + `fiscal_hash` and are red-first meaningful.

Findings are limited to MEDIUM/LOW: the headline "atomic rollback" test does not exercise the
post-failure (afterCommit) path that actually risks a committed-but-Draft inconsistency; the
overpayment posting branch is untested; and a couple of pre-existing convention smells live
adjacent to the change. No BLOCKER and no HIGH.

## MEDIUM

### M1 — "Atomic rollback" test gives false confidence; the real post-failure path is NOT exercised and cannot roll back
`CloseInvoiceWithToleranceServiceTest::test_atomic_rollback_when_gl_post_fails`
(`CloseInvoiceWithToleranceServiceTest.php:301-336`) forces failure by omitting the AR account,
which throws inside `getAccountByPurpose()` — i.e. BEFORE the journal entry is created and before
`User::findOrFail()`. That correctly proves the pre-create failure path rolls back. But the POST
itself runs in `DB::afterCommit` (`GeneralLedgerService.php:78-91`): when an outer transaction is
open (it always is for both callers), posting is deferred until after the outer commit. If posting
throws there (unbalanced entry, hash-chain error, or `User::findOrFail` had it been deferred), the
Draft journal entry + the `PaymentAllocation` row + `invoice.status = Paid` / `balance_due = 0`
are ALREADY COMMITTED and cannot be rolled back. The result is a committed Draft GL entry with an
invoice marked Paid — the exact "Draft entry not counted by PartnerBalanceService" inconsistency
H-2 set out to eliminate, just relocated to the post-commit window. The actor `findOrFail` running
pre-create (Codex's remediation) mitigates the most likely cause, so residual risk is low, but the
test name overstates the guarantee. Recommend an explicit test that makes the POST (not account
resolution) fail and documents the post-commit consistency boundary.
Severity rationale: not a BLOCKER because the pre-create actor lookup removes the common failure,
and balance/hash failures here are improbable for a 2-line balanced entry; but the safety claim is
only partially tested.

### M2 — Overpayment posting branch is untested
Both new tests (`PaymentAllocationServiceTolerancePersistenceTest.php:146-191`,
`CloseInvoiceWithToleranceEndpointTest.php:202-208`) exercise only the `underpayment` branch
(Dr 658 / Cr AR). The `overpayment` branch (Dr AR / Cr 758 income,
`GeneralLedgerService.php:752-770`) now also posts when an actor is present but has no test
asserting Posted + posted_by + fiscal_hash for that account/direction. The shared posting helper
makes a regression unlikely, but the claim "tolerance entries post" is only proven for one of two
directions. [HYPOTHESIS — low risk]

### M3 — Silent Draft for an authenticated-but-non-member allocation actor
On the smart-payment allocation path, if `Auth::id()` resolves to a user lacking an Active
`UserCompanyMembership` for the company, `resolveCommandActor()` returns `null`
(`PaymentAllocationService.php:397-404`) and the tolerance entry is silently created as Draft
while the allocation and balance trigger still commit. This is consistent with "actorless stays
draft," but it is a quiet downgrade for a request that did carry an authenticated user — the
caller gets no signal that the GL leg did not post. Membership is normally a precondition enforced
upstream, so this is an edge, not a defect. Worth a log/metric on the draft-downgrade branch.

## LOW

### L1 — `type` remains a magic string, not an enum
`applyTolerance(..., string $type, ...)` and `createPaymentToleranceJournalEntry(..., string $type)`
pass `'underpayment'`/`'overpayment'` as raw strings (`PaymentToleranceService.php:164`,
`GeneralLedgerService.php:660`). This violates the "enums for all status/type columns" rule, but it
is pre-existing and untouched by this commit.

### L2 — Cross-module domain-model import (pre-existing)
`GeneralLedgerService` (Accounting) imports `App\Modules\Identity\Domain\User`
(`GeneralLedgerService.php:17`) and runs `User::query()->findOrFail()` directly. The new actor
lookup extends an already-established cross-module pattern rather than going through a Shared
contract. Pre-existing; flagging for the module-boundary ledger only.

### L3 — `currencyCode: (string) $invoice->currency` could pass `''` if currency were null
`CloseInvoiceWithToleranceService.php:102` casts a possibly-null currency to string before handing
it to the scale resolver. Invoices carry a currency in practice, so this is theoretical, but a
`''` would reach `scaleResolver->getScale('')`. [HYPOTHESIS — not reproduced]
