## 1. What the ruling asked for, and the shape it landed in

The 2026-08-19 ruling (`docs/handoff/reviews/wave3-3c-3d/ORCHESTRATOR-RULING-2026-08-19-m5-oq12-gate.md`) treated the flip as **one global deploy switch** held behind expert-comptable ratification. The owner superseded that on 2026-08-25: posting is seeded **true**, and the expert reviews the Option A account choice (6586 shortage / 7586 overage) later at onboarding.

Flipping `config/inventory.php` from `false` to `true` would have satisfied the letter of that in one line. It would not have satisfied the brief, which asks for a **per-country seeded, tenant-editable** setting — and that is also the only shape in which the expert's later review has a lever that does not need a deploy. So the config key stopped being *the* gate and became the last link of a chain that already exists in this codebase for exactly this family (`inventory_valuation_mode`, DPA Wave 3 T9):

```
companies.count_correction_gl_posting_enabled          (tenant override; NULL = inherit)
  -> country_inventory_settings.count_correction_gl_posting_enabled   (jurisdiction, seeded ON)
    -> config('inventory.count_correction_gl_posting_enabled')        (system, now TRUE)
```

Structurally `CountCorrectionGlPostingResolver` is `InventoryValuationModeResolver` with a boolean where the enum was — deliberately the same idiom, not a second one.

## 3. The migration and its predicate

`apps/api/database/migrations/tenant/2026_08_25_140000_seed_count_correction_gl_posting_default.php`

Three steps, each independently `hasTable`/`hasColumn`-guarded and re-runnable:

1. add `country_inventory_settings.count_correction_gl_posting_enabled` — `boolean NOT NULL DEFAULT true` (PostgreSQL backfills existing rows from the DEFAULT inside the same `ALTER TABLE`, so on a first run step 3 finds nothing to do);
2. add `companies.count_correction_gl_posting_enabled` — `boolean NULL`, **undefaulted**;
3. the flip:

```php
DB::table('country_inventory_settings')
    ->whereIn('country_code', $countriesToEnable)   // only countries the pinned map says ON
    ->where('count_correction_gl_posting_enabled', false)
    ->update(['count_correction_gl_posting_enabled' => true, 'updated_at' => now()]);
```

**"Explicitly set" needed no heuristic, and I want to be precise about why.** The brief allowed for the possibility that an edited setting is indistinguishable from a default. It is not, because the setting did not exist before this lane: it is being *introduced* here, in the shape T9 already uses, where the company column is **nullable and undefaulted** and NULL means "never decided". So the migration's guarantee is stronger than a predicate — **it never writes the companies column at all**. A tenant that set `false` keeps `false` because nothing touches it; a tenant that never touched it keeps NULL and re-inherits any future country ruling instead of being frozen at today's answer. Both are pinned (`test_a_company_that_explicitly_set_false_stays_false_across_the_migration`, `test_the_migration_never_stamps_an_override_on_an_untouched_company`).

The `country_inventory_settings` half **is** rewritten, and that is deliberate and consistent: the sibling `inventory_valuation_mode` is pinned by its seeder on every run for the stated reason that the country row *is* the jurisdiction, not operator state. The `whereIn` keeps the raise inside the pinned map, so a future country ruling of `false` is expressed in `CountryInventoryDefaults` and is not stomped by a re-run.

**MIGRATION-BEARING, fleet-safe.** Additive DDL plus one narrow UPDATE; no constraint existing rows could violate, so no violation census is required. The what-will-move census is in the migration docblock:

```sql
SELECT country_code, count_correction_gl_posting_enabled
FROM country_inventory_settings WHERE count_correction_gl_posting_enabled = false;

SELECT id, name, count_correction_gl_posting_enabled
FROM companies WHERE count_correction_gl_posting_enabled IS NOT NULL;   -- NEVER touched
```

Exercised from scratch on PostgreSQL (database created and dropped) in §5.

## 7. Residuals

* **R-1 (owner, LEDGER — supersedes the C-33 (iv) wording).** The expert-comptable review of the Option A 6586/7586 liasse presentation is **re-sequenced, not cancelled**. It now has a lever that needs no deploy: a tenant whose accountant disagrees turns posting off in Settings → Inventory, keeps the costed movement rows, and can rebuild the ledger later. Nothing in this lane ratifies the account choice.
* **R-2 (owner, LEDGER — now LIVE, was contingent).** W4-6 residual **R-8**: the pre-count half of the ± ambiguity window resolves by posting, so a `basket_window` line whose nearby movement was booked before the count but shelved after it produces a wrong stock correction — and, from this lane onward, **a wrong journal entry too**. `is_flagged` plus the `basket_window` chip remain the only signal. Excluding `basket_window` lines from GL until reviewed is still a design option, still not taken.
* **R-3.** `config('inventory.count_correction_gl_posting_enabled')` is now the SYSTEM link, not the gate. Setting `INVENTORY_COUNT_CORRECTION_GL_POSTING_ENABLED=false` in a deployment turns posting off for every company **that has not set its own override** — it does not override a tenant that explicitly said `true`. That is the intended precedence (a tenant's own decision outranks a fleet default) but it means the env var is not a universal off switch. Stated so nobody reaches for it as one in an incident.
* **R-4.** `country_inventory_settings.count_correction_gl_posting_enabled` carries **no CHECK constraint** and no ops UI. It is a plain boolean pinned by the seeder, so an out-of-band write survives only until the next provisioning run of that tenant. The sibling `inventory_valuation_mode` has a CHECK because its column is a string that could hold a third value; a boolean cannot.
* **R-5 (FE).** The toggle **saves on change** rather than joining the page's Save batch, because it writes a different endpoint (`PATCH /settings/company`) than the margins/reservation controls. Consequence: no undo affordance beyond re-toggling, and no "unsaved changes" state for this one control. Deliberate — folding it into `hasChanges` would make one Save button mean two different scopes depending on which control was touched.
* **R-6 (i18n, structural).** `apps/web/src/locales/ar/inventory.json` had **no `settings` node at all** — the whole inventory-settings tab is English for Arabic users and is baselined as such (417 `ar|inventory|missing|…` entries). This lane authored `settings.countCorrectionGl.*` in ar, which is the first key under that node, so `apps/web/src/lib/i18n.ts:326-329` now deep-merges `settings` the way it already deep-merges `products`; without that, the shallow spread would have shadowed every other `settings.*` key English supplies. The remaining Arabic inventory-settings gap is untouched and belongs to the standing Arabic backfill lane.
* **R-7 (worktree hygiene).** `apps/api/vendor`, `apps/api/.env`, `node_modules` and `apps/web/node_modules` were copied in to run the lanes; all ignored, none in any commit. Throwaway `autoerp_test_p1` was dropped.
* **R-8 (not taken, rule 4).** `CompanySettingsData` is a shaped array with no `#[TypeScript]` attribute, so `php artisan typescript:transform` does not cover it; the FE contract for this payload is hand-maintained in the component (as the T10 valuation leg already is). Generating it is a separate concern for the whole DTO, not a bolt-on here.
