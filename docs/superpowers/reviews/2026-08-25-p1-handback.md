Structurally `CountCorrectionGlPostingResolver` is `InventoryValuationModeResolver` with a boolean where the enum was — deliberately the same idiom, not a second one.

## 3. The migration and its predicate

`apps/api/database/migrations/tenant/2026_08_25_140000_seed_count_correction_gl_posting_default.php`

Three steps, each independently `hasTable`/`hasColumn`-guarded and re-runnable:

1. add `country_inventory_settings.count_correction_gl_posting_enabled` — `boolean NOT NULL DEFAULT true` (PostgreSQL backfills existing rows from the DEFAULT inside the same `ALTER TABLE`, so on a first run step 3 finds nothing to do);
2. add `companies.count_correction_gl_posting_enabled` — `boolean NULL`, **undefaulted**;
3. the flip:

```php
DB::table('country_inventory_settings')
    ->whereIn('country_code', $countriesToEnable)   // only countries the pinned map says ON
    ->where('count_correction_gl_posting_enabled', false)
    ->update(['count_correction_gl_posting_enabled' => true, 'updated_at' => now()]);
```

**"Explicitly set" needed no heuristic, and I want to be precise about why.** The brief allowed for the possibility that an edited setting is indistinguishable from a default. It is not, because the setting did not exist before this lane: it is being *introduced* here, in the shape T9 already uses, where the company column is **nullable and undefaulted** and NULL means "never decided". So the migration's guarantee is stronger than a predicate — **it never writes the companies column at all**. A tenant that set `false` keeps `false` because nothing touches it; a tenant that never touched it keeps NULL and re-inherits any future country ruling instead of being frozen at today's answer. Both are pinned (`test_a_company_that_explicitly_set_false_stays_false_across_the_migration`, `test_the_migration_never_stamps_an_override_on_an_untouched_company`).

The `country_inventory_settings` half **is** rewritten, and that is deliberate and consistent: the sibling `inventory_valuation_mode` is pinned by its seeder on every run for the stated reason that the country row *is* the jurisdiction, not operator state. The `whereIn` keeps the raise inside the pinned map, so a future country ruling of `false` is expressed in `CountryInventoryDefaults` and is not stomped by a re-run.

**MIGRATION-BEARING, fleet-safe.** Additive DDL plus one narrow UPDATE; no constraint existing rows could violate, so no violation census is required. The what-will-move census is in the migration docblock:

```sql
SELECT country_code, count_correction_gl_posting_enabled
FROM country_inventory_settings WHERE count_correction_gl_posting_enabled = false;

SELECT id, name, count_correction_gl_posting_enabled
FROM companies WHERE count_correction_gl_posting_enabled IS NOT NULL;   -- NEVER touched
```

Exercised from scratch on PostgreSQL (database created and dropped) in §5.

## F-2 — the ledger does not get the benefit of the doubt

The gate's probe A2 was the sharp end and it reproduced exactly, red, before any edit: a sale stamped in the **same second** as the count, on a line whose `final_qty_movement_marker` is NULL, is subtracted a second time — on-hand `56 → 52` — and this lane's flip turned that guess into **one shrinkage entry**.

`MovementReplayService::signedDelta()` `:105-114` says so itself: with a null marker "the boundary second stays inclusive — the r1 semantics, unchanged". W4-6's order-based tie-break simply cannot run without a marker, and markers are written on the submit path, so the exposure is precisely **counts in flight across the upgrade** — the window this promotion opens.

**The rule, and why it is narrower than "NULL marker ⇒ no GL".** A null marker only changes the arithmetic when the boundary second actually carries a movement; the marker branch narrows nothing else, so for an empty boundary second a marker-less line and a marker-bearing line compute the identical delta. Keying the refusal on the null marker alone would therefore withhold a **correct** journal entry from every line counted before the marker columns shipped — the overwhelming majority, whose replay is not in doubt at all. A correct entry suppressed is a cost, not a saving. The condition is `marker === null && boundarySecondIsAmbiguous(...)`, and the existing suite is the evidence that the flat rule over-blocks: every case in `CountCorrectionGlPostingTest` builds items with no marker, and all of them are unambiguous.

**Stock applies, value does not.** `CountingItemFlagReason::MissingBoundaryMarker` answers a **third** question the enum did not have — `blocksGlPosting()`. `isBlocking()` true (the reviewer sees the line), `blocksStockApplication()` **false** (refusing the shelf correction would strand the operator mid-count with a shelf nobody can fix), `blocksGlPosting()` true (an unprovable number is far more expensive to undo in a ledger than on a shelf). The withheld posting is `Log::warning`-ed with the movement id, company id and reason, so the entry can still be built by hand after review — the movement is written and costed either way.

**When a NULL marker can occur** (the gate asked this documented): `final_qty_movement_marker` is stamped by `InventoryCountingItem::submitCount()` and frozen at finalize / manual override (`InventoryCountingService.php:1110`, `:1221`). It is NULL for (a) lines submitted before `2026_08_25_120000_add_count_movement_markers_to_counting_items` ran on that tenant — a count open across the upgrade; (b) legacy rows predating W4-6 entirely; (c) any future write path that sets `final_qty_as_of` without going through `submitCount()`. It is **not** NULL for anything a first tenant counts after promotion, so the blast radius is the upgrade window and existing dev/staging/demo data.

**Report semantics, stated once.** `variance_applied` has always meant *reached STOCK* and still does — the gate's own NEW-4 note on W4-6 said as much. `gl_posted` is the VALUE half, which that column never spoke for. `gl_not_posted_reason` is null when no reason on **this line** withheld the entry; it does not assert an entry exists, because posting can also be off for the whole company, which is a setting rather than a property of the line.

So every non-historical, non-flat count-correction movement written **before** the flip, above that cutover, with no movement-keyed entry, becomes a permanent D-e finding the moment posting is on — and those movements were movement-only *by the then-current design*, not failures. D-e is the compensating control for the missing-chart fail-soft (stock corrected, zero GL, only a `Log::warning`), so a detector that exits 1 on historical noise is a detector nobody reads and the genuine findings drown. **Reachability: zero for a freshly provisioned first tenant; non-zero for any tenant that finalized a varying count between T21 landing and this flip — dev/staging/demo at minimum.** No code this round, per the condition. Run this per tenant before promotion and either accept the count knowingly or stamp a per-company `count_correction_gl_posting_enabled_at` and filter D-e's counting arm on it (advancing `inventory_gl_cutover_at` would blind the other arms and is not recommended):

```sql
-- movements that become D-e findings the moment posting goes on, per company
SELECT sm.company_id, count(*)
FROM stock_movements sm
JOIN companies c ON c.id = sm.company_id
WHERE sm.reason = 'count_correction'
  AND sm.is_historical = false
  AND sm.quantity_before <> sm.quantity_after
  AND sm.created_at >= c.inventory_gl_cutover_at
  AND NOT EXISTS (
    SELECT 1 FROM journal_entries je
    WHERE je.source_id = sm.id AND je.source_type = 'inventory_shrinkage')
GROUP BY sm.company_id;
```
