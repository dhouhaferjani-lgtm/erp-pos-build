# Session G imports hardening — adversarial spec review, round 1

**Baseline reviewed:** `a4ceeb0f5`. Current source under `apps/api`, `apps/web`, `apps/pos`, and `packages/shared` has no diff from that baseline.  
**Verdict:** **REWORK**.

The census-then-refuse migration pattern, RUL-1 preview choice, and RUL-3 one-writer/presets shape are sound. The design is not executable safely yet. In particular, M2 contradicts the binding cross-company barcode ruling, duplicate execution has no durable per-row outcome and conflicts with multi-location imports, and the proposed opening reset can reverse the wrong location and leave batch stock inconsistent with aggregate stock.

## Verdict: REWORK

The next spec revision must resolve these gate conditions before implementation lanes start:

1. Preserve/define a cross-company barcode namespace and complete the variant consumer/constraint-name census (G-R1–G-R2).
2. Define deleted-holder behavior for product SKU and partner VAT, including request/import/generator handling (G-R3).
3. Remove XLSX money/quantity floats and replace G-8’s numeric-cell assertion with an exact-decimal contract (G-R4).
4. Add durable per-row duplicate outcomes, execute-time reclassification, and product-master versus product-location duplicate semantics (G-R5–G-R6).
5. Resolve the blank-SKU/same-name identity contradiction and make sequence allocation first-use/manual-create safe (G-R7–G-R8).
6. Replace the current product-wide reset call with one atomic, location- and batch-aware opening correction operation (G-R9–G-R11).
7. Preserve source blank provenance and distinguish deliberate computed NULLs; enumerate and deliberately amend all cited pinned tests (G-R12).
8. Complete warning/error enums and JSONB DTOs, and repair synthetic party-code identity (G-R13–G-R14).
9. Perform evidence-based company backfill and define unattributed history without a “first company” visibility guess (G-R15).
10. Make country convention backfill migration-owned, validate reversible export mappings/SQLite queries, and serialize every F1-colliding lane after F1 (G-R17–G-R19).
11. Enforce CompositeItems module entitlement, use one atomic execute claim in both paths, and make ProductImages company/hash/source retention explicit (G-R20–G-R22).

## Deliberately NOT taken

- **No objection to census-then-refuse or forward-only M1/M2/M3.** The payment-method precedent is appropriate, and an auto-migration should abort the affected tenant before dropping a constraint if a collision exists. The staging tenants’ prior 23505s are evidence that conflicting inserts were rejected, not proof that every tenant is clean; the runtime census and pre-promotion read-only census remain justified.
- **No POS SQLite schema migration required for company-scoped SKU.** The device database is company-selected and local product/variant writes key by entity ID; server catalog endpoints are company-scoped. The missed consumers are ProductImageImportService and the variant constraint/label services, not POS storage.
- **No report rewrite required solely for SKU scope.** Current sales reporting joins/groups on `product_id`; SKU is a display label.
- **No rejection of PostgreSQL nested transactions.** Laravel creates savepoints for nested transactions, and `ProductCostLock` sorts product IDs. The defect is the absence of an explicitly atomic, location/batch-aware correction coordinator—not SAVEPOINT support itself. No independent deadlock was demonstrated from the proposed SKU lock while the current row/finalize transaction boundary remains; document lock ordering if that boundary changes.
- **No new import queue required.** Both jobs use `imports`, and Horizon covers it. The reaper should remain a per-tenant scheduled console command.
- **No request for a second customer/supplier writer.** RUL-3’s Parties presets are the correct shape. Keeping both balance columns and the existing signed AR/AP convention is defensible and compliant.
- **No demand for a magic clear token.** “Blank preserves on update” is defensible if deliberate domain-computed NULLs remain able to clear stale derived fields and UI edit remains the explicit clearing path.
- **No rejection of aggregate duplicate preview cost by itself.** Three batched queries per 500 rows is roughly 300 lookups for 50,000 rows and is plausible. The gate issue is durable row classification, execute-time drift, and side-effect identity; benchmark/index evidence can settle performance.
- **No claim that ordinary ProcessImportJob currently relies on CompanyContext.** It already receives company and tenant IDs explicitly. The spec should preserve that and close the ProductImages/special-branch gap.
- **No rejection of nullable `import_jobs.company_id`.** Ambiguous historical jobs justify NULL permanently. The objection is discarding attribution that can be recovered and assigning NULL visibility to an arbitrary first company.
