## Part 2 — verification of v3's NEW claims (the five asked, plus what they turned up)

### (a) `cartStore.ts:508-518` makes the line discount TTC — **TRUE**; the canonical key is `line_items[].line_discount_amount`
`apps/pos/src/stores/cartStore.ts:508` `const grossTotal = bcmul(item.unit_price, String(item.quantity), decimals)` — `item.unit_price` is the tax-inclusive cart price, so `grossTotal` is TTC; `:511` percentage discounts are taken **off `grossTotal`**, `:514` a fixed amount is subtracted from it (`:515 rawTotal = bcsub(grossTotal, discountAmount)`), and `:519` recomputes `tax_amount` from the post-discount `lineTotal`. The discount is therefore TTC in both modes.
The canonical key is **`payload.line_items[].line_discount_amount`** — declared at `apps/pos/src/lib/fiscal/payloads/AccountChargePayload.ts:69`, emitted at `apps/pos/src/lib/accountCharge/accountChargeService.ts:383` (`line_discount_amount: bcformat(line.lineDiscountAmount, scale)`), part of the canonical key set (`FiscalEventEngine.ts:2119`), validated server-side at `FiscalPayloadConstraintValidator.php:2165,2187`, typed at `Fiscal/Domain/DTOs/Canonical/LineItemDTO.php:57`, and read into `document_lines.discount_amount` at `POSAccountChargeDraftService.php:90`. §D's input list is exact.
**Bonus verification that supports §D:** the ACCOUNT_CHARGE line arm validates money with the **unsigned** regex (`FiscalPayloadConstraintValidator.php:2165-2168` → `moneyRegex()` `:3706-3713`, `/^(0|[1-9]\d*)\.\d{n}$/`). No negative quantity or amount can appear on an account charge, so Task 2's blanket **decrement** direction is provably safe — there is no return line to flip.

### (b) `payload.line_shape_version` — **safe, but only in one precise place**
`POSAccountChargeDraftService.php:68-72` writes `documents.payload` as a **server-authored** envelope with exactly three keys (`fiscal_event_id`, `account_charge_uuid`, `canonical_payload`). The device-signed bytes live *nested* under `canonical_payload`, and `fiscal_events` canonical bytes / `current_hash` / `previous_hash` are never referenced by this service (r1 verified; still true in the file as read).
The mirror `assertExistingDraftMatches()` checks only those three keys (`:149-159`), and `payloadSnapshotsMatch()` `:157,236-243` compares the **canonical snapshot** by sorted deep equality. Therefore:
- stamping `documents.payload.line_shape_version` at **top level** (sibling of `canonical_payload`) touches no hash input and no mirror predicate — **safe**;
- stamping it **inside** `canonical_payload` would (i) corrupt the verbatim device snapshot and (ii) make **every** replay mismatch `payload.canonical_payload` → `pos_account_charge_draft_conflict` → `ApplyFiscalEventProjectionJob.php:414` → dead-letter. That is the exact failure this discriminator exists to prevent, so the location must be pinned in the brief (**C3**).

### (c) "the header/rounding line the document engine already owns" (`BRIEF:28`) — **INVENTED. No such mechanism exists.**
- `Document/Domain/Services/DocumentTotalsCalculator::recalculate()` `:33-56` writes exactly `subtotal`, `line_tax_amount`, `stamp_duty_amount`, `tax_amount`, `total`. **No rounding line, no remainder line, no remainder column.**
- `grep -rn "rounding" app/Modules/Document app/Modules/Taxation` returns only comments (`CreditNoteService.php:271`, `RefundService.php:723`, `ProformaLineAmounts.php:20`, `PostedLineTaxSnapshotBuilder.php:41`) — no document-level rounding artefact.
- The **only** remainder absorber in the repo is GL-side: `AccountingService.php:383-396` — `residual = arFacingTotal − (revenue + vat)`; negative ⇒ `GlResidualRefusal::NegativeResidual`; positive ⇒ **`SystemAccountPurpose::SalesStampDutyPayable` first**, falling back to `SalesRoundingDifferenceIncome/Expense` only when no stamp-duty account exists. `groupTaxByRate()`'s own docblock `:1928-1931` says the per-line recomputation "is biased DOWN relative to the header — which is why the document residual runs positive and needs an absorbing account."
⇒ `BRIEF:28` simultaneously (i) names a non-existent mechanism and (ii) forbids the only real one, without scoping the change that would be required. See **K1-S3-04 / K1-S3-06**.

### (d) `resolveTerminal()` → `terminal.location_id` — **TRUE, and the hard-fail ruling is safe**
`PosCoreReceiptProjection.php:586-600` `resolveTerminal()` queries `Terminal` by `tenant_id`/`company_id`/`event->terminal_id`; the sale lane passes `locationId: (string) $terminal->location_id` at `:1968`; the missing-terminal case is a `Log::warning` + `return` at `:253-261`. `pos_terminals.location_id` is **NOT nullable** (`database/migrations/tenant/2026_01_08_190429_create_pos_terminals_table.php:29-31`, `foreignUuid()->constrained('locations')`), so a resolved terminal always yields a location — the only failure mode is the missing terminal, exactly as `BRIEF:48` says.
**Additional support for the hard-fail ruling:** each projector runs on its **own** projection row/job (`FiscalEventProjectionDispatcher.php:118,187-211`; `ApplyFiscalEventProjectionJob.php:392-421`), so throwing in the account-charge projection does **not** block `TreasuryAccountChargeBridge` or the document bridge for the same event. The hard failure is correctly isolated; `BRIEF:48` is sound.

### (e) `fiscal:seed-account-charge-fixture` "wrapping the existing PHP fixture builder" — **there is no such builder**

### K1-S3-02 [MAJOR] The stated tolerance holds only if the SAME truncated `net_discount` is used in the derivation and in storage
The bound in `BRIEF:28` (`≤ quantity × 10⁻ˢᶜᵃˡᵉ`) is correct **only** when `unit_price = trunc((line_subtotal + D') ÷ quantity)` uses the *stored* `D' = trunc(net_discount)`, because `computeLineTotal` (`DocumentLine.php:280-302`) subtracts that same `D'` and the two cancel. `BRIEF:25-26` computes `net_discount` "at scale+1 then `bcformatStrict`" and `unit_price` "at scale+1" — if the scale+1 discount is used in the numerator while the scale-s value is stored, the residual gains an extra `10⁻ˢᶜᵃˡᵉ` and the mandated tolerance test fails on real data.
**C4:** pin the order — compute `D'` first, truncate it to currency scale, **store that value**, and use *that* value in the `unit_price` numerator. Add a `quantity > 0` guard with a named failure (the payload regex is unsigned but `0.000` is representable, and `bcdiv` by zero is fatal).

### K1-S3-03 [MAJOR] The stamping location for `line_shape_version` must be pinned, or the discriminator becomes the dead-letter

### K1-S3-04 [BLOCKER] `BRIEF:28`'s absorption mechanism does not exist

**C5:** delete the "header/rounding line" clause and replace it with the truth: *under §D there is no header remainder at all — `documents.subtotal`/`tax_amount`/`total` are stored verbatim from the device totals and `Σ line_total == Σ line_subtotal == totals.subtotal`; the per-line derivation remainder exists only in the RECOMPUTING readers (`DocumentTotalsCalculator::recalculate()` `:43`, `TaxCalculationService::calculateSubtotal()` `:364-368`), and its consequences are (a) the confirm-time header rewrite at `InvoiceController.php:645-649` and (b) the VAT-declaration base at `:652`.* Both must be asserted within the §D tolerance, and the confirm-time rewrite (`tax_amount`, `total`) must be named as an explicit test target — it is the only place the derivation remainder can mutate stored money.

### K1-S3-05 [BLOCKER — owner ruling required] An ACCOUNT_CHARGE already books AR + revenue + VAT; making the invoice postable double-recognises the sale
`Treasury/Application/Projections/TreasuryAccountChargeBridge.php:59-101` is a registered `FiscalEventProjector` for `ACCOUNT_CHARGE` that calls `GeneralLedgerService::createPOSChargeEntry()` (`:4528-4620`) with the sealed canonical totals: **AR debit = `totals.total`**, **revenue credit = `totals.subtotal` (NET)**, **VAT credit = `totals.vat_total`** (docblock `:4522-4525`: "it increases AR and recognizes sale revenue/VAT"). ### K1-S3-12 [MAJOR] Task 2 never states how the canonical `product_id` resolves to a server product, or what happens when it does not
`BRIEF:21` promises a "real `product_id`" and `BRIEF:49-50` assume a resolvable product for stock, lots and COGS. ### K1-S3-14 [MINOR] Second-of-everything shape for the new allocation table
