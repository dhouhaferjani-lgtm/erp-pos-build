# Verdict

**Major concerns — not "fixed once and for all."** The four B5 commits genuinely close the *receipt-side* half: the mounted UI flow works, the v3 hash binds the voucher serial, the per-tender writes are atomic with the receipt insert on the offline path, and the online `ReceiptPaymentService` correctly delegates to `VoucherRedemptionService::redeem()` inside the same DB transaction (with `lockForUpdate()` inherited from the redemption service). All 31 new TS tests + 6 new PHP tests pass; PHPStan clean; typecheck clean; v2 path bit-for-bit unchanged; fixture-01 and fixture-08 hashes preserved; no new `app()`/`mixed`/`any` lines.

**But the offline-then-sync path — which is the *only* checkout path the Tauri POS exercises in production (`HomePage` → `processAdvancedCheckout` → `createReceiptLocalFirst` → `createOfflineReceipt`; `executeCheckout`/`onlineCheckout` has zero non-test callers) — never lands the redemption server-side.** The offline writer creates a `voucher_ledger` row with `receipt_id = null`, the sync push pipeline ships it, and `VoucherLedgerPushService::push()` rejects every such row with `'receipt_id_required_for_redemption'` (Service.php:83-85). Worse, the client (`syncService.pushVoucherLedgerEntries`, lines 1068-1081) **only inspects HTTP-level errors**, not the per-entry `status: 'failed'` in the 200 response body, and unconditionally calls `markVoucherLedgerEntrySynced` after `apiPost` resolves. The pending row is marked synced even though the server refused it. Net effect: voucher remains indefinitely re-redeemable on the canonical projection; the local mirror's debit is reverted on the next `pullVouchers`. Spec §6.5 is *still* not satisfied for the production checkout path the cashier actually drives.

This is **B5 Blocker 1** below. The push pipeline (`pushVoucherLedgerEntries`) is pre-existing (commit `d90dd63c`), but B5 is the first commit that creates pending rows that flow through it; B5 lights up a latent bug in its own consumer. The receipt-side redemption *never fires* on the production POS Tauri path.

There is also a smaller correctness gap (B5 Minor 1): `VoucherTenderModal` does not accept the `methodCode` of the tile that was tapped. `restaurant_voucher` and `gift_card` taps open the same modal, but the modal's hard-coded MPV gate means the lookup will always show "Voucher not found" for those kinds. The `Complete` handler in `AdvancedPaymentsModal` then unconditionally hardcodes `instrument_type: 'store_voucher'` for every tender row — so even if the parent set up a non-store_voucher tile to route through here, it would mislabel the resulting tender. Acceptable as Phase 1 (only store_voucher is wired) but the audit-checklist requirement to discriminate by methodCode is not met.

## Outstanding issues

### Blocker — Offline-then-sync redemption silently dropped

The offline path writes a `voucher_ledger` Redeemed row with `receipt_id = null` (`receiptService.ts:442`), and the comment at the top of `voucherRepository.ts:439-440` deliberately calls this out: *"for offline rows `receipt_id` is null at write time, and the push payload uses the ledger `id` as the natural correlation key."* The implementer assumed `receipt_id = null` would be acceptable on push.

It is not. `VoucherLedgerPushService.php:83-85` rejects every entry with null receiptId:

```php
if ($payload->receiptId === null) {
    return $this->failed($payload->id, 'receipt_id_required_for_redemption');
}
```

`pushVoucherLedgerEntries` (`apps/pos/src/lib/sync/syncService.ts:1068-1081`) treats the controller's 200 response (which contains per-entry `{status: 'failed', error: 'receipt_id_required_for_redemption'}`) as a *push success* and unconditionally calls `markVoucherLedgerEntrySynced(db, entry.id)`. The pending row never retries; the redemption never lands on the canonical projection.

`ReceiptSyncService::syncBatch()` does NOT independently call `VoucherRedemptionService::redeem` either — it only writes `pos_receipt_payments` rows with the instrument fields. So neither sync code path produces the redemption journal, decrements the voucher's `current_balance` server-side, or transitions its `status`. The voucher remains `Issued` with full balance, indefinitely re-redeemable.

Local-mirror divergence is also masked: `pullVouchers` (`syncService.ts:929-960`) calls `upsertVouchers` which **overwrites** the local `current_balance` and `status` from the server's canonical state. So on the next sync the local mirror's "FullyRedeemed, balance 0.00" gets reverted to "Issued, balance 50.00" — and the cashier sees the voucher as fresh again.

This is the load-bearing fiscal/accounting hole that B5 was supposed to close. The Codex review B5 finding said: *"On apply/confirm, write a local pending `voucher_ledger` redemption row tied to the local receipt identity, update local voucher projection, and push it through `VoucherLedgerPushService`."* — the **"push it through"** half is *technically* present but **does not actually redeem the voucher** because of the receipt_id contract mismatch.

The `processReceiptPayments` HTTP path that B5 wired up correctly **is reachable**, but only from `POSTransactions.tsx` (web admin POS view) and `ExchangeService` (server-internal). It is NEVER hit by the Tauri POS default checkout — that flow is offline-first via `paymentStore.processAdvancedCheckout` → `createReceiptLocalFirst` → `createOfflineReceipt`. So the entire `156ed65c` commit is sound, but it doesn't cover the production checkout path the cashier actually drives.

What would close this:

- **Option A — backfill receipt_id on push**: extend `pushVoucherLedgerEntries` to look up the receipt's `server_receipt_id` (already set during `pushOfflineReceipts` via `setServerReceiptId`) by joining `voucher_ledger` rows to the receipt that originated them, and populate `receiptId` in the push payload. Requires the offline writer to either tag the ledger row with the local receipt id (`offline_receipts.id` or `idempotency_key`) so the push step can resolve to the synced server id, or to defer the ledger row write entirely until after the receipt syncs.
- **Option B — server-side redemption inside sync**: have `ReceiptSyncService` itself call `VoucherRedemptionService::redeem` for every store_voucher payment row it writes, mirroring what `ReceiptPaymentService` does at line 284-303. That sidesteps the push pipeline for offline-originated receipts. The push pipeline can be reserved for refund-issued vouchers later.
- **Option C — both**: Option B for first-pass correctness, plus tighten the push client to actually inspect per-entry `status` from the controller's 200 response and route `'failed'` to `markVoucherLedgerEntryFailed` for retry.

Either way: a real end-to-end integration test that runs the **full sync push** against a stub server returning the controller's actual response shape, asserts the voucher's canonical state moves AND the local pending row only marks synced on `'synced'`/`'duplicate'` per-entry status, would have caught this.

### Minor 1 — VoucherTenderModal can't discriminate by tile methodCode

`requiresInstrumentForMethodCode` returns true for `store_voucher`, `restaurant_voucher`, AND `gift_card` (verified — see `PaymentInstrumentKind::cases()`). All three open `VoucherTenderModal`. But:

- The modal hard-codes `SUPPORTED_VOUCHER_KIND = 'MPV'` (`VoucherTenderModal.tsx:49`). Restaurant vouchers and gift cards aren't stored in the local `vouchers` table at all (per spec §3.2.1, restaurant vouchers are tracked only on `pos_receipt_payments.instrument_type`). So a `restaurant_voucher` tap → modal opens → cashier types code → `findByCode` returns null → "Voucher not found" cashier error. Confusing UX for Phase 1 — those tile taps shouldn't open the modal at all.
- `addVoucherPayment(code, amount)` (`paymentStore.ts:485-497`) does not carry `instrumentType`. When `AdvancedPaymentsModal::handleComplete` builds the `voucherPayments` array (lines 354-362), it unconditionally hardcodes `instrument_type: 'store_voucher'`. So even if the modal accepted a different kind, the resulting tender would mislabel itself.

This is acceptable for Phase 1 (only store_voucher is wired end-to-end), but the audit-checklist asked: *"Verify it accepts a `methodCode` / `expectedMethodCode` prop and uses it to set `instrumentType` correctly on apply."* — that requirement is not met. Recommend either:

(a) gate the tile-tap routing so only `store_voucher` opens the modal in Phase 1; `restaurant_voucher` and `gift_card` tiles surface a Phase-2-deferred message; or  
(b) thread `methodCode` through both `VoucherTenderModal` and `addVoucherPayment` so the discriminator is correct end-to-end and won't need refactoring when Phase 2 lands.

### Minor 2 — Push-pipeline tests bake in the silent-drop

`apps/pos/src/lib/sync/__tests__/voucherSync.test.ts:251-261` `'posts each pending entry and marks it synced on success'` mocks `apiPost.mockResolvedValueOnce({})` and asserts `markVoucherLedgerEntrySynced` is called. There is no test for the case where the controller returns 200 + `{status: 'failed', error: '...'}` per entry. The current `pushVoucherLedgerEntries` implementation gives that case "synced" status anyway, so even if a future server-side fix adds `receipt_id` validation that the controller exposes via the structured response, the client will still pretend it succeeded. The test asserts the bug.

A targeted regression test should: mock `apiPost.mockResolvedValueOnce({ data: { results: [{ id: 'ledger-1', status: 'failed', error: 'receipt_id_required_for_redemption' }], synced: 0, duplicates: 0, failed: 1 } })` and assert `markVoucherLedgerEntryFailed` is called.

### Minor 3 — Idempotency contract not actually present

`receiptService.ts` docblock at lines 433-438 claims: *"the push payload uses the ledger `id` as the natural correlation key."* But `VoucherLedgerPushService.php:30-35` says: *"the client-supplied `id` is NOT persisted to voucher_ledger.id (the redemption service generates a server-controlled UUID); it round-trips back to the client only as a correlation key in the response."* The "natural correlation key" the implementer documented does not exist on the canonical voucher_ledger projection — it's only echoed back in the response payload. So a retry of the same offline ledger row would not be deduplicated by `id` server-side; deduplication is via `(voucher_id, receipt_id, event=Redeemed)` (which can never match because receipt_id is null).

In practice, retries don't happen because the silent-drop in Minor 2 marks every row synced on first push. But if the client ever did get fixed to retry on `'failed'`, the fix would also need to address idempotency.

### Nit — `voucherCheckout.integration.test.ts:15` describes a non-existent assertion

The docblock at line 14-15 says: *"a pending voucher_ledger Redeemed row exists with the receipt's idempotency key as its id-prefix correlation point"* — but the actual test at line 199 asserts `voucher_id` only and there is no idempotency-key assertion in the test (as expected, since no such tie exists in the schema). The docblock is stale narrative from the audit checklist; the test itself is fine. Recommend a docblock fix for clarity.

## Adversarial probes

## Recommendation

Do not declare B5 closed "once and for all" until the offline-then-sync redemption path actually lands the voucher state on the canonical projection. The receipt-side work in `156ed65c` is sound but unreachable from the production POS Tauri checkout. Either:

1. Have `ReceiptSyncService` invoke `VoucherRedemptionService::redeem` for every store_voucher payment row it ingests (mirrors the online path; sidesteps the `receipt_id`-null contract problem entirely); OR
2. Tag the offline `voucher_ledger` row with the originating local receipt id, backfill `receipt_id` from `setServerReceiptId` after `pushOfflineReceipts` completes, AND fix `pushVoucherLedgerEntries` to inspect per-entry status from the controller's structured 200 response.

Option 1 is the smaller delta and aligns with the existing online path. Either way: an integration test that runs the **full sync push** against a stub server returning the controller's actual response shape, asserts the voucher's canonical state moves AND the local pending row only marks synced on `'synced'`/`'duplicate'` per-entry status, would have caught the silent drop.
