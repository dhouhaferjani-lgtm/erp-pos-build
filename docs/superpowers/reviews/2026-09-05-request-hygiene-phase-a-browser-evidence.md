### Guards — what is measured and what is tolerated

**All 32 legs install the 5xx + console-error guard and report their MEASURED counts in the table below. 31 of 32 assert both are zero**; the single exception is `RH-T6-b`, which asserts its 5xx count and the T6 scope contract but deliberately does **not** assert zero console errors — the one it emits is the F-RH-3 defect and is reported as that leg's FAIL verdict instead of being tolerated away (gate BLK-1 ruling). A per-leg audit script confirms the split: 32/32 install, 31/32 assert `counts.detail === '[]'` or `assertClean()`, 1 documented exception — including the two SETUP reuse branches, which in rev 1 printed constants. There are no hardcoded counters left anywhere in the spec (`grep -c 'fivexx: 0'` = 0).

A deliberately forced failure is fulfilled through `guards.forceFail(route, status, body)`, which registers **that exact `Request` object** plus a budget of **one** console line for it. A second, unforced 5xx on the same URL is therefore *not* swallowed — the rev-1 path-scoped tolerance was the gate's MAJ-5. Tolerance state lives on the guard, so it dies with the leg and cannot leak into the next one (gate MIN-4); `harnessPaths` is cleared in `stop()` for the same reason.

The complete tolerance list (`support.ts:namedTolerance`, all disclosed):

| # | Tolerated | Why it is not a product signal |
|---|---|---|
| a | `/auth/me` 401 on `/login` or `/register` | the standing K-10 class: the public auth pages probe the session |
| b | `WebSocket connection to ws(s)://…/app/…` failed | no Reverb on this stack unless a leg mocks one |
| c | any failure whose URL is `https://fonts.(googleapis\|gstatic).com/…` | third-party origin; `index.html:10-13` loads Public Sans / IBM Plex Mono / Montserrat from a CDN. Declared explicitly rather than as a wildcard |
| d | a **4xx** on a path the harness itself fetched via `apiJson` in this leg | the leg expects that status; 5xx is still caught |
| e | one console line per response **this leg forced**, budgeted 1:1 | the browser logs the failure the leg created |
| f | a component's own `console.error` named by the leg (`Payment recording failed`, `Auto-save failed`) | the component reacting to (e) |

**Not tolerated, on purpose:** the 422 that `RH-T6-b` provokes. It is the F-RH-3 defect, so the leg is recorded **FAIL** and the number is its evidence (gate BLK-1 ruling).

## §Findings

### F-RH-1 · T3 · payment search does not escape LIKE wildcards — **MAJOR (P2), CONFIRMED**
`PaymentController::index()` interpolates the term raw (`apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:283-290`); the sibling shipped in the same programme escapes (`StockMovementController.php:79-93`, `LIKE ? ESCAPE '!'`).
Measured (`RH-T3-c`) against `RH-PAY-001 … RH-PAY-030`: `RH-PAY-00_` → **9**, `RH-PAY-0%1` → **12**, control `RH-PAY-001` → **1**. Escaped would be 0 / 0 / 1. Ledger verdict FAIL. Owner lane: T3; already a declared Task 3 follow-up, this is the empirical confirmation.

### F-RH-2 · Document module · draft autosave silently discards every header edit after the first save — **MAJOR (P2), NEW / UNDECLARED**
`DraftPersistenceService::saveDraft()` takes the `else` branch for an existing draft and calls `updateDraftLines()` under the comment "Update existing draft (lines only, header is immutable for now)" (`apps/api/app/Modules/Document/Domain/Services/DraftPersistenceService.php:135-136`).
Measured (`RH-T14-a`): five autosaves carrying `RH-T14 body 1 … 5`, every one answered 200 and the UI reported saved; `psql documents.notes` stayed at **`RH-T14 body 1`**.
Neither the Phase-A plan nor the night handover mentions "header is immutable"/"lines only", so this is **not a declared residual**. An operator who edits notes, date or partner after the first autosave and navigates away loses those edits while the UI says they were saved. Not a Task 14 regression — T14's serialization contract holds — but it makes "the last typed value is persisted" untrue for header fields. Owner lane: Document / draft persistence.

### F-RH-3 · company switch · the mounted document editor replays the old company's product ids under the new scope — **P3**
Measured (`RH-T6-b`, ledger **FAIL**): with `/purchases/orders/new` open on a company-1 line, switching company issues `POST /api/v1/line-entry/pricing-context/bulk` with `X-Company-Id` = company 2 and company-1 `product_id`s → **HTTP 422**, surfaced as a console error.
Product code: the editor keeps its lines across a scope change — `apps/web/src/features/documents/components/DocumentLineEditor.tsx:397-405` (`pricingContextLines` reads `lines`, which nothing resets on a company switch), feeding `:414` `debouncedPricingLines`, `:421-426` `pricingContextEnabled` and the query at `:428-438`; the switch itself only invalidates (`apps/web/src/components/organisms/CompanySelector/CompanySelector.tsx:41-48` — note a second, unrelated `apps/web/src/components/layout/CompanySelector.tsx` exists). Line numbers re-verified on `d56d62535`, which carries PR #214's credit-note changes to this file. The scope half of the T6 contract holds (0 requests under the old company); the editor should drop its lines or unmount instead of replaying them. Direct sibling of the filed `F-W2-44`. Owner lane: FE company-scope / placeholder follow-up.

### F-RH-4 · T8 · the gap-recovery sweep does not fire for a peer-initiated socket close — **P2, PRE-EXISTING (inherited, not introduced by T8)**
`apps/web/src/providers/WebSocketReconnectProvider.tsx:55` keys off `useWebSocketConnection().isConnected`, which is driven only by pusher's `connected` / `disconnected` / `error` events; `unavailable` merely increments `failedAttempts` and never clears `isConnected` (`useWebSocketConnection.ts:94-133`).
Measured (`RH-T8-a`), with the in-page pusher `state_change` trail captured:
- peer-initiated close ×2 → trail `connected→connecting→connected` → **0 refetches** (no sweep, cooldown never armed)
- explicit `pusher.disconnect()` + `connect()` → `connected→disconnected→connecting→connected` → **exactly 1 refetch**
- a second explicit cycle inside the 30 s window → **0 refetches** ✓
**Provenance:** the hook was last touched by `bc1dd4faf` (2026-07-02) and the provider's dependence on `isConnected` predates Phase A; T8's own commits (2026-09-04, latest `e56b6b6a7`) only reworked the cooldown. T8 **inherits** this, it did not introduce it.
**Limit of the claim:** the drop was a **server-initiated clean close** produced by `page.routeWebSocket`; the close code is not recorded and no real Reverb restart or network drop was measured. The extrapolation to "laptop sleeping / network blip" is a hypothesis this run does not prove — it proves the peer-close case. Suggested direction: treat any `state_change` away from `connected` as the disconnect edge.

### F-RH-5 · i18n · 15 plural keys are dead because they use the i18next v3 suffix — **P4, systemic (re-rooted)**
Not "the plural form is missing": it **exists** and is never selected. i18next v4 JSON expects `_other`; the repo has no `compatibilityJSON: 'v3'`, so every `_plural` key is inert. `apps/web/src/locales/en/` holds **15 `_plural` keys against 31 correct `_other` ones**:
`locations.json:6` · `common.json:942` · `products.json:6, 27, 32, 93, 96` · `inventory.json:101, 121, 248, 338, 385, 974` · `compliance.json:126, 192`.
Visible in this run as `43 movement recorded` / `0 movement recorded` (`inventory.json:338` `movements.subtitle_plural`) in `RH-T2-a` and `RH-PLACEHOLDER-b`. Mechanical fix (`_plural` → `_other`); the scope is 15 keys across five namespaces, not one label.

### F-RH-6 · Purchase-order detail page offers "Record Payment" against an endpoint that always refuses it — **MAJOR (P2 UX)**
Now carries its own evidence (`RH-F6-a`, artefact `evidence/F-RH-6-422.json`). `PurchaseOrderDetailPage.tsx:325` turns the button on for `confirmed`/`received` POs with an outstanding amount and mounts the modal at `:709`; the endpoint refuses **both** states with `422 DOCUMENT_NOT_ALLOCATABLE`:
