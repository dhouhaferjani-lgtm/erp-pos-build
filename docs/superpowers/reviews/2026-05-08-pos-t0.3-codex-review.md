## Findings

### BLOCKER: Timeout path still marks receipt sync as `failed`, contradicting the unknown-state contract

The helper's caller contract says timeout means unknown sync state and callers should **not** mark receipts failed locally because the next sync tick should reconcile through the stable idempotency key [apps/pos/src/lib/fetchWithTimeout.ts:35](../../apps/pos/src/lib/fetchWithTimeout.ts#L35)-[38](../../apps/pos/src/lib/fetchWithTimeout.ts#L38). The receipt-sync caller says the opposite in its local comment: on `FetchTimeoutError`, the catch marks the receipt `failed` with the typed error message [apps/pos/src/lib/sync/syncService.ts:247](../../apps/pos/src/lib/sync/syncService.ts#L247)-[250](../../apps/pos/src/lib/sync/syncService.ts#L250). The actual catch does exactly that for every thrown error, including `FetchTimeoutError`: it derives `message` from `error.message`, increments retry count, updates receipt status to `failed`, logs the same message, pushes it into the sync error array, and increments `failed` [apps/pos/src/lib/sync/syncService.ts:320](../../apps/pos/src/lib/sync/syncService.ts#L320)-[333](../../apps/pos/src/lib/sync/syncService.ts#L333).

The retry query does include `failed` receipts under the retry cap [apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts:138](../../apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts#L138)-[145](../../apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts#L145), so the receipt is not permanently abandoned immediately. But for a TIER-0 cashier-blocking fix, the implementation still violates its own unknown-state invariant and temporarily records a successful-server/unknown-client receipt as a local failure.

## Overall Recommendation

REQUEST-CHANGES. The core `fetchWithTimeout` primitive is structurally sound: it races Tauri fetch against a JS timeout, translates signal-honored aborts, and clears timers through `finally`. But the receipt-sync call site still records a timeout as a local `failed` receipt despite the helper's own unknown-state contract, and the typed timeout message includes the full URL, which can flow through existing log and UI surfaces. For a TIER-0 cashier-critical hotfix, fix those two surfaces before approving.
