The CRITICAL question raised by the brief — is `where('company_id', $companyId)`-only scoping in PartnerBalanceService sufficient? — resolves to **NICE-TO-HAVE, not REQUEST-CHANGES**, with explicit caveats documented in Finding 1 below. Verdict: **APPROVE** (Finding 1 referred to a follow-up sibling cluster, not applied as part of this review). The committer's reasoning ("companies are tenant-owned, so a foreign tenant's partner UUID cannot match `where('company_id', $companyId)`") is correct *iff* the `$companyId` parameter itself is constrained to the user's tenant. The PartnerBalanceController route signature (`public function refresh(string $companyId, string $partnerId)`) accepts `$companyId` as a route parameter that is NOT structurally validated against the user's tenant or `UserCompanyMembership` rows — `CompanyContextMiddleware::userHasAccessToCompany` validates the `X-Company-Id` header (or the user's default company), not the route segment. A user from tenant A who is a member of company X could in principle send `POST /api/v1/companies/{tenant-B-company-id}/partners/{tenant-B-partner-id}/balance/refresh` with `X-Company-Id: X` (so middleware passes) and exfiltrate / mutate balances on a foreign tenant's partner row, because the service-tier scope `Partner::query()->where('company_id', $companyId)->whereKey($partnerId)->firstOrFail()` would happily resolve the cross-tenant partner. **However**, this is a **pre-existing controller-tier bug** in PartnerBalanceController routing that is OUT OF SCOPE for the api.accounting inventoried callsites (which are service-tier and validator-tier) and NOT a regression introduced by this commit. The api.accounting fix is a strict improvement (was: bare `Partner::findOrFail` with no scoping at all; now: at least company-scoped). The Treasury R3 F14 strict reading would still prefer both predicates as defense-in-depth — promoting this to REQUEST-CHANGES would require the api.accounting cluster owner to fix a controller-tier route guard that does not appear in their inventoried callsites and that is the api.partner / api.accounting-controller responsibility. Filing as Finding 1 (NICE-TO-HAVE) with a recommended sibling-cluster sweep.

## Findings

1. **Severity: NICE-TO-HAVE (defense-in-depth gap, partially controller-tier responsibility)** — `PartnerBalanceService::refreshPartnerBalance` and `::getCachedOrCalculateBalance` (api.accounting.004/005) scope by `where('company_id', $companyId)` only, not by both `tenant_id + company_id`. The committer's argument in the commit message — "companies are globally unique UUIDs and are themselves tenant-owned, so a foreign tenant's partner UUID cannot match" — is mathematically correct *as a property of the data model*, but it shifts the burden of tenant isolation onto the upstream `$companyId` parameter being trustworthy. The controller chain is:
   - `PartnerBalanceController::refresh(string $companyId, string $partnerId)` reads the route parameter `{companyId}` directly and passes it to the service unchecked.
   - `CompanyContextMiddleware::userHasAccessToCompany` validates the user's access only against the `X-Company-Id` header (or the user's default company membership) — NOT against the route segment `{companyId}`.
   - Therefore an authenticated user from tenant A (member of company X) can send `POST /api/v1/companies/{tenant-B-company-id}/partners/{tenant-B-partner-id}/balance/refresh` with `X-Company-Id: X` (middleware passes), and the service-tier scope would happily load the cross-tenant partner — because both `company_id` and `partner_id` are foreign-tenant and self-consistent.

   This is a **pre-existing controller-tier route-parameter trust bug**, not a regression introduced by this commit. The api.accounting fix narrows the gap (was: zero scoping; now: company-scoped) and is strictly better. The Treasury R3 F14 strict-reading invariant would prefer both predicates so that the service tier provides defense-in-depth even if the controller's route guard is weak — and that is achievable today because the controller already does `requireCompany()` which loads the Company model (and could expose `company->tenant_id`). Suggested follow-up: pass `$tenantId` from the controller (`$this->companyContext->requireCompany()->tenant_id`) into both service methods and add `->where('tenant_id', $tenantId)` to the scope chain. Or open a sibling api.partner-balance-controller cluster to harden the route-parameter trust at the controller tier (validate `route('companyId') === $companyContext->requireCompanyId()`). Either approach closes the gap end-to-end.

   - File: `apps/api/app/Modules/Accounting/Application/Services/PartnerBalanceService.php:296-299, 374-377`
   - File: `apps/api/app/Modules/Accounting/Presentation/Controllers/PartnerBalanceController.php:160-179, 186-194` (controller-tier route-param trust)
   - File: `apps/api/app/Http/Middleware/CompanyContextMiddleware.php:67-74` (membership check is on header, not route)
   - Suggested fix (service tier, defense-in-depth): add a third parameter `string $tenantId` to both methods and prepend `->where('tenant_id', $tenantId)` to the scope chain. Or open a new cluster (api.partner-balance-controller) to fix the route-parameter trust at the controller tier.

## Confidence

High confidence the api.accounting cluster is closed against the Codex Finding-14 invariant for all 7 inventoried callsites at the validator tier (api.accounting.001/002/003) and at the explicitly-typed service signatures (api.accounting.006/007). The two structural-SQL-log invariants pin SQL shape rather than just behavior, so a future regression that drops either tenant_id or company_id from `getAccountDetails` or the journal-entry account validator would fail loudly. Pre-fix bug-reproduction confirms the tests exercise real defects, not vacuous green lines.

Lower-but-still-acceptable confidence on api.accounting.004/005 (PartnerBalanceService company-only scope). The fix is a strict improvement over the pre-fix state (was: zero scoping; now: company-scoped), and the structural argument ("companies are tenant-owned, foreign partner UUIDs cannot match foreign company_id") holds *in the absence of an upstream attacker controlling `$companyId`*. The actual upstream surface (`PartnerBalanceController::refresh(string $companyId, string $partnerId)`) does not validate the route segment `{companyId}` against the user's `UserCompanyMembership` rows — the middleware only validates the X-Company-Id header. So defense-in-depth requires either (a) hardening the service tier to also pin `tenant_id` (one extra parameter, one extra `where` clause), or (b) opening a sibling api.partner-balance-controller cluster to validate route-param trust at the controller tier. Either approach closes the gap end-to-end. Promoting to REQUEST-CHANGES would force the api.accounting cluster owner to fix a controller-tier bug that is not in their inventoried scope; instead, this is filed as Finding 1 NICE-TO-HAVE for follow-up.
