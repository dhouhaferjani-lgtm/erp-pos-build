## 1. Where the default lived

`apps/web/src/features/documents/components/DocumentLineEditor.tsx:362` (pre-fix) —
`handleAddProduct` seeded every new line from `decimalValue(product.sale_price)` with no
document-type discrimination, and used the same value for `line_total`. That single component is
the line editor for **all** document types: `apps/web/src/components/documents/DocumentLineEditor.tsx`
is only a re-export shim, and `DocumentForm.tsx:777` renders it for PO **create and edit** alike
(`documentTypeToApiEndpoint.purchase_order = '/purchase-orders'`, `DocumentForm.tsx:102`). So one
fix covers both PO surfaces.

There is **no server-side default on the PO create/update path** — the FE sends `unit_price`
verbatim (`buildLinePayload`, `DocumentForm.tsx:226`). The defect was purely client-side; no API
feature test was warranted (and none of the API is touched).

## 3. Permission interaction (verified, not assumed)

`/products` redacts cost fields for callers without `pricing.view_cost_prices`:
`ProductController.php:154-166` → `ProductData::withoutCostFields()` (`ProductData.php:145-155`)
nulls `purchase_price`. A purchaser without that permission therefore lands on **step 3 (EMPTY)** —
which is the correct degradation: a blank field is honest, a retail price is not. No new data is
exposed by this lane; the FE reads a field the endpoint already returned.

Rule compliance: money stays a **string** end-to-end (no `parseFloat`/`Number`), the value is
rendered through the existing `<MoneyInput>`, colours on every touched line are design tokens
(`textColors.warning` / `textColors.secondary`), no hardcoded strings, no `any`, no new TanStack keys.

### Why `''` is normalised to `'0'` at the wire boundary only
`lines.*.unit_price` is `required|numeric` server-side and the **draft autosave fires at keystroke
frequency** (`DocumentForm.tsx:331-350`), so leaving `''` in the payload would turn an unpriced line
into a stream of 422s and trip the autosave-failed / beforeunload guard. `''` is therefore a UI
state only: the operator sees a blank field, an unsaved-yet-drafted line is visibly worth nothing
(the honest state), and it can never become the retail price.

## 7. Residuals seen and NOT touched (out of lane scope)

1. **P2 — `/line-entry/resolve-code` does not redact cost fields.** `LineEntryController.php:41-56`
   returns a full `ProductData` (with `purchase_price`, `cost_price`, `last_purchase_cost`) with no
   `withoutCostFields()` call, while `/products` (`ProductController.php:154-166`) does. A barcode
   scan leaks cost data to a user without `pricing.view_cost_prices`. Pre-existing; a tenancy/authz
   lane, not this one.
2. **P3 — `AddQuickProductModal.tsx:224`** does `sale_price: parseFloat(data.sale_price)` —
   a rule-19 float-on-money violation on a live path. Pre-existing, outside the brief's files.
3. **No supplier-specific purchase price anywhere in the product.** Step 1 of the funnel is a
   documented hole. If the owner wants per-supplier buying prices, it needs either a
   `kind` discriminator on `price_lists` (+ a purchase branch in a NEW resolver — `PricingService`'s
   order is locked and sale-only) or a `supplier_products` table. Not a bug; a missing capability.
4. **A stored `purchase_price` of exactly `0.000` is treated as a real price**, not as absent
   (`isBlankMoney` only rejects null/undefined/blank). Matches the server-side
   `DraftPurchaseOrderService` semantics. Flagging in case the owner prefers 0 → EMPTY.
5. **N-14 orphan draft POs** (`PO-2026-0001…0009`, 0.000 totals from StrictMode autosave) are
   unrelated to this lane and untouched. Note that the `''` → `'0'` normalisation above means an
   unpriced line drafts at 0 rather than blocking — deliberate, see §4.
