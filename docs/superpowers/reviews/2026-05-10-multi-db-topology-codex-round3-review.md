It still cannot be approved because two core cutover promises remain unsound as written: rollback replay is not actually captured by the proposed reverse subscription, and initial extraction's write freeze depends on all-table RLS even though the referenced foundation plan only pilots RLS on POS fiscal tables.

## New findings introduced by v3

1. **BLOCKER - §5.B.5 rollback - Reverse logical replication does not produce a since-cutover delta as written.**

   Issue: v3 says rollback replay is now concrete, then proposes: "create publication on TARGET, subscription on SOURCE, sync TARGET->SOURCE delta" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:386-397`). That is not a delta unless a target-side logical slot or change-capture stream was created at cutover. A newly created subscription normally copies a publisher snapshot and then streams subsequent changes; if `copy_data=false`, it streams only future changes. PostgreSQL's logical replication architecture docs describe the initial snapshot plus subsequent change stream (`https://www.postgresql.org/docs/17/logical-replication-architecture.html`), and the conflicts docs warn that local subscriber data can conflict with incoming replicated changes (`https://www.postgresql.org/docs/17/logical-replication-conflicts.html`). The old source is a database already containing the pre-cutover rows.

   Proposed fix: make rollback replay a first-class primitive. Either create and retain a logical slot/publication on the target at the original cutover LSN, add an application outbox/change ledger for post-cutover writes, or define rollback as full target-to-source rebuild plus catalog flip. Until then, keep loss-only rollback as the only implementable branch or remove the replay-required claim.

2. **BLOCKER - §5.A.4 extraction cutover - The source freeze relies on RLS for every tenant-scoped table, but the referenced plan only pilots POS fiscal RLS.**

   Issue: v3 says extraction cutover locks source rows by "temporary RLS policy" on "every tenant-scoped table" and says this "leverages the foundation plan Phase 3 RLS infra" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:325-329`). The foundation plan explicitly says "Do not start with every ERP table" and pilots RLS only on POS fiscal tables (`docs/superpowers/plans/2026-05-02-tenant-isolation-nf525-database-foundation-plan.md:118-126`). The same plan says live DB has no RLS policies (`docs/superpowers/plans/2026-05-02-tenant-isolation-nf525-database-foundation-plan.md:63-66`).

   Proposed fix: make "all tenant-scoped tables have enforceable freeze policies or equivalent write-block triggers" a prerequisite artifact/gate for §5.A. Do not reference the POS-only Phase 3 pilot as sufficient. If all-table RLS is out of scope, replace the temporary-RLS freeze with a concrete app-level 423 plus database trigger/lock mechanism that covers all writers, including jobs and direct SQL maintenance.

3. **MAJOR - §5.B.2 / G6 - Replica identity acceptance is too weak and misses partial-index realities.**

   Issue: v3 requires `REPLICA IDENTITY DEFAULT` for PK tables and `FULL` for rare no-PK tables (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:357-364`), while G6 only asserts every tenant-scoped table has `DEFAULT` or `FULL` (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:628`). `DEFAULT` is the catalog default even on a table without a primary key, so that test can false-pass. The repo also uses many partial unique indexes, for example `pos_receipts_company_refund_request_unique ... WHERE refund_request_id IS NOT NULL` (`apps/api/database/migrations/2026_05_05_000001_add_refund_audit_fields_to_pos_receipts.php:43-49`) and `users_tenant_id_email_unique ... WHERE email IS NOT NULL` (`apps/api/database/migrations/2026_03_23_000001_make_user_email_nullable.php:23-28`); PostgreSQL's publication docs require a usable replica identity for updates/deletes and document restrictions around indexes and `FULL` (`https://www.postgresql.org/docs/17/logical-replication-publication.html`). Partial indexes cannot be treated as a replica identity substitute, and `FULL` can be very inefficient on large rows.

   Proposed fix: G6 must inspect `pg_class.relreplident`, `pg_index.indisprimary`, `pg_index.indisreplident`, partial predicates, expression indexes, nullable identity columns, row width, and update/delete publications. Require a real primary key or valid `REPLICA IDENTITY USING INDEX` for every table that can receive updates/deletes. Allow `FULL` only by explicit table-level exception with measured row width and update/delete volume.

4. **MAJOR - §5.B.4 / §3.2 - Cutover ordering and cache fencing are under-specified.**

   Issue: v3 says cutover locks writes, catches up to source LSN, copies sequences, atomically flips the catalog, drops subscription, and deletes the slot (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:378-382`). §3.2 also says reads during `migrating` use the canonical binding "which is still the source until cutover flips it" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:197-198`). But the resolver caches catalog reads in Redis for 60 seconds (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:215`), and no gate proves all app instances stop using stale source bindings before target writes resume. That can produce read-after-write anomalies or writes hitting source if any bypass misses the lock.

   Proposed fix: specify the cutover transaction and barriers: set tenant `migrating` with a monotonic catalog version, reject writes everywhere, wait for resolver-cache invalidation acknowledgements or require versioned cache keys, wait for subscriber replay LSN, copy sequences using `setval(max + margin)` while source writes are blocked, flip catalog in one `erp_control` transaction, then resume writes only after all app processes observe the new catalog version.

5. **MAJOR - §5.B.3 - TimescaleDB hypertables copied at cutover can violate the <=30 minute window.**

   Issue: v3 excludes TimescaleDB hypertables from logical replication and says they are "copied via `pg_dump --table=...` snapshot at cutover" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:365-370`). The same section promises a cutover lock of seconds to a minute for typical tenants (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:384`). Audit trails are exactly the tables likely to grow large, and `pg_dump --table` during cutover has no size gate in the acceptance criteria.

   Proposed fix: inventory all hypertables and their per-tenant size before topology lock. Either pre-copy audit hypertables before cutover with a concrete catch-up mechanism, include them in a supported replication path, or mark tenants above measured thresholds as extended-window migrations with explicit operator approval.

6. **MAJOR - §8 - PgBouncer capacity math treats Y1 as comfortable without a Postgres memory/workload budget.**

   Issue: v3's Y1 row computes `100 x 1 x 7 = 700`, adds headroom to `~800`, and calls PG `max_connections` 900 "comfortable on one Hetzner PG node" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:550-564`). PgBouncer reserve connections only kick in after `reserve_pool_timeout`, and `pool_size` is the maximum normal pool size per database entry per PgBouncer's config docs (`https://www.pgbouncer.org/config`). That makes `pool_size=5` the immediate per-tenant transaction concurrency. The current Dokploy shape is one TimescaleDB service and one PgBouncer with `DEFAULT_POOL_SIZE=20` and `MAX_CLIENT_CONN=200` (`docker-compose.dokploy.yml:55-63`, `docker-compose.dokploy.yml:124-132`), so v3 is a large operational change. 900 PostgreSQL backends can consume multiple GB before `shared_buffers` and per-query `work_mem`, and Horizon workloads can hold transactions longer than web requests.

   Proposed fix: replace "comfortable" with a measured capacity envelope: target node RAM, `shared_buffers`, `work_mem`, active backend estimate, Horizon worker count, p95 transaction duration, reserve-pool timeout, client queue limits, `max_user_connections`, and noisy-tenant behavior under `max_db_connections=10`. Treat the 750 split trigger as an engineering threshold to prove, not an assertion.

7. **MAJOR - §7.3 - Migration fan-out linter can be bypassed and the existing corpus plan is not concrete.**

   Issue: v3 says the lint rule "trusts" `// @migration-phase: additive` comments while only warning (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:512`) and grandfathering existing single-phase mutative migrations via a baseline allowlist (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:514-516`). The three spot-checked migrations confirm why this is risky: one file mixes rename, add column, check constraint, and backfill (`apps/api/database/migrations/2026_05_03_000002_rename_voucher_serial_to_instrument_serial_on_pos_receipt_payments.php:31-48`), one changes nullability in place (`apps/api/database/migrations/2026_04_26_120000_make_payment_id_nullable_on_payment_allocations.php:23-27`), and one drops an index then adds a unique constraint in the same migration (`apps/api/database/migrations/2026_05_08_000002_add_unique_to_billing_payments_provider_payment_id.php:64-72`).

   Proposed fix: require machine-detected categories to dominate comments, not the reverse. Allow comments to select an approved phase only when the AST/raw SQL classifier agrees. Commit a baseline file with migration filename, detected operations, human disposition, and expiry rule. New mixed migrations must fail unless split into expand, backfill, deploy, and contract pieces.

8. **MAJOR - §5.A.2 / §5.A.3 - FK closure and reference/system ownership are still hand-wavy for shared rows.**

   Issue: v3 says shared/system rows are exported via "copy-as-needed" deduplication and reference data is recreated by seeders, not copied (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:303-318`). The schema is not that clean. `companies.default_tax_configuration_id` references `tax_configurations` (`apps/api/database/migrations/2025_12_30_103000_add_tax_fields_to_companies.php:13-19`), `products.default_tax_configuration_id` also references it (`apps/api/database/migrations/2026_03_22_100000_add_default_tax_configuration_id_to_products.php:13-18`), and `vat_period_breakdowns.tax_configuration_id` can reference the same table (`apps/api/database/migrations/2026_03_23_200000_create_vat_periods_table.php:49-55`). `withholding_tax_rules` even has nullable `company_id`, mixing country-level and company-specific rules (`apps/api/database/migrations/2026_01_08_172123_create_withholding_tax_rules_table.php:17-49`).

   Proposed fix: add an ownership taxonomy to the manifest: tenant-owned, company-owned, global immutable reference, global mutable reference, and shared-with-tenant-overrides. For every FK to shared data, define whether the target row is copied, seeded by stable natural key, or rejected until normalized. The exporter must hold a consistent snapshot for copied shared rows or version them so another tenant's concurrent modification cannot change the extracted meaning mid-run.

9. **MINOR - §11 A2/G1/G6 - Validation gates do not prove the new cutover and replication claims.**

   Issue: A2/G1 cover only `(tenants.status x shards.status)` (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:612-624`). That is consistent with the single-binding invariant, but it does not test cutover atomicity, stale cache behavior, source/target LSN ordering, sequence copy, or subscription cleanup. G6 claims a "Logical replication table prereq scan" but only names `DEFAULT` or `FULL` (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:628`).

   Proposed fix: add separate cutover/protocol fixtures: promotion cutover ordering, rollback replay setup, cache-version fencing, sequence `setval` after source write lock, replica identity introspection, excluded-table sizing, and trigger inventory. Keep A2 small, but do not let G1 be the only resolver safety proof.

10. **NIT - §6.5 / §11 G2-G5 - CrossTenantContext sunset relationship is understandable but should be named.**

   Issue: A4 and G2 already require a complete disposition inventory (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:615`, `docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:624`). G5 separately fails routes using `cross_tenant=true` in `TENANCY_MODE=multi_db` unless mapped in A4 (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:627`). This is not wrong, but the spec does not state whether G5 is redundant with G2 or a runtime-mode guard.

   Proposed fix: state that G2 proves inventory completeness before topology lock, while G5 remains the multi-db-mode safety net that prevents future bypass routes from landing without A4 disposition.

## Verdict reasoning

v3 is materially better than v2, and most of the nine v2 re-review findings are addressed or moving in the right direction. The remaining failures are not wording tweaks. The spec still claims replay-required rollback without a valid since-cutover change-capture primitive, and it claims pooled-public extraction can freeze tenant writes through an RLS mechanism that does not exist for most tenant-scoped tables under the referenced plan.

Approve the Path 3 direction only after those mechanics are replaced with implementable primitives and the acceptance gates are strengthened to prove them. At minimum, v4 needs: target-side rollback change capture created at cutover, an all-table extraction freeze mechanism, a real replica-identity introspection gate, measured hypertable and PgBouncer capacity thresholds, and a concrete migration-corpus baseline for expand/contract enforcement.
