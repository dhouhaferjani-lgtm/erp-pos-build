# H-7.3 COGS Posting — Opus Adversarial Review

- Item: H-7.3 (event-driven COGS GL entries post as system-generated, nullable `posted_by`, from immutable `InvoicePosted` currency)
- Commit: `35fc50727`
- Reviewer: Opus 4.8 (adversarial, refutation-oriented). Prior reviews were Codex-only.

## Summary

The functional claim holds and is genuinely red-first verified: before the change the
event-driven COGS entry stayed `Draft`; after it, the `InvoicePosted` listener path produces
a `Posted` COGS entry with `posted_by = NULL`, balanced legs, a `fiscal_hash`, and a
`posted_at`. PHPStan L8 is clean, the money math stays in `bcmath` (no float drift), and
the `InvoicePosted` event is not mutated.

However, refutation surfaced one serious integrity problem that is NOT specific to this
commit but is materially worsened by it: posting COGS through
`GeneralLedgerService::postEntry()` writes a `fiscal_hash` while leaving `chain_sequence`
NULL, which makes the entry fail the existing GL chain verifier
`GeneralLedgerHashService::verifyChain()`. There are two parallel, incompatible hash-chain
schemes on the single `journal_entries` table, and H-7.3 now injects a posted, hashed,
sequence-less entry into the table that the verifier reads. The only reason this is not an
immediate production BLOCKER is that `GeneralLedgerHashService::verifyChain()` currently has
NO production caller (test-only). It is, today, latent corruption of the GL integrity model.

Two further gaps: the new test cannot actually prove the "immutable event currency" half of
the claim (CompanyContext fallback masks it), and there is no idempotency guard, so a
re-delivered `InvoicePosted` now double-posts real GL financials (previously the duplicate was
a harmless Draft).

## BLOCKER

None that trip a live production path today. The most severe finding (dual-chain /
verifyChain) is filed as HIGH because the verifier has no production caller — see HIGH-1.

## HIGH

### HIGH-1 — Posted COGS entry breaks `GeneralLedgerHashService::verifyChain()` (dual incompatible GL chains)

There are two independent hash-chain mechanisms operating on the same `journal_entries`
table for the same company:

- Chain A — `AccountingService::createInvoiceGLEntries()` (the real production invoice GL
  path fired by `InvoicePostedListener`) sets `chain_sequence`, `previous_hash`, `fiscal_hash`
  using `JournalEntry::getNextChainSequence()` / `getLastChainHash()` (ordered by
  `chain_sequence`).
  - `apps/api/app/Modules/Accounting/Application/Services/AccountingService.php:110-125`:
    `$previousHash = JournalEntry::getLastChainHash(...); $chainSequence = JournalEntry::getNextChainSequence(...);` then `JournalEntry::create([... 'status' => Posted, 'chain_sequence' => $chainSequence, 'previous_hash' => $previousHash])`.

- Chain B — `GeneralLedgerService::postEntry()` (the path H-7.3 routes COGS through) sets
  `fiscal_hash`, `previous_hash`, `posted_at` but **never sets `chain_sequence`**, and
  computes `previous_hash` via `getPreviousHash()` ordered by `posted_at`.
  - `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:1278-1284`:
    `$entry->update(['status' => Posted, 'fiscal_hash' => $hash, 'previous_hash' => $previousHash, 'posted_at' => $postedAt, 'posted_by' => $user?->id])` — no `chain_sequence`.
  - `:1751-1760` `getPreviousHash()` orders by `posted_at`, not `chain_sequence`.

The official GL verifier reads ALL entries that have a `fiscal_hash` and requires a
continuous integer `chain_sequence`:

```
apps/api/app/Modules/Accounting/Application/Services/GeneralLedgerHashService.php:87-104
  $entries = JournalEntry::where('company_id', $companyId)
      ->whereNotNull('fiscal_hash') ... ->orderBy('chain_sequence')->get();
  ...
  if ($entry->chain_sequence !== $expectedSequence) { return false; }
```

A COGS entry posted by H-7.3 has `fiscal_hash` set (so it is included by the
`whereNotNull('fiscal_hash')` filter) but `chain_sequence = NULL`. `NULL !== 1/2/3...` →
`verifyChain()` returns `false`. So for any company that posts BOTH an invoice (Chain A) and
a COGS entry (Chain B) — i.e. essentially every retail/automotive sale of a physical product —
the GL chain now reports as tampered/broken.

Why this is HIGH and not BLOCKER: `GeneralLedgerHashService::verifyChain()` has **no
production caller** today — `rg verifyChain app/ routes/` finds only
`WithholdingHashChainService` (a different chain) and tests. The GL chain tests
(`GLHashIntegrationTest`, `CompleteGLHashChainE2ETest`, `GeneralLedgerHashServiceTest`)
exercise Chain A entries exclusively, so the breakage is invisible to CI. This is latent
corruption of the documented GL integrity model: the commit message and work-list claim the
entry posts through "the canonical balance/hash/event path," but the canonical GL *chain*
(`chain_sequence` + `verifyChain`) is precisely the part it does not honor. Any future
compliance/audit feature, NF525-style GL export, or re-enabling of the verifier will report
false tampering. Note this is a series-wide issue (H-7.1 expense, H-7.2 voucher, H-7.4
write-off all use the same `postEntry` path) but H-7.3 is the highest-volume offender
(one COGS entry per physical-product sale).

Recommendation: either (a) route system-generated posts through the same
`chain_sequence`/`getLastChainHash` mechanism as `AccountingService` so all hashed entries
share one chain, or (b) explicitly document and segregate the `postEntry` "soft" chain from
the compliance `chain_sequence` chain (e.g. `verifyChain` should scope to
`whereNotNull('chain_sequence')`, and `getPreviousHash`/`postEntry` should stop writing a
`fiscal_hash` that the verifier will pick up). Until one of these is done, the
"canonical hash path" claim is not accurate.

### HIGH-2 — New test does not actually verify the "immutable event currency" claim

The headline of H-7.3 is that COGS posts "from the immutable `InvoicePosted` currency."
The listener does forward it
(`apps/api/app/Modules/Inventory/Listeners/PostCOGSOnInvoice.php:79` `currencyCode: $event->currency`),
but the new test cannot distinguish that from the company-currency fallback:

- `tests/Feature/Accounting/StockMovementGLIntegrationTest.php:128` sets
  `CompanyContext` to the test company; the company currency is `'TND'`
  (`:97`), and the invoice/event currency is also `'TND'` (`:271`).
- If the `currencyCode: $event->currency` argument were deleted, `createCOGSEntry()` would
  fall back to `currencyCodeForCompany()` (GLS `:74`) → still `TND` → scale resolves
  identically → the test still passes.

So the test gives false confidence on the specific claim it is named for. A meaningful test
would use an event currency that differs from the company/context currency (or assert the
resolver is invoked with the event currency) so that dropping the forwarding fails red.
(The functional posting/`posted_by`/status assertions ARE meaningful — those were verified
red-first below.)

## MEDIUM

### MED-1 — No idempotency guard; re-delivered `InvoicePosted` now double-posts real financials

`createCOGSEntry()` has no "already posted for this invoice" guard
(`GeneralLedgerService.php:937-1018` — no `where('source_id', ...)->exists()` check), and the
new test asserts existence via `firstOrFail()`
(`StockMovementGLIntegrationTest.php:344-347`), which would still pass with duplicates.
Before H-7.3 a re-delivered `InvoicePosted` created a duplicate **Draft** COGS entry —
harmless to balances and chains. After H-7.3 the duplicate is **Posted**: double COGS debit +
double inventory credit hit the GL, and two more `fiscal_hash` rows enter the table. The
Codex review acknowledges the gap but mislabels it "pre-existing" — the change in lifecycle
(Draft → Posted) is exactly what converts a benign latent issue into a financial-correctness
one. Delivery is synchronous single-fire today (low probability), hence MEDIUM, but it should
be guarded (`source_type='cogs' + source_id` uniqueness or pre-check) given it now writes
money.

### MED-2 — Listener swallows posting failures; entry can be silently stranded as Draft

`PostCOGSOnInvoice::handle()` wraps everything in `catch (\Throwable)` and only logs
(`PostCOGSOnInvoice.php:106-115`). `createCOGSEntry()` first commits the Draft entry in its
own inner `DB::transaction` (`GeneralLedgerService.php:970-1013`) and only THEN posts
(`:1015`). If posting throws (unbalanced edge, scale-resolver failure, hash uniqueness
collision on the `idx_gl_fiscal_hash_unique` constraint), the Draft entry is already
committed and persists unposted while the exception is swallowed — the invoice posting
reports success and no COGS appears in the books. There is no test for the failure path. The
create+post are not atomic, so "posted as system-generated" is best-effort, not guaranteed.

### MED-3 — `afterCommit` guard in the system-generated helper is effectively dead in the real flow

`postSystemGeneratedEntryAndDispatchPostedEventAfterCommit()` defers when
`DB::transactionLevel() > 0` (`GeneralLedgerService.php:100-108`). But in both production
listener flows the event itself is dispatched from `DocumentPostingService` via
`DB::afterCommit` (`DocumentPostingService.php:193-195`), so the COGS listener always runs at
transaction level 0, and `createCOGSEntry`'s own inner transaction has closed by the time the
helper is called. The deferral branch is never taken in production and is untested. It is not
wrong, but it is dead defensive code that mirrors the actor-path helper without a path that
reaches it — minor maintainability smell.

## LOW

### LOW-1 — Hash excludes `posted_by`, so nullable actor is hash-safe (positive confirmation, no action)

`calculateHash()` hashes only `entry_number`, `entry_date`, `description`, and line
account/debit/credit (`GeneralLedgerService.php:1737-1746`); `posted_by` is not part of the
hash, so making it nullable does not perturb any hash. Migration already has
`posted_by ... nullable()` (`migrations/tenant/2025_11_30_100000_create_journal_entries_table.php:31`).
No issue — recorded so the next reviewer need not re-derive it.

### LOW-2 — Coordination/work-list wording overstates "canonical hash path"

`work-list.md` and the coordination log state COGS now posts through "the canonical
balance/hash/event path." Given HIGH-1, the entry does not join the `chain_sequence`
compliance chain that `verifyChain` treats as canonical. The note should be qualified to
"canonical `postEntry` lifecycle (balance check + `fiscal_hash` + `JournalEntryPosted`), which
is a separate soft chain from the `chain_sequence` invoice chain."

## Verdict

NEEDS-REVISION. The feature works and is red-first tested, but it injects posted, hashed,
`chain_sequence`-less entries into a table whose verifier requires continuous
`chain_sequence` (HIGH-1), the named "immutable currency" claim is not actually tested
(HIGH-2), and the Draft→Posted lifecycle change turns an unguarded re-delivery into a
double financial posting (MED-1). HIGH-1 should be resolved or explicitly designed-around
before this is relied on for any GL integrity/compliance surface.
