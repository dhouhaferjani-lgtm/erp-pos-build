## Findings

### MAJOR-1 — `VatSpecialItems` is now the only en-US/2dp island on a page where every sibling renders in the company-currency locale
`apps/web/src/features/vat-reporting/components/VatSpecialItems.tsx:38-52` (`formatItemValue`, hardcoded `'en-US'`, `2`), rendered by `apps/web/src/features/vat-reporting/pages/VatReportPage.tsx:99` **on the same screen** as `VatSummaryCards` (`VatReportPage.tsx:62`) and two `VatBreakdownTable`s (`VatReportPage.tsx:78,91`), all three of which this commit converted to currency-driven formatting.

Failure scenario (measured with the probe, TND company): the breakdown total renders `15 000,000` and the special-items card renders `1,234.57` a few inches below it. To a Tunisian or French reader `1,234.57` reads as ~1.23 — this is verbatim the W-7 F-7 bug class the codebase already documented in `apps/web/src/lib/format.ts:150-160`. Before this commit all four surfaces were uniformly (wrongly) `en-US`, so they at least agreed; the commit converted "uniformly wrong" into "mutually contradictory on one screen". Additionally `retenue_source_amount = 1234.567` renders `1,234.57` — a real millime rounded away on a Tunisian VAT-return figure (that specific loss is pre-existing, unchanged by the commit; the notation mix is new).

The stated blocker — "no type tag to tell money from count apart at this layer" — is refuted by the file's own config at `VatSpecialItems.tsx:15-27`, which enumerates every key per country. Adding `kind: 'money' | 'count'` is a ~4-line change entirely inside the file the lane already edited.

**Not merge-blocking today only because of MAJOR-2** (the panel never renders). It goes live the instant the key contract is fixed.

*Fix directive:* add `kind: 'money' | 'count'` to `SpecialItemConfig`, route `kind: 'money'` through `useCurrency().format(v, { symbol: false })` and `kind: 'count'` through an integer formatter; delete the hardcoded `'en-US'`/`2`.

### MAJOR-2 — (pre-existing, outside the diff; discovered while verifying MAJOR-1) the special-items FE/BE key contract does not overlap at all, so the panel is dead UI in every country
FE expects (`VatSpecialItems.tsx:16-25`): `timbre_fiscal_count`, `timbre_fiscal_amount`, `retenue_source_amount`, `credit_tva_previous`, `eu_acquisitions_vat`.
Backend emits:
- `apps/api/app/Modules/Taxation/Infrastructure/Strategies/TunisiaVatStrategy.php:118-122` → `stamp_duty_count`, `stamp_duty_total`, `retenue_source_total`
- `apps/api/.../FranceVatStrategy.php:114-117` → `intra_community_acquisitions`, `intra_community_supplies`
- `apps/api/.../UkVatStrategy.php:131-134` → `ec_supplies`, `ec_acquisitions`

Zero keys match. `hasValues` (`VatSpecialItems.tsx:64`) is therefore always false and the component returns `null`.

Failure scenario: a Tunisian tenant's stamp-duty count/total and retenue-à-la-source total — figures the TN declaration needs — are computed, persisted into `vat_periods.special_items`, and never displayed. Silent, no error.

*Fix directive:* out of this lane's scope — file as its own ticket; align `countryItemConfigs` to the strategy keys (or rename in the strategies) and add a render test with real strategy output. Do it **together with** MAJOR-1 so the panel does not go live in mixed notation.

### MINOR-1 — YTD accumulator changed from round-once to round-at-every-step
`apps/web/src/features/vat-reporting/pages/VatPeriodsPage.tsx:26-27`: `bcadd(totalOutput, period.total_output_vat ?? '0', decimals)` rounds the running total to the currency scale on **each** iteration and carries the rounded value forward. The pre-commit code summed then `toFixed(decimals)` once (`round-once`, though on floats). `docs/architecture/precision-contract.md` says round once at the boundary, intermediates at `scale+1`.

Failure scenario: EUR company (`decimals = 2`), backend money columns are `decimal(N,3)`; three periods at `100.005` → per-step: `100.01 → 200.02 → 300.03`; round-once: `300.02`. A 1-cent YTD discrepancy that grows with period count. (Counter-argument, stated for fairness: per-step rounding makes the total agree with the visibly-rounded per-period rows below it. Either is defensible; the contract picks round-once.)

*Fix directive:* drop the third argument (`bcadd(totalOutput, …)` → default scale 3) and let `useCurrency().format()` round once at render.

### MINOR-2 — `Number(value)` survives inside the component the sweep converted
`apps/web/src/features/vat-reporting/components/VatSpecialItems.tsx:44`: `const isNumeric = value.trim() !== '' && !isNaN(Number(value))`. The float is used only as a validity predicate and never reaches the rendered value, so there is **no precision loss** — but it is literally the API the commit message claims to have eliminated from the directory, and it is invisible to `no-parsefloat-on-money` only because the identifier is named `value`. It also silently changed behaviour for junk input: `"12abc"` used to render `12.00` (parseFloat prefix-parse), now renders the raw `"12abc"`.

*Fix directive:* replace with a decimal-string regex (or a `try { new Big(value) }` probe) so the file contains no float coercion at all.

### MINOR-3 — a count is rendered with 2 decimals (pre-existing, unchanged)
`apps/web/src/features/vat-reporting/components/VatSpecialItems.tsx:40-41`: `timbre_fiscal_count: 3` renders as `3.00` (probe-confirmed). Not currency-formatted (no currency locale/scale is applied), which answers the spec question — but "3.00 stamps" is still wrong. Pre-existing; folds into MAJOR-1's `kind: 'count'` fix.

### MINOR-4 — displayed rows may not sum to the displayed total under a 2dp currency
`apps/web/src/features/vat-reporting/components/VatBreakdownTable.tsx:20-21` accumulate at `bcadd` default scale 3, then `format()` rounds to the currency scale. EUR + rows `2000.005` / `350.005`: rows show `2 000,01` + `350,01` = `2 350,02`, total shows `2 350,01`. Same class as the pre-commit float behaviour (not a regression); flagged so it is a decision rather than a surprise.
