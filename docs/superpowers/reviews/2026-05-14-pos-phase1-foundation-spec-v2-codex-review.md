## Executive summary
- v2 genuinely resolves the original two-chain/two-route ambiguity on paper: `SALE_RECEIPT` is now authored through `FiscalEventEngine.append()` and `/pos/receipts/sync` is retired.
- B1 is resolved: §13's Treasury `Payment` writer inventory now matches the corrected audit and the live `apps/api` grep; `App\Modules\Billing\Domain\Payment` is correctly excluded.
- The central rewrite still has one buildability hole: `OutboxIngestor` stores the fiscal event and then applies receipt business projection, but the projection failure/retry/transaction contract is not specified.
- v2 also introduces a false codebase claim inside that projection design: the old `ReceiptSyncService` does not create Treasury `Payment` rows. Those come from `ReceiptPaymentService`.
- The `ON CONFLICT` primitive is the right direction, but the ingest algorithm is still not coherent enough: it returns duplicate success on sequence conflicts without proving the conflicting payload is the same event, and its step ordering contradicts itself.

## New findings
### [BLOCKER] `ReceiptBusinessProjection` is based on a false source for Treasury `Payment` effects
**Dimension:** codebase-claim
**Spec location:** §7.3 and §14 (`spec v2:303-305,391-392`)
**Evidence:** v2 says the stock / voucher / `pos_receipts` / Treasury-`Payment` side effects are the business logic extracted from old `ReceiptSyncService` (`spec v2:303-305`) and classifies `ReceiptSyncService` stock/voucher/payment logic as reused/relocated (`spec v2:391-392`). Actual `ReceiptSyncService` creates `ReceiptPayment` rows at `apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:598-609`, redeems vouchers at `:683-710`, and decrements stock at `:713-735`; it does not create `App\Modules\Treasury\Domain\Payment` rows. Treasury `Payment` rows and direct-to-revenue GL posting are created by `ReceiptPaymentService` at `apps/api/app/Modules/POS/Application/Services/ReceiptPaymentService.php:35-43,252-276`.
**Issue:** The projection service is specified around the wrong extraction source. If implementers literally extract the "payment" logic from `ReceiptSyncService`, they get POS `ReceiptPayment` rows, not Treasury `Payment` rows with `origin = pos` and `fiscal_event_id`.
**Impact:** Phase 1 would appear to satisfy §13 tests while the new `SALE_RECEIPT` ingestion path omits the actual Treasury payment/GL side effects or implements a second ad hoc payment writer. That corrupts the `Payment.origin` / `Payment.fiscal_event_id` requirement that Phase 2 account payment reconciliation consumes.
**Suggested fix:** Redefine `ReceiptBusinessProjection` as a composition of two explicit units: extracted receipt projection from `ReceiptSyncService` for `pos_receipts`, lines, VAT, `ReceiptPayment`, voucher, and stock; plus a reused/refactored `ReceiptPaymentService` path for Treasury `Payment` + GL posting, accepting `fiscal_event_id` and `origin`. Add projection tests that assert Treasury `Payment` rows, `ReceiptPayment` rows, GL entries, voucher redemptions, and stock movements are all created exactly once from one `SALE_RECEIPT` fiscal event.

### [BLOCKER] Projection failure semantics after fiscal-event persistence are undefined
**Dimension:** buildability
**Spec location:** §7.2 / §7.3 (`spec v2:280-305`)
**Evidence:** v2 says `OutboxIngestor.ingest()` is a standalone operation (`spec v2:283`), inserts the `fiscal_events` row (`spec v2:284-295`), then invokes `ReceiptBusinessProjection.apply(fiscal_event)` (`spec v2:296-297`). It also says the row is always persisted and never rejected (`spec v2:298`). Actual old receipt sync avoided this split by wrapping receipt creation, finalization, voucher redemption, stock movement, and rollback in one transaction (`ReceiptSyncService.php:189-195,612-623,665-735`).
**Issue:** The spec does not define whether `ReceiptBusinessProjection` runs in the same database transaction as the `fiscal_events` insert or in a separate projection transaction. Same transaction contradicts "row is ALWAYS persisted" if projection fails. Separate transaction preserves the fiscal row but leaves no specified `projection_status`, retry queue, dead-letter state, operator alert, or idempotent replay API for a verified `SALE_RECEIPT` whose business projection failed.
**Impact:** An implementer cannot build the central one-ingestion-path model without inventing failure semantics. A voucher, stock, FK, or GL error could either roll back fiscal truth in violation of D1/D13, or persist an authoritative sale event with no `pos_receipts`, Treasury `Payment`, stock movement, or voucher redemption. Both outcomes break Phase 1's receipt rebuild and the first deployable slice.
**Suggested fix:** Specify the projection contract explicitly. Recommended: persist `fiscal_events` in its own transaction with `integrity_status`; enqueue or mark a projection row keyed by `fiscal_event_id`; apply business projection in a separate idempotent transaction with `projection_status = pending|applied|failed`, structured failure reason, retry/backoff, and operator-visible dead-letter handling. Fiscal integrity exceptions should suppress business projection when payload parsing fails; projection failures should not mutate or delete the fiscal event.

### [P1] The `ON CONFLICT` idempotency algorithm still treats non-identical sequence conflicts as success
**Dimension:** consistency
**Spec location:** §7.2 (`spec v2:280-301`)
**Evidence:** v2 uses `ON CONFLICT (tenant_id, terminal_id, sequence_number) DO NOTHING RETURNING id`, then if no row is returned it selects the existing row and returns idempotent success (`spec v2:284-288`). It also says steps 2..5 "run before the INSERT" while placing the insert as step 1 (`spec v2:284-295`). PostgreSQL documents `ON CONFLICT DO NOTHING` as avoiding insertion of the conflicting row and `RETURNING` as returning rows actually inserted ([PostgreSQL INSERT docs](https://www.postgresql.org/docs/current/sql-insert.html)). SoT v3 requires per-class anomaly handling and explicit chain/recovery records, not silent replacement (`source-of-truth v3:23-24,95-98,260`).
**Issue:** A conflict on `(tenant_id, terminal_id, sequence_number)` is only an idempotent duplicate if the existing row has the same immutable identity and bytes/hash. v2 never requires comparing `id`, `current_hash`, `canonical_bytes`, `source_event_*`, or envelope identity on the conflict path. A different event with the same sequence would be silently treated as a successful duplicate. The step ordering is also self-contradictory: the prose says checks decide the insert values, but the pseudocode shows insert first and checks "before the INSERT" second.
**Impact:** Concurrent replay is safer than v1, but chain forks, device bugs, or tampered envelopes can be acknowledged as success without being persisted, quarantined, or turned into a chain-recovery incident. That violates the accept-and-flag model and can hide the exact anomaly the fiscal ledger is supposed to expose.
**Suggested fix:** Make conflict handling explicit: compute/validate hash, strict parse, and linkage inputs before the insert; attempt the insert atomically; on conflict, load the existing row and compare immutable identity plus `canonical_bytes`/`current_hash`. If identical, return duplicate success. If different, do not call it idempotent success; record a structured `sequence_conflict`/chain incident path or require a `CHAIN_BREAK_DETECTED` recovery event because the unique key prevents storing two events at the same sequence.

### [P2] `/pos/receipts/sync` retirement has live code/test dependencies that need to be named in the writing plan
**Dimension:** new-issue
**Spec location:** §7.1, §14, §17.3 (`spec v2:276-279,391,457`)
**Evidence:** v2 retires `/pos/receipts/sync` and says the device posts `SALE_RECEIPT` to the fiscal-event endpoint (`spec v2:276-279,391,457`). Live production dependencies exist at `apps/pos/src/lib/sync/syncService.ts:333-336`, `apps/api/app/Modules/POS/routes.php:85`, and `apps/api/app/Modules/POS/Presentation/Controllers/SyncController.php:49-68`. Test dependencies are broad: `apps/pos/src/lib/sync/__tests__/syncService.test.ts:293,800`; `apps/pos/src/lib/__tests__/fetchWithTimeout.test.ts:51,61`; POS backend feature suites such as `SyncReceiptsTest.php:30,66,107` and `ReceiptSyncServiceV3Test.php:112,134,232`.
**Issue:** v2 conceptually accounts for route retirement, but it does not name the concrete cross-app cleanup surface. Given this codebase's history of route-retirement misses, the writing plan should not leave the old route caller, controller, request validation, DTO tests, and timeout tests as implicit fallout.
**Impact:** Phase 1 writing-plans could correctly build `OutboxIngestor` but leave the POS client or backend test suite targeting the retired endpoint, producing either runtime sync failure or a stale compatibility route that undermines the "one ingestion path" decision.
**Suggested fix:** Add a §14/§17 checklist item: replace `pushOfflineReceipts` / `receiptToPayload` with fiscal-event envelope push; remove or hard-disable the `/pos/receipts/sync` route and `SyncController::syncReceipts`; migrate receipt sync tests to fiscal-event ingestion tests; update timeout helpers and fixtures that encode the old path; keep no adapter unless the owner explicitly chooses one.
