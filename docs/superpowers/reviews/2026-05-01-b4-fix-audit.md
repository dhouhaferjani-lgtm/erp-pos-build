## Outstanding issues

**Minor 1 — PHP↔TS source-of-truth has no CI guard.** `PaymentInstrumentKind` (PHP) and `INSTRUMENT_BEARING_METHOD_CODES` (TS) are required to stay in sync, but the synchronization is enforced only by docblock comments. If a future contributor adds a 4th instrument-bearing case to the PHP enum (e.g. `MealVoucher = 'meal_voucher'`):
  - The PHP `PaymentInstrumentKindTest::test_enum_has_expected_cases` would fail (`assertCount(4)` → 5), so the PHP side at least surfaces the change.
  - The TS test `paymentMethodKind.test.ts` would NOT fail — `INSTRUMENT_BEARING_METHOD_CODES` is asserted equal to the literal 3-code list, and that's it.
  - The UI would silently keep showing the new method as a free-form tile, the cashier could create a malformed payment line, and the *server* would reject it with 422 (defense-in-depth still bites). So the worst-case is degraded UX, not a fiscal-hash hole.
  - Recommendation: either generate the TS list from a PHP-emitted JSON (existing `php artisan typescript:transform` pattern), or add a parity test that runs `php artisan tinker -e 'echo json_encode(...)'` and asserts equality. Acceptable as Minor for B4 scope.

**Minor 2 — UX dead-end pending B5.** `handleSelectMethod` shows `t('advancedPayments.voucherTenderFlowRequired')` ("…use the voucher button or scan the code…") but `VoucherTenderModal` is *not* mounted anywhere in the live render tree (`grep VoucherTenderModal apps/pos/src --include='*.tsx'` excluding tests/the file itself returns only docblock mentions in `AdvancedPaymentsModal.tsx` and `paymentStore.ts`). The cashier is told to use a button that does not yet exist in the modal. The B4 commit message acknowledges this and explicitly hands the mount to B5 — so this is documented, but the message is misleading until B5 ships. Recommend either mounting `VoucherTenderModal` here as part of B5 (already planned, task #28) or softening the i18n string until then.

**Minor 3 — Pre-existing cross-tenant `PaymentMethod` lookup risk (not introduced by B4).** The validator's `PaymentMethod::query()->find($paymentMethodId)` at `StoreReceiptPaymentsRequest.php:194` and the existing `exists:payment_methods,id` validation rule both hit the `payment_methods` table without a tenant scope. `PaymentMethod` has a `tenant_id` column but no global scope and no schema-isolation (verified: `grep -rn addGlobalScope apps/api/app` returns nothing). If a cashier has a leaked `payment_method_id` UUID from a *different* tenant, the lookup will succeed and B4's value-conditional rule will fire on the cross-tenant code. This is a pre-existing tenant-isolation gap that the B4 commits inherit but do not introduce — the existing payment flow has the same exposure. Worth surfacing as a follow-up on the broader tenant-isolation audit, but **not a B4 blocker**.

**Nit — `SyncReceiptsRequest::messages()` doesn't include the new B4-specific keys.** The validator builds inline error strings like `"instrument_type is required when method_code is store_voucher"`, which is what the tests assert against — so functionally fine, but the `messages()` array is a useful single place for translatable error copy. Not blocking.
