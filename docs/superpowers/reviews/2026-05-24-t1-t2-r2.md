# Adversarial Review (Round 2) — T1 + T2
## Reviewer: Claude general-purpose
## Date: 2026-05-24

## Verdict (per spec)
- **T1 Stock Transfer:** APPROVE-WITH-MINOR-EDITS
- **T2 Variants:** NEEDS-REVISION

## Summary

T1 v2 makes a clean, verifiable recovery from round-1. The Codex BLOCKER B-1 (batch column on `stock_movements`) is resolved correctly — the spec now explicitly disclaims any `stock_movements.batch_id` addition and points to the existing `inventory_batch_movements` join (with `batch_id` + `movement_id` columns) verified at the cited migration. The event-naming inconsistency (P3-1) is fixed. P1-5 is addressed via the new `InTransitAvailability` setting + `AvailableQuantityService` consumed by `ReceiptCreationService`, with explicit Wave 2 POS deltas captured separately. The architecture grounding is mostly accurate; one notable execution gap is that the spec talks about "extending `StockAdjustmentService::transfer()`" but doesn't acknowledge that `transfer()` currently takes NO `$batchId` parameter (only `receive()` and `issue()` do), so the implementation needs to thread batch identity through the call surface — this is worth flagging in the workflow recommendation. There are also two callable concerns that didn't survive my read: the existing `BatchStockService::transferBatchStock()` already exists but is currently called only from `BatchController` and notably does NOT take a `$movementId`, so it cannot create `inventory_batch_movements` rows linked to the new `TransferOut`/`TransferIn` movements. T1 needs to use the underlying `recordBatchMovement` mechanism (or extend `transferBatchStock` to accept paired movement IDs), not call `transferBatchStock` as-is.

T2 v2 partially resolves the round-1 findings but introduces a new BLOCKER in the schema-change list and leaves an unresolved cross-spec contradiction with the topology contract. P1-7 (`CompositeItemVariant` as full-lifecycle pattern) is correctly downgraded to "style reference only," and P2-2 (wrong stock-level migration cited) is fixed. However, the schema-changes list includes `receipt_line_batch_allocations` — a table that does not exist; the actual table is `pos_receipt_line_batch_allocations` (under `apps/api/database/migrations/2026_02_19_000001_create_pos_receipt_line_batch_allocations_table.php`). The partial-unique-index strategy described in section 7 has a hidden migration-safety hazard: it adds `company_id` to the unique key for `stock_levels`, but the existing constraint is `(tenant_id, product_id, location_id)` and `company_id` was added as a nullable backfill column. If any pre-existing row has `company_id = NULL`, the partial unique `WHERE variant_id IS NULL` index across `(tenant_id, company_id, product_id, location_id)` will let two NULL-company rows for the same product/location coexist — a regression of the old constraint. The spec does not specify a backfill of `company_id` before tightening uniqueness.

Both specs do well on workflow choreography and reference the topology contract correctly. The cross-spec ownership boundary for `variant_id` is clean — T2 owns the column additions and T1 only references the resulting nullable column on `StockTransferLine`. No conflicting migrations are proposed. The biggest sprint-execution risk remaining is the T2 partial-index design, plus the file-path drift on `pos_receipt_line_batch_allocations` and the implicit assumption that `BatchStockService::transferBatchStock` is fit to wire from `StockTransferService`.

## Findings

### BLOCKER

**B-1 (T2) — `receipt_line_batch_allocations` table does not exist**
- **Where:** `apps/erp/docs/superpowers/specs/2026-05-24-t2-variants.md:91, 285`
- **Claim:** T2 schema-changes list says "`receipt_line_batch_allocations`: ADD `variant_id` (FK, nullable)" and the coordination notes claim T2 "Owns: `variant_id` column additions to ... `receipt_line_batch_allocations`."
- **What I found:** No such table exists. The migration at `apps/erp/apps/api/database/migrations/2026_02_19_000001_create_pos_receipt_line_batch_allocations_table.php` creates `pos_receipt_line_batch_allocations`. A grep across all migrations for `receipt_line_batch_allocations` returns only the `pos_*` variant.
- **Why it matters:** The migration will fail at runtime (`ALTER TABLE receipt_line_batch_allocations` against a nonexistent relation). Reviewers downstream will lose trust in the architecture-grounding claims. The topology contract section 2 also propagates this error (line 62) — it should be corrected in both places to keep the contract authoritative.
- **Suggested fix:** Replace `receipt_line_batch_allocations` with `pos_receipt_line_batch_allocations` in T2 §3 schema-changes list, T2 §12 coordination notes, and topology contract §2 tenant-table classification.

**B-2 (T2) — Partial unique index changes `stock_levels` key to include `company_id` while `company_id` is still nullable**
- **Where:** `apps/erp/docs/superpowers/specs/2026-05-24-t2-variants.md:80-85` and topology contract §7
- **Claim:** Drop existing `(tenant_id, product_id, location_id)` unique, replace with two partial unique indexes that include `company_id`: `(tenant_id, company_id, product_id, location_id) WHERE variant_id IS NULL` and `(tenant_id, company_id, product_id, variant_id, location_id) WHERE variant_id IS NOT NULL`.
- **What I found:** The original unique constraint at `apps/erp/apps/api/database/migrations/2025_11_30_110000_create_inventory_tables.php:27` is `(tenant_id, product_id, location_id)` — it does NOT include `company_id`. The 131000 migration (`2025_11_30_131000_add_company_id_to_stock_tables.php:33`) added `company_id` as `->nullable()` with a doc comment: *"company_id is nullable initially to allow gradual data migration. A future migration will make it required after data is migrated."* PostgreSQL treats `NULL` as distinct in unique indexes (including partial). If any pre-existing `stock_levels` row has `company_id = NULL`, the new partial index `WHERE variant_id IS NULL` keyed on `(tenant_id, company_id, product_id, location_id)` will allow multiple NULL-company rows for the same `(tenant_id, product_id, location_id)` — silently weaker than today's constraint.
- **Why it matters:** Data corruption window opens during migration. Two POs received under different companies for the same product/location (if `company_id` is null on legacy rows) would no longer be deduplicated. The non-variant flows that round-1 P2-2 was asking to verify are exactly the ones at risk.
- **Suggested fix:** Add an explicit prerequisite step to T2 Phase 1 migrations: backfill `stock_levels.company_id` (via `Location->company_id`) and assert non-null before dropping the old unique. Alternatively, keep the old `(tenant_id, product_id, location_id)` unique-equivalence by NOT including `company_id` in the partial indexes — match the old key shape: `(tenant_id, product_id, location_id) WHERE variant_id IS NULL` and `(tenant_id, product_id, variant_id, location_id) WHERE variant_id IS NOT NULL`. Document the decision in the spec.

### P1

**P1-1 (T1) — Batch preservation needs a movement-linked batch-movement insertion path that `BatchStockService::transferBatchStock()` does not currently expose**
- **Where:** T1 spec lines 196–202 and §11 Phase 1 ("extend `transfer()` to populate `inventory_batch_movements`")
- **Claim:** Phase 1 (Codex, ~2 PD) "extend `transfer()` to populate `inventory_batch_movements`."
- **What I found:** `apps/erp/apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:196-308` (`transfer()`) has no `$batchId` parameter and does not call into batch services. The natural reuse path — `BatchStockService::transferBatchStock()` at `apps/erp/apps/api/app/Modules/BatchExpiry/Application/Services/BatchStockService.php:130-169` — does NOT accept `$movementId` params for either leg; it just calls `recordBatchMovement()` with no `movementId`, so the resulting `inventory_batch_movements` rows would have a NULL `movement_id` (or worse, the `foreignUuid->constrained()` at `2026_01_05_150002:22` will throw, since `movement_id` is non-nullable per the migration). The pattern that DOES work is in the same file at `recordBatchMovement` (private) called from `receive()`/`issue()` with the freshly-created `$movement->id` — but that exists only on the single-leg paths.
- **Why it matters:** As written, Phase 1's "extend `transfer()`" task is ambiguous about whether to (a) extend `transferBatchStock()` to accept paired movement IDs, (b) inline the `recordBatchMovement()` call into `transfer()` directly, or (c) introduce a new `StockTransferService` that owns this orchestration end-to-end. Each is reasonable; without a decision, implementer will pick (b) and we'll end up with two private `recordBatchMovement` helpers that have already drifted (note: `BatchStockService` writes `inventory_batch_stock` via `BatchStock::firstOrCreate` while `StockAdjustmentService::recordBatchMovement` does the same thing with subtly different default precision).
- **Suggested fix:** In T1 §11 Phase 1, explicitly state: "extend `BatchStockService::transferBatchStock()` to accept `$sourceMovementId` and `$destMovementId`, and have `StockAdjustmentService::transfer()` (or the new `StockTransferService`) call it after creating both movements. Don't duplicate batch-stock bookkeeping in a second private helper."

**P1-2 (T1) — `StockAdjustmentService::transfer()` callers do not pass `$batchId`; callsite enumeration missing**
- **Where:** T1 §8 adversarial checklist line 249 ("existing `StockAdjustmentService::transfer()` callers continue to work — grep for callsites, list each")
- **Claim:** Checklist asserts backward compat will be verified.
- **What I found:** Today only `StockMovementController::transfer()` at `apps/erp/apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:180` calls `StockAdjustmentService::transfer()`. The endpoint accepts only `product_id`, `from_location_id`, `to_location_id`, `quantity`, `reference` — no batch_id field. Existing callers won't break, but the spec needs to be explicit that the endpoint is being EXTENDED (not just preserved) if Phase 1 wants the batch preservation fix to be reachable via the existing UI/API.
- **Why it matters:** Without an API contract change, the batch-preservation feature is only reachable from the NEW `StockTransferService::initiate()` path. Whether the legacy controller endpoint should ALSO be extended (with optional `batch_id` and `variant_id` body params) is not specified — and the acceptance criteria don't disambiguate. Implementer guesses, reviewer disagrees, rework.
- **Suggested fix:** Add an explicit decision in T1 §4 or §11 Phase 1: "the legacy `POST /api/v1/stock-movements/transfer` endpoint is preserved as-is (no batch_id support; existing simple intra-location moves continue to work), and all batch-preserving transfers route through the new `POST /api/v1/stock-transfers` workflow. OR: extend the legacy endpoint with optional `batch_id` and document the dual entry points." Pick one.

**P1-3 (T2) — Backward-compat sweep needs to enumerate callsites with verified counts**
- **Where:** T2 §8 adversarial checklist line 227 ("Backward compat sweep: grep callsites of `StockAdjustmentService::receive`, `::issue`, `::transfer`, `::reserve`")
- **Claim:** Checklist promises a grep sweep.
- **What I found:** I verified the actual surface area. `StockAdjustmentService` is called from `StockMovementController` (4 actions), and indirectly via `BatchStockService` (only batch-side, no aggregate stock). `ReceiptCreationService::decrementStock` at `apps/erp/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:837-904` writes `StockMovement::create([...])` and `StockLevel` updates DIRECTLY without going through `StockAdjustmentService` at all — meaning the variant-aware refactor proposed in T2 §2 patterns ("every method taking `product_id` today gets an optional `variant_id`") will silently miss the POS sales-decrement path unless explicitly listed. P1-5 in round-1 referenced this same file; the spec acknowledges integration with `AvailableQuantityService` but does NOT call out that `decrementStock` writes `StockMovement` without `variant_id`.
- **Why it matters:** A POS sale of a variant will write a `stock_movements` row with `variant_id = NULL`, breaking the variant-aware stock ledger silently. The acceptance test ("Receive 10 units of `(Taille 39, Couleur Noir)`; sell 1 — all flows identical") will pass for the stock_levels decrement but the audit/movement trail will be incomplete.
- **Suggested fix:** Add `ReceiptCreationService::decrementStock` explicitly to T2 §2 file list and adversarial checklist. Mandate that the variant-aware update covers BOTH `StockAdjustmentService` AND the direct-write paths in `ReceiptCreationService`.

**P1-4 (T2) — `product_batches` partial-unique-constraint update needs the same `(company_id)` analysis as `stock_levels`**
- **Where:** T2 §3 schema-changes line 88
- **Claim:** "`product_batches`: ADD `variant_id` (FK, nullable). Update unique constraint to include `variant_id` (partial unique index trick same as above). **Removes the TODO comment.**"
- **What I found:** Current unique is `(company_id, product_id, batch_number)` at `2026_01_05_150000_create_product_batches_table.php:47`. `company_id` here is NOT nullable (it's `foreignUuid('company_id')->constrained()->cascadeOnDelete()` at line 19). So the `product_batches` case is safer than `stock_levels` re: B-2 above, but the spec's hand-wave "same as above" hides the fact that the two tables have different `company_id` nullability and so need different migration prereqs. Also: the partial-index strategy would be `(company_id, product_id, batch_number) WHERE variant_id IS NULL` and `(company_id, product_id, variant_id, batch_number) WHERE variant_id IS NOT NULL` — should this be spelled out in the spec so implementer doesn't accidentally drop the `company_id` qualifier?
- **Why it matters:** Spec hand-waves on a load-bearing migration. Implementer guesses, fails review.
- **Suggested fix:** Write out the exact partial-index definitions for `product_batches` in §3 (don't say "same as above"), and add a one-line note that `product_batches.company_id` is non-nullable so no backfill is required (in contrast to `stock_levels`).

### P2

**P2-1 (T1) — `InTransitAvailability` storage location undefined**
- **Where:** T1 §3 enums list line 104 ("stored in tenant settings table") and §4 services list line 119-120
- **Claim:** "InTransitAvailability (tenant setting: Available, Pending, NotAvailable) — controls whether in-transit stock is sellable; stored in tenant settings table."
- **What I found:** There is no "tenant settings table" listed in the topology contract §2. Searching the codebase didn't reveal one (no `tenant_settings` table, no clear `settings` JSONB on `tenants` per the topology contract — `tenants` itself is central per the contract). The closest analogue would be `Company::$reservation_settings` (a JSONB column on `companies`) as seen in `apps/erp/apps/api/app/Modules/Company/Domain/Company.php:506-518`.
- **Why it matters:** Critical ambiguity. Is `InTransitAvailability` per-tenant (across all the tenant's companies) or per-company (each company sets its own)? The spec says "per-tenant" but tenants live in central DB post-flip — so a per-tenant setting would itself be a Pattern A cross-DB reference. More likely you want this per-company (like `reservation_settings`) — but then "InterCompanyBalanceDashboard" needs to aggregate across companies.
- **Suggested fix:** Specify the storage table: either (a) add a `tenant_settings` table to topology contract §2 (with explicit ownership), or (b) store as JSONB on `companies` and clarify the scope is per-company.

**P2-2 (T1) — `transfer_cost` semantics and currency assumptions undefined**
- **Where:** T1 §3 lines 77-78
- **Claim:** "`transfer_cost` (decimal, nullable — additional cost like delivery fees)" + four distribution strategies.
- **What I found:** No currency is specified. For Scenario A (intra-company), the company's `currency` field is unambiguous. For Scenario B (inter-company), the FROM and TO companies may have different currencies (`Company::$currency` per `Company.php:55`). The spec does not address FX, who pays the transfer cost, how it's allocated, or whether transfer cost is in the source or destination company's currency.
- **Why it matters:** WAC math (acceptance "WAC at Y reflects inter-company price + allocated transfer cost") is undefined when currencies differ. Reviewer will block.
- **Suggested fix:** Add an explicit constraint to §9 out-of-scope: "Both companies must share a currency for Scenario B in this sprint; cross-currency intercompany is out of scope." OR specify the FX path.

**P2-3 (T2) — `pos_receipt_lines` already has XOR(product_id, composite_item_id); adding `variant_id` needs disambiguation**
- **Where:** T2 §3 line 90
- **Claim:** "`pos_receipt_lines`: ADD `variant_id` (FK, nullable)"
- **What I found:** `pos_receipt_lines` has an existing CHECK constraint (`2026_03_03_100000_add_composite_item_id_to_pos_receipt_lines.php:36-40`): `(product_id IS NOT NULL AND composite_item_id IS NULL) OR (product_id IS NULL AND composite_item_id IS NOT NULL)`. So a line is EITHER a product OR a composite-item; variants must hang off the product side.
- **Why it matters:** Implementer may try to combine `variant_id` with `composite_item_id` (a CompositeItemVariant is its own concept) and produce a confusing 3-way XOR. The spec doesn't clarify that `variant_id` is only meaningful when `product_id IS NOT NULL`.
- **Suggested fix:** Add to §3 line 90: "`variant_id` is only set when `product_id IS NOT NULL`; enforce via CHECK constraint `(variant_id IS NULL OR product_id IS NOT NULL)`."

**P2-4 (T2) — Variant cost flow for WAC is undefined**
- **Where:** T2 §3 lines 70-72 (variant `price_override`/`cost_override`)
- **Claim:** Variants can have `cost_override`.
- **What I found:** Existing WAC code (`WeightedAverageCostService` via `GoodsReceiptService`) operates per-product. The spec does not specify whether WAC is computed per-product (variants share parent WAC) or per-variant (each variant has its own WAC ledger). Both have business merit — per-product WAC is simpler; per-variant WAC is more accurate for variants with different supplier prices (e.g., color-specific sourcing).
- **Why it matters:** WAC correctness for variant products is the single most expensive decision to undo. Implementer guesses, accounting math drifts.
- **Suggested fix:** Add an explicit §3 decision: "WAC is computed per `(product_id, variant_id)` tuple when `variant_id IS NOT NULL`, else per-product. Document `WeightedAverageCostService` signature change."

### SUGGESTION

- **Observation:** Acceptance line 215 mentions cancellation but only that "retrying completion is safe" — not retrying cancellation.
- **Suggested:** Add explicit cancellation-idempotency acceptance criterion (retry of `cancel` with same key is safe; movements reversed once; no duplicate reversing movements).

**S-4 (T2) — Variant matrix generation cartesian explosion bound**

- **Suggested:** Add a coordination note to both specs: "If T1 and T2 ship in different PRs, the second to land must rebase the `BatchStockService::transferBatchStock()` signature change."

**variant_id ownership boundary:** Clean. T2 explicitly owns `variant_id` additions to `stock_levels`, `stock_movements`, `stock_reservations`, `product_batches`, `document_lines`, `pos_receipt_lines`, and the (incorrectly named) batch allocations table. **Batch preservation approach in T1 vs T2 batch migration in T2:** Consistent in direction, but operationally fragile.
- T1 says: batch preservation uses the EXISTING `inventory_batch_movements` join table (`batch_id` + `movement_id`). Verified: migration `2026_01_05_150002` confirms this shape; the table has no `variant_id`.
- T2 says: `product_batches` gets a `variant_id` column; FEFO queries filter by `(product_id, variant_id)`.
- The implicit contract: an `inventory_batch_movements` row links a `product_batches` row (which carries the variant) to a `stock_movements` row (which T2 makes carry `variant_id`). So variant info is reachable from a movement via two paths: directly (`stock_movements.variant_id`) AND indirectly (`stock_movements → inventory_batch_movements → product_batches.variant_id`). These MUST agree. Neither spec asserts they must. Suggest adding an integration test: "if a movement carries `variant_id = V`, every `inventory_batch_movements` row joined to it must link to a `product_batches` row with `variant_id = V`."

**Migration directory placement:** Both specs commit migrations to `database/migrations/tenant/` per topology contract §3. No conflicting migration statements. No collision in table names. No cross-DB FKs proposed.

## What's solid

1. **Round-1 finding resolution discipline is strong.** All four cited findings are demonstrably fixed with annotations in the spec text. The annotation style ("[per Codex P3-1 finding]" inline) makes review trace-able.
2. **T1's batch preservation grounding is verified end-to-end.** The spec correctly identifies `inventory_batch_movements` (with `batch_id` + `movement_id`) as the canonical linkage and explicitly disclaims adding a redundant column to `stock_movements`. The cited migration line ranges check out.
3. **Cross-spec `variant_id` ownership is unambiguous.** T1 doesn't try to add `variant_id` to existing tables; T2 owns those additions. T1's own new table (`StockTransferLine`) carries its own `variant_id` definition. No conflicting migration statements.
