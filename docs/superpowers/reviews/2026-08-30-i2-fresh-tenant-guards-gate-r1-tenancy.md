## Findings

### BLOCKER
None. No cross-tenant read, no auth/gating change, no prod code path altered, no money/quantity arithmetic, no `latestOfMany`, no new `can:` guard, no route middleware touched.

### MAJOR

**M-1 — The `waiver` field carries zero discriminating signal, and baseline growth is unbounded ⇒ the ratchet is self-service.**
`tests/Architecture/Support/TenantOnlyUniqueBaseline.php:41-43` *requires* a non-empty `waiver` on **every** entry, so a waiver is not a distinguishing act — it is the price of admission. Seven of the nine shipped entries carry the identical string `"Pre-existing tenant-only catalogue key; company-scope ownership remains to be resolved."` (`baselines/tenant-only-unique-baseline.json:4,8,12,16,32,36`), which by `docs/conventions/09-SECOND-OF-EVERYTHING.md:63-65` ("A waiver is legitimate when the value is tenant-global by nature — a user email, a signing-key id, an idempotency key") is **not a legitimate waiver at all**; it is frozen debt. Consequence: a contributor who lands `unique(['tenant_id','code'])` on `categories` tomorrow silences the ratchet in the same diff by pasting a `waiver` string that reads *character-identical* to seven accepted entries, and no reviewer heuristic separates the two. Nothing else constrains the file — the checker enforces shrink-only for *removals* (`TenantOnlyUniqueRatchetChecker.php:38-43`) but there is **no entry-count ceiling, no protected/pinned blob, and no classification**, unlike the DPA precedent this repo already runs (`ci.yml:167-172`: "the anti-growth ratchet resolves the owner-pinned baseline blob out of the object store, and fetches the pin tag", `fetch-depth: 0`).
*Fix:* require a `"kind": "tenant_global" | "legacy_frozen"` on each entry (reject unknown values in `fromFile`); rewrite the seven generic strings to either a real tenant-global justification (vehicles VIN is arguably one; `loyalty_members.phone` and `brands.slug` are not) or a `legacy_frozen` entry naming the owning follow-up; and assert a hard-coded `MAX_LEGACY_FROZEN = 7` (or the final count) constant **in the test class**, so any growth requires editing a test file line that a reviewer cannot mistake for boilerplate.

**M-2 — `CATALOGUE_TABLES` is a hardcoded allowlist with no unclassified-table detector: a new catalogue table gets zero coverage, silently.**
`TenantOnlyUniqueOnCatalogueTablesRatchetTest.php:30-48` enumerates 17 tables and the docblock (`:21-24`) names 9 "deliberately excluded" ones. The live schema contains tenant-only uniques on tables in **neither** list: `companies(tenant_id,code)`, `companies(tenant_id,tax_id)`, `roles(tenant_id,name,guard_name)`, `stock_levels(tenant_id,product_id,location_id)` ×2, `media_attachments(tenant_id,owner_type,owner_id,media_asset_id)`, `replenishment_capture_receipts(tenant_id,client_request_uuid)`, `grouped_write_offs(tenant_id,idempotency_key)`, `model_has_permissions`/`model_has_roles` (verified by live `pg_index` scan). None of those is a second-company hazard today, but the *structure* is: the set of covered tables can only rot, and the rot is invisible — exactly the failure mode `tools/feature-lane-manifest-check.php` was built to prevent for CI lanes ("a top-level group with no disposition … the property that cannot rot", `ci.yml:186-189`). A future `price_lists`, `expense_categories` or renamed catalogue table is outside the scan and nothing says so.
*Fix:* add a second `#[Test]` that scans **all** tables carrying a tenant-only unique and asserts each one appears in `CATALOGUE_TABLES` ∪ a new committed `TENANT_GLOBAL_TABLES` const — failing with "table X carries a tenant-only unique and is classified by neither list; classify it". One-time cost: classify the ~10 tables listed above.

**M-3 — The scan predicate is narrower than the rule it enforces: two trivial spellings evade it.**
`TenantOnlyUniqueIndexScanner.php:47` drops any index whose **leading** column is not `tenant_id`, and `:50` only excludes on `company_id`. Therefore, on a catalogue table:
(a) `unique(['sku','tenant_id'])` — same hazard, tenant_id not leading — is invisible;
(b) `unique(['sku'])` with **no** tenant_id at all — the *most likely* future spelling, since under db-per-tenant `tenant_id` is physically redundant and new code keeps dropping it — is invisible. The live schema already contains that shape on a catalogue table: `products_platform_submission_id_unique | platform_submission_id` and `product_variants_default_unique | product_id`. A migration writing `$table->unique('code')` on `categories` would block company B from company A's code and pass this ratchet green.
*Fix:* change the predicate to "unique key on a catalogue table whose column list does not contain `company_id`", excluding the PK and single-surrogate-id keys, and regenerate the baseline (the extra entries are exactly what the `waiver` field is for). If the owner prefers the narrow version, at minimum relax `:47` from `$columns[0] !== 'tenant_id'` to `! in_array('tenant_id', $columns, true)` and record (b) as a written residual.

**M-4 — The census re-implements the units-visibility predicate that its owner declares a single substitution point (conv. 11).**
`DayOneCensus.php:91-97` inlines `is_active = true AND (tenant_id IS NULL OR tenant_id = :tenant)`. That is a character-copy of `app/Modules/Uom/Application/Services/UnitsProvisioningService.php:18-27`, whose docblock reads: *"This is the ⛔ SCOPE-DEPENDENT predicate of spec §4.13.2 and is the single substitution point for OQ-G-25."* When the owner rules OQ-G-25 and the predicate becomes per-company, `UnitsProvisioningService` changes and the census keeps asserting the old, always-identical-for-both-companies predicate — i.e. the guard whose entire purpose is to catch "units 0 / not visible per company" (N-9) goes false-green on the very ruling that makes the question interesting. (Today the two agree, so no live defect; verified by reading both.)
*Fix:* inject `UnitsProvisioningService` and call `visibleActiveUnitCount($company)` — precedent for that exact cross-module use already exists in production code at `app/Modules/Company/Presentation/Controllers/CompanyController.php:30,58`. If a `Company` model instance is unwanted in the census, add a `Shared/Contracts` read port; do not keep a second copy.

### MINOR

**m-1 — `--company` is bound into a PG `uuid` column with no `Str::isUuid()` guard.** `DayOneCensusCommand.php:32-34` → `DayOneCensus.php:67-69` `$query->where('id', $companyId)`. `php artisan tenant:census-day-one --company=acme` throws `QueryException: invalid input syntax for type uuid` instead of the clean "company … does not exist" message the command already has at `:37-41`; under `tenants:run` an escaping exception aborts the remaining tenants. *Fix:* validate and return `self::FAILURE` with the existing message.

**m-2 — Magic status string instead of the enum (rule 9).** `DayOneCensus.php:288` `->where('status', 'draft')` (and the test twin, `FreshTenantCensusInvariantsTest.php:387`) while `App\Modules\Document\Domain\Enums\DocumentStatus:9` defines `case Draft = 'draft'`. Use `DocumentStatus::Draft->value`.

**m-3 — `classifiedPurposePresence` re-introduces the fail-open pattern the manifest explicitly documents as forbidden.** `DayOneCensus.php:345-351` compares `$entry['classification'] !== 'CONDITIONAL'|'SOFT'` — bare strings against `ProvisioningRequiredPurposesV1`'s **private** consts, the precise anti-pattern its docblock condemns ("a bare string compared against a PRIVATE const. That comparison FAILS OPEN … every such filter silently matches nothing"). Impact is limited to the reported `conditional=0/0 soft=0/0` counters (not asserted), but the failure is silent. *Fix:* ask the authority (add a read accessor there, or reuse `entries()` + a public classification accessor) rather than string-comparing.

**m-4 — SCOPE_REQUIRED is hardcoded rather than derived.** `DayOneCensus.php:160-164` hardcodes `SalesStampDutyPayable` and `country_code !== 'TN'`. The manifest carries the classification (`ProvisioningRequiredPurposesV1` SCOPE_REQUIRED entry) but no country field, so the TN scope is the implementer's inference and a second SCOPE_REQUIRED entry would be silently unchecked. *Fix:* enumerate SCOPE_REQUIRED from `entries()` and cite the source of the TN scope in the description.

**m-5 — Census location predicate ≠ test location predicate.** `DayOneCensus.php:214-219` selects `pos_enabled = true` with **no** `is_active` filter; `FreshTenantCensusInvariantsTest.php:164-168` filters `is_active`. A deactivated-but-`pos_enabled` location therefore reads DRIFT from the operator command while the CI test that is supposed to mirror it reads clean. Pick one predicate (deactivated locations should almost certainly be exempt).

**m-6 — A company with zero POS locations is vacuously CLEAN.** `DayOneCensus.php:221-239` emits drawer rows only per existing POS location, so the N-12 invariant disappears entirely for a company whose Main lost `pos_enabled`. Consider a row asserting ≥1 `pos_enabled` location per company on day one.

**m-7 — The country-template pin only exercises TN.** Invariant 4's stated purpose (brief §Part A.4) is that "a future template that omits them fails HERE". The fixture is TN-only (`BuildsFreshTenantCensusFixture.php:39,74`), so `FranceChartOfAccountsSeeder` and `GenericChartOfAccountsSeeder` are unguarded in CI; only a live FR tenant would surface the regression. Add an FR (or generic) company leg.

**m-8 — Zero-entry `CATALOGUE_TABLES` membership is unpinned.** The baseline pins membership only for the 6 tables it references, and liveness pins `products` (`TenantOnlyUniqueRatchetLivenessTest.php:33,38`) and `payment_methods` (`:52`). `documents` — kept in the list by explicit gate ruling (brief §Part C, dispatch note line 21) — can be deleted from the const with everything staying green. Add `assertSame([...expected list...], self::CATALOGUE_TABLES)` or fold it into M-2's classification test.

**m-9 — `ci.yml` tokens appended with no rationale comment.** Every prior batch on that filter carries a comment block explaining why (`ci.yml:1093-1113` for G-7/G-12/G-6a/G-3a/G-3b/G-3c). This diff appends 4 tokens with none. The manifest note (`tests/feature-lane-manifest.json`, Tenant 29→31) documents only the two Feature classes; the two Architecture classes are documented nowhere in CI. Add the 3-line precedent comment.

**m-10 — `docs/conventions/09-SECOND-OF-EVERYTHING.md:20` is now stale.** It still lists `documents(tenant_id,type,document_number)` and `product_variants(tenant_id,sku)` among "live tenant-wide uniques on operator-edited tables"; both are company-scoped in the live schema (verified). ## VERDICT: **CHANGES-REQUIRED** (spec ❌ on ratchet strength; census implementation quality otherwise good)

The census half is solid and I found no tenancy defect in it. The ratchet half ships the *shape* convention 09 promises but not its *force*: as committed, a new tenant-only unique on a catalogue table can be waived in the same diff with boilerplate indistinguishable from the accepted entries (M-1), a new catalogue table gets no coverage at all with nothing to say so (M-2), and two ordinary spellings of the same hazard are simply not scanned (M-3). Since this batch exists to install the guard, landing the weak form makes the weak form permanent.

**Minimum to flip to MERGEABLE:** fix **M-1** (kind field + hard-coded legacy count in the test class) and **M-4** (delegate to `UnitsProvisioningService::visibleActiveUnitCount`), plus **m-1** and **m-2**. **M-2** and **M-3** are acceptable to defer *only* if the orchestrator records them as a named follow-up lane in the Session I ledger before promotion, with the residual stated in writing; they must not be dropped. **m-10** and **o-1** are orchestrator actions, not implementer work.

**One line to fix before merge:** make the waiver mean something (M-1), stop copying the units-visibility predicate (M-4), guard the `--company` UUID (m-1), use `DocumentStatus::Draft` (m-2) — then re-run the four classes on one PG leg.
