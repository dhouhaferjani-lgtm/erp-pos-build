## 1. What was broken

**W4-2 (P0).** Three cash rails that never spoke to each other, and no path from any of them to a
day-one float:

- Treasury → "Adjust balance" refuses a never-seeded repository (`REPOSITORY_NOT_SEEDED`) and, if it
  did not, would credit `PaymentToleranceIncome` — booking the float as **revenue**, sealed into the
  fiscal hash chain.
- The ACCOUNTING opening-balance wizard posted `Dr 53 / Cr 119` and wrote **nothing** to Treasury.
- A transfer out of the resulting empty till fails `INSUFFICIENT_REPOSITORY_BALANCE`.

`MovementSourceType::OpeningBalance` had exactly one reference in the whole API and it was a **read**
(`ReconcileTreasuryCommand.php` `isJournalEntryExempt`). The schema anticipated a writer that did not
exist. Campaign evidence: GL cash 1364.200 vs repositories 209.200.

**W4-10 (P1).** `ExpenseService::create()` defaults `is_paid` to `true`. A payload setting neither
`payment_repository_id` nor `payment_date` minted an expense **born paid with no till**: posting
settled it against the default cash GL account (`Dr 65 + Dr 4456 / Cr 53 45.000`) with **no**
`repository_movements` row, and `/pay` — the only endpoint that accepts a repository — then refused
it as already paid. GL cash fell 45.000; the drawer never moved, irreversibly.

## 2. The design, and the two places it departs from the research brief

The wizard's ACCOUNTING template gains an optional **`repository_code`** column. A row carrying it
posts the GL line **and** the repository's opening movement inside `postBatch`'s existing
`DB::transaction`, keyed `opening_balance:{batchId}:repository:{repositoryId}`.

The opening-balance **batch is the justifying document** (document-per-action): it carries the
cutover date, the row, a `Draft → Validated → Locked` lifecycle that seals immutably at post, and now
the treasury leg. No new document type was invented.

Research brief `RESEARCH-opening-float-and-vat-doc-count-2026-08-23.md` §1.7 sketched a different
shape. Two deliberate departures, both worth the reviewer's attention:

1. **The movement carries a `journal_entry_id`** (the batch's own historical entry), not the `null`
   the reconciler already exempts. §1.7 proposed null-JE. Linking it is what makes
   `ReconcileTreasuryCommand` **check 2** — which treats the JE's line(s) on the repository's own
   `gl_account_id` as AUTHORITATIVE — *enforce* `till == ledger` for the life of the tenant rather
   than merely tolerate a divergence. The null-JE exemption is untouched and still covers other
   paths.
   *Consequence the reviewer should probe:* a MERGED row (one `Dr 53 1200.000` line intended to seed
   two tills) would fail check 2's per-line/sum match and **freeze the drawer in production**. That
   is exactly why one row seeds exactly one repository, why a repository may be named only once per
   batch, and why the test now mirrors the predicate directly.
2. **No new `MovementReasonCode` case.** §1.7 suggested `opening_float`. `MovementReasonCode` is the
   operator-chosen count-variance vocabulary the "Adjust balance" dialog renders
   (`count_variance | correction | theft_loss | other`); adding a case there would surface "opening
   balance" as an adjustment choice and reopen the exact revenue-booking misuse
   `RepositoryNotSeededException` closes. The movement carries `reason_code = null`;
   `source_type = opening_balance` already carries the meaning.

**Module boundaries.** Accounting depends only on
`App\Shared\Contracts\Treasury\RepositoryOpeningBalanceSeederInterface` and three Shared DTOs — never
on a Treasury model. The `@throws` for the Treasury domain exception is named **in prose** in the
interface docblock, because pint's `fully_qualified_strict_types` fixer converts an `@see`/`@throws`
FQCN into a real `use` statement (the same trap `RepositoryNotSeededException` documents).

## 6. Residuals — seen, deliberately NOT touched

- **R-1 — the drawer and the safe share GL account `53`.** `PaymentRepositorySeeder.php:120` links
  both to the `Cash` purpose account, so a drawer→safe remittance posts no journal entry and cash
  location is invisible in the ledger (the campaign report flags this too). W4-2 works correctly
  either way — the per-row match handles two lines on one account — but the seeded provisioning
  choice is the owner's. The TN chart ships `531 Caisse siège`.
- **R-2 — `reference` vs `description`.** The ACCOUNTING template offers a `reference` column that
  the backend never reads (it validates `description`), so the operator's audit reference is silently
  dropped. One-word fix, adjacent to files this lane touched, deliberately left alone (rule 4). The
  new `repository_code` column does NOT share this defect — it is validated end to end.
- **R-3 — `MovementResult::$balanceAfter` is typed `string`, documented "numeric-string".**
  `OpeningFloatResult` mirrors it rather than narrowing to `numeric-string`, which would have pushed
  a PHPStan error onto six `new MovementResult(...)` sites in `TreasuryMovementService` — out of lane.
  Tightening both together is a clean follow-up.
- **R-4 — the W4-10 carve-out is method-shaped, not rail-shaped.** A non-cash method born paid with
  no repository is allowed and still credits the **Cash** purpose account via `createFromExpense`'s
  `RepositoryType::CashRegister` default. That is the brief's scope boundary ("unless a non-cash
  payment method is chosen"), but a card/transfer expense arguably belongs on a bank account. Worth
  an owner ruling before a second tenant.
- **R-5 — a repository with `gl_account_id = NULL` is accepted** on an opening row and seeded against
  whatever account the row debits. The account-match refusal can only fire when the link exists.
  `PaymentRepositorySeeder` warns and leaves the link null when the chart is missing, so this is
  reachable on a mis-provisioned tenant.
- **R-6 — no backfill for tenants already seeded GL-only.** A tenant whose opening batch is already
  `Locked` cannot be re-posted; its tills stay at zero in Treasury. The runbook's remedy (a Treasury
  transfer, or a fresh batch naming the repository) is documented at
  `docs/handoff/RUNBOOK-opening-cash-float-2026-08-23.md` §4. No migration and no repair command
  shipped — flagged for the owner rather than guessed at.
- **R-7 — `TREASURY_SHIFT_VARIANCE_GL_ENABLED` stays `false`.** W4-2 closes the *float* half of SV-3.
  The deposit/payout half (SV-3's other half) and SV-4 (`recordOpening` fires no event) are untouched,
  so the pre-enable gate is **not** cleared. `config/treasury.php:28` unchanged.
- **R-8 — `docs/modules/treasury.md` not updated.** It documents payment methods and instruments and
  has no opening-balance section; the runbook is the right home and carries the change.
