# Session C spec+plan adversarial review r1

## Verdict

CHANGES-REQUESTED

## Findings

**F-1 · Critical · area A** — The proposed universal `closed` predicate is unreachable for several document types. The spec requires `posted ∧ fulfilled/n-a ∧ paid/written_off`, while orders never post and delivery/return notes seal at `confirmed`; payment is also NULL for DN/RN/RFQ ([SPEC:22](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:22), [SPEC:65](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:65), [SPEC:100](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:100), [ReturnNoteService.php:651](apps/api/app/Modules/Document/Domain/Services/ReturnNoteService.php:651), [DeliveryNoteService.php:156](apps/api/app/Modules/Document/Domain/Services/DeliveryNoteService.php:156)). Consequently, PurchaseOrders, SalesOrders, DeliveryNotes and ReturnNotes can never close, violating the owner mandate. Replace the universal conjunction with a normative per-`DocumentType` closure table; specify recompute links for posting/confirmation, fulfilment changes, payment reversals, credit applications, returns and cancellation.

**F-2 · Critical · area A/C** — The payment-status formula would misclassify historical openings and native credit notes. The spec says `unpaid` iff no allocations, but historical AR/AP rows deliberately have authoritative `balance_due=open_amount` without allocations ([SPEC:56](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:56), [ArApOpeningService.php:311](apps/api/app/Modules/Document/Application/Services/ArApOpeningService.php:311), [Document.php:739](apps/api/app/Modules/Document/Domain/Document.php:739)); credit-note settlement is instead outward application keyed by `credit_note_id`, while the generic balance formula joins `invoice_id` ([Document.php:698](apps/api/app/Modules/Document/Domain/Document.php:698)). A historical invoice with total 1,500/open 300 becomes “unpaid,” and a credit note’s cache tells the wrong directional story. Define type-specific settlement bases: authoritative `balance_due` for AR/AP openings; outward applied/refunded amount for CNs; supplier-side application for SCNs. Derive `written_off` from live tolerance allocations, not a separately mutable boolean.

**F-3 · Critical · area B/I** — The proposed VAT fix is type-blind and would delete all posted expenses from input VAT. The query currently includes invoice, credit note and expense together ([EloquentVatDataRepository.php:30](apps/api/app/Modules/Taxation/Infrastructure/Repositories/EloquentVatDataRepository.php:30)); expenses only change lifecycle to `Posted` and are not fiscally sealed ([ExpenseService.php:309](apps/api/app/Modules/Expense/Application/Services/ExpenseService.php:309)). C-R1 proposes adding `fiscal_status=SEALED` to that shared query ([PLAN:85](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:85)). Use a grouped predicate such as fiscal sales documents sealed, plus the appropriate posted predicate for expense/input-VAT types. Add expense and cancelled-CN regressions and quantify the tenant-period delta before owner acknowledgement.

**F-4 · Critical · area B/I** — Fiscal-chain remediation is incomplete and `SEALED` alone is the wrong chain membership predicate. The verifier admits only Invoice/CreditNote and filters lifecycle `Posted` ([VerifyFiscalChainsCommand.php:258](apps/api/app/Modules/Compliance/Commands/VerifyFiscalChainsCommand.php:258), [VerifyFiscalChainsCommand.php:280](apps/api/app/Modules/Compliance/Commands/VerifyFiscalChainsCommand.php:280)); both DeliveryNotes and ReturnNotes maintain independent sealed chains ([DeliveryNoteService.php:105](apps/api/app/Modules/Document/Domain/Services/DeliveryNoteService.php:105), [ReturnNoteService.php:590](apps/api/app/Modules/Document/Domain/Services/ReturnNoteService.php:590)). Cancellation keeps the fiscal hash but changes fiscal status to `VOIDED` ([DocumentPostingService.php:217](apps/api/app/Modules/Document/Domain/Services/DocumentPostingService.php:217)), so selecting only `SEALED` drops a real chain member and can reuse/fork the head. The verifier also reconstructs the hash date from `document_date`, although writers hash the actual posting/confirmation date ([VerifyFiscalChainsCommand.php:309](apps/api/app/Modules/Compliance/Commands/VerifyFiscalChainsCommand.php:309), [DocumentPostingService.php:477](apps/api/app/Modules/Document/Domain/Services/DocumentPostingService.php:477)). Define one chain-membership scope keyed by company, type, non-null hash/sequence, including SEALED and VOIDED; support Invoice, CreditNote, DeliveryNote and ReturnNote; verify using persisted sealing instant. Add chain-head, verification and voided-tail tests for every type.

**F-5 · Critical · area C/F** — Deferring OQ-3 leaves an active writer producing the wrong GL direction while Phase 2 advertises PurchaseOrder payment status. On the N-6 branch, unmatched document pairs fall through to `ReceivableClearing` ([fix/campaign-n6-payment-advance:DocumentAllocationClassifier.php:82](apps/api/app/Modules/Treasury/Application/Services/DocumentAllocationClassifier.php:82)); a PO is treated as non-supplier and reaches customer-receipt GL ([fix/campaign-n6-payment-advance:PaymentController.php:591](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:591), [fix/campaign-n6-payment-advance:PaymentController.php:1149](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:1149)), while its refund uses supplier-advance GL ([VendorRefundService.php:167](apps/api/app/Modules/Treasury/Domain/Services/VendorRefundService.php:167)). Do not leave this as a residual: immediately classify PurchaseOrder as refused until the 409 path exists, or make the 409 fix a prerequisite to C-2a.

**F-6 · Critical · area D/F** — The lane graph has an impossible dependency cycle. C-R1 depends only on C-2a but consumes `DocumentFulfilmentService` and `fulfilment_status`, which C-P1 creates; C-P1 in turn promises supplier-return decrement while the required `quantity_returned` column is created by C-R1 ([PLAN:22](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:22), [PLAN:26](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:26), [PLAN:66](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:66), [PLAN:85](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:85)). Create a shared fulfilment-schema foundation lane before both P and R, or make R depend on P and explicitly use the same return cache for purchases.

**F-7 · High · area C** — Supplier-invoice cancellation is materially under-specified. Posting increments PO `quantity_invoiced`, receipt-line `quantity_invoiced`, bonus counters and creates the GR-IR clearing JE ([SupplierInvoicePostingService.php:153](apps/api/app/Modules/Procurement/Application/SupplierInvoicePostingService.php:153), [SupplierInvoicePostingService.php:211](apps/api/app/Modules/Procurement/Application/SupplierInvoicePostingService.php:211), [SupplierInvoicePostingService.php:343](apps/api/app/Modules/Procurement/Application/SupplierInvoicePostingService.php:343), [SupplierInvoicePostingService.php:276](apps/api/app/Modules/Procurement/Application/SupplierInvoicePostingService.php:276)). C-P2 only says “reversal JE, refuse allocations, VAT guard” ([PLAN:79](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:79)). Require atomic reversal of the exact receipt slices, PO paid/free invoiced counters, 408/401/VAT GL, match snapshot, balance/payment cache and downstream eligibility; test repost after cancellation and locked-period refusal.

**F-8 · High · area A** — The “every document” model omits Expense, Income, CorrectingEntry, Quote and RFQ semantics while enforcement intends to route their writers. `DocumentType` contains thirteen cases ([DocumentType.php:7](apps/api/app/Modules/Document/Domain/Enums/DocumentType.php:7)); the edge-guard table only covers four grouped families ([SPEC:98](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:98)). Expense and Income currently post directly from Draft ([ExpenseService.php:309](apps/api/app/Modules/Expense/Application/Services/ExpenseService.php:309), [IncomeService.php:145](apps/api/app/Modules/Income/Application/Services/IncomeService.php:145)); CorrectingEntry already requires Confirmed ([CorrectingEntryService.php:140](apps/api/app/Modules/Document/Application/Services/CorrectingEntryService.php:140)). Add an exhaustive `DocumentType × lifecycle × fulfilment × payment × fiscal × closure` applicability/guard matrix before routing writers.

**F-9 · High · area D/I** — `quantity_returned` on “the source line” is not a safe cache design. Return notes can source either an invoice or a delivery note, and current correctness depends on the union of the invoice plus all backing delivery notes, aggregated by product/location ([ReturnNoteService.php:296](apps/api/app/Modules/Document/Domain/Services/ReturnNoteService.php:296), [DeliveredQuantityResolver.php:463](apps/api/app/Modules/Document/Domain/Services/DeliveredQuantityResolver.php:463)). Writing only the directly referenced DN’s lines will not update the invoice cache. Supplier goods-return confirmation moves stock but does not adjust PO receipt facts ([SupplierGoodsReturnNoteService.php:413](apps/api/app/Modules/Inventory/Application/Services/SupplierGoodsReturnNoteService.php:413), [SupplierGoodsReturnNoteService.php:462](apps/api/app/Modules/Inventory/Application/Services/SupplierGoodsReturnNoteService.php:462)). Specify a canonical `(commercial source, product, location)` recompute, or maintain both direct and aggregate caches transactionally; test invoice-sourced RN, DN-sourced RN, consolidated DN sets, supplier return, and reversal/cancellation.

**F-10 · High · area G** — The policy design creates two authorities for the same purchase-posting decision. It adds `purchase_posting_policy` while also layering country defaults into `procurement_policies` ([SPEC:124](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:124)); the existing resolver already treats the company row as the override over a vertical default ([ProcurementPolicyResolver.php:14](apps/api/app/Modules/Procurement/Application/ProcurementPolicyResolver.php:14)). This contradicts the expert’s “one authority” requirement ([expert ruling:23](docs/superpowers/tickets/2026-08-10-expert-rulings-deferred-revenue-vat-issuance.md:23)). Use one country-default record feeding the existing procurement policy vocabulary, with precedence `company override > country default > fail-closed system default`; remove the duplicate posting column. Treat FR purchase defaults as provisional pending owner/expert approval rather than copying TN.

**F-11 · High · area E** — The enforcement claim exceeds what the PHPStan rule can prove, and `initialStatus()` risks becoming a sanctioned bypass. Phase 1 explicitly admits unresolved enum expressions, raw SQL, migrations and seeders are outside coverage ([fix/campaign-n6-payment-advance:DocumentStatusWriteOnlyViaStatusService.php:48](apps/api/app/PHPStan/Rules/DocumentStatusWriteOnlyViaStatusService.php:48)); C-2c nevertheless claims “ANY” write and allowlists the whole service ([PLAN:57](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:57)). The production demo seeder still creates `Paid` rows and will fail after CHECK tightening ([DemoPharmacySeeder.php:1680](apps/api/database/seeders/DemoPharmacySeeder.php:1680)). Specify `initialStatus()` as a pure Draft-only value or create API with no caller-supplied status; update seeders/factories; retain the rule’s documented boundary; add checked query-builder/raw-writer census and DB parity coverage.

**F-12 · High · area B/C/F** — C-3b is not an implementer-day lane and its 472 accounting is incomplete. It combines schema, seeds, resolver precedence, company overrides, frontend UI and deferred-revenue GL ([PLAN:99](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:99)). The proposed “Dr 411 / Cr 472 for the undelivered share” omits full Art. 18 VAT treatment and the delivered revenue split; the expert requires VAT immediately on issuance but revenue deferral under NCT 03 ([expert ruling:7](docs/superpowers/tickets/2026-08-10-expert-rulings-deferred-revenue-vat-issuance.md:7)). Split schema/seeding, resolver/UI, posting deferral, delivery recognition and reversal/CN behavior into separate lanes with a balanced JE matrix and per-line physical/service allocation rules.

**F-13 · High · area B/H** — The program carries an unresolved legal contradiction on confirmed-unposted printing. N-6 permits a definitive-looking print with VAT ([BRIEF:45](docs/sessions/session-A-2026-08-24/BRIEF-N6-payment-advance.md:45)), while the adopted expert ruling says VAT mention creates immediate liability and recommends no definitive invoice before delivery, using a VAT-free proforma instead ([expert ruling:12](docs/superpowers/tickets/2026-08-10-expert-rulings-deferred-revenue-vat-issuance.md:12), [expert ruling:18](docs/superpowers/tickets/2026-08-10-expert-rulings-deferred-revenue-vat-issuance.md:18)). Add an owner question and state the fail-safe default: confirmed-unposted output is explicitly proforma/non-definitive and contains no VAT mention until the owner resolves the conflict.

**F-14 · High · area B** — The spec places the binding TN QR condition out of scope. It states TN “posted = sealed + Ministry QR” but then leaves QR as another fiscal lane ([SPEC:88](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:88)); the confirmed model requires both before `posted` ([BRIEF:8](docs/sessions/session-A-2026-08-24/BRIEF-N6-payment-advance.md:8)). That permits lifecycle `posted` while the fiscal dimension is incomplete. Specify a TN posting guard or an explicit intermediate fiscal state; this cannot be deferred without owner approval.

**F-15 · High · area A/I** — Retiring lifecycle `Paid` can silently stop or duplicate `DocumentFullyPaid` events. N-6 dispatches only by testing lifecycle `status === Paid` ([fix/campaign-n6-payment-advance:PaymentController.php:1062](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:1062)); C-2a replaces that status write with recomputation but names no event-edge behavior or test ([PLAN:31](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:31)). Emit the existing immutable event only on a locked transition from non-paid to `payment_status=paid`; preserve its schema and add replay, duplicate-allocation and reopen/re-pay tests.

**F-16 · Medium · area C/I** — `overpaid` is presented as an ordinary per-type state although current writers deliberately prevent it. Customer allocations are capped and excess becomes an advance; supplier excess is rejected ([fix/campaign-n6-payment-advance:PaymentController.php:595](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:595), [fix/campaign-n6-payment-advance:PaymentController.php:778](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:778)). C-2a nevertheless requires overpaid tests for every type ([PLAN:44](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:44)). Define whether `overpaid` is legacy/import defence only, or introduce a legitimate credit-balance writer; do not invent unreachable fixtures as proof.

**F-17 · Medium · area E/F** — Migration and CHECK ownership is contradictory. C-2b is marked “NO” migration and “YES, index-only” in the same row; C-2a and C-P1 successively tighten the same Phase-1 CHECK; Session B Slice D also owns CHECK parity ([PLAN:19](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:19), [PLAN:20](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:20), [PLAN:22](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:22), [HANDOVER:57](docs/sessions/session-C-lifecycle-2026-08-24/HANDOVER-document-lifecycle-dimensions-program.md:57)). Give each versioned constraint/index one owner and dependency; update Slice D’s parity list only after the final status-domain migration.

**F-18 · Medium · area F** — Several lanes exceed the plan’s stated one-day size. C-2c spans 31 writers, many modules, a PHPStan rule and a transition-log migration; C-R1 combines returns caching, lifecycle routing, fiscal verifier, payment derivation and VAT reporting; C-3b combines schema, UI and a new accounting engine ([PLAN:14](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:14), [PLAN:57](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:57), [PLAN:85](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:85), [PLAN:99](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:99)). Split them by invariant and hotspot; do not run C-2c concurrently with C-P1 because both edit `SupplierInvoicePostingService`.

**F-19 · Medium · area H** — OQ-11’s premise is false: bank-reconciliation facts exist. `payments.is_reconciled` and `reconciled_at` are persisted and cast ([Payment.php:52](apps/api/app/Modules/Treasury/Domain/Payment.php:52), [Payment.php:118](apps/api/app/Modules/Treasury/Domain/Payment.php:118)); current `getPaymentStatus()` incorrectly queries a nonexistent treasury status value `reconciled` ([Document.php:905](apps/api/app/Modules/Document/Domain/Document.php:905)). Removing `in_payment` is therefore a product/accounting choice, not cleanup justified by absence. Correct the premise and require an owner ruling.

**F-20 · Medium · area I** — The red-first matrix does not prove several normative claims. Missing named tests include historical partial openings, service-only `not_applicable`, every closure recompute link, Expense/Income/CorrectingEntry routing, DB-trigger-to-cache parity, DN and VOIDED fiscal chains, expense VAT retention, PO payment refusal, supplier-cancel counter restoration, DN-sourced returns, country/company policy precedence, immutable event dispatch, demo seeding after CHECK tightening and 472 delivery/reversal GL ([PLAN:44](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:44), [PLAN:54](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:54), [PLAN:76](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:76), [PLAN:90](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:90), [PLAN:93](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:93)). Add explicit test names and claims before implementation dispatch.
