# POS receipts/reporting spec adversarial gate — round 1

## 1. Gate verdict — REVISE

The direction is sound, the owner rulings are mostly carried forward, and most source citations survive inspection. The spec is not safe to dispatch yet. A builder cannot produce the promised separate refunds register from the specified single-value filter, and the live refund projection does not expose the human refund reason, original receipt number, or refund destination that the screen requires. More seriously, the proposed chain panel treats a verifier that flattens four independently sequenced fiscal chain contexts as an authoritative receipt-chain verdict, while the A0 dossier explicitly says the receipt-side verifier and projection↔event mirror check are not yet honest. The spec also omits membership-level location authorization from every receipt read, states a cash-rounding-invalid aggregate identity, mixes refunds back into the primary “All” list despite the owner’s separate-register ruling, and assigns voucher-link healing to a wave that does not contain the detail route. These are contract defects, not implementation polish; correct them in the spec before build dispatch.

## 3. Defects found and required fixes

1. **The primary list violates the separate-refunds ruling, and the refund register has no valid paginated query.** `/pos/receipts` defaults to “All,” which blends REFUND/VOID into the sales register, while S-2 defines only a singular `invoice_type_code` equality filter; `/refunds` needs REFUND **or** VOID in one server-side paginated result (`SPEC:124-137,224-253,291-304`; owner ruling `OWNER-DECISIONS-ui-audit-2026-08-10.md:54-60`). **Required fix:** make the registers disjoint by contract: primary register defaults to production SALE (plus explicit TRAINING opt-in), refunds register uses a validated `invoice_type_codes[]=REFUND&invoice_type_codes[]=VOID` or a dedicated server predicate. Remove refund/void tabs from the primary register unless the owner explicitly rules that duplication still counts as “separate.” Add a pagination test proving a mixed REFUND/VOID page is server-generated, not client-merged.

2. **The live refund row cannot render three promised columns.** Index output has `original_receipt_id` and the legacy enum `return_reason`, not original receipt number or destination (`ReceiptController.php:113-132`). V4 projection deliberately stores `return_reason=other`; the actual free-text reason remains in the canonical fiscal payload (`PosCoreReceiptProjection.php:434-446`). No `refund_destination` receipt column/response field is present in the opened receipt model/projection, while the spec requires destination display (`SPEC:248-255`). **Required fix:** add an additive reporting DTO/resource projection that supplies `original_receipt_number`, authoritative `refund_reason`, and `refund_destination` from the parsed fiscal event (never by sending `canonical_bytes`). Specify names, null/legacy behavior, joins, and tests for v4 plus legacy returns.

3. **The current HTTP verifier is not safe to present as a receipt-chain verdict.** It flattens independently sequenced contexts and lacks the projection↔event mirror check (`ReceiptHashService.php:234-250`; fiscal unique key `2026_05_14_100001_create_fiscal_events_table.php:91-95`; A0 contract `HANDOVER-event-sourcing-remediation-2026-08-11.md:107-126`). A caption cannot turn a false negative/false positive into an honest control. **Required fix:** make screen (d) a hard dependency on A0, remove the “ship earlier with captions” option, and re-verify the post-A0 endpoint shape before freezing UI copy/tests. Do not implement the verifier fix in this lane.

4. **Membership-level location authorization is absent from the whole read surface.** `ReceiptController` scopes by company only for index/show/PDF (`ReceiptController.php:66-69,473-488,594-599,627-632`), while users can have restricted `allowed_location_ids` and the canonical helper fails closed (`LocationContext.php:181-238`). Passing `useViewScope` IDs from the browser is not authorization. **Required fix:** define and apply allowed-location intersection to index, show, both PDF actions, S-7 terminals/cashiers, and receipt-chain terminal selection. Add deny tests for a same-company receipt/terminal outside the caller’s membership scope, including direct-ID and PDF requests. Decide whether denial is 403 or non-enumerating 404 and pin it.

5. **The aggregate integrity equation is wrong for valid rounded receipts.** The spec omits signed `cash_rounding_adjustment`, contradicting the live constraint (`SPEC:209-220,365-387`; `PosCoreReceiptProjection.php:417-430`). **Required fix:** state the current aggregate equation exactly as `subtotal + tax_amount - discount_amount + COALESCE(cash_rounding_adjustment, 0) == total` (or algebraically equivalent), keep VAT-breakdown sums, and include rounded and legacy-null fixtures. Preserve the ban on line arithmetic.

6. **S-4/S-5 have no exact safe response schema.** “Use a `ReceiptResource`” leaves a builder to decide which raw company, user, payment, product, and fiscal fields survive; nested refund receipts can leak `canonical_bytes` even if the root is stripped (`ReceiptController.php:475-508`; `Receipt.php:194-229`). **Required fix:** enumerate the complete list/detail/line/payment/VAT/lineage wire schemas, use allowlists at every nesting level, state that `canonical_bytes` is recursively forbidden, and test the entire JSON tree (for example, a recursive key search), not only the root.

7. **S-9 omits mandatory generated-permission work and creates misleading POS navigation.** The generator is CI-enforced (`scripts/preflight.sh:136-161`), and the POS sidebar parent plus existing children use the broad `pos` alias (`Sidebar.tsx:227-243`). Granting accountant `pos.view_receipts` makes those entries pass the OR alias even when their routes require manage/operate permissions (`routes/index.tsx:2870-2939`); voucher routes also use `moduleKey="pos"` (`routes/index.tsx:3113-3132`). **Required fix:** add `permissions:export-frontend-map` and the generated map to S-9/wave 1. Audit the POS group to exact least-privilege identity keys so accountant sees only intended receipt/report links; add sidebar↔route permission tests for accountant and cashier.

8. **A-1 is role-correct but permission-model-incomplete.** The page hosts three separately gated capabilities but the proposed route gate names only reprint-log permission (`Compliance routes.php:60-71`; `ComplianceExportPage.tsx:8-20`; `RequirePermission.tsx:55-63`). **Required fix:** either (a) route-gate with `permissions={[export_jet, verify_chains, view_reprint_log]}` using any-of semantics and gate each panel individually, or (b) explicitly declare these permissions an indivisible bundle and test that invariant. Also state the navigation entry that makes the page discoverable; direct-URL acceptance alone does not satisfy user story U-6.

9. **S-7’s endpoint contract is underspecified.** It lacks route placement, request validation, location-scope semantics, inactive/archived terminal policy, cashier ordering/dedup semantics, and a decision on whether cashiers are snapshot names or current users (`SPEC:291-304`). **Required fix:** freeze the route before `/{id}`, validated params, response envelope, allowed-location intersection, terminal lifecycle inclusion rule, deterministic ordering, cashier source, and empty-scope behavior. Extend BT-8 beyond cross-company to restricted same-company locations.

10. **All new receipt filters lack a validation/time-boundary contract.** Current code compares raw request strings and allows unbounded `per_page` (`ReceiptController.php:71-109`); `posted_at` is a timezone-less DB timestamp populated from device event time (`create_pos_receipts_table.php:47-53`; `PosCoreReceiptProjection.php:365-380`), while the frontend “today” value comes from browser local time (`OwnerDashboardPage.tsx:30-45`). **Required fix:** specify a FormRequest or equivalent validation for UUID arrays, enum filters, booleans, date ordering, and bounded pagination; define which timezone converts calendar dates into inclusive/exclusive timestamp bounds and test receipts around midnight/DST boundaries applicable to configured tenants.

11. **Wave sequencing is impossible as written.** Wave 1 cannot heal `/pos/receipts/:id` links without the detail route/component assigned to wave 2 (`SPEC:405-422`). CL-4 and CL-2 have no wave owner (`SPEC:350-361`). **Required fix:** either move the minimal read-only detail route/page plus S-4/S-5 to wave 1, or move CL-3/CL-4 and the “both links healed” exit criterion to wave 2. Assign every cleanup item explicitly; CL-4 must travel with the route regression.

12. **OI-4 and OI-5 are not valid open items.** OI-5 is resolved by `RequirePermission` source (`RequirePermission.tsx:50-63`). OI-4’s main training authoring path is already a tracked chain-context defect: it omits `chain_context`, defaults to operational, and is rejected for `training_flag=true` (`receiptService.ts:489-505`; `FiscalEventEngine.ts:565-574,810-824`; ownership `FINDINGS-other-problems-2026-08-11.md:58-62`). **Required fix:** close OI-5 as verified. Replace OI-4 with a cross-reference to ES-19/A1 and state that this lane does not fix it; after A0/A1, re-evaluate what the chain panel counts and captions.

13. **The reprint tests stop at frontend request counting.** That guards render/cancel behavior but does not pin the fiscal consequence that motivates the design (`SPEC:389-401`; live audit calls `ReceiptController.php:604-612,637-645`). **Required fix:** add backend feature tests for both PDF endpoints asserting exactly one new print-audit row, incremented `copy_number`, correct method/user/receipt, and no row on unauthorized/not-found requests. Keep FT-4/FT-5 for zero-fetch-on-render and confirmation behavior.

## 4. Implementability assessment

**Not dispatchable without invention.** The list shell, live detail/PDF endpoints, S-1/S-2/S-3/S-6 feasibility, permissions primitives, surviving translations, and reprint interaction rules are concrete enough to build. The blocked areas are load-bearing:

- A backend implementer has no specified query that returns a correctly paginated REFUND+VOID register, nor response fields for the real refund reason, destination, or original receipt number.
- A security-conscious implementer must invent same-company location authorization rules for five receipt access paths and the chain terminal selector.
