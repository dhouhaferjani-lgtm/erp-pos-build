## Critical findings

### R4-C-1 — The final ACCEPT register cannot be in either exact candidate A or the permitted post-promotion commit, so P3's P2 proof is unsatisfiable

**Evidence:** The bridge creates the verdict file only while running the review: it makes the output directory, invokes the reviewer, copies its result to `--out`, and only then parses ACCEPT (`scripts/adversarial-review.sh:47-48,82-100`). The harness first commits the milestone and then invokes that bridge; only after the verdict does it record the verdict path/result and mark the milestone passed (`docs/handoff/SELF-REVIEW-HARNESS.md:23-46`). The enforcement brief likewise sends every register to `docs/handoff/reviews/enforcement-<p>/...` (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:75-85`). But the promotion contract permits no commit after final ACCEPT before merging A, and its post-promotion admin commit may touch only `docs/handoff/progress/*.progress.yaml` and `docs/handoff/LEDGER.md` (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:380-386`; `LEDGER.md:56`). `docs/handoff/reviews/**` is outside that allowlist. P3 M0 nevertheless requires P2 M4's `verdict:` path to resolve at the base to a parseable ACCEPT artifact (`enforcement-p3.progress.yaml:23-30,73-76,92`; `CODEX-DISPATCH-enforcement-guards-2026-08-12.md:65,335`).

**Failure scenario:** P2 M4 commits candidate A, then the bridge writes `docs/handoff/reviews/enforcement-p2/M4-roundN.md` and returns ACCEPT. Merging exactly A cannot include a file created after A. Committing the register before merge changes A and violates the exact-head dispatch proof. The allowed post-promotion admin commit cannot add the register. P3 subsequently reads the landed P2 YAML: either `verdict` remains null, or it points to an artifact absent from the base. P3 M0 must block forever even though P2 was genuinely reviewed.

**Required repair:** define a non-self-referential landing path for final review evidence. The smallest repair is to extend the post-promotion administrative allowlist to the exact final register/handback paths, bind their contents explicitly to accepted implementation SHA A, and require the admin commit to contain no production/workflow changes. Then state that top-level completion, final milestone status/commit/verdict, the final register, receipts, and announcement acknowledgement are all recorded together after promotion. Alternatively store a durable owner attestation outside git and make P3 verify that object. Do not require evidence generated after A to be contained in A.

### R4-C-2 — “Merge exactly A” has no base-freshness or restart rule and is impossible for the second of the expressly parallel P1/P2 promotions

**Evidence:** The package model says the gates are independent (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:59`) and expressly allows P1 and P2 to run in parallel (`:65`). Each package pins its branch base at dispatch (`enforcement-p1.progress.yaml:10-17,33`; `enforcement-p2.progress.yaml:10-19`). The promotion sequence then requires the parent to merge exactly accepted/dispatched A such that promotion SHA == A, followed by a new admin commit on dev (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:380-386`; `LEDGER.md:56`). It has no pre-merge assertion that current dev is an ancestor of A and no invalidation/re-gate procedure for a stale A, a red remote dispatch, or any other event requiring A to change.

**Failure scenario:** P1 and P2 branch from dev commit B and both reach final ACCEPT, as the schedule allows. P1 A1 is fast-forwarded and its required admin commit advances dev again. P2 A2 still descends from B, not the new dev tip. A normal merge creates merge commit M, violating `promotion SHA == accepted SHA == dispatched head`; force-moving dev to A2 would discard P1; rebasing P2 creates A2′, invalidating the M4 verdict, final announcement, variable bootstrap, and dispatch against A2. The same dead end occurs if the pre-promotion dispatch discovers a workflow defect: r8 blocks promotion but defines no legal route back into the harness.

**Required repair:** add an explicit promotion freshness/restart protocol. Immediately before step 2, require `git merge-base --is-ancestor <current-dev-tip> A`; only a fast-forward to A is legal. If false—or if remote dispatch is red—return the package to an in-progress final milestone, rebase/fix onto the current dev tip, rerun all invalidated local evidence and the whole-package bridge gate, produce a new A, resend P2's final announcement for that A, reset any stale promotion state, and restart all five steps. Serialize the two promotion critical sections even if implementation runs in parallel.

## High findings

### R4-H-1 — Repository variables are not the admin-only authority the brief claims

**Evidence:** r8 repeatedly characterizes the protected values as owner/admin-authenticated and “settable only by a repo admin” (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:162-165,400`; `enforcement-p1.progress.yaml:37-51`; `enforcement-p2.progress.yaml:28-39`). GitHub's official configuration-variable documentation states that an organization repository's secrets or variables can be created by a user with repository **write** access, not only an administrator: [Store information in variables — Creating configuration variables for a repository](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables#creating-configuration-variables-for-a-repository). The official REST contract likewise authorizes repository-variable writes through the `Variables` repository permission: [REST API endpoints for GitHub Actions variables](https://docs.github.com/en/rest/actions/variables#create-a-repository-variable). Repository variables are automatically available through the `vars` context on the workflow's PR, push, and dispatch events, so event readability itself is not the defect; the authority boundary is.

**Failure scenario:** a collaborator with repository write access authors a new violation and matching baseline key, changes the candidate YAML mirror, and updates the repository variable to the candidate's new blob. Variable and mirror agree, the protected and working sets agree, and the matched-growth change is green. The brief's no-push/no-admin restriction on the Codex executor does not establish that all candidate authors or write collaborators lack this configuration permission.

**Required repair:** either narrow and record the trust model honestly—identify every principal with repository-variable write authority and obtain an owner assertion that none can author these candidates—or move the ceiling to an actually owner/admin-controlled mechanism, such as a protected environment/organization authority with repository-level shadowing prevented. Add a pre-promotion check of the authority's provenance/permissions, not only its value. Remove every false “repo admin only” claim.

### R4-H-2 — A raw protected blob has no durable remote reachability after the “throwaway” ref is removed

**Evidence:** The reviewed base is explicitly an unpushed local-dev state (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:53`). The checker fails closed if the variable-named blob is unfetchable and proposes full-depth checkout or an explicit fetch (`:162`). Promotion pushes A only to a “throwaway remote ref,” then merges it only to local dev (`:383-385`; `LEDGER.md:56`). No rule retains that ref, tags the protected commit, pushes the landed commit to a permanent remote branch, or defines when the throwaway ref may be deleted.

**Failure scenario:** the owner deletes the throwaway ref after its green dispatch—the ordinary meaning of throwaway—while local dev remains unpushed. A concurrent or later PR run checks out another remote ref. The variable still names A's baseline blob, but no advertised remote ref reaches A, so full-depth checkout cannot obtain it and fetching a bare blob hash is not a durable ref contract. The guard fails closed on every such event until someone recreates reachability.

**Required repair:** pin each protected baseline through a durable owner-controlled remote commit/tag/ref and retain it until a permanent remote branch reaches the protected blob. Store that commit/ref alongside the blob hash, fetch the commit/ref explicitly, verify the resulting blob hash, and define safe deletion/re-pin ordering. A raw blob hash plus an unspecified throwaway-ref lifetime is not an availability contract.

### R4-H-3 — A seed-changing fix round cannot update the seed commit SHA and its mirror truthfully in the single fix commit r8 mandates

**Evidence:** Both progress schemas define `*_baseline_seed_commit` as the dedicated commit that generated the baseline and define the protected blob as `git rev-parse <seed_commit>:<baseline-path>` (`enforcement-p1.progress.yaml:42-53`; `enforcement-p2.progress.yaml:33-41`). Initial order correctly uses a later metadata commit. But both then say a fix round that regenerates the seed recomputes the blob and updates the mirrors “in the fix commit” before re-review (`enforcement-p1.progress.yaml:45-48,119`; `enforcement-p2.progress.yaml:34-37,108`; `CODEX-DISPATCH-enforcement-guards-2026-08-12.md:161,256`). The harness's fix path is one scoped fix commit followed by re-review (`docs/handoff/SELF-REVIEW-HARNESS.md:43-47`).

**Failure scenario:** a reviewer finds that the seed baseline omitted a scanner case. If the executor regenerates it in fix commit F and sets `*_baseline_seed_commit: F`, F's SHA cannot be embedded in F because changing the field changes F. If the field remains at commit 1, the regenerated working baseline is no longer the baseline at that recorded seed commit; if only the protected blob changes, the declared `git rev-parse <seed_commit>:<path>` relationship is false. The next review sees internally inconsistent provenance.

**Required repair:** require every seed-changing fix round to recreate the same two-step topology: a seed-revision commit containing the regenerated baseline, followed by a distinct metadata commit recording that earlier commit and its blob, then re-review both. Because the branch is unpushed, rewriting the original two commits is also acceptable if explicitly required; a single self-identifying fix commit is not.

### R4-H-4 — The designed unset-variable bootstrap makes the wave's own required green commands fail before first promotion

**Evidence:** P1 says the variable does not exist until promotion and the checker must fail closed when it is unset (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:162-163`). Yet P1 acceptance starts with a green guard command before any environment initialization (`:183-192`); the only local export instruction appears later inside tamper case 5 (`:194-199`). P2 gives the same unset/fail-closed contract (`:256`) but its required green `node tools/audit-i18n-completeness.mjs` and whole-package evidence contain no export at all (`:271-281`; `enforcement-p2.progress.yaml:131-138`). P1 M3 likewise reruns the full accumulated evidence without specifying the local authority setup (`enforcement-p1.progress.yaml:126-133`). Repository `vars` do not populate a local desktop shell.

**Failure scenario:** on first implementation, neither repository variable exists and the executor is forbidden to create it. Following the exact P1 or P2 acceptance block causes the anti-growth checker to fail closed during the green run, so M2/M3 or M1/M4 cannot reach ACCEPT. If the executor silently treats unset as bootstrap mode to get green, the mandated unset-variable negative proof becomes false and recreates an unprotected bypass.

**Required repair:** add an explicit local/review setup before every normal green invocation and whole-package gate: derive the reviewed seed blob, verify it equals the YAML mirror, and export it under the same environment name. Run the unset negative case in an isolated command/subshell, then restore the exported value. Separately require CI YAML to map `${{ vars.DPA_BASELINE_PROTECTED_BLOB }}` / `${{ vars.I18N_BASELINE_PROTECTED_BLOB }}` into the checker environment on every actual workflow event.

### R4-H-5 — P3's claimed “P1 accepted and landed” gate checks only an arbitrary ancestor plus a candidate-editable top-level status

**Evidence:** The brief calls P1 landing a hard P3 dispatch prerequisite (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:65`). Operatively, P3 checks only that parent-supplied `p1_landed_sha` is an ancestor of `base_sha` and that `enforcement-p1.progress.yaml` reads top-level `status: complete` (`enforcement-p3.progress.yaml:20-22,46-49,70-72,92`). It does not require P1 M3 `status: passed`, a parseable ACCEPT register, M3's recorded commit, or M3.commit → `p1_landed_sha` → base ancestry. The same P3 M0 correctly demands all of those stronger whole-package facts for P2 (`enforcement-p3.progress.yaml:23-30,73-76,92`) and country defaults (`:31-44,92`).

**Failure scenario:** a base contains a progress snapshot with P1 top-level `status: complete`, while `p1_landed_sha` is set to any old ancestor. The written M0 check passes even if P1 M3 was rejected or the accepted P1 implementation commit was never merged. P3 then consumes a missing or unreviewed P1 census—the same partial-snapshot forgery class the brief explicitly rejects for P2 and country defaults.

**Required repair:** harden P1 symmetrically: require P1 top-level complete, M3 passed, a parseable ACCEPT artifact, a recorded M3 commit, and M3.commit → `p1_landed_sha` → `base_sha` ancestry (or equality at the landed hop if exact-A promotion remains the rule). Coordinate this with R4-C-1 so the final artifact can actually land.
