**Verdict: NEEDS-MAJOR-REVISION**

**BLOCKER: OQ-1 premise is wrong for the live POS path.**  
Composite sales do not currently double-deplete ingredients across Path A and Path B. Path A, `ReceiptCreationService`, does explode and deplete composite leaves once: composite receipt lines store `product_id = null` / `composite_item_id = ...`, then call `deductCompositeItemStock()` and leaf `decrementStock()` ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:332), [line 685](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:685), [line 1230](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:1230)). But Path B does not explode composites at all. It loops canonical `lineItems`, reads only `productId`, and calls product `decrementStock()` ([PosCoreReceiptProjection.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Projections/PosCoreReceiptProjection.php:873)). The canonical line DTO has no composite identity, only `productId` plus variant fields ([LineItemDTO.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Fiscal/Domain/DTOs/Canonical/LineItemDTO.php:39)). So the spec’s “projection records composite ingredients” design has no data to do so.

**BLOCKER: the spec targets a retired checkout path.**  
`POST /pos/receipts` returns 410 for new-sale authoring ([routes.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/routes.php:127)), and `ReceiptFinalizationService` says new-sale `SALE_RECEIPT` authoring is never invoked server-side; device fiscal events are authoritative ([ReceiptFinalizationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptFinalizationService.php:59)). The live path is `/pos/sync/fiscal-events` ([FiscalEventIngestionController.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Fiscal/Presentation/Controllers/FiscalEventIngestionController.php:17)). A “server checkout pre-commit gate” in `ReceiptCreationService` will not protect live Tauri sales.

**BLOCKER: “no device schema change in v1” is incompatible with composite depletion on sync.**  
The device signs `product_id: item.product.id` in canonical line items ([SaleReceiptPayload.ts](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/pos/src/lib/fiscal/payloads/SaleReceiptPayload.ts:317)). The server validator rejects extra line-item keys outside the exact v1/v2 sets; there is no `composite_item_id` key ([FiscalPayloadConstraintValidator.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Fiscal/Application/Services/FiscalPayloadConstraintValidator.php:1721), [line 1745](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Fiscal/Application/Services/FiscalPayloadConstraintValidator.php:1745)). Without a new canonical event version or another immutable recipe snapshot, the server cannot know whether a `product_id` was a composite and cannot historically explode its recipe.

**HIGH: Inventory-OFF gate is underspecified and time-unsafe.**  
Today missing `stock_levels` rows are graceful: `decrementStock()` returns `null` ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:907)), so a CompositeItems-only tenant with no stock rows sells without movement. But if a tenant had Inventory, has rows, then disables Inventory, current code would still decrement any existing rows. Adding a current `hasModule('Inventory')` gate fixes future sales, but the spec does not define event-time vs projection-time module state. The resolver is tenant-level cached for 24h ([DefaultModuleActivationResolver.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Fiscal/Application/Services/DefaultModuleActivationResolver.php:24)), and projection jobs may run after a module toggle. You need a module-state snapshot or explicit “current state wins” data-loss decision.

**HIGH: batch/FEFO claim is false for composites.**  
Direct product sales allocate batches only after `decrementStock()` returns a movement ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:673)). Composite leaf deductions call `decrementStock()` but discard the returned movement and never call `allocateBatches()` ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:1230)). FEFO itself hard-blocks strict shortfall ([FEFOInventoryService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/BatchExpiry/Domain/Services/FEFOInventoryService.php:229)), but composites do not reach that path today.

**HIGH: offline Option A silently downgrades Block.**  
For Menu tenants, the POS stock gate returns PASS before reading policy or stock ([stockGate.ts](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/pos/src/lib/stock/stockGate.ts:53)). `pullLocationStock()` also skips Menu tenants entirely ([syncService.ts](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/pos/src/lib/sync/syncService.ts:867)). So a Block tenant can sell composites offline with no hard control. If this is accepted, it needs an explicit owner decision, risk banner, and likely permission/audit semantics; otherwise it is a correctness/fraud hole.

**HIGH: lock ordering/deadlock risk is real.**  
Current composite depletion locks leaf stock rows in receipt/recipe order ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:1209), [line 905](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:905)). The repo has a canonical sorted per-product lock pattern via `ProductCostLock` ([ProductCostLock.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Inventory/Domain/Services/ProductCostLock.php:13)) and WAC comments mandate stock-level-before-product ordering ([WeightedAverageCostService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:87)). The spec should require flattening all leaf demands, sorting by product/variant/location, then locking/depleting in that order.

**MEDIUM: T6 cart math is achievable, but not as written.**  
Current code can catch combined shared-ingredient demand because it mutates stock line-by-line in one transaction, and later checks see reduced quantity. But that is not a pre-decrement availability pass and gives no clean warning payload. A real “running map” requires flattening the whole cart before locking/writing, including simple product lines that share an ingredient product.

**HIGH: `CompositeItemAvailabilityService` reuse is much larger than stated.**  
Current signature is only `checkAvailability(CompositeItem $item, string $locationId)` ([CompositeItemAvailabilityService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Catalog/Application/Services/CompositeItemAvailabilityService.php:26)). It has no tenant/company scoping, no cart-consumption injection, no lock mode, no variant handling, no batch availability, and uses `stockLevel->quantity` rather than `getAvailableQuantity()` / reserved-aware availability ([CompositeItemAvailabilityService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Catalog/Application/Services/CompositeItemAvailabilityService.php:55)). This is not a light refactor.

**HIGH: refunds/voids miss composite ingredient re-credit.**  
Void and return stock restoration skip lines where `product_id === null` ([ReceiptVoidService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptVoidService.php:92), [ReceiptReturnService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptReturnService.php:396)). Legacy composite sales create exactly those null-product lines, so ingredients depleted on sale are not restored on void/return.

**MEDIUM: recipe history and variant ingredients are missing.**  
If projection later explodes current `activeRecipe`, a recipe edit between sale and sync changes historical stock effects. Also `RecipeLine` has `component_variant_id` ([RecipeLine.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/Catalog/Domain/Entities/RecipeLine.php:20)), but composite depletion ignores it and always decrements product-level stock ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:1234)).

**LOW: performance is undercalled.**  
`deductCompositeItemStock()` reloads each composite recursively ([ReceiptCreationService.php](/Users/houssamr/Projects/syneriva/apps/erp.vmgate/apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:1203)), and the availability service does per-leaf stock queries. A busy F&B cart needs flattened, batched queries.

**Conclusion**  
The spec must be rewritten around the live device-authored fiscal event flow, add a canonical way to carry composite/recipe identity or recipe snapshots, define module-state timing, implement exactly-once stock ownership, and cover returns/voids and FEFO before implementation.

Confidence: 90%.
