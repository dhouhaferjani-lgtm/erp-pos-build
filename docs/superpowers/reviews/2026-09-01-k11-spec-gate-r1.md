## §0 — Mechanism reproduced from code (all three questions answered)

**(a) Why the census says `in_file: 0`.** `DuplicateCensusService::census()` (`DuplicateCensusService.php:34-41`) runs BEFORE execution, against an empty catalogue, so every row resolves to "no match" (`ProductResolver.php:137`) → bucket `New` (`DuplicateCensusService.php:287`). The in-file dimension is a **single scalar placement key** (`DuplicateCensusService.php:321-346`); when there is no matched product the identity is built by the ladder at `:337-342`:

```php
$identity = $sku !== null
    ? 'sku:'.$sku
    : ($barcode !== null ? 'barcode:'.$barcode : 'name:'.$name);
```

859 **distinct supplied SKUs** ⇒ 859 distinct keys ⇒ `seenPlacementKeys` (`:74-80`) never collides ⇒ `in_file = 0`, `new = 856`. Note the precise scope of the blindness the brief overstates: **the census DOES model in-file barcode collisions when the SKU cell is blank** (`:342`); it is blind **only** when a distinct SKU is supplied alongside a colliding barcode. That distinction is load-bearing for the fix.

**(b) Why execution matches a product created moments earlier in the same run.** Rows are applied one at a time (`ImportService::processPendingRow` → `duplicateCensus->decide()`, `ImportService.php:512-514`), and `decide()` re-resolves against the **live** table (`DuplicateCensusService.php:134`, `:230-241`). `ProductResolver::resolveInput()` tries the supplied SKU first (`ProductResolver.php:72-85`), misses, then falls through to barcode (`:87-108`) and returns `matchedBy = Barcode` with the earlier row's product id (`:101-107`). Bucket becomes `ExistingBarcode` (`DuplicateCensusService.php:285`).

**(c) How that becomes `duplicate_skipped` under bucket `new`.** `isExistingBucket()` counts `ExistingBarcode` as existing (`ImportService.php:603-613`); with `duplicate_policy = skip` (`ImportService.php:557-559`) the row is written `outcome = DuplicateSkipped`, `import_error = null` (`ImportService.php:560-569`). The stored preview bucket is the census's `new` — the divergence IS detected and stamped as a `preview_drift` warning (`ImportService.php:528-537`, merged in at `:563`), so the brief's "no per-row explanation" is **imprecise**: a generic drift warning exists. It is useless to the operator for two reasons, both worth fixing in this lane (see K11-S1-05, K11-S1-06).

Arithmetic checks out: 859 rows − 3 invalid (negative quantities on rows 141/160/827, per the evidence's own note) = 856 census `new`; 179 imported + 677 skipped = 856.

**Not in the evidence, found here — the same bug under the OTHER policy is worse.** `DuplicatePolicy::Override` is the **default** (`ImportService.php:558`). Under it the row is not skipped; it reaches `ProductService::upsertWithResult()`, which runs the same ladder (`ProductService.php:106-120`), finds `$existing` = the earlier row's product, and **merges the attributes onto it** (`:212-230`) — 859 catalogue rows collapse into ~180 products with last-write-wins names and prices, and the SKU column silently keeps the FIRST row's SKU. Same data loss, no `duplicate_skipped` counter to notice it by.

## §1 — Attack on the brief

### (1) Is "distinct supplied SKU + colliding barcode = warn, import under own SKU" implementable?

**Schema:** there is **no unique index on `products.barcode` at any scope** — the column is a plain indexed `varchar(100)` (`database/migrations/tenant/2025_11_30_052910_create_products_table.php:27,39`), and `ProductService.php:126-129` says so in a load-bearing comment left by the G-3a gate. `products` uniqueness is `unique(company_id, sku)` only (`database/migrations/tenant/2026_08_30_100000_enforce_company_scoped_product_skus.php:54-58`). `docs/glossary.md:36` records barcode as **optional, not a key** ("`product_variants` barcode stays tenant-wide by RUL-2"). So the brief's option (a) is **not blocked by a constraint** — it is blocked by consequences:

- **Every future import row carrying that barcode is REFUSED.** Two live products on one barcode ⇒ `ProductResolver.php:92-100` returns `BarcodeAmbiguous` ⇒ `DuplicateCensusService::throwIfResolutionFailed()` (`:312-318`) throws ⇒ row `failed`. Importing 677 colliding rows converts a one-run warning into a permanent, self-inflicted refusal for the same catalogue.
- **Scanning picks an arbitrary winner, silently.** `InventoryCountingController.php:771-773` is `Product::where('barcode', …)->where('company_id', …)->first()` — one of 97 twins, non-deterministic. Same shape at `:1205`, `CountingItemController.php:146`, `ProductController.php:266`.
- **PG-only landmine:** `product_variants` DOES carry `CREATE UNIQUE INDEX product_variants_tenant_barcode_unique … WHERE barcode IS NOT NULL AND deleted_at IS NULL` (`database/migrations/tenant/2026_06_02_100003_create_product_variants_table.php:40-41`), PG only. The import never creates variants today (no `ProductVariant::create` anywhere in `Modules/Import` or `Modules/Product`), so it does not fire now — but any later variant/label lane over those 677 twins fails on PG and passes on SQLite.

**Honest outcomes, enumerated:**

| # | outcome | result on the real file | cost |
|---|---|---|---|
| **(a)** import under own SKU, **keep** the colliding barcode | 856 imported, 677 warnings | permanent `barcode_ambiguous` refusals + arbitrary scan winner (above). **Do not choose.** |
| **(b)** import under own SKU, **drop the barcode** (write `null`) + row warning `barcode_conflict` (detail: barcode + winning SKU/row) | 856 imported, 677 warnings, barcode→product stays 1:1 | the operator loses the barcode cell for 677 rows and must re-import that column after fixing the file. Reversible. Matches the existing "ignore the cell, warn" vocabulary (`ImportWarningCode::ExpiryIgnoredNotBatchTracked`, `LocationCodeUnknown`). |
| **(c)** refuse the row, coded `barcode_conflict` error | 179 imported, 677 **failed** | honest, closest to the Odoo/ERPNext framing, but the operator's first import of a 859-row catalogue still yields 179 products. |

**Recommendation: (b) as the default, with (c) reachable only if the owner prefers refusal.** (b) preserves the catalogue, keeps the barcode key 1:1, and — decisive — the observed collisions are **Excel float corruption of the barcode column** (evidence, data note), i.e. the values are not barcodes at all. Dropping a corrupted cell and warning is the correct semantics; refusing 677 rows over a spreadsheet formatting artefact is not. **OWNER RULING OR-1 required** ((b) vs (c)) — it is a data-loss policy choice either way.

**Precedence tests are only safe if the rule is implemented at the IMPORT layer, not in the resolver.** The brief's sentence "a *contradictory* barcode match downgrades to a warning instead of winning over a distinct SKU" describes a change to the shared ladder, which would turn `ProductIdentityResolutionTest.php:32-56` (`test_supplied_sku_miss_falls_to_barcode_but_never_to_name`, asserts `matchedBy === Barcode`) RED and would change behaviour for **every** `ProductResolverInterface` consumer including the non-import API path (`ProductService.php:36,106`). The resolver already exposes everything needed: `ProductIdentityResolutionData` carries `matchedBy` and `sku` (= the MATCHED product's SKU, `ProductIdentityResolutionData.php:14-16`), so the import layer can derive the conflict as `matchedBy === Barcode && suppliedSku !== null && suppliedSku !== $resolution->sku` **without touching the ladder**. Also note `DuplicateCensusTest.php:217-270` case 2 (barcode-only row, blank SKU → `ExistingBarcode` → `DuplicateSkipped`) must stay green: the new rule must be gated on a **non-blank supplied SKU**.

### (2) Census extension shape, and the collision/merge-order list

The brief says "model in-file BARCODE collisions the same way it models name/SKU". Implemented literally — i.e. folding barcode into `placementKey` (`DuplicateCensusService.php:321-346`) — two rows with **distinct SKUs** and a shared barcode become one placement group, `decide()` (`:144-178`) elects the last row as winner and stamps the other 677 `DuplicateLoser` (`ImportService.php:539-554`). **Same 179-row outcome, moved from execution to preview.** Barcode collision is a **second key space** (a warning dimension), not another value of the placement key. The brief must say so explicitly.

Concrete surface facts the brief must carry:
- Bucket counts are a **hand-rolled FE union** at `apps/web/src/features/import/types.ts:78` that duplicates the **generated** `packages/shared/types/generated.d.ts:1054` (while `:80` correctly aliases the generated `ImportErrorCode`) — a one-surface-per-concept violation the lane inherits.
- The preview panel hardcodes the six buckets at `ImportWizardPage.tsx:1030` inside a `sm:grid-cols-6` grid (`:1028`), and the headline sentence sums exactly three buckets at `:1021-1026`. A 7th bucket touches all three.
- **The warning contract is SIX files, not five:** `ImportWarningCode.php` + `apps/web/src/features/import/warningCodes.ts:29` (`satisfies Record<ImportWarningCode, true>` — a missing key fails `pnpm typecheck`) + `locales/{en,fr,ar}/import.json` (parity pinned by `apps/web/src/features/import/__tests__/ImportWarningLocales.test.ts:9-21`) + the **committed** `packages/shared/types/generated.d.ts:1060`, which requires `php artisan typescript:transform`.
- If the lane instead adds an **error** code, that is a *different* contract: `ImportErrorCode.php:32-49` is an exhaustive `match` with no `default` (row-level vs job-level must be declared), `generated.d.ts:1056` regenerates, and there is **no locale-parity test for error codes**. The brief conflates the two contracts; it must pick one.

**Merge order — the brief's list is stale and incomplete.** `feat/g2-sku-generation`, `feat/g4-duplicate-policy-merge`, `feat/g5-opening-correction-fence` are **already merged into `dev`** (verified). The real collisions are two lanes whose work is **uncommitted in worktrees**:
- `.worktrees/k89-units` (K-8/K-9) — modified `Import/Services/ImportService.php`, `Import/Presentation/Controllers/ImportController.php`, `web/.../ImportWizardPage.tsx`, `web/.../types.ts`, `ImportWizardPage.duplicates.test.tsx`.
- `.worktrees/k67-import` (K-6/K-7) — modified `Import/Domain/Enums/ImportWarningCode.php` (**adds 5 enrichment cases**), `ImportController.php`, `ProcessImportJob.php`, `ImportServiceProvider.php`.

**Required merge-order rule for the brief:** K-11 branches from `dev` **after** K-8/K-9 and K-6/K-7 land, or it rebases onto them before its final gate; the warning/bucket union and any `feature-lane-manifest.json` ceiling are recomputed from the **then-current** files, never from `dev` at dispatch time.

### (3) Does part of the fix belong in G-4's `CoalescingAttributeMerger` world? — **Yes, and the brief misses the case that makes the bug permanent.**

`ProductService::upsertWithResult()` writes `'barcode' => $barcode` into `$attributes` **unconditionally** (`ProductService.php:145`), on both branches. On the **update** branch the value survives the merge whenever the operator supplied the cell, because `barcode` falls to the `default => [$field]` arm of `CoalescingAttributeMerger::governingCellWasProvided()` (`CoalescingAttributeMerger.php:56`). Consequences the brief does not address:

- **Re-run of the same file** (the brief's own idempotency requirement): pass 2, row 2 now matches **by its own SKU** (`ExistingSku`, `ProductResolver.php:72-85`), so no conflict is detected by any identity check — and under the default `Override` policy the upsert **writes barcode B onto row 2's product**. Two live products on barcode B ⇒ every subsequent run refuses both with `barcode_ambiguous`. **A K-11 that only guards the identity path leaves the catalogue one re-import away from the poisoned state it was built to avoid.**
- The same hole is reachable today from the API: `UpdateProductRequest.php:200` and `CreateProductRequest.php:216` have **no uniqueness rule on barcode**.

So the guard must be on the **barcode WRITE**, evaluated for every product write on the import path (create AND update), implemented by removing `barcode` from BOTH `$attributes` and `$data['_provided']` before the merger runs (the merger itself needs no change). **OWNER RULING OR-2 required:** whether the same guard also lands in `ProductService` for the API path (correct, but expands the lane beyond imports) or stays import-only for now with a recorded follow-up.

**OWNER RULING OR-3 (recommend NO for this lane):** do **not** add a DB unique index on `products.barcode`. Existing tenants — including the tester's staging tenant, which after F-W1-6 holds ~180 products but any earlier `Override` run holds twins — would make the migration throw, and per the standing rule a push to `origin/dev` auto-runs `tenants:migrate` fleet-wide. If uniqueness is ever wanted it needs the G-3a treatment: a census that refuses with the collision list before dropping/adding anything (`2026_08_30_100000_enforce_company_scoped_product_skus.php:71-113`), a PG partial index + SQLite fallback, and a glossary edit at `docs/glossary.md:36`.

### (4) Test-plan sufficiency — insufficient as written

Missing, each of which is a way the lane ships green and still loses catalogues: both duplicate policies (the brief's numbers only describe `skip`; `Override` is the DEFAULT and is the more destructive path); the re-run barcode-write case above; a census↔execution **counts** parity assertion (not just per-row buckets); the workbook classification (K11-S1-06); the FE preview panel + 6-file contract; and an explanation of the unexplained **179 vs 180** (the lane must reproduce the real file's shape closely enough to account for it, else the mechanism is not fully understood). Second company and PG+SQLite are correctly required already; the second-company test must assert that a colliding barcode in company A does **not** constrain company B (`ProductResolver.php:152-153` scopes by company — assert the data, not a status code).

### (5) The benchmark note

`Odoo`/`ERPNext` behaviour **cannot be verified from this repo** — treat it as an unverified external claim and do not let it carry the decision. The half that IS verifiable is ours, and it contradicts the note's implicit conclusion: our `products.barcode` is deliberately non-unique at every scope (`ProductService.php:126-129`, `2025_11_30_052910_create_products_table.php:39`) and the glossary says so (`docs/glossary.md:36`). A benchmark table per `docs/conventions/10-BENCHMARK-FIRST-SPECS.md` (guarantee · AutoERP today `path:line` · decision) is missing and is a round-0 blocker for a user-facing flow.
