## New risks introduced by v2

### N1 — BLOCKER — green-main image push and digest-pinned release commit form a bootstrap cycle

The workflow may push only after successful CI on `main` (`design:1262`), while the digest-pinned production manifest is required in Phase 0.8c before the single dev→main promotion at 0.9 (`design:1273-1278,1475-1479`). The production digest is a function of the release commit/build, so it is not available for inclusion in that same first release commit. If a post-merge workflow commits the discovered digest, that creates a new commit which itself requires CI/build and a new digest. No bootstrap exception, two-commit release protocol, external release-lock file, or “manifest digest update does not rebuild images” path is specified. Current repository state confirms there is no pre-existing production workflow or manifest to break the cycle: `.github/workflows/ci.yml:921-950` only builds/uploads the web artifact, and the three production paths are absent.

Required closure: define an acyclic two-stage bootstrap/release protocol. For example, build candidate images from an owner-approved PR SHA, record immutable digests in a separate environment/release manifest that does not alter the image input, run the final approval/verification against those exact digests, and promote that manifest without recursively rebuilding different images. Whatever mechanism is chosen must explicitly cover the first-ever promotion.

### N2 — BLOCKER — `MANIFEST.json` can say complete before both offsite legs succeed

The normative prose says `result=complete` is written last, after both uploads (`design:621`). The outline calls `write_manifest` at step 6, then uploads to Object Storage and restic at steps 7 and 8 (`design:674-683`). If Object Storage succeeds and restic fails, the Object Storage copy can contain a manifest that is machine-readable as complete even though the documented RPO condition “both offsite uploads succeeded” is false (`design:497-500`). This defeats restore-candidate selection and the dead-man semantics.

Required closure: write/upload an incomplete manifest first if desired, but publish/atomically promote the **complete marker only after both legs acknowledge durable success**. A restore candidate must prove completion of each named leg, not rely on one pre-upload boolean.

### N3 — BLOCKER — the new hourly media leg conflicts with its credential and cannot perform its stated verification

The new L4a command is `rclone sync ... --backup-dir` (`design:671-672`), while the same host-side WORM credential is explicitly denied `DeleteObject` and `DeleteObjectVersion` (`design:727-733`). A sync must reconcile destination deletions, and `--backup-dir` must move/replace prior destination objects; that is not compatible with a strict write-without-delete destination identity once media is deleted or replaced. Separately, DR-3 asks for sample checksums “against the manifest” (`design:950`) but the manifest records only media object/byte counts (`design:615`). The primary media RPO/restore leg therefore is not executable as written.

Required closure: choose an append-only media replication layout compatible with the write-only credential (for example immutable versioned object keys plus a signed inventory), or use a distinct constrained media credential and threat model. Record per-object key/version/checksum inventory sufficient for DR verification, then test replace/delete cases as well as upload/restore.

### N4 — REQUIRED — digest pinning has no operator-grade update or rollback procedure

v2 says keep the last N digests and a `last-known-good` (`design:1268`), points Dokploy apps at digests (`design:1266,1554`), and says a panel-outage hotfix is “pull the new digest and `docker compose up -d <service>`” (`design:1285`). It does not define: how N is chosen; how five related digests are promoted as one atomic release set; where the previous set is recorded; how the checked-in compose and five Dokploy app references are kept synchronized; how schema compatibility is checked before rollback; or the exact rollback commands and post-rollback V-suite. For one operator, digest pinning without this rotation procedure converts supply-chain safety into manual configuration drift.

Required closure: add a numbered release-set rotation/rollback runbook with an immutable release-set ID, old/new digest table, database rollback compatibility decision, ordered service rollout, health gates, exact rollback commands, manifest/Dokploy reconciliation, and evidence retention.

### N5 — REQUIRED — late v2 sections retain factually stale instructions that contradict the governing sections

These are operationally relevant, not cosmetic:

- §9.3 says backups enumerate `pg_database` every run (`design:1613-1616`), contradicting the central-dump-authoritative rule (`design:584-592`).
- R-11 says panel loss stops deploys (`design:1659`), contradicting the claimed panel-independent hotfix path (`design:1285`) and DR-4 (`design:925`).
- R-12 still justifies host build queues with the 64 GB production box (`design:1660`), despite production having no git provider and no host builds (`design:1266`).
- Appendix A says DR-3 has a 4-hour RTO (`design:1798`), contradicting the committed ≤8 h / 4 h target distinction (`design:510-529`).
- Appendix B still lists GHCR as €0/free and computes the headline total from it (`design:1814-1815`) before withdrawing the same claim (`design:1821-1826`).
- The service table specifies `minio/minio:latest` (`design:278`) despite the patch policy requiring production image pinning (`design:1104`).
- The E-1 inventory calls the application `AWS_*` pair “MinIO root creds” (`design:1040`), contradicting the bucket-scoped application identity (`design:400-406`).

Required closure: make one pass over §§9-10 and Appendices A-E against the governing rulings, then add a consistency check for the high-risk duplicated facts (RTO, enumeration source, image references, credential identity, and cost status).

### N6 — REQUIRED — Appendix D's “acceptance threshold” column contains non-threshold placeholders

H-5, H-10, and H-13 were sampled as requested; all have an owner and method, but their threshold cells are respectively circular or merely say what the result will feed (`design:1917,1920,1925,1928`). H-6, H-8, H-9, and H-15 likewise say “recorded,” “feeds…,” or equivalent (`design:1921,1923-1924,1930`). This is a v2-introduced assurance mechanism that does not meet v2's own binding rule at `design:28`.

Required closure: give every hypothesis a numeric or binary acceptance/reopen rule. If a measurement is informational only, label it “measurement output” rather than “acceptance threshold” and state the downstream decision formula.

## Final verdict
