## Findings

**MEDIUM — `prohibited` does not reject present-but-empty cross-vertical metadata.**  
`CreateProductRequest` and `UpdateProductRequest` use `['prohibited']` for disallowed `parapharmacy_metadata` / `automotive_metadata` ([CreateProductRequest.php:102](apps/api/app/Modules/Product/Presentation/Requests/CreateProductRequest.php:102), [CreateProductRequest.php:125](apps/api/app/Modules/Product/Presentation/Requests/CreateProductRequest.php:125), [UpdateProductRequest.php:102](apps/api/app/Modules/Product/Presentation/Requests/UpdateProductRequest.php:102), [UpdateProductRequest.php:125](apps/api/app/Modules/Product/Presentation/Requests/UpdateProductRequest.php:125)). Laravel implements `prohibited` as “not required” ([ValidatesAttributes.php:2200](apps/api/vendor/laravel/framework/src/Illuminate/Validation/Concerns/ValidatesAttributes.php:2200)), and `required` fails for `null` and empty arrays ([ValidatesAttributes.php:2117](apps/api/vendor/laravel/framework/src/Illuminate/Validation/Concerns/ValidatesAttributes.php:2117), [ValidatesAttributes.php:2121](apps/api/vendor/laravel/framework/src/Illuminate/Validation/Concerns/ValidatesAttributes.php:2121)). Result: a wrong-vertical client can send `parapharmacy_metadata: null`, `parapharmacy_metadata: []`, `automotive_metadata: null`, or `automotive_metadata: []` and avoid the promised 422. These values do not persist because the controller still checks vertical before writing ([ProductController.php:364](apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:364), [ProductController.php:370](apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:370), [ProductController.php:492](apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:492), [ProductController.php:501](apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:501)), but the stated contract is not true. Nested JSON objects are rejected; top-level literal dotted keys like `"parapharmacy_metadata.category"` pass validation but are not persisted.

**MEDIUM — frontend gates parapharmacy UI by module, backend writes by vertical, so overrides can create a self-inflicted 422 path.**  
`ProductForm` now shows parapharmacy fields whenever `hasModule('Parapharmacy')` is true ([ProductForm.tsx:93](apps/web/src/features/inventory/ProductForm.tsx:93)), and `ProductInfoModal` does the same for the tab ([ProductInfoModal.tsx:169](apps/web/src/features/pos/organisms/ProductInfoModal/ProductInfoModal.tsx:169)). Backend write access is stricter: it only allows `Vertical::Parapharmacy`, not “has Parapharmacy module” ([CreateProductRequest.php:53](apps/api/app/Modules/Product/Presentation/Requests/CreateProductRequest.php:53), [CreateProductRequest.php:54](apps/api/app/Modules/Product/Presentation/Requests/CreateProductRequest.php:54)). Today `config/verticals.php` only gives the module to the parapharmacy vertical ([verticals.php:327](apps/api/config/verticals.php:327), [verticals.php:345](apps/api/config/verticals.php:345)), but the app explicitly supports DB-first vertical module overrides ([VerticalConfigService.php:53](apps/api/app/Services/VerticalConfigService.php:53), [VerticalConfigService.php:57](apps/api/app/Services/VerticalConfigService.php:57)) and merges enabled extras into `all_enabled_modules` ([CompanyConfigService.php:65](apps/api/app/Services/CompanyConfigService.php:65)). If an admin config enables `Parapharmacy` for a non-parapharmacy vertical, the UI invites metadata input that the API rejects. Either gate the UI by `config.vertical === 'parapharmacy'` for product metadata, or make backend metadata authorization module-based too.

**LOW — docs overstate the parapharmacy frontend/backend behavior.**  
The doc says parapharmacy frontend UI “only shows them to parapharmacy tenants” ([vertical-module-gating.md:202](docs/architecture/vertical-module-gating.md:202)), but the code gates on `hasModule('Parapharmacy')`, and the new fixture explicitly models a non-parapharmacy tenant with that module enabled ([companyConfig.ts:63](apps/web/src/test/fixtures/companyConfig.ts:63), [companyConfig.ts:69](apps/web/src/test/fixtures/companyConfig.ts:69)). The doc also says only the parapharmacy vertical can reach parapharmacy master-data routes ([vertical-module-gating.md:197](docs/architecture/vertical-module-gating.md:197)), while the route actually enforces `module:Parapharmacy` ([routes.php:72](apps/api/app/Modules/Product/routes.php:72)). That is true under current static config, but not under the documented DB override model.
