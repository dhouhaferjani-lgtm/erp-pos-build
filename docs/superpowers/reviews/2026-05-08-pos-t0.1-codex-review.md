## Verdict per point

### (a) RED-before-GREEN audit — PASS

The regression test is not a tautology. On `cbbdcc31`, the cash/card/advanced-payment catch blocks in `paymentStore.ts` set `paymentStore.error` using the raw `error.message` property directly (no `instanceof` check, no fallback). When `createOfflineReceipt` rejects with `new SqliteBusyError()` (an `Error` subclass with `message = ''`), the old code set `paymentStore.error = ''`. The test assertion that `.error` contains the constructor name `"SqliteBusyError"` would have **failed** on the old code — it is a genuine RED → GREEN transition.

### (b) Cashier critical-path regression — MAJOR

**Real `Error` with non-empty message:** The new `formatCheckoutError` still returns `error.message` for this case — behaviour unchanged. ✓

**Non-`Error` string thrown:** Old code: `paymentStore.error = String(thrown)` (generic, no detail). New code: `'<i18n.checkoutFailed>: string — <slice 0-200>'`. The slice exposes up to 200 characters of the raw string to the cashier banner. If a lower-level library (SQLite, Tauri IPC) throws a plain string containing internal state (table names, SQL fragments, file paths, or anything that coincidentally contains customer data injected into a query string), those details now appear on the cashier screen. This is a **MAJOR** regression risk. The old generic i18n string was intentionally opaque. The new suffix should be dev-console only, not included in the user-visible banner.

**Tautology gap:** The regression test covers only the empty-message `Error` subclass branch. The non-`Error` string branch (the risky new behaviour) has no test coverage. The test can pass while the banner change is live.

### (c) TypeScript escape hatches — PASS

No `as any`, `as <concrete type>`, `!` non-null assertions, or `// @ts-ignore` were introduced in the diff. All added code uses `error: unknown` + `instanceof` type narrowing correctly.

### (d) Silent catch audit — MINOR

The author's explicit omissions are defensible:

- `syncService.ts` lines 1182–1185, 1228, 1234 (`/* non-critical */`) — these are cleanup paths (local state reset, SQLite log writes) where a secondary failure should not mask the primary error. The annotation is intentional.
- Catches that already call `logSyncOperation` are excluded correctly — they already emit a structured record.

**Residual gaps:** Two catches in `syncService.ts` at approximately lines 1240 and 1246 (inner retries within `pushOfflineReceipts`) remain silent and were not annotated. These are not `/* non-critical */` paths — they wrap individual receipt push attempts. If the T0.1 playbook intended "every silent catch in the sync critical path", these should have been included or explicitly annotated as out-of-scope.

### (e) Sensitive data leak in structured logs — MAJOR

None of the added `console.error` callsites directly log `cardLastFour`, PAN fields, or customer PII from the store state. However, several callsites pass the raw `error` object (not just `error.message`) to the payload:

- `paymentStore.ts`: `{ error, errorType, isError, ... }` — if the thrown object carries a `.body` or `.response` property (e.g., from an `ApiRequestError` that embedded the full HTTP response body, which could include a card number in a decline response), that propagates into the console log.
- `syncService.ts` inner catch: same pattern.

The risk is not from *direct* property references but from passing the full throwable reference. In a Tauri WebView the console is readable by the host process and captured by crash reporters. Recommendation: log `{ errorType, errorName, message, stack }` explicitly rather than spreading the raw `error` object.

### (f) Circular object danger — MINOR

Tauri's WebView (WebKit/WKWebView on macOS, WebView2 on Windows) does not throw when `console.error` receives a circular object — it serialises to `[Circular]` or similar. However, the `String(error)` call used in the `catch`-path payload construction of `formatCheckoutError` for the `non-Error other` branch *can* throw if the object has a `.toString()` override that itself throws or calls into an already-torn-down module. The consequence is that `formatCheckoutError` itself throws, the outer catch re-catches it (there is no outer catch in some callsites), and `paymentStore.error` is left in whatever state it was before. A `try { ... } catch { return '<checkoutFailed>: [unstringifiable]' }` wrapper around `String(error)` would close this gap.

### (g) receiptService.ts §6e nested ROLLBACK semantics — PASS

The nesting is correct. The inner try/catch around `ROLLBACK` ensures that if `ROLLBACK` itself throws (connection in bad state), the inner catch logs that secondary failure and does **not** rethrow it. The `throw error` in the outer catch then propagates the **original** `BEGIN`/`INSERT`/`COMMIT` error to the caller. No error is silently dropped; the ROLLBACK failure goes to `console.error` and the original error surfaces to the caller. Semantics are correct.

### (h) syncScheduler checkSession non-401 logging — MINOR

The old silent ignore was intentional: `checkSession` is called on every sync tick (every 30 s) and during intermittent outages will fail with a network error on every tick. Logging to `console.error` on every non-401 failure means a 10-minute connectivity drop produces ~20 `console.error` entries in the Tauri log, creating noise that could obscure real errors surfacing after reconnection. The correct level for a transient network miss is `console.warn` with rate-limiting (or the log should be suppressed when the connectivity check (from `connectivity.ts`) has already flagged offline state). As-is this is noisy but not functionally broken — `MINOR`.

## Overall recommendation (Round 1)

**REQUEST-CHANGES**

Two issues need resolution before merging. First (b)/(e): the non-`Error` string branch of `formatCheckoutError` exposes raw thrown-string content in the cashier UI banner and the raw `error` object reference in console logs creates an unbounded PII surface via attached response bodies. The user-visible banner should show only the generic i18n string for non-`Error` throwables; the detail can go to `console.error` only. Second (d): the two untagged silent catches in `syncService.ts` around ~1240–1246 are in the receipt-push critical path and should either be instrumented or annotated `/* non-critical */` with justification. Points (c), (g) are clean; (a) confirms the test is genuine; (f) and (h) are low-severity but worth a one-line fix each.
