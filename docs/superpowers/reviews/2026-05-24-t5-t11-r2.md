The remaining issues are mostly P2/SUGGESTION: T11's new "channel override" step (§4.2 step 3) is placed AFTER the default-price-list step, which means it will never fire in tenants that have a default price list (resolver short-circuits on first match) — this is a logical-ordering bug in the design that needs disambiguation before T11-impl-B ships. Several SUGGESTIONs improve precision but nothing rises to BLOCKER.

## Findings (BLOCKER / P1 / P2 / SUGGESTION)

### BLOCKER
None.

### P1
- **[P1-A] T11 §4.2 — "Channel override" placed in unreachable position in first-match resolver.** The resolver order is: (1) partner price list → use; (2) default price list → use; (3) channel override → use; (4) base. Read as a first-match algorithm (which mirroring `PricingService::getPrice` implies, see `apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:41-77`), step 3 will never execute when a default price list exists — and every active tenant has one by initialization. The spec needs to clarify one of: (a) channel override has higher priority than partner/default lists (move to step 0), (b) channel override is multiplicative/additive on top of step 2's result rather than alternative-match, or (c) it only fires when step 2 returns null (rare in practice). Without this clarification, T11-impl-B will produce a resolver that silently swallows channel-specific pricing. **Recommended fix:** Pick one semantic and document it; the most likely correct reading per typical commerce systems is "channel override has highest priority IF set" → reorder to (1) channel override → (2) partner price list → (3) default price list → (4) base.

### P2
- **[P2-A] T5 §120 asserts `dashboard.owner` permission without verifying it exists.** `grep -rn "dashboard.owner" RolesAndPermissionsSeeder.php` returns no matches. The permission must be added in T5 (likely via the project's `/add-permissions` skill for the new feature directory). Spec should state explicitly: "Permission `dashboard.owner` does not exist today; T5 adds it via RolesAndPermissionsSeeder + assigns to Owner + Admin roles by default." Without this, integrators will assume a pre-existing permission and silently get 403s.

- **[P2-B] T5 §72-82 "DB views" — naming versus the 3-tier rule.** The 6 view names are prefixed `tenant_v_*` per the spec, but the canonical rule (referenced as `claude/database-topology.md`) lives in the parent `syneriva/` repo, not `apps/erp/`. The ERP repo's own conventions don't yet codify "tenant_v_" as a view prefix. Either (a) cite the actual rule file path (which is `../../../../claude/database-topology.md` relative to the spec) so implementers can verify, or (b) decide the prefix locally and state it in this spec authoritatively. Right now an implementer following only this spec will not know whether `tenant_v_*` is a real ERP convention or invented for this work.

- **[P2-C] T5 §44 "ReportsController.php (lines 61-71)" cites the constructor injection lines, but no actual report endpoint method appears in that range.** Verified at `apps/api/app/Modules/Accounting/Presentation/Controllers/ReportsController.php:61-71` — those lines are class declaration + constructor signature. The "existing report endpoints" claim is true (file has trial balance, P&L, balance sheet, aged receivables, aged payables methods further down) but the line citation is misleading. Update to "the file in its entirety, especially the trial-balance / P&L / aged-receivables endpoint methods" or remove the line range.

- **[P2-D] T11 §4.3 "DocumentEmissionPolicy" — `Receipt` is not a `DocumentType`.** The spec writes `canEmit(DocumentType $type, ...)` and lists "`Receipt` (always)" among allowed types. But `Receipt` is a separate entity (`apps/api/app/Modules/POS/Domain/Receipt.php`) — not a `Document` row, not in the `DocumentType` enum. The policy interface as written cannot have `Receipt` as a `DocumentType` input. Fix: either (a) introduce a broader `EmittableArtifactType` enum that unions DocumentType + 'Receipt', or (b) carve receipts out of the policy entirely (POS always emits a Receipt; the policy gates only the optional B2B `Document` emission alongside the Receipt). Option (b) matches the architectural separation already in production.

### SUGGESTION
- **[S-1] T5 §6 generic-ness checklist line "Permissions: widgets respect user's location-level permissions (shop manager sees only their location)".** "Shop manager" is a role-flavour label that may confuse implementers. Rephrase to "users with location-scoped permissions" to stay generic across verticals.

- **[S-2] T5 §200 performance target "< 800ms for tenant with 10k receipts/month and 30 locations" — no seeded fixture exists for this scale.** State whether a perf seeder will be added (linked to `DemoTenantSeeder`?) or whether the team will create one during the perf-test phase. Without this, the perf criterion is unverifiable.

- **[S-3] T11 §4.2 `ResolveContext` includes `variant_id` but the existing `PricingService::getPrice()` does not accept variant_id (signature is `(string $productId, ?string $partnerId, string $quantity, string $currency, ?\DateTimeInterface $date)` per `PricingService.php:32-38`).** This is fine — T11 explicitly extends the resolver for variant awareness post-T2 — but should be called out as a deliberate extension, not a "mirror".

- **[S-4] T11 §3.41-42 enumerates per-country payment methods (Tunisia / France).** This is legitimate context for design, but the design itself should reference an abstraction (`PaymentMethod::is_tendered_at_counter()` boolean or similar) rather than hard-coding country-specific lists in the policy enforcer. Otherwise the policy will need updating each time a new country comes online. The spec's later phrasing in §118 ("POS spec already discriminates via `instrument_type` / `instrument_serial`; the policy enforcer uses this discrimination to gate") does the right thing — surface this as the primary mechanism, with country lists demoted to "examples".

- **[S-5] T11 §4.4 step 4 references existing `holdStore` pattern (`apps/pos/src/stores/holdStore.ts`).** Verified — `holdCurrentCart`, `recallTransaction`, `discardTransaction` all present at lines 38-40. But the "Save as Draft Order" hand-off needs a new repository (it persists to web ERP `documents` table, not the local SQLite `heldTransactions` repository). Note that this requires online connectivity OR an offline-queued draft-order sync mechanism. Worth one extra sentence in §4.4: "Save as Draft Order requires online connectivity at time of save; offline behavior (queue locally + push when online) is a Phase 2 enhancement for impl-C."

- **[S-6] T11 §4.5 introduces `channel` drill-down values `pos | web | online_<channel_id>`.** The `online_<channel_id>` shape mixes a string literal with a UUID — query-unfriendly for filtering. Suggest using two columns: `channel_kind` enum (`pos | web | online`) + `channel_id` nullable UUID.

- **[S-7] T5 acceptance §170-172 "Severity colors: red / orange / yellow"** are color names, not design-token references. Per CLAUDE.md rule 18, new code should consume `designTokens.ts`. Acceptance criterion should say "via `colors.error` / `colors.warning.*` tokens" so the test can verify token usage rather than literal class names.

## What's solid

1. **File-path accuracy is excellent in both specs.** I verified ~20 paths. Every one exists; every line-range where given is accurate (the only quibble is T5's `ReportsController.php:61-71` citation which is the constructor, P2-C). After Codex round-1 caught fabricated paths in T3/T6, the v2 specs for T5/T11 demonstrate disciplined grounding.

2. **Both specs explicitly defer to the migration topology contract** with the right boundaries (T5 §74 / §218; T11 §164 / §190). No cross-DB FK proposals.

3. **T11's deletion of the "Business customer group" path is unambiguous** — three separate callouts (§32, §92, §185) make it nearly impossible to mis-implement the resolver as the v1 wrong path.

4. **T5's reframing of ECharts state is intellectually honest.** Rather than papering over the v1 mistake, it explicitly says "Codex correctly noted... v1 was wrong" and re-anchors to the POS Analytics components that actually use ECharts. This is the right way to handle review-driven corrections.

5. **T11's "tendered at the counter" vs "settled later" line in §118 is the right architectural primitive** for the POS-vs-web policy split. It correctly avoids the trap of "POS = B2C only" and instead lets B2B walk-in customers transact at POS when payment is immediate, which is the realistic counter behavior. The instrument_type / instrument_serial mechanism (already in the fiscal POS work) is the right discriminator.

6. **T11 correctly scopes itself as design-only** (§1 + §141 + §216) and produces 3 named implementation tracks (T11-impl-A/B/C) for next-cycle scheduling. No silent scope creep into the sprint.

7. **T5 acceptance criteria include multi-company + multi-location + permission-edge-case cases** (§191-194), not just happy-path. This is the right discipline given the cross-cutting nature of reporting.
