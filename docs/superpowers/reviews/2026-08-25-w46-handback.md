## 1. Root cause — four defects, not one

**RC-1 — `basket_window` vetoed the whole adjustment.**
`CountingReplayGuardEvaluator::preApply()` (`CountingReplayGuardEvaluator.php:13-18` at `3bbe28480`) mapped `hasMovementNear === true` straight to `CountingItemFlagReason::BasketWindow`, and
`ApplyStockAdjustmentsOnCountingCompleted::applyReplay()` (`ApplyStockAdjustmentsOnCountingCompleted.php:276-281` at `3bbe28480`) treated *any* non-null return as a hard block: flag the item, `return false`, no movement, no GL.
`MovementReplayService::hasMovementNear()` (`apps/api/app/Modules/Inventory/Domain/Services/MovementReplayService.php:184-201`) is a `±window` `exists()` probe over **every** movement on the grain — a goods receipt 13 minutes before the count instant is enough. In a shop that keeps selling while it counts (the entire premise of the flow) that is every counted line.
The veto was also **redundant**: `StockAdjustmentService::applyCountResult()` (`:1279-1352`) already computes `expected_now = final_qty + Σ(as_of, now]`, which is precisely what keeps an in-window sale counted exactly once. The campaign verified that half worked (SIRO ended at 56, not 52). The guard only ever destroyed the honest counted-vs-expected delta on top of it.

**RC-2 — the report's variance was zero by construction.**
`CountingDiscrepancyReportService::varianceQuantity()` (`CountingDiscrepancyReportService.php:132-140` at `3bbe28480`) used `expected_qty_at_apply` as the baseline. That column stores the replay **target** — `final_qty + replayed_delta` (`ApplyStockAdjustmentsOnCountingCompleted.php:345-349`) — so it is *derived from* `final_qty`, and `final − baseline` collapses to `−replayed_delta`: **0.0000 on every replay-path line that had not moved since it was counted**. That is why `items_with_variance: 0` while `flagged_items[]` carried the real ones. It was wrong for applied lines too, not just flagged ones.

**RC-3 — nothing said "not applied".** The finalize response is `200`, the report had no per-line applied/not-applied field, and no summary counter for it.

**RC-4 — a batch-tracked shortage never moved a lot.**
`StockAdjustmentService::postCountCorrection()` (`:1417` at `3bbe28480`) topped the DEFAULT lot on a **positive** adjustment (remainder-safe since W2-7) but did nothing at all on a **negative** one, so Σ lots drifted permanently above the aggregate and FEFO kept promising stock that is not on the shelf. Same hole on the legacy arm (`postAdjustmentWithinLock`, the lot-less-negative fallthrough).

Independent of all four: `config('inventory.count_correction_gl_posting_enabled')` ships **false** — see §5.

## F-2 — the baseline, stated once and enforced

The gate's probe 2 was the sharp end: a sale stamped in the **same second** as the count was excluded by the strict `>` on the replay window, treated as already-counted, and posted as a **+4 phantom gain** that inflated stock back to 60 — and would become a wrong shrinkage/gain journal entry the moment the GL flag flips.

The baseline is now defined explicitly rather than left to a comparison operator (`apps/api/app/Modules/Inventory/Domain/Services/MovementReplayService.php:32-62`):

* **strictly before** the count instant → part of what the counter saw; **never replayed** (re-adding it would double-count the shelf);
* **from the count instant onwards** → neutralised exactly **once**, so `expected_now = counted + Σ[as_of, now]`.

So the window is now **closed at both ends** — `signedDelta()` `:88-89` (`>=`), `computeMany()` `:157`. `count_N_at_estimate` and `occurred_at`/`created_at` are both second-precision, so the collision is an operating case, not a rounding curiosity; between two unprovable readings the replay takes the one that **invents no stock**. Probe 2's line now resolves at variance **0** and writes no movement.

What that leaves standing is stated in the code rather than left implicit (`CountingItemFlagReason.php:27-45`): a `basket_window` line whose only nearby movement is in the **pre-count** half still resolves by posting its delta. Correct when the goods were on (or off) the shelf before the counter reached it, wrong when they were booked before the count but moved physically after it — see residual **R-8**.

Sentinel re-pinned: `MovementReplayServiceTest::test_boundary_exactly_at_from_is_excluded_exactly_at_to_is_included` → `test_boundary_movements_at_both_ends_are_included`, which now also pins that a movement one second **before** `from` stays baseline (`+5` not re-added).

## F-3 / F-4 — the drawdown

`StockAdjustmentService::drawLotsDownForCountShortage()` (`:1482-1620`):

* the `is_recalled = false` predicate is **gone**. Recall is the single most likely reason batch-tracked stock is physically off a shelf, so a recalled lot is exactly where a shortage lands; excluding it left the aggregate lowered and the recalled lot still claiming units that no longer exist. Order is now **saleable first, FEFO within each class, recalled last** (`orderBy is_recalled, expiry_date, created_at`) — quarantined stock is reachable but never consumed while saleable stock can absorb the shortage.
* the candidate list is read **`lockForUpdate()`** on the same `inventory_batch_stock` rows `issueBatchStock()` re-reads, so `min(available, remaining)` is held rather than a snapshot. Lock order stays `stock_levels` → `inventory_batch_stock`; no lock is taken on `product_batches`.
* each issue is additionally wrapped in `catch (InsufficientBatchStockException)` → log + next lot. `handle()` wraps the whole item loop in ONE root transaction with no per-item catch, so an escaping throw would have unwound **every already-applied item in the count**.
* an unclosed remainder is `Log::warning`-ed naming product, location, movement and quantity — the one case where the two ledgers stay diverged.

## NEW-1 — the tie is resolved by ORDER, not by time

The gate was right that r1 did not eliminate the same-second ambiguity, it flipped it. Probe P2a (counter had **not** seen the sale) resolves at variance 0 under `[from, to]`; probe P2b (counter **had** seen it) subtracts the same 4 units twice, 56 → 52. **A timestamp cannot separate them — at second precision it has no information left.** Both readings produce identical `occurred_at` and identical `final_qty_as_of`.

Insertion order can. The count now freezes the **last `stock_movements.id` that existed on its own stock line at the moment it was submitted**, and the replay treats a boundary-second movement as baseline when its id is at or below that marker (it was already there when the counter reported) and neutralises it when it is above (it arrived afterwards). `stock_movements.id` is a UUIDv7 (`HasUuids::newUniqueId()` → `Str::uuid7()`), so lexicographic order **is** creation order, and `ORDER BY id DESC LIMIT 1` supplies it (PostgreSQL has no `max(uuid)` aggregate — a repo pitfall of record).

| Piece | Where |
|---|---|
| additive, self-guarding migration — 4 nullable `uuid` columns | `apps/api/database/migrations/tenant/2026_08_25_120000_add_count_movement_markers_to_counting_items.php` |
| `count_N_movement_marker` stamped as the count is submitted | `InventoryCountingItem::submitCount()` `:283-291`, `latestMovementMarker()` `:330-350` |
| the winning phase's marker travels with its instant | `FinalQuantityAsOfResolver::resolveMarker()` + shared `winningPhase()` |
| frozen at finalize / manual override | `InventoryCountingService.php:1110`, `:1221` |
| the tie-break itself | `MovementReplayService::signedDelta()` (+ `compute()`, `computeMany()` mirror) |

**Two deliberate departures from the condition as written, both to avoid a worse defect:**

1. **The marker is per ITEM per PHASE, not on the counting session.** A session-level marker taken at activation would neutralise *every* movement since activation — including sales that happened before the counter reached that shelf. Worked example: activation 10:00, sale of 4 at 10:15 (60 → 56), counter counts **56** at 10:30. Session marker ⇒ `Σ = −4` ⇒ `expected_now = 56 − 4 = 52` against an on-hand of 56 ⇒ a **−4 correction that is pure fiction**. The count instant is per line, so its snapshot must be too. The columns still live on `inventory_counting_items`, the row that owns `final_qty_as_of`.
2. **The marker refines ONLY the boundary second.** Pure id ordering is wrong on the offline-device path: `final_qty_as_of` may be a *device* instant hours before the marker was taken (a count synced later), and ordering by id alone would then stop neutralising every sale made between the count and its sync. Time decides everything time can decide; order decides only the tie it cannot. Pinned by `test_a_later_movement_is_neutralised_even_below_the_marker`.

With no marker (legacy rows, lines counted before the migration) the r1 `[from, to]` semantics apply unchanged — which is why nothing already verified moved.

**Red-first**, marker branch disabled in `signedDelta()` + `computeMany()`, then restored:

```
⨯ same second movement before the count is baseline      (P2b — on-hand 52, must be 56)
✓ same second movement after the count is neutralised    (P2a — r1's inclusive boundary already handled this reading)
Tests:  1 failed, 15 passed
```
Both P2 and P2b now report `variance_qty 0.0000` and write no movement, on sqlite **and** PG.

## NEW-2 — the lock-order comment now states the truth

`StockAdjustmentService::drawLotsDownForCountShortage()` docblock. It previously claimed "no lock is taken on `product_batches`" — false, and the F-1 class defect one round later. On PostgreSQL `->lockForUpdate()` over a JOIN compiles to a bare `FOR UPDATE` with no `OF`, and PostgreSQL locks the matched rows in **every** table in the `FROM` list. The comment now says so, records that this is the only joined `lockForUpdate()` in `app/` and that nothing else locks `product_batches` at all (so there is no AB-BA cycle today), and tells the next author what to do: take a `product_batches` lock *after* `inventory_batch_stock`, or narrow this read to `->lock('for update of inventory_batch_stock')`. The query is unchanged, so nothing verified at r2 moved.
