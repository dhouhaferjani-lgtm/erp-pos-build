## 1. Root cause — four defects, not one

**RC-1 — `basket_window` vetoed the whole adjustment.**
`CountingReplayGuardEvaluator::preApply()` (`CountingReplayGuardEvaluator.php:13-18` at `3bbe28480`) mapped `hasMovementNear === true` straight to `CountingItemFlagReason::BasketWindow`, and
`ApplyStockAdjustmentsOnCountingCompleted::applyReplay()` (`ApplyStockAdjustmentsOnCountingCompleted.php:276-281` at `3bbe28480`) treated *any* non-null return as a hard block: flag the item, `return false`, no movement, no GL.
`MovementReplayService::hasMovementNear()` (`apps/api/app/Modules/Inventory/Domain/Services/MovementReplayService.php:184-201`) is a `±window` `exists()` probe over **every** movement on the grain — a goods receipt 13 minutes before the count instant is enough. In a shop that keeps selling while it counts (the entire premise of the flow) that is every counted line.
The veto was also **redundant**: `StockAdjustmentService::applyCountResult()` (`:1279-1352`) already computes `expected_now = final_qty + Σ(as_of, now]`, which is precisely what keeps an in-window sale counted exactly once. The campaign verified that half worked (SIRO ended at 56, not 52). The guard only ever destroyed the honest counted-vs-expected delta on top of it.

**RC-2 — the report's variance was zero by construction.**
`CountingDiscrepancyReportService::varianceQuantity()` (`CountingDiscrepancyReportService.php:132-140` at `3bbe28480`) used `expected_qty_at_apply` as the baseline. That column stores the replay **target** — `final_qty + replayed_delta` (`ApplyStockAdjustmentsOnCountingCompleted.php:345-349`) — so it is *derived from* `final_qty`, and `final − baseline` collapses to `−replayed_delta`: **0.0000 on every replay-path line that had not moved since it was counted**. That is why `items_with_variance: 0` while `flagged_items[]` carried the real ones. It was wrong for applied lines too, not just flagged ones.

**RC-3 — nothing said "not applied".** The finalize response is `200`, the report had no per-line applied/not-applied field, and no summary counter for it.

**RC-4 — a batch-tracked shortage never moved a lot.**
`StockAdjustmentService::postCountCorrection()` (`:1417` at `3bbe28480`) topped the DEFAULT lot on a **positive** adjustment (remainder-safe since W2-7) but did nothing at all on a **negative** one, so Σ lots drifted permanently above the aggregate and FEFO kept promising stock that is not on the shelf. Same hole on the legacy arm (`postAdjustmentWithinLock`, the lot-less-negative fallthrough).

Independent of all four: `config('inventory.count_correction_gl_posting_enabled')` ships **false** — see §5.

## 3. Shapes

### Movement — one per varying line

```
stock_movements
  movement_type   = adjustment
  reason          = count_correction
  reference_type  = inventory_counting
  reference_id    = <inventory_countings.id>
  reference       = 'COUNT_REPLAY'            (replay path)  |  'COUNTING:{number}' (legacy)
  quantity        = expected_now − on_hand_now   (signed; NEVER 0 — a zero writes no row)
  quantity_before = on_hand_now
  quantity_after  = expected_now                (= counted + Σ movements after the count)
  unit_cost       = Product::resolveMovementUnitCost()  (T21, resolved before the row)
```

Campaign shape, verified: `-2.0000  70.0000 -> 68.0000` and `+1.0000  40.0000 -> 41.0000`; the agreeing line writes nothing.

Lot ledger, batch-tracked:
* shortage → `inventory_batch_movements` negative rows, FEFO (soonest expiry first, **expired lots included**), `min(available, remaining)` per lot, keyed to the same `stock_movements.id`. Σ lots stays equal to the aggregate.
* overage → `BatchStockService::ensureDefaultBatchForUntrackedRemainder()` (W2-7 semantics). No phantom DEFAULT is minted or inflated: with LOT-A 30 + DEFAULT 35 and a count of 67, DEFAULT becomes 37, LOT-A stays 30, batch count stays 2.

### GL — unchanged mechanism, now reachable

```
JournalEntry  source_type = 'inventory_shrinkage'  source_id = <stock_movements.id>
  shortage :  Dr SystemAccountPurpose::InventoryShrinkageExpense   (TN 6586)
              Cr SystemAccountPurpose::Inventory                   (TN 37)
  overage  :  Dr Inventory (37) / Cr InventoryGainIncome (7586)
  amount   =  movement.unit_cost × |quantity_after − quantity_before|, rounded ONCE at the currency scale
```
Proven balanced on PG: `4.250000 × |68 − 70| = 8.500` Dr 6586 / Cr 37.

### Report

Per row (added, additive — nothing removed): `expected_qty`, `counted_qty`, `variance_qty`, `variance_applied`, `not_applied_reason`.
Summary (added): `items_applied`, `items_not_applied`. `items_with_variance` / `total_variance_value` now read the real numbers.
`variance_applied` is `true` when the line agrees with the shelf (nothing outstanding) or when a `stock_movements` row carries this counting as its source document — **evidence, not the absence of a flag**. `not_applied_reason` names the first recorded reason that answers `blocksStockApplication()`.

## 5. Residuals

**R-1 (owner, deploy-time — carried forward, NOT resolved here).** `inventory.count_correction_gl_posting_enabled` still ships **`false`** (`apps/api/config/inventory.php:29`). `ORCHESTRATOR-RULING-2026-08-19-m5-oq12-gate.md` makes the flip a deploy-time blocker pending expert-comptable ratification of the Option A (6586 / 7586) liasse presentation, so this lane deliberately did **not** flip it — the GL tests enable it explicitly. **Consequence for tenant #1: a count correction moves stock and carries its row cost, but posts no journal entry until the flag is flipped.** Smoke-sheet row 7.5 stays unmet on a default tenant. `test_the_flag_is_off_by_default_and_the_dormant_listener_posts_nothing` still pins the shipped default.

**R-2 (W4-8, P2, separate lane).** Counting still has no lot grain — `InventoryCountingItem` is keyed on `(product_id, variant_id, location_id)`. The FEFO drawdown added here is the best attribution available at this layer; an operator still cannot enter a per-lot count.

**R-3.** The FEFO drawdown deliberately **includes expired lots**. Stock found missing off a shelf is more plausibly the oldest than the newest, and skipping expired lots would push the shortfall onto saleable stock while leaving the expired lot claiming units that are gone. This differs from `FEFOInventoryService::consumeBatchesAtomically()`, which excludes them for sales — stated so a reviewer sees it as a choice.

**R-4.** The drawdown is **tolerant**: if the lots hold less than the shortage it drains what is there and leaves the rest. The aggregate has already moved inside the lock, so a refusal would strand the operator mid-correction; a partial consumption cannot overshoot and strictly narrows the gap. Same posture as the pre-existing `issueFromDefaultBatchByDelta()` (gate N-2).

**R-5.** `expected_qty_at_apply` keeps its existing meaning (the replay **target**) — the FE reads it and this lane did not migrate it. The report no longer treats it as a baseline. If a future lane renames it, `expectedQuantity()` is the one place that decides.

**R-6.** `flagged_items[].flag_reason` (singular, legacy free-text) still disagrees with `flag_reasons[]` on the same row — reported by the campaign under "also observed", untouched here.

**R-7 (worktree hygiene).** `apps/api/vendor`, `apps/api/.env`, `node_modules` and `apps/web/node_modules` were copied in to run the lanes; they are ignored and not in any commit. Throwaway `autoerp_test_w46` was dropped.
