## Findings

### BLOCKER
1. **Return receipt fixtures still cannot persist on PostgreSQL.**  
   Evidence: r2 generalizes `seedReceipt()` to accept `ReceiptType::Return` and the tests call it with negative totals (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:356`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:638`). The helper sets `receipt_type` and negative `total` but does not set `original_receipt_id` or `return_reason` (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:241`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:248`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:252`). PostgreSQL requires return receipts to have both (`apps/api/database/migrations/tenant/2026_03_09_200000_add_return_fields_to_pos_receipts.php:45`, `apps/api/database/migrations/tenant/2026_03_09_200000_add_return_fields_to_pos_receipts.php:47`). The same helper then writes `ReceiptPayment.amount = $total`, so a negative return payment violates `amount > 0` (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:256`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:260`, `apps/api/database/migrations/tenant/2026_01_08_190640_create_pos_receipt_payments_table.php:62`).  
   Concrete fix: Add a dedicated return fixture helper that first creates a valid original sale, sets `original_receipt_id` and a valid `return_reason`, and writes a positive tender/refund payment amount or omits payments if the table contract allows no payment row. Add an assertion that a return fixture persists before using it in service/endpoint tests.

### MEDIUM
1. **`averageBasket` truncates instead of rounding at the ratio boundary.**  
   Evidence: r2 computes `gross / saleCount` with `bcdiv(..., $scale + 1)` and then formats with `CurrencyScale::bcformatStrict()` (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:460`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:461`). `bcformatStrict()` is a `bcadd(..., $scale)` formatter, so it truncates (`apps/api/app/Shared/Domain/CurrencyScale.php:130`, `apps/api/app/Shared/Domain/CurrencyScale.php:144`). The approved spec says ratios, including average basket, are rounded once at the boundary (`docs/superpowers/specs/2026-06-19-owner-reporting-experience-design.md:66`).  
   Concrete fix: Use `CurrencyScale::bcround()` for `averageBasket` after a higher-precision `bcdiv()`, and add a test such as gross `100.00`, sale count `6`, EUR scale `2` expecting `16.67`.

2. **Task 11’s proposed memo code likely fails the plan’s own lint command.**  
   Evidence: r2 creates `locationParam` outside `useMemo()` and closes over it inside the memo callback while the dependency list includes `filters.locationIds` but not `locationParam` (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:1259`, `docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:1260`). The repo keeps `react-hooks/exhaustive-deps` as a warning (`apps/web/eslint.config.js:83`, `apps/web/eslint.config.js:86`), and r2 runs lint with `--max-warnings=0` over `src/features/owner-dashboard` (`docs/superpowers/plans/2026-06-20-owner-reporting-dashboard.md:1264`).  
   Concrete fix: Build the conditional spread inside the `useMemo()` callback, or memoize `locationParam` separately and include it as a dependency.
