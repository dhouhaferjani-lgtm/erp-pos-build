## Executive summary

- All 6 v3 Codex findings are **genuinely resolved**, not reworded. The two that are resolved by reinterpretation rather than code change (the BLOCKER, and the inbound `payment_methods` FK) are resolved against the **locked** SoT v3 §13.6 / D16 2026-05-14 amendment, which explicitly authorizes the inbound/outbound asymmetry. v4 does not over-claim — it stops asserting "zero Treasury dependency" and stops claiming the FK is removed.
- The asymmetric bounded-modules seam is **buildable as specified**: `FiscalEventProjector` + `ModuleActivationResolver` + `FiscalEventProjectionRegistry` are all-new interfaces (confirmed absent in code), the engine/`OutboxIngestor` depend only on those interfaces, and the Treasury bridge is the only module-gated projector. The honest disclosure in §18.3 — that a *production* Treasury-inactive deployment is not yet possible — is correct and correctly scoped out.
- One real buildability defect survives: a **module-name casing mismatch** between the projector's `requiresModule()` (`'treasury'`, lowercase) and the actual module identifiers in `Vertical::defaultModules()` (`'Treasury'`, PascalCase) that `CompanyConfig::hasModule()` strict-compares. As written, the Treasury bridge would never run in the reference deployment. P1.
- Two cross-app omissions in the disposition checklists: §14.2 names only `store`/`storePayments` as the web-POS server-authoring surface, but `void` (`ReceiptController::void`) and `processReturn` (`ReceiptController::processReturn`) are equally server-authoring receipt mutation/creation paths reachable from `apps/web` (and `apps/pos`). And §7.4/§14 mis-attributes all of `ReceiptPaymentService` to the Treasury bridge when it also creates the POS-core `ReceiptPayment` row.

## New findings

### [P1] `ModuleActivationResolver` Phase 1 implementation has a module-name casing mismatch that would prevent the Treasury bridge from ever running
**Dimension:** buildability / internal consistency
**Spec location:** §5.0, §7.3, §7.4 (`spec v4:247,368-389`)
**Evidence:** v4 §7.3 says the Phase 1 `ModuleActivationResolver` "delegates to the existing module-activation surface — `CompanyConfigService` / `CompanyConfig::hasModule()`." The projector interface example and §7.3/§5.0 prose use the module token **`'treasury'`** (lowercase) — `requiresModule(): ?string // ... 'treasury' = module-gated` (`spec v4:370`), `isActive('treasury', …)` (`spec v4:247,382,388`). But the actual module identifiers in `Vertical::defaultModules()` are **PascalCase**: `'Treasury'`, `'Accounting'`, `'Sales'`, `'Inventory'` (`Vertical.php:124-136`, verified). `CompanyConfig::hasModule()` does a **strict** `in_array($module, $this->allEnabledModules, true)` (`CompanyConfig.php:50-53`). `hasModule('treasury')` therefore returns `false` for every tenant.
**Issue:** As specified, the Phase 1 resolver implementation `isActive('treasury', …)` would always return `false`, so `FiscalEventProjectionRegistry.activeProjectorsFor()` would **always exclude `TreasuryReceiptBridge`** — even in the reference deployment where Treasury is active. The reference deployment would silently produce no Treasury `Payment` rows and no GL entries for POS receipts.
**Impact:** The single most important Phase 1 projection path (the reference deployment's Treasury bridge) would be dead on arrival, and the §17.3 "end-to-end with Treasury active" test would fail — or, worse, the implementer "fixes" it ad hoc without the spec recording the canonical module token, producing drift.
**Suggested fix:** Pin the module token explicitly in §7.3: either state that `requiresModule()` returns the canonical PascalCase identifier used by `Vertical::defaultModules()` (`'Treasury'`), or state that the `ModuleActivationResolver` Phase 1 implementation normalizes case before calling `hasModule()`. Add a §17.3 assertion that `isActive('Treasury', …)` (or whatever token is chosen) returns `true` for a standard seeded tenant, so the casing contract is test-locked.

### [P2] §14.2 web-POS disposition omits the `void` and `processReturn` server-authoring receipt paths
**Dimension:** completeness / cross-app
**Spec location:** §14.2, §2 (`spec v4:599-613,68`)
**Evidence:** §14.2 names only the `createReceipt` / `processReceiptPayments` write surface. But `apps/web` has two more live server-authoring receipt paths: `ReturnItemsModal.tsx:5,90` calls `processReturn` → `POST /pos/receipts/{id}/return` → `ReceiptController::processReturn` (`:203`), which **creates a new negative receipt** server-side (`ReceiptController.php:200-260` — "Creates a new negative receipt (return receipt)"); and `ReceiptSearchPage.tsx:129` calls `POST /pos/receipts/{id}/void` → `ReceiptController::void` (`:152`), which mutates receipt fiscal state via `ReceiptVoidService`. The Tauri POS also hits both routes online-only (`apps/pos/src/components/pos/VoidReturnModal.tsx:143,166`).
**Issue:** §14.2 claims it dispositions "the web-POS server-authoring surface" so it "does not coexist with the rebuilt device-authority chain `[SoT D8]`," but `void` and `processReturn` are server-authoring receipt mutation/creation paths that remain fully live and untouched. The reserved event types `SALE_VOID` / `REFUND_RECEIPT` / `PARTIAL_REFUND` (Appendix A) are explicitly Phase 2+, so leaving these server-side in Phase 1 may be a legitimate scoping decision — but the spec must say so explicitly rather than silently omit them, otherwise the §14.2 "does not coexist" claim is internally inconsistent.
**Impact:** A writing-plan executing §14.2 disables `store`/`storePayments` and believes the web-POS server-authoring surface is closed, while `void` and `return` keep authoring/mutating `pos_receipts` rows server-side — the exact two-model coexistence §14.2 claims to eliminate. Or the implementer disables `void`/`return` without realizing they are shared with the Tauri POS and breaks online void/return for the offline client.
**Suggested fix:** Add `void` / `processReturn` (and their `apps/pos` callers, `VoidReturnModal.tsx:143,166`) to §14.2 as **knowingly retained for Phase 1**, with an explicit cross-reference to the reserved `SALE_VOID` / `REFUND_RECEIPT` / `PARTIAL_REFUND` event types and a note that they remain server-side until their event types land in a later phase. State the rationale so the "does not coexist with the rebuilt chain" claim is scoped to *new sale* authoring, not all receipt mutation.

### [P2] §15.2 `fiscal:enqueue-resolved-event-projections` resume path conflicts with the §3.3 immutability trigger's write-once `payload` rule on re-resolution
**Dimension:** internal consistency
**Spec location:** §3.3, §7.5, §15.2 (`spec v4:197,435,635`)
**Evidence:** §3.3 states `payload` is **write-once** and `payload_parse_status` is **write-once** `pending → parsed` or `pending → failed`. §7.5 / §15.2 describe the resolver writing `payload` and flipping `payload_parse_status → parsed`, then `fiscal:enqueue-resolved-event-projections` creating the projection rows. §15.2 says the command is idempotent "if `fiscal_event_projections` rows already exist." But there is an unhandled gap: if the resolution transaction commits the `payload` write + status flip but then **fails or crashes before** the projection rows are enqueued (they are described as separate steps — the resolution action "then" invokes the command), a re-run of the resolution action cannot re-write `payload` (write-once trigger raises). The only recovery is running `fiscal:enqueue-resolved-event-projections` standalone — which §15.2 does support — but §7.5 frames the enqueue as something "the resolution path **must** then" do as if it were part of the same logical unit, without specifying it must be in the same transaction or idempotently recoverable.
**Issue:** The spec does not state whether the `payload` write + status flip + projection-row creation + enqueue is one transaction or a sequence, and the write-once trigger makes a partial-failure mid-sequence non-retriable through the normal resolution action. The standalone command is the de facto recovery path but §7.5 does not say so.
**Impact:** An implementer could build the resolution action as a non-atomic sequence; a crash between the status flip and the enqueue leaves a `parsed` event with no projections and no obvious operator signal, and re-running the resolution action fails on the write-once trigger. Recoverable only by an operator knowing to run the standalone command.
**Suggested fix:** In §7.5, specify that the `payload` write + `payload_parse_status` flip + `fiscal_event_projections` row inserts happen in **one transaction**, with the queue enqueue after commit (mirroring the §7.2 Step 2/3 pattern). Explicitly name `fiscal:enqueue-resolved-event-projections` as the recovery path for the "status flipped but projections missing" state, and have §17.3 cover the crash-between-flip-and-enqueue case.

### [P3] §7.4 / §14 mis-attributes all of `ReceiptPaymentService` to the Treasury bridge
**Dimension:** consistency / codebase-claim
**Spec location:** §7.4, §14 disposition table (`spec v4:401-404,569`)
**Evidence:** §7.4 says `TreasuryReceiptBridge` "creates the Treasury-operational effects, which are the logic of `ReceiptPaymentService`," and §14 dispositions `ReceiptPaymentService` as "REUSE (relocated → `TreasuryReceiptBridge`)." But `ReceiptPaymentService` also creates the POS-core `ReceiptPayment` row at `ReceiptPaymentService.php:297` — its class doc lists "(1) Treasury Payment records (2) Receipt Payment records (3) General Ledger entries" (`:35-41`). The `ReceiptPayment` row is POS-core (per §7.4 it belongs to `PosCoreReceiptProjection`), not Treasury.
**Issue:** Two different live code paths create `ReceiptPayment` rows: `ReceiptSyncService.php:598` (offline-sync path) and `ReceiptPaymentService.php:297` (web/`storePayments` path). The spec attributes the former to POS-core and the latter wholly to the Treasury bridge — but part of `ReceiptPaymentService` (the `ReceiptPayment::create`) is POS-core logic.
**Impact:** A writing-plan that lifts `ReceiptPaymentService` wholesale into `TreasuryReceiptBridge` would put `ReceiptPayment` creation inside the module-gated bridge — so a Treasury-inactive deployment would produce `pos_receipts` but **no `ReceiptPayment` rows**, contradicting §7.4's claim that the POS-core projector "creates ... `ReceiptPayment` rows" and "runs to completion with Treasury inactive."
**Suggested fix:** In §7.4 / §14, clarify that the relocation splits `ReceiptPaymentService`: the `ReceiptPayment::create` logic (`:297`) goes to `PosCoreReceiptProjection`; only the Treasury `Payment` (`:252`) + GL (`:269`) logic goes to `TreasuryReceiptBridge`. State that `PosCoreReceiptProjection` is the single owner of `ReceiptPayment` row creation regardless of which input path the receipt came from.

### [P3] §14.1 backend feature-suite scope still partly relies on "and the other ... receipt-sync tests"
**Dimension:** completeness
**Spec location:** §14.1 (`spec v4:595`)
**Evidence:** §14.1 names `SyncReceiptsTest.php` and `ReceiptSyncServiceV3Test.php` then says "and the other `tests/Feature/POS/* receipt-sync tests`." The live suite also includes `SyncReceiptsRequestTest.php`, `ReceiptSyncServiceInstrumentGuardTest.php`, `ReceiptSyncServiceTrainingModeTest.php`, `ReceiptSyncServiceVoucherRedemptionTest.php`. This is the same pattern Codex flagged as v3 P2 ("name the concrete classes ... not [leave it] implicit under grep").
**Issue:** Minor residual of v3 P2. The class-level scope is materially better than v3 (the production classes are all named), but the feature-test scope is still a glob.
**Impact:** Low — a `tests/Feature/POS/*ReceiptSync*` + `*Sync*Receipt*` grep finds them; the production class scope is concrete. But naming them removes ambiguity.
**Suggested fix:** Replace "and the other ... receipt-sync tests" with the explicit list: `SyncReceiptsTest.php`, `SyncReceiptsRequestTest.php`, `ReceiptSyncServiceV3Test.php`, `ReceiptSyncServiceInstrumentGuardTest.php`, `ReceiptSyncServiceTrainingModeTest.php`, `ReceiptSyncServiceVoucherRedemptionTest.php`.

## Out-of-scope concerns (not blocking; locked or future)

- The §18.3 residual — that no current vertical can run with Treasury inactive (it is not even a `compatibleExtras()` option, verified `Vertical.php:104-114`) — means the asymmetric seam is, in Phase 1, **only ever exercised by a test double**, never by a real deployment. v4 discloses this honestly and scopes the production config-model change out. This is consistent with SoT v3 D16 (which defines the *mechanism*, and v4 builds the mechanism). Noted only so the owner is aware the seam ships unproven against production config until the §18.3 follow-up lands.

## Verdict rationale

All 6 v3 findings are genuinely resolved. The two resolved-by-reinterpretation (BLOCKER, inbound FK) are authorized by the locked SoT v3 §13.6 / D16 amendment, verified verbatim. The remaining four are resolved with concrete, buildable mechanisms. No new BLOCKER: nothing in v4 is unbuildable or violates a locked decision. The P1 (module-name casing) is a precise, one-line spec fix that does not require rearchitecting — it is a naming-contract gap, not a design flaw. The two P2s are completeness/consistency gaps that a writing-plan would otherwise stumble on. **APPROVE-WITH-MINOR-EDITS**: apply the P1 + both P2 edits before writing-plans; the P3s are cleanup that can fold into the same pass.
