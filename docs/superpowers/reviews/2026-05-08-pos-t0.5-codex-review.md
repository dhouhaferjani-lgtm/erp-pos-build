### (g) URL leak / PII — BLOCKER (round-1)

`syncScheduler.ts` (the new fire-and-forget `.catch` for `paymentStore.refreshFromSQLite`) was logging raw `err` reference instead of `serializeErrorForLog(err)`:

```ts
// Pre-fix:
usePaymentStore.getState().refreshFromSQLite().catch((err: unknown) => {
  console.error('[SyncScheduler] paymentStore refreshFromSQLite failed:', err);
});
```

The `paymentStore.refreshFromSQLite` inner catch correctly uses `serializeErrorForLog`. But if the inner catch itself throws (edge case — bounded but possible if `serializeErrorForLog`'s try/catch chain mis-fires), the outer scheduler catch would log a raw `err` object — which could carry an axios-shaped error with `config.url` / auth headers spread into devtools.

**Resolution (round-1 fix-up):** outer `.catch` now uses `serializeErrorForLog`:

```ts
// Post-fix:
usePaymentStore.getState().refreshFromSQLite().catch((err: unknown) => {
  console.error('[SyncScheduler] paymentStore refreshFromSQLite failed', {
    ...serializeErrorForLog(err),
  });
});
```

Note: the existing `productStore.refreshFromSQLite` outer `.catch` has the same shape (raw `err`). Per kickoff scope discipline ("Things you must NOT do" → "Do NOT propagate productStore.refreshFromSQLite's `console.error` lapse — wrap your new catch with `serializeErrorForLog` even though the template doesn't"), T0.5 wraps ONLY the new (paymentStore) line. ProductStore's pre-existing lapse is out of T0.5's scope; tracked as follow-up.
