# Delivery-note consolidation spec gate — round 1

## 1. Gate verdict: REVISE

The spec is well grounded on the current eligibility, pagination, permission, and unlocked-read defects, and it is faithful to the approved view set. It is not safe to dispatch yet. The P0-3 protocol does not enforce the promised cross-lane rule: the SO→Invoice path creates and populates its invoice before it silently skips an already-stamped DN, so `insertOrIgnore` can preserve a marker while still billing the same delivered goods again (`SalesOrderToInvoiceConverter.php:167-204,445-461`). Its lock order is also the inverse of the proposed consolidation order: SO takes the invoice-number sequence while creating the invoice and only later touches DNs, whereas the spec makes consolidation lock DNs before creating/numbering the invoice (`DeliveryNoteToInvoiceConverter.php:177-218`; `CopiesDocumentData.php:74-94`; `DocumentNumberingService.php:44-64`). In addition, the prescribed FE `RequirePermission moduleKey="Sales"` is not a real module gate in this codebase: unknown keys are allowed, and only lowercase `sales` exists in the permission-alias map (`RequirePermission.tsx:45-58`; `usePermissions.ts:21-24,130-134`). These are release-blocking correctness issues, not polish.

## 3. Defects and required fixes

1. **P0-3 does not enforce the cross-lane billed-once invariant.** An SO invoice is created and receives all order lines before `markDeliveryNotesAsInvoiced`; an already-invoiced DN is merely skipped (`SalesOrderToInvoiceConverter.php:167-204,431-462`). `insertOrIgnore` would make the marker collision non-decisive, so consolidation can win and SO can still create a second invoice for the same goods. **Required fix:** obtain an explicit owner/domain ruling for the losing SO path, then make claiming every relevant DN a precondition before invoice creation. The safe default is batch-atomic refusal with attributed DNs; do not claim silent skip is equivalent. Add cross-lane tests with consolidation winning and SO winning.

2. **Lock ordering is local, not global.** Sorted DN locks prevent consolidation-vs-consolidation AB/BA deadlocks, but SO currently numbers/creates the invoice first and touches DNs later (`SalesOrderToInvoiceConverter.php:167-204`), while the proposal locks DNs before target creation (`SPEC...md:153-177`; `DeliveryNoteToInvoiceConverter.php:177-218`). Invoice numbering itself takes a row lock (`DocumentNumberingService.php:44-64`). **Required fix:** publish one order for every lane that can claim an existing DN—begin transaction → lock/claim sorted DN ids → acquire invoice sequence/create invoice → write lines/state/events—and refactor SO to it. Insert marker rows in the same sorted order. Test consolidation-vs-SO as well as opposite-order consolidation sets.

3. **The FE module gate named in P0-2 is a no-op.** Uppercase `Sales` is not a `MODULE_PERMISSIONS` key and unknown keys pass (`usePermissions.ts:21-24,130-134`). **Required fix:** wrap route surfaces in `<ModuleGuard module="Sales">` plus a real `RequirePermission permission=...`; use `hasModule('Sales')` for inline tab/action visibility. Add `module:Sales` to both the existing consolidation POST and the new queue GET—the spec currently says only newly added routes (`SPEC...md:141-143`), while the existing POST has only `can:invoices.create` (`Document/Presentation/routes.php:286-289`). Test each layer independently with Sales disabled.

4. **The claim protocol is underspecified and the table is not minimal.** A lock + affected-row CAS inside the invoice transaction is already enough to roll back a losing invoice; the marker adds a useful declarative association, but also creates a dual-write representation. Calling payload the sole truth while the marker chooses the winner is internally inaccurate (`SPEC...md:169-203`). **Required fix:** define one injected billing-claim service used by all three writers. It must merge the JSON patch in SQL (`COALESCE(payload,'{}') || patch`) rather than overwrite a stale PHP payload, assert tenant/company/type, insert/check the marker decisively, and commit marker + payload + invoice atomically. Catch only the named marker uniqueness constraint after transaction rollback, then re-read the winner for the 422; do not translate unrelated 23505s. Replace the string lane with a backed PHP enum, consistent with the repository's enum rule (`CLAUDE.md:39-40`).

5. **The partner balance line has no server contract for its monetary total.** Offset pagination supplies record count in `meta.total`, not a money aggregate (`PaginatesResults.php:55-94`), yet View A2 says count and monetary total come from the same call's `meta` (`SPEC...md:248-252`). **Required fix:** define and test an `aggregates: { count, total }` response computed across the full filtered set, independent of the current page. Do not overload pagination metadata.

6. **The queue API is not implementable without invention.** The spec promises roll-ups plus lazy per-partner rows, location scope, filters, and pagination, but defines only one route and no request/response contract (`SPEC...md:256-269,425-432`). The reused service has neither location nor partner-type scope and materializes all rows (`UninvoicedDeliveryNoteService.php:59-84`). Also, the existing unconstrained `GET /delivery-notes/{deliveryNote}` precedes any new static GET (`Document/Presentation/routes.php:269-289`), so a misplaced `/delivery-notes/uninvoiced` route will be captured as `{deliveryNote}`. **Required fix:** specify exact summary and expanded-group contracts, pagination unit, filters, location default/validation, customer-partner predicate, and cache key inputs. Register the static route before the parameter route or add `whereUuid('deliveryNote')`. Reconcile this required query work with the false “no new query logic” promise.

7. **M1 and M3 disagree on ownership of the queue endpoint.** M1 must pass auth tests against `GET /delivery-notes/uninvoiced`, while M3 says it creates that endpoint (`SPEC...md:358-369,425-432`). OI-1 also bundles the optional accountant grant with whether the approved queue endpoint exists (`:411-416`). **Required fix:** put the thin endpoint and its authorization/module contract in M1, leaving roll-ups/lazy expansion UI work in M3, or move its tests out of M1. Split “grant accountant `deliveries.view`” from “serve existing `deliveries.view` roles”; lack of the former must not silently cancel the owner-approved queue.

8. **The DTO/type plan conflicts with the actual FE type.** Type generation updates ambient `DocumentData` (`packages/shared/types/generated.d.ts:659-710`), but the consolidation client uses a hand-written `DeliveryNote` interface (`deliveryNotes.ts:11-35`). Merely deleting its phantom payload field leaves no invoiced fields and regenerating types does not update it. **Required fix:** specify that the client consumes or narrows generated `App.Modules.Document.Application.DTOs.DocumentData`; do not hand-edit another domain mirror. Separate payload-backed state (`invoiced_at`, `invoice_id`, lane) from the resolved invoice number, which cannot be produced by `fromPayload(array)` alone.

9. **The concurrency test needs a deterministic harness and CI wiring.** The repo supports committed PG fixtures and `pcntl_fork`, but the production converter has no stated barrier at “DN lock acquired,” so “assert B blocks” cannot be implemented deterministically from the prose alone (`SPEC...md:371-380`). The PG gate is a literal allowlist (`.github/workflows/ci.yml:617-629`). **Required fix:** name the test class/file, add it to that allowlist, use `connectionsToTransact(): []` or no `RefreshDatabase` with explicit cleanup, and define a deterministic barrier (for example, hold the invoice-sequence row so process A blocks after taking sorted DN locks, observe the wait, then start B and release). Set finite lock/statement timeouts and guarantee child/connection cleanup.

10. **The event boundary is asserted but not regression-tested.** Current code emits one registered `DocumentConverted` per DN (`DeliveryNoteToInvoiceConverter.php:232-238`; `DomainEventSubscriber.php:381-401,1088`), while P0-3 substantially rewrites the transaction. **Required fix:** add a production-entry test asserting N events and N durable audit records with the same target invoice, distinct source DNs, and consolidation metadata; assert zero survive any rolled-back batch. This keeps the build within ES-31 without accidentally regressing the already-correct event surface (`00-CONSOLIDATED-REGISTER.md:97`).

11. **Legacy classification and migration failure policy are not proven.** The spec defaults every stamped row lacking `invoiced_via` to `consolidation` (`SPEC...md:310-314`), but current code only proves present-day writers: SO and guided delivery stamp explicit lanes (`SalesOrderToInvoiceConverter.php:457-461`; `InvoiceController.php:1000-1015`) while consolidation omits one (`DeliveryNoteToInvoiceConverter.php:327-332`). That does not prove the history of all legacy rows. **Required fix:** either demonstrate a reliable backfill discriminator, introduce an honest `legacy_unknown` lane, or document an owner-approved lossy classification. Before enforcing invoice/DN FKs, report and define handling for stamped rows with missing/cross-company invoice ids; do not let a surprise orphan turn the deploy migration into an unexplained fleet-wide stop.

12. **Two factual corrections must be folded into the spec before dispatch.** The explicit-JSON-null rationale is false (Laravel compiles the single arm to `payload->>'invoiced_at' is null`: `PostgresGrammar.php:706-720`; `Grammar.php:417-420`), and Update validation is already optional (`UpdatePartnerRequest.php:97-102`). **Required fix:** retain predicate-parity tests but describe the production SQL accurately; remove the nonexistent Update `required_if` task. Also change “only role that can open lane separation” to “the specialized accountant role”: admin has every permission (`RolesAndPermissionsSeeder.php:516-517,530-532`).

## 4. Design-challenge outcomes

### P0-3 soundness and minimality

The dedicated marker table is a valid relational way to express “one winning invoice per DN”: `delivery_note_id` as the PK/unique key is the right key, while unique `invoice_id` would reject legitimate many-DN consolidation (`DeliveryNoteToInvoiceConverter.php:188-224`). It is not sound as currently composed because the SO collision is deliberately ignored after invoice construction (`SalesOrderToInvoiceConverter.php:167-204,449-461`). It is also not minimal: a shared conditional claim update checked inside every invoice transaction can prevent a losing invoice without a second representation. Keeping both CAS and marker is defensible for a fiscal workflow only if the marker insert result is decisive in every lane and one service owns the dual write; an integrity test alone does not enforce that runtime discipline (`SPEC...md:201-203,366-368`).

### Deadlock analysis

`orderBy('id')->lockForUpdate()` materially reduces deadlock risk between two consolidation requests, but only when every contender takes those rows in the same order (`SPEC...md:153-165`). A concrete remaining AB/BA cycle exists with SO conversion: consolidation can hold DN rows and wait for the invoice sequence, while SO holds the invoice sequence and later waits to update/claim those DNs (`DocumentNumberingService.php:44-64`; `SalesOrderToInvoiceConverter.php:167-204`; `DeliveryNoteToInvoiceConverter.php:177-218`). Sorting only the consolidation query does not fix that. Guided pre-post delivery locks its existing invoice and creates a fresh DN, so it does not normally contend on an existing claimable DN (`InvoiceController.php:908-928,971-1015`). DN confirmation locks a DN and then the fiscal-chain head (`DeliveryNoteController.php:307-331`; `DeliveryNoteService.php:99-108`); because consolidation accepts confirmed DNs, no unavoidable same-row cycle is evident there, but the implementation must still document the global lock inventory and apply finite deadlock retry policy.

### Event boundary

The events-register boundary is currently honored: one `DocumentConverted` is emitted per DN, the consumer is registered, and ES-31 explicitly says that surface is correct (`DeliveryNoteToInvoiceConverter.php:232-238`; `DomainEventSubscriber.php:372-401,1088`; `00-CONSOLIDATED-REGISTER.md:97`). P0-3 should preserve that loop after all claims succeed and before commit, with the rollback regression in Defect 10. No new or renamed event is warranted.

## 5. Implementability

As written, a Codex builder would have to invent decisions in four load-bearing places: the losing SO lane, the global lock order, the queue's lazy API shape/location semantics, and the FE module-gating mechanism. The milestone table also demands an endpoint in M1 that it assigns to M3 (`SPEC...md:358-369,425-432`), and View A2 requests a monetary aggregate that its endpoint does not return (`:248-252`; `PaginatesResults.php:77-94`). Those are dispatch blockers.

The grants table is otherwise evidence-based: the current role permissions match the seeder (`RolesAndPermissionsSeeder.php:638-700,739-804`). Keep only the accountant read grant as an owner choice; the queue for already-authorized `deliveries.view` roles is part of the approved build and should not wait on that choice (`OWNER-DECISIONS-ui-audit-2026-08-10.md:54-60`). OI-4 through OI-7 are honest follow-ons. OI-2 and OI-3 can be closed unless the owner expressly reopens them: “approved as proposed” ratified the research proposal that deletes the old route after Views 1+2 and recommends the 30/60/90/90+ buckets (`13-research-dn-consolidation-ux.md:155-185,253-273`; `OWNER-DECISIONS...md:54-60`).

After the required corrections, the sequence is implementable as: M1 shared eligibility/projection + real route/module authorization + shared DN-claim protocol and migrations; M2 partner tab/balance line/lane link; M3 specified queue contract/UI; M4 retirement and frequency-copy cleanup. Retirement remains strictly after M2+M3 (`SPEC...md:425-434`).

## 6. Residual risk

Even after correction, legacy payload/marker reconciliation and cross-lane SO semantics remain the one-line residual risk: prove both on real PostgreSQL before exposing any billing action.
