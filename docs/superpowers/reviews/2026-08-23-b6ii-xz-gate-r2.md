```

tax_amount 10.00  / table 10.01  (1 ulp @scale 2)               → hasRefundVat false, isReconciled FALSE  (warns)

```

- **Sub-resolution wedges do not warn** (row 3): both figures are `bcformat`-ed to the currency
  scale before the comparison, so anything finer than 1 ulp is annihilated. Only a **≥ 1 ulp**
  negative wedge warns.
- **Is a ≥1-ulp negative wedge reachable on a legitimate sealed Z? No — and here is why, from the
  writer, not from memory.** `salesVat` is `Σ receipt.tax_amount` over sale rows
  (`zReportService.ts:960`, `endOfDayPreview.ts:294`, `reportApi.ts:583`), and
  `receipt.tax_amount` is itself `Σ item.tax_amount` over exactly the cart items whose per-line
  `tax_amount` is written into `lines` JSON — `computeLineTotals()`
  (`apps/pos/src/lib/offline/receiptService.ts:144-157`) then `receiptService.ts:547-548` emits
  `subtotal`/`tax_amount` and the same items as `lines[].tax_amount`. So the receipt-level and
  line-level sale VAT are the **same sum**, at the same scale, with no independent rounding step to
  drift. The refund contribution is `bcabs`-then-subtract on the two signed surfaces
  (`zReportService.ts:872-874`, `reportApi.ts:541-543`), so it can only make the wedge **more**
  positive. Wedge < 0 therefore requires a corpus anomaly — which is exactly what the warning
  claims. Independently: the F-4 server tripwire refuses a refund-free Z whose
  `Σ vat_amount != tax_amount` at all, so such a Z cannot be sealed. **No cry-wolf.**
- **Row 1 (negative accumulator) is a latent typing hole, not a live bug.** The only producer of
  `refund_vat_amount` is `endOfDayPreview.ts:378` (`bcabs`-then-add) and `:611`
  (`bcformat`), so a negative value cannot occur today; if one ever did, the component would render
  `--2.00` and call it reconciled. Recorded as r2-3 (Minor).
- **Row 6 (empty breakdown) is the mirror asymmetry.** A positive wedge is presented as a confident
  "VAT on refunds" figure with no `refunds_count` cross-check, where a negative wedge gets a
  warning. Both require corrupt data (missing/truncated `lines` JSON); recorded as r2-4 (Minor).

**1d. Docblock precision — the parent brief's own framing needs correcting.** The commit message and
`vatDisclosure.ts:55` say `isReconciled` "is computed from the RAW wedge". Literally it is not:
`:140` is still `bccomp(bcsub(salesVat, refundVat, scale), netVat) === 0`. In the **wedge path** that
expression is *equivalent* to `wedge >= 0` (I verified all three branches), so the behaviour claim
is sound — but the stronger claim at `:69`, "**INDEPENDENT of** `hasRefundVat`", is only true when an
authoritative accumulator is supplied; on the signed X/Z surfaces `!isReconciled ⟹ !hasRefundVat`
still holds algebraically. The nuance IS stated correctly 27 lines later (`:96-98`) and in the
inline comment at `:136-139`, so this is a locally-overstated sentence, not a false model. What
actually made case (c) reachable is the **consumer guard**, and the file says so at
`VatDisclosureSummary.tsx:57-62`. Recorded as r2-2 (Minor, doc precision).

### r2-1 — [Important, comment-only] The EOD legacy-refund asymmetry cites a safety net that **cannot fire for the case it names**.

**File:** `apps/pos/src/lib/offline/endOfDayPreview.ts:560-565`

```
// NOT folded into `refundVatAmount`: … on a mixed shift it
// under-reports refund VAT — which `isReconciled` then reports honestly
// rather than hiding, because the signed table and the accumulator will
// disagree.
```

They will **not** disagree. On a mixed-era shift the legacy refund is invisible to *both* sources in
exactly the same way: `vat_breakdown` is built only from the `offline_receipts` loop
(`:351-395`), which a legacy refund never enters (`:503-512`), and `refundVatAmount` is accumulated
only inside that same loop (`:378`). So `wedge == refundVatAmount == v4-only`, `isReconciled` comes
out **true**, and the screen shows "Refunds: 2 / 45.00" beside a refund-VAT figure covering one of
them, silently. The under-report itself is correctly disclosed one clause earlier; only the "which
`isReconciled` then reports honestly" claim is false.

**Why it matters:** this round exists because r1 found an honesty mechanism advertised in comments
that could not fire. This is a smaller instance of the same class, in the file that documents it —
and a future reader will trust the sentence and skip building the disclosure that is actually
missing. The shipped UI is not wrong (the tile is now complete, and the VAT table genuinely contains
no legacy VAT to show), so this is not a merge blocker.

**Fix (comment-only, parent-verifiable at merge):** replace the causal clause with the truth — e.g.
*"…on a mixed shift it under-reports refund VAT, and `isReconciled` will NOT catch it: both the
per-rate table and this accumulator are built from the same `offline_receipts` loop, so both are
blind to a legacy record in the same way. The refunds tile above is the only surface that shows the
legacy refund at all. Recorded as a residual of the §9.3 coexistence window."*
