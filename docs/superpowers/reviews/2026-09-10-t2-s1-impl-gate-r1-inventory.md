### MAJOR

**M-1 — Spec invariant I7 is violated on a cancelled transfer: `freight_uncapitalized` stays 0 although nothing was capitalised.**
What: freight is only ever written by `StockTransferReceiptService::capitalizeFreight()` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferReceiptService.php:478-495`), reached only from `post()` under `if ($transfer->status->isTerminal())` (`:403-405`). `StockTransferService::cancel()` (`:394-420`) writes `status = Cancelled` and never touches `freight_uncapitalized`, which keeps its column default `0` (`2026_09_09_100200_add_close_columns_to_stock_transfers.php:25`).
Why it matters: spec rev 11 states I7 as `transfer_cost = Σ lines.allocated_transfer_cost + freight_uncapitalized` **"at 4 dp on every terminal transfer"** (`docs/superpowers/specs/2026-09-09-transfer-destination-receipt-and-blind-receiving-design-rev-11.md:172`), and S1's own `TransferStatus::isTerminal()` includes `Cancelled` (`apps/api/app/Modules/Inventory/Domain/Enums/TransferStatus.php:60-66`). Any consumer that reads the new column as "freight that was never capitalised" — S4's reconciliation panel, the header events, future cost reporting — under-reports uncapitalised freight by the whole `transfer_cost` on every cancelled transfer with a non-zero freight.
Failing scenario (empirically reproduced by the reviewer, then removed): initiate 10 units with `transfer_cost = 140.0000`, `POST /cancel` → `status = cancelled`, `Σ allocated_transfer_cost + freight_uncapitalized = 0.0000`, expected `140.0000`. Assertion output: `-'140.0000' / +'0.0000'`.
Minimum fix: in `cancel()`, after the terminal status write, set `$transfer->freight_uncapitalized = $transfer->transfer_cost;` (nothing was capitalised, so this is exact at 4 dp by construction) and pin it with a test case in `StockTransferCloseTest` or `InventoryTransferServiceTest`. `StockTransferService.php` is already in S1's declared modify list (plan §7.2), so no scope expansion is needed. If the orchestrator instead rules that I7 is scoped to `completed`/`closed_*` only, amend spec `:172` and plan §7.11 to say so and add a test pinning `0.0000` on cancel as intentional.

**M-2 — S1 makes three new transfer statuses reachable on live, unflagged routes while the only shipped operator surface can neither label nor act on them; a `partially_received` transfer is a web dead end.**
What: `POST /stock-transfers/{id}/receive` and `/close` ship unflagged (`apps/api/app/Modules/Inventory/Presentation/routes.php:108-126`) behind `inventory.transfers.complete` and the newly seeded `inventory.transfers.reconcile` + `inventory.transfers.close`, both granted to manager and admin (`apps/api/database/seeders/RolesAndPermissionsSeeder.php:201-202`, `:604`). The generated union now has seven members (`packages/shared/types/generated.d.ts:1453`), but the shipped web feature still carries a hand-rolled four-member union — `apps/web/src/features/stock-transfers/types/index.ts:12` (`'draft' | 'in_transit' | 'completed' | 'cancelled'`), whose own header comment already concedes it must be replaced by generated output. Consequences on the live surface: `apps/web/src/features/stock-transfers/components/StockTransferStatusBadge.tsx:5-10` has no `statusVariant` entry for the three new values, so `<Badge variant={undefined}>` renders with a missing `status.partially_received` key (no such key exists in the `stock-transfers` namespace — the `partially_received` hits are `sales.json`, the purchase-order concept); `apps/web/src/features/stock-transfers/pages/StockTransferListPage.tsx:15-21` cannot filter them; and `apps/web/src/features/stock-transfers/pages/StockTransferDetailPage.tsx:38-39` computes `canComplete = status === 'in_transit'`, so the Complete button disappears for a `partially_received` transfer while `canBeCancelled()` correctly refuses cancel (`TransferStatus.php:74-77`) and no Close button exists until S4.
Why it matters: after this slice merges and `tenants:migrate` + the seeder run, one API-posted partial receipt strands a transfer's remainder in a state that the shipped web UI can neither name nor terminate — the remainder stays in `CARRYING_STATUSES`, so it keeps inflating every "incoming" reader and the WAC denominator indefinitely. Convention 11 also names exactly this shape: a hand-rolled FE type shadowing a generated DTO is an undeclared second surface, and plan §15 does not list the web status-representation gap among the boundaries deferred to later lanes.
Minimum fix (orchestrator decision, since §2.3 forbids web edits in S1): (a) permit the three-line widening in S1 — add the three members to `types/index.ts:12`, three `statusVariant` rows, three `stock-transfers` i18n keys, and `canComplete = status === 'in_transit' || status === 'partially_received'`; or (b) keep S1 backend-only and gate `receive`/`close` (route flag or withheld permissions) until S4 ships the surface; or (c) record it explicitly in `docs/handoff/PROMOTION-CHECKLIST-2026-09-09-t2t3.md` as a disclosed pre-S4 residual with an operator instruction not to use `POST /receive` before S4. Option (c) alone leaves the live-route hazard in place.

### MINOR

**I-1 — Money scaled by the quantity-scale constant, and truncation rather than HALF-UP at the persistence boundary.** `StockTransferReceiptService.php:489-490` computes and persists the freight pool and residual with `QuantityScale::SCALE` as the scale of a MONEY value, and `StockTransferMovementSupport.php:138,147,148,150` does the same for `allocated_transfer_cost`. Numerically 4 = 4 and the I7 identity is exact by construction, but the constant is semantically wrong for money (contrast `CurrencyScale`), and `bcmul` truncates where the precision contract asks for one HALF-UP rounding at the boundary — every truncated millième silently migrates into `freight_uncapitalized`. Fix: introduce a named 4-dp money constant for these columns (or `CurrencyScale::bcformatStrict` at the persist step) and state the truncation direction in the code comment.

**I-2 — Receipt-line DTOs emit raw scale-4 quantities with no unit-precision hint.** `StockTransferReceiptLineData.php:29-31`, `TransferCloseLineData.php:28-32` and the `TransferReconciliationSummaryData` totals built at `TransferReconciliationService.php:98` carry `quantity_*` strings at scale 4, whereas `StockTransferLineData.php:43,67` carries `quantity_decimals` and `TransferReconciliationLineData.php:31` carries `unit_decimal_places` (the established precedent is `StockAdjustmentLineData.php:19-20,43`).
