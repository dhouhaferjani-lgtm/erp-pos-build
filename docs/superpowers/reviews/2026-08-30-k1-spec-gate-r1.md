## Findings

### K1-S1-01 [BLOCKER] Task 3(c) mandates a reversal/repost service pair that does not exist
`docs/.../LANE-K1-...BRIEF.md:26` — *"re-derives the GL + VAT-snapshot rows via the existing reversal/repost services"*.
The only document-GL reversal is `Accounting/Application/Services/AccountingService.php:995 reverseDocumentGl(Document)`. Its own docblock `:983-987` states it is **idempotent once**, "keyed on `source_type = DOCUMENT_CANCELLATION_SOURCE_TYPE` + `source_id`" — i.e. it *means* "this document was cancelled", not "this document was corrected" — and `:996-998` returns `null` for anything other than Invoice/CreditNote. **There is no repost counterpart**: `DocumentPostingService::post()` is a draft→posted transition, not a re-derivation of an already-posted document.
The remedy that DOES exist under document-per-action is the **correcting-entry DOCUMENT** linked via `source_document_id`, described in `Accounting/Domain/Exceptions/UnreversibleDocumentGlException.php:31-38` and pinned by `CorrectingEntryUnblocksCancellationTest`.
*Why it matters:* an unattended Codex lane told to use non-existent services in posted-GL territory will either invent a raw path (the brief's own prohibition, `:26` "no raw UPDATE on posted GL") or mis-use `reverseDocumentGl` and stamp real invoices as cancelled.
*Fix before dispatch:* name the correcting-entry document path explicitly, or (preferred, matching the brief's own stock decision) make **Task 3(c) REPORT-ONLY for GL and VAT** and route the money correction to an owner decision. Add: a document in a closed fiscal period cannot be re-derived at all — that subset is report-only by construction.

### K1-S1-02 [BLOCKER] The fix makes replayed pre-fix ACCOUNT_CHARGE events dead-letter

### K1-S1-03 [BLOCKER] `unit_price` on the account-charge document line is TTC — fixing only `line_total` does not fix the tax base
`apps/pos/src/lib/accountCharge/accountChargeCartMapper.ts:74` — `unitPrice: bcformat(item.unit_price, scale), // gross / tax-inclusive, verbatim`. `POSAccountChargeDraftService.php:88` copies that TTC value straight into `document_lines.unit_price`.
The shared document engine treats that column as **net/HT** and *recomputes* from it:
- `Document/Domain/Services/DocumentTotalsCalculator.php:43` — `$lineSubtotal = $line->calculateTotal($scale)` (= qty×unit_price − discount);
- `Taxation/Domain/Services/TaxCalculationService.php:363-368` — same call, explicitly *"NET line … is the taxable base"*;
- `Document/Presentation/Controllers/InvoiceController.php:652` snapshots the **sales** VAT declaration from that recomputation.
Today the two are accidentally congruent (both gross). After Task 1.1 the stored `line_total` is net while every recomputing reader still returns gross: the VAT snapshot is still taken on a **TTC base**, the header subtotal diverges from Σ `line_total`, and `AccountingService.php:378-390` (`residual = arFacingTotal − (revenue+vat)`) can flip sign and refuse the posting. The brief says nothing about `unit_price` at all.
*Why it matters:* the lane's headline claim — "VAT leg = net×rate, no VAT-on-VAT" — is only true for the `AccountingService` arm and remains false for the declaration arm. Precision contract §`unit_price` (`docs/architecture/precision-contract.md:192-205`) is the governing document and it explicitly warns this field is context-overloaded.
*Fix before dispatch:* an explicit owner ruling in the brief on what the POS account-charge line writes into `document_lines.unit_price` (recommended: the derived **net** unit price, keeping the TTC cart price only in the canonical payload snapshot, since `documents` is a B2B surface), plus a test asserting the *recomputed* subtotal equals Σ stored `line_total`.

### K1-S1-05 [MAJOR] There is no SALE_RECEIPT-style replay guard in the account-charge projector to "mirror"
Brief `:22` — *"mirror the SALE_RECEIPT replay guards"*. The SALE_RECEIPT guard is: `DB::transaction` (`PosCoreReceiptProjection.php:252`) → `$insertedId = $this->insertReceiptOnConflictDoNothing($row); if ($insertedId === null) { return; }` (`:462-466`) → **every** subsequent write (lines, VAT, payments, loyalty, `applyStockMovementForLines`, vouchers) gated behind that anchor.
`AccountChargeReceiptProjection::apply()` (`:47-71`) has **no `DB::transaction` at all**, and `insertOnFiscalEventConflictDoNothing()` (`:75-93`) uses `DB::affectingStatement` but **discards the return value**. The fast-path probe at `:49` is not a race guard. Adding stock writes there as-is = **double decrement on concurrent redelivery** (Critical class per rule 20).
*Fix before dispatch:* the brief must require the anchor be built (wrap in a transaction; return and check the affected-rows count; gate the stock write on it), not "mirrored".
