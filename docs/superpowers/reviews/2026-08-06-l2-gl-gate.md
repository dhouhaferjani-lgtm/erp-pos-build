## FINDINGS

### [IMPORTANT] I-1 — Two concurrent cancels can DOUBLE-REVERSE the ledger
`apps/api/app/Modules/Accounting/Application/Services/AccountingService.php:719-727` (idempotence is an `exists()` probe, not a lock) + `apps/api/app/Modules/Document/Domain/Services/DocumentPostingService.php:149-155` (`$document->refresh()` is a plain SELECT — no `lockForUpdate`, no row lock taken until `:185`).
Under READ COMMITTED the interleaving `txn2.exists()→false` → `txn1 commit` → `txn2.getNextChainSequence()` (now sees txn1's row, allocates N+1) → `txn2 insert` succeeds. Two reversals for one document ⇒ revenue and AR credited twice ⇒ **wrong money in the GL and in `partners.receivable_balance`**.
Two unique indexes only *incidentally* narrow the window: `unique(tenant_id, entry_number)` (`2025_11_30_100000_create_journal_entries_table.php:40`) collides only if both land in the **same second** (`entry_number` = `REVCAN-<YmdHis>-<uuid>`, `AccountingService.php:803`), and `uniq_je_company_chain_sequence` (`2026_07_08_100400_...:36-40`) collides only if both allocate the **same** sequence. The interleaving above defeats both.
**Fix:** take the document row lock at the top of `cancel()`'s transaction (`Document::whereKey($document->id)->lockForUpdate()->firstOrFail()`), and/or add a partial unique index on `journal_entries (company_id, source_id) WHERE source_type = 'DocumentCancellation'` — the same backstop the codebase already uses for treasury transfers and procurement (`2026_07_12_100000_unique_journal_entries_source_treasury_transfer.php`).

### [IMPORTANT] I-2 — `balanceAssertable` is a parallel reimplementation of L1's predicate, derived from mutable document state
`AccountingService.php:788` (`$document->lines->isNotEmpty()`) duplicates the L1 predicate at `:147` (`$document->lines->isEmpty()`). Two independent expressions of one fiscal invariant is exactly the drift class L1's own DTO comment warns about ("Deriving the numbers separately is how the two could drift", `:106-107`).
Worse, it asks the question of the **current document** rather than of the **sealed entry**: any state where a posted document has zero lines flips the DOC06 refusal OFF and mints a mirror of an unbalanced entry — precisely what `UnreversibleDocumentGlException` exists to prevent. Not reachable through the documented API today (`InvoiceController.php:400` refuses edits to non-editable documents; `DocumentLine` has no soft deletes and no immutability trigger), so this is a latent, not live, bypass.
**Fix (one line):** `$balanceAssertable = $this->residualPlan($document, $scale)->balanceAssertable;` — literally L1's predicate, single source. Stronger: derive it from the sealed entry (a single leg with no counterpart) so the reversal never depends on post-seal document mutability.

### [IMPORTANT] I-3 — Reversing the VAT leg silently desynchronises the GL from the VAT declaration
The VAT declaration aggregates `document_tax_details` joined to `documents` on **`d.document_date`** with **no status filter** (`apps/api/app/Modules/Taxation/Infrastructure/Repositories/EloquentVatDataRepository.php:30-44`), and journal entries never enter that aggregation. After this lane, cancelling a January invoice in March debits 4457 in **March's GL** while **January's declared output VAT is unchanged** and March's declaration sees nothing. Cumulative GL VAT-collected and cumulative declared VAT now disagree by the cancelled amount, permanently, with no reconciliation surface. Before this lane cancel wrote no GL, so the two agreed (both wrong in the same direction).
`vat_periods` already carries `OPEN/CLOSED/FILED` + `closed_at`/`filed_at` (`database/migrations/tenant/2026_03_23_200000_create_vat_periods_table.php:21,33-36`; transitions in `VatPeriodManagementService.php:103,181`) but **nothing consults it on cancel**.
**Fix / ruling needed:** ticket the GL↔declaration reconciliation, and block cancellation (require a credit note instead) once the document's VAT period is CLOSED or FILED — see ruling 6a.

### [IMPORTANT] I-4 — The reversal is scoped to `source_type='Document'`; the same document's COGS entry is left standing
`AccountingService.php:730-733` filters `source_type = 'Document'`. In production a posted sales invoice with physical lines ALSO writes a COGS entry keyed on the **same** `source_id` with `source_type='cogs'` (`apps/api/app/Modules/Inventory/Listeners/PostCOGSOnInvoice.php:73-80` → `GeneralLedgerService::createCOGSEntry`, `GeneralLedgerService.php:1667-1677`). Cancel does not restock (no listener is registered for `InvoiceCancelled` in `EventServiceProvider`; only the Compliance audit subscriber handles it, `DomainEventSubscriber.php:1073`), so leaving the inventory credit is internally consistent — but the resulting ledger books **COGS with zero revenue** on every cancelled invoice, and the interface docblock promises to "reverse a document's GL" without qualification (`app/Shared/Contracts/Accounting/DocumentGlReversalInterface.php:10-24`).
**Fix:** narrow the contract wording to "the document-sourced sales entry" and raise a ticket for the COGS/stock disposition on cancel, or extend the mirror to all entries keyed on the document.

### [IMPORTANT] I-5 — The reversal seals its hash with a no-arg `getScale()` while `verifyChain()` uses the explicit currency
`AccountingService.php:846` calls `calculateHash($freshEntry, $previousHash)` with no `$currencyCode`, so `GeneralLedgerHashService::serializeForHashing()` falls to `$this->scale()` → `scaleResolver->getScale()` with no argument (`GeneralLedgerHashService.php:31-33,74-77`). `verifyChain()` always passes the company currency (`:99-100,126`). Those two are **not the same function**: no-arg resolves from the country row's `currency_decimal_places` (`app/Shared/Infrastructure/CurrencyScaleResolver.php:43-63`), the explicit path uses the static ISO map (`:39-41`). If they ever differ for a company, every entry fails verification. The no-arg call also **throws** outside request context (`CurrencyScaleResolver.php:45-52`) — rule 20.
Inherited from the posting paths (`:641` does the same), so not a regression — but this is brand-new code written after L1's "pass the currency" doctrine, with `$document->currency` in hand (`documentScale()` already uses `getScaleSafe($document->currency, 3)` at `:66-69`).
**Fix:** `calculateHash($freshEntry, $previousHash, $document->currency)`; ticket the two pre-existing sites.

## RULINGS

### 6a — `entry_date = now()` vs the invoice date: **now() is CORRECT. Keep it.**
There is no fiscal-period lock on journal entries, but the period abstractions that matter **do** exist and are stateful: `vat_periods` carries `OPEN → CLOSED → FILED` with `closed_at`/`filed_at`/`filing_reference` (`2026_03_23_200000_create_vat_periods_table.php:21,33-36`, transitions at `VatPeriodManagementService.php:103,181`), and every GL report slices on `journal_entries.entry_date` (`GeneralLedgerReportService.php:208-211,269,296`). Back-dating the reversal to the invoice date would retroactively rewrite a January that may already be CLOSED or FILED — trial balance, P&L and the VAT-payable GL balance for a declared period would change under a filed declaration. That is the one outcome a compliance-ready ledger must never produce. `now()` puts the correction in the period the withdrawal actually happened in, which is also the house pattern for the only comparable existing mirror (`GeneralLedgerService::reverseInventoryWriteOffEntry`, `:4409`).
**Two conditions attach to this ruling:**
1. Fix I-3 — with `now()` dating, the GL and the VAT declaration now disagree for any cancelled invoice. Ticket it.
2. The deeper instrument question: in FR/TN, an invoice whose VAT period is already CLOSED/FILED is not cancelled at all — it is credited (avoir). Cancel should be **refused** once `vat_periods.status != OPEN` for the document's `document_date`, pointing the user at a credit note. That refusal is out of this lane's scope but belongs on the same ticket, and it is what makes `now()` dating unambiguously safe.

### 6b — `entryType = 'document_cancellation'` on `JournalEntryCreated`: **no breakage. Approved.**
Sweep result: `JournalEntryCreated` has exactly one consumer, `Compliance\Listeners\DomainEventSubscriber::handleJournalEntryCreated` (`:83-93`, wired at `:1068`), which writes `entry_type` into an opaque audit payload (`Events/JournalEntryCreated.php:52-59`) and branches on nothing. No `$listen` entry, no wildcard listener, no other `entryType` consumer anywhere in `app/` (grep confirmed: the only other `entry_type` hits are Workshop's unrelated `TimeEntryType`). `source_type='DocumentCancellation'` is likewise consumed by nobody — no production query filters `journal_entries.source_type = 'Document'` outside the new constant, and all GL/trial-balance reports read `journal_lines` joined on status+date, so the reversal is picked up automatically.
Nit only: `'document_cancellation'` is a magic string, exactly like the existing `'invoice'`/`'credit_note'`. Acceptable as consistent debt; if `entryType` ever becomes a discriminator, promote all three to an enum (rule 9) in one go.

### 6c — SupplierInvoice out of scope: **confirmed no reversal fires; leaving AP unreversed is NOT coherent. Accept the exclusion, require a ticket before merge.**
Two independent guards keep supplier invoices out: `reverseDocumentGl()` returns `null` for any type other than `Invoice`/`CreditNote` (`AccountingService.php:717-719`), and `cancel()` never even calls it because `requiresFiscalChain()` matches only those two types (`DocumentPostingService.php:41-47,510-513`, and the non-fiscal branch at `:189-191` just updates status). Verified: there is no other supplier-invoice cancellation path (`grep SupplierInvoice … | grep -i cancel` → nothing).
But the AP side has the identical defect the lane just fixed on AR: a posted supplier invoice writes AP + expense + deductible VAT (`GeneralLedgerService.php:645-655`, `source_type='supplier_invoice'`), and cancelling it via `DocumentPostingService::cancel()` leaves all of it standing — plus the input VAT stays declared. Calling it "out of scope" is right for *this* lane (it would double the blast radius under a merge gate); calling it "coherent" is not. **Required before merge: a ticket referencing `DocumentPostingService.php:189-191` and `GeneralLedgerService.php:645-655`, so the AP gap is recorded rather than implied to be intentional.**
