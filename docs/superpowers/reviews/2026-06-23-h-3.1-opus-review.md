# H-3.1 Supplier Payment Posting — Opus Adversarial Review

Date: 2026-06-23
Reviewer: Opus 4.8 (adversarial cross-model review; prior reviews were Codex + Codex-fallback only)
Commit: `407cea426` — "Phase 0.1.13: Post supplier payment GL entries"
Item: H-3.1 (work-list `docs/superpowers/audits/2026-06-22-balance-conventions-audit/work-list.md`)

## Summary

The patch makes `PaymentController::store()` recognise purchase-order allocations as an outgoing
`SupplierPayment`, posts a partner-tagged `supplier_payment` journal entry
(Dr SupplierPayable / Cr Bank), decreases the selected repository balance, and rejects (a)
mixed PO/customer allocations and (b) supplier payments that leave unallocated excess. The
double-entry, sign conventions, money/precision handling, and PHPStan L8 all hold up under
refutation, and the two new tests pass and are meaningful for what they assert.

The implementation is directionally correct and the core fiscal mechanics are sound. However it
falls short of the stated H-3 acceptance criteria in two ways: (1) there is **no guard that the
payment's `partner_id` matches the allocated document's `partner_id`**, so the new SupplierPayable
subledger can be tagged to the wrong partner; and (2) the acceptance criteria explicitly require
"`partners.payable_balance` updates" and "idempotency are covered" — neither is exercised by an
H-3.1 test, and there is no end-to-end test that a supplier invoice credit followed by this payment
debit nets `payable_balance` back to zero. These are gaps against the criteria, not fiscal-math
errors, so the verdict is APPROVE-WITH-MINOR-EDITS with one HIGH to address as follow-up coverage.

Verified: `php artisan test --filter 'purchase_order_payment'` → 2 passed (15 assertions);
PHPStan L8 on both changed app files → No errors.

## BLOCKER

None. No float touches money/quantity; `bcsub`/`bcadd` with the injected
`CurrencyScaleResolverInterface` scale throughout; no `(float)` cast or `number_format` on money;
double-entry is balanced (Dr SupplierPayable = Cr Bank = `$totalAllocatedForGL`); the
SupplierPayable line is partner-tagged and the Bank line is partnerless (correct subledger shape).
The full-allocation guard (`SUPPLIER_PAYMENT_REQUIRES_FULL_ALLOCATION`) is load-bearing and holds:
combined with the pre-existing `ALLOCATION_EXCEEDS_PAYMENT` check and the per-document balance cap,
it forces `totalAllocatedForGL == paymentAmount` for supplier payments, so the GL bank credit
always equals the repository decrease — no orphan cash delta. No event was renamed/restructured;
hash-chain posting path is unchanged.

## HIGH

### H1 — No check that payment `partner_id` matches the allocated document's `partner_id` (AP subledger mis-tag)

`PaymentController::store()` tags the SupplierPayable GL line and the payment with the
request-supplied `$validated['partner_id']` (PaymentController.php:426 `partnerId: $validated['partner_id']`),
while the allocated document is fetched and balance-reduced purely by `document_id` scoped to
tenant/company (PaymentController.php:181-185, 316-345). There is **no assertion that
`$document->partner_id === $validated['partner_id']`** (grep of all `partner_id` usages confirms the
two are never cross-checked). A caller can pay supplier B's purchase order while passing supplier
A's `partner_id`: the SupplierPayable debit lands on supplier A's subledger (clamping to zero via
`liabilityMagnitude` and logging a warning if A has no credit), supplier B's PO `balance_due` is
reduced, and the AP subledger diverges from both the documents and the control account.

This bug shape pre-exists on the AR/customer path, but H-3.1 is the commit that makes the
SupplierPayable subledger live and makes `PartnerBalanceService::reconcileSubledger()` depend on
partner-tag accuracy for AP. The new test only exercises the matching-partner happy path
(`$supplier` is both the PO partner and the payment partner), so the mismatch path is unguarded and
untested. Recommend rejecting an allocation whose `document.partner_id` differs from the payment
`partner_id` (a single 422 in the existing allocation loop), and adding a red-first test.

## MEDIUM

### M1 — Acceptance criterion "`partners.payable_balance` updates" is not tested in H-3.1, and the AP round-trip is never tested end-to-end

The work-list acceptance criteria for H-3 require "`partners.payable_balance` updates." The new
`test_purchase_order_payment_posts_supplier_payment_gl` asserts the journal-line shape, the
repository balance (`400.000`), and `JournalEntryStatus::Posted`, but never asserts
`$supplier->payable_balance`. The invoice leg's test in the next commit (`53115efaa`,
`test_confirmation_posts_supplier_invoice_gl_and_refreshes_payable_balance`) asserts payable_balance
on the credit side only. **No test anywhere confirms the interaction**: PO confirmation credits
SupplierPayable (e.g. 1000), then this payment debits it (e.g. 600), netting `payable_balance` to
the expected 400. That round-trip is the actual proof the two legs agree and is the substantive
verification AP needs. Because the H-3.1 PO is built with `Document::create(... status => Confirmed)`
— bypassing the `PurchaseOrderConfirmed` event entirely — the SupplierPayable was never credited in
the test, so the debit produces a net-debit that `liabilityMagnitude` silently clamps to zero. The
test passes anyway only because it never inspects `payable_balance`. Recommend a combined
invoice→payment feature test asserting the netted cached `payable_balance`.

### M2 — Acceptance criterion "idempotency are covered" is unmet

The criteria explicitly call for source-linkage AND idempotency coverage. Source linkage is tested
(`source_type='supplier_payment'`, `source_id=payment_id`). Idempotency is neither tested nor
guarded: nothing prevents two `supplier_payment` journal entries sharing the same `source_id`. In
practice each `store()` mints a fresh `Payment`, so the natural one-payment→one-entry key provides
de-facto protection on this path, but the criterion is not demonstrably met and a future retry/replay
surface would not be caught. Recommend either a documented note that the one-payment-per-entry key is
the idempotency mechanism, or a uniqueness guard + test on `(source_type, source_id)`.

### M3 — Supplier payment with no repository (or a repository without `account_id`) records with zero accounting effect

`repository_id` is `nullable` (PaymentController.php:125-129). A supplier payment created without a
repository, or with a repository whose `account_id` is null, skips both the repository-balance
decrease (guarded by `if ($repositoryId)`, line 374) and the GL posting (guarded by
`$repository->account_id`, line 422). The `SupplierPayment` row is persisted with no SupplierPayable
debit and no cash movement, leaving `payable_balance` stale and the payment fiscally inert. This
mirrors the existing customer-payment behaviour, but for AP it silently breaks the "production
supplier payment posts AP" guarantee whenever the cash source is unconfigured. Consider requiring a
GL-mapped repository for supplier payments, or at minimum documenting the no-op path.

## LOW

### L1 — `RepositoryBalanceChanged.changeAmount` now carries negative values

For supplier payments `changeAmount` is `bcsub('0', $paymentAmount, scale)` (negative). The event is
not consumed by any projector (grep shows only `PaymentController` emits it), and `previousBalance`/
`newBalance` carry the authoritative truth, so this is self-consistent and not an immutability
violation (no rename/restructure). Flagged only so future consumers do not assume a non-negative
delta.

### L2 — Fully-paid purchase order never transitions to `Paid` and emits no `DocumentFullyPaid`

`DocumentType::canTransitionToPaid()` returns true only for Invoice/CreditNote, so a fully-allocated
PO keeps `status = Confirmed` while `balance_due` reaches 0, and `DocumentFullyPaid` never fires for
POs (PaymentController.php:341,348). This appears intentional (PO is not an invoice) and re-payment
is prevented by the balance cap, but the resulting "balance_due 0 / status Confirmed" state is worth
confirming against PO lifecycle expectations.

## Verdict

APPROVE-WITH-MINOR-EDITS

The fiscal core — double-entry, sign conventions, money precision, full-allocation invariant, posted
lifecycle, partner-tagging shape — is correct and PHPStan/test-clean. The merge is not fiscally
unsafe. But H1 (partner-tag mismatch) should be guarded before this AP path is exercised by real
multi-document workflows, and M1/M2 close real gaps against the written acceptance criteria
(payable_balance round-trip + idempotency). None rise to BLOCKER on the isolated H-3.1 slice; H1 is
the one to fix soon.
