## Findings

### [Important] K67-R1-01 — `GET /imports` now hydrates every warning-bearing row of every terminal job on the page
`apps/api/app/Modules/Import/Presentation/Controllers/ImportController.php:92` changed `$this->formatJob($job, false)` → `$this->formatJob($job, $job->status->isTerminal())`, which routes each listed job through `warningSummary()` at `:990-1022`, whose first statement is `$job->rows()->whereNotNull('warnings')->get(['warnings'])` (`:994`) — an unbounded hydration, once per job. `per_page` accepts up to 100 (`:70`) and defaults to 20 (`:80`). A tenant with a handful of 10k-row product imports carrying `sku_generated` / `unit_defaulted` / `location_not_supplied` warnings will hydrate hundreds of thousands of `ImportRow` models on one history page load. The list deliberately skipped this before; `ProductsImportPipelineTest.php:413-436` was edited to assert the new behaviour, confirming the change is intentional but not that it is bounded.
**Why it matters:** the import history page is the durable operator surface C6 chose; it must not degrade with import size. This is invisible to every existing test (all use 1–2 row files) and to the wave-1 browser evidence.
**Fix:** keep the list payload to `enrichment_summary` only, or compute the per-code counts with a SQL aggregate (PG `jsonb_array_elements` + `GROUP BY`, SQLite branch as in `countWarningRows` at `:975-985`), or persist the summary into a column at finalisation and read it back.

### [Important] K67-R1-02 — `$timeout = 3600` on the enrichment job is 40× the queue's `retry_after`
`apps/api/app/Modules/Import/Application/Jobs/EnrichImportedProductsJob.php:38-40` sets `$tries = 1; $timeout = 3600;`. The Redis connection's visibility timeout is `retry_after = 90` (`apps/api/config/queue.php:71`) and the Horizon supervisor's worker timeout is `60` (`apps/api/config/horizon.php:217`). No other job in the repo sets `$timeout` at all. With the C10 budget of 500 sequential lookups — each `timeout(10)` + `connectTimeout(5)` + `retry(3, 200, …)` in `PlatformHttpClient` — exceeding 90 s is the normal case, not the edge. Redis then re-releases the still-running job; the second reservation trips `tries = 1` and is written to `failed_jobs` / Horizon as `MaxAttemptsExceeded` while the first instance keeps going to completion.
**Why it matters:** rule 20's queue-contract class of bug. Every non-trivial enrichment run produces a spurious failed-job alert, and the operator cannot distinguish it from a real failure. (The row-level idempotency guards at `:106-109` and the warning dedup at `:210-214` do prevent double-writes, so this is noise and confusion, not corruption.)
**Fix:** bound one job's runtime under `retry_after` — e.g. process a slice of the barcode budget and re-dispatch a continuation — or raise `REDIS_QUEUE_RETRY_AFTER` above the job timeout and record it as a deploy precondition on the promotion checklist.

### [Important] K67-R1-03 — opting in on a file with no `barcode` column is a completely silent no-op
`apps/web/src/features/import/pages/ImportWizardPage.tsx:378` makes the toggle visible on the tenant capability alone; unlike `prices` (`:381`), `placement` (`:382`) and `stock` (`:383`), it carries no column-mapping predicate. On the backend, `EnrichImportedProductsJob.php:101-104` `continue`s any row whose `data['barcode']` is missing or blank — without a warning, without a counter, without a log line. `storeSummary()` (`:196-205`) then writes `{}`, so the completion screen shows nothing (`ImportWizardPage.tsx:1356`), the history row shows nothing (`ImportHistoryPage.tsx:165-179`), and the result workbook — the operator's only feedback channel — shows nothing (`ResultWorkbookService::formatWarnings`, `:110-123`, renders row warnings only).
**Why it matters:** the operator explicitly asked for enrichment and gets zero feedback that it did not and could not run. This is the "silently dropped feedback" class the workbook rule exists to prevent, and it is the *most likely* real-world configuration (a products file mapped `name,sku,price` with no barcode column).
**Fix (either):** gate `optionVisibility.enrichment` on a mapped `barcode` column (mirroring `:382-383`), **or** have the job record a job-level counter/warning when it finds zero barcode-bearing candidate rows, surfaced the same way as `enrichment_vertical_not_supported`.

### [Minor] K67-R1-04 — the new glossary row overstates the single-surface claim
`docs/glossary.md:42` states "no caller writes a backlink **or dispatches the apply job** independently", but `apps/api/app/Modules/Product/Presentation/Console/RunEnrichmentCommand.php:94-100` dispatches `ApplyCatalogEnrichmentJob` directly, bypassing `CatalogBacklinkDispatcher`. (It re-applies enrichment for already-linked products and writes no backlink, so it is benign — but convention 11 requires the surface to be *declared*, not discovered.)
**Fix:** amend the row to name the re-apply console command as the third, read-only surface, or route it through the dispatcher.

### [Minor] K67-R1-05 — adding a required `tenantId` to `ApplyCatalogEnrichmentJob` breaks payloads already on the queue at deploy
`apps/api/app/Modules/Product/Application/Jobs/ApplyCatalogEnrichmentJob.php:44` adds `public readonly string $tenantId` as a required constructor argument. Jobs serialized before the deploy unserialize without calling the constructor, leaving the readonly property uninitialized; `withTenantContext()` (`:55`) then throws "Typed property must not be accessed before initialization". Low volume (enrichment jobs are short-lived), but it is a real deploy-window hazard.
**Fix:** drain the `enrichment` queue as a promotion step, or make the property nullable with a `$product->tenant_id` fallback.
