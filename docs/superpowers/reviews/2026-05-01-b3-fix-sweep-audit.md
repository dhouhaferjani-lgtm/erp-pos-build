# Verdict

**Minor concerns — no blockers.** The four commits land what they claim. B3 plumbs `instrument_type`, `instrument_serial`, and `payment_method_code` end-to-end through online API → offline POS → sync DTO → server writer, with both-or-neither cross-field validation enforced per-row via `withValidator()` on both the online and sync request validators. Hash stability is preserved (fixture-01 = `4db73253...`, fixture-08 = `100f2395...`, byte-identical TS↔PHP), the v2 hash path is unchanged in both languages (zero-line diff), and all production-path tests pass: 4 online-binding, 2 offline-cutover-sync, 5 V3ReceiptHashComputer, 9 TS canonical parity, 17 receiptService, 38 syncService, 4 v28 migration replay, 8 LedgerHistoryTable. R1, R3, R4 each do exactly what they advertise.

The two minor concerns are: (a) the new offline-cutover voucher sync test pre-computes the expected hash via PHP (`ReceiptFinalizationService::finalize`), not via the actual TS canonicalizer — the implementer acknowledges this in the test header and bridges it through `canonicalPayload.test.ts` fixture-08 parity, which is defensible but means a future TS-only drift in `receiptService.ts`/`syncService.ts` payload shape would not be caught by this test alone; (b) `method_code` is `nullable` rather than `required` on both the sync request validator and the DTO, with a fallback to `PaymentMethod::code` lookup — for any voucher-bearing offline receipt produced by a post-B3 client the field IS sent and the wire roundtrip works, but a stale pre-B3 client could in theory still seal a voucher receipt and push it without `method_code`, which the writer would silently substitute. Neither rises to a blocker since (i) the fallback only ever fires for pre-B3 cash-only queued rows by construction (no pre-B3 voucher tender path existed), and (ii) the server's hash-mismatch guard at `ReceiptSyncService.php:458-464` would catch any case where the substituted `method_code` actually changed the recomputed hash, rolling back the receipt rather than silently accepting bad data.

There is one **outstanding scope gap that is not B3's responsibility but should be tracked**: `paymentStore.voucherTenders` state is wired in (added by `VoucherTenderModal`), but `AdvancedPaymentsModal.tsx:203-209` builds `AdvancedPaymentLine[]` without spreading `instrument_type`/`instrument_serial`, and never merges the voucher-tender state into `processAdvancedCheckout`'s payment array. Combined with `offlineCheckoutService.ts:30-37` whose `CheckoutInput.payments[]` type omits instrument fields entirely (and would strip them in `onlineCheckout` even if present), there is no live UI flow today that produces a voucher tender carrying `instrument_type`/`instrument_serial` into B3's writers. This means B3's plumbing is correct but currently has no production caller exercising it — the production-path proof for voucher binding rests entirely on the `OfflineV3CutoverSyncTest` synthetic payload. Flagging as a Major outstanding item for the next phase, not a B3 blocker.

## Outstanding issues

### Major — `paymentStore.voucherTenders` has no live UI consumer; `AdvancedPaymentsModal` strips instrument fields

**File:** `apps/pos/src/components/organisms/AdvancedPaymentsModal/AdvancedPaymentsModal.tsx:203-209` and `apps/pos/src/lib/offline/offlineCheckoutService.ts:30-37` and `:78-86`.

**What's wrong:** `paymentStore.voucherTenders` state is added by `VoucherTenderModal` but no callsite merges it into `processAdvancedCheckout`'s payment array. `AdvancedPaymentsModal.handleComplete()` builds `AdvancedPaymentLine[]` from local `PaymentLineItem[]` state which has no voucher-instrument fields, and never reads `voucherTenders`. The unused `offlineCheckoutService.ts` (only test callers) similarly drops the fields. So in production, B3's writer plumbing currently has no UI flow producing a voucher-bearing payment with `instrument_type`/`instrument_serial` populated — every live cashier path either omits voucher tenders or strips the fields.

**Why it matters:** B3's stated goal is "voucher-bearing v3 receipts must seal/sync with the instrument identity bound into the hash." The writer plumbing is correct, but without a UI consumer that actually fills the fields, the production-path proof is synthetic. The `OfflineV3CutoverSyncTest` voucher case constructs the payload by hand to exercise the wiring; no real cashier-driven flow does today. This is not a B3 blocker (B3 was scoped to writer plumbing), but it should be tracked as the next-phase wiring gap so a future drift in `AdvancedPaymentsModal` or the introduction of a voucher checkout flow does not re-discover this gap with a sealed receipt that hashes a null serial.

**What would close it:** Wire `voucherTenders` into `processAdvancedCheckout` so each `VoucherTenderRow` maps to an `AdvancedPaymentLine` with `instrument_type: 'store_voucher'` and `instrument_serial: <code>` set. Update `AdvancedPaymentsModal` to either render voucher tender rows from `paymentStore.voucherTenders` alongside its local `paymentLines`, or document the cashier UX path that ferries voucher state into the modal. Add an integration test that exercises a real `processAdvancedCheckout(...)` call with a voucher tender row and asserts the persisted SQLite `payments_json` carries the instrument fields end-to-end.

### Minor — `method_code` is nullable on the sync wire (DTO + validator); should be required

**Files:** `apps/api/app/Modules/POS/Presentation/Requests/SyncReceiptsRequest.php:94` and `apps/api/app/Modules/POS/Application/DTOs/SyncReceiptPayload.php:100`.

**What's wrong:** The audit checklist explicitly called this out: "`method_code` should be REQUIRED on the payload (not nullable). Without it, the server can't recompute the hash with the same `method_code` the POS used." The current rule is `['nullable', 'string', 'max:64']`. The DTO defaults a missing field to `null`. The writer at `ReceiptSyncService.php:426-429` then falls back to a live `payment_methods.code` lookup. The implementer documents the fallback in the comment as a "stale pre-B3 client" path.

**Why it matters in practice — narrowly:** A pre-B3 client (i.e. a Tauri build that predates this commit) could in theory queue a voucher-bearing receipt with no `method_code`. The server would fall back to the live `PaymentMethod::code`. If the live code matches what the client lowercased into the canonical hash input (the typical case for `cash`/`card`/`store_voucher`), the recomputed hash matches and the receipt syncs. If the live code drifted (e.g., a method was renamed between offline-seal and sync), the recomputed hash diverges and the hash-mismatch guard at `ReceiptSyncService.php:458-464` rolls back the transaction with `OfflineFiscalHashMismatchException`. Net effect: the worst case is a sync rejection, not silent corruption. **Combined with the empirical observation that no pre-B3 voucher path existed (voucher tender wiring landed with B3)**, this is at most a minor robustness concern.

**What would close it:** Promote the rule to `['required', 'string', 'max:64']` on `SyncReceiptsRequest` and remove the nullable arm from the DTO. The fallback in `ReceiptSyncService` becomes a never-taken branch and can be deleted with a comment pointing to PR #76. Add a 422 negative-case test at the sync controller level to lock the contract.

### Minor — `OfflineV3CutoverSyncTest` voucher case precomputes the expected hash via PHP, not the TS canonicalizer

**File:** `apps/api/tests/Feature/POS/OfflineV3CutoverSyncTest.php:286-289`.

**What's wrong:** The test calls `ReceiptFinalizationService::finalize()` (PHP server code) on a synthetic in-DB receipt to produce `$expectedHash`, then submits a sync payload with that same hash. The server then re-finalizes the synced receipt, also via PHP server code, and the test asserts the two hashes match. The TS path (`createOfflineReceipt` → `receiptToPayload`) is not executed.

**Why it matters:** The audit checklist flagged exactly this as the "PHP shortcut" risk. The implementer documents it in the test header (lines 48-56) and argues the bridge: `canonicalPayload.test.ts` proves TS=PHP for canonical bytes on fixture-01 (cash) and fixture-08 (voucher). Combined, TS=PHP=PHP, so the implementer's hash assertion is transitively true for any input shape covered by those fixtures. This is defensible. **However**, it does not catch a future drift in the TS-only mappers — if `receiptService.ts:167-173` or `syncService.ts:1191-1211` regress (e.g., dropping a field, changing the lowercase normalization, mismatching the payment-row sort order), the existing tests pass: `canonicalPayload.test.ts` validates the canonicalizer in isolation; `OfflineV3CutoverSyncTest` validates the server end with a hand-built payload. Nothing today exercises the TS production code paths against the real wire.

**What would close it:** Add a Vitest integration test (or a Playwright/E2E test) that calls `createOfflineReceipt(...)` and `receiptToPayload(...)` with a voucher-bearing input, captures the produced payload, and asserts byte-equality against the corresponding PHP `CanonicalPayloadBuilder` output for the same input. The receiptService self-consistency test at `receiptService.test.ts:470-541` is most of the way there but stops at the hash, not the wire payload — extending it to also assert `receiptToPayload(insertedRow)` equals the canonical input shape would close the gap.

### Nit — `syncService.ts:1226` silently downgrades unknown `fiscal_schema_version` to 2

**File:** `apps/pos/src/lib/sync/syncService.ts:1226`.

**What's wrong:** `const fiscalSchemaVersion = receipt.fiscal_schema_version === 3 ? 3 : 2;`. The comment at `:1222-1225` explicitly says "any unexpected value is a schema bug and should fail loudly via the server's hard-reject path", but the code does NOT fail loudly — it silently coerces to 2. If an offline receipt's column ever read back as `undefined`, `null`, or a corrupted value (e.g., 4 in some future migration), this would push it as v2, and a v3 server would correctly hash-reject it.

**Why it matters:** Pre-existing B1 territory, not a B3 regression. The server-side hard-fail path eventually catches this, so it's not a fiscal correctness hole. But the comment is at odds with the code.

**What would close it:** Either fail loudly on unexpected values (`throw` or assert via Sentry breadcrumb) or update the comment to match the silent-default-to-2 behavior. Trivial cleanup; not worth blocking on.

## What's solid

- The per-row both-or-neither cross-field rule is implemented correctly via `withValidator()` on both the online (`StoreReceiptPaymentsRequest`) and the sync (`SyncReceiptsRequest`) request validators. I tried to construct a payload that would slip through Laravel's broken `required_with` semantics — the `withValidator()` callback iterates the array with explicit indices, so a half-configured row at any index produces a properly-keyed error path (`payments.{i}.instrument_serial` or `receipts.{r}.payments.{p}.instrument_serial`). 422 negative tests confirm the actual response body.
- `instrument_type` is coerced through `PaymentInstrumentKind::from()` on both writers (online at `ReceiptPaymentService.php:215-217`, sync at `ReceiptSyncService.php:431-433`). An unknown string at this layer would throw `\ValueError`, which is the correct fail-fast behaviour. The request validator's `in:` rule should make this unreachable, but the defense-in-depth coercion is correct.
- The TS canonicalizer parity proof for fixture-08 (the voucher-binding case) is genuine: the test reads the fixture JSON, runs `buildCanonicalPayload(fixture.input)`, and asserts byte-equality on `expected_canonical` AND hex-equality on `expected_hash`. A drift in the TS payment-block sort order or the field ordering would fail.
- The hash-mismatch guard at `ReceiptSyncService.php:458-464` provides a real safety net: even if the validator/DTO/writer let some malformed payload through, the recomputed hash diverges and the transaction rolls back. This is the load-bearing fiscal-integrity check, and it's untouched by B3.
- The Voucher module truly has no `pos_receipt_payments` writer. A grep across `apps/api/app/Modules/Voucher/` returns zero matches, confirming the implementer's claim that no voucher-side writer was missed. `VoucherRedemptionService` writes only `voucher_ledger` rows + GL journal entries; voucher-tender `pos_receipt_payments` rows are written by the standard POS payment paths (now correctly wired in B3).
- v2 path is provably untouched at the hash-computation layer, both PHP and TS, by zero-line `git diff` against the merge-base. v2 terminals continue to seal and sync identically to before this commit chain.
- R1 / R3 / R4 land precisely what they claim. R1 is a clean real-SQLite test added in isolation. R3 fixes a real UI drift bug with backend-shaped test fixtures. R4 is a true mechanical doc fix with no behaviour change (verified by reading the code 5–10 lines past the docblock and matching the docblock claims against the `$wiredEvents` array).
