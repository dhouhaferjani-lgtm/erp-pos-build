# 4. Ricochet findings

## R1 - NEW MAJOR: foreground/background race contract relies on a guard the foreground path does not set

- Kickoff evidence: `docs/superpowers/plans/2026-05-09-pos-t2.1-catalog-truthfulness-kickoff-prompt.md:160` says the foreground 500-fetch is debounced by `isSyncing`; `:175` says the existing `isSyncing` guard debounces the scheduler until the foreground pull completes and yields "no double-pull"; `:171` says background ticks continue to call `pullProducts` directly, not `pullProductsForeground`.
- Source evidence: `apps/pos/src/lib/sync/syncScheduler.ts:65-72` checks `useSyncStore.getState().isSyncing` and then sets it via `startSync`; `apps/pos/src/stores/productStore.ts:65-69` sets only product-store `isLoading`; `apps/pos/src/stores/productStore.ts:1-10` has no `useSyncStore` import.
- What is wrong: v2's no-double-pull acceptance is false as written. The scheduler guard protects scheduler ticks from other scheduler ticks, not a foreground `productStore.fetchProducts` pull. Because v2 also says the scheduler keeps calling unwrapped `pullProducts`, the foreground wrapper's dedupe at `docs/...kickoff-prompt.md:179` cannot dedupe scheduler-vs-foreground overlap.
- Severity: MAJOR. This is a v2-introduced race explanation regression and keeps M0 only partially closed.

## R2 - NEW MAJOR: `pullProductsForeground` cannot reject typed non-timeout errors while calling unmodified `pullProducts`

- Kickoff evidence: `docs/superpowers/plans/2026-05-09-pos-t2.1-catalog-truthfulness-kickoff-prompt.md:163-168` requires `pullProductsForeground` to call existing `pullProducts(db)` and reject on timeout/network/HTTP errors; `:180` says existing `pullProducts` is not modified; `:540` repeats "add wrapper export" and "do NOT modify existing `pullProducts`".
- Source evidence: `apps/pos/src/lib/sync/syncService.ts:565` defines `pullProducts(db)` with no options; `apps/pos/src/lib/sync/syncService.ts:579-581` calls `apiGet('/products', ...)` without timeout/signal options; `apps/pos/src/lib/sync/syncService.ts:616-620` catches every error, logs it, and returns `0`.
- What is wrong: a wrapper around the current unmodified function can see `0`, but cannot distinguish an empty successful pull from an HTTP 5xx, network error, or timeout swallowed inside `pullProducts`. The v2 typed-error contract is not implementable without either modifying `pullProducts` to accept a foreground mode/options object or extracting shared pagination into a lower-level function that can throw.
- Severity: MAJOR. This keeps M2 only partially closed.
