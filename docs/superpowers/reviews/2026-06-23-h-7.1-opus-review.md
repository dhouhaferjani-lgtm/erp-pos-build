## MEDIUM

- **M1 — Newly chained expense entries have no GL-reversal path; relies entirely on
  upstream document immutability (acceptable today, fragile if expense void/edit is ever
  added).** Before this commit the expense JE was Draft (never hashed, never chained). It is
  now Posted with a `fiscal_hash` linked into the per-company chain
  (`GeneralLedgerService.php:1272-1283`, `getPreviousHash` :1751). The safety today rests on
  `ExpenseController::update`/`destroy` rejecting any non-Draft expense with 422
  (`ExpenseController.php:155-160`, `:188-191`) and `post` rejecting an already-Posted
  expense (`:218-221`), plus `ExpenseService::post` guarding `status !== Draft` (`:107`). So
  a posted expense cannot be edited or deleted, and there is no orphaned/dangling posted
  entry. This is correct now, but the change moves expenses into fiscal-chain territory
  without any reverse/contra mechanism — if an "edit/void posted expense" feature is later
  added, it MUST post a reversing entry, not delete. Recommend a one-line note on the H-7
  work-list documenting that expense corrections now require a contra entry, not a delete.
  [HYPOTHESIS — based on current controller code; no void path exists today]

- **M2 — Expense JE remains partner-untagged even though the source Document carries a
  `partner_id`.** Both lines are written with `partner_id => null`
  (`GeneralLedgerService.php:1591`, `:1601`), so `RefreshPartnerBalanceOnJournalEntryPosted`
  (lines filter on `partner_id`) no-ops and the vendor's AP balance is unaffected. This is
  consistent with the in-code comment ("Expenses typically don't have partner tracking") and
  with the H-7 scope boundary ("non-partner operational GL lifecycle only"). It is therefore
  *correct for this slice*, but it is an explicit modeling decision worth flagging: a posted
  cash/bank expense to a known vendor produces no partner-tagged GL line. If expenses are
  ever expected to feed supplier statements, that is a separate item. Not changed here; not a
  defect of H-7.1. [Pre-existing data shape, unchanged by commit]

## LOW

- **L1 — Hash-chain has no row lock; concurrent posts to the same company can fork the
  chain.** `getPreviousHash` does `orderByDesc('posted_at')->first()` with no
  `lockForUpdate`/serialization (`GeneralLedgerService.php:1751-1761`), and posting now runs
  in the `afterCommit` callback (outside the transaction). Two concurrent posting events for
  one company could read the same previous hash and produce two entries claiming the same
  predecessor. This is a *systemic* property of every posting path (invoice, credit note,
  AP, advance, tolerance, voucher, and now expense), not introduced by H-7.1, and the audit
  item explicitly mandates "canonical postEntry() semantics." Out of scope for this item but
  worth a cross-cutting ticket. [HYPOTHESIS — not exercised concurrently here]

- **L2 — `entry_date` uses `$metadata->payment_date ?? $expense->document_date`** while
  `calculateHash` serializes `entry_date->toDateString()`. Harmless and pre-existing; the
  posting change does not alter it. Noted only for completeness.

- **Money/precision:** PASS. No float cast on money. Lines write `$expense->total ?? '0'`

- **Sign conventions:** PASS / N/A. Debit expense account, credit cash/bank, equal magnitude;

- **Event immutability:** PASS. Reuses existing `JournalEntryPosted` event unchanged; nothing
  renamed/restructured. Hash chain extended via existing `calculateHash`.
- **GL correctness:** PASS. Double-entry balanced (debit == credit == total), so the
  `postEntry` balance assertion cannot fail for a well-formed expense. Idempotency is
  enforced upstream (post guards Draft; cannot re-post). Posted-vs-draft lifecycle correct;
  actor required (`User` is non-nullable on the path).
- **Transaction/concurrency:** PASS for leak-safety. `post()` wraps in `DB::transaction`;
  `createFromExpense` runs an inner transaction then defers posting to `DB::afterCommit`
  (`transactionLevel() > 0` branch, `:82-86`), so a rollback of `post()` leaves no posted
  entry and emits no `JournalEntryPosted`. Concurrency caveat = L1 (systemic).
- **Migration safety:** N/A — no schema change in this commit.
- **Test quality:** PASS. Red-first independently reproduced (revert → fail at Posted
  assertion). The test drives the real `ExpenseService::post()` path, not the GL helper in
  isolation, and asserts status/actor/posted_at/fiscal_hash. Not a false-confidence test.
- **Strict typing / enums / module boundaries:** PASS. PHPStan L8 clean; statuses are enums
  (`JournalEntryStatus`, `DocumentStatus`); the test imports `ExpenseService` from its public
  Application namespace (acceptable cross-module use of a public service, not a model import).
