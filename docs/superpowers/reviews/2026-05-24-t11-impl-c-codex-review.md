# T11-impl-C — Thin-POS B2B Hand-off — Spec Review (round 1, Codex)
## Verdict: REJECT
## Summary
The thin-POS keystone is directionally coherent: current POS code creates `Receipt` rows, not `Document` rows, and `holdStore.ts` really is a local SQLite park-sale flow with cart clear and idempotency-key discard at the cited lines. The target spec also correctly identifies `DocumentStatus::Draft`, `DocumentType::SalesOrder`, and the existing sales-order conversion infrastructure.

The spec is not ready to hand to an implementing engineer because its office conversion path is factually wrong against production code. It says the office opens a draft sales order and converts it to an invoice using the existing converter, but the existing converter explicitly rejects draft sales orders, the web action bar only exposes conversion for confirmed sales orders, and the conversion endpoint accepts no credit-terms input. There are also material contract gaps around the draft-order queue DTO/display fields, `originTerminalId`, and `variantId`.

The POS coordination story also needs one cleanup before implementation: the sibling coordination log still instructs fiscal work to extend `holdStore.ts`, while this spec says the new action must be a separate sibling store and leave `holdStore.ts` untouched. That contradiction is exactly the kind of handoff ambiguity this spec is supposed to eliminate.

## Findings
### BLOCKER
- The office conversion acceptance cannot work as written because the spec creates a `SalesOrder/Draft` and then claims the office can convert that draft through the existing converter. The target spec states the hand-off creates `status = Draft` at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:95` and acceptance says the office opens it and converts to invoice at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:185`. Production code rejects draft sales orders: validation adds "Sales order must be confirmed before conversion" at `apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/SalesOrderToInvoiceConverter.php:100`, `convert()` throws for `DocumentStatus::Draft` at `apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/SalesOrderToInvoiceConverter.php:143`, and the web action bar only shows convert-to-invoice for `status === 'confirmed'` at `apps/web/src/features/documents/components/DocumentActionBar.tsx:98`. The spec must add an explicit office confirmation/finalization step before conversion, or define a new finalise-and-convert workflow instead of saying the existing converter handles drafts directly.

### P1
- The "with terms" claim overstates the existing conversion flow. The spec says the office rep "sets credit terms there" with no new conversion UI at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:153`, but `SalesOrderDetailPage` posts an empty body to `/orders/{id}/convert-to-invoice` at `apps/web/src/features/documents/sales-orders/SalesOrderDetailPage.tsx:107`, the controller only validates `partial` and `line_ids` at `apps/api/app/Modules/Document/Presentation/Controllers/DocumentConversionController.php:58`, and the converter hardcodes `due_date` to `now()->addDays(30)` at `apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/SalesOrderToInvoiceConverter.php:166`. If "credit terms" means anything other than fixed Net 30, this spec needs a concrete terms path.

- The default no-migration queue contract cannot display the fields the spec promises. The spec says `DraftOrderQueuePage` shows partner, location, line count, total, and origin terminal at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:152`, while also choosing the no-migration default at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:109`. The generated `DocumentData` DTO has no `location_id`, no location name, no `origin_terminal_id`, and no `payload` field at `packages/shared/types/generated.d.ts:426`; the PHP DTO likewise omits payload and location from its constructor at `apps/api/app/Modules/Document/Application/DTOs/DocumentData.php:21`. The existing list page renders only number/type/status/partner/date/total at `apps/web/src/features/documents/DocumentListPage.tsx:342`. The spec should define a dedicated queue DTO or explicitly drop those fields from acceptance.

- `originTerminalId` is specified but has no persistence/display contract in the default path. The command includes `?string originTerminalId` at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:93` and the event includes `origin_terminal_id` at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:125`, but `documents` has no `origin`/terminal column in its fillable fields at `apps/api/app/Modules/Document/Domain/Document.php:112`, and `DocumentData` does not expose payload at `apps/api/app/Modules/Document/Application/DTOs/DocumentData.php:154`. Either store it in `payload` and expose a queue DTO, or remove "origin terminal" from the queue requirements.

- The spec has a hidden T2 dependency if it keeps `variantId` in the draft-order line DTO. `DraftOrderLineInput` includes `?variantId` at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:93`, but current `document_lines` and `DocumentLine` have no `variant_id`; `DocumentLine::$fillable` lists `product_id`, `batch_id`, `product_code`, and `service_id` but no variant at `apps/api/app/Modules/Document/Domain/DocumentLine.php:64`, and current document creation validation has no `lines.*.variant_id` rule at `apps/api/app/Modules/Document/Presentation/Requests/CreateDocumentRequest.php:89`. The topology contract says T2 owns adding `variant_id` to `document_lines` at `docs/sprint-planning-2026-05-24:docs/superpowers/coordination/2026-05-24-migration-topology-contract.md:61`. Add T2 as a conditional dependency or remove `variantId` from this track until T2 lands.

- The POS coordination log still contradicts the spec's sibling-store rule. The target spec says "do not add to `holdStore` itself" and use a new `draftOrderStore.saveAsDraftOrder` at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:134`, but the sibling coordination log's T11-D2 row lists `holdStore.ts` and says "Extend existing `holdStore`" at `docs/sprint-planning-2026-05-24:docs/superpowers/coordination/2026-05-24-pos-coordination-log.md:59`. Since the fiscal session consumes that log, this must be reconciled before implementation.

### P2
- The spec's route middleware guidance should name the current Document module route stack, not only the minimum CLAUDE rule. CLAUDE requires `['api', 'auth:sanctum', SetPermissionsTeam::class]` at `CLAUDE.md:48`, but Document routes currently also include `EnforceTokenTenantClaim::class` at `apps/api/app/Modules/Document/Presentation/routes.php:33`. A new `/api/v1/draft-orders` route added to this module should preserve that extra tenant-claim guard unless the spec intentionally places it elsewhere.

- The `GET /api/v1/draft-orders` contract is under-specified relative to the existing `/orders?status=draft` path. Existing sales-order listing already filters status through `SalesOrderController::index()` at `apps/api/app/Modules/Document/Presentation/Controllers/SalesOrderController.php:87` and `HandlesDocuments::applyFilters()` applies the status enum at `apps/api/app/Modules/Document/Presentation/Controllers/Concerns/HandlesDocuments.php:136`. The spec should choose either a dedicated endpoint/DTO or the existing list filter and state the permission model accordingly.

- The spec's "server creates on Web/API surface" wording is coherent with impl-B, but it should name the exact `EmissionSurface` value the hand-off service uses. impl-B allows Web/Api and blocks POS `SalesOrder` at `docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:135`; impl-C says "Web/API surface" at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:29`. To prevent an implementer from choosing `Pos` and fighting the policy, state `EmissionSurface::Api` or `EmissionSurface::Web` explicitly and keep the POS-surface rejection test at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:197`.

### SUGGESTION
- Consider reusing existing `orders.view`, `orders.create`, and `orders.confirm` permissions unless there is a product reason for separate `draft-order.*` abilities. Existing routes already gate sales orders with `orders.view`, `orders.create`, and `orders.confirm` at `apps/api/app/Modules/Document/Presentation/routes.php:81`; adding a second permission family may be useful, but the spec should explain the role split.

- If the queue remains "all draft sales orders" in the no-migration default, call out that web-created draft sales orders will appear beside POS hand-offs. The spec already states POS-originated drafts are not distinguished from web-drafted orders at `docs/superpowers/specs/2026-05-24-t11-impl-c-thin-pos-handoff.md:106`; the UI acceptance should reflect that limitation.

## Ready-to-implement verdict
Not ready. Fix the BLOCKER first by specifying the office lifecycle explicitly: draft hand-off → office review/edit → confirm sales order → convert to invoice, with the real terms behavior either accepted as fixed Net 30 or extended in scope.

Before handing this to an engineer, also resolve the P1 queue/display contract, define where `originTerminalId` lives, handle or defer `variantId` until T2, and update the POS coordination log so fiscal work does not modify `holdStore.ts` against this spec's own constraints. Once those are corrected, the core thin-POS architecture is implementable without violating the POS `Document`-emission policy.
