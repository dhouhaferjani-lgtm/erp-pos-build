## Summary

The api.service cluster fix was originally bundled into commit 77185828 ("submit api.catalog.001-017 for review") by a parallel session's wide-net staging — that part of the attribution context is accurate. When the Service module diff is examined in isolation (`git diff 516c6f61 77185828 -- apps/api/app/Modules/Service apps/api/tests/Feature/Service`), it cleanly closes all 3 inventoried callsites (api.service.001/002/003 in `ServiceCatalogService::updateService` / `deleteService` / `getService`) by injecting `CompanyContext` into the constructor, replacing every bare `findOrFail` with a `tenant_id`+`company_id`-scoped `firstOrFail`, hardening the controller-tier route lookups in `ServiceController` + `ServiceCategoryController`, folding the parallel ServiceCategory CRUD findOrFails into the same pattern, and adding a defense-in-depth `assertCompanyMatchesContext` helper. The 13-test ServiceTenantIsolationTest.php (28 assertions) is honest — pre-fix rollback produces 7 failures with the exact shapes claimed (cross-tenant `ModelNotFoundException` not thrown, drift-rejection `InvalidArgumentException` not thrown, structural-SQL log shows `where "company_id" = ? and "id" = ?` with no `tenant_id` predicate).

However: the very next commit on the branch — f08a6ba2 dated 2026-05-04 22:22:03, message "chore(tenant-isolation): claim + start api.workshop cluster (4 callsites)" — touches NO workshop files, NO inventory.yml, and instead applies a verbatim REVERT of the api.service Service module fix:

- `ServiceCatalogService.php` — constructor injection removed; `Company::findOrFail` restored; `assertCompanyMatchesContext` deleted; every scoped `Service::query()->where('tenant_id')->where('company_id')->where('id')->firstOrFail()` reverted to `Service::findOrFail`. -152 / +0 lines net.
- `ServiceController.php` — `where('tenant_id')->where('company_id')->where('id')` chains in `show` / `update` / `destroy` reverted to bare `where('company_id')->where('id')`.
- `ServiceCategoryController.php` — same 3-method revert.
- `ServiceCatalogServiceTest.php` — CompanyContext setUp removed.

The new ServiceTenantIsolationTest.php remains in tree, so the cluster regression suite is now actively RED on the branch tip. The inventory.yml's "submitted" event for api.service.001/002/003 (recorded against commit 77185828) is no longer reflected in the actual code state — verify-history doesn't catch this because it only checks event-chain integrity, not code-state correspondence.

This is the SAME parallel-session staging accident pattern that caused the original bundling into 77185828 — except now operating in reverse, undoing rather than over-attributing. The commit message is misleading (claims workshop, actually reverts service); a reviewer trusting commit messages would miss the regression.

ServiceTenantIsolationTest.php (still in tree) fails 7 of 13 tests against this state with the same failure shapes as the pre-77185828 code. This is a tenant-isolation regression. The cluster cannot be approved while the branch tip carries this revert.
   - Files: `apps/api/app/Modules/Service/Application/Services/ServiceCatalogService.php`, `apps/api/app/Modules/Service/Presentation/Controllers/ServiceController.php`, `apps/api/app/Modules/Service/Presentation/Controllers/ServiceCategoryController.php`, `apps/api/tests/Feature/Service/ServiceCatalogServiceTest.php` — all reverted at f08a6ba2.

Re-run `vendor/bin/phpunit tests/Feature/Service/` to confirm 66/224/0 before continuing the workshop work.

2. **Severity: HIGH (process gap, exposed by Finding 1)** — Pre-merge gates do not catch this class of regression. PHPStan returns `[OK] No errors` and Pint returns `{"result":"pass"}` at f08a6ba2 because the test file's symbol references (`ModelNotFoundException`, `CompanyContext`) still resolve as types — only PHPUnit catches the runtime regression, and `php artisan sweep:inventory:verify-history` returns `0 problem(s)` because it only audits event-chain integrity, not code-state correspondence to the recorded `under_review` status. A "claim" commit that touches implementation files should be flagged by a structural CI check, e.g.: a claim/submit/approve transition that touches files OUTSIDE `docs/superpowers/plans/tenant-isolation-sweep-inventory.yml` should fail unless the touched files match the cluster being transitioned.
   - Suggested fix (orchestrator-level, not a code change in this cluster): add a `sweep:inventory:claim`-only file-allowlist gate that rejects claim commits with non-YAML changes; or require the claim commit to also assert `vendor/bin/phpunit tests/Feature/<previously-shipped-cluster>/` is green for the most-recently-submitted cluster on the branch.

3. **Severity: NICE-TO-HAVE (would be the only finding if Finding 1 didn't exist)** — `EloquentServiceRepository.php` (line 14: `Service::query()->find($id)`; line 17–22: `findByIdForTenant` with tenant_id only, no company_id) is dead/skeleton code with zero callers in app/. The fix correctly did not touch it. Accepting as documented "no-caller defensive scaffolding" is reasonable, but adding `where('company_id', ...)` to `findByIdForTenant` and renaming it to `findByIdForTenantAndCompany` (or marking the file `@deprecated`) would future-proof against a controller wiring this method up later and inheriting the gap. Not blocking on its own — only a structural concern if the file is wired into DI somewhere I missed (it is not — `Service::class` is not bound in the AppServiceProvider, and grep confirms no callers).
   - File: `apps/api/app/Modules/Service/Infrastructure/Persistence/EloquentServiceRepository.php:14,17-22`
   - Suggested fix (deferable): add `->where('company_id', $companyId)` predicate, rename to `findByIdForTenantAndCompany($id, $tenantId, $companyId)`. Or annotate `@deprecated dead-code; add tenant+company predicates before wiring`.

4. **Severity: NICE-TO-HAVE (validator-tier blind spot, surfaced in hostile-grep)** — `CreateServiceRequest.php` line 38, `UpdateServiceRequest.php` line 40, `CreateServiceCategoryRequest.php` line 34, `UpdateServiceCategoryRequest.php` line 36 all use `'exists:service_categories,id'` for `category_id` / `parent_id` validation WITHOUT `ScopedExists::tenantAndCompany`. A tenant-A user can therefore POST a tenant-B category UUID via `category_id` on service create/update, and the validator will accept it (the row is then created with tenant-A scoping but a tenant-B `category_id` reference). The service-tier `Service::create` does not re-verify category ownership. This is the same symmetry-gap pattern the api.cart cluster called out as Finding 2 (preferred_supplier_partner_id). It does NOT cause cross-tenant data leakage on the inventoried callsites (api.service.001/002/003 are all on the Service entity, not Category), but a tenant-A service row can be persisted with a foreign tenant-B `category_id`, which (a) breaks the canonical Treasury two-tier defense template and (b) creates a side-channel for downstream consumers (e.g., reports that JOIN services to service_categories) to leak across tenants. Not blocking for closure of api.service.001/002/003, but worth tracking — likely belongs to a future "validator-tier sweep" cluster or should be folded back here as a hardening pass.
   - Files: `apps/api/app/Modules/Service/Presentation/Requests/CreateServiceRequest.php:38`, `UpdateServiceRequest.php:40`, `CreateServiceCategoryRequest.php:34`, `UpdateServiceCategoryRequest.php:36`
   - Suggested fix: replace `'exists:service_categories,id'` with `ScopedExists::tenantAndCompany('service_categories', $companyContext->getTenantId(), $companyContext->getCompanyId())`.

5. **Severity: INFORMATIONAL (out-of-scope referrals)** — The hostile grep surfaced `Service::` reads from outside the Service module that belong to other clusters and should NOT be folded into api.service. Tracking only:
   - `apps/api/app/Modules/Workshop/Bundle/Infrastructure/Resolvers/EloquentServiceResolver.php:21` — `Service::query()->find($serviceId)` (Workshop cluster).
   - `apps/api/app/Modules/Document/Domain/Services/DraftPersistenceService.php:202` — `Service::find($lineData['service_id'])` (Document cluster).
   - `apps/api/app/Modules/Document/Domain/Services/DraftPersistenceService.php:407`, `QuoteController.php:223,331`, `InvoiceController.php:238,348`, `DeliveryNoteController.php:228`, `SalesOrderController.php:223,331`, `PurchaseOrderController.php:232,342` — `Service::whereIn('id', $serviceIds)->get()` patterns (Document cluster). All would benefit from a `where('tenant_id')->where('company_id')` lead but belong to api.document, not api.service.

Medium confidence on Finding 3 (EloquentServiceRepository): I verified zero callers via grep; if the file is wired up via a future provider binding I'd miss it. Current grep of `EloquentServiceRepository::class` in app/Providers/ returned no matches and the class is `final`, so it's not silently inherited from. Medium rather than high only because I did not exhaustively scan service tests / other clusters' DI bindings for late-bound usage.

Medium confidence on the broader Workshop/Document Service::find blind spots (Finding 5). I confirmed they exist as separate cluster surfaces; I did not verify they appear in inventory.yml under their respective cluster ids. Out-of-scope for this review.
