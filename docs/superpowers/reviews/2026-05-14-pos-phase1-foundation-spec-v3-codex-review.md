## Executive summary
- v3 correctly fixes v2's false attribution: `ReceiptSyncService` owns POS-core receipt projection effects; `ReceiptPaymentService` owns Treasury `Payment` + GL effects.
- The projection failure model is materially better: fiscal-event insert is separate from projector jobs, with per-projector status and retry/dead-letter semantics.
- The bounded-modules seam is still not buildable against the current code. POS-core receipt payment rows still hard-depend on Treasury `payment_methods`, and the cited module-activation surface is tenant-level/default-module based, not a per-company bridge switch that can represent POS-only without Treasury.
- The web POS is live, not theoretical. v3 acknowledges this, but the cleanup checklist does not name the concrete browser/server write paths that must be disabled or rebuilt.
- The `sequence_conflict` path is directionally right, but the proposed quarantine table does not actually store the conflicting envelope verbatim or enough metadata to make the chain incident auditable.

## New findings
### [BLOCKER] The bounded-modules seam is not buildable on the current POS payment-method boundary
**Dimension:** grounding / buildability / codebase-claim
**Spec location:** §5.0, §7.3–§7.4, §13 (`spec v3:235-240,353-391,495-517`)
**Evidence:** SoT D16 requires the POS fiscal engine to have zero hard dependency on Treasury/accounting/sales and says POS-only is a supported deployment (`source-of-truth v3:237-242,265`). The owner fiscal strategy separates POS fiscal engine responsibilities from ERP responsibilities (`fiscal_chain_architecture_strategy.md:87-123`). v3 says POS-core projection always runs with no Treasury dependency and the Treasury bridge is included only when the Treasury module is active (`spec v3:237-240,373-389`). Actual POS-core `ReceiptPayment` rows still depend on Treasury: `ReceiptPayment.php` imports `App\Modules\Treasury\Domain\PaymentMethod` (`:8`) and relates to it (`:148-154`); the `pos_receipt_payments.payment_method_id` FK points at `payment_methods` (`2026_01_08_190640_create_pos_receipt_payments_table.php:29-32`); `ReceiptSyncService` imports and queries Treasury `PaymentMethod` before creating `ReceiptPayment` rows (`ReceiptSyncService.php:33,560-567`). The cited module-activation mechanism is also not as described: `CompanyConfigService` is tenant-level (`CompanyConfigService.php:29-38`), `RequireModule` reads the authenticated user's tenant (`RequireModule.php:51-63`), and every current vertical default includes `Treasury` and `Accounting` (`Vertical.php:124-136`).
**Issue:** v3 asserts the D16 seam but does not specify the codebase changes needed to make it real. A POS-only deployment cannot currently create POS receipt payment records without Treasury-owned `payment_methods`, and the existing activation surface cannot exclude Treasury per company or even by default for current verticals.
**Impact:** Writing-plans can implement a registry that looks modular while still hard-linking the POS-core projector to Treasury tables/models. That violates the locked D16 boundary and makes the promised POS-only deployment fail at schema/model/service level.
**Suggested fix:** Add an explicit Phase 1 seam task before `PosCoreReceiptProjection`: either move payment method/repository concepts needed for POS tenders into POS/shared core, or define a POS-owned tender-method snapshot table and remove `ReceiptPayment`'s hard FK/model dependency on Treasury `PaymentMethod`. Separately, specify a server-side `ModuleActivationResolver` with the actual scope it supports; if POS-only is required now, change the current default-module model so Treasury can be inactive and test `TreasuryReceiptBridge` excluded while POS-core projection still succeeds.

### [P1] Web POS disposition does not name the live server-authoring write paths
**Dimension:** completeness / scope
**Spec location:** §1.3, §2, §14, §18 (`spec v3:52-54,66-68,540,638-642`)
**Evidence:** v3 correctly says a live web-POS receipt-creation path cannot coexist with the rebuilt device-authority chain (`spec v3:52,66`). The live browser POS path is concrete: `POSTransactions.tsx` creates a web terminal (`:111-124`), posts `/pos/receipts` (`:313-318,366-368`; `receiptApi.ts:73-77`), then posts `/pos/receipts/{id}/payments` (`POSTransactions.tsx:318-329,396`; `receiptApi.ts:121-128`). Backend routes remain live at `routes.php:45,98,102`; `ReceiptController::store()` invokes `ReceiptCreationService::createReceipt()` (`ReceiptController.php:284-315`) and `ReceiptController::storePayments()` invokes `ReceiptPaymentService` (`ReceiptController.php:505-510`).
**Issue:** The spec only says "hide/disable" web POS in the preflight gate. It does not add a cleanup checklist equivalent to §14.1 for the actual web frontend page/API methods/routes/services that author server-side receipts and payments.
**Impact:** Phase 1 could retire offline `/pos/receipts/sync` while leaving browser POS server-authoring intact. That preserves exactly the two-model coexistence D8 forbids and keeps a server-recompute receipt path live beside the new device-authored chain.
**Suggested fix:** Add a §14.2 web-POS disposition checklist naming the concrete targets: disable/hide `POSTransactions` sale completion, `createReceipt`, `processReceiptPayments`, `POST /pos/receipts`, and `POST /pos/receipts/{id}/payments` for web terminals unless/until they delegate to the fiscal-event engine. Preserve read-only receipt search/PDF/download routes separately.

### [P1] `sequence_conflict` quarantine is not actually verbatim enough to support the claimed incident path
**Dimension:** consistency / buildability
**Spec location:** §7.2, §8, §15 (`spec v3:340-351,438-462,567-571`)
**Evidence:** v3 says a non-identical sequence conflict inserts "the conflicting envelope verbatim" into `fiscal_event_quarantine` (`spec v3:341-344`) and exports/verifier include that quarantine surface (`spec v3:462,567-571`). The proposed table stores only `tenant_id`, `terminal_id`, claimed sequence, `envelope_event_id`, `canonical_bytes`, hashes, class/reason, conflicting event id, and timestamps (`spec v3:442-459`).
**Issue:** The table does not store the actual typed envelope or enough queryable metadata to make the incident self-contained: no `company_id`, `event_type`, `event_version`, `payload_version`, `operator_id`, `business_date`, `source_event_class/source_event_id`, signature fields, `last_server_time_seen`, or raw envelope JSON. Some of that may be inside `canonical_bytes`, but the spec's own server model treats envelope metadata as columns on `fiscal_events` (`spec v3:123-168`), and the quarantine table omits them.
**Impact:** A `sequence_conflict` could be "persisted somewhere" but not auditable, exportable, or resolvable with the same fidelity as admitted fiscal events. Chain verifier and JET export work would have to parse opaque bytes or invent missing metadata extraction later.
**Suggested fix:** Add a raw envelope column (`envelope_json`/`raw_envelope` as `JSONB` or `BYTEA`) plus the same query-critical metadata columns used by `fiscal_events`: `company_id`, `event_type`, `event_version`, `operator_id`, `business_date`, `source_event_*`, `signature_version/status/object fields` as applicable, and `payload_parse_status` if a strict parse was attempted. Then specify exactly which fields the verifier and export use.

### [P1] Resuming projections after `canonical_parse_failure` resolution has no owner or mechanism
**Dimension:** completeness / buildability
**Spec location:** §7.5 and §17.3 (`spec v3:416-420,615-616`)
**Evidence:** v3 says no `fiscal_event_projections` rows are created for `canonical_parse_failure`, and projection resumes only after operator resolution flips `payload_parse_status → parsed` (`spec v3:419`). It also tests suppression (`spec v3:616`). The projection dispatch mechanism only creates projection rows in the original insert transaction (`spec v3:416`).
**Issue:** If projection rows are deliberately not created at insert time, there is no specified resolver action, command, trigger, or job that creates the missing `fiscal_event_projections` rows after parse resolution. The immutability trigger allows the parse-status transition (`spec v3:193-195`), but nothing connects that state change to projector dispatch.
**Impact:** A once-unparseable but later-resolved `SALE_RECEIPT` can remain permanently unprojected: no `pos_receipts`, no receipt payments, no stock/voucher effects, and no bridge execution. Operators would think resolution restored the event, but the business projection would never run.
**Suggested fix:** Define the resolver contract: when an authorized resolution writes `payload` and transitions `payload_parse_status` to `parsed`, it must create `pending` `fiscal_event_projections` rows for all currently active projectors and enqueue them, or call a named `projection:enqueue-resolved-event` command. Add a test for parse-failure resolution followed by POS-core projection.

### [P2] `/pos/receipts/sync` retirement checklist still omits concrete old-sync classes and client integration tests
**Dimension:** completeness
**Spec location:** §14.1 and §17.5 (`spec v3:544-558,623-626`)
**Evidence:** v3 names `pushOfflineReceipts`, `receiptToPayload`, two client unit-test line refs, route/controller, feature suites, and `SyncReceiptPayload` (`spec v3:548-558`). Live old-sync surface also includes `SyncReceiptsRequest.php:20`, `SyncReceiptResult.php:16`, `ReceiptSyncService.php:54`, `SyncStatus::ChainBroken` usages through result factories (`SyncReceiptResult.php:99-108`), and client integration tests that import/call `pushOfflineReceipts` (`offlineFirstFlow.test.ts:110,279,340`).
**Issue:** The checklist is better than v2 but still leaves old-sync DTO/request/result/service classes and integration tests implicit under "grep." This codebase has already had misses from broad cleanup wording; the spec should name the concrete classes that become dead or must be repointed.
**Impact:** Writing-plans may remove the route and update the obvious unit tests while leaving old service/DTO/request code compiling and old integration tests exercising an obsolete sync model. That makes a stale compatibility path more likely to survive.
**Suggested fix:** Expand §14.1 to explicitly retire or repoint `ReceiptSyncService`, `SyncReceiptsRequest`, `SyncReceiptPayload`, `SyncReceiptResult`, old `SyncStatus` values that only support receipt-sync semantics, and `apps/pos/src/__tests__/integration/offlineFirstFlow.test.ts`. Keep the final repo-wide grep as verification, not as the only specification of scope.

### [P2] Projection retry/dead-letter state is underspecified for operations
**Dimension:** buildability
**Spec location:** §7.5 (`spec v3:397-420`)
**Evidence:** v3 defines `projection_status` as `pending|applied|failed`, with `attempts`, `last_error`, and `applied_at` (`spec v3:400-412`), and says jobs retry with backoff then dead-letter after max attempts (`spec v3:417-418`).
**Issue:** The table has no `next_attempt_at`, `last_attempted_at`, `dead_lettered_at`, `locked_at`, `locked_by`, or distinct `dead_lettered` status. A queue can handle some of this transiently, but the spec claims an operator-visible dead-letter view and manual replay. With only `failed` and `attempts`, implementers must invent how to distinguish "waiting for retry" from "dead-lettered" and how to avoid duplicate concurrent projector jobs.
**Impact:** Projection behavior may vary across implementations, especially under retry storms or worker concurrency. Operators may see a generic failed row without knowing whether it is still retrying, permanently dead-lettered, or safe to replay.
**Suggested fix:** Either define that the queue system owns all locking/backoff/dead-letter metadata and name the queue mechanism, or add operational columns/statuses: `projection_status = pending|running|applied|retry_scheduled|dead_lettered`, `next_attempt_at`, `last_attempted_at`, `dead_lettered_at`, `locked_at`, `locked_by`, and a compare-and-set claim rule for workers.
