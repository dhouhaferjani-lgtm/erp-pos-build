## Critical findings

### R8-C-1 — The final review has no sealed A snapshot, and candidate-owned progress fields still control the supposedly trusted invocation

**Evidence:** r15 calls A “reviewed data only” and preflights only committed changes in `base_sha..A` to the bridge, brief, harness, and `.claude/agents/*-reviewer.md`; it does not require `git status --porcelain` to be empty, materialize a fresh detached worktree at A, or isolate project-local reviewer configuration (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:434`). The only statement that the candidate must be clean at every handover is in the historical r15 revision-log claim (`:87`), not in the execution-mode rule (`:110`), promotion step 1 (`:434`), any final milestone (`docs/handoff/progress/enforcement-p1.progress.yaml:169-176`; `enforcement-p2.progress.yaml:174-181`; `enforcement-p3.progress.yaml:172-179`), or LEDGER S-14 (`docs/handoff/LEDGER.md:56`). Moreover, the handback is intentionally created after A and first committed in C (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:434,438,460-466`), so the handed-over worktree is expected to contain at least one post-A file unless the parent first copies it elsewhere.

The candidate progress YAML also remains a live control input. The harness says the YAML supplies `review_lenses` and `max_fix_rounds`, and its bridge command takes the lens list from that file (`docs/handoff/SELF-REVIEW-HARNESS.md:14-15,29-37,43-47`). r15 repeats that the package YAML is the operative milestone state and the standard call uses the milestone's `review_lenses` (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:97,111,113-125`). Those candidate-editable files are not in the four-path control preflight. Their final lens fields are ordinary candidate content (`docs/handoff/progress/enforcement-p1.progress.yaml:169-176`; `enforcement-p2.progress.yaml:174-181`; `enforcement-p3.progress.yaml:172-179`). The bridge then places the passed labels in its prompt and tells the reviewer to run `git diff` and read surrounding code from its current checkout; it performs no clean-tree or detached-A check (`scripts/adversarial-review.sh:21-45,49-64,82-86`).

**Failure scenario:** an untrusted executor commits A, changes a final milestone's `review_lenses` to `[]` inside the allowed `docs/handoff/**` surface, and hands over with the required uncommitted handback plus unstaged source/test changes that make the acceptance commands green. The four-path `base_sha..A` preflight passes: the progress YAML is not a rejected control path, and unstaged files are outside that commit range. The parent follows the harness, passes the candidate's empty lens list to its trusted bridge, and runs the review in the handed-over checkout. The reviewer receives only the general lens prompt and its test commands execute the dirty working-tree bytes, not A. A can receive parent ACCEPT and owner tags even though neither the applied lens set nor the tested bytes are mechanically bound to A. This uses only the explicitly untrusted executor; no malicious parent/owner is required.

**Required repair:** make step 1 operate on an immutable review bundle. The parent must copy the handback into its own workspace, verify the candidate worktree has no other tracked/untracked changes, and materialize a fresh read-only detached worktree at exactly A for diff inspection and tests. Source milestone id, full lens list, `max_fix_rounds`, and other immutable review controls from a parent-pinned control manifest, not from candidate state; field-check the candidate YAML against that manifest while permitting only the necessary state fields to vary. Run the reviewer with project-local instruction/settings loading either disabled or pinned as part of that manifest. Record the snapshot/control-manifest identity in the attestation.

## High findings

### R8-H-1 — “Parent-pinned” is a post-hoc label, and the required trusted bridge does not yet exist

**Evidence:** the r15 log names a “parent-pinned control SHA,” but none of the three schemas has a `control_ref`, expected control digest, or parent-owned control-manifest field (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:85`; `docs/handoff/progress/enforcement-p1.progress.yaml:1-8`; `enforcement-p2.progress.yaml:1-8`; `enforcement-p3.progress.yaml:1-8`). Operatively, the first durable control identity is written only after ACCEPT as `control_sha256:` lines in the step-3 pin-tag annotation (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:436`). Recording what happened after the fact is not a pin to a previously approved source, and P3-M0 does not compare those control hashes with any expected values (`docs/handoff/progress/enforcement-p3.progress.yaml:29-54,148-155`).

The only bridge on disk accepts `--brief`, `--milestone`, `--lenses`, `--range`, `--out`, and `--round`; it rejects every other argument (`scripts/adversarial-review.sh:21-31`). Its prompt receives lens labels as prose and does not load or accept explicit lens-contract paths (`:49-64`). r15 nevertheless requires a trusted-copy interface with `--handback` and `--handback-sha256` and claims that pinned lens-contract copies are consumed (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:88,434`). No owner step creates, tests, approves, or pins that extended executable before dispatch.

**Failure scenario:** the parent selects the current repository bridge at the parent-approved base as its “pinned copy.” At the final gate, adding the required handback flags reaches the bridge's unknown-argument branch and exits 3 without a reviewer run. None of P1/P2/P3 may repair that control file because any such candidate change is a scope/preflight failure. If the parent instead patches an ad hoc external copy, there is no pre-invocation expected SHA/ref against which to verify that it is the approved extension or that it actually injects the pinned lens contracts; the later tag merely records whichever bytes happened to run.

**Required repair:** before any package dispatch, create and test the trusted bridge revision in an owner-controlled location/ref. It must implement the handback interface and accept explicit absolute paths (or embedded bytes) for every lens contract. Add a parent-owned pre-dispatch control manifest containing the exact source ref and expected hashes for the bridge, brief, harness/control projection, and lens contracts; step 1 verifies those bytes before invocation, and P3/closing verification compares the tag's `control_sha256` lines to that manifest. The current post-ACCEPT-only hashes are not sufficient.

### R8-H-2 — The handback echo can be copied from the prompt, and the tag may bind a different post-review file

**Evidence:** step 1 has the parent compute a digest, pass both path and digest to the bridge, require the reviewer to echo them, and verify that echo (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:434`). An echo of a value included in the prompt proves only that the reviewer reproduced prompt text; no content-derived assertion or independently computed digest is required. After the invocation, the parent separately hashes the “already-bound” handback, and step 3 places `sha256(handback)` in the pin-tag annotation (`:434,436`). There is no explicit equality check between this later digest and the pre-invocation digest. C then lands the tag-digested bytes (`:438`), and P3 verifies the landed bytes against the annotation, not against the digest echoed in the final register (`docs/handoff/progress/enforcement-p3.progress.yaml:29-39,50-54`).

**Failure scenario:** the reviewer does not open a large P1 census handback, copies the supplied path/digest into its register, and reviews only `base_sha..A`. The echo check passes. Alternatively, the executor modifies the handback after the parent's pre-hash/reviewer read but before the parent's post-run hash. The parent verifies the register's old digest D1, then the pin tag records D2 and C lands D2. P3's annotation/base-blob checks all pass on D2 even though the final review applied to D1. The untrusted executor is inside the recorded threat model; no malicious trust root is required.

**Required repair:** before invocation, the parent must copy the handback bytes into an immutable parent-owned path and use that exact copy for the review, post-review digest, pin-tag annotation, and C. Keep the expected digest out of the reviewer prompt; require the reviewer/bridge to compute and echo it independently, then verify it against the parent's hidden value. The register must also contain content-derived review evidence for the required census/classification tables, not just a digest echo. Re-hash the immutable copy immediately before tagging and require exact equality with the pre-invocation digest.

### R8-H-3 — A transient final-bridge tool error has two contradictory owners and no legal same-A retry state

**Evidence:** the execution-mode exception says that on a tool error “the parent re-invokes,” but the same sentence sends control to the executor to fix, commit, increment `fix_rounds`, and hand over (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:110`). Promotion step 1 likewise groups CHANGES-REQUIRED and tool error together, requiring an executor fix commit and `fix_rounds` increment for both (`:434`). All three final milestone titles reproduce that combination (`docs/handoff/progress/enforcement-p1.progress.yaml:169-176`; `enforcement-p2.progress.yaml:174-181`; `enforcement-p3.progress.yaml:172-179`). The underlying harness allows one review invocation per milestone round and requires a scoped fix commit before the next round (`docs/handoff/SELF-REVIEW-HARNESS.md:29-47`). No rule gives a unique parent-workspace path/attempt counter for same-A retries or says when a stale tool-error register is removed/quarantined; only the eventual ACCEPT file is said to land.

**Failure scenario:** the parent's round-2 bridge fails transiently because the CLI is unavailable and produces no candidate finding. A same-A parent retry follows “parent re-invokes” but violates the one-invocation/per-round transition and can overwrite or coexist ambiguously with the round-2 error register. Returning control to the executor follows the other clause, but there is no scoped code fix to make and no legitimate commit; manufacturing an empty commit changes A and forces a needless full re-gate. The package either deadlocks or consumes fix rounds for infrastructure errors.

**Required repair:** split the states. `tool_error` must remain parent-owned and retry the same A without a candidate commit or `fix_rounds` increment, using immutable unique paths such as `round<n>-attempt<m>` in the parent workspace; define a bounded tool-attempt limit and its blocked state. Only a substantive CHANGES-REQUIRED register transfers control to the executor and increments `fix_rounds` after a new commit. Specify that superseded parent registers are quarantined outside the candidate and that exactly the final ACCEPT attempt is copied into C.

## Minor findings

### R8-M-1 — P3 verifies close-tag annotation claims but not the close tag's target or its `closing_check` payload

**Evidence:** step 5 defines the close tag as an annotated tag **at C** containing `closing_commit: C`, `closing_check: sha256(verbatim check output)`, and `accepted_sha: A` (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:438`). P3-M0 requires the P1/P2 close-tag annotation's `closing_commit` and `accepted_sha` to match, but does not require the tag itself to resolve to C and does not obtain or hash the verbatim check output (`docs/handoff/progress/enforcement-p3.progress.yaml:39-41,50-54`). By design that output is absent from C (`enforcement-p1.progress.yaml:91-97`; `enforcement-p2.progress.yaml:78-84`; `enforcement-p3.progress.yaml:106-112`), and no other durable output path is named.

**Failure scenario:** an honest owner accidentally pushes the close tag at the wrong commit while its annotation text names the derived C, or hashes a different/incomplete command transcript. P3 derives and checks C independently, then accepts the annotation fields; it never detects the wrong tag target and cannot validate `closing_check`. This does not require a threat actor outside the model, but it is Minor because P3 independently repeats the substantive C/diff/blob checks and the owner is the trust root.

**Required repair:** require `git rev-parse <close-tag>^{commit} == C` in every consumer. Either retain the verbatim named-check output in an owner-controlled immutable object and verify its digest, or define `closing_check: pass` as an owner attestation and remove the currently unverifiable hash. Apply the same complete close-tag schema to P3's no-workflow path even though it has no current downstream package consumer.
