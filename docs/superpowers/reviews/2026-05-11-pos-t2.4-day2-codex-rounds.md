# PR #108 — T2.4 Day 2 (AppRouter wiring + BootstrapErrorScreen) — Codex review trail

**Branch:** `feat/pos-t2.4-day2-app-router-wiring`
**Base:** `dev`
**Reviewer:** Codex CLI (`codex review --base dev`)
**Final state:** 6 rounds, APPROVE.

The Day 1 review trail (`docs/superpowers/reviews/2026-05-10-pos-t2.4-bootstrap-store-day1-codex-rounds.md` L7-update lesson) flagged that the kickoff under-specified the bootstrap lifecycle. This PR's downstream lifecycle audit (PR body §Pre-flight) preempted some of that, but Codex still surfaced four discrete failure modes that required wiring fixes: a logout trap (r1), a session-safety regression introduced by the r1 fix (r2), a concurrent /user/companies race with CompanyRecoveryScreen (r3 → r4 reopen on orphan recovery), and a missing companies dep on the resume effect (r5 — closed together with r5 P1 on busy sign-out).

## Round 1 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed)

### P2 — Sign Out from BootstrapErrorScreen left the cashier trapped

`AppRouter`'s `phase === 'error'` early-return is checked BEFORE the `!isAuthenticated` LoginPage branch. Clicking Sign Out cleared auth state but bootstrap stayed in `error`, so the error screen kept rendering instead of forwarding to LoginPage — the advertised recovery affordance silently failed.

**Closure (`3b416dbe`):** new `bootstrapStore.reset()` action sets `phase='ready'`, `error=null`, `lastSuccessfulPhase=null`, `running=false`. `authStore.logout()` calls it via dynamic import (keeps the bootstrap → auth dependency one-way). Tests +3: store reset clears state + restarts from authenticating; logout integration via `vi.waitFor` because the .then runs on a macrotask.

## Round 2 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P1, session safety — REGRESSION introduced in r1)

### P1 — The r1 fix let logout rehydrate a just-signed-out session

After logout, `bootstrapStore.reset()` set `phase='ready'` and `lastSuccessfulPhase=null`. The dep-change useEffect then immediately fired `retry()` → re-ran authenticating → `authStore.initialize()` read storage. Because logout's `removeStoredValue` calls are fire-and-forget, the re-read could hit stale TOKEN/USER and restore the just-signed-out session.

**Closure (`5422bbf1`):** added `if (!isAuthenticated) return;` to the dep-change effect's guards. The retry only fires when prerequisites have flipped to a state where bootstrap can make progress — for the post-logout case that means waiting for the cashier to log in again. The store-level reset/retry/start actions are unchanged; the session-safety gate is a UI-layer concern.

**This was a regression I introduced in r1.** Without r2's catch, every logout from BootstrapErrorScreen would have restored the session.

## Round 3 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed)

### P2 — Bootstrap's fetching-companies raced CompanyRecoveryScreen's fetchCompanies

A cached-authenticated boot with `companies=[]` ran the bootstrap `fetching-companies` phase at the same moment `CompanyRecoveryScreen` mounted and auto-fired its own `fetchCompanies()`. Two concurrent `/user/companies` requests. If the bootstrap-side fetch failed/timed out while recovery succeeded, the BootstrapErrorScreen preempted the now-recovered recovery screen — silently overriding a working recovery flow.

**Closure (`4e1d9b3f`):** bootstrap's `fetching-companies` phase body is now a no-op. `CompanyRecoveryScreen` owns the empty-companies fetch exclusively. The phase entry stays in the enum so `canEnterPhase` keeps gating fetching-terminal on `isAuthenticated` before any terminal API call. The PR #106 r6 P2 closure was a half-measure (skip-when-non-empty); this closure completes the intent (skip always — recovery screen is the sole owner). Tests updated accordingly.

## Round 4 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed)

### P2 — Orphan empty-companies + stale companyId still advanced past recovery

With `companies=[]` but a stale non-null `companyId` (the exact orphan state `CompanyRecoveryScreen` is designed to repair), the pre-fix `canEnterPhase('fetching-terminal')` gate only checked `companyId`. Bootstrap advanced into terminal init, and on terminal failure the BootstrapErrorScreen preempted CompanyRecoveryScreen — blocking the recovery flow from refreshing `/user/companies`.

**Closure (`24194caa`):** `canEnterPhase('fetching-terminal')` and `('checking-pins')` now also require `companies.length > 0`. With companies empty, bootstrap stops at 'ready' with `lastSuccess='fetching-companies'`; AppRouter renders CompanyRecoveryScreen. After recovery updates the companies cache (or clears the stale companyId via the existing fetchCompanies side-effect), the dep-change effect fires `retry()` and bootstrap resumes. Tests +1 for the orphan scenario.

## Round 5 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P1 + 1 P2 closed)

### P1 — Sign Out could race in-flight retry/skipWithCache

If the cashier clicked Retry or Use Cached Data and then clicked Sign Out before that promise settled, the in-flight bootstrap run could complete a phase and `setState({ lastSuccessfulPhase: phase })` AFTER `reset()` — polluting the cleared session state.

**Closure (`46db6f3a`):** Sign Out is now disabled while `isBusy` is true (mirrors the Retry / Use Cached Data buttons). The other logout entry points (auth-init internal 401, sync scheduler 401) cannot fire concurrently with a retry from this screen because bootstrap is in `error` state (sync scheduler only runs after the operator gate, i.e. `phase === 'ready'` and beyond). Test +1: sign-out disabled while retry in flight, re-enabled after settle.

### P2 — `companies` was missing from the dep-change useEffect deps

The orphan-recovery scenario (r4 closure) stops bootstrap before terminal init when companies is empty. When CompanyRecoveryScreen's `fetchCompanies` returns a non-empty list that validates the existing companyId, only `companies` changes (companyId + terminal stay as-is). Without `companies` in the deps, the effect would never re-fire and bootstrap would never advance, leaving the app on TerminalSetupPage instead of initializing the cached terminal/PIN state.

**Closure (same commit):** added `companies` to the dep-change useEffect's deps.

## Lesson updates (proposed for memory notes)

- **L6 (lifecycle audit, expanded):** The Day 1 trail's L6 said "include a lifecycle audit section that traces every consumer of the modified state through every entry point." For Day 2 the PR body did include an upfront AppRouter render-branch coverage map — and r1 was still missed because the audit didn't trace the SIGN-OUT → AppRouter precedence loop. **Refinement:** lifecycle audits must trace BOTH directions (state machine → AppRouter renders, and user actions on rendered screens → state machine writes). The four r1-r5 findings all fall in the second direction.
- **L8 (cross-screen ownership):** When a new screen takes ownership of a state transition (here: BootstrapErrorScreen owning retry/skipWithCache), audit every OTHER screen that previously co-owned anything in that transition surface (here: CompanyRecoveryScreen's auto-fetch) for races. r3 P2 (CompanyRecoveryScreen co-owning the empty-companies fetch) and r4 P2 (orphan stale companyId at the canEnterPhase gate boundary) were both about boundary co-ownership.
