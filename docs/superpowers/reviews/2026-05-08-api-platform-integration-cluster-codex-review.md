## Novel Findings
1. MUST-FIX: `StripeWebhookController` still has two provider-blind payment reconciliation paths. `handleInvoicePaid()` uses `Payment::updateOrCreate(['provider_payment_id' => $paymentIntentId], [... 'provider' => PaymentProviderCode::Stripe ...])` at `apps/api/app/Modules/Billing/Presentation/Controllers/StripeWebhookController.php:279-294`; `handleInvoicePaymentFailed()` repeats that shape at `:354-371`. Because `updateOrCreate()` uses the first array as lookup attributes, a PayPal/Klarna/etc. row with the same `provider_payment_id` can be matched and then overwritten as Stripe. This is the same provider-filter invariant fixed in `resolveStripePayment()` at `:654-658`, and it becomes more important after the migration intentionally allows the same external id across different providers (`ExternalIdUniquenessTest.php:138-185`). Fix both lookup arrays to include `provider => PaymentProviderCode::Stripe->value` (or equivalent stored scalar) and add regression tests that seed a foreign-provider row first, then drive `handleInvoicePaid()` and `handleInvoicePaymentFailed()` so only a Stripe row is created/updated.
