The claim holds up. `BatchWriteOffService::writeOff()` now forwards its existing
`userId` and the company currency into `GeneralLedgerService::createInventoryWriteOffEntry()`,
which validates the actor (`User::findOrFail`) and posts the `batch_write_off`

ran the test and it passes (1 test / 8 assertions), confirming the entry reaches
`Posted` with a non-null `fiscal_hash`, `posted_at`, and `posted_by = user`.
PHPStan L8 is clean on both changed files. The precision behaviour (`124.017` for
TND scale-3) is preserved, no float touches money, scale flows from the
constructor-injected `CurrencyScaleResolverInterface`, and the journal entry is
balanced and partner-less (correct for an operational write-off). I found no
BLOCKER and no HIGH. Findings below are MEDIUM/LOW and largely shared with the
sibling H-7.x slices rather than introduced here.

## MEDIUM

### M1 — afterCommit hash-chain read/write is unlocked (shared with H-7.1/.2/.3)
`postEntryAndDispatchPostedEventAfterCommit` defers posting to `DB::afterCommit`
(GeneralLedgerService.php:84-90) because the write-off runs inside the outer
`DB::transaction` in `BatchWriteOffService::writeOff()` (BatchWriteOffService.php:59).
The post then calls `getPreviousHash()` (GeneralLedgerService.php:1751-1760) which
reads the last Posted entry's `fiscal_hash` ordered by `posted_at`, and writes the
new hash — with **no row lock / advisory lock** around the read-modify-write, and
now *outside* any transaction. Two concurrent write-offs (or a write-off racing an
expense/voucher/COGS post) for the same company can read the same `previous_hash`
and fork the chain. This is a pre-existing property of the canonical helper, not
introduced by H-7.4, but H-7.4 adds another producer onto that unlocked path.
`[HYPOTHESIS]` — not reproduced under concurrency; flagged for the hardening
session owner to track once across all H-7 posters rather than per-slice.

### M2 — afterCommit posting failure leaks a committed Draft + escapes the catch
The `try { ... } catch (\RuntimeException $e)` in `BatchWriteOffService` (lines
84-108) wraps only *entry creation*. Actual posting happens later in `afterCommit`,
after the outer transaction has already committed the stock movement and the Draft
`batch_write_off` entry. If `postEntryWithOptionalActor` throws (e.g. the
`InvalidArgumentException` for an unbalanced entry at GeneralLedgerService.php:1268,
or a hash failure), the exception is raised from the afterCommit callback — *not*
caught by the `\RuntimeException` handler — leaving a committed Draft GL entry and
a committed stock deduction with no posted GL. In practice the write-off entry is
always balanced (`debit == credit == amount`), so the unbalanced path is
unreachable here, which is why this is MEDIUM not HIGH. Still, the "log but don't
block" guarantee the catch advertises does not actually cover the posting phase.

### M3 — Actor lookup failure rolls back the whole write-off (behavioural asymmetry)
`User::query()->findOrFail($postedByUserId)` (GeneralLedgerService.php:1644) runs
inside the outer write-off transaction but is a `ModelNotFoundException`, which the
`\RuntimeException` catch does not absorb. So a bad actor id aborts the entire
write-off (stock + movement rolled back), whereas a missing GL account merely logs
and proceeds. This is *safe* (atomic, no partial state) and unreachable from the
only production caller (`auth()->id()` in BatchController.php:368 is always a valid
authenticated user), but the failure philosophy is inconsistent with the adjacent
GL-account-missing path. Worth a one-line comment so a future service-direct caller
(queue job) understands a bad actor is fatal-by-design.

## LOW

### L1 — Cross-module model import (pre-existing)
`GeneralLedgerService` imports `App\Modules\Identity\Domain\User`
(GeneralLedgerService.php:17). This violates the "no cross-module model import"
rule, but it is long-standing (the whole `postEntry(User $user)` API depends on it)
and not introduced by H-7.4. No action for this slice.

### L2 — No idempotency guard on `source_id` (pre-existing, correctly out of scope)
`createInventoryWriteOffEntry` does not dedupe on `movementId`/`source_id`; a
re-invocation would create a second entry. Write-off is a synchronous,
user-driven action (not an event-replay path), so double-delivery is not a
realistic risk, and both internal reviews correctly flagged this as pre-existing
and out of the lifecycle slice.

### L3 — Residual draft writer noted but not addressed
The work-list/coordination notes a separate `UninvoicedDeliveryNoteService` draft
adjustment writer. Correctly tracked as a follow-up; not part of this slice.
