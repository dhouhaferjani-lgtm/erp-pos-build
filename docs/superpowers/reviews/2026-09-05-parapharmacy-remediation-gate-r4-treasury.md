## 2. New findings

### MAJOR — R4-M1. The refund twin of the shared entry has no debit-override seam, and spec:167's "sole per-leg writer" is only true of the sale path.

**Spec:** line 167 — *"`GeneralLedgerService.php:3944–3966` is the **sole** per-leg writer of proportional revenue and sealed per-rate VAT"*; acceptance line 221 — *"mixed tender and **refund** preserve each class"*; the W2 seam list (line 230) names the bridge's every-leg loop but no refund writer.

**Source, read at HEAD.** `TreasuryReceiptBridge.php:1508–1521` branches on `$isRefund`: the refund arm calls `createPOSRefundReversalEntry(payment, receipt, repository, vatSplit)` — **no `cashAccountOverrideId` argument**. The signature confirms the seam does not exist there: `GeneralLedgerService.php:4175–4180` takes `Payment, Receipt, PaymentRepository, PosRevenueVatSplit` only, and `:4181–4187` still hard-requires `$repository->gl_account_id`. That method is also a second writer of the same lines: `:4228–4234` calls `writePosRevenueAndVatLines(… onDebitSide: true, revenueDescription: 'POS sales revenue reversed (refund)')`. Movement suppression, by contrast, **is** shared — `:1556–1558` runs for both arms.

**Failure scenario.** An implementer extends only `createPOSPaymentEntry` as spec:167 instructs. A voucher- or loyalty-settled sale is later refunded on the same tender. The refund leg takes the `$isRefund` arm, ignores the non-money destination, and credits the **resolved repository's** `gl_account_id` — a cash or bank account — for money that never left custody, while `$shouldRecordMovement = false` keeps the repository balance flat. Result: the GL cash/bank account and the treasury repository balance diverge by the refunded voucher amount, permanently and silently (the entry still balances). In the other branch — a non-money leg for which no repository was resolved at all, exactly what spec:167 authorizes — `:4181` throws and the refund projection fails hard on a queue worker.

**Minimum correction (one sentence + one seam entry).** State that the same debit-only substitution applies to the refund reversal writer `GeneralLedgerService.php:4175–4234`, add it to the W2 seam list beside `createPOSPaymentEntry`, and qualify the "sole writer" claim as "the sale-leg writer; `:4175–4234` is its refund twin and writes the same revenue/VAT lines with `onDebitSide: true`". The acceptance row at spec:225/226 should exercise a **voucher/loyalty refund**, not only mixed-tender refunds.

### IMPORTANT — R4-I1. A blocked non-money leg leaves an unmatched clearing/liability suspense that the spec never names.

spec:213 requires (correctly) that "**Blocked Treasury never blocks POS-core receipt/revenue/stock projection**", and POS-core is where redemption posts `Cr PosTenderClearing` (`PosCoreReceiptProjection.php:1616–1632`, `GeneralLedgerService.php:2955`, `VoucherRedemptionService`). Under v4 the offsetting debit now lives in the Treasury leg. So whenever a non-money leg blocks — the most likely cause being exactly the new CONDITIONAL purpose of spec:189 not yet seeded for that company — the clearing (or loyalty liability) account carries a one-sided balance until a rebind/resolution runs. That is a *correct* consequence of two correct rules, but it is invisible in the spec: acceptance spec:225 asserts "clearing nets to zero" for the happy path only. **Minimum correction:** one clause in the blocked-leg paragraph (spec:213) stating that a blocked non-money leg leaves a visible, aged, per-source suspense balance on the clearing/liability account, and one acceptance line asserting the suspense is attributable to the blocked leg and nets on resolution — not a trial-balance-only check.

### MINOR — R4-m1. MEAL_VOUCHER: "maintain physical custody where applicable" (spec:182) versus "no … repository inflow" (spec:226).

MEAL_VOUCHER is seeded `is_physical=true, requires_third_party=true, has_deducted_fees=true, fee_percent=1.50` (`PaymentMethodSeeder.php:337–351`, verified). Paper tickets physically enter the drawer, yet the class forbids any repository movement, and the two sentences cannot both be implemented if physical custody is modelled as a repository. Low blast radius (France-seeded, outside the Tunisia launch under D2), but one clause should say where physical ticket custody is tracked if not in Treasury, or defer it explicitly with the rest of the method.

### MINOR — R4-m2. Three off-by-one/scope-loose citations.

`PaymentInstrumentKind.php:16–22` is cited for "unsupported-state refusals"; the `RestaurantVoucherNotYetSupportedException` note is `:19–22` and the GiftCard rejection is at `:23`, outside the range (use `:17–23`). `paymentMethodKind.ts:22–26` — the `INSTRUMENT_BEARING_METHOD_CODES` array is `:21–25`. `ProvisioningRequiredPurposesV1.php:57` is offered as the pattern for classifying the two new purposes **CONDITIONAL**, but `:57` is a `self::REQUIRED` entry (PosTenderClearing); the CONDITIONAL pattern with its 4xx precheck is `:65–68`. All three resolve close enough to find, but the third invites the wrong manifest class.

### MINOR — R4-m3. The live bypass TODO stays in the code as a booby trap.

spec:169 supersedes `GeneralLedgerService.php:2960–2962` "in design", but the comment still instructs future readers that "Voucher tender rows MUST bypass `GeneralLedgerService::createPOSPaymentEntry()` … TODO: wire the bypass". That is verbatim the defect R3-B1 was raised against. Add a line requiring the first authorized W2 lane to correct that docblock (documentation-only, no behaviour change) so the spec and the code stop disagreeing.
