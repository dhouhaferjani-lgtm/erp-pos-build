## MEDIUM

### M1 — Non-EUR (scale-3) posting path is unverified by either named test
The two H-2.4 verification tests do not exercise posting at a non-EUR scale:
- `tests/Feature/Treasury/VendorPrepaymentRefundTest.php` (the new test `test_refund_prepayment_posts_supplier_advance_reversal_entry`) seeds an **EUR** company (`'currency' => 'EUR'`, line 76) — scale 2.
- `tests/Feature/Treasury/VendorRefundScalingTest.php` is the TND/scale-3 test, but it deliberately sets `account_id` to null to **skip the GL reversal path** (`// account_id deliberately null to skip GL reversal path`, ~line 116). It asserts only `balance_due`/`repository.balance` scaling, never a posted journal entry.

Net: there is no test where a TND supplier-advance refund is actually *posted* through `getScale('TND')`. Risk is low because the reversal is Dr Bank = Cr SupplierAdvance with the identical magnitude string, so `postEntryWithOptionalActor()`'s `bccomp(totalDebit, totalCredit, $scale)` balances at any scale. Recommend adding a TND case that sets `account_id` and asserts a posted, balanced entry to lock the scale path.

### M2 — New posting test does not assert the GL line content (double-entry shape)
`test_refund_prepayment_posts_supplier_advance_reversal_entry` (lines ~197-222) asserts `status == Posted`, `posted_by`, `posted_at`, `fiscal_hash`, and `journal_entry_id` linkage, but never asserts the two `JournalLine` rows (Dr payment-method/bank account = amount, Cr SupplierAdvance account with `partner_id` = amount). Double-entry correctness is only validated implicitly by `postEntryWithOptionalActor()` throwing on imbalance. A test that posts but has a wrong account on a line, or a missing `partner_id` subledger tag, would still pass. Recommend asserting the two lines (accounts, debit/credit magnitudes, and `partner_id` on the advance line).

### M3 — afterCommit posting takes the fiscal hash chain outside the row lock [HYPOTHESIS, system-wide, not introduced here]
`refundPrepayment()` locks the PO and repository with `lockForUpdate()` inside its `DB::transaction()`, but posting is deferred via `DB::afterCommit()` (`postEntryAndDispatchPostedEventAfterCommit`, GeneralLedgerService.php:84-90). `getPreviousHash()` (lines 1751-1761) reads the last posted entry by `orderByDesc('posted_at')` with no lock or chain serialization. Two concurrent posts for the same company could read the same previous hash and fork/duplicate the chain link. This is a pre-existing property shared by *every* H-2 slice (payment-received, customer-advance, tolerance all post through the same after-commit helper); H-2.4 does not make it worse and follows the canonical path. Flagged for the H-2 program owner, not as an H-2.4 regression. [NEEDS-REAL-PG] to reproduce under true concurrent transactions.

## LOW

### L1 — Actor lookup occurs inside the caller's outer transaction
`User::query()->findOrFail($postedByUserId)` (GeneralLedgerService.php:396-399) runs before the inner `DB::transaction`, but `refundPrepayment()` has already opened an outer transaction, so the lookup executes at `transactionLevel() > 0`. The Codex/fallback reviews assert "an invalid actor id does not leak a draft journal entry outside an outer transaction" — that is correct: an invalid id throws `ModelNotFoundException` before any `JournalEntry::create`, and even if it threw later the outer transaction rolls back. Behavior is safe; the review wording is just slightly imprecise about "outside an outer transaction." No action required.

### L2 — `partnerId` typed non-nullable while sourced from `$lockedPo->partner_id` [pre-existing]
`reverseSupplierAdvanceJournalEntry(..., string $partnerId, ...)` is non-nullable, fed by `$lockedPo->partner_id`. If a confirmed PO ever had a null partner this would TypeError. Unchanged by this commit; noted only for completeness.
