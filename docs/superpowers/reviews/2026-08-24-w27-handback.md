## 2. Policy decision, with file:line evidence

**What an implicit reservation on a batch-tracked product is supposed to do.**

Read of the code before deciding:

- `app/Modules/BatchExpiry/Application/Services/BatchStockService.php:61-108` — `ensureDefaultBatch()` is a
  **top-up to a caller-supplied target**, never a reconciliation. Its own docblock says "Never reduces stock"
  and it deliberately writes **no** `BatchMovement` ("a default/seeded backfill has no movement").
  So whatever target the caller passes IS the DEFAULT lot's quantity.
- `app/Modules/Inventory/Application/Services/StockReservationService.php` (base) — the caller passed
  `targetQuantity: (string) $stockLevel->quantity`, i.e. the tuple's **entire** aggregate on-hand quantity,
  with no subtraction of the real lots. That is the defect.
- `app/Modules/BatchExpiry/Domain/Services/FEFOInventoryService.php:41-155` — `suggestBatchesForSale()` is the
  house FEFO selector: `orderBy('product_batches.expiry_date','asc')`, `available_quantity > 0`, skips
  inactive/recalled/expired lots, bcmath end-to-end. This is what "FEFO against real lots" means in this codebase.
- `app/Modules/Inventory/Application/Services/StockReservationService.php:658-664` — `reserveWithFEFO()` already
  proves the intended shape (FEFO suggestions, one reservation per lot). It is **not** the path a sales-order
  confirm takes.
- `app/Modules/Document/Domain/Services/SalesOrderService.php:144-155` — `confirm()` calls `reserve()` once per
  physical line **with no `batch_id`**, so the implicit resolution is exactly what the operator's confirm reaches.
- `app/Modules/Product/Domain/Product.php` (parapharmacy vertical forces `requires_batch_tracking = true`) — which
  is why every imported product hit this on its first order.

**Decision (implemented exactly as the brief states it):**

1. The `DEFAULT` lot backs **only the untracked remainder** = `stock_levels.quantity − Σ(real lot quantities)`,
   clamped at zero; a zero remainder mints **nothing**.
2. The reservation is then booked **FEFO** — the earliest-expiry lot that covers the request whole.
3. **A request no single lot can cover falls back to the aggregate branch** (`batch_id = null`). `reserve()` writes
   ONE row with ONE `batch_id` (`StockReservationService.php:166-180`), so a spill-over cannot be lot-pinned
   without splitting the reservation and changing `reserve()`'s return contract (3 callers: `SalesOrderService`,
   `MarketplaceOrderService`, `StockReservationController`) — out of this lane's scope. The aggregate branch still
   enforces `stock_levels` availability, and **issuance** stays FEFO regardless
   (`FEFOInventoryService::consumeBatchesAtomically()`). This is pinned by a test, not left implicit.
4. The reservation path **never shrinks** an already-over-seeded `DEFAULT` lot. Reducing a lot's quantity is a stock
   quantity change and belongs to an operator-run, evidence-gated repair — not to a silent side effect of a confirm.

## 4. Migration / command decision

**No migration. A console command.** `inventory:repair-phantom-default-batches`
(`app/Console/Commands/RepairPhantomDefaultBatchesCommand.php`).

Why not a migration:

- `git push origin dev` auto-deploys and runs `tenants:migrate`, so a migration would rewrite **every tenant's batch
  ledger unattended**, with no census read first and nobody looking at the numbers.
- The correction needs a per-reservation judgement (below) and a tenant whose real lots cannot absorb a parked
  reservation must be **reported**, not silently mangled.

Safety shape:

- Extends `TenantScopedCommand`; `forEachExplicitlySelectedTenant()` **refuses to run** without `--tenant=<uuid>` or
  `--all-tenants` (exit 2).
- **Refuses to run without exactly one of `--dry-run` / `--execute`** (`:100-111`, exit 2) — neither, or both, is a
  refusal. There is no default.
- `--company=` narrows inside the selected tenant(s).
- Every invocation prints a **repair run id** stamped onto every movement it writes as `reference_id`, so one run's
  corrections can be pulled back out of `stock_movements` as a batch.

**Document-per-action.** Every lot reduction writes its own justifying pair inside one transaction
(`RepairPhantomDefaultBatchesCommand.php:328-360`):

- a `stock_movements` row — `movement_type = adjustment`, `reason = count_correction`,
  `reference_type = 'batch_ledger_repair'`, `reference_id = <run id>`;
- an `inventory_batch_movements` row carrying that `movement_id` and the **negative** lot delta.

The movement's aggregate `quantity` is **`0.0000`**, with `quantity_before === quantity_after`, because the aggregate
on-hand quantity is not changing and never was wrong — only the lot ledger was inflated. Recording a non-zero
aggregate delta here would invent a stock movement that never happened and would corrupt WAC. This is asserted, not
just asserted-in-prose: `RepairPhantomDefaultBatchesCommandTest::test_execute_zeroes_the_phantom_lot_…`.

Reservation re-pointing moves only `batch_id` / `reserved_quantity` — a soft hold, no on-hand quantity moves, so it
carries no movement of its own (and the DPA scanner classifies it `not_applicable`, matching the live
`StockReservationService` shape it already baselines).

**Reservation policy.** An active reservation parked on a `DEFAULT` lot is re-pointed to the earliest-expiry real lot
whose available quantity covers it **whole** — the same predicate the fixed reservation path applies, so repaired rows
match what the fixed code would have written. A reservation no single real lot can cover is **left** on the `DEFAULT`
lot and reported; the lot's quantity is then **floored at its remaining `reserved_quantity`** so the reservation stays
honoured, and the residual is surfaced as `Lots only partially reduced: N`. Pinned by
`test_it_keeps_the_untracked_remainder_and_floors_at_reservations_no_real_lot_can_cover`.

## B. `stock_levels.reserved` — a REAL oversell hole, reachable from SO confirm. Fixed.

**Verdict: yes.** Determined from code and then demonstrated by a failing test before any fix.

Mechanism, with file:line:

```sql
SELECT p.sku,
       sl.location_id,
       sl.quantity                    AS stock_levels,
       COALESCE(SUM(ibs.quantity), 0) AS lot_ledger,
       COALESCE(SUM(ibs.quantity), 0) - sl.quantity AS drift
FROM   stock_levels sl
JOIN   products p ON p.id = sl.product_id AND p.requires_batch_tracking
LEFT   JOIN product_batches pb

        AND pb.variant_id IS NOT DISTINCT FROM sl.variant_id
LEFT   JOIN inventory_batch_stock ibs
         ON ibs.batch_id = pb.id AND ibs.location_id = sl.location_id
GROUP  BY p.sku, sl.location_id, sl.quantity
HAVING COALESCE(SUM(ibs.quantity), 0) <> sl.quantity
ORDER  BY drift DESC;

Lot A read 0 with 5 of its units physically back on the shelf; lot B read 10 while only 5 of its units exist. `Σ lots == stock_levels` reconciles either way — which is exactly why nothing else caught it — but two lot balances are wrong at rest, `BatchTraceabilityController` (which still reads those allocation rows) reports a recall wrong in both directions, and short-dated units get a longer expiry so FEFO ships them **last**. Same product-safety failure mode as the `DEFAULT@today+365` phantom, one notch less visible.

**Fix — one service, two inputs.** `restoreBatchesForReturn()` takes an optional `array<int, numeric-string> $preferredLots`:

1. **Provenance first.** Each hint is applied before anything else and is still **capped by that lot's outstanding outbound**, so a stale or over-stated hint can only ever under-credit.
2. **Heuristic** (most-recently-shipped, outstanding-outbound ceiling) for whatever provenance does not cover — pre-lane sales with no snapshot, unattributed returns.
3. **`DEFAULT` lot** for the rest.

- **POS** passes the sale line's `ReceiptLineBatchAllocation` rows, netted by what prior returns of that line already credited (the same proportional arithmetic the deleted `cumulativeBatchRestitution()` used).
- **DN/RN** passes the issue legs of the **originating delivery** — resolved from `inventory_batch_movements` whose `stock_movements.reference_id` is the return's `source_document_id` or a document raised from that same source. Per-document rather than per-line (a delivery note has no allocation snapshot), which is still strictly better than the tuple-wide heuristic; when nothing resolves the hint is empty and the heuristic answers, exactly as before.
- **Composite leaves** have no provenance and still reach the fallback — which is what R4-7 was actually asking for.
