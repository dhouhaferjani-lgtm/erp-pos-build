# PR #96 — Codex Round-1 Adversarial Review

**Verdict:** REQUEST-CHANGES (one P1 / BLOCKER)

**Summary:** Codex correctly identified that Sanctum's `Guard::isValidAccessToken` ANDs the global `SANCTUM_TOKEN_EXPIRATION` with the per-token `expires_at`, so the 12-month POS session contract is silently broken at 30 days without an `authenticateAccessTokensUsing` override. Fixed at `b991aefe`.

## Findings

### BLOCKERS

**P1 — Don't rely on `expires_at` to bypass Sanctum's global TTL**
File: `apps/api/app/Modules/Identity/Presentation/Controllers/AuthController.php:72` (the `tokenExpiresAt` helper).

With `SANCTUM_TOKEN_EXPIRATION` still set to 43200 (30 days, in `apps/api/config/sanctum.php:53`), Sanctum treats tokens older than 30 days as expired regardless of the row-level `expires_at`. So a POS login that issues `now()->addYear()` here will still be rejected after the global 30-day TTL.

**Verification (vendor/laravel/sanctum/src/Guard.php:127-130):**
```php
$isValid =
    (! $this->expiration || $accessToken->created_at->gt(now()->subMinutes($this->expiration)))
    && (! $accessToken->expires_at || ! $accessToken->expires_at->isPast())
    && $this->hasValidProvider($accessToken->tokenable);
```

Both checks must pass. The per-token `expires_at` does NOT bypass the global TTL — it's an AND, not an OR.

**Fix** (`b991aefe`):
- `AppServiceProvider::boot()` registers a `Sanctum::authenticateAccessTokensUsing` callback that lets per-row `expires_at` win when set:
  ```php
  if ($token->expires_at !== null) {
      return ! $token->expires_at->isPast() && $token->tokenable !== null;
  }
  return $isValid;
  ```
- Web back-office tokens (no per-row expiry) defer to the default `$isValid` → global TTL still governs.
- 4 new unit tests of the registered callback called directly via `Sanctum::$accessTokenAuthenticationCallback`.
