## 1. Root cause

Supplier-invoice input VAT never reached the Tunisian VAT declaration. A double lock, either half of
which alone produces a zero deductible figure — which is why neither showed a symptom.

**Lock 1 — no writer.** `SupplierInvoicePostingService::post()` posted the GR/IR clearing entry and
transitioned Draft → Posted, but never called `TaxCalculationService::snapshotTaxDetails()`. A posted
supplier invoice carried **zero** `document_tax_details` rows.
`CreateSupplierInvoiceService.php:197` *does* call `calculateDocumentTaxes()`, but only to read
`->documentTaxTotal` for `stamp_duty_amount` (`:201`); the result was discarded.

**Lock 2 — no reader.** `EloquentVatDataRepository::aggregateByRateAndDirection()` restricted the
document arm to `['invoice','credit_note','expense']` and mapped only `expense` to `'INPUT'`.

**Live proof** (local PG 5433, demo tenant `tenant019fbe86-…`, 2026-08-26):

```
 type             | status | docs | Σ tax_amount | docs with a tax-detail row
------------------+--------+------+--------------+---------------------------
 supplier_invoice | draft  |  31  |  390.517     | 0
 supplier_invoice | posted |  12  |  313.884     | 0
```

390.517 + 313.884 = **704.401 TND** — the owner sheet's figure, against 0 rows. Reproduced on five
further tenants. Both gates independently re-ran this census and got the same numbers.

## 2. Where each arm snapshots — the parity table

The snapshot point was the lane's central design question. The answer contradicts the brief's literal
wording ("at creation"); the brief also said *check parity*, and this is what the check found.

| Document type | Writer | Transition | Snapshots at draft creation? |
|---|---|---|---|
| Invoice | `InvoiceController::confirm()` | Draft → Confirmed | **No** |
| Credit note | `CreditNoteController::confirm()` | Draft → Confirmed | **No** |
| Quote | `QuoteController::confirm()` | Draft → Confirmed | **No** |
| Sales order | `SalesOrderService::confirm()` | Draft → Confirmed | **No** |
| Purchase order | `PurchaseOrderService::confirm()` | Draft → Confirmed | **No** |
| Delivery note | `DeliveryNoteService::confirm()` | Draft → Confirmed | **No** |
| Return note | `ReturnNoteService::confirmWithFiscalChain()` | confirm | **No** |
| Expense | `ExpenseService::writeDeductibleVatSnapshot()` ← `post()` | Draft → Posted | **No** |
| **Supplier invoice** (this lane) | `SupplierInvoicePostingService::post()` step 9 | Draft → Posted | **No** |
| **Supplier credit note** (this lane) | `SupplierCreditNotePostingService::post()` step 8 | Draft → Posted | **No** |

**Zero arms snapshot at draft creation**, and the reason is structural: the repository applies **no
status predicate**, so "a `document_tax_details` row exists" *is* the system's proxy for "this document
is fiscally recognised". Snapshotting at creation would have declared all 31 unposted demo drafts
(390.517 TND) against documents carrying no journal entry. Both gates ratified `post()`.

No other supplier-invoice path needs a snapshot point: every creation funnels through
`CreateSupplierInvoiceService::create()`; there is **no update/PATCH/delete route**; and
`SupplierInvoiceReceiptLinkingService` / `RematchDraftSupplierInvoicesCommand` mutate only match
provenance, never `quantity`, `unit_price`, `tax_rate` or `tax_amount`.

## 3. `PostedLineTaxSnapshotBuilder` — the contract

`app/Modules/Taxation/Domain/Services/PostedLineTaxSnapshotBuilder.php`, introduced in fix round 1 under
the orchestrator ruling **the declaration follows the LEDGER**.

**What it does.** Groups the document's persisted lines by their stored `tax_rate` and sums:

* base per bucket = Σ `document_lines.line_total`
* VAT per bucket = Σ `document_lines.recoverable_tax_amount` — the exact leg posted to 4456

**What it is not.** It is an aggregator, not a second tax engine: it applies no rate to any base and
makes no rounding decision. `TaxCalculationService::snapshotTaxDetails()` remains the writer, so a
purchase row is structurally identical to a sales row.

**Why it exists.** Two conventions produced two different numbers for the same money.
`CreateSupplierInvoiceService` rounds each line's VAT **half-up** (`CurrencyScale::bcround`) and the GL
posts that figure; `TaxCalculationService` accumulates at `scale+1` and **truncates once per rate
bucket**. Live: `10 × 12.601 = 126.010 × 19% = 23.9419` → ledger **23.942**, engine **23.941** (demo
tenant `SI-2026-0008`, `SI-2026-0020`). A declared figure that cannot be tied to the 4456 movement is an
unexplainable reconciliation break at audit.

**Why `recoverable_tax_amount` and not `tax_amount`.** `snapshotTaxDetails()` persists no
`is_recoverable` flag and the repository re-derives recoverability via
`COALESCE(tc.is_recoverable, true)`, so declaring gross line tax would claim VAT the ledger capitalised.
Today the two are always equal (`CreateSupplierInvoiceService` hardcodes `tax_recoverable => true`); the
builder **refuses** the moment they diverge, so the partial-recoverability lane cannot silently
over-claim when it lands.

**No stamp row, by construction.** The builder derives line tax only and can never emit an
`is_stamp_duty = true` row. That is protection, not omission: `scopeForDocumentType()` matches any
config whose `applicable_document_types` is an empty array, and `getSpecialLineItems()` counts stamp
rows with no document-type filter — so such a config would drop purchase timbre into the SALES
`stamp_duty_count`. Residual config hole ledgered `D-B19-2`.

**`divergences()` — one implementation, two callers.** The posting services throw on a non-empty list;
the backfill skips and reports. They can never take opposite positions on the same document.

1. header VAT decomposition: `line_tax_amount + stamp_duty_amount == tax_amount`
2. lines reconstruct `subtotal`
3. Σ `recoverable_tax_amount` == `line_tax_amount` (the deductible-share check)
4. header records VAT but no line carries a `tax_rate` (no bucket to declare it in)
5. no lines at all

Plus `currencyRefusal()` as a **precondition** (fix round 2 / N5): an empty document currency is a check
failure, never a default-scale guess — `getScaleSafe(null, 3)` returns its fallback only on an
`UnboundCompanyContextException`, so the same document would otherwise resolve scale 3 in the console
backfill and the company's scale in the HTTP writer, and every comparison above is a `bccomp` at that
scale.

**Deliberately NOT checked: `subtotal + tax_amount == total`.** Not a declaration invariant, and it has
a legitimate counter-example on this very arm — a supplier credit note carries the un-reversed purchase
timbre in `tax_amount` while `total` excludes it (`SupplierCreditNoteGlTest::test_timbre_is_not_reversed`:
subtotal 20.000 / tax_amount 4.400 / total 23.800). `total` is a payable figure the declaration never
reads. Found by the fixture, not by inspection — round 0 shipped that check.

**N4, RULED PARKED (treasury r2).** The builder `bcadd`s at the currency scale while the GL legs
accumulate at `scale+4`/`scale+1` and round once. Summing values that are **already at that scale**
(`recoverable_tax_amount` and `line_total` are written rounded by `CreateSupplierInvoiceService`) is
exact — no truncation occurs. The theoretical divergence needs sub-scale persisted amounts, which no
production path produces, and check 3 would refuse rather than mis-declare if one ever did. No change.

## 4. Repository

`supplier_invoice` and `supplier_credit_note` both join the document arm on the **INPUT** side.
Supplier invoices are **not** negated (positive = deductible, exactly like `expense`); supplier credit
notes **are** negated at aggregation, the same `-dtd.tax_base` / `-dtd.tax_amount` shape the OUTPUT arm
uses for `credit_note`. Rows are always stored positive — a `document_tax_details` row must never be
sign-overloaded.

Shipping the invoice arm alone would have converted a symmetric under-claim (both purchase arms
declaring zero — the DGI-safe direction) into a **net over-claim** for any tenant that returns goods to
a supplier, because `createSupplierCreditNoteEntry()` credits Σ `recoverable_tax_amount` back out of 4456
while the declaration went on claiming it. The two halves are not separable and were not separated.

## 5. Period safety on the live writers

Both posting services call `PeriodBackdatingGuardInterface::assertBackdatingPeriodIsOpen()`. Posting is a
**declaration mutation** now, and `issue_date` is unvalidated operator input, so a back-dated supplier
invoice could otherwise rewrite a CLOSED or FILED month silently. Both period tables are
absent-permits.

**Ordering matters (fix round 2 / N1).** The idempotency probe runs FIRST: a re-post writes nothing, so
refusing it for a declaration reason refuses a declaration-neutral call — and the AP-opening population
is back-dated by construction. `SupplierCreditNotePostingService` already ordered it this way.

**The refusal is actionable (fix round 2 / N2).** `PeriodBackdatingGuardInterface` gained
`backdatingRefusalDetail()` (primitives in, primitives out, like its sibling `backdatingRefusalCode()`).
`SupplierInvoiceController::post()` returns the shared renderer's envelope verbatim — `code`, `message`,
`document_number`, `return_date`, `period_label`, `recoverable` — plus `period` (id, bounds,
`reopenable`) and `remedies`. `reopenable` mirrors `VatPeriodManagementService::reopenPeriod()` exactly:
false for FILED, and false for a CLOSED period with any closed/filed successor. The refusal never offers
a remedy the system would reject.

The guard also consults `fiscal_periods` Closed/Locked. That is a **behaviour expansion** beyond the
original finding (defensible — the post writes a GL entry dated on `document_date`) and belongs in the
release note: any tenant that closes accounting months monthly will now see back-dated supplier-invoice
posts refused.

The stranded-draft consequence — no correction path pre-post — is `D-B19-4`.

## 6. Backfill procedure

`vat:backfill-tax-details`, supplier-document leg. **Owner-executed, never wired into a deploy step.**

```
tenants:run vat:backfill-tax-details          # DRY-RUN by default
# review the printed per-tenant census
tenants:run vat:backfill-tax-details --apply
```

**Why a backfill is needed at all:** documents posted before B-19 carry zero rows and cannot self-heal —
`post()` is idempotent and a re-post returns at its no-op without ever rewriting. The main
invoice/credit-note leg cannot reach them either: its scope requires an EXISTING row as proof of a real
`confirm()`. This leg is the mirror image.

**Scope:** `supplier_invoice` + `supplier_credit_note`, no existing row, `is_historical = false`, status
Posted/Paid **or** Cancelled-with-a-surviving-journal-entry.

**Excluded, each with its own census bucket:** already snapshotted · historical AR/AP openings (their VAT
was declared under the previous system) · drafts (no journal entry) · cancelled without a journal entry
(never posted) · any other status. The buckets **partition** the total.

**Period safety, three tiers:** FILED → skipped unless `--include-filed` (escalate to the accountant
instead) · CLOSED that cannot be reopened (a successor is already closed/filed, so `reopenPeriod()`
throws) → **refused unconditionally**, no flag, because there is no remedy the product can offer · CLOSED
and reopenable → written, with the reopen + re-close instruction.

**Local demo tenant, dry run (final):**

```
Population: 43 total = 12 in scope + 0 already snapshotted + 0 historical AR/AP opening
            + 31 draft + 0 cancelled without a journal entry + 0 in another status.
Scanned 12 in-scope document(s). Would snapshot 12. Nothing to declare (zero VAT) 0.
Unresolvable currency 0. Skipped 0.
  TND rate 19.00%: base 1652.020, VAT 313.884, 12 row(s)
  TOTAL deductible VAT delta (TND): 313.884
```

313.884 is exactly the posted/paid VAT total in the database. In round 0 two of those twelve were
refused on the millime divergence; the ledger-derived snapshot dissolved that residual.

Deploy step: LEDGER `S-23` + `PROMOTION-CHECKLIST-2026-08-26.md` §3.

## 7. Expense arm — verdict: not a defect, no fix made

The brief's deliverable 4 was "fix if same root cause, else file". Filed as `D-B19-1`.

The owner sheet's "149/156 expense documents lack tax-detail rows" was reproduced and explained: **all 7
posted expenses carrying positive VAT have their row (7/7)**. The 149 are 64 drafts (48 soft-deleted,
never posted) + 85 posted expenses whose `tax_amount` is NULL. `ExpenseService.php:631-633` early-returns
on a null/zero VAT amount by design, after the unconditional stale-row delete at `:620-626`, and is
called from both `post()` branches. **Different root cause.** Both gates independently reproduced this.

The residual risk is real but is an onboarding/UX gap, not this bug: an operator who omits VAT on a
VAT-bearing expense forfeits the deduction with no warning anywhere in the product.

## 8. Unresolved / carried forward

1. **The two rounding conventions still coexist.** B-19 no longer depends on it — the declaration reads
   the persisted amounts — but any future code that recomputes purchase VAT through the engine will
   disagree with the ledger again. Reconciling changes GL amounts for future invoices: treasury-owned lane.
2. **`is_recoverable` is not persisted on the snapshot** (fiscal I-3). The builder refuses any document
   whose recoverable and gross line VAT differ, so the over-claim is blocked — but when a
   partial-recoverability lane lands, the correct fix is to persist the flag rather than rely on the
   repository's `COALESCE(tc.is_recoverable, true)` re-derivation. Recorded in the builder's docblock.
3. **The TN mapping has no per-bucket deductible section** (fiscal I-2). `mapToDeclaration()` emits
   `base_*`/`vat_*` for output only; the whole input side collapses into `total_deductible_vat`. Supplier
   VAT lands in the only deductible slot that exists. Pre-existing and identical for `expense` — flagged
   so the gate record does not imply per-bucket deductible correctness was proven.
4. **`--include-filed` remains a foot-gun.** Documented in the signature, the class docblock, `S-23` and
   the checklist; nothing technically prevents an operator from passing it. Deliberate — it is an
   owner-executed command.
5. **Cancelled-after-post keeps declaring** (`D-B19-3`), and the refusal codes carry a `RETURN_` prefix
   (`RETURN_PERIOD_CLOSED` etc.) on a supplier-invoice surface — the shared `ReturnPeriodRefusalCode`
   vocabulary, kept verbatim rather than forked so both surfaces stay on one code set. Cosmetic; renaming
   would touch the return-note contract.
6. **Inherited reds, confirmed on clean dev and not chased:**
   `FranceTaxConfigurationSeederTest::seeds_five_french_vat_configs_with_20pct_default` (a `decimal:4`
   vs `decimal:2` cast expectation on `percentage_rate`, SQLite and PG alike), and three
   `SupplierInvoiceApiTest` cases that fail **on PostgreSQL only** because a fixture builds a
   `locations.code` longer than `varchar(20)` (`link_receipts_requires_pending_draft_invoice`,
   `pending_link_receipts_then_post_consumes_receipt_and_clears_gr_ir`,
   `post_invoice_first_missing_approval_permission_record_returns_domain_error`). Both verified against
   dev with none of this lane's changes applied.
