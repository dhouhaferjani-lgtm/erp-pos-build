## Summary

This commit is **documentation-only**. It changes exactly two files:
`docs/superpowers/audits/2026-06-22-balance-conventions-audit/work-list.md` and
`docs/superpowers/coordination/2026-06-22-balance-and-event-sourcing-hardening-autonomous-session.md`.
No PHP, no migration, no test, no event, no GL code is touched. The substantive claim under review
is the *classification decision*: that `UninvoicedDeliveryNoteService::generateYearEndAdjustment()` and
`generateReversalEntry()` are not production-reachable and therefore the H-7 draft-lifecycle remediation
can be DISCARDED for them with a forward-looking caveat.

I attempted to refute the reachability claim from multiple angles and **could not**. The claim holds.

### Reachability verification (independent of Codex's own scan)

1. **No caller in `app/`.** `rg -n "generateYearEndAdjustment|generateReversalEntry"` over `apps/api/app`
   returns only the two definitions in
   `app/Modules/Compliance/Services/UninvoicedDeliveryNoteService.php:214,298`. All other hits are
   `apps/api/tests/Feature/Compliance/UninvoicedDNReportTest.php` and an archived doc
   (`docs/_archive/tasks-2/sales-lifecycle-implementation.md`).
2. **The whole service is unwired**, not just the two writers. The read-only helpers
   (`getUninvoicedDeliveryNotes`, `calculateUninvoicedTotals`, `generateYearEndReport`) have no `app/`
   caller either — they are referenced only inside the service itself and by the two test files
   (`UninvoicedDNReportTest`, `UninvoicedDeliveryNoteScalingTest`), both of which resolve the service via
   `app(UninvoicedDeliveryNoteService::class)` directly.
3. **No HTTP surface.** `app/Modules/Compliance/Presentation/routes.php` exposes only fraud-settings,
   fraud-alerts, and NF525 export/verify/reprint endpoints. Compliance controllers are
   `AuditController`, `FraudAlertController`, `FraudSettingsController`, `Nf525ExportController` — none
   reference the service.
4. **No console/scheduled surface.** Compliance commands are `BackfillFiscalHashesCommand`,
   `ExportNf525JetCommand`, `VerifyFiscalChainsCommand` only. No scheduler entry references uninvoiced/year-end.
5. **No event/listener surface.** Compliance listeners are `DomainEventSubscriber`,
   `EnsureFraudSettingsOnCompanyCreated`, `OpenFraudAlertForShiftVariance`. None map to the service.
6. **No frontend/cross-app surface.** `rg` over `apps/web/src`, `apps/pos` for `uninvoiced`/year-end returns
   nothing. The repo-wide hits outside `apps/api/app` are: `packages/shared/types/generated.d.ts` (just the
   `'uninvoiced_revenue'` enum string in `SystemAccountPurpose`), `apps/api/docs/CODEBASE_AUDIT_REPORT.md`,
   and the two Document tests `DNConsolidationTest`/`DocumentConversionScenarioTest` — both of which query
   the `documents` table directly (`Document::where('type', DocumentType::DeliveryNote)`) and do **not** call
   the service.

### Consistency with acceptance criteria

The H-7 acceptance criteria (work-list.md:101-104) explicitly permit a discard:
> "Confirmed production operational writers either post immediately with a real actor/system actor
> **or are explicitly classified/deferred with rationale.**"

A DISCARD-with-rationale is therefore an in-spec outcome, not a skipped task. The recorded rationale is
accurate and the forward-looking caveat (any future caller must supply a real actor or explicit
system-posting policy before posting) is the correct guard, and is consistent with how the *posting*
sibling items (H-7.1..H-7.4) handled the actor question.

## MEDIUM

1. **Classification is correct but the underlying code remains a latent draft-lifecycle + actor hole, and
   the doc caveat is the only thing tracking it.** If `generateYearEndAdjustment()`/`generateReversalEntry()`
   are ever wired, they currently (a) create `JournalEntry` with `status = JournalEntryStatus::Draft`
   (`UninvoicedDeliveryNoteService.php:265,326`) and never post, (b) have no `posted_by`/actor concept at all,
   and (c) bypass the canonical `postEntry()` / balance-validation / `JournalEntryPosted` path that every
   H-7.1..H-7.4 sibling routes through. The discard note captures the actor concern but does not record that
   the writer also skips canonical posting semantics and balance validation. Recommend the residual ticket
   text name the canonical-post requirement explicitly, not just "actor or system-posting policy."

2. **No guard prevents silent re-wiring without revisiting the caveat.** The classification rests entirely on
   a point-in-time `rg` scan recorded in a markdown file. There is no test, deptrac rule, or CI assertion that
   fails if a future controller/command/listener begins calling these methods while they still emit Draft
   entries. A lightweight architecture test (e.g., assert the two methods have no non-test callers, or assert
   the service is not bound into any route/command) would make the discard durable. Optional, but it is the
   difference between "classified once" and "stays classified."

## LOW

1. The discard note says "referenced only by feature tests and archived docs." Strictly, the read methods of
   the same service are also referenced by `UninvoicedDeliveryNoteScalingTest`; the statement is true for the
   two named writers but the surrounding service is broader dead-weight than the note implies. Cosmetic.

2. `getUninvoicedDeliveryNotes()` uses a dual `whereNull('payload->invoiced_at')` /
   `orWhereJsonContains('payload', ['invoiced_at' => null])` predicate
   (`UninvoicedDeliveryNoteService.php:68-71`) whose Postgres-vs-SQLite JSON semantics differ. Out of scope for
   a discard classification (the method is unreachable), noted only so a future wiring effort revisits it.

## Verdict

**APPROVE.**

The reachability claim is true and independently confirmed across every plausible entrypoint. The DISCARD
is an explicitly permitted H-7 outcome, the rationale is accurate, and the forward-looking caveat is the
right guard. The commit introduces no money/precision change, no migration, no event mutation, and no GL
behavior change — so there is no fiscal or data-integrity surface to break. The two MEDIUM points are
durability/completeness improvements to the *tracking*, not defects in the decision, and do not warrant
blocking. No real-PG verification is required (no constraint/migration touched).
