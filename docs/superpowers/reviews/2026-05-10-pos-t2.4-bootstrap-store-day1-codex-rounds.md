# PR #106 — T2.4 Day 1 (bootstrapStore + withTimeout primitives) — Codex review trail

**Branch:** `feat/pos-t2.4-bootstrap-store-day1`
**Base:** `dev`
**Reviewer:** Codex CLI (`codex review --base dev`)
**Final state:** 8 rounds, APPROVE.

The state machine kickoff doc under-specified several integration concerns. Codex iteratively surfaced them; each round closed real correctness or security gaps. The final shape is materially safer than the round-1 baseline.

## Round 1 — APPROVE-WITH-MINOR-EDITS-APPLIED (2 P2 closed)

### P2-1 — Settle aborted timeout races instead of hanging

`withTimeout`'s abort handler only cleared the timer and left the outer promise pending forever. Any caller awaiting the helper would hang indefinitely after abort once the underlying work hung.

**Closure (`e0ffd60f`):** introduced `BootstrapAbortedError` (name `'AbortError'`, in SAFE_ERROR_NAMES); abort now rejects the outer promise. Internal `settled` flag makes timer/abort/resolve/reject mutually exclusive — no double-settle.

### P2-2 — Reset completed progress on fresh bootstrap starts

`start()` did not reset `lastSuccessfulPhase` to null. A second `start()` after a previous `ready` run that then failed in an earlier phase would leave the stale marker, and a follow-on `retry()` would skip past the actually-failing phase to falsely promote `ready`.

**Closure:** `start()` now clears `lastSuccessfulPhase` and `error` before running. `retry()` / `skipWithCache()` deliberately preserve them.

## Round 2 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P1 + 1 P2 closed)

### P1 — Gate dependent phases on auth and company state

The state machine advanced unconditionally through every phase. From a logged-out boot it would call `fetchCompanies` without a token (401 → bootstrap error instead of login screen). From a multi-company state with no `companyId` selected, it would call terminal APIs without `X-Company-Id`.

**Closure (`036eaddf`):** new `canEnterPhase(phase)` guard mirrors the existing AppRouter gates. Failed gate exits with `phase='ready'` and clears error — the orchestration is "as ready as it can be" given the current auth/company state.

### P2 — Reject already-aborted timeout signals

If the caller passes an `AbortSignal` already aborted at call time, `addEventListener('abort', ...)` never fires, so `withTimeout` waits the full duration.

**Closure:** check `signal?.aborted` at the top of the Promise constructor and short-circuit immediately.

## Round 3 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed)

### P2 — Drain wrapped promise on pre-aborted signals

The pre-abort short-circuit returned before attaching a rejection handler to the wrapped promise. A later rejection from the underlying init work would become an unhandled rejection.

**Closure (`770eda5c`):** drain the wrapped promise with `.catch(() => {})` before bailing out, mirroring the normal abort path's settled-flag guard.

## Round 4 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed) — REVERTED IN R5

### P2 — Set a PIN fallback when skipping the PIN check

When the recoverable failing phase was `checking-pins`, `skipWithCache` marked bootstrap `ready` without changing `useOperatorStore.hasPins`, leaving AppRouter on the loading screen.

**Round-4 closure (`5747401b`):** `skipWithCache` flipped `hasPins=false` for the checking-pins branch.

**Round-5 reverted this** — see below. The flip introduced a security risk.

## Round 5 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P1, security)

### P1 — Avoid treating an unknown PIN check as no PINs

Round-4's `hasPins=false` flip routed the cashier to `PinSetupPage` (first-time setup), not PIN entry. If PINs already existed on the terminal, that bypass would let any cashier create a fresh PIN without going through the operator gate.

**Closure (`44fa464d`):** marked `checking-pins` non-recoverable. The kickoff doc's "falls through to PIN entry" claim was wrong for the actual UI routing semantics. `operatorStore.checkHasPins` already does an internal API → SQLite fallback; if even SQLite fails (the only path that gets here), we genuinely cannot determine PIN state and must not guess.

## Round 6 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P1 + 1 P2 closed)

### P2 — Avoid blocking cached offline boots on company refresh

The unconditional `fetchCompanies` call would reject for a returning cashier with cached `TOKEN`/`USER`/`COMPANIES` who boots offline, pushing the bootstrap store to error even when the cached company list is fully usable.

**Closure (`125851f4`):** `runPhase('fetching-companies')` now checks `useAuthStore.getState().companies.length > 0` first and skips the network call entirely when the cache is non-empty. Mirrors the existing AppRouter contract — `fetchCompanies` only fires from the empty-companies recovery branch.

### P1 — Treat unknown PIN state as a bootstrap failure

`operatorStore.checkHasPins` swallows API + SQLite failures and resolves `false` without updating store state. A naive `await` would mark `checking-pins` as successful and downstream routing would send the cashier to first-time `PinSetupPage`. The non-recoverable policy from round-5 was bypassed via this path.

**Closure:** after the `await`, read `useOperatorStore.getState().hasPins`. If still `null`, throw — the lookup did not produce a definitive answer; the phase fails non-recoverably.

## Round 7 — APPROVE-WITH-MINOR-EDITS-APPLIED (1 P2 closed)

### P2 — Compute recoverability from available cache

The static `RECOVERABLE` map advertised "Use cached data" for phases where no cached fallback actually existed. `fetching-companies` only ran when the cache was empty (from round-6), so its failure meant the recovery cache was empty too. `fetching-terminal` was statically true regardless of whether SQLite had a cached record.

**Closure (`fa0d80c7`):** replaced the static map with `phaseRecoverable(phase)` computed at error time. `authenticating` / `fetching-companies` / `checking-pins` are always non-recoverable; `fetching-terminal` is recoverable iff `useTerminalStore.getState().terminal !== null`.
