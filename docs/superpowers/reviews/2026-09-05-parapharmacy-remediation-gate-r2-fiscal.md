**M-1 [MAJOR — blocks spec approval] v2 decides, without an owner row, that `SALE_RECEIPT` gains a sealed `repository_id`, while the structurally identical lot-field question is an OPEN owner decision (D7).** CONFIRMED.
- Spec line: 143 — "Recommended W2 transport is resolved `repository_id` plus the necessary binding revision on a **new compatible SALE_RECEIPT version**"; and 143 again — "R3 forbids iteration 1 **lot** payload changes, not an independently gated W2 tender version". §2.3 (spec:55-66) has no row for this; §5 (spec:316) lists W2's prerequisites as "D2/RD3, writer/binding census and fiscal version cutover review" — D2 is "which tenders are enabled" (spec:58), not a transport choice, and RD3 is the fallback reversal (spec:65).
- Source: the parallel choice for lots is D7 (spec:63), an OPEN owner row, and R3's own words are "the sealed payload is unchanged in iteration 1" (handover `HANDOVER-parapharmacy-remediation-codex-spec-fix-round-2026-09-05.md:32`).
- Failure scenario: Fable dispatches W2 from an accepted spec; a lane ships `SALE_RECEIPT` vN+1 carrying a treasury configuration id inside the fiscal hash. The owner later rules that money destination must not be part of the sealed fiscal record (a defensible position — it is Treasury policy, not a fiscal fact about the sale). The bytes are immutable by rule 8/spec:88, so the only remedy is a third version and a permanently mixed fleet.
- Minimum correction: add row **D8/RD5 — "sealed tender destination on a new `SALE_RECEIPT` version vs. an unsealed authored binding carried in sync metadata"**, status OPEN, with the same tradeoff treatment D7 gets, and cross-reference it from §5's W2 prerequisites. Keep the current recommendation as the recommended default.
- Blocks: **spec approval** (cheap: one table row plus one dependency cell).

**M-2 [MAJOR — blocks plan] The ACCOUNT_PAYMENT precedent v2 tells W2 to copy is enforced only on the server half; the device half seals the field as optional and unvalidated.** CONFIRMED.
- Spec line: 143 — "`TreasuryAccountPaymentBridge.php:406–418` requires and validates a sealed repository reference within tenant/company."
- Source: server half confirmed — `apps/api/app/Modules/Treasury/Application/Projections/TreasuryAccountPaymentBridge.php:406-409` throws `payment_repository_required` when `$view->payment->repositoryId === null`, then scopes the lookup by tenant+company+`is_active`. Device half contradicts it — `apps/pos/src/lib/fiscal/FiscalEventEngine.ts:2844` validates the field with `assertOptionalNonEmptyStringAt(payment, 'repository_id', …)` inside `validateAccountPaymentPayment()` (`:2824`): **optional, and not even UUID-shaped**; the frozen canonical vector seals it as null (`apps/pos/src/lib/fiscal/payloads/AccountPaymentPayload.ts:143`, byte-frozen string at `:173`), and the type is `string | null` (`:56`).
- Failure scenario: W2 copies the precedent onto the highest-volume event in the system. A terminal on a stale/empty policy cache seals `repository_id: null` (legal at the device validator), the device validator passes, the chain seals, and every card leg on that terminal dead-letters at the receipt bridge with `payment_repository_required`. ## Verdict rationale

The fiscal core of v2 is sound: no sealed-bytes violation, no invented refund/void event, no no-arg currency-scale resolution proposed in a worker path, correct idempotency reasoning, correct queue coverage, and a citation set that survived line-by-line checking. Five MAJORs stand, four of which are omissions that block only the execution plan. **M-1 alone blocks spec approval**, because an accepted spec would carry a decided sealed-payload change that the owner never ruled on — the same class of silent decision this gate exists to catch. All five corrections are textual and cheap.
