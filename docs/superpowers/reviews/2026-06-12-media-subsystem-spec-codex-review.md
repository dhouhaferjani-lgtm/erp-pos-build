# Media Subsystem Spec Review

Date: 2026-06-12  
Reviewer: Codex adversarial review  
Specs reviewed:
- `docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md`
- `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md`

## 1. Architectural Soundness

**FINDING [severity: HIGH]**: The specs assert that the asset library naturally belongs in `Media` because "`Media` covers all media" and Product will consume it only through `CatalogMediaQueryInterface` (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:108-124`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:78-105`). The actual `Media` module is not a generic DAM today; it is a document-attachment module. Its only domain model is `DocumentAttachment`, which imports `Document`, `User`, and `Tenant` directly (`apps/api/app/Modules/Media/Domain/DocumentAttachment.php:5-13`), is hard-wired to `document_attachments` (`apps/api/app/Modules/Media/Domain/DocumentAttachment.php:41-60`), and its routes are explicitly "Document attachment management routes" nested under `documents/{document}` (`apps/api/app/Modules/Media/routes.php:10-41`). The architecture reference permits cross-module communication only through `Shared/Contracts`, events, or public services and forbids direct model/entity imports across modules (`.claude/context/architecture.md:45-52`). Putting catalog PIM media into this module without first separating the document-attachment bounded context over-couples fiscal document attachments and catalog assets under one provider and route namespace.

**FINDING [severity: HIGH]**: The specs ignore that this repo already has a `Catalog` module for product variants, attributes, composite items, and recipes (`apps/api/app/Modules/Catalog/Domain/Entities/ProductVariant.php:5-15`, `apps/api/app/Modules/Catalog/Application/DTOs/ProductVariantData.php:5-10`). Product variants already carry `image_url` as catalog data (`apps/api/app/Modules/Catalog/Domain/Entities/ProductVariant.php:17-31`, `apps/api/app/Modules/Catalog/Domain/Entities/ProductVariant.php:57-71`). The program spec calls category `image_path` and variant `image_url` bare strings a gap (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:42-47`), and the Stage 1 spec includes `PRODUCT_VARIANT` and `CATEGORY` owner types (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:66-73`), but its actual API and delivery plan only preserve `/products/{product}/images` and product seeding (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:130-155`). The module-placement decision is incomplete because it never explains why catalog-owned asset linking does not belong in the existing `Catalog` module, or how `Catalog` variant/attribute/composite image strings migrate to the new asset model.

**FINDING [severity: HIGH]**: `ProductData` cannot "consume" a query contract as written. The spec says `ProductData` consumes `CatalogMediaQueryInterface` to populate `primary_image_url` and `media[]` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:107-128`). The actual DTO has a static `fromModel(Product $product)` factory and computes `primary_image_url` from an eager-loaded `primaryImage` relation and a route helper (`apps/api/app/Modules/Product/Application/DTOs/ProductData.php:48-89`). Controllers call `ProductData::fromModel()` directly for show/create/update responses (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:268-274`, `apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:373-381`, `apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:514-522`), and index delegates DTO construction through pagination formatting after eager-loading `primaryImage` (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:67-101`). A Spatie Data DTO is not a service container boundary. The spec must move media composition into controller/application service/query orchestration, or define an explicit DTO input shape; otherwise the proposed contract seam is not implementable without service-location or hidden dependencies.

## 2. Three-Table Asset/Rendition/Link Model vs Simpler Alternatives

**FINDING [severity: MEDIUM]**: The 3-table model is more than Stage 1 needs and the specs admit part of it is deferred. Stage 1 is image-only (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:17-25`), but it creates future enums for documents, videos, external videos, and 360 spins (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:32-52`), role values for datasheets/manuals/video posters/spins/swatches (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:66-70`), and `channel`/`locale` columns while explicitly deferring channel/locale resolution (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:91-95`, `docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:178-185`). The current image model needs only `product_id`, storage fields, dimensions, `sort_order`, and `is_primary` (`apps/api/database/migrations/tenant/2025_12_29_155412_create_product_images_table.php:14-31`). If channel/locale resolution and non-image serve semantics are out of scope, they should not be part of Stage 1 invariants or acceptance criteria.

**FINDING [severity: HIGH]**: The rendition table design contradicts the stated JPEG fallback requirement. The spec defines `media_renditions` with `name`, `format`, and "Unique (`media_asset_id`,`name`)" (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:56-64`), then leaves open "whether to keep both WebP and JPEG fallback" (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:191-198`). A unique key on only asset+name cannot store both `THUMBNAIL` WebP and `THUMBNAIL` JPEG fallback. The existing implementation only has `sm` and `md` WebP variants (`apps/api/app/Modules/Product/Application/Services/ImageVariantService.php:11-17`, `apps/api/app/Modules/Product/Application/Services/ImageVariantService.php:43-84`), so the fallback is not current parity. The schema must either make fallback explicitly out of scope or use a uniqueness key that includes format.

**FINDING [severity: MEDIUM]**: Soft-delete and cleanup semantics are under-specified for a reused asset model. The spec says `media_assets` soft-delete and `media_renditions.media_asset_id` FK cascades (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:27-59`) but later lists "Soft-delete cascade policy for renditions/attachments" as an open question (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:191-198`). Current `ProductImageService::delete()` has explicit behavior: if the primary image is deleted, it promotes the next image, soft-deletes the row, and after commit deletes original plus variant files (`apps/api/app/Modules/Product/Application/Services/ProductImageService.php:134-166`). A reusable asset linked to many owners cannot safely inherit that behavior. Stage 1 is not ready until it specifies whether deleting a link, deleting an asset, and replacing a primary delete binary files, detach links, or leave orphaned renditions.

## 3. Replacing `product_images` With No Backfill

**FINDING [severity: BLOCKER]**: The "no backfill - there is no production data" premise is UNVERIFIED and cannot be accepted from the repository. The specs state this as a locked decision (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:54-56`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:1-8`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:75-77`). The only verified "no production tenant data" statement in architecture context is about the 2026-05-25 database-per-tenant flip, not about product images on 2026-06-12 (`.claude/context/architecture.md:54-70`, `.claude/context/architecture.md:88-88`). The code has a real tenant migration for `product_images` (`apps/api/database/migrations/tenant/2025_12_29_155412_create_product_images_table.php:14-44`), upload paths that create rows and S3 objects (`apps/api/app/Modules/Product/Application/Services/ProductImageService.php:32-90`), and seeders that insert URL-disk images (`apps/api/database/seeders/ProductImagePlaceholderSeeder.php:20-83`). Dropping the table without a data audit query or backfill/explicit discard procedure is data-loss by design.

**FINDING [severity: BLOCKER]**: The specs materially undercount `product_images` consumers. The program spec says replacing `product_images` touches the working gallery, `ProductData.primary_image_url`, and demo seeders (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:187-191`); the Stage 1 spec preserves only authenticated `/products/{product}/images` routes and seeders (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:130-155`). Actual code also has public e-commerce image routes (`apps/api/app/Modules/Product/routes.php:140-147`, `apps/api/app/Modules/Product/Presentation/Controllers/PublicProductImageController.php:20-69`), POS sync image URLs (`apps/api/app/Modules/POS/Presentation/Controllers/SyncController.php:62-83`), ZIP product-image import (`apps/api/app/Modules/Import/Presentation/Controllers/ImportController.php:78-106`, `apps/api/app/Modules/Import/Presentation/Controllers/ImportController.php:532-565`), the async image import job (`apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:21-31`, `apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:64-150`), an import enum value (`apps/api/app/Modules/Import/Domain/Enums/ImportType.php:7-14`), a variant-generation maintenance command (`apps/api/app/Console/Commands/GenerateProductImageVariants.php:13-69`), generated shared TypeScript including `product_images` and `primary_image_url` (`packages/shared/types/generated.d.ts:670`, `packages/shared/types/generated.d.ts:1422`), and POS SQLite image caching (`apps/pos/src/lib/db/migrations.ts:232-242`, `apps/pos/src/lib/images/imageCache.ts:38-61`, `apps/pos/src/lib/images/imageCache.ts:188-192`). The implementation plan would break these paths unless each one is migrated.

**FINDING [severity: HIGH]**: Dropping `ProductImage` is not just a table swap; it removes a domain model and relations used throughout Product. `Product` exposes `images()` and `primaryImage()` relations against `ProductImage` (`apps/api/app/Modules/Product/Domain/Product.php:287-305`), `ProductData` depends on the `primaryImage` relation (`apps/api/app/Modules/Product/Application/DTOs/ProductData.php:73-81`), and `ProductImageController` uses `ProductImage` in return types, queries, validation, and route operations (`apps/api/app/Modules/Product/Presentation/Controllers/ProductImageController.php:7-15`, `apps/api/app/Modules/Product/Presentation/Controllers/ProductImageController.php:39-46`, `apps/api/app/Modules/Product/Presentation/Controllers/ProductImageController.php:128-142`, `apps/api/app/Modules/Product/Presentation/Controllers/ProductImageController.php:173-185`). The specs do not enumerate these model/relation removals or the migration sequence needed to keep the app compiling while the table is dropped (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:181-189`).

## 4. Preserved API Compatibility Facade

**FINDING [severity: HIGH]**: The compatibility facade is underspecified because the old `{image}` identifier had exactly one meaning: a `product_images.id`. The new model has at least `media_assets.id` and `media_attachments.id`, but the spec does not say which one is accepted by `GET /products/{product}/images/{image}/download` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:130-145`). Current web code passes `image.id` from `GET /products/{id}/images` into download/update/delete calls (`apps/web/src/features/products/api/productImages.ts:7-35`, `apps/web/src/features/products/api/productImages.ts:41-93`, `apps/web/src/features/products/components/ProductImageGallery.tsx:101-110`). Current backend resolves that ID through `ProductImage::query()->where('product_id', ...)->where('id', ...)` (`apps/api/app/Modules/Product/Presentation/Controllers/ProductImageController.php:173-185`). If `{image}` becomes asset ID, reuse across owners makes product scoping ambiguous. If it becomes attachment ID, the facade leaks link IDs as "image IDs" forever. The spec must choose and document the compatibility contract.

**FINDING [severity: HIGH]**: The preserved API list omits the public product-image API. The spec lists preserved authenticated routes under `/products/{product}/images` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:130-139`) but says nothing about `/api/v1/public/products/{product}/images` (`apps/api/app/Modules/Product/routes.php:140-147`). The public controller returns a different shape with public URLs and no auth, guarded by `is_active_for_ecommerce` (`apps/api/app/Modules/Product/Presentation/Controllers/PublicProductImageController.php:20-69`). This is not optional compatibility: it is documented as a cross-tenant-by-design public storefront integration in code attributes (`apps/api/app/Modules/Product/Presentation/Controllers/PublicProductImageController.php:23-49`). Stage 1 cannot claim preserved behavior while leaving this route unmapped.

**FINDING [severity: MEDIUM]**: The facade deliberately carries the old `sm|md` vocabulary while the new model introduces named purposes (`THUMBNAIL|SMALL|WEB|ZOOM`) (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:81-95`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:132-145`). Current clients build download URLs without a variant in the gallery (`apps/web/src/features/products/api/productImages.ts:88-93`, `apps/web/src/features/products/components/ProductImageGallery.tsx:104-110`), while `ProductData` and POS sync explicitly request `variant=sm` (`apps/api/app/Modules/Product/Application/DTOs/ProductData.php:73-81`, `apps/api/app/Modules/POS/Presentation/Controllers/SyncController.php:71-78`). This is acceptable only as a short-lived adapter, but the spec leaves retirement to "Stage 3 may" (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:140-145`). That creates a second permanent media API unless Stage 1 includes a deprecation/removal criterion.

## 5. Single-Primary Invariant

**FINDING [severity: BLOCKER]**: App-level enforcement of "one primary per owner/channel/locale" is unsafe under concurrent requests. The Stage 1 spec repeats the current app-level invariant (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:66-73`). Current code already shows the race: upload sets `is_primary` by counting existing images inside a transaction without locking the product or image set (`apps/api/app/Modules/Product/Application/Services/ProductImageService.php:61-90`), and `setPrimary()` flips other rows then updates the target row without a database uniqueness constraint (`apps/api/app/Modules/Product/Application/Services/ProductImageService.php:102-112`). The current migration even documents that the single-primary rule is application-level (`apps/api/database/migrations/tenant/2025_12_29_155412_create_product_images_table.php:41-44`). This repo is PostgreSQL-first under database-per-tenant (`.claude/context/architecture.md:60-70`; `apps/api/config/tenancy.php:68-84`), and it already uses partial unique indexes for similar invariants, e.g. one default product variant per product (`apps/api/database/migrations/tenant/2026_06_02_100003_create_product_variants_table.php:38-43`). The new invariant needs a partial unique index, not only service logic.

**FINDING [severity: HIGH]**: The proposed unique domain is not fully defined for nullable `channel` and `locale`. The spec says one `PRIMARY` per (`owner`,`channel`,`locale`) while `channel` and `locale` are nullable (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:66-73`), and it separately says channel/locale resolution is deferred (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:91-95`, `docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:178-185`). PostgreSQL unique indexes treat `NULL` values as distinct unless explicitly normalized or using `NULLS NOT DISTINCT`. Without an explicit index expression or rule such as `COALESCE(channel, '')`, the "global primary" case can still have multiple rows with `NULL` channel/locale. The spec must define the database invariant precisely.

## 6. Database-Per-Tenant Implications

**FINDING [severity: BLOCKER]**: `GenerateRenditions` is specified as a DB-writing queue job but no tenant rebinding contract is specified. The program spec says upload goes through `UPLOADED -> PROCESSING -> READY` and a queued `GenerateRenditions` job generates rows (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:97-106`), and Stage 1 tests require it to produce rendition rows and set `READY` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:164-169`). Under the repo's database-per-tenant architecture, tenant migrations run per physical DB and the default connection is swapped by Stancl (`.claude/context/architecture.md:54-70`; `apps/api/config/tenancy.php:38-43`, `apps/api/config/tenancy.php:68-84`). The existing `GenerateImageVariants` job is safe only because it explicitly performs zero DB queries and works from storage path/disk only (`apps/api/app/Modules/Product/Application/Jobs/GenerateImageVariants.php:15-18`, `apps/api/app/Modules/Product/Application/Jobs/GenerateImageVariants.php:39-77`). Jobs that touch tenant DBs use `BindsTenantContext` and must carry `tenantId` (`apps/api/app/Jobs/Concerns/BindsTenantContext.php:11-39`, `apps/api/app/Jobs/Concerns/BindsTenantContext.php:62-75`), as `ProcessProductImageImport` does (`apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:21-31`, `apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:53-68`). The spec must require `GenerateRenditions` to carry `tenantId`, use `BindsTenantContext`, and tenant-scope every query.

**FINDING [severity: HIGH]**: Storage tenancy is under-specified. The spec says `storage_disk` abstracts S3/public/url and serving reuses `Storage::disk($disk)->response()` (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:97-106`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:101-105`). Actual Stancl filesystem tenancy suffixes `local` and `public`, but not `s3` (`apps/api/config/tenancy.php:103-116`), and `suffix_storage_path` is enabled (`apps/api/config/tenancy.php:129-147`). Existing product images use `s3` with an explicit tenant/product path (`apps/api/app/Modules/Product/Application/Services/ProductImageService.php:41-59`), while document attachments use `local` with `attachments/{tenant}/{document}` (`apps/api/app/Modules/Media/Application/Services/AttachmentService.php:56-75`, `apps/api/app/Modules/Media/Application/Services/AttachmentService.php:181-198`). The spec must define per-disk path rules, whether `s3` is intentionally not bootstrapped by Stancl, and how external URL assets are validated and scoped.

**FINDING [severity: MEDIUM]**: Migration placement is correctly stated but the table definitions are internally inconsistent. The Stage 1 spec correctly says tenant DB migrations go under `apps/api/database/migrations/tenant/` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:27-31`), matching the architecture reference (`.claude/context/architecture.md:67-70`) and existing `product_images`/`document_attachments` tenant migrations (`apps/api/database/migrations/tenant/2025_12_29_155412_create_product_images_table.php:14-44`, `apps/api/database/migrations/tenant/2025_12_14_000001_create_document_attachments_table.php:11-32`). But the same paragraph says all new tables have `tenant_id`, while the explicit `media_renditions` column list omits `tenant_id` (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:27-30`, `docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:56-59`). In db-per-tenant this may be acceptable through the asset FK, but the spec must choose: either every table has tenant_id for defense-in-depth/query tests, or renditions intentionally inherit tenant scope only through `media_asset_id`.

## 7. Missed, Under-Specified, or Over-Engineered

**FINDING [severity: HIGH]**: Category and variant media are named as first-class gaps but not delivered. The program spec says category `image_path` and variant `image_url` are bare strings, not real assets (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:42-47`), and Stage 1 includes `CATEGORY` and `PRODUCT_VARIANT` owner types (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:66-70`). Actual `Category` has `image_path` and `CategoryData` converts it through `asset('storage/...')` (`apps/api/app/Modules/Product/Domain/Category.php:19-58`, `apps/api/app/Modules/Product/Application/DTOs/CategoryData.php:20-45`), and actual `ProductVariant` has `image_url` persisted and exposed (`apps/api/app/Modules/Catalog/Domain/Entities/ProductVariant.php:17-31`, `apps/api/app/Modules/Catalog/Application/DTOs/ProductVariantData.php:22-57`). The Stage 1 API surface only covers product images (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:130-145`). Either remove these owner types from Stage 1 or specify the migration/API/query behavior for categories and variants.

**FINDING [severity: HIGH]**: Product image import is a missing migration path. The UI and API accept `product_images` ZIP imports (`apps/web/src/features/import/pages/ImportDashboardPage.tsx:35-51`, `apps/web/src/features/import/pages/ImportWizardPage.tsx:71-73`, `apps/api/app/Modules/Import/Presentation/Controllers/ImportController.php:78-106`), the import job is tenant-aware and delegates to `ProductImageImportService` (`apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:53-89`), and that service uploads through `ProductImageService` (`apps/api/app/Modules/Product/Application/Services/ProductImageImportService.php:24-26`, `apps/api/app/Modules/Product/Application/Services/ProductImageImportService.php:210-245`). The specs mention replacing seeders only (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:147-155`) and do not mention import at all. Dropping `ProductImageService` without redesigning this import pipeline breaks a user-visible ingestion path.

**FINDING [severity: MEDIUM]**: Security for future catalog documents/videos is deferred too casually while Stage 1 creates the storage and URL primitives they will use. The program spec correctly treats document preview as stored-XSS risk and forbids inline SVG (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:143-150`, `docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:187-194`), but catalog media creates `DOCUMENT`, `VIDEO`, `EXTERNAL_VIDEO`, `EXTERNAL_URL`, and `external_url` now (`docs/superpowers/specs/2026-06-12-catalog-media-backend-foundation-design.md:32-52`) and marks external URL assets `READY` immediately (`docs/superpowers/specs/2026-06-12-media-subsystem-architecture-design.md:99-106`). Current attachment upload validates MIME types in both request and service (`apps/api/app/Modules/Media/Presentation/Requests/UploadAttachmentRequest.php:20-37`, `apps/api/app/Modules/Media/Application/Services/AttachmentService.php:151-165`). The catalog spec must define Stage 1 allow-lists, external URL validation, and future non-image rejection points so untrusted document/video paths cannot enter the asset table ahead of the safe preview/viewer work.

## SUMMARY

Verdict: REJECT

Required changes before implementation should proceed:

1. Replace the unverified "no backfill/no production data" premise with an explicit tenant-data audit, discard approval, or migration/backfill plan.
2. Enumerate and migrate every existing consumer: authenticated image CRUD, public e-commerce image routes, POS sync/cache, product image ZIP import, variant generation command, generated shared types, tests, and seeders.
3. Define the compatibility facade ID contract: whether legacy `{image}` maps to attachment ID, asset ID, or a stable alias table.
4. Enforce single-primary with a PostgreSQL partial unique index that handles nullable channel/locale semantics explicitly.
5. Specify tenant-aware queue behavior for `GenerateRenditions`: tenantId payload, `BindsTenantContext`, and tenant-scoped queries.
6. Resolve module ownership explicitly: either split generic catalog media from document attachments inside `Media`, or justify why the existing `Catalog` module is not the bounded context for catalog asset links.
7. Fix the rendition schema before implementation: decide JPEG fallback scope and include `format` in uniqueness if fallback is required.
8. Decide Stage 1 scope for category/variant/composite/attribute image strings; do not include owner types whose migration/API behavior is unspecified.
9. Define storage-path and disk tenancy rules for local/public/s3/url assets under database-per-tenant.
10. Define Stage 1 security gates for external URLs and rejected non-image asset types before future document/video support is enabled.
