## 1. What was wrong, and what changed

The device computed VAT per rate from the LINE roll-up and sealed it, then applied the transaction
discount to the **total only**. On a 640.000 TND ticket with a 50.000 remise it sealed base 600.000 /
VAT 71.000 and collected 590.000. `EloquentVatDataRepository` reads those sealed rows verbatim, so the
tenant over-declared `discount × rate/(1+rate)` of output VAT on an immutable, hash-chained document,
and the printed ticket showed the customer a VAT figure they had not paid.

Under the owner ruling the taxable base excludes a remise granted on the invoice, ventilated pro-rata
per rate. The fix is a new sealed version — **`SALE_RECEIPT` `event_version = 5`** — and is strictly
forward-only: v1..v4 stay parseable and projectable forever.

## 3. Worked example (the ruling's own: 7 / 13 / 19 % + exempt, 50.000 TND remise, scale 3)

Cart, TTC per line: 19 % → 238.000 · 13 % → 226.000 · 7 % → 107.000 · exempt → 69.000. **Σ gross 640.000.**

| rate | gross_r | exact share | floor | remainder | **disc_r** | net_ttc_r | **base_r** | **vat_r** |
|---|---|---|---|---|---|---|---|---|
| 19.00 | 238.000 | 18.59375 | 18.593 | .750 **← +1 ulp** | **18.594** | 219.406 | **184.375** | **35.031** |
| 13.00 | 226.000 | 17.65625 | 17.656 | .250 | **17.656** | 208.344 | **184.375** | **23.969** |
| 7.00 | 107.000 | 8.359375 | 8.359 | .375 | **8.359** | 98.641 | **92.188** | **6.453** |
| 0.00 (exempt) | 69.000 | 5.390625 | 5.390 | .625 **← +1 ulp** | **5.391** | 63.609 | **63.609** | **0.000** |
| **Σ** | **640.000** | 50.000 | 49.998 | **residue 0.002** | **50.000** | **590.000** | **524.547** | **65.453** |

- The residue is exactly 2 ulps and lands on the two largest remainders (.750 and .625).
- `Σ base + Σ vat = 524.547 + 65.453 = 590.000` = the total tendered. ✓
- Pre-D-1 the same ticket sealed **base 569.000 / VAT 71.000** — 5.547 TND of VAT the customer never paid.
- Exempt participates in the allocation and carries base only, never VAT.

## 5. Version-gate matrix (forward-only)

The canonical payload carries no application version, and adding one would change the sealed bytes of every
receipt. `devices.app_version` is user-scoped and set at login, with no reliable link to the authoring
terminal. So the gate uses the fact the chain ALREADY records: **once a terminal has sealed any
`SALE_RECEIPT` at `event_version >= 5`, it is on the new build and may never author `<= 3` again.** Monotonic
per terminal, derived from signed data rather than an asserted header.

| device build | payload shape declared | disposition |
|---|---|---|
| old (no v5 on this terminal) | v3 pre-discount base | **ACCEPTED** — projects as it always did; `discount_allocated` NULL |
| old | v3 + non-zero remise | **ACCEPTED** — pre-D-1 semantics, honestly recorded |
| new (terminal has a v5 watermark) | v3 pre-discount base | **REFUSED** `sale_receipt_version_downgrade:` — stored, NOT projected |
| new | v5 post-remise base | **ACCEPTED** |
| new | v5 declared, PRE-discount base inside | **REFUSED** `payload_total_arithmetic_mismatch` (then `payload_aggregate_consistency:…` as the belt) |
| any | v4 REFUND | **ACCEPTED** — exempt; v4 is a sibling fan-out of v3, not a predecessor of v5 |
| other terminal, same tenant/company | v3 | **ACCEPTED** — the watermark is per terminal |

A refusal routes as a parse failure, the same path every other payload-contract violation takes: bytes kept
verbatim, event stored, projection withheld. Nothing is silently dropped and nothing is rewritten.

## 6. 100 %-comp receipts (G3-A fold-in)

`pos_receipt_payments CHECK (amount > 0)` refused the `0.000` tender leg the device emitted for a full comp,
so `PosCoreReceiptProjection` refused the whole receipt on PostgreSQL, upstream of the GL bridge.

- **Device**: `receiptService` filters zero-amount tender legs out of the canonical payload AND `payments_json`.
- **Engine + server validator**: an empty `payments[]` is accepted **only** at v5 and **only** when `total`,
  `subtotal` and `vat_total` are all canonical zero with a positive remise. v3 never accepts it.
- **DB CHECK kept, untouched** — satisfied by absence. The projection test proves it is still in force by
  attempting the very insert the device used to make (SQLSTATE 23514).
- Every group lands on exactly `net == vat == 0` because the allocator clamps the split inside the group's own
  line sums — no ±1 ulp residue.

**(b) `2026_08_25_090100_widen_pos_receipts_totals_check_for_post_remise_base_d1` — MIGRATION-BEARING.**
`pos_receipts_totals` was `total = subtotal + tax_amount − discount_amount + rounding`. At v5 the header
aggregates are post-remise, so the identity becomes `total = subtotal + tax_amount + rounding`. BOTH forms must
pass forever — historical rows and rows from not-yet-upgraded devices satisfy the first, v5 rows the second —
so the constraint becomes their disjunction. With `discount_amount = 0` they coincide, i.e. it is a no-op for
almost every existing row and never weakens them. The tight per-version identity is enforced upstream and
unconditionally by `validateSaleReceiptAggregateConsistency()`, which knows the version; a CHECK cannot.

**Per-tenant pre-flight census — MUST be 0 before the deploy:**
```sql
SELECT count(*) FROM pos_receipts
 WHERE NOT (
       total = subtotal + tax_amount - discount_amount + COALESCE(cash_rounding_adjustment, 0)
    OR total = subtotal + tax_amount + COALESCE(cash_rounding_adjustment, 0)
 );
```
A non-zero count means rows already violate the OLD constraint (only possible if it was left NOT VALID with
residue). Fleet-abort risk is contained the same way `2026_07_28_100200` contains it: `ADD … NOT VALID`
followed by a savepoint-protected `VALIDATE`, so a tenant carrying residue degrades to an unvalidated
constraint (still guarding every NEW row) instead of aborting the fleet. Any non-`23514` error re-raises so the
deploy stays retryable.

## 9. POS release coupling

**This lane cannot ship server-only, and cannot ship device-only.**

- The device must ship for any receipt to be authored at v5. Until it does, every terminal keeps authoring v3
  and the server keeps accepting it — no breakage, no fix either.
- The server must ship first or simultaneously: a v5 payload reaching a server without this lane is refused by
  `envelope_event_version_mismatch` (the registry's supported set) and quarantined.
- **Ordering: server first, then the POS build.** The reverse strands v5 receipts in quarantine.
- Both tenant migrations must run before the first v5 receipt projects; migration (b) is the hard one —
  without it a discounted v5 receipt fails the `pos_receipts_totals` CHECK on PostgreSQL. Proven by execution.
- The LEDGER D-1 build-rollout row applies. Once a terminal takes the build its watermark is set and it can
  never be rolled back to a pre-D-1 build without every subsequent receipt being quarantined — **a POS
  rollback after D-1 is not a supported operation.** State this on the rollout row.

## 12. Addendum — closing the P0 in the ledger (`a57f1889f`)

W4-9 merged to `dev` as `dd67a2c3a`, so the §10 P0 became this lane's to close.

### The problem, precisely

`PosReceiptVatAllocator::allocate()` derived revenue as `net = tender + discount − vat`. That reproduced the
sealed base EXACTLY — but only while the sealed base was PRE-discount. On a v5 receipt it books
`590.000 + 50.000 − 65.453 = 574.547` against a sealed and declared base of **524.547**: books ≠ filing by
5.547, the same wedge D-1 removed from the receipt, reappearing one layer down.

### The balanced shape, worked out

Three candidate shapes for the example (tender 590.000, sealed base 524.547, sealed VAT 65.453, remise 50.000
TTC whose HT part is 44.453 and VAT part 5.547; pre-remise HT revenue Σ `line_subtotal` = 569.000):

| # | Shape | Balances? | Verdict |
|---|---|---|---|
| **A** | `Dr 53 590.000 / Cr 70x 524.547 / Cr 4457 65.453` | ✅ 590.000 = 590.000 | **CHOSEN** |
| B | `Dr 53 590.000 / Dr 709 44.453 / Cr 70x 569.000 / Cr 4457 65.453` | ✅ 634.453 = 634.453 | correct but needs a per-rate HT split the read model does not carry, and books an on-invoice remise in 709 |
| C (W4-9's prediction) | `Dr 53 590.000 / Dr 709 50.000 / Cr 70x 574.547 / Cr 4457 65.453` | ✅ 640.000 = 640.000 | rejected — see below |

The coordinator's doubt about C ("`Cr 70x 574.547??`") was well founded, though not because it fails to
balance — it does balance, and `70x − 709 = 524.547` is the right turnover. It fails because **neither gross
figure means anything**: pre-remise HT revenue is 569.000, not 574.547 (the 5.547 gap is the VAT part of the
remise leaking into an HT account), and a 50.000 **TTC** debit to a revenue-contra account buries that same
5.547 of VAT inside `709`.

**A is chosen** because it is the doctrinally correct treatment, not merely the simplest. Under both the French
PCG and the Tunisian plan comptable, `709 "Rabais, remises et ristournes accordés"` carries RRR granted **hors
facture** (by avoir); an RRR granted **on the invoice** is deducted directly from the sale and never recorded
there. D-1's ruling makes the POS remise an on-invoice remise — it reduces the taxable base on the ticket — so
debiting `709` as well would deduct it twice. Pre-D-1 the `709` leg was the *correct compensating* treatment
precisely because the sealed base was NOT reduced. Each era's ledger shape follows its own base, which is why
this is **version-aware rather than a replacement**.

### How the version is known

`pos_receipt_vat_details.discount_allocated` — `NULL` on every receipt sealed at `event_version <= 4`, written
verbatim by `PosCoreReceiptProjection` on v5. Read directly rather than joining `fiscal_events.event_version`,
because it is the fact that actually matters ("did the device ventilate the remise into this base?") and it
lives in the table the allocator already reads. Keeping it nullable rather than defaulting it to `'0'` — the
choice made in §7(a) — is what makes this possible.

A **mixed** set (some rows with a share, some without) cannot be read as either era, so it is refused with a
new typed reason `SealedBaseEraAmbiguous` rather than resolved by guessing. A guess would book a wrong revenue
base on a receipt whose VAT the declaration still reports.

### Behaviour

| era | revenue | `709` leg | guard base |
|---|---|---|---|
| v1..v4 (`discount_allocated` NULL) | `tender + discount − vat` | yes, the remise TTC | `tender + discount` |
| v5 (`discount_allocated` present) | `tender − vat` | **none** (`discountAmount` = `'0'`) | `tender` |

`PosRevenueVatSplit::assertReconciles()` is unchanged and satisfied by both: `net + Σvat − discount == tender`
reduces to `net + Σvat == tender` when the discount is zero. No DTO change, no GL-writer change —
`hasDiscount()` already gates the `709` spec and `assertPosPurposesProvisioned()` already requires
`SalesDiscount` only when it fires.

### The ACCOUNT_CHARGE ruling (F-4 / I-4) — refuse, don't ventilate

`accountChargeCartMapper.ts` seals `subtotal`/`vatTotal` on the PRE-remise line roll-up and applies the remise
to `total` alone — the D-1 defect, alive, on a sibling type fed by the **same cart and the same discount UI**.
Since D-1 a paid ticket seals a post-remise base, so one cart would declare **two different taxable bases
depending on tender**, and `createPOSChargeEntry()` would over-credit `4457` on every discounted credit sale.

Ventilating ACCOUNT_CHARGE properly is a versioned-payload change of its own — new event version, projection
column, GL era-awareness — which this lane can neither author nor test end-to-end. **Refusing is fail-closed,
immediately correct, reversible in one block, and cannot leave a wrong number on a sealed document.** The
device refuses first; the server refusal
(`payload_account_charge_transaction_discount_unsupported`) is what binds a device that has not taken the
build. Consequence for `709x`: on the POS it now goes genuinely **empty** rather than partial — which is a
cleaner story for whoever reads it than the asymmetry the gate warned about.

**Booked as a follow-up lane:** *ACCOUNT_CHARGE post-remise ventilation* — an `ACCOUNT_CHARGE` version bump with
a ventilated base + `discount_allocated`, the owner ruling of 2026-08-25 attached, plus the era treatment for
`createPOSChargeEntry()`. Until it lands, an on-account sale simply cannot carry a remise.
