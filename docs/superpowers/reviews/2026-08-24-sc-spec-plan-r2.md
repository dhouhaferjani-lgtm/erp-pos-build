## Findings

**F-21 · Critical · area A/C/I** — Expense and Income cannot use the specified allocation-based payable/receivable basis. Expense settlement is recorded through `expense_metadata.is_paid`, a repository movement, and a dedicated GL entry—not a payment allocation; Income similarly uses `income_metadata.is_received` and records cash during posting ([ExpenseService.php:122-147](apps/api/app/Modules/Expense/Application/Services/ExpenseService.php:122), [ExpenseService.php:671-749](apps/api/app/Modules/Expense/Application/Services/ExpenseService.php:671), [IncomeService.php:74-98](apps/api/app/Modules/Income/Application/Services/IncomeService.php:74), [IncomeService.php:164-188](apps/api/app/Modules/Income/Application/Services/IncomeService.php:164)). SPEC nevertheless assigns “payable basis” and “receivable basis” and C-2b1 seeds `balance_due=total` for all payable types ([SPEC-document-lifecycle-dimensions.md:43-44](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:43), [PLAN-phase2-3-P-R.md:63-70](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:63)). Existing default-paid expenses and default-received income would therefore become `unpaid`, fail their closure predicates, and possibly emit `DocumentFullyPaid` with a null partner into a non-nullable event argument ([DocumentFullyPaid.php:18-26](apps/api/app/Modules/Document/Domain/Events/DocumentFullyPaid.php:18)). Required change: replace the two matrix cells with either “metadata-authoritative: `is_paid`/`is_received`, with `balance_due` synchronized to 0 or total by those writers” or commit a separate migration that converts these flows to canonical allocations. Specify nullable-partner event behavior and add existing-flow tests for paid/unpaid Expense and received/unreceived Income.

**F-22 · Critical · area C/F/I** — C-P2 promises exact supplier-invoice receipt-slice reversal but the necessary provenance is not persisted. Posting FIFO-consumes multiple receipt lines and stores only cumulative `goods_receipt_lines.quantity_invoiced`; the invoice line has at most one `matched_receipt_line_id` ([SupplierInvoicePostingService.php:300-373](apps/api/app/Modules/Procurement/Application/SupplierInvoicePostingService.php:300), [2026_07_04_100000_create_goods_receipts_tables.php:38-50](apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:38), [2026_07_04_110000_add_match_snapshot_to_document_lines.php:13-16](apps/api/database/migrations/tenant/2026_07_04_110000_add_match_snapshot_to_document_lines.php:13)). After subsequent invoices consume the same receipt pool, the original slices cannot be reconstructed reliably. SPEC demands exact slice restoration, while PLAN marks C-P2 `NO` migration ([SPEC-document-lifecycle-dimensions.md:141-147](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:141), [PLAN-phase2-3-P-R.md:28](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:28)). Required change: insert a prerequisite migration lane creating an immutable `supplier_invoice_receipt_allocations` ledger with invoice line, receipt line, paid/free quantity, cost basis, and posting/reversal identity. C-P2 must reverse that ledger atomically and test two invoices consuming overlapping FIFO receipt sets.

**F-23 · Critical · area A/D/H/I** — The new closure table remains internally contradictory and contains predicates with no available facts. Quote/RFQ closure requires lifecycle `confirmed ∧ cancelled`, yet cancellation changes lifecycle to `cancelled`; the recompute table separately says cancellation clears `closed_at` ([SPEC-document-lifecycle-dimensions.md:33-34](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:33), [SPEC-document-lifecycle-dimensions.md:57](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:57)). ReturnNote closure depends on “credit note posted or no-credit disposition,” while the program explicitly leaves `ReturnNoteMetadata`/`RefundMethod` untouched until R-3 ([SPEC-document-lifecycle-dimensions.md:40](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:40), [SPEC-document-lifecycle-dimensions.md:162-165](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:162)); current creation stores only `source_document_id` and payload reason/condition ([ReturnNoteService.php:137-155](apps/api/app/Modules/Document/Domain/Services/ReturnNoteService.php:137)). A fully returned invoice also fails the invoice’s `fulfilled-or-n/a` closure predicate because its fulfilment becomes `returned`. Required change: rewrite closure as explicit terminal conditions, for example Quote/RFQ `(converted_at ∨ expired_at ∨ status=cancelled)`; define whether cancellation stamps or clears closure; defer RN closure until a disposition fact exists; and add an owner-approved rule for fully returned invoices. C-3a2 cannot precede R-3/R-4 under the present table.

**F-24 · High · area A/C/I** — Credit-note settlement uses the wrong denominator. SPEC defines outward applied/refunded value “over total” ([SPEC-document-lifecycle-dimensions.md:38](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:38), [SPEC-document-lifecycle-dimensions.md:95-96](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:95)), but the authoritative application writer deliberately excludes the credit note’s stamp duty because it never reduces the customer receivable ([CreditNoteService.php:1248-1265](apps/api/app/Modules/Document/Application/Services/CreditNoteService.php:1248), [CreditNoteService.php:1312-1334](apps/api/app/Modules/Document/Application/Services/CreditNoteService.php:1312)). A fully applied stamped TN credit note would remain partially paid and never close. Required change: define the sales-CN settlement base as `total − stamp_duty_amount`, with any cash-refund component classified consistently; give supplier CNs their own country/accounting basis rather than assuming symmetry. Add stamped, unstamped, partially applied, and applied-plus-refunded tests.

**F-25 · High · area C/E/I** — The payment recompute caller census is incomplete. C-2b1 names `PaymentAllocationService`, `PaymentRefundService`, controller paths, MultiPayment, CN application, and tolerance ([PLAN-phase2-3-P-R.md:63-70](docs/sessions/session-C-lifecycle-2026-08-24/PLAN-phase2-3-P-R.md:63)), but `VendorRefundService` independently creates negative allocations ([VendorRefundService.php:140](apps/api/app/Modules/Treasury/Domain/Services/VendorRefundService.php:140)); allocations are also created at several independent controller/service locations ([PaymentController.php:1012](apps/api/app/Modules/Treasury/Presentation/Controllers/PaymentController.php:1012), [MultiPaymentService.php:115](apps/api/app/Modules/Treasury/Domain/Services/MultiPaymentService.php:115), [PaymentRefundService.php:1883](apps/api/app/Modules/Treasury/Domain/Services/PaymentRefundService.php:1883)). Add one test per distinct production writer.

Add concurrent-genesis and concurrent-tail PG tests for all four chains.

**F-27 · High · area B/E/I** — `sealed_at` is neither safely backfillable nor immutable as written. “Backfill from the hash-input stamp where recoverable” and an unnamed “legacy date rule” do not define an evidence order or what happens when `document_date` differs from the actual seal date ([SPEC-document-lifecycle-dimensions.md:122-125](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:122)). The current trigger’s frozen-field list does not include the new `sealed_at` column ([2025_12_11_054716_add_document_immutability_trigger.php:33-45](apps/api/database/migrations/tenant/2025_12_11_054716_add_document_immutability_trigger.php:33)). Required change: define deterministic provenance precedence per type—persisted `posted_at`/`confirmed_at`, immutable domain-event payload, then “unverifiable/quarantined”; never claim that substituting `document_date` verifies the original hash. Add `sealed_at` to the immutable fields and test tampering plus a backdated document.

**F-28 · High · area B/E** — C-8 still fails to protect non-fiscal documents after cancellation and does not protect their lines. The proposed arm keys on current `status='posted' AND fiscal_category='NON_FISCAL'` ([SPEC-document-lifecycle-dimensions.md:126-128](docs/sessions/session-C-lifecycle-2026-08-24/SPEC-document-lifecycle-dimensions.md:126)); after `posted→cancelled`, that predicate no longer applies. Required change: key immutability on a persistent seal fact such as `sealed_at`/posting JE, retain protection after cancellation, cover document-line update/delete and document deletion, and whitelist only cache/status/reversal-reference fields.

Add a concurrent-transition PG test and stale-model test.
