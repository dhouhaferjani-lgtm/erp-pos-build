## New findings introduced by v2

1. **BLOCKER - §5.2/§5.4 promotion and rollback - The WAL delta/replay primitive is not specified.**

   Issue: v2's <=30 minute cutover depends on "final delta sync via WAL or repeated short export" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:319-320`) and rollback depends on "target.WAL diff" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:349-352`). PostgreSQL exposes logical decoding/replication mechanisms, not a generic DB-to-DB `WAL diff` artifact: official docs say changes are streamed via "logical replication slots" and formatted by an output plugin (PostgreSQL docs, `https://www.postgresql.org/docs/current/logicaldecoding.html`, lines 53-58). Logical replication copies an initial snapshot and then streams publisher changes to a subscriber in commit order (PostgreSQL docs, `https://www.postgresql.org/docs/17/logical-replication-architecture.html`, lines 29-37).

   Why this is fundamental: without choosing one concrete delta path, v2 cannot prove the write-lock window, cannot implement replay-required rollback, and cannot know the required table-level prerequisites (`REPLICA IDENTITY`, publications, row filters, trigger behavior, excluded tables, sequence handling).

   Proposed fix: split §5 into named strategies and select one before approval: (a) PostgreSQL logical replication with publications/subscriptions/slots and documented table prerequisites; (b) application trigger/outbox change log; or (c) no live delta, with a measured freeze-and-export window that explicitly replaces the current <=30 minute claim for tenants that exceed it. Remove `target.WAL diff` wording unless it is backed by a precise logical-decoding procedure and tooling.

2. **MAJOR - §5.5 Tunisia-first - Initial public-schema extraction is not the same operation as recurring promotion.**

   Issue: v2 says every existing tenant must move from "current pooled `public` schema in `autoerp` DB" to a tenant DB and "This becomes the first promotion shape" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:367`). But §5.2 promotion is DB-to-DB `pg_dump`/restore (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:312-320`), while the master plan initial migration is per-tenant export "from public schema -> import into new tenant DB (or schema)" (`docs/superpowers/plans/2026-05-02-tenant-isolation-master-plan.md:840`). A row-filtered extraction from a pooled schema must classify tenant-owned tables, company-owned tables, shared/system rows, central tables, users/auth tables, FK closure, sequences, and fiscal hash verification differently from a whole tenant-DB dump.

   Proposed fix: define two related but separate runbooks/state machines: `tenant:extract-from-public` for the one-time row-level-to-DB migration, and `tenant:promote`/`tenant:demote` for ongoing DB-to-DB moves. They may share catalog flip, communication, verification, and rollback concepts, but they cannot share the same export/delta implementation without proof.

3. **MAJOR - §8.2 PgBouncer capacity - Pool math is conditional on a single forced server user but the spec does not require it.**

   Issue: v2 computes Y1 as `100 x 5 = 500` server connections (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:495-501`). PgBouncer's own docs say "A new pool entry is made for each couple of (database, user)" (`https://www.pgbouncer.org/usage.html`, SHOW POOLS section), and the config docs say if `user=` is set then "there will be only one pool for this database"; otherwise there is "one pool per user" (`https://www.pgbouncer.org/config`, lines 799-803). v2's generated `[databases]` section is not shown and does not require `user=autoerp_app`/forced user, so the correct formula is `tenant_databases x distinct_server_users x pool_size`, plus reserve pools.

   Proposed fix: make generated database entries explicit, e.g. `tenant_x = host=... port=5432 dbname=tenant_x user=autoerp_app pool_size=5 reserve_pool_size=2 max_db_connections=...`. Recompute Y1/Y3/Y5 as `(pool_size + reserve_pool_size) x tenant DBs x forced users`, and set `max_db_connections`/`max_user_connections` so one hot tenant cannot consume cluster capacity.

4. **MAJOR - §7.3/§7.5 migration fan-out - The tolerance contract does not match current migration practice.**

   Issue: v2 requires app code to tolerate `(migration-N applied, migration-N+1 not applied)` during fan-out (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:444-475`). Current recent migrations include single-phase rename (`renameColumn('voucher_serial', 'instrument_serial')`, `apps/api/database/migrations/2026_05_03_000002_rename_voucher_serial_to_instrument_serial_on_pos_receipt_payments.php:31-33`), single-phase column constraint change (`->nullable()->change()`, `apps/api/database/migrations/2026_04_26_120000_make_payment_id_nullable_on_payment_allocations.php:23-27`), and index replacement (`dropIndex` then `unique`, `apps/api/database/migrations/2026_05_08_000002_add_unique_to_billing_payments_provider_payment_id.php:64-72`). These are normal Laravel migrations in this repo, but they are not all covered by v2's allowed/disallowed table.

   Proposed fix: expand the migration contract beyond the simple shape table. It must cover renames, constraint swaps, partial indexes, data backfills, raw `DB::statement`, `change()`, long-running `UPDATE`, and framework code that references either old or new columns. Require an explicit expand/contract migration template and dual-schema tests for each cohort before claiming deploy-on-previous-schema is realistic.

5. **MAJOR - §4.4 database bootstrapper - Current config resolves PostgreSQL to the schema manager, not the database manager.**

   Issue: v2 says Stancl's `PostgreSQLDatabaseManager` is the destination and the database bootstrapper will be activated (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:68`, `docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:281`). Current `tenancy.php` defines `'pgsql' => PostgreSQLDatabaseManager::class` and then later defines the same key as `PostgreSQLSchemaManager::class`; in PHP the later key wins (`apps/api/config/tenancy.php:69-85`). The tenant model does have `TenantWithDatabase` and `HasDatabase` (`apps/api/app/Modules/Tenant/Domain/Tenant.php:18-65`), but the config currently points at schema-per-tenant behavior.

   Proposed fix: add an acceptance criterion or spec note that the config must remove the duplicate `pgsql` key and make the active manager `PostgreSQLDatabaseManager` for Path 3. Include an architecture test or config assertion so this does not regress.

6. **MAJOR - §3.2 status matrix - The matrix covers the Cartesian product but not promotion source/target shard states.**

   Issue: the matrix's `migrating | any` row says writes are locked and reads go to `from_shard`/`from_database_name` until cutover (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:187-191`), while §5.3 says reads may serve from source or target depending on `cutover_ended_at` (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:331-338`). The resolver binding sketch only returns the tenant's current `shard_id`, `database_name`, and `shard_status` (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:238-247`), not the promotion row needed to know source vs target. This is not a missing tenant_status x shard_status cell, but it is a missing state dimension.

   Proposed fix: add an explicit promotion resolver matrix keyed by `(tenant.status, promotion.state, source_shard.status, target_shard.status, cutover timestamps)`, or constrain catalog updates so `migrating` has exactly one canonical binding and no source/target branch in request-time resolution.

7. **MINOR - §11 acceptance criteria - Count and specificity drift.**

   Issue: v2 says the decision locks when "every artifact below is committed" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:544-546`) and later says "all 15 items" (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:574`), but the checklist has 17 boxes: 6 architectural (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:548-555`), 4 operational (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:557-562`), and 7 validation (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:564-572`). Some validation items duplicate artifacts, which is fine, but the count and artifact/test distinction should be precise.

   Proposed fix: split "artifacts" from "validation gates" and fix the count. For runbooks, name required headings, not only file paths.

8. **MINOR - §6/§12 transition escape hatches - Pattern C is banned, but `CrossTenantContext` has no retirement criterion.**

   Issue: v2 correctly says `cross_tenant=true` is a discipline-based escape hatch being closed (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:65`) and bans shared-DB privileged role Pattern C (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:382-389`). But §12 keeps `CrossTenantContext.php` as a "Pattern C remnant" relevant during row-level transition (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:593-599`). The actual middleware still sets a request flag that lets downstream code "legitimately bypass tenant filters" (`apps/api/app/Http/Middleware/CrossTenantContext.php:11-23`) and remains registered as `cross_tenant` (`apps/api/bootstrap/app.php:41-49`).

   Proposed fix: keep the transition aid, but add a sunset artifact: inventory all `#[CrossTenantRoute]`/`cross_tenant` uses, map each to Pattern A/B/control-plane, and fail CI in `TENANCY_MODE=multi_db` for any route still relying on bypass semantics instead of catalog iteration or analytics.

9. **NIT - §3.1 DDL order - The schema snippet is not runnable as written.**

   Issue: `tenants.shard_id` references `shards(id)` before `shards` is created (`docs/superpowers/specs/2026-05-09-multi-db-topology-design.md:100-130`). PostgreSQL requires the referenced table to exist before adding that FK in a single script.

   Proposed fix: put `shards` before `tenants`, or create `tenants` first without the FK and add the FK after `shards`.

## Verdict reasoning

This is not the same failure as v1. The topology has been corrected to true Path 3, and most of the v1 findings are addressed or substantially addressed.

The reason this still cannot be approved is that the design now centralizes risk in an unchosen migration primitive. The spec claims short-lock promotion, replay-required rollback, and Tunisia-first initial migration using "WAL delta", "target.WAL diff", and "repeated short export" language that is not a concrete implementation contract. Approve Path 3 as the intended direction only after v2 is split into two migration shapes (initial public-schema extraction vs ongoing DB-to-DB promotion) and the delta/replay mechanism is selected, with PgBouncer capacity and migration fan-out contracts tightened accordingly.
