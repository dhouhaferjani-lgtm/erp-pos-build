# T11-impl-B — Spec Review (round 1, Codex)
## Verdict: REJECT
## Summary (2-3 paragraphs)
The proposed resolver shape is sound only at the narrow `PricingService` level: `getPrice()` really does resolve partner price list, then default price list, then product base price, and it returns the claimed `source` strings (`apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:32`, `apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:41`, `apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:53`, `apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:63`). The policy discriminators are also real: `Partner.payment_terms_days` exists and is cast to integer (`apps/api/app/Modules/Partner/Domain/Partner.php:37`, `apps/api/app/Modules/Partner/Domain/Partner.php:95`, `apps/api/app/Modules/Partner/Domain/Partner.php:139`), `PaymentMethod.has_maturity` exists (`apps/api/app/Modules/Treasury/Domain/PaymentMethod.php:26`, `apps/api/app/Modules/Treasury/Domain/PaymentMethod.php:66`, `apps/api/app/Modules/Treasury/Domain/PaymentMethod.php:89`), and `DocumentType` has no `Receipt` case (`apps/api/app/Modules/Document/Domain/Enums/DocumentType.php:7`).

The spec is not ready to hand to an implementation engineer because its core current-state claim is false at the sales-document surface. The spec says web sales documents price through `PricingService::getPrice` (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:17`) and tells the engineer to replace existing sales-document `PricingService::getPrice` call sites (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:164`), but the actual document UI uses `product.sale_price` directly (`apps/web/src/features/documents/components/DocumentLineEditor.tsx:187`) and the backend document controllers trust submitted `unit_price` (`apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:165`, `apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:196`, `apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:257`). Routing documents through the new resolver would therefore not be behavior-preserving when partner/default price lists exist.

The track is migration-free as written; no production implementation files are changed on this branch, and the only `channel_product_mappings` references are in this spec (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:35`, `docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:94`). The `variant_id` limitation is honestly documented: `PricingService::getPrice()` has no variant/location/channel parameters (`apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:32`), while the spec says non-null `variantId` resolves at product level until T2 (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:107`).

## Findings
### BLOCKER
1. The web-pricing parity premise is factually wrong at the document surface. The spec claims web sales documents price through `PricingService::getPrice` (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:17`) and instructs replacement of existing sales-document `PricingService::getPrice` calls (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:164`). Actual web document line creation uses `product.sale_price` directly (`apps/web/src/features/documents/components/DocumentLineEditor.tsx:187-190`), and the API controllers calculate totals from submitted `unit_price` rather than calling `PricingService` (`apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:192-200`, `apps/api/app/Modules/Document/Presentation/Controllers/SalesOrderController.php:177-185`, `apps/api/app/Modules/Document/Presentation/Controllers/QuoteController.php:177-185`). The only current `PricingService::getPrice` route is the pricing operation endpoint (`apps/api/app/Modules/Pricing/Presentation/Controllers/PricingController.php:332-364`, `apps/api/app/Modules/Pricing/Presentation/routes.php:64-66`). Implementing the spec as written can change web document prices instead of preserving them.

2. The policy wiring target is contradictory and names a non-existent method. The spec says the policy is wired in `ReceiptCreationService` and cites a `create()` signature (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:52`), but the actual method is `createReceipt()` (`apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:112-125`). More importantly, the spec also says `Receipt` is outside `DocumentEmissionPolicy` scope (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:65-67`), while the policy interface requires a `DocumentType` (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:116-119`). `ReceiptCreationService` creates a POS `Receipt`, not a `Document` (`apps/api/app/Modules/POS/Application/Services/ReceiptCreationService.php:565-603`). There is no coherent way to call `DocumentEmissionPolicy::canEmit(DocumentType, ...)` from this receipt flow.
### P1
1. The document-emission guard lacks a real chokepoint and surface derivation. The spec says to assert policy at every POS-capable `Document` creation entry point and place it at the `Document` creation service (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:166`), but current code creates documents directly in multiple controllers/services, including invoices (`apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:216`), sales orders (`apps/api/app/Modules/Document/Presentation/Controllers/SalesOrderController.php:201`), quotes (`apps/api/app/Modules/Document/Presentation/Controllers/QuoteController.php:201`), cart conversion (`apps/api/app/Modules/Cart/Application/Services/CartConversionService.php:89`), marketplace orders (`apps/api/app/Modules/Marketplace/Application/Services/MarketplaceOrderService.php:269`), and drafts (`apps/api/app/Modules/Document/Domain/Services/DraftPersistenceService.php:102`). The spec must define either a new central creation chokepoint or the exact POS-originating routes/services and how `EmissionSurface::Pos` is derived; otherwise `Api` allow-all can become a bypass (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:134-136`).

2. The new endpoint names an RBAC permission that does not exist in the seed data. The spec requires `pricing.resolve` (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:170`), but current pricing permissions are `pricing.view`, `pricing.manage`, and margin/cost controls only (`apps/api/database/seeders/PermissionSeeder.php:133-142`). Existing pricing operation routes use `can:pricing.view` (`apps/api/app/Modules/Pricing/Presentation/routes.php:64-82`). The spec must either add `pricing.resolve` to permissions and role syncs or reuse `pricing.view`.

3. Endpoint tenant validation is weaker than the current pricing endpoint pattern. The spec says malformed UUIDs are checked with `Str::isUuid()` and scoping is inherited from `PricingService` (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:170`), but the existing `getPrice` endpoint validates `product_id` and `partner_id` with tenant/company `ScopedExists` rules before calling the service (`apps/api/app/Modules/Pricing/Presentation/Controllers/PricingController.php:337-345`). The new FormRequest should follow that pattern for `product_id`, `partner_id`, and any future `channel_id`/`location_id`, not just UUID format validation.
### P2
1. The `PaymentMethod.has_maturity` citation is off by one. The spec cites fillable line 67 (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:49`), but `has_maturity` is fillable at `apps/api/app/Modules/Treasury/Domain/PaymentMethod.php:66`; line 67 is `requires_third_party`.

2. `config/documents.php` is described as the config path (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:148`), but no such config file exists today under `apps/api/config` (`apps/api/config/app.php:1`, `apps/api/config/verticals.php:1`). This is acceptable as a new artifact, but the spec should mark it explicitly as new and define the expected array shape.

3. The `DocumentEmissionNotAllowedException` to 422 mapping is an acceptance criterion without an implementation location. The spec requires 422 with `reason` and message (`docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:213`, `docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:236`), but does not say whether this is implemented via exception `render()`, Laravel exception registration, or controller handling. This needs to be pinned down for a deterministic TDD target.
### SUGGESTION
1. Keep the `variant_id` story, but make the test wording stricter: assert that `ChannelPriceOverrideResolver` receives `variantId`, while the fallback `PricingService::getPrice()` call intentionally omits it because the service signature has only product/partner/quantity/currency/date (`apps/api/app/Modules/Pricing/Domain/Services/PricingService.php:32-38`; `docs/superpowers/specs/2026-05-24-t11-impl-b-pricing-resolver-doc-policy.md:107`).

2. If `pricing.resolve` remains a new permission, include role-assignment expectations for POS operators. Current POS roles already receive `pos.operate`/`pricing.view` combinations in the seed data (`apps/api/database/seeders/PermissionSeeder.php:190-192`, `apps/api/database/seeders/PermissionSeeder.php:224`), but there is no guidance for who receives `pricing.resolve`.
## Ready-to-implement verdict (is it ready to hand to an engineer? what must change first?)
Not ready. First fix the current-state pricing premise: either prove an actual web document call path to `PricingService::getPrice`, or rewrite the spec to say this track introduces negotiated pricing into web/POS documents and update backward-compat expectations accordingly. Then remove `DocumentEmissionPolicy` wiring from `ReceiptCreationService`, define the real POS-originating `Document` chokepoint/surface propagation, and align the endpoint permission/validation with current route and `ScopedExists` conventions.
