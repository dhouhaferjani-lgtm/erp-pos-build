# Inventory Transfer Remediation Plan v3 — Codex Adversarial Review

**Verdict:** BLOCKER
**Confidence:** high
**Date:** 2026-05-29

## Summary

v3 closes the exact joined-`stock_transfers` deadlock shape from v2 by moving denominator reads into `WeightedAverageCostService::recordCostAdjustment()`, locking only `Product`, and using plain aggregate `sum()` calls without `lockForUpdate()` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:640`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:664`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:674`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:686`).

The plan is still not safe to execute. The new safety proof depends on an invariant that is false in the current code: public stock mutations can change `stock_levels.quantity` without locking the product (`apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:81`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:49`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:56`, `apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:231`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:434`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:441`). v3 only adds a brittle substring architecture test and says to fix failures if found, but does not specify the actual lock-order rewrite for those public mutators (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:713`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:743`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:765`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:814`).

v3 also asserts a product-id sorting fix across all per-line product-lock flows, but the only concrete snippet sorts `recordCostEvent()` lines; `moveSourceToInTransit()`, `complete()`, and `cancel()` are not given concrete sorted-loop edits (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:878`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:990`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:993`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:1108`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2124`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:303`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:167`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:242`).

## Regressions from v2 (NEW issues introduced by the v3 edits)

### BLOCKER: the product-lock invariant is not actually established

v3 makes the product row the single serialization point for `(on_hand + in_transit)` and explicitly drops row locks from both aggregate reads (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:636`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:670`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:680`). That is only correct if every `stock_levels.quantity` writer locks `Product` first (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:657`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:659`).

Two-process scenario:

- P1 records a cost event for product P. Inside WAC, P1 locks `products(P)` and then reads `stock_levels` using a plain `sum()` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:664`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:674`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:678`).
- P2 concurrently posts a normal stock receipt for product P through `StockMovementController::receive()`, which calls `StockAdjustmentService::receive()` (`apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:57`, `apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:81`). That method gets or creates a stock level and updates `quantity` without any `Product::query()->lockForUpdate()` (`apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:49`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:56`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:491`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:499`).
- P2 does not wait on P1's product lock, so P1's denominator read is not serialized against the stock-level mutation. The v3 proof says product lock alone serializes all denominator writers, but this public writer bypasses it (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:636`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:40`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:56`).

`StockAdjustmentService::adjust()` has the same problem: it mutates `stock_levels.quantity` through `getOrCreateStockLevel()` and `update()` without a product lock (`apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:208`, `apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php:231`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:426`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:435`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:441`). `reserve()` / `releaseReservation()` mutate only `reserved`, not `quantity`, so they do not affect WAC denominator quantity, but they demonstrate that the architecture-test provider is manually curated rather than exhaustive (`apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:326`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:351`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:381`, `apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php:398`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:743`).

### BLOCKER: cross-product deadlock sorting is asserted but not specified for every flow

v3 correctly identifies that every flow locking products per line must sort by `product_id` ascending (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:878`). The only concrete sorted-loop snippet is in `recordCostEvent()` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:990`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:993`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:995`).

Two-process scenario:

- P1 initiates transfer A with lines `[P, Q]`; current `moveSourceToInTransit()` iterates `$transfer->lines` directly and locks P then Q (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:303`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:304`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:307`).
- P2 initiates transfer F with lines `[Q, P]`; it locks Q then waits for P by the same loop (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:303`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:304`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:307`).
- P1 now waits for Q while P2 waits for P. The plan text says sorting applies to initiate/complete/cancel, but the concrete tasks do not edit those loops (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:878`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:1079`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:1113`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2124`).

`complete()` and `cancel()` have the same unsorted-loop surface in the current code (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:167`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:168`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:242`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:243`).

### BLOCKER: reversal idempotency cannot be enforced as specified

Task A1 adds `reverses_event_id` and a PostgreSQL partial-unique index (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:160`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:166`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:190`). Task F3 depends on `recordCostEventInternal()` writing `reverses_event_id = $original->id` so duplicate reversal attempts hit that index (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2467`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2469`).

The planned model fillable omits both `idempotency_payload_hash` and `reverses_event_id` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:330`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:339`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:341`). The planned DTO also has no `reversesEventId` field, so F3 has no typed path to carry that value into the internal create (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:445`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:452`).

Two-process scenario:

- P1 cancels transfer A and selects original cost event E for reversal. F3 says P1 creates a negative event with `reverses_event_id = E` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2465`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:2469`).
- P2 submits the same reversal concurrently or retries after a timeout. The intended protection is the partial-unique index on non-null `reverses_event_id` (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:187`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:190`).
- Because the plan does not make `reverses_event_id` mass-assignable and does not add it to `RecordCostEventData`, the review cannot verify that the reversal row ever carries a non-null `reverses_event_id`; if it is discarded or omitted, the unique index does not fire and WAC can be reversed twice (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:330`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:341`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:445`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:452`).

The same fillable omission also breaks cost-event idempotency payload validation: A7 writes `idempotency_payload_hash`, but the model fillable does not include that column (`docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:949`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:951`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:330`, `docs/superpowers/plans/2026-05-28-inventory-transfer-remediation.md:341`).
