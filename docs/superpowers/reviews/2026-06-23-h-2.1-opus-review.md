## Summary

The core claim holds and is implemented correctly: `createPaymentReceivedJournalEntry()`
now optionally posts the draft entry when a real `User` actor is supplied, threads an
explicit `currencyCode` (avoiding the no-arg `getScale()` that throws without a bound
`CompanyContext` on queued/projection paths), and refreshes the partner balance only after
posting. Money handling is pure bcmath (no float casts, no `number_format((float)…)`), the
scale resolver is constructor-injected (no `app()`), sign conventions are correct
(receivable is debit-normal magnitude), and the GLIntegrationTest is a genuine red-first
assertion of posted status + fiscal_hash + posted_by + refreshed balance. The double-entry
is always balanced (Dr Bank `amount` / Cr AR `amount`).

The main concern is an architectural inconsistency that was merged: the three production
callers post the entry INLINE inside their outer `DB::transaction`, whereas the sibling
supplier-payment path (`createSupplierPaymentJournalEntry`, committed in the same session)
already used the `postEntryAndDispatchPostedEventAfterCommit` helper. At THIS commit the
inline post is benign because `JournalEntryPosted` had no registered listeners yet, but it
is a forward-risk that the team itself corrected two commits later (`5d30776ac`). No
fiscal/money/data-integrity violation is introduced by this commit. Verdict:
APPROVE-WITH-MINOR-EDITS (the inline-vs-afterCommit inconsistency is the only item I would
want resolved, and it already has been on HEAD).

## HIGH

### H1 — Inline `postEntry` inside the caller transaction diverges from the established afterCommit posting pattern
`GeneralLedgerService.php` (as of `6252cc499`, lines ~669-671):
```php
if ($user !== null) {
    $this->postEntry($entry, $user, $currencyCode);
    $entry->refresh()->load('lines');
    $this->partnerBalanceService->refreshPartnerBalance($companyId, $partnerId);
}
```
All three production callers invoke this INSIDE an outer `DB::transaction`:
- `PaymentController::store()` — `DB::transaction` at line 203, GL call at ~388.
- `PaymentController::storeMultiple()` — `DB::transaction` at line 557, GL + new excess GL inside.
- `PaymentAllocationService::applyAllocationFromCommand()` — `DB::transaction` at line 157, GL call at ~262.

The sibling `createSupplierPaymentJournalEntry()` (lines 544-602) does NOT post inline; it
calls `postEntryAndDispatchPostedEventAfterCommit($entry, $user, $companyId, $currencyCode)`
which defers the `postEntry` + `event(JournalEntryPosted)` until `DB::afterCommit`. The
helper existed and was used by the same author in the same work session, so the customer
path should have used it too for consistency.

Why this is HIGH (not BLOCKER) for this commit specifically: at `6252cc499`,
`JournalEntryPosted` has NO registered listeners (verified: it is absent from
`EventServiceProvider` and from `DomainEventSubscriber::subscribe()` at this commit), so the
synchronous `event(new JournalEntryPosted(...))` in `postEntry` is a no-op dispatch. The
posted row + fiscal_hash are written inside the same transaction, so a rollback atomically
discards them — no orphaned posted entry, no event side-effect leak. The defect is latent:
the moment a synchronous listener is registered (which happened in `5d30776ac`
"Refresh balances from journal posted events"), this inline post would fire that listener
inside the open payment transaction (reading not-yet-committed rows, and re-running on every
retry). The team recognized this and refactored the customer path to the afterCommit helper
on HEAD. Recommendation: confirm the HEAD refactor (`5d30776ac`) fully supersedes this
inline form on every customer-payment caller before relying on H-2.1 in production; no
further change needed if so.

## MEDIUM

### M1 — Fiscal hash chain head is selected by `posted_at` with no chain-head lock (pre-existing, aggravated by inline posting)
`getPreviousHash()` (lines 1751-1761):
```php
$lastPosted = JournalEntry::query()
    ->where('company_id', $companyId)
    ->where('status', JournalEntryStatus::Posted)
    ->whereNotNull('fiscal_hash')
    ->orderByDesc('posted_at')
    ->first();
```
The chain head is chosen by a non-monotonic `posted_at` timestamp with no `lockForUpdate`
on the chain tip. Two concurrent posts for the same company can read the same
`previous_hash` and fork/duplicate the chain. This is a pre-existing GL design weakness, not
introduced by H-2.1, but H-2.1 adds another high-frequency posting site (every customer
payment) inside a transaction, widening the exposure window. [NEEDS-REAL-PG] to demonstrate
the race; SQLite tests run serially and cannot surface it. Out of scope to fix here; flag
for the chain-integrity item in the same audit.

### M2 — `storeMultiple` manual excess UNDER-allocation leaves cash with no GL credit (pre-existing, now visible)
Validation rejects OVER-allocation (`totalManualAllocation > excessAmount` throws, store
method lines ~542-552) but ALLOWS under-allocation. When
`sum(excess_allocations[].amount) < excessAmount`, the repository balance is incremented by
the full payment (physical cash) yet GL only credits AR for the allocated portion and the
remainder is silently dropped — no customer-advance entry, no AR credit. This produces a
cash-vs-GL mismatch. H-2.1 does not introduce this (it only added GL posting where an
allocation already occurred), but by wiring posted GL into this path it makes the gap a
ledger correctness concern rather than a cosmetic one. The new test only covers the exact
balance case (200 excess, 200 allocated). Recommend a follow-up test + a guard that the
unallocated excess always falls back to a customer-advance GL entry.

### M3 — Tests are SQLite-only; no real-PG verification of the fiscal hash chain
`GLIntegrationTest` and `MultiPaymentTest` assert `fiscal_hash` is non-null and status
Posted, which is checkable on SQLite. There is no real-PG run for append-only / chain
behavior. Acceptable for this slice, but the claim "posts with real fiscal hash" is only
weakly evidenced under SQLite. [NEEDS-REAL-PG] for chain-append semantics.

On HEAD, `RefreshPartnerBalanceOnJournalEntryPosted` (sync listener) ALSO refreshes on the

recompute), so correct but wasteful. Tied to the H1 refactor; verify the inline call was
removed when the afterCommit helper took over.
