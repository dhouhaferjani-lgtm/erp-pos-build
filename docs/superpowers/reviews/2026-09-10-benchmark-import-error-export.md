# Benchmark note — what an import error export must contain (2026-09-10)

**Owner report (2026-09-10):** exporting the failing lines of a partially failed import returns "the same file you tried to import" — no useful information. Owner's acceptable shapes: (A) only the failing lines; (B) the full file with an added status column and the reason.

**Repository state.** The accepted imports-hardening spec already designs this surface: `docs/superpowers/specs/2026-08-29-imports-hardening-design.md` §4.10 "Error-line export (D4, R1)" — owner requirement R1 "error-line export (re-importable)" — and its lane **G-1** (`#### G-1 — Error-line export + coded errors`) was written (brief `docs/sessions/session-G-imports-hardening-2026-08-29/briefs/LANE-G1-error-line-export-coded-errors-BRIEF.md`, gitignored dir, on disk) but **never dispatched** (held behind lane F1, which merged 2026-08-29; the hold was never released — memory `project_session_g_imports_hardening_2026_08_29`). What ships today is the pre-G-1 `FailedRowsExportService` (`apps/api/app/Modules/Import/Services/FailedRowsExportService.php`): failed rows only, canonical post-mapping headers, no BOM, **no status / code / message columns**, warning rows excluded, unreachable from the wizard for async (≥100-row) jobs — exactly the symptom reported. The history page's button downloads the **result workbook** (`ImportHistoryPage.tsx:222`, `downloadResultWorkbookUrl`), a per-outcome multi-sheet echo of the rows, which is why it looks like the uploaded file.

**Domain norm.**

| System | Failure handling | Error export | Re-import |
|---|---|---|---|
| ERPNext Data Import (v13+) | Partial success: rows fail individually, "Show Failed Logs" per row | **"Export Errored Rows"** — downloads only the rows that failed, for correction ([community confirmation, issue 38918](https://github.com/frappe/erpnext/issues/38918); the [official manual](https://docs.frappe.io/erpnext/user/manual/en/data-import) documents only the pre-import warnings section and the Import Log) | Yes — the exported rows are re-uploaded after correction |
| Odoo (base_import) | Import is **atomic** by default: any invalid row aborts the whole import; the preview lists errors per row/field before anything is written | No error export; errors are shown inline in the preview | n/a (fix the source file, retry) |
| Dolibarr | Row-by-row; the run report lists each rejected line with its reason | Report only, no file | Fix and retry |
| Shopify / HubSpot / most SaaS importers | Partial success | "Download error report": the failed rows **plus an `Error` column with the reason** | Yes, after deleting the error column or ignoring it |

**Reading.** The norm for partial-success importers is option (A) **with** the reason attached: only the rows the operator must fix, in the operator's own column layout, with appended status/reason columns that the re-import ignores. Option (B) (whole file + status) is used by validators that never write anything (Odoo-style preview), not by partial-success importers, because re-uploading the full file would re-create the already-imported rows. Spec §4.10 is exactly the norm: selection = failed OR warning rows; columns = the **source file's own headers** (reverse column mapping); appended `_status`, `_code`, `_message` (underscore-prefixed so a re-upload ignores them); UTF-8 BOM; CSV + XLSX; available on async jobs; re-upload with `reimport_of` pre-applies the mapping.

**Recommendation (Fable does not decide product rules; this one is already ruled — R1, spec §4.10 gated r5):** dispatch G-1 as specified, plus a Playwright evidence campaign first (three sample files: success / hard fail / partial) that pins today's history page and export behaviour RED so the lane's tests are genuinely red-first. Owner confirmation asked for one point only: the history page's download button should offer the **row export** (the fixable lines with reasons) as the primary action and keep the result workbook as a secondary "full report" link.
