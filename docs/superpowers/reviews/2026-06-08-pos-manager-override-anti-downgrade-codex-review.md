**[MAJOR] Finding 1 — Offline fallback accepts any unexpected non-ApiRequestError**
Problem: The new anti-downgrade behavior is correct for the typed path where `apiPost` rejects with `ApiRequestError` for 5xx/408/429, but the fallback boundary is still too broad for a security decision: every non-`ApiRequestError` thrown during online verification is treated as "genuine transport failure" and returns a local manager approval. That includes not only fetch/network failures, but also wrapped HTTP errors, cross-module `ApiRequestError` instances that fail `instanceof`, malformed response/parser errors, or other unexpected exceptions inside the API layer. If a reachable-but-erroring server ever surfaces as a plain `Error` or wrapped error, this code reintroduces the downgrade path the change is meant to kill. I could not inspect `apiPost`/`fetchWithTimeout` within the four-command action-safety limit, so this is a callsite finding plus a classifier-contract risk that should be closed with code, not assumed away.
Evidence: apps/pos/src/lib/operatorApproval/scopedManagerPin.ts:170 only treats retryable server errors when `error instanceof ApiRequestError`; apps/pos/src/lib/operatorApproval/scopedManagerPin.ts:204 treats every other `ApiRequestError` as server rejection; apps/pos/src/lib/operatorApproval/scopedManagerPin.ts:229 then emits offline approval for the remaining catch-all path, followed by apps/pos/src/lib/operatorApproval/scopedManagerPin.ts:241 returning the local approval. Snippet: `if (error instanceof ApiRequestError) { ... throw error; }` then `type: 'pos.manager_override_offline_approved'` and `return { id: matched.id, ... }`.
Fix: Replace the implicit `non-ApiRequestError === transport` rule with an explicit transport classifier from the API layer. For example, have `apiPost` throw a dedicated `ApiTransportError`/`NetworkRequestError` for fetch network failures and abort/timeouts, unwrap `error.cause` before classification, and fail closed for unknown non-API exceptions. The fallback branch should be guarded by `isTransportError(error)` only; all unknown errors should emit `pos.manager_override_denied` with `denied_kind: 'service_unavailable'` and throw a 503.
