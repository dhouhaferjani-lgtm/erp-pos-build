## Summary

T3 v2 has executed the scope-reduction-to-infrastructure cleanly. The `ChannelAdapter` port, `AdapterRegistry` (empty out of the box), the encrypted-credential storage, the debounced outbound dispatcher, the signature-strategy framework with `NullSignatureStrategy` for test, and the admin UI with an "adapter modules coming in next release" empty state are all internally coherent. There is no `automattic/woocommerce` composer dependency, no concrete adapter classes, and no platform-specific signature implementation in production paths. The five new entities (`Channel`, `ChannelCredential`, `ChannelProductMapping`, `ChannelOrder`, `ChannelSyncOperation`) target `database/migrations/tenant/` per the topology contract. The two file-path citation BLOCKERs from round-1 (B-2) are corrected. The PlatformHttpClient timeout claim is corrected to "5s connect, 10s total" (P2-1). The WooCommerce SDK assumption is removed (P1-2). Effort drops from 12 PD to 6 PD which matches the reduced scope.

T4 v2 correctly drops the `tenant_id` FK that round-1 P1-3 suggested, and explicitly documents *why* per the topology contract: cross-tenant validation moves to service layer, not FK constraints. Phase 5 (the only T3-dependent phase) is now flagged with its dependency in the workflow recommendation, in the coordination notes, and in section 1 prose. The Tunisian governorate seeder is confined to a single named file (`TunisianGovernorateZoneSeeder`) and explicitly NOT part of `TenantInitializationService` automatic flow, per the productization rule that geography is opt-in. The Opus role on Phase 2 (ScoringStrategy + RuleEvaluator + OrderRoutingService semantics) is preserved in the spec's workflow recommendation, which addresses round-1 P2-3 from the spec side even if the roadmap also needs alignment.

The biggest remaining risk is a soft cross-spec contract: T3's `ChannelOrderIngestService::promote` says it "creates Document at routed location (T4)" but doesn't name `OrderRoutingService::routeFromChannelOrder` as the call site, and T4 doesn't pin which actor invokes it. This is recoverable in implementation but should be tightened pre-build.

## Findings (BLOCKER / P1 / P2 / SUGGESTION)

### P2

- **[P2-A] T3: typo "FK locations" in `Channel` entity definition**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t3-sync-hub.md:65`
  - Quote: `` `id` (UUID), `company_id` (FK locations within tenant DB), `name`, `adapter_type` enum``
  - Issue: `Channel.company_id` references the `companies` table, not `locations`. `Location` itself has its own `company_id` FK (verified at `apps/erp/apps/api/app/Modules/Company/Domain/Location.php:23,71`). An implementer reading this literally would write `->foreign('company_id')->references('id')->on('locations')` which is wrong.
  - Recommended fix: change to `` `company_id` (FK `companies` within tenant DB)``.

- **[P2-B] T3/T4: `ChannelOrder` → routing → `Document` handoff is implied but not contractually pinned**
  - Files: `apps/erp/docs/superpowers/specs/2026-05-24-t3-sync-hub.md:155` (`ChannelOrderIngestService::promote(UUID $channelOrderId): Document  // creates Document at routed location (T4)`) and `apps/erp/docs/superpowers/specs/2026-05-24-t4-order-routing.md:122` (`OrderRoutingService::routeFromChannelOrder(UUID $channelOrderId): RoutingDecision`).
  - Issue: Two services with overlapping responsibility surface but no explicit "who calls whom" pin. T3 says `promote` creates a Document at the routed location; T4 says `routeFromChannelOrder` returns a `RoutingDecision`. Three valid implementations exist (a) T3's `promote` calls T4's `routeFromChannelOrder` and then constructs the Document, (b) T4's `routeFromChannelOrder` calls a T3 Document-construction helper and writes the Document itself, (c) a third orchestration layer wires them. Without pinning, the two implementer sessions could ship conflicting integrations in Phase 5.
  - Recommended fix: add a paragraph to T3 §4 and T4 §4 (mirrored) that names the call direction: e.g. *"T3's `ChannelOrderIngestService::promote` calls `OrderRoutingService::routeFromChannelOrder`, then materializes the `Document` with `location_id = decision.chosen_location_id`, then writes `RoutingDecision.document_id` back. T4 does not construct Documents; it returns decisions."*

- **[P2-C] T4: `additional_costs` citation is slightly imprecise (not a blocker)**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t4-order-routing.md:33`
  - Quote: `` `apps/erp/apps/api/app/Modules/Document/Domain/Document.php` — `additional_costs` includes `transport`/`shipping`/...``
  - Reality: `additional_costs` is a related entity (`DocumentAdditionalCost` at `apps/erp/apps/api/app/Modules/Document/Domain/DocumentAdditionalCost.php:30`, table `document_additional_costs`) with a `cost_type` string field (`'transport', 'shipping', 'insurance', 'customs', 'handling', 'other'` per docblock line 17). It is not a JSON column on Document itself.
  - Impact: Low; spec is just citing existing model surface for context, not changing it. But the implementer following the citation will look in the wrong file.
  - Recommended fix: change the citation to `apps/erp/apps/api/app/Modules/Document/Domain/DocumentAdditionalCost.php` (cost_type enum docblock at line 17) and clarify "shipping is a separate `DocumentAdditionalCost` row keyed by `cost_type='shipping'`, not a column on Document".

### SUGGESTION

- **[S-1] T3: explicitly name the queue connection / backoff strategy for retry framework**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t3-sync-hub.md:170-173`
  - Spec lists four queue jobs (`DispatchProductToChannelJob`, `DispatchStockChangeToChannelJob`, `IngestChannelOrderJob`, `ChannelReconciliationJob`) and §4 mentions "queue-backed" but doesn't pin which connection (`redis` vs default), retry attempts, or backoff strategy. The existing `ProcessEnrichmentWebhookJob` pattern (which the spec mirrors per line 38) sets specific values; spec should call out that mirroring extends to job-level retry + queue configuration, not just the file-layout pattern.

- **[S-2] T3: idempotency-key collision domain**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t3-sync-hub.md:91, 277`
  - Spec mentions "tenant-scoped idempotency key" and `last_sync_hash` for product mappings, but `ChannelSyncOperation.idempotency_key` collision domain isn't specified (per-channel? per-channel-per-product? per-tenant?). Post-T6 each tenant DB is isolated, so the practical domain is per-channel within tenant — call it out so the unique index is correctly scoped.

- **[S-3] T4: `Document.location_id` mutation semantics on manual override**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t4-order-routing.md:203`
  - Acceptance criterion says "manual override updates `Document.location_id`". If the Document has already been promoted to subsequent fiscal/stock state (reservation already taken at chosen_location, etc.), an override must also release/re-take the reservation. Spec hints at "reservation race" in §8 but doesn't connect the manual-override path to reservation rebalance. Suggestion: add an acceptance criterion that override cancels the prior reservation and re-creates at the new location, or document that override is gated to a pre-reservation lifecycle stage.

- **[S-4] T4: Tunisian seeder file name vs path**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t4-order-routing.md:158, 187, 286`
  - Spec calls the file `TunisianGovernorateZoneSeeder` but never anchors a path. To preserve the productization rule, it should land in `apps/erp/apps/api/database/seeders/` (the existing seeder home, per round-1 P1-6 corrected paths), not inside the `OrderRouting` module. Pin the path so it isn't dropped under `app/Modules/OrderRouting/Database/Seeders/` where future code-scan grep for "Tunis" would catch it.

- **[S-5] T3: webhook URL → tenant resolution path**
  - File: `apps/erp/docs/superpowers/specs/2026-05-24-t3-sync-hub.md:247, 274`
  - Spec asserts "Webhook from one tenant's channel URL cannot mutate another tenant's data (channel_id in URL resolves tenant via Stancl)." Pre-flip (today), Stancl resolves tenant from domain/subdomain, not from URL path parameter. Post-flip the same is true. So "channel_id in URL resolves tenant via Stancl" is misleading — the actual resolution is *subdomain* → Stancl tenant binding → query `channels` table within that tenant DB → verify `channel_id` exists in this tenant's DB. Spec should clarify the resolution chain so an implementer doesn't write a custom path-parameter tenant resolver.

## What's solid

1. **Topology-contract compliance is consistent and intentional.** Both specs cite the constitutional document, name it as the source of truth, and execute its rules (tenant migrations directory, no cross-DB FKs, no `tenant_id` FK on T4 routing tables). Where the round-1 reviewer recommended a pattern the topology contract overrules, T4 v2 explicitly inverts course and explains why (T4 §2 lines 39–43).

2. **T3 scope-reduction-to-infrastructure is clean and disciplined.** The reframe correctly identifies that we don't know which platform the client uses, so building a WooCommerce adapter is premature. The deliverables list (port + registry + framework + UI + reconciliation skeleton) is internally coherent at 6 PD. Test-adapter strategy (`ExampleTestAdapter` + `NullSignatureStrategy`) gives acceptance criteria a runnable target without leaking adapter-specific assumptions into production code.

3. **Workflow recommendations match Opus-vs-Codex distinction.** T3 puts Opus on Phase 1 (port + DTO + signature-strategy interface design — architecture) and Codex on the rest (entities, services, UI, tests). T4 puts Opus on Phase 2 (`ScoringStrategy` + `RuleEvaluator` + `OrderRoutingService` semantics) and Codex on CRUD + strategy implementations + UI. Both are correct distinctions; the spec-level workflow assignments resolve round-1 P2-3 from the spec side.

4. **All cited file paths verified to exist.** Spot-checked 12 of ~15 unique citations across both specs (PlatformHttpClient, VerifySynerivaWebhookSignature, ProcessEnrichmentWebhookJob, StockMovementRecorded, SyncListingOnStockChange, Marketplace Domain, Product module, Document, DocumentType, DeliveryStatus, Location, StockLevel, StockReservation, Partner). All resolve. Line-range citations (e.g., `Location.php:22-88`, `PlatformHttpClient.php:215-221`) match actual code. The round-1 B-2 BLOCKER on wrong paths is fully addressed.

5. **Adapter registry empty-state UI is explicitly designed for the demo.** T3 §5 calls out "No adapters available yet" notice on `ChannelListPage` and "Adapter modules coming in next release" on the create-wizard adapter-type dropdown. This is the right UX for the productization phase — the framework is demoable without requiring a concrete adapter — and proves the deferment is real, not just spec text.
