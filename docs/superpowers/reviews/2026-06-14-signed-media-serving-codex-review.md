- `app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php`

I also read supporting code for route middleware resolution, tenancy, media storage, upload validation, models, migrations, and product/public image facades where needed to verify the security properties.

## Executive Summary

The core design holds: `media.serve` is outside Sanctum auth and is protected by Laravel `ValidateSignature`; URLs generated by `MediaUrlResolver::forAttachment()` use `temporarySignedRoute()` with a 60-minute expiry and include `tenant`, `attachment`, and optional `variant` in the signed URL. The endpoint works for unauthenticated `<img>` requests.

I did not find a direct signature-bypass or cross-tenant IDOR in the normal controller path. However, the serving controller is less strict than the product/public list paths: it tenant-scopes the attachment but not the loaded media asset/renditions, does not require `READY` status, accepts signed unknown variants by serving the original, and has no dedicated throttle despite being public.

## Findings

### MEDIUM - Media asset relation is not tenant-constrained in the signed serving query

File: `apps/api/app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php:85`

Observed in code:

`SignedMediaController` resolves the tenant, initializes tenancy, then queries `MediaAttachment` by `id` and `tenant_id` and eager-loads `mediaAsset.renditions` without a tenant constraint (`SignedMediaController.php:85-89`). It then trusts `$mediaAttachment->mediaAsset` and serves it if `$asset->type === MediaAssetType::Image` (`SignedMediaController.php:95-109`).

The normal product/public image paths are stricter. `ProductMediaController::loadAttachments()` filters assets with `whereHas('mediaAsset', tenant_id + READY)` and constrains the eager-loaded relation to the same tenant (`ProductMediaController.php:323-340`). `PublicProductMediaController::resolveAttachment()` also constrains the eager-loaded `mediaAsset` relation by product tenant (`PublicProductMediaController.php:103-113`).

Hypothesized attack path:

In the current shared-schema phase, a bad import, compromised admin path, application bug, or direct DB write could create a tenant-A `media_attachments` row pointing at a tenant-B `media_assets.id`. The signed controller would find the tenant-A attachment, load the tenant-B asset by `media_asset_id`, and serve tenant-B bytes under a valid tenant-A signed URL. The migrations only enforce `media_attachments.media_asset_id -> media_assets.id`; they do not enforce a composite `(tenant_id, media_asset_id)` constraint (`2026_06_12_100003_create_media_attachments_table.php:16-29`). `MediaAttachmentService::attach()` also creates the link without verifying the referenced asset's `tenant_id` (`MediaAttachmentService.php:47-75`).

Concrete fix:

Constrain the relation in `SignedMediaController` and fail closed if it does not match:

- Add `whereHas('mediaAsset', fn ($q) => $q->where('tenant_id', $tenant))`.
- Eager-load `mediaAsset` and `renditions` with tenant constraints; constrain renditions too if they remain in the shared schema.
- Add a DB-level tenant integrity backstop where feasible, or validate in `MediaAttachmentService::attach()` that the asset belongs to the requested tenant before creating the attachment.
- Add a regression test with an attachment whose `tenant_id` is A and whose asset belongs to B; a signed URL for tenant A must return 404.

### MEDIUM - Public signed media route has no dedicated throttle

File: `apps/api/app/Modules/Product/routes.php:149`

Observed in code:

The signed route is registered with only `['api', 'signed']` (`Product/routes.php:149-152`). `php artisan route:list --name=media.serve -vv` expanded the stack to Sanctum stateful handling, tenancy/security headers/bindings, and `Illuminate\Routing\Middleware\ValidateSignature`; it did not include a throttle middleware. By contrast, public product images use `throttle:public-product-images` (`Product/routes.php:154-160`), and image upload uses `throttle:image-upload` (`Product/routes.php:125-127`). The app defines a `public-product-images` limiter at 100/min/IP (`AppServiceProvider.php:302-305`), but it is not applied to `media.serve`.

Hypothesized attack path:

Any party with a valid signed image URL can replay it for the full 60-minute TTL without route-level throttling. That enables cheap scraping and storage egress amplification if URLs are leaked through browser history, logs, referrers, screenshots, or shared pages. Signature validation prevents guessing; it does not rate-limit valid bearer URLs.

Concrete fix:

Add a dedicated throttle to the signed route, for example `throttle:signed-media`, keyed by IP plus route tenant or attachment. Consider stacking a modest per-IP cap with a per-attachment cap. Keep the route unauthenticated for `<img>` compatibility.

### MEDIUM - Signed serving does not require media asset status READY

File: `apps/api/app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php:95`

Observed in code:

The signed controller checks only that the loaded asset exists and has `type === MediaAssetType::Image` (`SignedMediaController.php:95-100`). It does not check `status === MediaStatus::Ready`. Product and public list paths explicitly require ready assets (`ProductMediaController.php:323-333`, `PublicProductMediaController.php:122-137`). Tests create `MediaStatus::Ready` assets for the happy path (`SignedMediaServeTest.php:67-75`) but do not assert that `UPLOADED`, `PROCESSING`, or `FAILED` assets are rejected.

This matters because `ProductMediaController::store()` returns `formatOne()` immediately after upload/attach (`ProductMediaController.php:131-143`), and `formatOne()` mints a signed URL via `forAttachment()` (`ProductMediaController.php:348-360`). `MediaUploadService` creates uploaded assets with `MediaStatus::Uploaded` and only later dispatches rendition generation after commit (`MediaUploadService.php:130-152`).

Hypothesized attack path:

A signed URL issued immediately after upload can serve original bytes before asynchronous processing marks the asset ready. If rendition processing later fails due malformed content, the previously minted signed URL can still serve the original until expiry. The normal catalog/public query policy says only `READY` media should be displayed, but the byte-serving endpoint does not enforce that policy.

Concrete fix:

Have `SignedMediaController` require `MediaStatus::Ready` unless the product intentionally needs immediate post-upload preview of unprocessed originals. If immediate preview is required, create an explicit separate policy and test for it. Add tests for `UPLOADED`, `PROCESSING`, and `FAILED` signed URLs.

### LOW - Unknown signed variants are downgraded to original instead of rejected

File: `apps/api/app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php:103`

Observed in code:

The controller reads `?variant`, accepts only `sm` and `md`, but maps every other string to `null` (`SignedMediaController.php:102-107`). The storage adapter treats `null` or unknown variants as original (`MediaStorageAdapter.php:57-78`). The resolver signs whatever non-null variant string its caller supplies (`MediaUrlResolver.php:74-81`); it does not validate the variant before signing.

Tampering with `variant` after URL generation invalidates the signature, so this is not a signature-bypass. The issue is that a legitimately signed URL with `variant=bad` serves the original, which is surprising for a route that documents only `sm` and `md` as accepted variants.

Concrete fix:

Reject unknown variant strings in the controller with 404 or 400. Also validate the resolver input so internal callers cannot accidentally mint signed URLs for unsupported variants. Add a test that `URL::temporarySignedRoute('media.serve', ..., ['variant' => 'lg'])` returns the chosen rejection status.

### LOW - Serve path relies on creation-time image validation, not a serve-time MIME allow-list

File: `apps/api/app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php:98`

Observed in code:

The signed route rejects non-`IMAGE` asset types (`SignedMediaController.php:95-100`). Normal upload validation allows only JPEG, PNG, WebP, and GIF (`MediaUploadService.php:45-50`, `ProductMediaController.php:87-89`), so SVG/HTML are not accepted through the standard upload flow. The API middleware adds `X-Content-Type-Options: nosniff` (`SecurityHeaders.php:35-37`).

The serving path itself does not enforce `mime_type` or extension allow-lists before calling `Storage::disk($disk)->response($path)` (`MediaStorageAdapter.php:78`). If a stale, imported, or manually-created asset row is typed `IMAGE` but points at SVG/HTML or a path with dangerous content type metadata, the endpoint may inline it.

Concrete fix:

Add a serve-time MIME allow-list matching upload-time policy before streaming, and preferably set an explicit `Content-Type` from trusted metadata plus `Content-Disposition: inline; filename=...` for known-safe raster formats only. Reject `image/svg+xml` and text/html even if `type` is `IMAGE`.

## Positive Security Observations

### INFO - Signature middleware is actually active on `media.serve`

File: `apps/api/app/Modules/Product/routes.php:149`

Observed in code:

The route is registered under `Route::prefix('api/v1')->middleware(['api', 'signed'])` (`Product/routes.php:149-152`). Laravel's installed default middleware aliases map `signed` to `Illuminate\Routing\Middleware\ValidateSignature` (`vendor/laravel/framework/src/Illuminate/Foundation/Configuration/Middleware.php:779-791`). `php artisan route:list --name=media.serve -vv` confirmed `Illuminate\Routing\Middleware\ValidateSignature` in the expanded stack.

### INFO - Signature covers tenant, attachment, variant, and expiry for URLs generated by the resolver

File: `apps/api/app/Modules/Catalog/Application/Services/MediaUrlResolver.php:78`

Observed in code:

`MediaUrlResolver::forAttachment()` passes `tenant`, `attachment`, and optional `variant` to `URL::temporarySignedRoute('media.serve', now()->addMinutes(60), $params)` (`MediaUrlResolver.php:65-82`). Laravel's `signedRoute()` adds `expires`, sorts the parameters, and signs the full route URL with HMAC-SHA256 (`UrlGenerator.php:358-376`). `temporarySignedRoute()` delegates to `signedRoute()` (`UrlGenerator.php:413-415`). Validation checks both `hasCorrectSignature()` and `signatureHasNotExpired()` (`UrlGenerator.php:426-429`). Removing `signature`, changing/removing `expires`, or swapping `tenant`, `attachment`, or `variant` after generation changes the canonical URL and fails validation.

### INFO - The route is intentionally outside Sanctum auth and works for `<img>` tags

File: `apps/api/app/Modules/Product/routes.php:149`

Observed in code:

The signed route is registered separately from the authenticated product group. The authenticated group includes `auth:sanctum`, `SetPermissionsTeam`, `EnforceTokenTenantClaim`, and `module:Inventory` (`Product/routes.php:42-144`). The signed route only uses `api` and `signed` (`Product/routes.php:146-152`). The feature test requests the signed URL with no Authorization header and receives 200 (`SignedMediaServeTest.php:86-98`). The frontend components use plain `<img src={image.url}>` with no custom headers (`ProductPrimaryImageDisplay.tsx:90-95`, `ProductImageGallery.tsx:104-109`, `ImageGalleryModal.tsx:138-142` and `173-177`).

### INFO - Tenant parameter and attachment ID are both checked before serving

File: `apps/api/app/Modules/Catalog/Presentation/Controllers/SignedMediaController.php:62`

Observed in code:

The controller rejects non-UUID route params before querying (`SignedMediaController.php:62-65`), resolves the tenant (`SignedMediaController.php:67-73`), initializes tenancy via `TenancyResolver::initializeIfProvisioned()` (`SignedMediaController.php:75-80`), and queries the attachment by both `id` and `tenant_id` (`SignedMediaController.php:85-89`). In DB-per-tenant mode, `TenancyResolver` fails closed when the tenant database is missing or cannot be initialized (`TenancyResolver.php:51-95`).

### INFO - POS sync URL contract is preserved

File: `apps/api/app/Modules/Catalog/Application/Queries/CatalogMediaQuery.php:48`

Observed in code:

`CatalogMediaQuery` feeds POS sync and explicitly calls `forPosSync($a, 'sm')` rather than `forAttachment()` (`CatalogMediaQuery.php:48-53`). `forPosSync()` returns the legacy `products.images.download` route for uploaded assets (`MediaUrlResolver.php:111-124`). The old authenticated download route remains registered under `products/{product}/images/{image}/download` (`Product/routes.php:120-143`).

## Requested Checkpoints

### 1. Signature integrity

Observed: protected by `ValidateSignature`, confirmed by route list and Laravel alias table. Generated URLs use APP_KEY through Laravel's URL generator key resolver; the installed Laravel code signs with `hash_hmac('sha256', route(...), key)` (`UrlGenerator.php:370-376`). Expiry is included by `temporarySignedRoute()` and enforced by `hasValidSignature()` (`UrlGenerator.php:413-429`, `502-506`). Stripping or changing `expires`/`signature` is not a viable downgrade for resolver-generated URLs.

### 2. Tenant isolation / IDOR

Observed: direct route param swapping is blocked by the signature, and the controller scopes `MediaAttachment` to `tenant_id === {tenant}` (`SignedMediaController.php:85-89`). A valid signature for tenant A plus an attachment row belonging to tenant B returns 404 in the test (`SignedMediaServeTest.php:149-186`).

Residual risk: the loaded `mediaAsset` and `renditions` are not tenant-constrained in the signed controller; see MEDIUM finding above.

### 3. Untrusted-content serving

Observed: the controller only serves assets with `MediaAssetType::Image` (`SignedMediaController.php:95-100`). Normal upload flow rejects SVG/HTML by MIME and request validation (`MediaUploadService.php:45-50`, `ProductMediaController.php:87-89`). External URLs are not fetched server-side by `MediaUrlResolver::forAttachment()`; it returns the raw external URL for external assets (`MediaUrlResolver.php:61-63`). The storage adapter would redirect external-url assets if called directly (`MediaStorageAdapter.php:53-55`), but the normal resolver does not wrap them in signed media URLs.

Residual risk: no serve-time MIME allow-list; see LOW finding above.

### 4. Does it work for `<img>` tags?

Observed: yes. The route is unauthenticated except for the URL signature, and tests prove a request without an Authorization header returns 200 (`SignedMediaServeTest.php:86-98`). The React components use ordinary `<img>` tags with `src={image.url}` and no bearer-header fetch proxy.

### 5. Info leak / enumeration

Observed: malformed UUIDs, unknown tenants, and attachment misses return 404 (`SignedMediaController.php:62-73`, `91-93`). Invalid or expired signatures fail before the controller with 403, as tested (`SignedMediaServeTest.php:104-143`). This difference reveals whether the signature was valid, but an unauthenticated attacker cannot cheaply enumerate signatures without APP_KEY or a leaked signed URL.

Residual risk: no dedicated throttle on a public bearer-URL route; see MEDIUM finding above.

### 6. Regressions

Observed: POS sync still uses the frozen download URL through `forPosSync()` (`CatalogMediaQuery.php:48-53`, `MediaUrlResolver.php:111-124`). The old product image download route remains unchanged in `Product/routes.php:137-138`. Current tests cover valid/no-auth, tampered signature, expired signature, cross-tenant attachment ID, external URL resolver behavior, and upload signed URL generation (`SignedMediaServeTest.php:62-238`).

Test gaps:

- Signed URL with tenant-A attachment pointing at tenant-B asset.
- Non-ready asset statuses.
- Unknown signed variants.
- Serve-time MIME rejection.
- Dedicated throttling behavior once added.
