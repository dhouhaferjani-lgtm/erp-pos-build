## New Findings (if any)

### P2-H: Full replace-all must be page-complete and transactional
**Finding:** The spec says a full pull deletes local rows "absent from the full response" (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:120`) while the endpoint is paginated at 500/page (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:125`). It does not explicitly say the client must accumulate all pages and apply the replace-all delete only after the final page succeeds. A page-by-page delete implementation would briefly or permanently delete rows that merely live on later pages if the full pull is interrupted.
**Recommendation:** Specify that full-mode reconciliation runs in one SQLite transaction after all pages are fetched: upsert all returned rows, delete rows not in the complete fetched key set, update incoming columns, then advance the cursor. If any page fails, keep the previous local stock snapshot and cursor.

### P2-I: Incoming-only rows need explicit local materialization
**Finding:** The API returns `stock` rows and a separate complete `incoming` array (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:101-115`, `118`). The local table combines stock and incoming columns, and `pullLocationStock()` "upserts stock rows" then replaces incoming columns (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:155`). The spec does not explicitly say that an incoming row for a product/variant with no destination `stock_levels` row must create a `location_stock` row with zero quantity/reserved/available. Without that, zero-on-hand items with an active inbound transfer or PO may not show the required arriving indicator.
**Recommendation:** Add an explicit rule: every `incoming` key is upserted into `location_stock` if missing, with `quantity`, `reserved`, and `available` set to zero and incoming columns populated; in full replace-all, incoming-only keys must be preserved or inserted after stock deletion.

### P2-J: Operator note does not define mid-shift identity reversion on location status changes
**Finding:** The rollout note only covers a branch with `tax_id` but incomplete address reverting to company identity (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:215`). The spec also says terminal identity comes from `TerminalResource` (`docs/superpowers/specs/2026-06-11-pos-location-aware-stock-design.md:188`, `193`), and the existing POS refreshes the terminal record during sync ticks (`apps/pos/src/lib/sync/syncScheduler.ts:96-108`; `apps/pos/src/stores/terminalStore.ts:750-804`). Locations have `is_active` and `pos_enabled` fields (`apps/api/app/Modules/Company/Domain/Location.php:38-40`, `103-110`; `LocationResource.php:38-40`), but the spec does not say whether deactivating or POS-disabling the bound location mid-shift should freeze the old fiscal identity for the shift, revert to company identity immediately, block new sales, or wait until shift close.
**Recommendation:** Add a rollout/behavior clause for refreshed terminal/location metadata during an open shift. At minimum, state whether fiscal identity is snapshotted at shift open or re-resolved per receipt, and what operator-facing message/action occurs if the bound location becomes inactive, POS-disabled, deleted, or loses identity completeness mid-shift.
