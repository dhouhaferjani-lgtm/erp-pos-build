# Adversarial Review (Round 2) — T5 Reporting
## Reviewer: Codex headless
## Date: 2026-05-24

## Verdict
NEEDS-REVISION

## Summary
The v2 spec fixes the round-1 ECharts grounding error: `Dashboard.tsx` and `ReportsPage.tsx` are no longer described as existing chart surfaces, and the spec correctly points implementers at the POS analytics components for `ReactECharts` usage. The migration-topology language is also directionally aligned with the new contract: any reporting views are tenant-owned and the spec does not propose cross-DB foreign keys.

The remaining risk is authorization and scope, not charting. The proposed endpoints accept `company_ids[]` and `location_ids[]`, but the spec does not define the resolver/intersection layer that prevents crafted query strings from expanding a user's scope. Current code validates the `X-Company-Id` request context, and there are location-access helpers, but neither is enough by itself for multi-company and multi-location report arrays.

Several grounding claims still need tightening before implementation: `dashboard.owner` does not exist, `ProductVariant` is listed as an existing entity even though T2 has not added it, `ReportsController.php:61-71` is not an endpoint location, and one POS chart reference is mislabeled as a pie chart.

## Findings

### BLOCKER
#### Multi-company and location filter authorization is underspecified
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:90-112`, `:146`, `:191-193`, `:208-210`

**Claim under review:** New report services/endpoints support `company_ids[]` and `location_ids[]`, and shop managers/users restricted to Company A or one location cannot see other data.

**What I actually found:** `CompanyContextMiddleware` validates only the selected request company from `X-Company-Id` or the user's default membership before setting context (`apps/api/app/Http/Middleware/CompanyContextMiddleware.php:54-77`, `:102-111`). `CompanyContext::userHasAccessToCompany()` checks one company ID (`apps/api/app/Modules/Company/Services/CompanyContext.php:126-130`). Location restriction logic exists, but it is also per-location: `LocationContext::canAccessLocation()` checks a single location against `allowed_location_ids` (`apps/api/app/Modules/Company/Services/LocationContext.php:196-210`), and `ValidLocationAccess` validates one attribute value (`apps/api/app/Rules/ValidLocationAccess.php:62-96`). I did not find a report-scope resolver that intersects requested `company_ids[]` and `location_ids[]` with the authenticated user's allowed memberships/locations.

**Why it matters:** The proposed endpoints are array-filtered reporting endpoints. If implementation simply does `whereIn('company_id', $request->company_ids)` or `whereIn('location_id', $request->location_ids)`, a user can attempt to widen scope through query parameters even though the header company was valid.

**Suggested fix:** Add an explicit `ReportScopeResolver` or equivalent before Phase 1: resolve authorized company IDs from active `UserCompanyMembership` rows, resolve authorized location IDs from `allowed_location_ids`, intersect/deny requested filters, and pass only authorized IDs into services. Add crafted-URL tests for unauthorized `company_ids[]=...` and `location_ids[]=...`.

### P1
#### `dashboard.owner` permission is not grounded
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:120`

**Claim under review:** The new owner dashboard is accessible to roles with `dashboard.owner`.

**What I actually found:** The frontend permission map has `dashboard.view`, but no `dashboard.owner` (`apps/web/src/hooks/usePermissions.ts:39-56`). The backend `RolesAndPermissionsSeeder` creates many permissions, but no `dashboard.owner` in the permissions list (`apps/api/database/seeders/RolesAndPermissionsSeeder.php:32-140` and no repo matches for `dashboard.owner`). Existing protected app routing exposes `/dashboard` without a `RequirePermission` wrapper (`apps/web/src/routes/index.tsx:446-453`).

**Why it matters:** Implementers will either add a guard that always denies everyone, silently fall back to a broader permission, or add a new permission without seeding/role assignment/API parity.

**Suggested fix:** Decide explicitly: use existing `reports.view`/`dashboard.view`, or add `dashboard.owner` in the backend seeder and frontend permission map with role assignments and tests.

#### `ProductVariant` is listed as an existing entity, but it is not present yet
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:68-70`, `:165-172`, `:261`

**Claim under review:** T5 works on existing entities including `ProductVariant`, while top-SKU and low-stock widgets are variant-aware after T2.

**What I actually found:** There is no `ProductVariant` model or `product_variants` migration in the current code. Current matches are future/TODO references such as `product_batches` noting the table does not exist yet, and `inventory_counting_items.variant_id` comments for future support. The spec itself later says T5 soft-depends on T2 for variant-aware top SKUs (`docs/superpowers/specs/2026-05-24-t5-reporting.md:261`).

**Why it matters:** This creates a parallel-session trap. T5 implementers may type DTOs/services against a nonexistent class/table or add their own variant assumptions before T2 lands.

**Suggested fix:** Change Section 3 to say `ProductVariant` is a T2-created future dependency. Require T5 Phase 1 to aggregate non-variant products only, with a small adapter point or follow-up task after T2 merges.

#### Reports controller citation and endpoint grounding are misleading
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:44`

**Claim under review:** `apps/api/app/Modules/Accounting/Presentation/Controllers/ReportsController.php` lines 61-71 are existing report endpoints.

**What I actually found:** Lines 61-71 are the class declaration and constructor dependency list, not endpoint methods (`apps/api/app/Modules/Accounting/Presentation/Controllers/ReportsController.php:61-71`). Actual Accounting report routes are in `apps/api/app/Modules/Accounting/Presentation/routes.php:161-180`. Separately, Document also registers `/reports/aged-receivables`, `/reports/customer-statement/{partnerId}`, and `/reports/overdue-summary` (`apps/api/app/Modules/Document/Presentation/routes.php:349-360`), while `reportsApi.ts` calls those URI shapes (`apps/web/src/features/reports/api/reportsApi.ts:76-107`).

**Why it matters:** The spec tells backend implementers to extend the wrong line reference and underplays the existing `/reports/*` route namespace collision between Accounting and Document.

**Suggested fix:** Replace the citation with actual route files and controller methods. Explicitly choose where owner reporting routes live, and avoid reusing ambiguous `/reports/aged-receivables` naming patterns.

#### Tenant timezone handling is an acceptance criterion but has no implementation contract
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:131`, `:217`

**Claim under review:** Date range picker correctly handles tenant timezone.

**What I actually found:** Company timezone exists on the model (`apps/api/app/Modules/Company/Domain/Company.php:55-58`) and in the frontend company store, but the POS analytics pattern uses browser dates (`toISOString().split('T')[0]`) in the filter (`apps/web/src/features/pos/organisms/Analytics/AnalyticsDateFilter.tsx:11-31`) and backend parsing with `CarbonImmutable::parse()` (`apps/api/app/Modules/POS/Presentation/Controllers/AnalyticsController.php:157-162`). POS analytics services then use `startOfDay()`/`endOfDay()` without applying company timezone (`apps/api/app/Modules/POS/Application/Services/PosAnalyticsService.php:21-24`, `:141-145`).

**Why it matters:** T5 is supposed to report owner sales by local business day. Browser timezone and server/default timezone can shift records across day boundaries for tenants outside the user's or server's timezone.

**Suggested fix:** Specify a concrete timezone contract: backend resolves `Company::timezone`, parses `from` and `to` in that timezone, converts boundaries to the storage timezone for timestamp comparisons, and groups periods with `AT TIME ZONE`/equivalent. Add tests for a tenant timezone that differs from server/browser timezone.

### P2
#### One POS chart pattern is mislabeled as a pie chart
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:38-43`

**Claim under review:** `DiscountBreakdownChart.tsx` is a pie chart pattern.

**What I actually found:** `DiscountBreakdownChart` renders a bar chart: its series has `type: 'bar'` and a hardcoded hex color (`apps/web/src/features/pos/organisms/Analytics/DiscountBreakdownChart.tsx:16-32`). `SalesByCategoryChart` is the actual donut/pie reference.

**Why it matters:** Minor, but implementers could mirror the wrong chart for payment-method breakdown or category revenue.

**Suggested fix:** Reword the architecture grounding: `SalesByCategoryChart.tsx` is the donut/pie pattern; `DiscountBreakdownChart.tsx` is a bar chart plus KPI/table composition pattern.

#### Existing POS analytics pattern does not meet the new design-token requirement
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:60`, `:216`

**Claim under review:** New owner charts should mirror POS analytics while consuming `designTokens.ts`.

**What I actually found:** POS chart components do use `ReactECharts` (`SalesTimeSeriesChart.tsx:1`, `SalesByCategoryChart.tsx:1`), but some chart options use hardcoded colors, e.g. `#f59e0b` in `DiscountBreakdownChart.tsx:29` and `#8b5cf6` in `FnbMetricsPanel.tsx`. `designTokens.ts` exists and is Tailwind-class oriented (`apps/web/src/lib/designTokens.ts:1-80`), while ECharts needs raw color values.

**Why it matters:** "Mirror POS analytics" and "no hardcoded colors" pull in different directions unless the wrapper defines ECharts-compatible raw palette values.

**Suggested fix:** Require `OwnerChart` to translate design tokens or a small approved raw palette into ECharts option colors. Do not copy POS hardcoded hex values.

#### Backend "6 production report services" exists, but route exposure is not six ReportsController endpoints
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:23-26`, `:44-46`

**Claim under review:** Accounting has 6 production report services and existing report endpoints to extend.

**What I actually found:** The six service files exist in `Accounting/Application/Services/Reports/`: AgedPayables, AgedReceivables, BalanceSheet, GeneralLedgerReport, ProfitLoss, TrialBalance. Accounting routes expose trial balance, profit/loss, balance sheet, aged receivables, and aged payables (`apps/api/app/Modules/Accounting/Presentation/routes.php:161-180`). General ledger is routed separately through `LedgerController` at `/ledger` (`apps/api/app/Modules/Accounting/Presentation/routes.php:156-159`), not as a `ReportsController` report endpoint.

**Why it matters:** The existence of service classes is real, but "extend existing endpoints" is too imprecise for a parallel backend session.

**Suggested fix:** Say "six service files exist; five Accounting report routes plus separate ledger route exist." Point new owner endpoints to a new controller or a clearly chosen module.

### SUGGESTION
#### Define the route namespace for owner reports explicitly
**Where:** `docs/superpowers/specs/2026-05-24-t5-reporting.md:105-112`

**Claim under review:** New endpoints live under `/api/v1/reports/...`.

**What I actually found:** `/reports/*` is already shared by Document and Accounting modules, including duplicate `/reports/aged-receivables` route declarations (`apps/api/app/Modules/Document/Presentation/routes.php:349-352`, `apps/api/app/Modules/Accounting/Presentation/routes.php:174-176`).

**Why it matters:** Adding six more broad `/reports/*` endpoints may deepen ambiguity.

**Suggested fix:** Consider `/api/v1/owner-reports/...` or a dedicated `OwnerReporting` controller/module. At minimum, name the owning route file and controller in the spec.

## Adversarial Review Checklist verification
- **Tenant isolation:** PARTIAL. The T6 DB boundary and current `CompanyContextMiddleware` help, but new multi-company filters need explicit authorization/intersection before services run.
- **Company filter respects permissions:** FAIL. The spec requires it, but no implementation pattern is named for `company_ids[]`. Current helpers validate one request company, not arbitrary query arrays.
- **Location filter respects permissions:** PARTIAL. `LocationContext` and `ValidLocationAccess` exist for single-location checks, but the spec does not require array validation/intersection for `location_ids[]`.
- **ECharts pattern reuse:** PARTIAL. `echarts` and `echarts-for-react` are installed, and POS components use `ReactECharts`; however `DiscountBreakdownChart` is mislabeled as pie and POS charts should not be copied wholesale for colors.
- **DB view tenant scoping:** PASS conditional. The spec says views, if needed, go in `database/migrations/tenant/` and does not propose cross-DB FKs. This depends on T6 Phase 0 landing first.
- **Performance:** PARTIAL. The spec sets an <800ms target but does not specify seed fixtures, query plans, or concrete indexes. Current POS analytics queries filter by company/date but are not proof for 30 locations and 10k receipts/month.
- **Backward compat:** PASS. The spec says existing `Dashboard.tsx` and `ReportsPage.tsx` remain unchanged unless touched.
- **i18n:** PARTIAL. Existing components use `t()`, but the spec does not define the namespace/key files for FR and AR owner-dashboard labels.
- **No hardcoded colors in NEW code:** PASS as a spec requirement, with caveat that POS patterns include hardcoded raw colors and should not be copied blindly.
- **Date range picker:** FAIL. Tenant timezone is called out but no frontend/backend timezone contract is specified; the closest POS pattern uses browser/server-local date handling.
- **Migrations (if any):** PASS conditional. The spec places views in `database/migrations/tenant/` and avoids cross-DB FKs, but that directory is not present yet in this checkout; T6 Phase 0 must land first.

## Migration topology compliance
The spec is compliant in intent: it says any reporting views belong in `apps/api/database/migrations/tenant/` and does not introduce database tables or foreign keys. I found no proposed cross-DB FK declarations in the T5 spec.

The operational caveat is sequencing. In the current checkout, `apps/api/database/migrations/tenant/` does not exist yet; only `apps/api/database/migrations/` and `apps/api/database/migrations/manual/` are present. T5 migration work must wait for the T6 Phase 0 gate or it will have no valid target directory.

## What's solid
- The v2 spec correctly stops claiming that `Dashboard.tsx` and `ReportsPage.tsx` already use ECharts.
- `echarts` and `echarts-for-react` are installed at `apps/web/package.json:49-50`; no new chart dependency is needed.
- POS analytics provides real `ReactECharts` examples and TanStack Query hooks with `tenantScopedKey`.
- The spec's "no POS touch" boundary is credible for a reporting surface that only reads POS receipts/shifts and does not change Tauri/offline behavior.
- The migration guidance aligns with the topology contract: views are tenant artifacts and no cross-DB FK is proposed.

## Round-1 comparison (if applicable)
Round 1 P1-1 for T5 is resolved: v1 incorrectly called `Dashboard.tsx` and `ReportsPage.tsx` production-wired ECharts surfaces; v2 now states they do not import ECharts and reframes T5 as the first owner-dashboard chart surface.

Round 1 also called out the lack of a sprint-wide migration topology contract. T5 now references the new topology contract and places possible views under `database/migrations/tenant/`, which resolves the T5 side of that issue conditionally on T6 Phase 0 landing before implementation.
