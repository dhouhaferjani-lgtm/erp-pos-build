## The five recurring mechanisms

1. **Lot management stopped at the warehouse door.** Lots exist for goods receipt, transfer, write-off and B2B conversion. The POS device, the sealed SALE_RECEIPT payload, the counting model and the batch CRUD rules were never brought into the lot model. When DPA discovered the POS wrote no lot leg, the fix estimated the lot server-side and the estimate became "traceability". Covers F1, F7, F8, half of F6.
2. **Convention enforcement points that don't exist for some routes.** Action permissions live in FormRequests; routes without a body have no FormRequest and therefore no check. Covers F2. Same shape as F3: location scoping lives in an opt-in resolver call, so unmigrated endpoints are silently unscoped.
3. **Fix-the-scenario-in-front-of-you.** N-12 fixed cash→bank, not electronic→drawer. H-3 froze "unmapped method → drawer" as day-one truth. The sweep retries failures, not lost work. Gates reviewed the given scenario, never the full matrix. Covers F4, F5.2.
4. **Early design decisions never re-ratified when the stakes changed.** "Seal wins over GL" was fine for an audit listener in Dec 2025; it became a money-loss window once the listener was the sole GL writer and chain allocation went unlocked in June. Covers F5.1.
5. **Tests that assert code, not data meaning.** Z tests assert copied fields equal the payload; the tender test asserts the fallback is the drawer; the counting test pins DEFAULT top-up. Each pins the limitation as correct behaviour. Covers F4, F6, F7 (rule-22 class, already named 2026-08-29).

## Guards worth adding to the spec fix round (proposals, not rulings)

These are process/ratchet additions to fold into W1–W8 or a small W0. They target the mechanisms above, so the fix does not only move the failure.

- **Route action-permission ratchet** (mechanism 2, F2): an architecture test enumerating every mutating route under `Modules/*/Presentation/routes.php` and asserting a `permission:` middleware or a FormRequest `authorize()` that checks a permission. Baseline is legacy debt, shrink-only, same pattern as `TenantOnlyUniqueOnCatalogueTablesRatchetTest`.
- **Location-scope coverage census** (mechanism 2, F3): list every company-scoped read controller and mark scoped / bypass-declared / unscoped; a ratchet fails when an unscoped endpoint is added. Treasury repositories are the first entries.
- **Full-matrix acceptance for resolvers** (mechanism 3, F4): the tender resolver test file must contain all four cells (cash/electronic × drawer/settlement) plus "unmapped" per class; the spec's W2 acceptance already lists most of them. Reverse the H-3 pin explicitly (owner decision 3 in the Fable review).
- **Lot-model completeness statement** (mechanism 1): a short glossary entry for "lot evidence" with provenance values `operator_captured` / `system_fefo_estimate` / `unknown`, and a rule that no surface may display an estimate as captured. This is what W6 shelf-control labelling needs regardless of D3/D7.
- **Re-ratify "seal wins over GL"** (mechanism 4, F5.1): W3 already does this. Add to its acceptance: a PostgreSQL concurrency test, since the SQLite suite cannot show the collision.
- **Recovery scenarios as standing acceptance rows** (mechanism 3, F5.2): "enqueue lost after commit", "worker died in running", "registry threw at ingest" become required rows in every projection lane's acceptance, not only W4's.
- **Data-meaning assertions** (mechanism 5): when a lane pins a limitation as a test, the test name must carry `_pins_limitation_` (or an equivalent marker) so future audits can grep for frozen defects instead of rediscovering them. Candidates today: the H-3 seeded-method test, the DEFAULT top-up test, the Z copied-totals tests.
