- v5 genuinely resolves the five Opus v4 findings in the spec text: canonical module token is now `'Treasury'`, void/return are explicitly retained, parse-failure resume is transactional with a named recovery command, `ReceiptPaymentService` is split correctly, and §14.1 names the core old-sync classes.

Following v5 literally can still leave a server-authored `SALE_RECEIPT` path alive beside the new device-authority chain.
- Minor residual: the §14.1 backend feature-suite list is still not exhaustive; two live receipt-sync endpoint suites are omitted, though the verification grep would catch them.

## New findings
### [BLOCKER] Tauri online checkout still uses the retired server-authoring `SALE_RECEIPT` path, but v5 only dispositions browser web POS
**Dimension:** completeness / cross-app / grounding
**Spec location:** §5.0, §14.2, §17.5 (`spec v5:240-243,609-625,705-709`)
**Evidence:** SoT D8 requires one fiscal pattern with no two-model coexistence (`source-of-truth-v3.md:261`) and D16 says authoring/sealing/chain/ingestion must not depend on other operational runtimes (`source-of-truth-v3.md:242-246,269`). v5 states `SALE_RECEIPT` is authored only through `FiscalEventEngine.append()` and all fiscal events go through the single fiscal-event endpoint (`spec v5:240-243`). It dispositions the browser web POS callers (`spec v5:613-618`), but the Tauri POS has an online checkout branch that still calls the server-authoring receipt APIs: `onlineCheckout()` calls `createReceipt()` and `processReceiptPayments()` (`apps/pos/src/lib/offline/offlineCheckoutService.ts:83-115`), `executeCheckout()` chooses that online branch whenever connectivity is online (`:178-199`), and those API functions post to `/pos/receipts` and `/pos/receipts/{id}/payments` (`apps/pos/src/api/receiptApi.ts:14-27`). Those are the same backend authoring routes v5 wants hidden/disabled for web POS (`apps/api/app/Modules/POS/routes.php:98,102`; `ReceiptController.php:284-315,505-510`).
**Issue:** The spec closes the browser web-POS new-sale path but misses the Tauri online fallback. If implementers follow §14.2 literally, they can leave a physical POS terminal online mode that server-authors `SALE_RECEIPT` through `ReceiptController::store()` / `storePayments()` rather than the device `FiscalEventEngine.append()` and `/api/v1/pos/sync/fiscal-events`.
**Impact:** Phase 1 can ship with two authoring models for the same `SALE_RECEIPT`: offline/device-authority via `fiscal_events`, and online/server-authoring via `pos_receipts` + `ReceiptPaymentService`. That corrupts the central "one chain, one ingestion path" design and preserves the server recompute path the clean rebuild is supposed to remove.
**Suggested fix:** Add an explicit §14 disposition row for `apps/pos/src/lib/offline/offlineCheckoutService.ts` and `apps/pos/src/api/receiptApi.ts`: Phase 1 must remove or rework the online checkout branch so Tauri sale completion always authors locally via `FiscalEventEngine.append()` and then syncs the fiscal-event envelope. In §14.2, change "hide/disable backend routes" to "reject legacy `SALE_RECEIPT` server authoring for both `TerminalType::Web` and physical/Tauri online checkout, unless the route delegates to the fiscal-event engine." Add §17.5 tests proving online Tauri checkout does not call `/pos/receipts` / `/pos/receipts/{id}/payments` for new sales after the rebuild.

### [P3] §14.1 still omits two live backend receipt-sync feature suites
**Dimension:** codebase-claim / completeness
**Spec location:** §14.1 (`spec v5:603-607`)
**Evidence:** v5 says the backend feature suites targeting the retired endpoint are `SyncReceiptsTest.php`, `SyncReceiptsRequestTest.php`, `ReceiptSyncServiceV3Test.php`, `ReceiptSyncServiceInstrumentGuardTest.php`, `ReceiptSyncServiceTrainingModeTest.php`, and `ReceiptSyncServiceVoucherRedemptionTest.php` (`spec v5:603-605`). Live grep finds two additional feature suites posting to `/api/v1/pos/receipts/sync`: `apps/api/tests/Feature/POS/OfflineV3CutoverSyncTest.php:203,383,494` and `apps/api/tests/Feature/POS/PosStabilizationTenantIsolationTest.php:1366,1406`.
**Issue:** Opus v4 P3-2 asked for concrete receipt-sync feature suites. v5 improves the list but it is not exhaustive, so the codebase claim "the POS backend feature suites that target the retired endpoint" is still slightly false.
**Impact:** Low, because the §14.1 verification grep would catch these tests. Still, a writing-plan using the concrete list as scope can miss two suites and leave CI failures until late.
**Suggested fix:** Add `OfflineV3CutoverSyncTest.php` and `PosStabilizationTenantIsolationTest.php` to §14.1 / §17.5, or explicitly classify them as broader stabilization/cutover suites that must be migrated or deleted as part of the retired endpoint cleanup.
