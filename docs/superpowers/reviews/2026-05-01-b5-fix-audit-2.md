## What's solid

- **The hash-parity ordering invariant the implementer flagged is real, was respected, and is locked in by a real test.** When server's `ReceiptSyncService::syncSingleReceipt` enters its `DB::transaction`, it calls `finalize()` BEFORE `redeem()`. V3ReceiptHashComputer eager-loads `voucherLedgerEntries` from the DB during finalize — at that moment the DB has zero ledger rows for the freshly-created receipt → empty array → hash computed matches the offline hash. AFTER finalize succeeds, redeem() writes the canonical ledger row + GL leg. If the order were reversed, fixture-08 hash would diverge for every voucher-bearing receipt (because v3 binds voucher_ledger_entries in the canonical input). The proof is `OfflineV3CutoverSyncTest::test_v3_terminal_accepts_offline_voucher_payment_with_instrument_fields_intact:391-397` — server-recomputed v3 hash MUST equal offline hash for voucher-bearing receipt.

- **Defense-in-depth on the per-entry status inspection.** The new code adds (a) a TypeScript interface with explicit `'synced' | 'duplicate' | 'failed'` union, (b) a type-guard `isVoucherLedgerPushResponse` that REQUIRES `Array.isArray(v.results)` so a stale server returning `{}` fails the row safely, (c) a per-entry `id` matcher (with index-0 fallback) so the client matches its local row by id rather than by position, (d) explicit branching: `'synced'`/`'duplicate'` → markVoucherLedgerEntrySynced; `'failed'` → markVoucherLedgerEntryFailed with the per-entry error reason; HTTP-throws → markVoucherLedgerEntryFailed with the exception message. Every branch is tested.

- **Atomicity preserved through Option B.** The local voucher_ledger row write was removed but the local balance update stays inside the same `BEGIN TRANSACTION` block. A failure in `updateVoucherBalanceAndStatus` rolls back the receipt insert + chain advance + balance update atomically. Tested at `receiptService.test.ts:910` (mock-driven) and `voucherCheckout.integration.test.ts:271` (real SQLite).

- **Idempotency contract correctly documented and enforced.** The B5-fix audit Minor 3 was addressed: docblocks now correctly state that the canonical idempotency contract is the natural tuple `(voucher_id, receipt_id, event=Redeemed)` enforced by `VoucherRedemptionService.php:139-147`, NOT the client-supplied `id` (which is just a correlation key in the response payload). Idempotency on sync replay is doubly-guarded: (a) `ReceiptSyncService::syncSingleReceipt` short-circuits to `Duplicate` on idempotency_key match BEFORE entering the transaction, so redeem() never fires twice; (b) even if (a) somehow failed, `VoucherRedemptionService` would throw `VoucherDuplicateInTransactionException` on the second attempt for the same `(voucher_id, receipt_id, Redeemed)` tuple. Test `ReceiptSyncServiceVoucherRedemptionTest::test_offline_sync_idempotent_replay_does_not_double_redeem` covers (a).

Belt-and-braces.

- **Concurrent sync — two terminals redeeming the same voucher simultaneously**: `VoucherRedemptionService.php:86-89` uses `Voucher::query()->where('code', $code)->lockForUpdate()->first()` inside the inner `DB::transaction()` — Postgres SELECT FOR UPDATE serializes the second terminal until the first commits. The first terminal succeeds (status → PartiallyRedeemed, balance decremented); the second terminal finds the new state and either redeems against the remaining balance OR throws `VoucherInsufficientBalanceException` and rolls back. Phase 1's `redeemable_at_terminal_id` constraint also limits a voucher to a single terminal, so the cross-terminal scenario is theoretical, but the locking is correct regardless.

- **Offline → pull**: After sync, the next `runFullSync` cycle calls `pullVouchers` (`syncService.ts:929`) and `pullVoucherLedger` (`:965`). `pullVouchers` calls `upsertVouchers` which overwrites the local voucher's `current_balance` and `status` from the canonical state — the local mirror's tentative decrement gets canonical confirmation (or correction if a server-side adjustment happened). `pullVoucherLedger` calls `upsertVoucherLedgerEntries` which inserts the new server-authored Redeemed row into the local mirror. Both run unconditionally in `runFullSync` so the local terminal's history catches up to canonical. **No stuck-state risk.**

- **Hash invariant under sync** — verified by writing the test mentally: imagine `redeem()` runs BEFORE `finalize()` in `ReceiptSyncService::syncSingleReceipt`. The voucher_ledger Redeemed row would be in the DB before `V3ReceiptHashComputer::compute()` eager-loads `voucherLedgerEntries`. The canonical input would now have one entry → fixture-08-shaped hash → does NOT match the offline hash (which was computed with `voucher_ledger_entries: []`). `OfflineFiscalHashMismatchException` would throw → transaction rolls back → `SyncStatus::Failed`. The test `test_v3_terminal_accepts_offline_voucher_payment_with_instrument_fields_intact:391-397` would fail because the assertion `$expectedHash === $stored->fiscal_hash` would fail. The implementer's claim is correct; the test enforces it.

- **Per-entry response shape** — `VoucherSyncController::pushVoucherLedger` returns `response()->json(['data' => ['results' => $results, 'synced' => N, 'duplicates' => N, 'failed' => N]])`. The client uses `apiPost` which unwraps `response.data.data` (per project memory: "apiGet/apiPost already unwrap response.data.data — return them directly"). So the client receives `{results, synced, duplicates, failed}` directly. The new type guard `isVoucherLedgerPushResponse` checks `Array.isArray(v.results)` — correctly aligned with the controller's actual response shape.

- **`VoucherRedemptionException` mapping** — confirmed at `bootstrap/app.php:215-279`. Each subclass maps to a typed 422 with a stable `error.code`. The wrapping ReceiptSyncService transaction catches the exception via the Throwable handler in `syncBatch:102-112` and converts to `SyncStatus::Failed` with the exception's user-facing message. The HTTP path returns `{status: 'failed', error: '<msg>'}` per-entry. The cashier sees a meaningful error like "Voucher 'SV-2026-7777' has insufficient balance (15.00 EUR requested, 5.00 EUR available)."
