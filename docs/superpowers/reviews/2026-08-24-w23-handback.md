## 2. The decision the brief asked for: CREATE-on-miss (not warn-only)

Ruled **create-on-miss + per-row report**, from the existing brand behaviour and the
scoping rules. Evidence, with file:line:

1. **The sibling block already creates.** `ProductService.php:91-95` resolves `brand` through
   `BrandResolutionService::resolve()`, which ends in `Brand::create([...])`
   (`BrandResolutionService.php:85-92`). The same import created brands and discarded
   categories — an asymmetry with no stated policy behind it.
2. **Categories are COMPANY-scoped only — never vertical-scoped.** The table carries
   `company_id`, `parent_id`, `slug` and a unique `(company_id, slug)`; there is no vertical
   column (`database/migrations/tenant/2025_12_26_194624_create_categories_table.php:14-16,38`).
   `config/verticals.php` declares **no** category scoping — its only `Parapharmacy` block
   (`:331-356`) lists modules and a `requires_batch_tracking` default, nothing about
   `categories`. So a created row cannot land in the wrong vertical: `company_id` fully
   determines its scope.
3. **The vertical-gated "Parapharmacy → Product Category" of N-13 is a DIFFERENT field** and is
   deliberately untouched: it is `ParapharmacyProductMetadata.category`, a
   `ParapharmacyCategory` **enum** (`Product/Application/DTOs/ParapharmacyProductMetadataData.php:42`)
   behind `module:Parapharmacy` (`Product/routes.php:86-89`) — not a `categories` row. Nothing
   this lane does can satisfy it; the report's "the import cannot populate that field" stands,
   and stays with the N-13 lane (see §6).
4. **There is no other way in.** `category_name` is a **products** column
   (`Import/Domain/Enums/ImportType.php:125`) and no `categories` ImportType exists
   (`ImportType.php:9-43`), so a day-one tenant has no route to create categories before the
   products import. `docs/modules/imports.md` calls Categories a Level-1 foundation dependency
   but ships no importer for it — warn-only would leave the operator with a warning and no
   remedy, which is exactly the trap N-2's pre-delivery guard fell into.

**"Never silent" is honoured on both halves.** Auto-creating master data from a free-text
spreadsheet cell is itself a state change worth reporting (a typo'd `Hygène` becomes a real
category), so every create is reported per row and nothing is invisible:
- `_results['category']` = `matched` | `created` | `restored` (`ImportService.php`, importProduct).
- A non-blocking row warning `category_created` / `category_restored` with the offending name,
  which flows into the **`warnings` column of the result workbook**
  (`ResultWorkbookService.php:61,74,112-124`) and into `warning_rows`
  (`ImportController.php:672,681-691`). A **match** stays silent — no new noise on re-imports.

## 5. Correctness details a reviewer should poke at

- **Idempotent.** Re-import matches on exact name, then on slug. Test 2 runs the *same file
  twice* and asserts `Category::count() === 1` and `_results['category'] === 'matched'` on both
  passes.
- **Slug variants cannot collide.** `Hygiene` and `hygiene` both slug to `hygiene`, and the
  unique index is `(company_id, slug)` — matching on slug is what stops the second spelling from
  raising a unique violation instead of linking. Covered by row 2 of test 2.
- **Race + soft-delete.** `Category` uses `SoftDeletes` and the unique index is NOT partial, so a
  trashed row still holds its slug. `Category::create()` is wrapped: on `QueryException` the
  holder is re-fetched `withTrashed()`; a trashed holder is `restore()`d and reported as
  `restored`, a live holder is reported as `matched`, and if there is no holder the exception is
  re-thrown unchanged (never swallowed). This also covers two queue workers racing the same name.
- **Non-latin names.** `Str::slug('...')` returns `''` for pure Arabic/CJK/punctuation names,
  which would make every such category collide on `(company_id, '')`. Falls back to
  `'category-'.substr(hash('sha256',$name),0,16)` — deterministic, so re-imports still match.
- **Blank/whitespace-only values are ignored**, as before (`trim(...) !== ''`).
- **Money/quantity:** none touched. No float anywhere in this lane (rule 19 n/a).
- **Migration: NO.** No schema change, no DDL, no backfill. Nothing to census, no fleet-abort risk.

# FIX ROUND r1 — response to `docs/superpowers/reviews/2026-08-24-w23-import-gate-r1.md`

Gate r1 verdict was **CHANGES-REQUESTED** (3 blocking, 3 minor, 1 misfiling, 1 residual to log).
All 8 addressed. Commit `860f86ce8`, on top of `f49796107` (`git merge dev`).

The gate's core criticism was fair and the diagnosis was exact: the lane shipped its **own**
sqlite-masks-PostgreSQL defect while the handback claimed the path was "race + soft-delete safe".
It was not — on PG it was unreachable code. The fix uses the shape the gate proved (PROBE-H).

## Finding 1 [CRITICAL] — soft-delete/race recovery dead on PostgreSQL. FIXED

`CategoryResolutionService::resolve()` no longer relies on catching a failed INSERT to discover a
slug holder. Two changes, both from the gate's proven shape:

1. **`onlyTrashed()` pre-check before any insert** — a trashed row keeps its slug (soft deletes,
   non-partial unique index), and `CategoryController.php:269` soft-deletes empty categories, which
   is precisely the day-one flow. This is now settled with a SELECT while the transaction is still
   clean.
2. **The insert runs in a nested `DB::transaction()`** (`create()`), so Laravel emits a SAVEPOINT
   and a genuine concurrent-worker race rolls back to it instead of aborting the row transaction
   the caller owns (`ImportService::importRow`, `ProcessImportJob`). The `catch (QueryException)`
   re-read is kept as the race arm — it now actually works — and still re-throws untouched when no
   holder is found.

**Red-first ON POSTGRESQL**, new test
`test_soft_deleted_category_holding_the_slug_is_restored_and_linked` (the gate's PROBE-A):
```
1) ...::test_soft_deleted_category_holding_the_slug_is_restored_and_linked
Failed asserting that 0 is identical to 1.     (data.successful_rows — the row was REJECTED)
```
Green after the fix, on PG: `import_error` NULL, `_results.category='restored'`,
`category_restored` warning, product linked to the restored id, `Category::count() === 1`.

## Finding 2 [IMPORTANT] — `category_name` unvalidated, >255 chars rejected the row on PG. FIXED

`ImportType::getValidationRules()` Products now carries
`'category_name' => ['nullable', 'string', 'max:255']` (`ImportType.php:173-176`), so an over-long
cell is rejected at **validation**, with its row number and a readable message, instead of blowing
up mid-import with a raw SQLSTATE. Also clamped the slug — the gate is right that `Str::slug` can
*lengthen* a name (Arabic transliterates), so `slugFor()` now `mb_substr`s to 255
(`CategoryResolutionService::MAX_LENGTH`).

**Red-first on PG**, `test_over_long_category_name_is_a_row_validation_error_not_a_database_error`:
```
Failed asserting that true is false.    ($rows[1]->is_valid — a 300-char cell passed validation)
```
Green: row 1 invalid with an `errors['category_name']` entry, `import_error` NULL, row 2 imports
normally (`successful_rows 1 / failed_rows 1`), and no product is created for the bad row.

## Finding 3 [IMPORTANT] — silent slug merges. FIXED

New outcome `CategoryResolutionOutcome::MatchedBySlug` (`isStateChange() === true`). `resolve()`
now distinguishes an exact-name hit (`Matched`, silent — no new noise on ordinary re-imports) from
a slug hit under a *different* name, which is a master-data merge decided from a spreadsheet cell
and is reported:

```
category_matched_by_slug: category "Creme" was linked to the existing category "Crème" (same slug);
                          if these are meant to be different categories, rename one and re-import
```

The `CategoryResolutionDTO` gained `categoryName` (the **resolved** row's name) so the warning can
name both sides without a second lookup — this also answers the gate's finding 8 for this path.

**Red-first on PG**, `test_slug_match_on_a_different_name_is_reported_not_silently_merged`, driving
both of the gate's measured collisions (`Crème`/`Creme` and `Soins & Beauté`/`Soins Beauté`):
```

```
Green: 2 categories from 4 rows (the merge is still the intended behaviour), rows 2 and 4 carry
`category_matched_by_slug`, rows 1 and 3 `created`, exact-name hits stay silent.

The pre-existing `test_re_importing_the_same_categories...` was updated accordingly: its
`hygiene`/`Hygiene` row is now a reported merge, so `warning_rows` is 1, not 0. Both passes still
assert one category, no duplicates, and silence on the exact-name row.
