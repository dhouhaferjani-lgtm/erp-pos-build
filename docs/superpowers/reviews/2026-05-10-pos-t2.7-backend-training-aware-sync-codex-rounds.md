## Round 1 — 3 findings

### P1 — Avoid writing zero chain sequences for training receipts

`apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:387-388`

> When `is_training` is true this writes `chain_sequence = 0`, but the existing PostgreSQL constraint is `chain_sequence IS NULL OR chain_sequence > 0`, so the first offline training receipt will be rejected in production. On databases that do not enforce that check, the existing unique key on `(terminal_id, receipt_year, chain_sequence)` will still reject the second training receipt for the same terminal/year. The training sentinel needs to be compatible with those constraints, or the constraints/indexes need to be adjusted.

**Fix:** changed `chain_sequence = 0` to `null` for training receipts. NULL satisfies the CHECK constraint AND is treated as not-equal in PG unique constraints (multiple training rows coexist). Migration reference: `2026_05_01_000001_prepare_pos_receipts_for_pending_seal.php`.

**Side note (out of scope, tracked in PR body):** the online `ReceiptCreationService.php:540` still writes `chain_sequence = 0` and has the same constraint conflict. Needs a separate fix.

### P2 — Don't let failed training receipts poison production sync

`apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:179-185`

> Once this branch makes training receipts independent of the fiscal chain, a failed training receipt is still treated as chain-breaking by `syncBatch` because any `SyncStatus::Failed` sets the batch-level `$chainBroken` flag. In a mixed batch where a training receipt fails for a non-chain reason while the next production receipt still has a valid `previous_hash`, the service will incorrectly return `chain_broken` for the production receipt instead of syncing it. Only failures from receipts that participate in the production chain should poison subsequent receipts.

**Fix:** gated both the syncStatus-failed branch and the `\Throwable` catch branch on `! $payload->isTraining`. A failed training receipt no longer sets `$chainBroken=true`.

### P2 — Parse all validated truthy boolean values

`apps/api/app/Modules/POS/Application/DTOs/SyncReceiptPayload.php:175-178`

> The request rule uses Laravel's `boolean` validator, which accepts values such as JSON `1` and string `'1'`, but this DTO only treats the literal boolean `true` as training. A payload that passes validation with `is_training: 1` will be synced as a production receipt, re-enabling chain validation/finalization and voucher redemption for an allowed training input. Cast this field using the same semantics as the validator.

**Fix:** changed `=== true` check to `filter_var($data['is_training'] ?? false, FILTER_VALIDATE_BOOL, FILTER_NULL_ON_FAILURE) ?? false`. Mirrors Laravel's coercion semantics (accepts `true`, `1`, `'1'`, `'true'`; rejects `false`, `0`, `'0'`, `'false'`).

## Round 2 — 2 findings

### P1 — Exclude synced training receipts from NF525 chain verification

`apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:436-439`

> When this path persists an offline training receipt with `is_training=true`, `chain_sequence=null`, and the training sentinel hash, `/api/v1/compliance/nf525/verify-chains` will report the terminal receipt chain as broken because `Nf525DataProvider::verifyReceiptChain()` currently loads every receipt for the terminal without filtering training rows, then tries to rehash the sentinel as a production receipt. Any terminal that syncs one training receipt will therefore fail compliance chain verification until that verifier is updated to exclude `is_training` receipts.

**Fix:** added `where('is_training', false)` clause in `Nf525DataProvider::verifyReceiptChain` at line 270. Mirrors the filter already applied at `VerifyPosChainCommand.php:166` and `ReceiptHashService::verifyTerminalChain`. Z-report verifier needs no change (Z-reports already exclude training receipts at the aggregation layer).

### P2 — Don't let production failures skip later training receipts

`apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:104-105`

> In a mixed offline batch where a production receipt fails before a training receipt, this sets the global `$chainBroken` flag, and the next loop iteration returns `chain_broken` before checking whether that next payload is training. Since training receipts are explicitly independent of the fiscal chain, a valid training receipt after a production failure should still be attempted instead of being skipped.

**Fix:** added `! $payload->isTraining` to the loop short-circuit at the top of the syncBatch foreach. Combined with round-1's gate on the SET, the chain-broken propagation is now fully scoped to production-only receipts in both directions:

- production-fail → next production: `chain_broken` ✓ (correct)
- production-fail → next training: attempted ✓ (this round-2 fix)
- training-fail → next production: attempted ✓ (round-1 fix)
- training-fail → next training: attempted ✓ (both gates)
