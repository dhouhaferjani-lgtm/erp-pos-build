# Benchmark note — GL treatment of transfer receipt discrepancies and return-to-source (2026-09-09)

Owner question (OQ-1 ruling, 2026-09-09): "probably no GL entry on return-to-source; research industry standards first." Convention 10 benchmark for spec `docs/superpowers/specs/2026-09-08-transfer-destination-receipt-and-blind-receiving-design.md` §6.

| Case | Odoo (valuation cheat sheet, 17–19) | ERPNext (perpetual inventory) | Dolibarr | Domain norm | Recommended for AutoERP |
|---|---|---|---|---|---|
| Goods received as sent | Internal transfer, transit location: **no journal entry**, valuation layer untouched | Material Transfer between warehouses: stock-in-hand moves between warehouse accounts, **no P&L** | Stock moved, no accounting posting by default | Inventory stays an asset; location is an attribute | As today: `TransferIn`/`TransferOut`, no GL (matches `capitalizeTransferCost` freight-only behaviour) |
| Remainder physically **returned to source** (`return_to_source` disposition) | Return = another internal move (transit → source), **no journal entry** | Receive back into the source warehouse: asset moves back, **no P&L** | Same | No value is created or destroyed | **No GL.** Stock movement pair only (transit remainder → source), reusing the cancel restock loop |
| **Short** (missing in transit, written off) | Move to an *Inventory loss* location → journal entry **Dr inventory loss (expense) / Cr stock valuation** (Odoo 19: single "Loss Account" on the adjustment location) | Difference posted to the **Stock Adjustment** expense account (default difference account on stock entries/reconciliation) | Stock correction; accounting via manual entry | Shrinkage is an **expense** in the period it is discovered | GL entry via the existing stock↔GL bridge with `MovementReason::WriteOff` (`requiresGLEntry()` true) at destination or transit, per country chart (seeded, never hard-coded) |
| **Damaged** on receipt | Scrap → inventory loss/scrap account, same mechanism | Stock Adjustment / scrap expense | Same | Expense | `MovementReason::Damage`, same bridge |
| **Over-receipt** | Editable Done > Demand creates extra valued stock (gain) unless refused | Not blocked by default (allowance %) | Qty frozen after draft | Rare; policy usually refuses | **Refused** (owner Q2) → no GL case |

Conclusion: the owner's instinct holds. `return_to_source` is a pure stock movement with **no GL**; only shrinkage and damage hit the ledger, and they already do in the spec through the existing `MovementReason` → GL bridge. No new GL surface is introduced by T-2.

Pattern detection (owner 2026-09-09): regardless of GL, every receipt and close is a **stored** event carrying receiver identity and per-line sent/received/damaged/reason/blind facts, so an analytics query can flag an employee who mis-receives abnormally often. Spec §4 must carry those facts on `StockTransferReceivedV1` (or a companion per-line event), not defer them to `StockMovementRecordedV2`, which has no receiver or variance semantics.
