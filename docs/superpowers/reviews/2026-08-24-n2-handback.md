## 2. The policy decision — absent row == existing row at quantity 0 == REFUSE

The brief required the absent-row answer to be whatever the lane ALREADY does for an
existing row at quantity 0, not a new invention. What it already does, on the pre-fix
tree (`e70dcaad4`), on both lanes:

**Reservation lane** — `StockReservationService.php:120-126` @ `e70dcaad4`:

```php
$available = bcsub((string) $stockLevel->quantity, (string) $stockLevel->reserved, 4);
if (bccomp($available, $quantity, 4) < 0) {
    throw new \RuntimeException("Insufficient stock. Available: {$available}, Requested: {$quantity}");
}
```

A row at `quantity = 0, reserved = 0` yields `$available = '0.0000'`, so any positive
request fails `bccomp` and is REFUSED. It does not auto-create, does not clamp, does not
partially reserve.

**WAC sale lane** — `WeightedAverageCostService.php:418-422` @ `e70dcaad4`:

```php
if (bccomp($newQty, '0', 4) < 0) {
    throw new \DomainException("Insufficient stock for product {$product->id}. Available: {$currentQty}, Requested: {$quantityStr}");
}
```

Same answer: a row at 0 makes `$newQty` negative for any positive issue, and the sale is
REFUSED.

**Decision: an absent row is read as available `0.0000` and refused by exactly that
predicate — a typed 422 `INSUFFICIENT_STOCK`, not a 404, and not a created row.**

Rationale, three parts:

1. **Not a missing resource.** The product exists and the location exists; the *tuple*
   holds nothing. A 404 on `POST …/confirm` tells the operator the document is gone,
   which is false, and on the campaign run it arrived as a raw Laravel debug stack.
2. **Not `firstOrCreate`** (the shape `StockAdjustmentService` uses and the brief offered
   as an option). A refused write must not leave a side effect: `firstOrCreate` would
   write a phantom `stock_levels` row at 0 that the very next line refuses anyway, so the
   only observable difference is litter. The brief's tie-breaker is "match the existing
   zero-row policy exactly" — the existing zero-row policy refuses without writing.
   The parity is pinned by a test (§5, test 2).
3. **`extends \RuntimeException`, not `\DomainException`.** The reservation refusal is
   already a `\RuntimeException` and that is a *pinned* contract:
   `tests/Feature/Marketplace/StockReservationTest.php:327-328` asserts
   `expectException(\RuntimeException::class)` + message substring `'Insufficient stock'`
   on the marketplace cart path, which calls the same `reserve()`. Subclassing keeps that
   lane byte-identical. Riding on `\DomainException` was rejected because both
   `SalesOrderController::confirm` and `DeliveryNoteController::confirm` map EVERY
   `\DomainException` to `INVALID_STATUS_TRANSITION`, and a stock shortfall is not a
   status-transition error.

Side-finding while pinning the parity: on the pre-fix tree the **existing row at 0**
did not give a clean 422 either — `SalesOrderController::confirm` has no
`\RuntimeException` arm, so the bare `\RuntimeException` escaped as a **500** (red-proof
test 2 below). The absent-row case and the zero-row case are now the same honest 422.

## M-2 — a "no phantom row" pin that actually discriminates

The DB-level assertion cannot be made to discriminate in this infrastructure, and that is not a
test-harness limitation: in production the controller wraps the call in `DB::transaction` too,
so a `firstOrCreate`d row would be rolled back by the refusal there as well. `first()` vs
`firstOrCreate` is a **design** invariant with no observable DB difference on the refusal path.
It is therefore pinned structurally, the same way
`InventoryCostLockCoverageTest::test_lock_free_methods_operate_only_on_existing_rows` pins
`recordSale`'s `firstOrFail`:

`MissingStockLevelConfirmRefusalTest.php:307` asserts the service source contains no
`->firstOrCreate(` call, and that
`resolveDefaultBatchIdForImplicitReservation`'s body contains no `->firstOrFail(` call. Both
match **call syntax**, so the file's own prose explaining why `firstOrCreate` is not used cannot
satisfy them (that mistake was caught: the first draft matched the bare identifier and went red
on its own comment).

Verified red under both mutations, exactly the ones the reviewer used:
- `->first()` replaced by `->firstOrCreate([...])` in `reserve()` => `Tests: 1, Failures: 1`.
- `resolveDefaultBatchIdForImplicitReservation` reverted to `firstOrFail()` => the same test red.
