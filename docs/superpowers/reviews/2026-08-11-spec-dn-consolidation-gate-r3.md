# DN-consolidation spec - adversarial gate round 3

## 1. Gate verdict: FAIL

The r3 revision closes residual **4+8**, and most mechanics for residuals **1**, **2**, and **9** are well grounded. It does not pass: `finalise()` does not require or test an exact-`N` update of the payload projection; the SO auto-created-DN analysis omits durable `quantity_delivered` mutations; and the supposedly rollover-safe barrier can seed and lock the wrong year. The r2 history is now honest. No duplicated section, conflict marker, or dangling r3 reference was found, but new factual and stale-prose defects remain.

## 3. New defects introduced or exposed by r3

| ID | Severity | Finding and evidence |
|---|---|---|
| **ND-1** | Material factual error | r3 says `Document::create(['id' => ...])` honors the ID. It does not. `Document` uses `HasUuids` (`apps/api/app/Modules/Document/Domain/Document.php:106-112`), but `$fillable` excludes `id` (`:122-166`). Laravel filters create attributes through fillable keys (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Eloquent/Concerns/GuardsAttributes.php:248-260`; `Model.php:608-645`) and then generates an ID when empty (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Eloquent/Concerns/HasUniqueIds.php:24-35`). The cited calls create `DocumentLine`, not `Document`, and `DocumentLine::$fillable` also excludes `id` (`DocumentLine.php:67-115`). Correct `SPEC:257,813`: preallocation needs explicit assignment/force-fill or a model-contract change. This does not invalidate NULL reservation. |
| **ND-2** | Blocking protocol gap | Marker finalisation is count-guarded; payload finalisation is not (`SPEC:265,366,651`). Both must affect exactly `N`, and every payload invoice ID must match its marker. |
| **ND-3** | Blocking residual / incomplete disclosure | OI-14 and its test omit source order-line `quantity_delivered` writes (`DeliveryNoteFromDocumentFactory.php:172-174` versus `SPEC:282-290,652,784`). Record that they stop surviving failure, assert rollback restores them, and acknowledge their update locks when re-deriving the promised complete inventory. |
| **ND-4** | Factual overstatement | r3 says numbering is the only nested `DB::transaction` and calls nested success a "SAVEPOINT release." The SO lane can call `GeneralLedgerService::clearCustomerAdvanceToReceivable()` (`SalesOrderToInvoiceConverter.php:193,398-410`), which opens another nested transaction at `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:1660-1705`. Laravel creates a savepoint on begin but nested `commit()` only decrements the level and does not issue `RELEASE SAVEPOINT` (`ManagesTransactions.php:148-174,203-219`). The atomicity conclusion remains sound - none issues `PDO::commit()` below the outer level - but `SPEC:270,706,813` must say this accurately. |
| **ND-5** | Internal contradiction | `SPEC:66` calls all four `DocumentData` additions "payload-derived," conflicting with `:72,75,83-88`, which correctly says the number is joined. Say "four billing projection fields" (three payload-backed plus one joined). The canonical DTO table itself is consistent. |
| **ND-6** | Determinism defect | The same `date('Y')` expression evaluated at different times is not rollover-safe (`SPEC:686,700`; `DocumentNumberingService.php:45`). Fix as described under residual 9. |
