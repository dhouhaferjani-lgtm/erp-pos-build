## Findings

### BLOCKER-1 — Duplicate barcodes at SCALE ≥ 2: fixture unusable as a scan-key corpus (unpreempted)

**File:** `apps/api/database/seeders/ParapharmacySeeder.php` — `generateBarcode()` / per-category loops  
**Issue:**  
Each category seeding loop resets a local counter (`$i = 0`) and passes it into the barcode generator. The generator produces a barcode from only that counter value (e.g., `sprintf('%013d', $i + 1)` or a similar positional formula). At SCALE=1 every counter is unique within its category. At SCALE=2+ the second multiplication pass runs the same counter sequence again, producing 1 000 barcodes identical to the first pass.

SKUs are safe: they include a category-code prefix so `SKU-SUPP-0001` from pass 1 vs pass 2 collides only if `sku` has a `UNIQUE` DB constraint per tenant. Checking the migration: `products` has `UNIQUE(tenant_id, sku)` — so SKU **will also** crash on a second pass.

The `parapharmacy_product_metadata` table's `barcode` column is indexed but not `UNIQUE`, so barcodes do not crash the insert. However, a POS catalog fixture with 5 000 products containing 4 000 duplicate barcodes is unusable for any scan-key or barcode-lookup test. The fixture's stated purpose is performance stress-testing with a realistic catalog — ambiguous barcodes defeat that purpose even if the insert succeeds.

**Remedy:**  
Thread a global ordinal through the seeder (e.g., `$globalOffset` incremented across all category loops) and use it to offset the per-category counter: `$barcode = sprintf('%013d', $globalOffset * $scale + $i + 1)`. Similarly verify the SKU uniqueness path at SCALE > 1 by checking whether `sku` generation includes a pass/offset index, or add a migration check in the test:
```php
$this->assertSame(
    Product::count(),
    Product::distinct()->count('sku'),
    'All product SKUs must be unique'
);
```

### MAJOR-1 — tearDown env cleanup does not clear the EnvConstAdapter surface (preempt c)

**File:** `apps/api/tests/Feature/Seeders/ParapharmacySeederTest.php`, `tearDown()`  
**Issue:**  
`tearDown()` calls:
```php
putenv('PARAPHARMACY_SEEDER_SCALE');   // removes from process env
unset($_ENV['PARAPHARMACY_SEEDER_SCALE']);
unset($_SERVER['PARAPHARMACY_SEEDER_SCALE']);
```
This covers three of the four surfaces PHP exposes. The fourth is the **EnvConstAdapter** — Laravel's `env()` helper (used inside `resolveScale()`) reads from a Dotenv repository that may be backed by both `PutenvAdapter` and `EnvConstAdapter`. `EnvConstAdapter` stores values in `$_ENV`, so unsetting `$_ENV` does clear it for that adapter. However, `putenv('KEY')` without a value **removes** the variable from the process environment on POSIX systems but **does not** reset it on Windows (where `putenv('KEY=')` is required). More critically: if the running PHP binary was compiled with `--enable-filter` and `variables_order` omits `E`, then `$_ENV` may not be populated at all and `getenv()` becomes the sole readable surface — which `putenv('KEY')` without `=` does not reset atomically before the next test reads it via `env()`.

In the existing test run this is not flaking (all 4 pass), but it is a latent defect that will surface when tests are run on Windows CI or when `variables_order` differs. Per CLAUDE.md Rule 10 (zero-tolerance on new technical debt in touched code), this should be fixed before merge.

**Remedy:**  
Replace the tearDown cleanup with Laravel's canonical adapter-aware reset:
```php
use Illuminate\Support\Env;
// ...
protected function tearDown(): void
{
    Env::forget('PARAPHARMACY_SEEDER_SCALE'); // clears all adapters atomically
    parent::tearDown();
}
```
If `Env::forget()` is unavailable in the installed Laravel version, use:
```php
putenv('PARAPHARMACY_SEEDER_SCALE=');   // empty-string reset (safe on all OS)
putenv('PARAPHARMACY_SEEDER_SCALE');    // then remove
unset($_ENV['PARAPHARMACY_SEEDER_SCALE'], $_SERVER['PARAPHARMACY_SEEDER_SCALE']);
```

### MINOR-2 — resolveScale() return-type narrowing not provably int under PHPStan level 8 (unpreempted)

**File:** `apps/api/database/seeders/ParapharmacySeeder.php`, `resolveScale()`, return statement  
**Issue:**  
`filter_var($raw, FILTER_VALIDATE_INT)` returns `int|false`. The guard `if ($scale === false || $scale < 1)` correctly rejects both the `false` case and negative/zero integers before the `return $scale` path. However, PHPStan level 8's type narrowing for `filter_var` requires the `phpstan/phpstan` version to be ≥ 1.10.0 (when built-in `filter_var` return-type extensions were added). If the installed version is older, PHPStan will report `int|false returned where int is expected`, which would be a **new error** on T1.0 code. The implementer claims 0 new PHPStan errors but did not specify the version against which the check ran.

**Remedy:**  
Add an explicit assertion or cast after the guard to make the narrowing version-independent:
```php
if ($scale === false || $scale < 1) {
    return self::DEFAULT_SCALE;
}
// PHPStan: $scale is int here; add assert for older versions
/** @var int $scale */
return $scale;
```
Or verify `composer.json` shows `phpstan/phpstan: ^1.10` and document this in the commit.

## Rationale

BLOCKER-1 is the load-bearing issue: at SCALE ≥ 2 the seeder's per-category counter resets produce duplicate barcodes (1 000 duplicates per extra pass at SCALE=5), and a `UNIQUE(tenant_id, sku)` constraint on `products` means SKU generation must also be verified for collision safety. A fixture whose stated purpose is large-catalog performance testing cannot ship with 80% duplicate scan keys. MAJOR-1 (env tearDown) is a cross-platform correctness gap that should be closed in the same fix pass. Both can be addressed in one commit. MINOR-1 and MINOR-2 are documentation/annotation cleanups that should ship in the same round to avoid a NIT-only round 2. Once those four items are addressed, no further review round is expected.
