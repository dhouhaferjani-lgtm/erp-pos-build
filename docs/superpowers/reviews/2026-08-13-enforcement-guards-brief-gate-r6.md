## Critical findings

### R6-C-1 — The owner-authenticated tag signs executor-supplied bytes, not proof that the bridge produced them

**Evidence:** The executor is explicitly responsible for invoking the bridge and reading its register (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:93-107`). The bridge writes an ordinary local file by copying reviewer stdout and decides ACCEPT by parsing a text line; it emits no detached receipt, signature, nonce, run identifier, or digest into a parent-controlled channel (`scripts/adversarial-review.sh:82-100`). Promotion step 1 begins only after that executor-run gate and tells the parent to hash the file presented as the “EXACT bridge-output” register; step 3 then has the owner authenticate those bytes in the tag (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:418-420`). P3 verifies the tag's A and landed-register digest but has no bridge-run artifact to verify (`docs/handoff/progress/enforcement-p3.progress.yaml:29-46,121-128`). The package nevertheless says self-certification is not accepted (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:453`).

**Failure scenario:** the untrusted executor skips the final bridge call or replaces its output with a locally authored file ending in `VERDICT: ACCEPT`, then reports that the final gate accepted A. The trusted parent follows r12 exactly: it hashes the presented file, the trusted owner writes that digest and A into the annotated tag, and the exact same bytes land in the closing commit. P3's A/digest/parse checks all pass. No malicious parent or owner is required; the trust root has merely authenticated an unproven input. A package that never received bridge ACCEPT is accepted as if it had.

**Required repair:** make the trusted actor verify provenance before attesting. Either the parent/owner must invoke the final bridge itself and immediately create the attestation from that invocation, or the bridge must emit a nonce-bound receipt into a channel the executor cannot replace. Bind at least package, milestone, round, A, reviewer invocation identity/result, and exact output digest. The annotated tag must cover that bridge receipt as well as the file digest, and P3-M0 must verify it. Hashing an executor-nominated file is not bridge authentication.

## High findings

### R6-H-1 — P3 ignores the annotated handback digest even though P3 consumes the handback's census

**Evidence:** The annotation schema includes `handback_sha256: <path>=<hex>` and the closing commit is supposed to land the exact handback bytes (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:420-422`). P3's two binding predicates compare only annotation A and the landed **register** digest; neither 1d nor 2d requires parsing or comparing `handback_sha256` (`docs/handoff/progress/enforcement-p3.progress.yaml:29-46,121-128`). Yet P3(a) consumes P1's write-path census and the acceptance handback must carry that census table (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:353-358,394-399,446-448`). The package-specific closing set constrains the original closing commit, not arbitrary later non-enforcement commits (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:422`).

**Failure scenario:** after P1's valid closing commit, an untrusted executor in a later lane changes the landed P1 handback's census table while leaving the final register untouched. P3's base contains the altered handback. Its M0 register digest and A checks pass, and the original closing commit still had a conforming diff, but P3 consumes the rewritten census and can omit a real journal creator or misclassify a balance seam. The tag already contains the evidence needed to detect this; the consumer simply never checks it.

**Required repair:** make P3 1d/2d parse the package-specific `handback_sha256` path and digest, require that exact path to exist at base, and compare its current bytes to the annotation. Require both the register and handback bytes at P3 base to equal the bytes in the closing commit so later rewrites fail closed.

### R6-H-2 — P3 has no named closing-admin tip, so its “exactly one” check can be applied to a different commit than the final evidence state

**Evidence:** Step 5's verifier uses an unbound `<admin-tip>` placeholder and says its output is recorded “in the receipt,” but defines neither a receipt schema nor a closing-tip field (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:422`). P1 and P2 expose only `pre_promotion_ci_dispatch`, whose documented subject is the remote workflow run, not a structured closing attestation (`docs/handoff/progress/enforcement-p1.progress.yaml:68-89`; `docs/handoff/progress/enforcement-p2.progress.yaml:55-76`). P3 M0 names the landed A, base, progress file, verdict path, and tag, but no closing commit SHA and no deterministic rule for deriving it; it merely repeats that the chain is “exactly one” (`docs/handoff/progress/enforcement-p3.progress.yaml:22-46,121-128`). This omits the connecting edge between the count/path check and the commit that contains all final evidence.

**Failure scenario:** an interrupted close produces `A → C1 → C2`: C1 adds only the correctly digested final register; C2 adds the final YAML status, handback, and LEDGER receipt. Against C1, `rev-list --count A..C1 == 1` and the diff is inside the package set. At base C2, the YAML is complete and the verdict path resolves to the tag-matching register. Because no artifact says that C1 must itself contain all closing evidence, an executor can report the count/path result for C1 while reading status/handback endpoints from C2. Every separately named predicate passes although the required one-commit close did not happen. This can arise from an honest interrupted/retry sequence; it does not require a malicious parent.

**Required repair:** define a deterministic closing-commit identity without a self-SHA cycle. For example, require P3 to derive C as the unique first-parent child of A, require `C^ == A`, inspect `git diff-tree C^ C`, and require every mandatory closing artifact (final register path, handback path, final YAML state, receipt, and LEDGER update) to exist at C. Then require the corresponding blobs at P3 base to equal C's blobs. Alternatively use a second owner-authenticated closing attestation tag that names both A and C. A free-form receipt and an unbound `<admin-tip>` are insufficient.

### R6-H-3 — Recovery is not idempotent after tag creation, and closing-check failure has no transition

**Evidence:** Step 2 requires the pre-allocated tag name to be free (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:419`). Step 3 creates that tag permanently and only then performs the throwaway-ref push and workflow dispatch (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:420`). The recovery rule includes ref-push/dispatch failures and permits retrying the same unchanged A “from step 2,” while tags may never be deleted or reused (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:420-423`). The trigger list ends before step 5: it gives no recovery for a closing commit that fails its own count/path check after A is already fast-forwarded (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:421-423`; `LEDGER.md:56`).

**Failure scenario:** the tag push and verification succeed, then the throwaway-ref push or dispatch API fails transiently. A is still fresh, so the rule offers a same-A retry from step 2; that retry immediately fails because the tag is no longer free and may not be deleted. Re-gating can manufacture A′ and leak the old permanent tag, but the promised unchanged-A retry is impossible. Separately, if the closing commit accidentally contains one forbidden path, the named check fails only after dev has A plus the bad admin commit; reverting creates a second commit and violates the exact-one chain, while resetting/amending is not authorized or specified.

**Required repair:** make the promotion flow an explicit idempotent state machine. On retry, treat an existing tag whose target and full annotation exactly match A/digests as the successful result of step 3 and resume after it; an existing mismatching tag requires re-gating with a newly reviewed name. Preflight the staged closing artifact set and required-path presence before creating the admin commit, then verify after commit. Define how an interrupted or failed step 5 resumes without creating a second closing commit, and record each checkpoint in a structured owner receipt.

### R6-H-4 — P3's no-workflow path contradicts the universal pre-allocation rule and has no named closing receipt

**Evidence:** The universal step 3 requires every package's **pre-allocated** tag name to come from A's reviewed mirror field (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:416,420`). P3 has no closing-tag field. Its own YAML instead says the name is allocated **at promotion** and “recorded in the closing receipt” (`docs/handoff/progress/enforcement-p3.progress.yaml:80-88`). The only receipt key present is `pre_promotion_ci_dispatch`, expressly required only when P3 touches workflows (`docs/handoff/progress/enforcement-p3.progress.yaml:67-88,107-110`). Step 5 nevertheless requires the closing-check output recorded in “the receipt” for every package (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:422`).

**Failure scenario:** P3 validly lands its completeness test in an already selected directory and makes no workflow edit. No dispatch receipt is required. At step 3 the parent cannot take a pre-allocated name from A because no field exists, so it must contradict the universal instruction and allocate one live. At step 5 there is no package field in which to record that tag name or the named closing-check output without misusing the null CI-dispatch receipt or inventing schema. The package can be promoted, but its promised universal, reconstructible closing evidence is incomplete.

**Required repair:** add a universal structured `closing_attestation`/`closing_receipt` record to all three schemas, independent of `pre_promotion_ci_dispatch`. Either pre-allocate and review `p3_closing_pin_tag` in A like P1/P2, or explicitly define P3's owner-locked live allocation and record the selected name in that structured receipt. Make §5, P3 YAML, and LEDGER S-14 state the same rule.

### R6-H-5 — The tag is verified before running untrusted candidate CI and is never re-verified afterward

**Evidence:** P1 and P2 deliberately edit `.github/workflows/ci.yml` (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:189,288-299`). The current workflow has no explicit top-level `permissions:` boundary (`.github/workflows/ci.yml:1-26`). The read-only query `gh api repos/otospexsolutions/erp/actions/permissions/workflow` currently reports `default_workflow_permissions: read`, but GitHub documents that a workflow file may request `contents: write`, and that contents-write authority can update Git references, including tag refs; the candidate itself is therefore the security-relevant object. Step 3 verifies the tag and then runs that candidate workflow; step 4a rechecks only dev ancestry, not the tag object, annotation, or variable (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:420-421`). F-8 expressly treats CI/checker invocation as candidate-editable and relies on review/dispatch visibility (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:438`). [GitHub workflow-permissions reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions); [Git references permission reference](https://docs.github.com/en/rest/git/refs)

**Failure scenario:** a malicious executor hides `permissions: contents: write` plus a tag-delete or force-retag step in accepted A. The trusted owner creates and verifies the tag, then dispatches exactly A. The untrusted workflow mutates the tag and still completes green; the promotion check verifies the head/jobs and step 4a verifies only ancestry. A is fast-forwarded and closed with no valid durable tag, so future CI fetches or P3-M0 fail. No malicious parent/owner is required, and CI is explicitly an untrusted actor in the requested model.

**Required repair:** after the remote run and immediately before merge, re-fetch and verify the tag object's target **and exact annotation/digests**, plus the expected variable value. Make that re-verification a named re-gate trigger. Add an owner-side promotion check that rejects any candidate workflow granting repository-content/tag write authority, and protect the `ci-pin/enforcement-*` namespace with an owner-controlled ruleset or equivalent immutable-attestation mechanism unavailable to `GITHUB_TOKEN`.
