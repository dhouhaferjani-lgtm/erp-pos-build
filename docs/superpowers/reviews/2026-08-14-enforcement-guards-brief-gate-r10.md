## Critical findings

### R10-C-1 — The “parent-held dispatch record” is not a named artifact, so the candidate can still choose a truncated base and alternate manifest

**Evidence:** The bridge's trust comments and arguments require an independently supplied base and expected manifest digest (`scripts/adversarial-review-final.sh:5-12,27-45`), and §5 repeats that both come from “the parent's dispatch record” (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:451`). No path, schema, owner receipt, or creation/read-back step for that record exists. F-9 instead tells the parent to fill `control_manifest` in each package progress YAML (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:471`); those candidate-carried fields are the only shipped base/manifest pins (`enforcement-p1.progress.yaml:33,117-121`; `enforcement-p2.progress.yaml:14,104-108`; `enforcement-p3.progress.yaml:74,126-130`). The authenticated manifest itself contains package lenses/milestones/progress paths but no package base or parent-record identity (`enforcement-control-manifest.yaml:34-49`). The bridge consumes the caller's `--base`, `--manifest`, and `--expected-manifest-sha256`; it does not load an owner record (`adversarial-review-final.sh:27-52`).

**Failure scenario:** P1 has several commits. The untrusted executor changes its YAML `base_sha` from the true dispatch base D to a later package commit B immediately before A, and adds `docs/handoff/enforcement-control-manifest-p1.yaml` with the same valid bridge/brief/harness hashes but a reduced P1 lens list. P1's own final scope allows `docs/handoff/**` (`enforcement-p1.progress.yaml:175-180`), while the control preflight rejects changes to the canonical manifest path, not an alternate path (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:451`). An honest parent has no named record other than the on-disk pins, so it supplies B and the alternate manifest/hash. B is a strict ancestor of A, `B != A`, the alternate manifest authenticates against its candidate-selected expected hash, and final review omits D..B plus the removed lens. No malicious parent/owner is required; the trusted actor followed the only recorded inputs the package ships.

**Required repair:** create a concrete parent/owner-owned dispatch receipt outside candidate control, with a named durable location and exact schema containing package id, true base SHA, canonical manifest absolute path, expected manifest SHA-256, progress path, and immutable package controls. Create and read it at dispatch, preserve it through final review, and have the bridge consume or verify that receipt directly. Field-check the candidate's `base_sha` and `control_manifest` against the receipt. Reject every manifest path except the receipt's canonical path and reject any added manifest/control surrogate in `base..A`.

## High findings

### R10-H-1 — The bridge's active YAML fallback skips the promised milestone/status/fix-round checks

**Evidence:** The bridge tries `import yaml`, but on any exception falls back to a regex that extracts only `base_sha` and sets `milestones` to `None`; all milestone, `status: review`, and `fix_rounds` checks are conditional on `milestones is not None` (`scripts/adversarial-review-final.sh:103-122`). On this actual parent host, `python3 -c 'import yaml'` fails with `ModuleNotFoundError`. Exercising that exact block against the current P1 YAML with arguments `base=null`, `milestone=M3`, `max=5` returned `mode=fallback ... milestones=None`, exit 0, even though P1-M3 is currently `status: pending` (`enforcement-p1.progress.yaml:175-184`). The brief and final milestone titles claim the YAML is field-checked (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:97-101,451`; `enforcement-p1.progress.yaml:176`).

**Failure scenario:** after exhausting five substantive fix rounds, an executor leaves the final milestone at `blocked_review` with `fix_rounds: 6` (or simply leaves it `pending`) and hands over A. On this machine the fallback confirms only the base string, skips every state/fix-round predicate, and invokes the trust-producing reviewer. A later ACCEPT can be promoted despite the harness's mandatory stop condition.

**Required repair:** remove the partial fallback. Either ship/verify a YAML parser dependency before any side effect, or implement a complete fail-closed parser for the exact schema. Missing parser support must exit 3. Always require exactly one final milestone, `status == review`, integer `fix_rounds <= max_fix_rounds`, top-level `max_fix_rounds` equal to the manifest projection, and `control_manifest` equal to the owner dispatch receipt.

### R10-H-2 — The operative tag producer omits `manifest_sha256`, so P3 cannot perform the required identity comparison

**Evidence:** The bridge emits `manifest_sha256: <digest>` in the register (`scripts/adversarial-review-final.sh:73-77,177-188`), and the r17 log claims both the register and pin-tag annotation carry it (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:101`). The operative step-3 schema, however, specifies `accepted_sha`, register digests, handback digest, and final `control_sha256` lines only (`:453`); S-14 repeats only `control_sha256` (`LEDGER.md:56`). P3-M0 requires both `control_sha256` and `manifest_sha256` to match the dispatch manifest for P1 and P2 (`enforcement-p3.progress.yaml:29-43,52-58`). The close-tag schema is also only `{closing_commit, closing_check, accepted_sha}` (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:455`), so the missing line cannot be sourced there.

**Failure scenario:** the owner follows the exact step-3 tag schema and creates a valid pin tag without `manifest_sha256`. At P3-M0 the named comparison cannot succeed. If the executor/parent instead silently compares the register line or invents a tag field, the run deviates from the operative package and the expected-sha → authenticated tag → P3 chain is no longer reconstructible from the named artifacts. A stale but internally consistent manifest is therefore not rejected by the promised tag predicate.

**Required repair:** add a mandatory, exactly named `manifest_sha256: <hex>` line to the step-3 pin-tag schema, S-14, all three closing-receipt digest schemas, and step-4a exact-annotation re-verification. State explicitly that P3 parses it from the **pin tag** (not the close tag), compares it to the exact package dispatch receipt and base `control_manifest` value, and separately checks the register's identical line. Define `control_manifest` as a structured `{path, sha256}` value rather than free text.

### R10-H-3 — An exact ACCEPT line followed by a contradictory conclusion still exits 0

**Evidence:** The prompt requires the reviewer to **end** with exactly one exact verdict line (`scripts/adversarial-review-final.sh:141-153`). The parser counts lines beginning `VERDICT:` anywhere in the register and exact-matches that extracted line, but never requires it to be the final non-empty line (`:191-198`). Exercising the shipped parser logic with `VERDICT: ACCEPT\nCorrection: blocker found; changes are required.` produced one verdict and the `exit0_ACCEPT` branch.

**Failure scenario:** ordinary model formatting drift emits an exact `VERDICT: ACCEPT`, then a correction or caveat identifying a blocker. The bridge accepts and the owner authenticates the register even though the reviewer's final conclusion is negative. No malicious parent/owner or actor outside the trust model is needed.

**Required repair:** after requiring exactly one verdict line and exact equality, require it to equal the final non-empty output line and reject any bytes after it except one terminating newline. Add exercised cases for ACCEPT followed by prose, ACCEPT followed by a correction, leading/trailing whitespace, and duplicate/alternate verdict syntaxes.

### R10-H-4 — The neutral-cwd bridge does not require absolute paths for the handback it tells the reviewer to open

**Evidence:** The bridge accepts `--handback` verbatim and checks only that it is non-empty (`scripts/adversarial-review-final.sh:27-45`). It copies and hashes that path while still in the caller's cwd (`:124-132`), then injects the same uncanonicalized value into the prompt as the file the reviewer must open (`:141-149`) and launches Claude from a different neutral cwd (`:164`). The script's own prompt says to use only absolute paths (`:143-147`), but no `realpath`, absolute-path assertion, or exact parent invocation exists. Snapshot paths are absolute because they come from `mktemp` (`:133-136`); the handback path is not.

**Failure scenario:** the parent uses the repository's normal relative-path style and passes `--handback parent-workspace/enforcement-p1.md`. The copy and hash succeed relative to the control checkout. From the neutral cwd the reviewer resolves that string under the empty temp directory and cannot open the required census handback. It can return CHANGES-REQUIRED/tool error, or fabricate the requested first/last-row evidence and return ACCEPT without judging the package's mandatory review target.

**Required repair:** canonicalize and validate `MANIFEST`, `CANDIDATE`, `HANDBACK_SRC`'s candidate-relative source, immutable `HANDBACK`, and `OUT` before constructing the prompt. Inject only absolute existing paths; require the handback destination and output to be outside both checkouts. Alternatively inject the immutable handback contents directly. Ship one exact parent invocation template so the neutral-cwd contract is executable rather than conventional.
