## Consequence assessment of tenancy B-1(r2) / M-2(r2) from the inventory side

I **confirm** the tenancy reviewer's reasoning about the write-off path, and I closed the gap they flagged ("the write-off leg is reasoned from the same code path rather than executed"). Building the aggregate layer their fixture lacked is enough to reach the post-write resolve: `StockAdjustmentService::issue()` refuses when there is no `stock_levels` row, so a `StockLevel` row for the same `(product, location)` is the only missing ingredient.

**Probe** (temporary `tests/Feature/BatchExpiry/ZzInvGateProbeTest.php`, extending the committed `BatchPermissionFixture`, since deleted): lot with `inventory_batch_stock.quantity = 10.0000` at company location `$other` plus a matching `stock_levels.quantity = 10.0000`; actor restricted to `$this->location` (so `$other` is a company location **outside** the read scope); flag ON; two identical `POST /api/v1/batches/{uuid}/write-off {location_id: $other, quantity: '4.0000', reason: 'expiry'}` calls. Observed:

```
BEFORE      = {"batch_stock_qty":10,"stock_level_qty":10,"stock_movements":0,"journal_entries":0,"journal_lines":0}
CALL1 STATUS= 403  BODY={"error":{"code":"FORBIDDEN","message":"You do not have permission to perform this action…"}}
AFTER CALL1 = {"batch_stock_qty":6,"stock_level_qty":6,"stock_movements":1,"journal_entries":0,"journal_lines":0}
CALL2 STATUS= 403
AFTER CALL2 = {"batch_stock_qty":2,"stock_level_qty":2,"stock_movements":2,"journal_entries":0,"journal_lines":0}
```

**The double write-off is not a hypothesis — it is the observed behaviour.** 8 of 10 units left the lot and two `stock_movements` rows were authored while the operator saw nothing but two "forbidden" responses. There is no idempotency key on `WriteOffBatchRequest` (`apps/api/app/Modules/BatchExpiry/Presentation/Requests/WriteOffBatchRequest.php:31-38`), so a retry is a second write-off by construction. Mechanism, from the inventory side:

- `BatchWriteOffService::writeOff()` wraps aggregate decrement (`BatchWriteOffService.php:82` → `StockAdjustmentService::issue`, itself `DB::transaction` at `StockAdjustmentService.php:274`), batch-lot decrement (`:95` `issueBatchStock`) and the GL entry (`:106` `createInventoryWriteOffEntry`) in ONE `DB::transaction` (`:59`) and **commits on return**.
- Only *then* does `BatchController::writeOff()` call `loadScopedResourceRelations()` at `:516`, which calls `resolvedReadLocationIds()` (`:107` → `:56-73`), which re-reads request **input** (`:61-65`) and delegates to `LocationScopeResolver::resolve()` — a method that **throws `AuthorizationException`** (`apps/api/app/Modules/Company/Services/LocationScopeResolver.php:41-43`). Nothing wraps the write and the resolve in a common transaction.
- `location_id` is a **required body field** on this route (`WriteOffBatchRequest.php:35`) validated only for company membership (`ScopedExists::company`), so the throw is not an edge case — it is what *every* location-restricted operator writing off at a location outside `allowed_location_ids` gets.
- `journal_entries` stayed at 0 only because the fixture has no configured GL accounts and the service deliberately swallows that (`BatchWriteOffService.php:122-125` `catch (\RuntimeException)` → `Log::warning`). On a tenant with the inventory/write-off accounts configured, each retry also posts an `InventoryWriteOff` journal entry. **The stock doubling is executed; the GL doubling is reasoned from `:106` on the same committed path.**

Reachability, stated honestly so the orchestrator can weigh urgency: no first-party client calls `POST /batches/{uuid}/write-off` today — the pharmacy screen posts to `/batches/write-off-grouped` (`apps/web/src/features/batches/api/batches.ts:184` → `GroupedWriteOffController`, a different controller that builds no `BatchResource` and is untouched by this lane). So today's exposure is API/integration clients, the mobile app, and any future consumer of the documented per-lot route. `PATCH /batches/{uuid}` reproduces the *403-after-commit* mechanism (tenancy's PG probe) but the web never sends a stray `location_id`, and `POST /batches/{uuid}/transfer` cannot throw at all because its body carries `from_location_id`/`to_location_id`, never `location_id`, so `resolve($user, [])` returns the membership set (`LocationScopeResolver.php:37-38`). That does **not** reduce the severity: the code as written commits a stock movement and a GL entry and then tells the caller it was forbidden, with no rollback and no idempotency guard.

**M-2(r2), also executed.** Second probe, **unrestricted** actor (`allowed_location_ids = null`), flag ON, one lot holding 10 at `$other` and 7 at `$this->location`, `POST …/write-off {location_id: $other, quantity: '1.0000'}`:

```
STATUS= 200
total_quantity= "9.0000"  available_quantity= "9.0000"  batch_stock_count= 1
DB rows for lot: [{location:$this->location, quantity:7, available:7}, {location:$other, quantity:9, available:9}]
```

The lot holds **16.0000**; the 200 response reports **9.0000** and one `batch_stock` row, to an admin with **no location restriction whatsoever**. The mechanism is `BatchController.php:107` passing the whole `$request` into `resolvedReadLocationIds()`, which at `:65` treats the write-off's *target* `location_id` as a *read scope*; for an unrestricted actor `effectiveAllowedIds` returns every company location (`LocationScopeResolver.php:59-61`) so `resolve()` narrows to that one (`:45`) instead of returning `null`. Inventory consequences: the write-off response understates on-hand by 43% in this fixture; §6.3 describes these fields as physical on-hand / on-hand-minus-reserved with no such qualifier; and the understated `available_quantity` is exactly the field a client would use as the next `max`. It also means `total_quantity` no longer agrees with the lot — the very invariant Option B was adopted to establish. I therefore **confirm** M-2(r2) and endorse the orchestrator's ruling (derive the response scope from `LocationContext::getAllowedLocationIds()` only, resolved once **before** the write), which closes both findings with one change.
