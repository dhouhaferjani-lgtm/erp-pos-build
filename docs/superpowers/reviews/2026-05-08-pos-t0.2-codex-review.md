### (1) Race on synchronous double-click — APPROVE

Zustand v5 functional-set semantics confirmed from installed source: callback receives a snapshot, but in single-threaded JS, two synchronous Confirm clicks queue as two tasks on the event loop. The second click's `set()` callback runs after the first has already written `pendingIdempotencyKey`, so the second call reads the already-set key and returns the same key unchanged. The functional-set pattern is genuinely atomic against the double-click race.

### (2) Crash safety — CONCERN (acceptable for Tier 0)

If the app crashes after Confirm but before POST, the in-memory key is lost. A fresh sale after restart gets a new UUID. The pre-T0.2 state was strictly worse (would mint a new key on retry). T0.2 makes no regression here. Acceptable for Tier 0.

### (3) Cart-clear lifecycle gaps — MAJOR

| Callsite | File:Line | Calls clearLastReceipt? |
|---|---|---|
| holdStore recall | `holdStore.ts:137` | No |
| Header void | `Header.tsx:334` | No |
| Header void (variant) | `Header.tsx:342` | No |
| CloseShiftModal | `CloseShiftModal.tsx:35` | No |
| PinEntryPage | `PinEntryPage.tsx:29` | No (but calls reset() at :31, which clears pendingIdempotencyKey via initialState) |

A cashier voids a cart, starts a new sale, clicks Confirm → `processCashCheckout` reads stale `pendingIdempotencyKey` from the prior voided attempt and reuses it. If the voided attempt also reached the server (partial sync before void), the server's dedup rejects the new sale's POST as a duplicate.

**This is a confirmed scope-leak for void-cart and hold-recall paths.** Not merely a lifecycle gap — actively breaks the cross-sale dedup contract.

### F-1 BLOCKER — Local UNIQUE constraint collision on retry

`offline_receipts.idempotency_key` is declared `UNIQUE` in `apps/pos/src/lib/db/migrations.ts`. `insertOfflineReceipt` in `apps/pos/src/lib/db/repositories/offlineReceiptRepository.ts:72-79` is a plain `INSERT` with no `ON CONFLICT IGNORE`.

On retry: `processCashCheckout` reuses the same `pendingIdempotencyKey` (correct), calls `createOfflineReceipt` → `insertOfflineReceipt`, which issues `INSERT ... idempotency_key = '<same-uuid>'`. SQLite UNIQUE constraint fires; `SQLITE_CONSTRAINT_UNIQUE` throws. The error propagates to the catch, which sets `error: 'Failed to create receipt locally'` and aborts. **The retry that T0.2 is supposed to enable instead hard-fails locally.**

**Fix required**: change `insertOfflineReceipt` to `INSERT OR IGNORE`. `createOfflineReceipt` must detect duplicate-key BEFORE doing any work and return the existing receipt's data instead of re-doing hash-chain advance, voucher balance updates, etc.

### (4) Tautology gap — APPROVE

Genuine RED on dev tip for the right reason (different keys, not null equality). Mock always returns a string — no vacuous equality risk.

### (5) Scope leak — MAJOR

Same conclusion as (3). The stale key from a voided cart flows into the next `processCashCheckout` because the functional-set reads `state.pendingIdempotencyKey ?? crypto.randomUUID()` and finds a non-null stale value. No "is this key from the same cart?" guard.

### (6) Test honesty — APPROVE

### (c) — (h) — PASS

### F-3 MAJOR — Regression test mocks away the real INSERT failure

The test mocks `createOfflineReceipt` entirely, hiding the SQLite layer. F-1 (the local UNIQUE collision) cannot be caught by this test suite. An integration-style test against real SQLite (or sql.js / better-sqlite3 via the existing `migration22.integration.test.ts` pattern) would have caught F-1 immediately.

### F-4 MINOR — offlineCheckoutService.ts:143

`createOfflineReceipt` is called there without an `idempotencyKey`, falling back to fresh UUID. Pre-existing, but the new param makes it more visible. Background-sync re-attempt path; minting a fresh key here may cause a server duplicate if the original sync already committed.

## Overall Recommendation (Round 1)

**REQUEST-CHANGES**

F-1 is a hard blocker: the local SQLite UNIQUE constraint will throw on the first retry attempt. The very scenario T0.2 is designed to handle (retry after stall) is broken at the local persistence layer. Fix: add `ON CONFLICT(idempotency_key) DO NOTHING` to `insertOfflineReceipt` and treat 0-rows-affected as "already persisted, safe to proceed to sync."

F-2/F-3 are MAJOR but could be accepted as documented debt for a hotfix if F-1 is resolved. However, the void-cart scope leak can produce cross-sale server dedup collisions in a real cashier session, which is exactly the failure class T0.2 is supposed to prevent. Recommend wiring at minimum in `Header.tsx` (void cart) and `holdStore.ts` (recall hold) before merge.
