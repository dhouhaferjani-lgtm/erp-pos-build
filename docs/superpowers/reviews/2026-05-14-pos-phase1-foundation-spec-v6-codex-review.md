## New findings
### [BLOCKER] POS order close still server-authors `SALE_RECEIPT` through `ReceiptCreationService`, but v6 does not disposition it
**Dimension:** completeness / cross-app / grounding
**Spec location:** §5.0, §14, §14.2, §17.5 (`spec v6:245-249,581-597,619-642,722-727`)
**Evidence:** SoT D8 requires one fiscal pattern with no two-model coexistence (`source-of-truth-v3.md:261`); D1 makes the POS device the fiscal source of truth (`source-of-truth-v3.md:254`); D16 forbids the authoring/sealing/chain/ingestion path from depending on other operational runtimes and requires the engine to publish events (`source-of-truth-v3.md:242-246,269`). The owner strategy says fiscalized POS records are immutable, append-only, and locally resilient (`fiscal_chain_architecture_strategy.md:107-123`). v6 says `SALE_RECEIPT` is authored only via `FiscalEventEngine.append()` on every terminal type, regardless of connectivity, and that any code path posting a new sale to a server-authoring endpoint is discarded (`spec v6:245-249`). But the live POS order-close route still creates a receipt server-side: `POST /api/v1/pos/orders/{id}/close` is documented in `OrderController::close()` (`apps/api/app/Modules/POS/Presentation/Controllers/OrderController.php:348-358`) and routed at `apps/api/app/Modules/POS/routes_orders.php:27-28`; `OrderManagementService::closeOrder()` calls `OrderToReceiptService::convertToReceipt()` (`OrderManagementService.php:419-438`); `OrderToReceiptService` delegates to `ReceiptCreationService::createReceipt()`, whose doc says it handles stock decrement, hash chain, and fiscal compliance (`OrderToReceiptService.php:11-16,68-74`). v6 never mentions `OrderController`, `routes_orders.php`, `OrderManagementService`, or `OrderToReceiptService`.
**Issue:** v6 resolves the exact v5 blocker for `/pos/receipts` and Tauri `onlineCheckout`, but its new-sale server-authoring disposition is still incomplete. A cashier can close a POS order and produce a server-authored receipt through `ReceiptCreationService` without going through the device `FiscalEventEngine.append()` or the single fiscal-event endpoint.
**Impact:** Phase 1 can still ship with two `SALE_RECEIPT` authoring models: rebuilt device-authored sales through `fiscal_events`, and server-authored order-close receipts through `OrderToReceiptService`. That preserves the two-model coexistence D8 forbids and leaves part of the old server recompute receipt chain alive outside the cleanup checklist.
**Suggested fix:** Add a §14 disposition row for the POS order-close path: `routes_orders.php`, `OrderController::close`, `OrderManagementService::closeOrder`, and `OrderToReceiptService::convertToReceipt`. Either disable/hide order close in Phase 1 with the same rationale as web POS new-sale authoring, or rework it so closing an order creates a business document that is sealed by `FiscalEventEngine.append()` on a device and synced through `/api/v1/pos/sync/fiscal-events`. Add §17.5 tests asserting `POST /pos/orders/{id}/close` no longer server-authors a `SALE_RECEIPT` via `ReceiptCreationService` after the rebuild.
