## New Findings

### Finding #7 — MINOR: Smoke test coverage gaps for 5 of 8 protected keys

**File:** `apps/pos/src/__tests__/recoveryScreenI18n.test.tsx`

The smoke test's stated purpose is to catch "raw key leaks" for 8 keys. However, the test assertions only exercise the keys that are **visible in the default render state**. Five of the eight keys are rendered only in conditional branches that the test does not enter:

**Test 1 — CompanyRecoveryScreen:**
- `auth.companyRecovery.title` — covered via `toContain('No companies available')` (line ~133 of test)
- `auth.companyRecovery.signOut` — covered via `toContain('Sign out')` (line ~134 of test)
- `auth.companyRecovery.message` — covered by the absence regex IF the element renders (it does render in default state)
- `auth.companyRecovery.errorHint` — **NOT covered**: only rendered when `hasError=true`; test state has no error set
- `auth.companyRecovery.retrying` — **NOT covered**: only rendered when recovery loading state is active
- `auth.companyRecovery.retry` — **NOT covered**: only rendered when not retrying but error is present

**Test 2 — LoginPage:**
- `auth.signIn` — covered via `toContain('Sign in')` (line ~164 of test)
- `auth.stillTrying` — **NOT covered**: only rendered after 8 s of `isLoading=true`; test has `isLoading: false`
- `auth.cancel` — **NOT covered**: same condition as `stillTrying`

**Consequence:** Deleting any of the five uncovered keys from the locale files would **not** fail this smoke test. The test header comment states it covers "still-trying / cancel keys" — this is misleading for the `isLoading=false` render path.

**Severity: MINOR.** The keys exist and are correct. This is a future regression safety gap, not a current bug. The existing `LoginPage.test.tsx` tests for the 8 s slow-login banner (T1.1: LoginPage shows "still trying" sub-text after 8s of isLoading) exercise those branches behaviorally, though with mocked i18n. A follow-up fix would add error-state and slow-loading-state variants to the smoke test or upgrade to a key-existence check (e.g., verify the key resolves via `i18n.t('auth.companyRecovery.errorHint', { ns: 'common' })` directly). Does not block merge.
