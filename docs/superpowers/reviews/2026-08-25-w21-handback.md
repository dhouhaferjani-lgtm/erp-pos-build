## 1. What was actually wrong

Three separate things, and only all three together explain "no in-product recovery":

1. **Nothing cleared the scope on a NEW session.** `clearAllAppState()` drops the origin-wide
   `autoerp-company-selection` key, and it was wired to logout and to 401 expiry only.
   `RegisterPage.tsx` and `LoginPage.tsx` called `setAuth(...)` and navigated. A fresh signup
   therefore inherited the previous account's company id.
2. **The bootstrap call carried the stale header too.** `apps/web/src/lib/api.ts` attached
   `X-Company-Id` to *every* request, `/user/companies` included. That call is the one that would
   have taught the client the truth; because it 403'd like everything else, the membership list
   never loaded, the switcher opened empty, and the deadlock could not self-heal.
3. **The client had nothing to key a recovery on.** The middleware already returned a typed
   `COMPANY_ACCESS_DENIED`, but no client code read the code, so a 403 just logged and died.

And while in that middleware, **C-13(iii)**: `X-Company-Id` is client-supplied and flowed straight
into the `user_company_memberships.company_id` **uuid** predicate. A non-uuid raises SQLSTATE 22P02
on PostgreSQL — a 500, not a denial.

## 3. Why no loop

The 403 self-heal resets **only while a selection exists**. After the reset `currentCompanyId` is
null, so (a) the header stops being sent and the server falls back to the user's own default
company, and (b) a second rejection returns `false` without touching anything. The re-bootstrap is
causal rather than manual: `currentCompanyId` is a suffix of every `tenantScopedKey`, so clearing it
re-keys `['user','companies',tenantId,null]` and `CompanyProvider` refetches — now without the
header. `resolveCompanySelection` then picks the primary membership (the stale persisted id is gone).
`NO_COMPANY_ACCESS` is deliberately excluded: it means the user is a member of no company at all,
which no client-side reset can fix.

## 7. Residuals — seen, NOT touched (no scope creep)

1. **`user/companies` is still enforced server-side.** Its route group is commented *"Routes that
   don't require company context"*, but `CompanyContextMiddleware` sits in the global `api` group
   (`apps/api/bootstrap/app.php:142-146`), so it applies anyway. `UserController::companies` is
   entirely user-scoped (reads the caller's own memberships; never touches `CompanyContext`), so
   exempting that route name in the middleware would be safe and would make the deadlock impossible
   even for a stale cached client bundle. The brief scoped the backend to the typed contract + the
   uuid guard, so I did not add it. **Recommend as a follow-up.**
2. **`OwnerReportScope.php:30`** passes a request-derived company id to `userHasAccessToCompany`. It
   no longer 500s (fail-closed guard), but its own rejection is not typed the way the middleware's
   is; a client cannot key a scope reset on it.
3. **`AuthProvider` 401 handling and `handleUnauthorized` are untouched** — a 401 still hard-clears
   and redirects, which is correct and orthogonal to this lane.
4. **The campaign report quotes the 403 body as `{"message":"Access denied: …"}`.** No such string
   exists anywhere in `apps/api` (grep: 0 hits outside `EnsureSuperAdmin`). The real envelope is
   `{"error":{"code":"COMPANY_ACCESS_DENIED","message":"User does not have access to the requested
   company."}}`, now pinned by test. The report paraphrased; the code was already typed.
5. **Cross-tab `storage` listener** (`companyStore.ts` tail) adopts a new selection when
   `companies.length === 0`. Correct today (it is validated on the next fetch), but it means a reset
   in tab A momentarily propagates a null to tab B. Not a defect in this flow; noted.

## 8. Reviewer entry points

- Deadlock mechanism and the three layers: §1 and §3.
- Loop-safety argument: §3 — the specific claim to attack is *"after the reset the header stops
  being sent, so the server's default-company fallback cannot produce a second
  `COMPANY_ACCESS_DENIED`."*
- Authz surface: the middleware now rejects a class of request it previously accepted (malformed
  header → 400 instead of 403/500). No request that previously succeeded now fails: a valid uuid
  takes exactly the old path.
- The `X-Company-Id` exemption is the one deliberate loosening — argued in §2 and in the
  `COMPANY_CONTEXT_EXEMPT_PATHS` docblock: both endpoints are user-scoped server-side, so the header
  was never load-bearing there.
