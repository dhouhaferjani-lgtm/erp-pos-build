## Finding 3 [IMPORTANT] — the 7 stale campaign-tenant lines. EXTENDED, not documented away.

The gate is right that the handback's "credit note" framing was wrong: none of those rows is posted or
sealed, all are repairable, and `CopiesDocumentData::copyLine()` (`:141`) copies `tax_rate` verbatim, so
converting one after this deploy would mint a **new** wrong-VAT invoice — worse than the historical rows.
Extended the migration rather than writing a checklist step, per the recommendation:

`…_backfill_products_tax_rate_from_tax_configuration_n1.php` `repairUnpostedDocumentLines()` (+ `retotal()`):

- Repairs `document_lines.tax_rate` from the product's **configuration** (not from the just-repaired
  `products.tax_rate`, so the two halves stay independent), for lines whose document passes **three
  independent guards, all required**: `status IN ('draft','confirmed')`, `fiscal_status = 'DRAFT'`,
  `fiscal_hash IS NULL`. Nothing posted, sealed or voided is reachable; a posted document has GL entries
  derived from its tax and a sealed one is hash-chained — those are credit-note territory, and both are
  pinned by their own test.
- Lines with no product (free-text/service) state their own rate and are never touched.
- **Re-totals the affected documents** through `DocumentTotalsCalculator::recalculate()` — the module's own
  calculator, the same one the draft path calls — so TN stamp duty, line discounts and partner exemptions
  are handled by the code that owns them instead of re-derived in SQL. Scale comes from the document's own
  currency (same guard as `CopiesDocumentData::recalculateTotals()`), so it is safe in the
  no-`CompanyContext` world of `tenants:migrate` (rule 20). Without this the header would keep the
  19 %-derived total while the lines said 7 % — a document contradicting itself on paper.
- Its **own savepoint** and its own counters: the gate line is now
  `status=ok repaired=N doc_lines=M docs_retotalled=K`. A failure in this half cannot roll back the product
  half, which is the part that stops new drift.
- Idempotent: the predicate is "the two disagree", and `recalculate()` writes through Eloquent, which issues
  no UPDATE when the recomputed totals equal the stored ones.

## The decision: the document-line REPAIR is WITHDRAWN. That half now REPORTS.

Both gates attacked the same object — the `document_lines` UPDATE + re-total added in r1 — and between them
found **four independent defects, no two the same**:

| # | Gate | Defect |
|---|---|---|
| 1 | both | **Type-blind.** It rewrote draft credit notes (which mirror a SEALED invoice and disagree with the product *by design*), supplier invoices (whose rate is what the **supplier** charged), supplier credit notes, expenses, return notes, delivery notes — from the **sale-side** product master. Both gates proved it by execution. |
| 2 | treasury | **`document_lines.recoverable_tax_amount` / `non_recoverable_tax_amount` left stale** → a repaired draft supplier invoice becomes **permanently unpostable**: `GeneralLedgerService::createSupplierInvoiceGrIrClearingEntry()` refuses when `total != billedHT + recoverableVAT + …`. |
| 3 | treasury | **`documents.balance_due` left stale.** The cache trigger is bound to `payment_allocations`, never to a `documents` UPDATE, and `Document::outstandingBalance()` treats a non-null value as authoritative — so AR/AP outstanding and the payment ceiling would be wrong, and a confirmed SO with a prepayment could be left over-allocated. |
| 4 | treasury | **`document_tax_details` left stale.** The VAT declaration reads that snapshot, not the live lines, so a repaired confirmed invoice would declare the OLD rate to the DGI. |

Each of those is individually fixable, and I began doing exactly that. I stopped, and I want the reasoning on
the record rather than the patch:

- **The pattern, not the instances, is the problem.** A migration that rewrites a document is
  re-implementing the derivation chain the application performs on save — totals, the balance cache, the tax
  snapshot, line-level deductible VAT, exemption and stamp-duty re-derivation. Two review rounds found a new
  missing link each time. Closing four known links does not establish there is no fifth, and this runs
  **unattended on every tenant database** on push to `origin/dev`.
- **The population is four documents on one tenant.** The census (re-run below) is `QT-2026-0002` (1 line),
  `QT-2026-0003` (2), `QT-2026-0004` confirmed (2), `SO-2026-0001` (2) — 7 lines, all `quote`/`sales_order`,
  none sealed, on the campaign tenant only.
- **The manual repair is now correct and trivial**, because the product half of this same deploy fixed it:
  an operator re-picks the product on the line and the ordinary write path resolves the right band **and**

## Minors 3–6 — all folded in (each was under the time box)

- **3 (override false-positives).** `document_lines` stores a rate and never the configuration the line was
  put on, so a deliberate band override is indistinguishable from N-1 drift. I did **not** narrow the
  predicate to the company default — that would silently drop a genuinely drifted line whose stale value
  happens not to be the default (e.g. a product moved between bands twice). Instead the repair advice now
  carries `verify first that the line was not a deliberate band override`. Narrowing remains available if the
  owner prefers precision over recall; recorded here rather than chosen unilaterally.
- **4 (grouping key).** The aggregate is keyed on `documents.id` and prints `document_number`
  (`(no number yet)` when null). `document_number` is unique only per `(tenant_id, type)` and is nullable
  until a document seals, so the old key could have collapsed unrelated documents into one entry and made
  `flagged_docs` under-report the list a checklist greps.
- **5 (bounded fetch).** Counters now come from a `COUNT(*) / COUNT(DISTINCT d.id)` statement with the same
  predicate, and the enumeration takes a `LIMIT`. The gate-line numbers stay exact for any population size
  while PHP never materialises the whole drift set inside an unattended `tenants:migrate`. The truncation
  line reports against the true `documents=` count.
- **6 (never-500).** `resolveLineTaxRates()` moved **inside** `DraftController`'s `try`. Its two queries plus
  one per line now reach the silent-failure arm instead of 500-ing an endpoint the editor calls every three
  seconds — restoring the property the code had before the tier relocation, which the method's own docblock
  claimed.
