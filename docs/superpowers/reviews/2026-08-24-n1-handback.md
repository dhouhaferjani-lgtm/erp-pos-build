Migration behaviour: self-guarding (`Schema::hasTable` on both tables → `status=skipped` gate line, no throw);
idempotent by construction (predicate is "the two disagree", so a second run affects 0 rows and does not
re-stamp `updated_at`); never throws (caught + `status=FAILED` gate line, contained in a `DB::transaction()`
savepoint so a failure cannot abort the tenant's migration bookkeeping on PG); logs exactly one
`PRODUCT TAX-RATE N1 BACKFILL MIGRATION:` line per tenant at **WARNING** level (production is
`LOG_LEVEL=warning`) with `tenant=`, `status=`, `repaired=<count>`; `down()` is a declared irreversible
no-op. Skips `DOCUMENT_TOTAL` / fixed-amount configurations (TN stamp duty) and products with no
configuration; uses `IS DISTINCT FROM` so a NULL `tax_rate` is repaired rather than dropped by the
comparison. Two census queries are in the migration docblock.

## Residuals seen, not touched (out of lane)

- `DocumentLineTaxResolver`'s branch order still lets an explicit `lines.*.tax_rate` outrank a
  `tax_configuration_id` sent on the same line. The frontend now never sends both, but any other client can,
  and the server would take the client's number. Worth an owner ruling on whether the configuration should
  outrank an explicit rate server-side, the way it now does on the product write path.
- The two resolvers (`TaxResolutionService::resolveRateFromTaxConfiguration()` and
  `DocumentLineTaxResolver::rateFromConfigurationId()`) are byte-for-byte equivalent scope filters in two
  modules. They must stay mirrored; nothing enforces that today.
