## 1. The defect

`hasPins()` answered `SELECT EXISTS(... users WHERE tenant_id = ? AND pos_pin IS NOT NULL)` — no company
scope, no membership belt, no account belt — while `verifyPin()` and `pinData()` answered from the
ACTIVE-member / ACTIVE-account population of the `CompanyContext` company.

That gap is a hard lockout, not a cosmetic inconsistency. The device (`apps/pos/src/stores/operatorStore.ts:378`,
`apps/pos/src/App.tsx:312-324`) routes `has_pins === false` to the first-run **PinSetupPage** and `true` to
**PinEntryPage**. Every user row that `has-pins` counted but `pin-data`/`verify-pin` reject put the terminal on
the PIN prompt for a roster `pin-data` returns empty — a cashier with no PIN to enter and no path to create one.
Four live populations hit it:

- the shop's only PIN holder was **offboarded** (membership revoked + account deactivated) — the campaign scenario;
- the only PIN holder is **deactivated** with a stale `Active` membership row (pre-cascade / hand-edited data);
- the only PIN holder belongs to a **sibling company** in the same tenant;
- the only PIN holder has **no membership anywhere**.

## 2. The fix

`apps/api/app/Modules/POS/Presentation/Controllers/PosAuthController.php`

- **`:33-57`** — new `private function pinHolders(string $tenantId, string $companyId): Builder`. The single
  definition of "an operator PIN this terminal may act on": tenant + `user_company_memberships.status = Active`
  for the context company + `users.status = Active` + `pos_pin IS NOT NULL`. (Extraction of the query the
  uncommitted partial fix in this worktree already routed `verifyPin` through; that call site is `:87`.)
- **`:320-351`** — `hasPins()` now resolves `$this->companyContext->requireCompany()` and answers
  `$this->pinHolders($currentUser->tenant_id, $company->id)->exists()`. Docblock records why (device bootstrap
  routing → lockout).
- **`:197-206`** — `pinData()` switched onto the same helper. **Behaviour-identical** (the inline query was
  literally the same four predicates); it removes the duplicate definition that N-5's drift grew out of, so the
  three surfaces cannot re-diverge silently. Covered green by the pre-existing `PinDataEndpointTest`.
- **`:80-84`** — the `verifyPin` parity comment ("the three PIN surfaces admit precisely the same population")
  is now true: `has-pins` was the outlier that made it a lie.

Rule compliance: strict types, constructor injection only (no `app()` in production code), enum-valued status
comparisons (`MembershipStatus::Active->value`, `UserStatus::Active->value`), no placeholders.

## 5. Blast radius of the behaviour change

`has-pins` now calls `requireCompany()`, which throws (500) when no company context is bound. This is not new
exposure: `pinData()` on the same route group already does exactly this, and both are called from the same device
bootstrap. The device's `checkHasPins` wraps the call in try/catch and falls back to the local SQLite operator
cache on any error, so the failure mode is unchanged for offline/degraded terminals.

Backend consumers of the endpoint: `routes.php:46` and the new test only (`grep -rln 'has-pins\|hasPins' tests/ app/`).
No server-side caller depended on the old tenant-wide semantics.

## 6. Residuals / adjacent defects seen but NOT touched (out of scope)

1. **`pos_pin` is not cleared on deactivation/offboarding** (the brief's named follow-up). The fix is correct as a
   read-side belt, but the fired employee's bcrypt PIN hash still sits in `users.pos_pin` forever. Recommend a
   follow-up lane: clear `pos_pin` in the offboarding cascade (membership revoke / user deactivate), which also
   frees the PIN for reuse under `setupPin`'s uniqueness check.
2. **`setupPin` uniqueness is tenant-wide, unscoped** (`:133-136`): it rejects a PIN held by ANY tenant user —
   including deactivated accounts and members of other companies that this terminal can never verify against.
   Same asymmetry class as N-5, opposite direction (over-broad instead of over-narrow): a shop can be told "PIN
   already used" by a ghost. Not in this lane's scope.
3. **Device-side prune never fires for the last operator.** Verified at `apps/pos/src/lib/sync/syncService.ts:1320`:
   `pruneOperatorsExcept` is gated on `operators.length > 0`, so an **empty** `pin-data` response is deliberately
   treated as non-authoritative and never prunes (FU-1's guard against wiping legitimately-offline operators). A terminal whose
   last remaining operator is offboarded therefore keeps the stale cached PIN offline while the server now
   correctly says `has_pins=false`. Device sync behaviour is explicitly out of scope per the brief — flagging for
   the sync lane.
