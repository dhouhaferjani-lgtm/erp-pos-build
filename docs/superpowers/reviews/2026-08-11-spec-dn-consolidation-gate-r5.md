## 3. New defects

| ID | Severity | Finding and required correction |
|---|---|---|
| **R5-ND-1** | **Blocking; replacement enforcement claim is still overstated** | `SPEC:459` says the WorkOrder precedent fails CI on any status write and that `DeliveryNoteBillingWritesOnlyViaClaimService` makes any marker/payload-key write outside the service a CI-blocking error. The precedent is only a `Rule<Assign>` and returns immediately unless the left-hand side is a direct property fetch (`WorkOrderStatusWriteOnlyViaTransitionService.php:31-64`); it is not a precedent for model `update`, query-builder insert/update, or raw SQL coverage. Moreover, PHPStan currently analyses only `app/` (`apps/api/phpstan.neon:5-8`), while this spec deliberately requires a migration/backfill writer outside the service. Define the exact covered write forms and the intentional migration exception, add rule fixtures for every supported model/query/DB write form, and narrow “any write” / “cannot bypass” to what the rule actually enforces. A name plus one fixture is not the mechanical guarantee claimed. |
| **R5-ND-2** | **Material; R4-ND-4 inventory remains self-contradictory** | The binding prescription says the SO header is locked explicitly “immediately after BEGIN” (`SPEC:330`). Since the auto-created-DN factory is subsequently run inside step 2 and takes the delivery-note sequence (`DeliveryNoteFromDocumentFactory.php:73-85`), that prescription yields `own source header -> delivery-note sequence -> own source lines -> claimed DNs`. The prose and inventory instead publish `delivery-note sequence -> own source header -> own source lines` (`SPEC:345,377,385,980`). Choose one real first-acquisition point and make the prescription, acyclicity account, inventory and same-order test agree. The simplest consistent form is the already-prescribed header-first lock in both SO sub-lanes; own-source locks remain outside the mandatory cross-lane relative chain. |
| **R5-ND-3** | **Material owner-disclosure provenance error** | `SPEC:340` and OI-14 at `SPEC:948` say a failed conversion can leave the order fully delivered against a delivery note that “does not exist.” The current branch creates the DN and mutates the order before the invoice transaction (`SalesOrderToInvoiceConverter.php:154-167,520-533`), so on a later invoice failure that draft DN, its number, the payload link and line stamps all survive; `SPEC:318,322,331` itself calls it an orphan draft DN. The retry-skips-auto-create conclusion is valid, but it skips because it sees a surviving linked draft DN plus the delivered line projection, not a nonexistent DN. Correct Layer 0b and OI-14 to say “surviving orphan/unconfirmed draft DN” so the owner is deciding the actual observable behavior. |
| **R5-ND-4** | **Material rendering defect** | The unescaped pipe inside the `SPEC:757` inline code span truncates a normative validation requirement in GFM, and the SQL concatenation pipe pair at `SPEC:1033` breaks the five-column r2 history row. Escape or entity-encode the literal pipe characters and re-render both complete tables. Because §5 loses normative content, this is not merely cosmetic. |
