### MAJORS

**P2 — Do not trust client fields for 12-month tokens (round-3 carry)**
File: `apps/api/app/Modules/Identity/Presentation/Controllers/AuthController.php:101-107`

> When a non-POS client logs in with valid credentials, it can set `X-Client-Type: pos-tauri`, any non-empty `device_id`, and `platform: macos`/`windows`/`linux` to receive a 12-month Sanctum token. These values are all unauthenticated request inputs accepted by `LoginRequest`, so this bypasses the intended 30-day web/API token policy rather than providing a server-side POS check; gate the longer expiry on a server-verified terminal/device pairing or similar trusted state.

The activation hardening plan §Phase 2 design (`docs/superpowers/plans/2026-04-30-pos-activation-hardening.md:91`) anticipated this:
> "create a POS-specific ability/scope (e.g. `pos-terminal`) when issuing a token from a terminal-pairing flow"

But the plan's "Backend change" section (line 92) describes the simpler header-only approach this PR implements — without the cryptographic device-pairing flow. The plan also explicitly accepts the resulting risk surface (lines 105-107):
> "Token revocation: with 12-month tokens, a stolen device is exposed for up to a year. Mitigation: every successful checkSession() re-validates server-side that the token is still in personal_access_tokens and the user is still active. An admin can revoke a token via Filament back-office, and the next checkSession call (which the POS does on every shift open) will return 401 and force logout."

## Recommendation surface (for orchestrator)

Three paths forward, all requiring an explicit decision:

**A. Accept the residual spoofing risk and merge as-is.**
- Rationale: the plan explicitly accepted the broader "stolen device exposure" risk. Spoofing is a different shape of the same risk class — a credentialed adversary can already do harm; the marginal addition is "longer-lived token." Server-side revocation via Filament + per-shift `checkSession` re-validation is the agreed mitigation.
- Cost: documents the residual risk in the PR / plan; merges T1.4 with explicit caveat.
- Time to close: ~30 minutes (doc updates).

**B. Defer T1.4 until a server-verified terminal-pairing flow lands.**
- Rationale: Codex's preferred fix shape. Closes the spoofing surface entirely.
- Cost: full architectural workstream — new endpoint(s), device handshake, key storage on Tauri side, key revocation flow on backend, migration of existing devices. Estimated 3-5 days.
- Time to close: revert this PR; queue terminal-pairing as a separate workstream.

**C. Reduce the per-token expiry to a more conservative window (e.g. 90 days) and merge.**
- Rationale: limits the marginal exposure from spoofing while still buying meaningful QoL improvement over 30 days.
- Cost: change `now()->addYear()` → `now()->addDays(90)`. Update tests + docs. ~1 hour.
- Time to close: ~1 hour (smaller version of A).

**Recommended:** Path A or C. Path B should be queued as a follow-up regardless of the current PR's outcome.
