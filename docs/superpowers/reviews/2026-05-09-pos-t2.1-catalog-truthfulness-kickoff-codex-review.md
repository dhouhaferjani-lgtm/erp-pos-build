# 5. Industry comparison section - how does this fix compare to Square POS / Toast / Lightspeed Retail / Shopify POS? Are there architectural patterns the kickoff misses?

The kickoff is directionally aligned with industry POS/catalog practice in one important way: it moves from a capped foreground list toward incremental local-cache truth. That matches the broad pattern used by mature systems: local catalog projection, update notifications or polling, and targeted lookup when a scanned item is not in the warm in-memory set.

It still misses several mature patterns:

- Versioned catalog watermarks/version vectors. Square documents a `catalog.version.updated` webhook and explicitly says integrations do not need to refetch the entire item library when syncing; they can retrieve mutated catalog objects since the last notification. Source: https://developer.squareup.com/docs/catalog-api/webhooks and https://developer.squareup.com/docs/catalog-api/sync-with-external-system.
- Webhook plus polling fallback. Toast's menus webhook is positioned as the preferred stale-menu signal, with `/metadata` polling recommended as a backup if a webhook is missed. Source: https://doc.toasttab.com/doc/devguide/apiMenusWebhook.html.
- Cursor pagination and queryable updated timestamps. Shopify's GraphQL `products` query supports cursors, `updated_at` filters, and barcode/SKU filters for product/variant retrieval. Source: https://shopify.dev/docs/api/admin-graphql/latest/queries/products.
- Product/inventory webhook separation. Lightspeed's docs warn that product-update webhooks are not sufficient for inventory tracking and recommend inventory-specific synchronization where needed. Source: https://x-series-api.lightspeedhq.com/docs/webhooks.
- Lookup cache and collision handling. The proposed three-tier path is useful, but mature POS scanners usually separate "scan token resolution" from "catalog browsing" and cache recent scan resolutions. Step B should add, or at least defer explicitly, a small recent-scan LRU cache keyed by normalized barcode/SKU with collision metadata.
- Content-addressed or snapshot-aware catalog hydration. For 5K-10K SKUs, a foreground pull should ideally know whether the local snapshot is complete for a tenant/menu/version before showing "truthful" status. The current plan relies on local rows plus `updated_since` wall-clock metadata, which is weaker than a server-issued catalog version/watermark.
- Menu-aware projections. Toast-style menu systems treat published menus as separate structures from raw products. The kickoff defers the Otospex/Menu tenant desync, but if Otospex is a launch tenant, this leaves AutoERP below the industry pattern for menu truthfulness.

Net comparison: Step A+B+C is a reasonable tactical fix for IziPOS standard retail catalog truthfulness if the blockers above are corrected. It is not yet equivalent to Square/Toast/Shopify/Lightspeed-style sync architecture because it lacks server-issued catalog versions, webhook/poll replay strategy, collision-aware scan resolution, and menu-aware catalog snapshots.
