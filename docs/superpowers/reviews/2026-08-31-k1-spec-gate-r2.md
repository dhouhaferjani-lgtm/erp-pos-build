## Part 2 — verification of v2's NEW claims

### (a) Dual-shape tolerance at `lineMismatches()` as the replay remedy — **sound in principle, under-specified in two ways**
The mechanism is right. `assertExistingDraftMatches()` (`POSAccountChargeDraftService.php:101-195`) collects mismatches and throws `pos_account_charge_draft_conflict:` at `:192-193`; the line arm is `lineMismatches()` `:201-231`, whose money loop `:218-228` compares `unit_price` (`:220`) **and** `line_total` (`:223`) with `bccomp(..., $currencyScale)`.

*Net-first-then-legacy-gross matching* is sound: net candidate `line_subtotal`, legacy candidate `bcadd(line_subtotal, line_vat)`. On a **zero-VAT line the two candidates are byte-identical**, so the "ambiguity" collapses to a single value — ambiguous but genuinely harmless, exactly as the question supposed. On a VAT-bearing line the two differ by `line_vat`, so no false accept of an unrelated value is possible at the currency scale in any realistic case. **No finding on the matching logic itself.** The two real defects are K1-S2-02 (the tolerance must cover `unit_price` too) and K1-S2-03 (no cutover discriminator ⇒ the guard never re-tightens).

### (b) Derived-net `unit_price` division — **the brief's own invariant is unsatisfiable; two separate defects**
Verified chain: `DocumentLine::computeLineTotal()` (`DocumentLine.php:280-302`) = `bcmul(qty, unit_price, scale)` minus `discount_percent` else `discount_amount`, floored at 0; `DocumentTotalsCalculator::recalculate()` `:43` and `TaxCalculationService::calculateSubtotal()` `:364-368` both call it; `unit_price` is cast `decimal:3` (`DocumentLine.php:143`), so there is no headroom to hide a remainder.
- **Discount:** the POS cart's `line_total` is already post-discount **gross** (`apps/pos/src/stores/cartStore.ts:508-518`: `grossTotal = unit_price × qty`, `lineTotal = grossTotal − discountAmount`), so the mapper's `lineSubtotal = line_total − tax_amount` (`accountChargeCartMapper.ts:67`) is post-discount **net** — while `line_discount_amount` (TTC, computed on `grossTotal`) is *separately* stored into `document_lines.discount_amount` (`POSAccountChargeDraftService.php:90`). ⇒ **K1-S2-01 (BLOCKER)**.
- **Rounding:** `bcformatStrict()` is `bcadd($v,'0',$scale)` — it **truncates** (`CurrencyScale.php:130-145`; the half-up variant is a different method, docblock `:147-158`). So `qty × trunc(line_subtotal ÷ qty)` ≤ `line_subtotal`, with an error up to `qty × 10⁻³`. ⇒ **the brief must mandate storing `line_total` from `line_subtotal` directly and must state a remainder policy instead of a strict equality test** — **K1-S2-04 (BLOCKER)**. Note the good news the brief should cite: `PurchaseOrderController.php:100-105,122` already implements exactly this pattern (derive `unit_price` at `scale+1` then truncate; **keep the submitted `line_total` unchanged**).

### (c) "posted-GL population may be near-empty" — **directionally right, materially incomplete**
With gross `line_total`: `revenue = Σ line_total ≈ document.total` (`AccountingService.php:649`) and `vat = Σ(line_total × rate) > 0` (`:1941-1943`), so `residual = arFacingTotal − (revenue+vat) < 0` → `GlResidualRefusal::NegativeResidual` (`:383-391`). Correct — **for VAT-bearing lines only**. Two populations the claim silently excludes: (i) **0 %/exempt lines**, where gross == net and the posting succeeded normally; (ii) any flow that ran `DocumentTotalsCalculator::recalculate()` before posting, which rewrites `document.total` from the same gross basis and drives the residual back toward zero — i.e. a posted, doubly-inflated invoice. ⇒ **K1-S2-06**.

### (d) `POS-ACCOUNT-CHARGE:` reference prefix at `:22` — **TRUE, but unsafe as a sole key**
Verified verbatim: `POSAccountChargeDraftService.php:22` `$reference = 'POS-ACCOUNT-CHARGE:'.$command->fiscalEventId;` and `:67` writes it to `documents.reference`. It is deterministic and prefix-indexable as the brief says. But `documents.reference` is client-writable (`CreateDocumentRequest.php:87`, `UpdateDocumentRequest.php:83`, fillable `Document.php:155`) — which makes it unsafe both as a `--fix` selector (**K1-S2-11**) and as a delivery-gate condition (**K1-S2-10**).

## Part 3 — new findings (K1-S2-xx)

### K1-S2-01 [BLOCKER] Ruling 3's formula double-subtracts the line discount, and subtracts a TTC amount from an HT base
`accountChargeCartMapper.ts:67` sets `line_subtotal = item.line_total − item.tax_amount`, and `cartStore.ts:508-518` proves `item.line_total` is already **post-discount**. `POSAccountChargeDraftService.php:90` separately stores `line_discount_amount` (a **TTC** figure — `cartStore.ts:508` computes it on `grossTotal`) into `document_lines.discount_amount`. With `unit_price := line_subtotal ÷ quantity` (BRIEF:10), `DocumentLine::computeLineTotal()` (`DocumentLine.php:287-295`) returns `line_subtotal − discount_amount_TTC`, i.e. the discount removed **twice**, the second time as a tax-inclusive amount off a tax-exclusive base.
*Why it matters:* every discounted account-charge line understates the taxable base by roughly `discount × (1 + rate)`, the header `subtotal` diverges from Σ stored `line_total`, and the VAT declaration snapshot (`InvoiceController.php:652` → `TaxCalculationService::snapshotTaxDetails()` `:509`) is taken on that understated base. This is a *new* VAT error introduced by the fix, in the lane whose purpose is removing one. It also makes the brief's own Task 1.4 invariant false by construction.
*Fix before dispatch:* the ruling must state the full derivation, one of: (A) `unit_price = (line_subtotal + net_discount) ÷ quantity` **and** store `discount_amount = net_discount = discount_amount_TTC ÷ (1 + vat_rate/100)` at guarded scale — documents stay pure HT end to end; or (B) fold the discount into the derived unit price and store `discount_amount = '0'` (loses discount disclosure on the invoice — an owner call). Add a discounted-line test to the non-negotiable list.

### K1-S2-02 [BLOCKER] `:223` is no longer "the ONLY mirror" — ruling 3 makes `unit_price` (`:220`) a second one, and the replay tolerance must cover it
`BRIEF:27` instructs "update the drift mirror `:223` (verified the ONLY mirror)". That r1 verification was scoped to `line_total`. Under ruling 3 the writer at `:88` also changes (TTC → derived net), and its mirror is `lineMismatches()` `:220` `'unit_price' => $this->money($lineItem, 'unit_price')` — which still expects the raw TTC payload value. If `:220` is left alone, **every replay of a POST-fix draft throws `pos_account_charge_draft_conflict:line_N_unit_price`** → `ApplyFiscalEventProjectionJob.php:414` → retry → dead-letter. That is the exact failure K1-S1-02 exists to prevent, inverted onto the new rows.
*Fix before dispatch:* correct the sentence (two mirror fields, `:220` and `:223`), and extend `BRIEF:28`'s dual-shape requirement to `unit_price` (net candidate = derived net; legacy candidate = raw payload TTC). Extend the mandated replay test to assert on both fields.

### K1-S2-03 [MAJOR] The dual-shape tolerance has no cutover discriminator, so the drift guard is disarmed forever
`BRIEF:28` says the mirror "tolerates BOTH shapes **for rows written before the fix**" but names no discriminator, and none exists on the row: `assertExistingDraftMatches()` reads only the document, its payload and its lines — nothing records which code version wrote them. Implemented literally, the tolerance is unconditional: a future regression that reintroduces a gross `line_total` (or a TTC `unit_price`) passes the mirror silently — permanently deleting the only detector for the class of defect this lane is fixing.
*Fix before dispatch:* name the discriminator (`documents.created_at < <stamped cutover>`, or a `payload.line_shape_version` written by the fixed writer) **and** state the removal condition: once the Task-3 sweep reports zero remaining legacy drafts per tenant, the legacy arm is deleted. Add a test that a post-cutover gross value **still throws**.

### K1-S2-04 [BLOCKER] The derived-net division cannot round-trip; the mandated equality test is unsatisfiable and the remainder lands in a tax account
`CurrencyScale::bcformatStrict()` truncates (`CurrencyScale.php:130-145`), `unit_price` is `decimal:3` (`DocumentLine.php:143`). For `quantity = 3, line_subtotal = 10.000`: `unit_price = 3.333`, `computeLineTotal` returns `9.999`. So `BRIEF:30`'s "test that recomputed subtotal == Σ stored `line_total`" **fails on every non-divisible line**, and Codex will either weaken the test silently or chase it.
Worse, the drift is not neutral. Truncation makes the recomputed subtotal *smaller*, so `revenue` shrinks while `document.total` (device-sealed) does not ⇒ `residual > 0` at `AccountingService.php:385-387`, and the positive branch `:392-396` credits it to **`SystemAccountPurpose::SalesStampDutyPayable`** when that account exists (it does, in TN) — a rounding remainder posted as **stamp duty payable**, a misdeclared tax. Falls back to a rounding-difference account only where no stamp-duty account exists.
*Fix before dispatch:* (i) mandate explicitly that `line_total` is stored **from `line_subtotal` verbatim**, never recomputed from the derived `unit_price`; (ii) replace the strict-equality invariant with a stated tolerance (`|recomputed − stored| ≤ quantity × 10⁻ˢᶜᵃˡᵉ` per line) **and** a rule for where the aggregate remainder may land — explicitly NOT stamp duty; (iii) cite `PurchaseOrderController.php:100-105,122` as the in-repo precedent (derive at `scale+1`, truncate, keep the submitted `line_total`). If the owner wants exact round-trip instead, that is a schema decision (widen `unit_price` scale) and must be ruled here, not discovered by Codex.

### K1-S2-05 [MAJOR] `CheckCogsCoverageCommand` cannot be "taught the new reference type" — its FROM clause is `pos_receipt_lines`
`BRIEF:35` says teach `CheckCogsCoverageCommand.php:402` the new reference type "so the coverage scan sees these movements". The POS arm of that scan is `DB::table('pos_receipt_lines as lines')->join('pos_receipts as receipts', …)` (`CheckCogsCoverageCommand.php:371-372`); `:402` is only the `whereNotExists` predicate. An ACCOUNT_CHARGE creates **no** `pos_receipts`/`pos_receipt_lines` rows, so account-charge lines are invisible to that query regardless of what `:402` says. Additionally `pos_account_charge_receipts` has **no line table at all** (only `2026_05_21_150000_create_pos_account_charge_receipts_table.php` exists), so a per-line coverage arm has nothing to iterate.
*Fix before dispatch:* rule what the coverage guarantee is for account charges — either a new arm driven off the canonical payload's `line_items` (name it), or an explicit, documented "no per-line COGS coverage scan for ACCOUNT_CHARGE until it has line rows" carve-out. Do not leave `:402` as the instruction.

### K1-S2-06 [MAJOR] "Near-empty posted population" is an unmeasured claim used to justify scope, and it has two known exceptions
`BRIEF:44` puts the near-empty reasoning in a **docblock**. The reasoning holds only for VAT-bearing lines (see Part 2c): **0 %/exempt** account-charge invoices posted cleanly with a gross-but-equal `line_total`, and any document recalculated via `DocumentTotalsCalculator::recalculate()` before posting has a residual driven back toward zero and can be **posted and doubly inflated**.
*Fix before dispatch:* the sweep must **measure** the posted population per tenant and print it (count + total delta), and the brief must stop using "near-empty" as scope justification. State the 0 %-VAT subset explicitly (its correction is a no-op — worth saying, so the report is not misread).

### K1-S2-07 [BLOCKER] Lot allocations for an account charge are impossible as scoped — the allocation table has an FK to `pos_receipts`
`BRIEF:36` — "Lots: decrement DEFAULT/allocated lots as the sale lane does". The sale lane's second leg writes `pos_receipt_line_batch_allocations` (`PosCoreReceiptProjection.php:1964-1972` → `consumeLotsForSaleLine`, `:2098 snapshotLotAllocations`), and that table declares `receipt_id` **FOREIGN KEY → `pos_receipts(id)` ON DELETE CASCADE** plus a non-null `receipt_line_id` (`database/migrations/tenant/2026_02_19_000001_create_pos_receipt_line_batch_allocations_table.php:15-27`). An ACCOUNT_CHARGE has neither row. An unattended lane will therefore either hit an FK violation, **fabricate a `pos_receipts` row no device authored** (fiscal pollution — a receipt with no device chain), or silently skip lot provenance, leaving batch-tracked stock decremented with no lot record: `BatchTraceabilityController.php:81` recalls and `ReceiptReturnService::lotProvenanceForLine()` (`:1796`) both read that empty table.
*Fix before dispatch:* an explicit owner ruling — (A) a sibling `pos_account_charge_receipt_line_batch_allocations` table (+ readers taught), (B) generalise the existing table's anchor (migration dropping the FK, morph columns — the heavier option), or (C) account charges write the aggregate `inventory_batch_movements` leg only, with the traceability gap ticketed. State which, and update the readers list accordingly.

### K1-S2-10 [BLOCKER] The proposed delivery-gate second condition is forgeable, and its stated premise is false
`BRIEF:37` claims "the bridge posts via `Standard` today" — false: `DocumentAccountChargeFactureBridge.php` contains **zero** `post`/`PostingContext` references (grep); the document is created Draft (`POSAccountChargeDraftService.php:55-57`) and posted later by the ordinary HTTP endpoint, exactly as r1 stated. ### K1-S2-11 [MAJOR] The `--fix` sweep selects money rows to rewrite by a client-writable free-text column
