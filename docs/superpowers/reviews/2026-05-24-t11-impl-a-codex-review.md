# T11-impl-A — Customer Model Augmentation (`customer_contacts`) — Spec Review (round 1, Codex)
## Verdict: REJECT
## Summary (2-3 paragraphs)
The core design direction is sound: `party_contacts` already exists as the current Partner-to-Contact association, it is boolean-flag based, and `Partner::contacts()` remains tied to that table. The proposed `customer_contacts` table is justified as an additive B2B account-role layer, and the topology contract supports it as a new tenant table with intra-tenant FKs and Pattern D `tenant_id`.

I did not find a design-breaking blocker in the table shape or aggregate direction. However, the implementation spec is not ready to hand to an engineer because one §2 grounding citation is factually wrong in a way that points implementers at a bad service pattern, and the test plan does not prove the spec's own cross-tenant/company mutation contract for `changeRole`, `detach`, or `listForPartner`.

The spec should be revised before implementation. Most fixes are small, but they are material: correct the `ContactService` citation, make the tenant/company isolation tests match §8, and tighten a few line/path/middleware details so an engineer does not have to infer the intended conventions.

## Findings
### BLOCKER
None.

### P1
1. **`ContactService` is cited as a constructor-injected, DTO-input service style, but the actual file is the opposite.**  
   The spec tells implementers to mirror `ContactService` for "constructor injection, DTO inputs" at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:46`. Actual `ContactService` has no constructor at `apps/api/app/Modules/Contact/Application/Services/ContactService.php:11-20`, uses `array<string, mixed>` inputs at `apps/api/app/Modules/Contact/Application/Services/ContactService.php:16-28`, and uses scalar parameters in `linkToParty()` at `apps/api/app/Modules/Contact/Application/Services/ContactService.php:41-47`. This conflicts with the spec's own `CustomerContactService` constructor-injection contract at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:137-145` and with `CLAUDE.md` constructor-injection/strict-typing rules at `CLAUDE.md:32-40` and `CLAUDE.md:66-69`. Fix by replacing this citation with a real constructor-injected, DTO-oriented service example, or explicitly state that `ContactService` is legacy shape and must not be mirrored for DI/DTO style.

2. **The test plan does not prove the spec's own tenant/company isolation contract for all mutators.**  
   The checklist requires cross-tenant `attach` / `changeRole` / `detach` to resolve nothing and return 404 at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:255`, and the service contract says every method must assert current tenant/company via `CompanyContext::requireCompany()` at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:163`. The listed isolation test only covers `cross-tenant attach -> 404` at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:241`. This gap matters because both `Partner` and `Contact` are company-scoped (`company_id` is documented at `apps/api/app/Modules/Partner/Domain/Partner.php:29-30` and `apps/api/app/Modules/Contact/Domain/Contact.php:25-26`), and `CompanyContext::requireCompany()` is the intended source at `apps/api/app/Modules/Company/Services/CompanyContext.php:99-108`. Add explicit feature tests for `changeRole`, `setPrimary`, `detach`, and `listForPartner` where the `customer_contacts` row belongs to a different company/tenant context and must be invisible.

### P2
1. **The middleware contract omits the current Partner route group's tenant-claim guard.**  
   The spec says endpoints are behind `['api', 'auth:sanctum', SetPermissionsTeam::class]` at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:177`. Existing Partner routes are actually mounted with `['api', 'auth:sanctum', SetPermissionsTeam::class, EnforceTokenTenantClaim::class]` at `apps/api/app/Modules/Partner/routes.php:19`, with the middleware imported at `apps/api/app/Modules/Partner/routes.php:5-6`. The minimal trio matches `CLAUDE.md` at `CLAUDE.md:61-63`, but this spec should say to add the new routes inside the existing Partner route group so `EnforceTokenTenantClaim` is retained.

2. **The enum helper wording is internally imprecise: `label()` does not mirror `CustomerCategory`.**  
   The spec requires `label(): string` and `values()` "mirroring `CustomerCategory`" at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:113`. `CustomerCategory` only has `values()` at `apps/api/app/Modules/Partner/Domain/Enums/CustomerCategory.php:15-18`; it has no `label()` method at `apps/api/app/Modules/Partner/Domain/Enums/CustomerCategory.php:7-19`. If a label method is desired, point to an enum that actually has both methods, such as `PaymentTerms::label()` and `PaymentTerms::values()` at `apps/api/app/Modules/Partner/Domain/Enums/PaymentTerms.php:16-50` or `ConsolidationFrequency` at `apps/api/app/Modules/Partner/Domain/Enums/ConsolidationFrequency.php:12-26`.

3. **Some code paths in the spec are written from the parent monorepo root, not the stated working root.**  
   The review target states the working root is `/Users/houssamr/Projects/syneriva/apps/erp`, and from that root the production files are under `apps/api/...` as verified by `apps/api/app/Modules/Partner/Domain/Partner.php:5`. The §2 citations use `apps/erp/apps/api/...` at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:39-46`, which does not exist relative to the working root. This is a documentation precision issue, not a design issue; normalize the implementation spec paths to `apps/api/...` or explicitly say they are relative to `/Users/houssamr/Projects/syneriva`.

4. **The reading-order reference to module-local Partner conventions points at a missing file.**  
   The spec says to read `apps/erp/apps/api/app/Modules/Partner/.claude` at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:281`. The Partner module contains `Application`, `Domain`, `Infrastructure`, `Presentation`, `PartnerServiceProvider.php`, and `routes.php`, but no `.claude` file; the available module file layout is reflected by `apps/api/app/Modules/Partner/routes.php:1` and `apps/api/app/Modules/Partner/PartnerServiceProvider.php` existing in that directory. Either add the missing conventions file in the co-merge set or remove the reference.

### SUGGESTION
1. **Clarify the expected concurrent `setPrimary` outcome.**  
   The spec correctly mirrors the existing primary invariant: `party_contacts` uses a PG partial unique index guarded by `DB::getDriverName() === 'pgsql'` at `apps/api/database/migrations/2026_03_10_100002_create_party_contacts_table.php:37-42`, and the proposed `customer_contacts` table repeats that pattern at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:96-97`. The concurrent-promotion test at `docs/superpowers/specs/2026-05-24-t11-impl-a-customer-model.md:254` should specify whether one contender may fail with a handled 409/422 or whether the service must retry so both calls return successfully. Either result can preserve "exactly one primary"; the desired API behavior should be explicit.

2. **Warn implementers not to treat `Contact::parties()` as the complete role-flag projection.**  
   `Partner::contacts()` includes `is_invoice_contact` and `is_delivery_contact` in its pivot fields at `apps/api/app/Modules/Partner/Domain/Partner.php:365-367`, but `Contact::parties()` only includes `job_title`, `department`, `is_primary`, `start_date`, and `end_date` at `apps/api/app/Modules/Contact/Domain/Contact.php:116-120`. This does not undermine the new `customer_contacts` design, but it is a useful footnote if tests or DTOs inspect the Contact-side legacy relationship.

Not ready yet. The data model, table placement, no-cross-DB-FK posture, additive coexistence with `party_contacts`, and `CustomerContactRole` direction are all implementable as written.

Then clean up the P2 documentation issues so route placement, enum helper patterns, and file paths are unambiguous.
