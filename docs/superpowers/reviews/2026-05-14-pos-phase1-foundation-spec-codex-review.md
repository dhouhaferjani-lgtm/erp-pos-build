# Adversarial review — POS Phase 1 Foundation Spec
**Reviewer:** Codex
**Review date:** 2026-05-14
**Spec reviewed:** `/Users/houssamr/Projects/syneriva/apps/erp/docs/superpowers/specs/2026-05-14-pos-phase1-foundation-spec.md`
**Verdict:** BLOCK
**Total findings:** 3 BLOCKER, 3 P1, 3 P2, 0 P3

## Executive summary
- The spec covers the corrected roadmap's Phase 1 scope on paper, including durability and `Payment.origin` / `Payment.fiscal_event_id`, but it is not buildable as written.
- The Treasury `Payment` writer inventory is still incomplete. This is the exact recurring class of false codebase claim the prompt calls out.
- The spec has an unresolved structural fork: `SALE_RECEIPT` is a Phase 1 `fiscal_events` event, but receipt authoring is still described as reused `receiptService.ts`, with a separate receipt chain and separate sync route.
- The new fiscal-event outbox and the reused `/pos/receipts/sync` path are not composed. Implementers cannot tell which server path persists the authoritative `SALE_RECEIPT` fiscal event.
- Several items are fixable before writing-plans: atomic idempotency, the chain verifier scope, PostgreSQL immutability trigger mechanics, preflight targeting, and company-integrity emission semantics.

## Grounding fidelity
The spec is directionally faithful to source-of-truth v3's 15 locked decisions: it names device authority, server verify-only, canonical bytes, signature lifecycle, per-class exceptions, chain recovery, durability, company-integrity record types, and Tunisia/Phase 2+ exclusions (`spec:21-47,75-209,287-424`). It also enumerates the corrected roadmap v2 Phase 1 items (`roadmap v2:28-44`) and does not intentionally pull customer mirror, `ACCOUNT_PAYMENT`, `ACCOUNT_CHARGE`, approval, deposits, AML, or store credit into Phase 1.

The failure is not missing topics. The failure is composition. Source-of-truth v3 requires **one fiscal pattern** and says the existing receipt chain is rebuilt clean with `SALE_RECEIPT` as a first-class fiscal event (`source-of-truth:13-19,59-65,216-226,257`). The spec simultaneously says `FiscalEventEngine.append()` is the only way a fiscal event is authored (`spec:287-305`), says the fiscal-event chain is separate from the receipt chain (`spec:307-310`), and classifies existing receipt authoring/sealing as REUSE with only one addition, `canonical_bytes` (`spec:449-465`). That is not one buildable pattern yet.

The spec is also not faithful to roadmap v2's corrected `Payment` requirement. Roadmap v2 explicitly moved `Payment.origin` / `Payment.fiscal_event_id` to Phase 1 and says **every existing Treasury `Payment` writer** must be updated, listing three writers as examples (`roadmap v2:43-44`). The real code has more writers.

## Findings
### [BLOCKER] Treasury `Payment` writer inventory is still incomplete
**Dimension:** codebase-claim
**Spec location:** §13 writer updates and §16.2 tests (`spec:435-439,498`)
**Evidence:** The spec lists only `ReceiptPaymentService`, `PaymentController::store()`, and `PaymentController::storeMultiple()`. Actual Treasury `Payment::create()` calls also exist in `MultiPaymentService` (`apps/api/app/Modules/Treasury/Domain/Services/MultiPaymentService.php:61-76,133-148,273-285`), `PaymentRefundService` (`apps/api/app/Modules/Treasury/Domain/Services/PaymentRefundService.php:68-84,153-169,436-445`), and `VendorRefundService` (`apps/api/app/Modules/Treasury/Domain/Services/VendorRefundService.php:99-112`).
**Issue:** §13 says "all in the same change" but omits several production writers. This is not a minor naming miss; it means the migration/model change will not be consistently applied to the table's actual write surface.
**Impact:** Phase 1 would ship `payments.origin` with incomplete coverage, producing rows with NULL or default origin from real business flows. Any later reconciliation/reporting based on origin would be untrustworthy from day one, and tests would falsely pass because they cover only three writers.
**Suggested fix:** Replace §13's writer list with an exhaustive inventory from `rg "Payment::create\\(|new Payment\\(|->payments\\(\\)->create\\("` and define expected `PaymentOrigin` for each: POS receipt payments = `pos`; PaymentController and MultiPayment web/admin flows = `web_admin`; refunds inherit or explicitly classify as `web_admin` / `pos` based on original payment and caller; vendor refunds likely `web_admin`; billing-module `App\Modules\Billing\Domain\Payment` is excluded because it is not Treasury `Payment`. Add tests for every Treasury writer.

### [BLOCKER] `SALE_RECEIPT` has two unresolved authoring/sealing paths
**Dimension:** buildability
**Spec location:** §6.1, §6.2, §14, Appendix A (`spec:287-310,449-465,520-526`)
**Evidence:** Source-of-truth v3 requires one pattern and says rebuilt receipts make `SALE_RECEIPT` a first-class fiscal event (`source-of-truth:13-19,59-65,257`). The spec says `FiscalEventEngine.append()` is the only way a fiscal event is authored (`spec:305`) and Appendix A says `SALE_RECEIPT` is implemented in Phase 1 (`spec:522`). But §14 says existing `receiptService.ts`, `terminal_state`, and `offline_receipts` authoring/sealing are REUSE with only one addition, `canonical_bytes` (`spec:451`). Actual `receiptService.ts` computes the receipt hash, inserts `offline_receipts`, advances `terminal_state.last_hash/hash_sequence`, and updates vouchers in one transaction (`apps/pos/src/lib/offline/receiptService.ts:330-599`).
**Issue:** The spec does not say whether `receiptService.ts` calls `FiscalEventEngine.append(SALE_RECEIPT)`, whether `append()` wraps receipt insertion, or whether the old receipt path keeps sealing alongside the new fiscal-event path. §6.2 makes this worse by saying the fiscal-event chain is separate from the receipt chain (`spec:307-310`), which conflicts with `SALE_RECEIPT` being the rebuilt receipt chain's fiscal event.
**Impact:** An implementer cannot build Phase 1 without inventing the central integration decision. The result could be two local chains for one sale, duplicated sequence authorities, or a `SALE_RECEIPT` fiscal event that is only a shadow of the real receipt rather than the source of truth.
**Suggested fix:** Make one explicit design choice. Recommended: `receiptService.ts` becomes a business-document assembler that calls `FiscalEventEngine.append({ type: SALE_RECEIPT, reference_document_id: offline_receipts.id, payload })` inside the same SQLite transaction that inserts `offline_receipts` and voucher balance updates. The `fiscal_events` row's `sequence_number/current_hash` becomes the authoritative chain; receipt columns either mirror the fiscal event hash/sequence for compatibility or are deprecated with an explicit mapping. Remove "separate from the receipt chain" or narrow it to "separate columns during migration only, with SALE_RECEIPT as the authoritative chain."

### [BLOCKER] Receipt sync and fiscal-event outbox are two competing ingestion paths
**Dimension:** consistency
**Spec location:** §7.1, §14 (`spec:321-345,451-459`)
**Evidence:** The spec creates `POST /api/pos/sync/fiscal-events` handled by `OutboxIngestor`, distinct from `/pos/receipts/sync` (`spec:321-323`). It also classifies `ReceiptSyncService` batch orchestration, stock/voucher/payment logic as REUSE (`spec:452`) and only reworks the hash-mismatch branch (`spec:456`). Current client code posts receipts to `/pos/receipts/sync` (`apps/pos/src/lib/sync/syncService.ts:333-336`), and current server receipt sync is a single transaction around receipt, terminal lock, finalization, payments, stock, and voucher work (`apps/api/app/Modules/POS/Application/Services/ReceiptSyncService.php:189-195,612-630`).
**Issue:** For a rebuilt `SALE_RECEIPT`, the spec does not say which endpoint owns ingestion of the authoritative fiscal event. If receipts keep `/pos/receipts/sync`, they bypass `OutboxIngestor` unless `ReceiptSyncService` internally delegates. If receipts also post to `/api/pos/sync/fiscal-events`, there are two server paths capable of writing fiscal facts.
**Impact:** This breaks the "one fiscal pattern" guarantee and creates a high-risk duplicate/idempotency problem: the same sale could be mirrored once as a receipt sync side effect and once as a fiscal-event outbox event, or worse, only the business receipt syncs and the fiscal event remains unsynced.
**Suggested fix:** Define the sync composition. Recommended: the device sends `SALE_RECEIPT` through the fiscal-event outbox endpoint; `OutboxIngestor` verifies/stores `fiscal_events` first and then invokes a renamed receipt business projection/service for stock, voucher, `pos_receipts`, and Treasury effects idempotently. If `/pos/receipts/sync` remains for compatibility, it must be a thin adapter that constructs the same fiscal-event envelope and delegates to `OutboxIngestor`; it must not write fiscal truth itself.

### [P1] `payments.fiscal_event_id` is declared Phase 1 but intentionally left NULL during Phase 1
**Dimension:** grounding
**Spec location:** §13 (`spec:432-440`)
**Evidence:** Roadmap v2 moved `Payment.origin` / `Payment.fiscal_event_id` to Phase 1 because the receipt-chain rebuild makes `SALE_RECEIPT` fiscal events foundational and existing POS sale payments need origin / fiscal-event attribution from day one (`roadmap v2:43-44`). Source-of-truth v3 says rebuilt receipts are first-class `SALE_RECEIPT` fiscal events and the first go-live slice includes the rebuilt receipt chain (`source-of-truth:64,257,290`). The spec says `fiscal_event_id` stays NULL in Phase 1 and Phase 2 is the first writer to set it (`spec:440`).
**Issue:** This contradicts the corrected roadmap and the `SALE_RECEIPT` design. If Phase 1 creates fiscal events for sales and also creates Treasury `Payment` rows for POS receipt payments, those payment rows have an in-scope fiscal event to reference.
**Impact:** Phase 1 sale payments will not be traceable back to their fiscal event, forcing a later backfill over immutable/audit-sensitive data or leaving POS sale payments permanently weaker than Phase 2 account payments.
**Suggested fix:** Set `fiscal_event_id` for POS receipt payments in Phase 1 when the `SALE_RECEIPT` fiscal event is created. Non-fiscal web/admin flows can keep it NULL, but `ReceiptPaymentService` and any server-side receipt projection from `SALE_RECEIPT` must attach the event id.

### [P1] Query-first server idempotency is still racy under concurrent inserts
**Dimension:** buildability
**Spec location:** §7.2 (`spec:325-345`)
**Evidence:** The spec says `OutboxIngestor` does `SELECT` by `(terminal_id, sequence_number)` and then `INSERT`, and claims the unique-violation transaction-abort problem "does not apply" (`spec:327-345`). PostgreSQL's `INSERT ... ON CONFLICT` docs state the conflict clause is the mechanism for specifying an alternative action to a unique/exclusion violation ([PostgreSQL INSERT docs](https://www.postgresql.org/docs/current/sql-insert.html)). A prior `SELECT` does not serialize two concurrent transactions that both miss the row.
**Issue:** Two concurrent deliveries of the same fiscal event can both pass the query-first check. One insert wins; the other hits the unique constraint. In a standalone transaction, that may not poison a larger business transaction, but it still returns an error instead of idempotent success unless explicitly handled.
**Impact:** Retry storms, double-clicks, or parallel sync workers can turn valid duplicate deliveries into failed sync results. That violates the spec's own "idempotent success" contract and can leave device rows stuck in failed/pending states.
**Suggested fix:** Use an atomic idempotency primitive: `INSERT ... ON CONFLICT (tenant_id, terminal_id, sequence_number) DO NOTHING RETURNING id`, then select and return the existing row if no row was inserted; or acquire an advisory/row lock keyed by `(tenant_id, terminal_id)` before the select/insert. Tests must simulate concurrent duplicate ingestion.

### [P1] `fiscal:verify-event-chain` is a CI gate but parked as an open item
**Dimension:** completeness
**Spec location:** §16.4 and §17 (`spec:506-515`)
**Evidence:** §16.4 says `php artisan fiscal:verify-event-chain --terminal=...` is a CI gate (`spec:506-507`). §17 lists the same command as an open item (`spec:515`). The only existing command is `pos:verify-chains`, covering receipt and Z-report chains (`apps/api/app/Modules/POS/Commands/VerifyPosChainCommand.php:30-38`).
**Issue:** A required CI gate cannot be parked as an open item. If Phase 1 creates a new authoritative chain, its verifier is part of the deliverable, not optional follow-up.
**Impact:** Writing-plans can omit the verifier or leave CI dependent on a command that does not exist. That defeats a core Phase 1 acceptance test: re-hashing stored canonical bytes and locating the break point.
**Suggested fix:** Move `fiscal:verify-event-chain` from §17 to explicit Phase 1 scope/migration/testing deliverables. Define command signature, terminal/company filters, exit codes, and fixtures. Keep only Z-report rebuild as an open item.

### [P2] PostgreSQL immutability trigger mechanics are underspecified
**Dimension:** buildability
**Spec location:** §3.2 (`spec:201-204`)
**Evidence:** The spec says forbidden updates are excluded by a "column-scoped allow-list" (`spec:201-204`). PostgreSQL column-specific `UPDATE OF` triggers fire when listed columns are targets of an update, not when all other columns are excluded ([PostgreSQL CREATE TRIGGER docs](https://www.postgresql.org/docs/current/sql-createtrigger.html)). Existing receipt immutability is implemented by an unqualified trigger function with explicit OLD/NEW comparisons and state-transition checks (`apps/api/database/migrations/2026_01_08_190637_create_pos_receipts_table.php:143-186`; `apps/api/database/migrations/2026_05_01_000003_update_pos_receipts_immutability_trigger_for_pending_seal.php:30-73`).
**Issue:** The trigger design is conceptually right but not precise enough to implement safely. It also does not state "payload written once" and integrity transition rules as OLD/NEW state constraints.
**Impact:** Implementers may create an update trigger that either blocks legitimate ingestor writes (`payload`, `integrity_status`) or accidentally permits mutation of immutable fiscal columns.
**Suggested fix:** Specify the actual PostgreSQL mechanism: an unqualified `BEFORE UPDATE` trigger that compares OLD/NEW and raises unless only allowed columns changed; explicit state machine checks for `payload_parse_status` (`NULL/parsed` write-once, `failed` handling), `integrity_status` (`verified -> quarantined`, `quarantined -> verified/resolved` only through resolver), plus separate `BEFORE DELETE`, `BEFORE TRUNCATE`, and `REVOKE TRUNCATE`.

### [P2] Preflight gate targets `offline_receipts` as if it were in tenant PostgreSQL
**Dimension:** completeness
**Spec location:** §2 (`spec:61-67`)
**Evidence:** The preflight says to query every staging and production tenant database for `offline_receipts` (`spec:61-62`). Actual `offline_receipts` is a Tauri SQLite table created in the POS local schema (`apps/pos/src/lib/db/migrations.ts:88-122`), not a server tenant PostgreSQL table. The server sync route stores synced receipts into `pos_receipts` via `ReceiptSyncService`, while local pending rows remain on devices.
**Issue:** The operational gate is not executable as written. A PostgreSQL tenant DB query cannot prove that deployed terminals have no unsynced local `offline_receipts`.
**Impact:** The owner sign-off can falsely conclude the system is empty while a terminal has pending local fiscal rows. That would invalidate the no-migration clean rebuild precondition.
**Suggested fix:** Split the gate: server-side queries for `pos_receipts`, `pos_z_reports`, terminal chain state, print records; device-side inventory for any installed Tauri SQLite stores, including `offline_receipts`, `terminal_state`, `z_reports`, and pending sync rows. If no deployed terminals exist, record that operational fact explicitly with owner sign-off.

### [P2] Company-integrity records are "implemented" without an emission rule
**Dimension:** new-issue
**Spec location:** §11 and Appendix A (`spec:401-409,520-526`)
**Evidence:** Source-of-truth v3 says `TERMINAL_REGISTRY_SNAPSHOT` and `COMPANY_DAY_CLOSURE_MANIFEST` are first-slice engine-level structures, populated as terminals/closures come online (`source-of-truth:168-177,301`). The spec says Phase 1 delivers event types, payload DTOs, and "their place in the chain," but active population jobs are downstream (`spec:403-408`), while Appendix A says these types are "Implemented in Phase 1" (`spec:522`).
**Issue:** An event type can be reserved without being emitted, but "implemented" and "place in the chain" imply an append handler and at least one emission rule. For `TERMINAL_REGISTRY_SNAPSHOT`, there is no closure dependency, so deferring all population is not obviously justified.
**Impact:** Implementers may either overbuild downstream jobs in Phase 1 or underbuild the event types as inert enum values with no handler. Auditors later cannot rely on company-integrity completeness if no first snapshot is emitted.
**Suggested fix:** Clarify Phase 1 semantics: either "reserved + DTO schema only; `append()` throws until the downstream job phase" or "implemented handler plus initial/manual `TERMINAL_REGISTRY_SNAPSHOT` emission; `COMPANY_DAY_CLOSURE_MANIFEST` handler reserved until closure rollout." Make Appendix A match that decision.
