## 2. NEW findings

### MAJOR

#### N-r4-1 — The new terminal-location authority is anchored only on `claim()`; two self-service endpoints let any `pos.operate_terminal` holder obtain a terminal **at another branch** without forging anything, and no acceptance row covers it. CONFIRMED.

Spec 195 anchors enrollment on one gate: "Enrollment must preserve the existing `pos.operate_terminal` claim gate (`TerminalController.php:372`) and add allowed persisted-location custody plus proof issuance through the existing authorized claim/registration flow."

CONFIRMED at HEAD, there are three terminal-acquisition surfaces, not one, and two of them **create or hand back a terminal at a caller-chosen location**:
- `POST /pos/terminals/request` — `TerminalController::requestTerminal()` at `:686` `Gate::authorize('pos.operate_terminal')`, then creates a terminal at `$data['location_id']` after only a `locationHasPosEnabled(..., $company->id)` check (`:694`); route `app/Modules/POS/routes.php:58`.
- `POST /pos/terminals/web` — `getOrCreateWebTerminal()` at `:753` `Gate::authorize('pos.operate_terminal')`, validates `'location_id' => ['required','uuid', ScopedExists::company('locations', $company->id)]` (`:764`) — **company scope only, no caller-location membership** — then returns the existing web terminal for that location or creates one with `'location_id' => $locationId` (`:801`); route `routes.php:60`.
- `POST /pos/terminals` — `store()` at `:111` under `pos.manage_terminals`, same company-only location validation (`:118`, `:134`).

`pos.operate_terminal` is a **cashier** permission (`RolesAndPermissionsSeeder.php:687`, cashier block; also manager `:620`).

Failure scenario (no forgery, so every acceptance row at 227–228 still passes): a restricted branch-A cashier calls `POST /pos/terminals/web` with branch-B's `location_id`. It is B's own company, POS-enabled, so the request succeeds and returns a terminal whose persisted `location_id` is B. The cashier's device then completes the *legitimate* new flow — bind session, obtain proof, request tender config — and the server, obeying spec 195 exactly ("derive terminal location server-side from the claimed terminal record's persisted `location_id`"), returns **branch B's destination bindings** and accepts A-authored tender legs bound to B custody. The authority is honest; the input to it is operator-chosen. This is the same cross-branch custody misattribution B-r3-1 was raised to close, re-entered through provisioning instead of through a forged `terminal_id`. Row 228 tests "bound branch-A terminal requests B configuration" — but here the terminal legitimately *is* a B terminal.

Minimum correction (spec, ~2 sentences + 1 acceptance row):
1. In 195, name **all** enrollment surfaces — `TerminalController::claim()` (`:372`), `requestTerminal()` (`:686`) and `getOrCreateWebTerminal()` (`:753`), plus `store()` (`:111`) — and state that each must additionally require the caller's **allowed-location custody** over the target `location_id` (today only `ScopedExists::company` / `locationHasPosEnabled` apply, `:694`, `:764`), and that relocation of an existing terminal requires the same custody over both old and new location.
2. Add to the 223–228 table: "Branch-A operator requests or web-provisions a terminal at branch B's location: denied; no B terminal is created or returned, no B destination IDs/labels are projected, and an existing B web terminal is not handed back."

### MINOR

#### n-r4-1 — "blocked `fiscal_event_projections` row" has no state on the existing table, and the spec does not say whether it is a new enum case.
Spec 288 requires persisting a **blocked** row on the existing `fiscal_event_projections` table (and 96 requires the UI to distinguish "received, pending, blocked and applied"), but `apps/api/app/Modules/Fiscal/Domain/Enums/ProjectionStatus.php:9–12` has exactly `pending`, `running`, `applied`, `dead_lettered`. The spec's W4 seams (270) mention "fiscal projection schema if a policy snapshot is required" but never `ProjectionStatus`. An implementer choosing `pending` makes unresolved work indistinguishable from work merely waiting and feeds it into the retry selector at `RetryFiscalProjectionsCommand.php:299–307` (`dead_lettered` OR `pending` with `attempts >= EXHAUSTED_ATTEMPTS`) forever; choosing `dead_lettered` conflates configuration uncertainty with delivery exhaustion. Name `ProjectionStatus.php:9–12`, state that `blocked` is a new enum case (rule 9), and state its retry/census selection semantics.
