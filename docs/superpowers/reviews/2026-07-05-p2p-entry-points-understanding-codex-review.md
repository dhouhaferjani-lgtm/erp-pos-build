## Verified design claims

Note: neither is declared with a foreign key in this migration.
- Receipt-line column names match the design's ledger basis: `received_unit_price`, `landed_unit_cost`, `accrual_unit_cost`, `movement_id`, `quantity_invoiced`, and Wave 6/8 `free_quantity_invoiced` exist (`apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:44`, `apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:46`, `apps/api/database/migrations/tenant/2026_07_04_120000_add_free_quantity_invoiced_to_goods_receipt_lines.php:14`).
- `procurement_policies` currently has `bill_control_mode`, `match_mode`, `match_enforcement`, tolerances, and a nullable Wave 9 `preset`; it does not yet have `allow_receipt_first`, `allow_invoice_first`, or `invoice_first_requires_approval` (`apps/api/database/migrations/tenant/2026_06_25_100000_create_procurement_policies_table.php:34`, `apps/api/database/migrations/tenant/2026_07_05_090000_add_preset_to_procurement_policies.php:14`).
- `GoodsReceiptService::receiveGoods` requires a `Document` PO, quantity maps, optional batch/free/received-price maps, reason, and actor; it rejects non-POs and non-confirmed POs (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:59`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:68`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:72`).
- `receiveGoods` opens a transaction, pre-acquires sorted `ProductCostLock` locks, creates a posted `GoodsReceipt`, numbers it with `generateForKey('goods_receipt', 'GRN')`, writes lines, updates PO counters, and leaves partial POs `confirmed` (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:76`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:103`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:112`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:118`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:365`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:402`).
- Wave 8 `source_document_ids` exists in supplier invoice creation and is persisted in `payload->supplier_invoice->source_document_ids`, with `source_document_id` kept as the first PO (`apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:57`, `apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:113`, `apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:129`).
- `SupplierInvoiceMatcher` uses receipt-line windows when receipt lines exist, and price basis switches to PO unit price in two-way mode or receipt-plan basis/snapshot in three-way mode (`apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:151`, `apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:544`, `apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:548`, `apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:552`).
- `DocumentNumberingService::generateForKey` locks/creates a `DocumentSequence`, increments `last_number`, and returns `PREFIX-YEAR-NNNN` (`apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:29`, `apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:44`, `apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:63`).
- Enum claims are accurate: `DocumentStatus` has Draft/Confirmed/Posted/Paid/Received/Cancelled and `isEditable()` returns true for Draft and Confirmed; `GoodsReceiptStatus` has Draft/Posted/Cancelled; `DocumentType` has no GoodsReceipt case (`apps/api/app/Modules/Document/Domain/Enums/DocumentStatus.php:9`, `apps/api/app/Modules/Document/Domain/Enums/DocumentStatus.php:19`, `apps/api/app/Modules/Inventory/Domain/Enums/GoodsReceiptStatus.php:9`, `apps/api/app/Modules/Document/Domain/Enums/DocumentType.php:9`).

## Findings

### BLOCKER — Current receipt posting is not atomic with 408 accrual

The design invariant says implicit rows are created in the same transaction and includes "stock + 408 accrual". Current code does not guarantee that. `receiveGoods` creates stock movements and receipt lines in its transaction, then emits `GoodsReceived` (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:276`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:287`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:315`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:326`). Accounting subscribes via `PostGrIrOnGoodsReceipt` (`apps/api/app/Providers/EventServiceProvider.php:117`), but that listener catches all throwables and explicitly does not block the receipt (`apps/api/app/Modules/Accounting/Listeners/PostGrIrOnGoodsReceipt.php:41`, `apps/api/app/Modules/Accounting/Listeners/PostGrIrOnGoodsReceipt.php:42`). The GR-IR method creates a draft journal entry, then posts via an after-commit path when inside a transaction (`apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:1086`, `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:1141`, `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:100`).

What the spec must say: either make GR-IR accrual fail-closed and in-transaction for these flows, or explicitly weaken the invariant and define reconciliation/retry/blocked-posting behavior when stock exists without 408.

### BLOCKER — Confirmed/partially received POs are still editable and can break receipt ledger references

`DocumentStatus::Confirmed` is editable (`apps/api/app/Modules/Document/Domain/Enums/DocumentStatus.php:21`). `Document::isEditable()` delegates to status (`apps/api/app/Modules/Document/Domain/Document.php:574`). `PurchaseOrderController::update` accepts any editable PO and deletes/replaces lines when `lines` are provided (`apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:448`, `apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:480`). Partial receipts leave the PO status as `confirmed` (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:402`). Meanwhile `goods_receipt_lines.po_line_id` is a bare UUID, not an FK (`apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:39`).

This means a partially received PO can remain editable and its referenced PO lines can be deleted/replaced, orphaning receipt-ledger rows and breaking matcher/posting assumptions.

What the spec must say: before adding `revert()` or draft receipts, centralize PO edit guards: once any paid/free receipt exists, PO line mutation must be blocked or constrained to safe fields. Also consider adding real FKs or explicit immutable line IDs.

### BLOCKER — "Parked standalone Draft SI" is not supported by the current request/matcher model

The invoice-first/not-yet-delivered path says save a standalone Draft SI and later relink. Current creation requires `source_document_ids` with `min:1` and each line requires `source_line_id` (`apps/api/app/Modules/Procurement/Presentation/Requests/CreateSupplierInvoiceRequest.php:78`, `apps/api/app/Modules/Procurement/Presentation/Requests/CreateSupplierInvoiceRequest.php:91`). Cross-field validation requires every source document be a PO and every source line belong to one of those POs (`apps/api/app/Modules/Procurement/Presentation/Requests/CreateSupplierInvoiceRequest.php:151`, `apps/api/app/Modules/Procurement/Presentation/Requests/CreateSupplierInvoiceRequest.php:212`). The matcher treats null source lines as hard exceptions for posting (`apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:205`, `apps/api/app/Modules/Procurement/Application/SupplierInvoiceMatcher.php:207`).

`procurement:rematch-drafts` does not perform discovery/relinking. It scans Draft supplier invoices, refreshes `price_match_basis`, `matched_receipt_line_id`, and `match_status`, and saves those fields (`apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:45`, `apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:77`, `apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:85`, `apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:112`).

What the spec must say: define a new parked-invoice linkage model and user/command matching algorithm. Do not claim `procurement:rematch-drafts` covers parked standalone invoices unless it is expanded to select POs/receipt lines and rewrite `source_document_ids`/`source_line_id`.

### MAJOR — Receipt BL identity columns are absent and the migration hazard is underspecified

The design proposes `goods_receipts.external_reference` and `external_date`. Current `goods_receipts` has no such columns (`apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:14`). The model fillable/casts also omit them (`apps/api/app/Modules/Inventory/Domain/GoodsReceipt.php:47`, `apps/api/app/Modules/Inventory/Domain/GoodsReceipt.php:62`). Only `documents.external_document_number/date` exist in current document code (`apps/api/app/Modules/Document/Domain/Document.php:71`, `apps/api/app/Modules/Document/Domain/Document.php:151`).

What the spec must say: exact column names, nullability/backfill for existing receipts, uniqueness expectations per supplier/company if any, and how the receipt-line invoice picker surfaces BL number/date.

### MAJOR — Auto-PO hiding is not a local list tweak; current consumers will expose or act on auto-POs

Current PO list API has no auto-generated filter; it starts with all `DocumentType::PurchaseOrder` rows and applies generic filters (`apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:221`, `apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:225`). The React document list fetches `/purchase-orders` with only search/status/page params (`apps/web/src/features/documents/DocumentListPage.tsx:147`, `apps/web/src/features/documents/DocumentListPage.tsx:156`). The goods receipt workbench also queries `/purchase-orders` by status and filters client-side (`apps/web/src/features/purchases/GoodsReceiptListPage.tsx:121`, `apps/web/src/features/purchases/GoodsReceiptListPage.tsx:125`, `apps/web/src/features/purchases/GoodsReceiptListPage.tsx:137`).

Other consumers also treat every PO as normal: detail page enables receipt, SI creation, payments, print/email paths (`apps/web/src/features/documents/purchase-orders/PurchaseOrderDetailPage.tsx:131`, `apps/web/src/features/documents/purchase-orders/PurchaseOrderDetailPage.tsx:134`, `apps/web/src/features/documents/purchase-orders/PurchaseOrderDetailPage.tsx:636`); action bar enables receive/SI/payment based on type/status only (`apps/web/src/features/documents/components/DocumentActionBar.tsx:114`, `apps/web/src/features/documents/components/DocumentActionBar.tsx:119`, `apps/web/src/features/documents/components/DocumentActionBar.tsx:124`); related-doc chain includes payload-linked supplier invoices and ordinary descendants (`apps/api/app/Modules/Document/Domain/Document.php:369`, `apps/api/app/Modules/Document/Domain/Document.php:457`, `apps/api/app/Modules/Document/Presentation/Controllers/DocumentController.php:222`).

What the spec must say: exact provenance flag schema, default API filtering semantics, `include_auto_generated`/`show_auto_generated` behavior, and which consumers hide, label, or include auto-POs for audit.

### MAJOR — Policy defaults and route gates are currently fail-open/misaligned with the proposed controls

Missing policy rows resolve to an in-memory default `Standard` policy, not a fail-closed entry-point policy (`apps/api/app/Modules/Procurement/Application/ProcurementPolicyResolver.php:26`, `apps/api/app/Modules/Procurement/Application/ProcurementPolicyResolver.php:40`). Current defaults are vertical-based, not country-based (`apps/api/app/Modules/Procurement/Domain/ProcurementPolicy.php:90`, `apps/api/app/Modules/Procurement/Domain/ProcurementPolicy.php:106`). Current presets only set bill control, match mode, and enforcement (`apps/api/app/Modules/Procurement/Domain/Enums/ProcurementPreset.php:20`, `apps/api/app/Modules/Procurement/Domain/Enums/ProcurementPreset.php:48`). Supplier invoice routes use broad `documents.update`, not the proposed dedicated permissions (`apps/api/app/Modules/Procurement/Presentation/routes.php:95`, `apps/api/app/Modules/Procurement/Presentation/routes.php:106`).

What the spec must say: missing-row behavior for entry-point toggles, whether defaulting is country-derived or vertical-derived, migration/backfill for existing rows, and concrete route/service permission names. Entry-point services must fail closed server-side when toggles are absent.

### MAJOR — Draft goods receipts require a real lifecycle split, not only enum reuse

`GoodsReceiptStatus::Draft` exists, but `receiveGoods` only creates `Posted` receipts and immediately writes stock, WAC, receipt lines, and PO counters (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:108`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:118`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:315`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:365`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:402`). There is no current draft-post service in opened code.

GRN numbering happens at receipt-row creation through `generateForKey` (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:112`, `apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:63`). If drafts are numbered on save, abandoned drafts consume visible GRNs; if numbered on post, receipt drafts need a separate display identity.

What the spec must say: draft table invariants, whether draft lines use `goods_receipt_lines` before stock movement IDs exist, when GRN is assigned, and whether draft cancellation preserves or releases numbers.

### MINOR — Auto-PO confirmation event has no app listener, but system actor semantics are undefined

`PurchaseOrderService::confirm` dispatches `PurchaseOrderConfirmed` (`apps/api/app/Modules/Document/Domain/Services/PurchaseOrderService.php:100`, `apps/api/app/Modules/Document/Domain/Services/PurchaseOrderService.php:109`). I found no listener references outside the service/event files in `apps/api/app` using `rg`. Cannot verify global/framework listeners beyond opened code. The service sets `confirmed_by = auth()->id()` and event casts it to string (`apps/api/app/Modules/Document/Domain/Services/PurchaseOrderService.php:76`, `apps/api/app/Modules/Document/Domain/Services/PurchaseOrderService.php:117`).

What the spec must say: auto-PO creation/confirmation must pass an explicit actor/system user and not rely on ambient HTTP auth.

## R1-R7 answers

- R1: PO create in `PurchaseOrderController::store` creates a Draft PO and lines; I did not find a create event there (`apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:319`, `apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:357`, `apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:391`). PO confirm dispatches `PurchaseOrderConfirmed`, and I found no app listener for it with `rg`; cannot verify listeners outside opened worktree files. Risk remains around `confirmed_by` for non-HTTP/system flows.
- R2: Nested transactions are used already: PO confirm opens a transaction, `PurchaseOrderService::confirm` opens another, `receiveGoods` opens another, and SI creation opens another (`apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:619`, `apps/api/app/Modules/Document/Domain/Services/PurchaseOrderService.php:60`, `apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:76`, `apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:60`). `ProductCostLock` is sorted/advisory/xact-scoped (`apps/api/app/Modules/Inventory/Domain/Services/ProductCostLock.php:13`, `apps/api/app/Modules/Inventory/Domain/Services/ProductCostLock.php:40`). Cannot verify end-to-end deadlock freedom for create PO + receipt + SI + optional post in one outer transaction. Spec must define lock order and whether posting is included.
- R3: PO consumers that would show auto-POs include `/purchase-orders` API, document list, goods receipt workbench, PO detail/actions, related-doc chain, receipt-line picker, PDF/email routes by document id, RFQ group award checks if `source_document_id` points to RFQs, and SI chain payload links (`apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:225`, `apps/web/src/features/documents/DocumentListPage.tsx:156`, `apps/web/src/features/purchases/GoodsReceiptListPage.tsx:121`, `apps/web/src/features/documents/components/DocumentActionBar.tsx:114`, `apps/api/app/Modules/Document/Domain/Document.php:376`, `apps/api/app/Modules/Document/Presentation/Controllers/PurchaseOrderController.php:805`).
- R4: GRN numbering is `generateForKey('goods_receipt','GRN')` at current posted receipt creation (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:112`). Current `generateForKey` increments `last_number` in a transaction (`apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:44`, `apps/api/app/Modules/Document/Domain/Services/DocumentNumberingService.php:64`). There is no current draft GR behavior to verify.
- R5: `procurement:rematch-drafts` rewrites only line snapshot fields and invoice `match_status`; it does not discover/link later receipts to unlinked invoices (`apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:77`, `apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:85`, `apps/api/app/Console/Commands/RematchDraftSupplierInvoicesCommand.php:112`).
- R6: Company country exists (`apps/api/app/Modules/Company/Domain/Company.php:41`), but procurement defaults currently use tenant vertical, not country (`apps/api/app/Modules/Procurement/Domain/ProcurementPolicy.php:90`, `apps/api/app/Modules/Procurement/Domain/ProcurementPolicy.php:106`). Cannot verify any country-change/re-pick semantics for procurement presets in opened code.
- R7: Cannot verify `revert()` because I found no implementation. Existing RFQ award logic detects live POs by `source_document_id` (`apps/api/app/Modules/Procurement/Application/PurchaseQuoteRequestAwardService.php:85`). Existing supplier invoices link POs by both `source_document_id` and payload `source_document_ids` (`apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:113`, `apps/api/app/Modules/Procurement/Application/CreateSupplierInvoiceService.php:131`). A future PO revert must account for both RFQ awards and parked/draft SIs.
