## Summary

The api.workshop cluster fix at 148d2703 cleanly closes all 4 inventoried bare-`Partner::query()->find($partnerId)` callsites in `WorkOrderCreationService` (api.workshop.001/002/003/004). Approach is divergent from api.cart / api.service in a load-bearing way and is correct given the constraints: the service is invoked from a non-HTTP code path (Scheduling → AppointmentConversionService → WorkOrderCreationService) where `CompanyContext` is not available. Rather than smuggle CompanyContext into a domain service, the fix changes `WorkOrderCreationServiceInterface::createFromAppointment` to take explicit `string $tenantId, string $companyId` parameters, sourced by the only caller from `appointment.tenant_id` / `appointment.company_id`. Inside the service the four bare Partner::find callsites collapse into one `assertPartnerInScope($partnerId, $tenantId, $companyId)` defensive guard that scopes by both predicates and throws `RuntimeException` with a clear "refusing cross-tenant work order creation" message on miss. `resolveCurrency` is rewritten to use a tenant+company-scoped `Company::query()` chain. `resolveOpenedByUserId` is reduced to a pure tenant-only User lookup (correct — `users` table has no `company_id` column; user-company linkage lives in `user_company_memberships`). 6-test isolation suite is honest — pre-fix re-run returns the exact failure shape the brief predicted (`Unknown named parameter $tenantId` × 4 errors + 2 RuntimeException-mismatch failures, because reverting the interface signature makes the new call sites uncompilable). Two structural-SQL-log invariant tests pin BOTH predicates on the partner-existence guard query and the `tenant_id` predicate on the company lookup, satisfying the Treasury R3 Finding-14 invariant. PHPStan level 8 [OK]; Pint pass; sweep:inventory:verify-history reports `verified 810 event(s) across 268 callsite(s); 0 problem(s).`; POS surface diff `dev..HEAD` is empty.

## Findings

1. **Severity: NICE-TO-HAVE (defense-in-depth gap, pre-existing — NOT a regression introduced by this commit)** — `resolveOpenedByUserId($tenantId)` returns `User::query()->where('tenant_id', $tenantId)->first()` — i.e. the FIRST user in the tenant, regardless of whether that user has a `UserCompanyMembership` row for the supplied `$companyId`. In a multi-company tenant with hostile or mis-shaped data, the resulting WO's `opened_by_user_id` could point at a user who has no real authorization for the WO's company. This is informational rather than authorization-bearing today (the `opened_by_user_id` column is read for display, not for ACLs), so there is no exploitable cross-tenant disclosure. It is a placeholder pattern documented in the code (the controller `AppointmentConversionController::convert` already has the real `(string) $user->id` from `$request->user()->can('scheduling.appointments.convert')` and threads it as `convertedByUserId` into `convertToWorkOrder` — but that argument stops at line 47 of `AppointmentConversionService` and is never propagated to `createFromAppointment`). Folding `convertedByUserId` through to `WorkOrderCreationService` and using it as `opened_by_user_id` (with a `User::query()->where('tenant_id')->whereKey($id)->exists()` scope check) would close this end-to-end. NOT blocking and explicitly out of api.workshop scope — flagging only because the api.workshop fix narrative claims "the partner has been validated above; the user lookup remains tenant-only by design" which is correct but incomplete. The real `convertedByUserId` is already available; the user lookup could use it. Suggested follow-up cluster: api.scheduling (consumer-side change to AppointmentConversionService) + signature extension to WorkOrderCreationServiceInterface. Tracked as a follow-up, not as a request-changes against api.workshop.

## Confidence

High confidence the api.workshop cluster is closed against the Codex Finding-14 invariant for all 4 inventoried callsites. The structural-SQL-log invariant test on the partner-existence guard pins BOTH `tenant_id` AND `company_id` as literal substrings in the captured query — a future regression that drops one of the predicates would fail loudly. The currency lookup test pins `tenant_id`; the matcher-capture mechanism implicitly enforces `id =` is present. Pre-fix bug-reproduction failed all 6 isolation tests with the predicted shape, so the tests genuinely exercise the defect. The interface-signature change is the right design choice for a domain service called from a non-HTTP code path: smuggling CompanyContext into the domain tier would have been a layering violation and would have made the service uncallable from queue workers / event listeners / console commands.

What I could have missed:
- The NICE-TO-HAVE `convertedByUserId` propagation gap (Finding 1) is real but pre-existing and out of api.workshop scope. Folding it in would be a one-line signature change to the interface and a one-line `User::query()->where('tenant_id', $tenantId)->whereKey($convertedByUserId)->exists()` guard — cheap but explicitly out of scope per brief.
- The api.scheduling repository-tier gap (Finding 4) is the only finding I would mark as a real defense-in-depth concern. The current api.workshop fix is structurally protected by `AppointmentConversionController::convert`'s pre-check, so the gap is theoretical (no exploit path today). But the Workshop fix's narrative ("the appointment is already loaded inside its own scope; trusting its columns is correct") is only true while the controller path is the exclusive entry. If a future Section-X cluster lands a queue worker / event listener that calls `AppointmentConversionService::convertToWorkOrder(…)` without an upstream tenant guard, the api.workshop guard will faithfully propagate cross-tenant data into a new WorkOrder. Worth tracking as an api.scheduling cluster invariant ("repository-tier load MUST be tenant-scoped, not just lockForUpdate-scoped").
- I did not run the broader Treasury / POS / Compliance regression sweeps; the in-tree commit message + the empty `dev..HEAD` POS-surface diff give high confidence in no collateral damage. Workshop+Scheduling regression suite (326 tests) passes clean.
- I did not exhaustively audit the ~17 sibling Workshop reads I surfaced in Finding 3 — they are explicitly out of api.workshop scope per brief. Several of them (`EloquentWorkOrderRepository::find($id)` reached via WO route param, the three Technician controllers' `where('id', $X)` chains) look exploitable to me on a hostile-mindset reading, but proper triage requires looking at upstream guards in the routes — that is a follow-up sweep, not this cluster's gate.
- The brief's "8 tests, 18 assertions" claim for `WorkshopTenantIsolationTest.php` is wrong (actual is 6 tests). The "14 / 37 / 0" totals across all 3 affected test files are correct and re-verified. Inventory hygiene win for the orchestrator: keep the per-file counts honest in future briefs.
