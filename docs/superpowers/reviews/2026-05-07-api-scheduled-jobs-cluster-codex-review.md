## Adversarial findings

### BLOCKER: `ReconcileListingsJob` cat-(b) annotation claims a `company_id` guard that does not exist

`apps/api/app/Modules/Marketplace/Infrastructure/Jobs/ReconcileListingsJob.php:18-20` says downstream `Product` and `MarketplaceListing` queries explicitly filter by `seller.company_id`. The `Product` portions do at `apps/api/app/Modules/Marketplace/Infrastructure/Jobs/ReconcileListingsJob.php:39-52`, but the listing update is `MarketplaceListing::where('seller_id', $seller->id)->...->update(...)` at `apps/api/app/Modules/Marketplace/Infrastructure/Jobs/ReconcileListingsJob.php:54-58`. `MarketplaceListing` has no `company_id` property/fillable column at `apps/api/app/Modules/Marketplace/Domain/Models/MarketplaceListing.php:16-70`.

Suggested fix: either correct the annotation so it accurately states that listing writes are anchored by `seller_id` (and explain why the seller UUID/FK is the intended cross-tenant boundary), or harden the code path with an additional tenant/company-derived guard if the data model supports it. Until the annotation matches the implementation, the class-level `@cross-tenant-by-design` justification fails the cluster invariant.

### NICE-TO-HAVE: Architecture helper is not fully recursive for trait composition

`classUsesTrait()` walks parent classes and includes traits directly used by each trait at `apps/api/tests/Architecture/QueueJobTenantContextTest.php:212-228`, but it does not recurse beyond one nested trait level. This does not affect the current implementation, because both cat-(a) jobs directly use `BindsTenantContext` at `apps/api/app/Modules/Import/Application/Jobs/ProcessImportJob.php:37` and `apps/api/app/Modules/Import/Application/Jobs/ProcessProductImageImport.php:34`. For future trait composition, a recursive trait flattener would better match the test comment's defense-in-depth intent.
