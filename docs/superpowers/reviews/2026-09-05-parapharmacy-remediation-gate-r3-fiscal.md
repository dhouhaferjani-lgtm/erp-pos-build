- Source: the receipt path books revenue and VAT **inside the per-leg payment entry**. `TreasuryReceiptBridge.php:1515-1520` calls `GeneralLedgerService::createPOSPaymentEntry(payment, receipt, repository, vatSplit: $resolveVatSplit($index), …)`; that method takes a `PaymentRepository` and throws when it has no GL account (`GeneralLedgerService.php:3908-3919`), writes the tender debit at `:3946-3955` and then `writePosRevenueAndVatLines(… onDebitSide: false, 'POS sales revenue', 'POS output VAT')` at `:3957-3965`. Separately, the voucher side posts `Dr VoucherLiability / Cr PosTenderClearing` (`VoucherRedemptionService.php:45,203`; `GeneralLedgerService.php:2955,2988-2991`) and its offsetting debit is precisely the repository leg the branch would suppress — `ReceiptPaymentService.php:372-385`: *"The receipt payment row + treasury payment + repository GL entry above remain … The voucher repository's GL account should be configured as `PosTenderClearing` in deployment so the two journals net out to Dr VoucherLiability / Cr Revenue"*, and `PosCoreReceiptProjection.php:1620-1625` warns that without that debit you get *"a permanently unmatched PosTenderClearing balance"*. A live TODO records the same coupling as unfinished: `GeneralLedgerService.php:2960-2962` *"Voucher tender rows MUST bypass `createPOSPaymentEntry()` … TODO: wire the bypass in Tasks 22-25 / Task 53"*.
- Failure scenario (fiscal): a 100.000 TND parapharmacy sale settled 60.000 cash + 40.000 LOYALTY. The W2 lane implements spec:165 literally; the loyalty leg returns before repository resolution. GL books 60.000 of revenue and 60% of the output VAT; the sealed `SALE_RECEIPT` carries 100.000 and the full VAT breakdown. The trial balance still closes (the missing debit and the missing credit vanish together), so nothing alerts. W7 does **not** catch it: spec:386 derives VAT "from verified canonical receipts" and compares against device totals — both sides are fiscal, neither is the GL. The result is a sealed fiscal record permanently disagreeing with the accounting record on declared output VAT, which is the exact class §3.2 spec:99 forbids ("must never render as a clean zero … or a reconciled close").
- Minimum correction: qualify spec:165 — the non-money class **replaces the destination account and suppresses the treasury movement only**; the sale's proportional revenue + sealed-VAT lines and, for store vouchers, the `PosTenderClearing` offsetting debit are preserved (reuse the shipped maturity seam, `Concerns/HandlesMaturityTenderLeg.php:39-48`, which already does destination-account substitution without losing the entry). Add to the W2 baseline: `createPOSPaymentEntry` is the sole writer of those lines (`GeneralLedgerService.php:3957-3965` via `TreasuryReceiptBridge.php:1515`), the shipped `PosTenderClearing` deployment convention (`ReceiptPaymentService.php:378-385`), and the unresolved bypass TODO (`GeneralLedgerService.php:2960-2962`) with a disposition. **NEW-3 — W2's new cash-classification precondition ("drain and verify no unsettled projections … including offline pending outboxes") cannot be discharged by any existing server surface, and its escape hatch is unbounded. CONFIRMED-by-absence.**
- Spec line: 202 — "Before any mutation of `is_cash_tender` or related netting semantics, drain and verify **no unsettled projections on any terminal in the affected company, including offline pending outboxes**, or postpone that mutation."
- Source: the hazard is real and correctly cited — `TreasuryReceiptBridge.php:961-967` "the `payment_methods.is_cash_tender` flag (mutable operator state — **never flip it while a terminal has unsettled projections**; see the deploy checklist)", with `:965-967` explaining that a non-deterministic netting becomes "a permanently-failing queue job" via `TreasuryMovementService`'s `IdempotencyConflictException`. But the server cannot observe a device's *unsynced* sealed events: there is no outbox-depth or sync-completeness surface on the terminal (`grep last_sync|last_seen|heartbeat|outbox_depth|pending_events` over `POS/Domain` and `Fiscal/Domain` returns only `DeviceLossIncident.php:37 last_synced_event_at`, an incident record), and the device's own outbox lives in its SQLite (`apps/pos/src/lib/db/migrations.ts:1200,1432`). "Drain and verify" is therefore satisfiable only for terminals that have already checked in; a terminal offline for three days is invisible to it.
- Failure scenario: the classification cutover lane implements a drain check against server-side `fiscal_event_projections` (the only thing it can query), reports green, the operator flips `is_cash_tender`, and the offline terminal syncs receipts sealed under the old classification. Change-netting recomputes under the new flag, the movement key re-records at a different amount, and the leg becomes a permanently-failing job — for money that was correctly collected. The spec's alternative, "or postpone that mutation", has no bound and no detection criterion, so the operator has no way to know when postponement ends.
- Minimum correction: bind the precondition to a mechanism the spec already contains rather than to an unobservable drain — either (a) the event's **authored/seal-time classification revision** (spec:386's "W2 authored/cutover classification" and spec:202's "recorded company-scoped cutover decision"), so replay uses seal-time semantics and no drain is required, or (b) a terminal-level authoring quiesce plus an acknowledged-sequence check that makes "drained" server-observable. State which, and add the offline-terminal case to the W2 acceptance list (spec:204 currently has "classification-change deploy with unsettled work" — extend it to "with an *offline* terminal holding unsynced sealed receipts").
