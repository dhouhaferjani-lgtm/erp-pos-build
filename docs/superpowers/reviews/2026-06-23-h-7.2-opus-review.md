# H-7.2 Voucher Ledger Posting — Opus Adversarial Review

- Item: H-7.2 (voucher ledger GL entries post through the ledger event actor)
- Commit: 391b2159d ("Phase 0.1.36: Post voucher ledger journal entries")
- Reviewer: Opus adversarial (independent of Codex + Codex-fallback reviews already on the commit)
- Verdict: NEEDS-REVISION

## Summary

The change makes `GeneralLedgerService::createVoucherLedgerEntry()` post its
journal entry (Draft → Posted, hash-chained, `JournalEntryPosted` dispatched
after commit) using the ledger row's `user_id` resolved via
`User::query()->findOrFail($ledgerRow->user_id)`. The money math, double-entry,
afterCommit timing, PHPStan L8, and the focused/adjacent voucher tests all hold
up. The Issued path is genuinely red-first tested.

The problem is the actor-resolution strategy combined with the call sites. The
method is invoked from FOUR voucher paths (Issued, Redeemed, RoundingAdjustment,
Voided). The redemption / void paths feed `user_id` from the POS
`operator_id` / cashier id, and `voucher_ledger.user_id` has **no FK to
`users`** and is filled from values the codebase elsewhere treats as
possibly-not-a-user. `findOrFail` therefore converts a previously-harmless Draft
entry into a hard `ModelNotFoundException` that rolls back the entire voucher
redemption/void transaction. Only the Issued path is actually asserted Posted by
the tests; the redemption/rounding/void GL lifecycle is unverified.

## BLOCKER

None. The money, sign, hash-chain, balancing, and migration aspects are all
correct, and the regression below fails closed (no silent fiscal corruption).

## HIGH

### H1. `findOrFail` on a non-FK-constrained, possibly-non-user `user_id` can roll back POS voucher redemption/void

`apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:1082`

```php
$user = User::query()->findOrFail($ledgerRow->user_id);
```

This runs inside the caller's `DB::transaction` closure
(`VoucherRedemptionService::redeem()` opens `DB::transaction(...)` at
`VoucherRedemptionService.php:81`; the void paths in `VoucherCascadeService` and
`VoucherLookupService::autoVoidVoucher()` are likewise transactional). A throw
here aborts the whole redemption/void, not just the GL posting.

Why the actor may not resolve:

- The tenant migration declares `user_id` with **no foreign key**:
  `database/migrations/tenant/2026_05_02_000002_create_voucher_ledger_table.php:36`
  `$table->uuid('user_id');` — FKs exist for `voucher_id` (`:20`) and
  `reverses_voucher_ledger_id` (`:65`) but deliberately not for `user_id`. The DB
  does not guarantee the id is a real user.
- The redemption `user_id` is `$request->cashierId`, which in the POS projection
  path is `$event->operator_id`
  (`apps/api/app/Modules/POS/Application/Projections/PosCoreReceiptProjection.php:845`
  and `:890`).
- The codebase already assumes `operator_id` may NOT resolve to a `User`:
  `PosCoreReceiptProjection::resolveCashierName()` (`:393`) does
  `User::query()->find($operatorId)`, explicitly returns `'Unknown'` on `null`,
  and even catches `QueryException`. That defensive handling is direct evidence
  that an operator id is not guaranteed to be a `users.id` (offline operator
  identities, deleted/soft-removed users, device identities).

Before this commit those paths produced a harmless Draft GL entry. After it, an
unresolvable operator id throws `ModelNotFoundException` and rolls back a real
fiscal voucher redemption — a behavior regression on a fiscal projection /
offline-sync replay path that fails the whole sale operation.

Contrast with the sibling fixes: H-7.1 (`createFromExpense`, `:1613`) receives
the actor `User` from its caller and never re-resolves it; H-7.3 (COGS) posts as
a **system-generated** entry with nullable `posted_by` precisely because "no
actor is present on the immutable event" (work-list note). The voucher path is
the only one that hard-resolves a stored, non-FK, externally-sourced id.

Label: [HYPOTHESIS] on a confirmed production occurrence — I did not produce a
live offline-operator redemption. But the missing FK + the codebase's own
defensive `resolveCashierName` make this a credible, untested fail-closed
regression, not a theoretical one.

Recommended fix: either (a) set `posted_by` directly from the stored
`user_id` string without `findOrFail` (the canonical `postEntry` only needs
`$user?->id`), or (b) resolve with `find()` and fall back to the
system-generated posting path when null (mirroring H-7.3), so an unresolvable
operator never aborts the redemption. Add a test that exercises a voucher
redemption whose ledger `user_id` does not match any `users` row.

## MEDIUM

### M1. Only the Issued path asserts the posting claim; redemption/rounding/void GL lifecycle is unverified

The single augmented test
(`tests/Feature/Voucher/VoucherIssuanceServiceTest.php:141-144`) adds
`assertSame(Posted)`, `posted_by`, `posted_at`, `fiscal_hash` — but only for the
Issued path. The redemption and rounding tests
(`tests/Feature/Voucher/VoucherRedemptionServiceTest.php`) assert only
`assertNotNull($ledger->gl_journal_entry_id)` and the event type; grep for
`JournalEntryStatus::Posted` / `posted_by` / `posted_at` / `fiscal_hash` in that
file returns nothing. The Voided paths (`VoucherCascadeService`,
`VoucherLookupService::autoVoidVoucher`) have no posting assertion at all.

The claim is "voucher ledger GL entries post," but the test evidence only covers
1 of 4 wired events. The other three reach the same code, so behavior is likely
correct, but they are exactly the paths where H1's actor-resolution risk lives —
so the missing assertions are also the missing regression guard.

### M2. Actor-resolution design diverges from the established sibling pattern without rationale

H-7.3 (COGS) explicitly chose system-generated posting with nullable
`posted_by` for actorless immutable events; H-7.1 (expense) passes the actor in.
H-7.2 introduces a third pattern (re-fetch a stored id via `findOrFail`) on the
one column that has no FK and is sourced from POS operator ids. No note in the
work-list or the Codex/fallback reviews acknowledges the redemption/void
operator-id case — both reviews reason only about "schema requires user_id
non-null," which is true but does not imply the id is a resolvable `users` row.
The two prior reviews therefore missed the call-site reachability, which is the
crux.

## LOW

- L1. `(string) $ledgerRow->currency` (`:1134`) is safe — `currency` is
  `char(3)` NOT NULL (`migration :27`), so the cast never narrows a null.
- L2. afterCommit handling is correct: under the caller's outer transaction the
  post is deferred via `DB::afterCommit`; standalone it posts immediately. The
  focused test confirms the entry is `Posted` synchronously after
  `issueFromRefund()` returns under `RefreshDatabase`.
- L3. Double-entry integrity is preserved: `postEntry()` re-validates
  debit == credit at currency scale before stamping the hash
  (`:1267`), so a malformed voucher entry cannot post unbalanced.
- L4. No new float/precision drift — amounts stay numeric-string via `bccomp`/
  `bcmul` at `$this->scale()`; PHPStan L8 clean on the changed file.
- L5. Append-only/immutability respected — the GL entry is created Draft inside
  the txn and the status flips via `JournalEntry` update (not the append-only
  `voucher_ledger` row, which is INSERTed once with `gl_journal_entry_id`
  pre-populated). No trigger violation.

## Verdict

NEEDS-REVISION. The fiscal math and posting mechanics are sound and the Issued
path is genuinely tested, but the `findOrFail`-based actor resolution is a
fail-closed regression risk on the POS redemption/void paths (non-FK `user_id`
sourced from operator ids the codebase elsewhere treats as possibly-non-user),
and the test suite asserts the posting claim for only 1 of the 4 wired voucher
events. Address H1 (resolve softly / use stored id / fall back to system actor)
and add posting assertions for redemption + void (M1) before this is safe to
rely on.
