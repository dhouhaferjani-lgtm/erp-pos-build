## 2. Mechanism — what was wrong, in one paragraph

`PosCoreReceiptProjection` is the ONLY server-side stock writer for a device-authored POS
sale (its own `decrementStockForLines` docblock says so, and the three server-authoring
routes are 410). It moved `stock_levels` and `stock_movements` and **nothing else**: the
file contained no FEFO call and no batch write of any kind. `pos_receipt_line_batch_allocations`
was therefore empty for every live sale — which silently broke two downstream readers that
look right in code: `BatchTraceabilityController`'s recall trail, and
`ReceiptReturnService::lotProvenanceForLine()` (`ReceiptReturnService.php:1900`), which reads
those rows to credit a return back to the lot the sale took. W2-7/W4-5 DID build both FEFO
arms — on `ReceiptCreationService` (`ReceiptCreationService.php:1430-1447` composite leaf, `:1607-1637` direct line), which serves
`POST /pos/receipts`, retired at 410 `NEW_SALE_AUTHORING_RETIRED`. CLAUDE.md rule 20's own
warning, realised.

## 3. What the projection now writes, per receipt shape

All file:line in `apps/api/app/Modules/POS/Application/Projections/PosCoreReceiptProjection.php`
(post-merge line numbers).

| Receipt shape | Aggregate (unchanged) | NEW lot legs |
|---|---|---|
| **SALE**, direct line, batch-tracked | one `stock_movements` issue (`pos_sale`) | `consumeLotsForSaleLine()` `:2015` → `FEFOInventoryService::consumeBatchesAtomically()`: one `inventory_batch_movements` row per lot drawn, **keyed to that same issue movement id**, plus one `pos_receipt_line_batch_allocations` row per lot (batch id, quantity, batch_number + expiry snapshot) keyed to the sale's `pos_receipt_lines.id` |
| **SALE**, direct line, NOT batch-tracked | unchanged | none — `productRequiresBatchTracking()` gate `:2025` (pinned by a green-before-and-after regression test) |
| **SALE**, no `stock_levels` grain (service line / unseeded variant) | unchanged (nothing moved) | none — `decrementStock()` now returns `?StockMovement` (`:2177`, `null` at `:2221`) and the lot arm is entered only when a movement really was written (`:1962-1972`) |
| **SALE**, composite line | unchanged (nothing moved) | none — see W4R-3 below, and the docblock at `:1888-1903` |
| **REFUND / VOID**, `disposition = restock` (or legacy/pre-v4, which has no disposition) | one `stock_movements` receipt (`pos_return`) | `restoreLotsForRefundLine()` `:2477` → `FEFOInventoryService::restoreBatchesForReturn()` with **per-line provenance**: the ORIGINAL sale line's allocation rows become `preferredLots` (`lotProvenanceForOriginalLine()` `:2537`), netted by what earlier refunds of that same line already credited |
| **REFUND**, `disposition = scrap` | restore leg + cost-bearing write-off leg, net zero (unchanged) | **none, deliberately** — `applyScrapDisposition()` `:2641` calls `restockStock` directly and never reaches the lot arm; documented at `:2623-2636` |
| **REFUND**, `disposition = not_received`, or a `RestockPolicy::Never` product | unchanged (no movement) | none — those branches `continue` before `restockStock` |
| **REPLAY** of any of the above | unchanged | none — see §4 |

Two supporting changes:

* `writeLines()` `:1209` now reads the receipt-line id **off the created model** (`:1346`). `id`
  is not mass-assignable on `ReceiptLine`, so the pre-existing `'id' => Str::uuid()->toString()`
  was already being dropped and `HasUuids` minted the real key. Pre-generating one here would
  have keyed every allocation row to an id no `pos_receipt_lines` row carries — the refund arm
  would then find no provenance and fall back to the heuristic **silently**. This was caught by
  the provenance test (§6, first PG run credited the wrong lot), not by inspection.
* `writeLines()` returns `line_ids` + `original_line_ids` so exactly one place decides which
  local row a canonical line index maps to.

### The one deliberate divergence from the retired service: NON-STRICT fulfilment

`ReceiptCreationService::allocateBatches()` and `DeliveryNoteService` both call FEFO with
`strictFulfillment: true` and let `InsufficientBatchStockException` REFUSE the act. This
projector cannot: **a projector may never REJECT an already-signed event** (Model 1 §4.1 —
the doctrine `applyScrapDisposition()` states at length, in its own docblock above `:2641`). Throwing here would
dead-letter a real, signed, money-collected sale because the LOT ledger disagreed with the
aggregate, losing the receipt, its VAT and its drawer movement. So the draw takes what the
lots hold and the shortfall is logged (`:2079-2088`, structured: product, variant, location,
requested, shortfall) — pinned by `test_lot_shortfall_never_rejects_the_sealed_sale`.

**Residual, named:** a shortfall is the only case where `Σ lots != stock_levels` after this
lane. It is the same oversell the aggregate arm already permits and logs one level up
(`insufficient stock during projection`); the lot predicate is simply narrower (expired /
recalled / inactive lots are invisible, and `available_quantity` nets reservations, so a POS
sale over stock held by an open sales order will shortfall against lots while the aggregate
moves). Reviewer's call whether that deserves its own detector.

## 4. Replay proof

The lot legs inherit the projection's existing idempotency, they do not add a second one:
`apply()`'s fast-path `Receipt::exists()` probe on `fiscal_event_id` (`:232`) plus the atomic
`INSERT … ON CONFLICT DO NOTHING` (`insertReceiptOnConflictDoNothing`), all inside the
`ApplyFiscalEventProjectionJob` per-row `WithoutOverlapping` lock. A re-applied event returns
before any stock or lot write. Pinned twice, on real PostgreSQL:

* `test_replay_of_the_same_sale_writes_no_second_lot_leg` — apply twice: lot stays `8.0000`,
  `inventory_batch_movements` count `1`, `pos_receipt_line_batch_allocations` count `1`.
* `test_replay_of_the_same_refund_writes_no_second_credit` — sale + refund + refund again:
  aggregate back to `10.0000`, lot back to `10.0000`, exactly `2` batch movements
  (one issue leg, one credit leg — never three).

## 5. Sealed-bytes proof

`test_projection_leaves_the_sealed_bytes_and_chain_hash_byte_identical` reads
`fiscal_events.canonical_bytes` and `current_hash` before and after `apply()` and asserts
byte equality plus `sha256(before) === sha256(after)`, with a positive control
(`inventory_batch_movements > 0`) so it cannot pass vacuously.

Worth flagging to the gate: on PostgreSQL `canonical_bytes` is `bytea` and PDO returns a
**stream resource**, so `(string) $value` yields `"Resource id #N"` — a fresh number each
read. A naive before/after comparison fails on identical bytes and, worse, would have passed
vacuously had the bytes really changed. The test reads through `sealedBytes()`
(`stream_get_contents`). Nothing in the projection touches `canonical_bytes`, `current_hash`,
`previous_hash` or `payload`: the diff adds only reads of `$event->tenant_id` /
`company_id` / `id`, and writes to `inventory_batch_stock`, `inventory_batch_movements` and
`pos_receipt_line_batch_allocations`.

## 8. W4R-3 (NEW, P2/P3, for the owner queue) — the live projection has no composite arm

The brief asked for composite leaves. **They are not reachable on this path, and the reason
is a fiscal-payload decision, not an inventory one.** Evidence:

* The only producer of a `sellableType: 'composite_item'` cart line is `flattenMenuToProducts`
  (`apps/pos/src/api/productApi.ts:124-149`), which ids every Menu row
  `buildMenuCompositeId(sellable_id, category.id)` = `"<uuid>_<uuid>"` — **never** a bare UUID.
* The sealed payload takes `product_id: item.product.id` verbatim
  (`apps/pos/src/lib/fiscal/payloads/SaleReceiptPayload.ts:317`). The `receiptToPayload`
  unpacking that restores a bare `sellable_id` lives on the RETIRED `POST /pos/receipts` wire
  path (`apps/pos/src/lib/sync/syncService.ts:2546`), not on the fiscal-event path.
* So a composite line reaches `decrementStockForLines` with a non-UUID `product_id` and is
  skipped by the `Str::isUuid()` guard. `writeLines` additionally hardcodes
  `'composite_item_id' => null` (`:1321`).

Consequence: a composite POS sale moves **no aggregate stock and no lot stock**, so it
contributes **zero** to the Σ-lots-vs-aggregate drift this lane measures — consistent with the
re-run census, where all 27 units are direct-line sales/refunds. Building the leaf arm here
would mean creating a NEW aggregate stock decrement AND new COGS GL entries for Menu tenants,
off the back of a lot-drift lane, with no campaign evidence and no answer yet to how the
sealed `<sellable_id>_<category_id>` snapshot should resolve server-side. That is its own
defect with its own design, filed here as **W4R-3** and recorded in the code at `:1888-1903`
and in `ReceiptCreationService.php` on the composite arm.
