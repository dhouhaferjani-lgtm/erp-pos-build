# Verdict

**Clean — no blockers. Two minor concerns and one nit, all bounded.** The four follow-up commits (`9f7874db`, `5f3ab85b`, `a7a0b423`, `55dced44`) close the audit findings they claim to close. Voucher tenders now flow end-to-end from `paymentStore.voucherTenders` through `AdvancedPaymentsModal` (rendered as voucher rows, counted toward `totalPaid`, mapped to `AdvancedPaymentLine[]` with `instrument_type: 'store_voucher'` + `instrument_serial: <code>`) into both the offline writer (`createOfflineReceipt` → `payments_json`) and the online writer (`onlineCheckout` → `processReceiptPayments` request body). `method_code` is now hard-required across the wire (validator + DTO + writer fallback removed); the 422 negative-case test asserts the error path string. The TS-path integration test (Finding 3) genuinely closes the synthetic-payload gap by importing the production `receiptToPayload` via a `__test_*` alias and round-tripping the wire shape into the canonicalizer + back into the offline-sealed hash — drift in either mapper now fails loudly. Finding 4 makes invalid `fiscal_schema_version` throw with a message naming the receipt and bad value.

Hash stability is preserved on both fixtures (`4db73253...` for cash-only, `100f2395...` for store-voucher), the v2 path is bit-for-bit unchanged across PHP and TS (`git diff 2efc007e..HEAD -- …/hashService.ts …/ReceiptHashService.php` returns zero lines), the JSON fixture files are byte-identical between `apps/api/tests/Fixtures/Fiscal/v3-golden-hashes/` and `apps/pos/src/lib/fiscal/v3/__fixtures__/v3-golden-hashes/`, and no new `app()` / `mixed` / `: any` were introduced in production code.

The two minor concerns: (a) the bonus online-checkout fix for `offlineCheckoutService.onlineCheckout()` is correct by code reading but has **no automated test** — `apps/pos/src/lib/offline/__tests__/offlineCheckoutService.test.ts` does not exercise a voucher-bearing online path; (b) the voucher repository fallback in `AdvancedPaymentsModal` (`virtual` → `bank_account`) is bounded by a hard error if neither exists, but a tenant configured with bank_account and no virtual repo will silently route voucher tenders to a `bank_account` repository ID — the v3 hash still seals correctly, but the GL row posts the voucher payment against a bank account, which can cause downstream reconciliation drift. Neither rises to a blocker since (i) voucher tender wiring is brand-new, no historical receipts exist; (ii) the audit's stated goal — "writer plumbing has a live UI consumer producing instrument fields" — is met; (iii) the fallback is documented in the implementer's report and is reasonable as a release-day compromise.

## Outstanding issues

### Minor — bonus `onlineCheckout` voucher-path fix has no automated test

**File:** `apps/pos/src/lib/offline/offlineCheckoutService.ts:97-115` and `apps/pos/src/lib/offline/__tests__/offlineCheckoutService.test.ts`.

**What's wrong:** The implementer extended `onlineCheckout()` to forward `input.payments[]` with instrument fields into `processReceiptPayments`. The wiring is correct by code reading: each payment row spreads `instrument_type` and `instrument_serial` conditionally, the API request type (`ProcessReceiptPaymentsRequest` at `apps/pos/src/types/receipt.ts:61-81`) carries those fields, and the server's `StoreReceiptPaymentsRequest` validator (proven by the existing `StoreReceiptPaymentsInstrumentBindingTest`) accepts them. **However**, the test file `offlineCheckoutService.test.ts` only covers the cash-only happy path (lines 75-101) and offline-fallback paths (lines 102-184). No test feeds `input.payments[]` with a voucher tender into `executeCheckout()` and asserts the request body for `processReceiptPayments` carries the instrument fields. A future regression that reverts the conditional spread (e.g., someone "simplifies" the map back to a hardcoded single-cash payment, restoring the original B3 bug) would not be caught.

**Why it matters:** The audit task says "the bug was real before, but is it actually closed?" — for the offline path, yes, locked by `paymentStore.offlineFirst.test.ts:245-298`. For the online path, the fix is correct but unproven by automated test. This is the same shape of gap the original audit identified.

**What would close it:** Add a test in `apps/pos/src/lib/offline/__tests__/offlineCheckoutService.test.ts` that:
1. Sets `useConnectivityStore` to `isOnline: true`.
2. Mocks `createReceipt` and `processReceiptPayments` to capture their request bodies.
3. Calls `executeCheckout()` with `input.payments` containing a voucher row carrying `instrumentType: 'store_voucher'` + `instrumentSerial: 'SV-2026-…'`.
4. Asserts the captured `processReceiptPayments` request body's `payments[0]` includes `instrument_type` and `instrument_serial` verbatim.

### Minor — `voucherRepository` falls back to `bank_account` silently when no `virtual` repo is configured

**File:** `apps/pos/src/components/organisms/AdvancedPaymentsModal/AdvancedPaymentsModal.tsx:126-132`.

**What's wrong:** The fallback chain is `virtual` → `bank_account` → null. The null case correctly raises `voucherRepositoryMissing`. But the `bank_account` case is silent: a tenant with no virtual repo and a configured bank account will route voucher tender rows to a `bank_account` repository ID. The fiscal hash still seals the correct `instrument_serial` (the hash uses `payment_method_code` and `instrument_type`, not `repository_id`), so v3 chain integrity is preserved. **However**, the GL row posted by the receipt finalizer would credit the bank account for what is actually virtual money (a redeemed voucher). Downstream reconciliation against the bank statement would drift by the voucher amount.

**Why it matters:** This is bookkeeping correctness, not fiscal correctness. The implementer's compromise is documented as "to avoid blocking the cashier when the tenant has not configured a virtual one yet" — defensible at release time. But "fix once and for all" means the silent fallback should at minimum surface a warning (telemetry breadcrumb, console.warn, or i18n toast) so the operator notices. Today it's invisible.

**What would close it:** Either (a) drop the `bank_account` fallback and require `virtual` (raises `voucherRepositoryMissing` if no virtual repo); (b) keep the fallback but add a console.warn / Sentry breadcrumb + a one-time toast on first use ("Vouchers are being posted against a bank account because no virtual repository is configured — accounting may need to reconcile this manually"); (c) seed a `virtual` repo automatically when a tenant adds the `store_voucher` payment method.

### Nit — pre-v16 stale offline receipts will now hit 422 on sync

**File:** `apps/pos/src/lib/sync/syncService.ts:1178-1187` (synthesize fallback).

**What's wrong:** Pre-v16 offline receipts had no `payments_json` column. After migration 16 they get the default `'[]'`. With `method_code` now required and `payments` requiring `min:1`, both branches of `receiptToPayload` produce a wire payload the server rejects: (i) if `payments_json = '[]'`, `parsedPayments` is an empty array → server 422 on `payments.required|min:1`; (ii) if `payments_json` is null (column absent on a freshly-migrated row), the synthesize fallback emits `method_code: ''` → server 422 on `method_code.required` (string length ≥ 1 implied by `string|max:64` + the implementer's empty-string-rejection test).

**Why it matters:** Net effect is identical to the audit's analysis: stale pre-v16 queued receipts cannot sync. The implementer documents this as intentional (those payloads cannot reproduce the offline hash anyway, so failing loud is correct). The triage doc warned about this ("pre-v16 ≠ pre-B3"). For Otospex / IziPOS today: there is no production terminal carrying pre-v16 queued receipts because v16 shipped before B3 and queued offline receipts are short-lived (terminal sync runs continuously). Verify with operator before merge.

**What would close it:** Either (a) accept the implementer's intentional-fail behavior and document the upgrade-readiness check in the deploy runbook ("before merging this PR, verify all terminals have flushed any pre-v16 queued offline receipts; query `offline_receipts WHERE status = 'pending' AND payments_json IN (NULL, '[]')`"); (b) restore the synthesize fallback to emit `method_code: '<lookup>'` from the legacy `payment_method_id` column for these specific rows. Option (a) is simpler and matches "fix once and for all" intent.

## What's solid

- **End-to-end voucher tender wiring is now real**, not synthetic. A cashier scanning a voucher in `VoucherTenderModal` adds a row to `paymentStore.voucherTenders`. Opening `AdvancedPaymentsModal` renders the voucher row alongside cash/card lines, counts its amount toward `totalPaid` (so the running balance, "Pay Remaining" pill, change-due indicator, and "fully paid" gate all reflect tender state). Clicking Complete maps each voucher row to `AdvancedPaymentLine` with `instrument_type: 'store_voucher'` + `instrument_serial: <code>`, hands the merged array to `processAdvancedCheckout` (locked by `paymentStore.offlineFirst.test.ts:245-298`), which forwards to `createOfflineReceipt`, which writes both the v3 hash input and `payments_json` with the instrument fields populated. The TS-path test (`receiptService.test.ts:470-582`) proves the wire payload reconstructs the offline-sealed hash byte-for-byte.

- **`method_code` contract is now explicit at every layer.** Validator → DTO → writer → tests. The fallback that the audit flagged as silent hash-input substitution is gone. The 422 negative-case test asserts on the field name in the response body, so a future regression that reintroduces the fallback fails on the path string, not a generic 422.

- **The TS-path test (`__test_receiptToPayload`) is the right shape.** Imports the production parser via an aliased export — no shadow implementation. Round-trips `createOfflineReceipt` → `payments_json` → `__test_receiptToPayload` → `buildCanonicalPayload` → SHA-256, and asserts equality with the offline-sealed hash. A drop-a-field, change-case-normalization, or reorder-payments regression in `receiptService.ts` or `syncService.ts:receiptToPayload` will fail this test.

- **Fail-loudly on invalid `fiscal_schema_version` is correctly implemented.** The thrown Error names the receipt number, idempotency key, and the actual bad value — exactly what an on-call engineer needs to locate the row in `offline_receipts`. The server's hard-reject path remains as defense in depth, as the audit recommended.

- **No drift introduced**: zero new `app()` / `mixed` / `: any` in production code; all introductions are in test files for PHPUnit setup or test data shapes. v2 path is bit-for-bit unchanged. Fixture files byte-identical between PHP and TS sides. Existing 4 sync test files all updated to send `method_code` per payment row — no test was left in a broken state by the validator promotion.

- **The Major item flagged in the prior B3 audit ("paymentStore.voucherTenders has no live UI consumer") is fully closed.** The original audit said "production-path proof for voucher binding rests entirely on the `OfflineV3CutoverSyncTest` synthetic payload." Now the proof rests on a real cashier flow: `addVoucherPayment` → modal renders → modal Complete → store action → `createOfflineReceipt` → `payments_json` → `receiptToPayload` → wire payload → server. Each layer has a test. The synthetic-only era is over.
