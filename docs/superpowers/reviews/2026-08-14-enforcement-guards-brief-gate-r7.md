## Critical findings

### R7-C-1 — The parent invokes candidate-controlled acceptance machinery, so “parent-invoked” still permits ACCEPT laundering

**Evidence:** The final-milestone exception tells the executor to hand over A and the parent to invoke `scripts/adversarial-review.sh` against that handed-over branch (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:103-117,426-428`). The script used from the checkout is itself the entire trust-producing path: it converts the supplied range into a diff command, constructs the reviewer prompt from the supplied brief, invokes `claude`, copies stdout to the register, and returns exit 0 on the parsed ACCEPT line (`scripts/adversarial-review.sh:21-45,49-79,82-100`). It contains no self-blob check, trusted-ref lookup, or check of the brief and lens-contract blobs. The only pre-merge independent check after the invocation is step 4a's workflow-authority/tag/variable/freshness check (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:431`); step 5 checks only A→C's administrative closing diff (`:432`). F-8 expressly treats the executor as untrusted and candidate-authored control surfaces as a residual risk to be controlled (`:448`).

**Failure scenario:** the untrusted executor changes `scripts/adversarial-review.sh` in A so that it writes a plausible register ending in `VERDICT: ACCEPT` and exits 0 without invoking the reviewer. The executor hands over with the final milestone at `status: review`. The trusted parent follows r14 exactly and runs `scripts/adversarial-review.sh` from that checkout; because the parent really did invoke the candidate script, it regards the resulting bytes as its own invocation, hashes them, and the owner binds them into the annotated tag. Step 4a sees no workflow content-write grant and valid tag/variable state; C lands the same bytes. No malicious parent or owner is needed, and no actual final reviewer issued ACCEPT. The same structural problem applies if the candidate changes the acceptance brief or lens contracts consumed by the candidate script.

**Required repair:** run the final bridge from a trusted blob outside A, not from the candidate worktree—for example, materialize the bridge from a parent-pinned trusted ref and invoke it with A only as reviewed data. Pin or independently verify the exact brief and reviewer-contract blobs supplied to that trusted bridge. Before invoking it, the parent must also perform a machine path/blob preflight of `base_sha..A` that rejects changes to the bridge, brief, and reviewer contracts unless the owner explicitly re-gates those control files. The final attestation must name those trusted input blobs as well as package, milestone, round, A, and output digest.

### R7-C-2 — Closing commit C is required to contain its own SHA, making every package's closing state impossible

**Evidence:** Step 5 requires one commit C, with `C^ == A`, to contain the progress YAML's final state and a structured receipt whose `closing_commit:` value is C's own SHA; it then runs the closing check after C exists (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:432`). The same self-containing schema is operative in all three YAMLs: `closing_receipt` is written in C and includes `closing_commit: <C SHA>` plus post-commit `closing_check` output (`docs/handoff/progress/enforcement-p1.progress.yaml:91-96`; `enforcement-p2.progress.yaml:78-83`; `enforcement-p3.progress.yaml:103-108`). LEDGER S-14 likewise says C lands that receipt and the check output is recorded in it (`docs/handoff/LEDGER.md:56`).

**Failure scenario:** the parent prepares C with a placeholder, commits, and obtains SHA C1. Writing `closing_commit: C1` changes the progress-YAML blob and therefore the tree and commit object, producing C2. Replacing the field with C2 produces C3, and so on. Leaving C1 in C2 makes the receipt false. The authorized amend loop cannot solve this fixed-point problem; each attempted repair changes the value it is trying to record. Consequently no truthful C can satisfy the mandatory artifact/schema check, P3's expected evidence state cannot exist, and every package stalls after A has already been fast-forwarded.

**Required repair:** remove all data that can only be known after C from the contents of C. The smallest repair is for the in-C receipt to record A, tag, annotation digests, mandatory-path manifest, and preflight result while consumers deterministically derive C as A's first-parent child and verify `C^ == A`. Store the actual C SHA and post-commit check result in a second owner-authenticated object outside C (for example, a distinct immutable closing tag/attestation), or revise the chain explicitly if a child commit is chosen. Do not attempt to amend C until it contains its own hash.

## High findings

### R7-H-1 — A parent-returned final CHANGES-REQUIRED verdict has no coherent fix-round transition

**Evidence:** The base harness says the executor owns every review loop: after CHANGES-REQUIRED it reads the register, makes the scoped fix, increments `fix_rounds`, and re-runs the bridge (`docs/handoff/SELF-REVIEW-HARNESS.md:21-47`). r14 overrides only the final invocation: the executor must hand over at `status: review` and “never” run the final bridge (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:103-117`; the same rule appears in all final milestone titles at `docs/handoff/progress/enforcement-p1.progress.yaml:165-172`, `enforcement-p2.progress.yaml:170-177`, and `enforcement-p3.progress.yaml:165-172`). Promotion step 1 defines only the ACCEPT branch (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:428`). The re-gate protocol covers stale A, red dispatch, step-4a, and external side-effect failures, but not CHANGES-REQUIRED or tool error from the parent's final bridge (`:433`).

**Failure scenario:** the parent's first P2-M4 invocation returns CHANGES-REQUIRED. If the executor follows the harness, it fixes and then re-runs step 2 itself, producing an executor-controlled final invocation that r14 expressly rejects. If the executor obeys the exception and does not re-run, no rule says who changes M4 back to `in_progress`, who records the parent register/`last_verdict`, who increments `fix_rounds`, when control returns to the parent, or that the parent must invoke round 2. A tool error has the same gap. The wave can deadlock or accept on the wrong actor's retry.

**Required repair:** specify the final fix-round state machine in the brief, all three final milestone clauses, and S-14: the parent records the round-N register/result and returns it; the executor alone implements a scoped fix, commits, increments `fix_rounds`, sets the milestone back to `review`, and hands over; the parent invokes every final round, including tool-error retries. Define max-round exhaustion and stale parent register cleanup without committing a non-ACCEPT register into A accidentally.

### R7-H-2 — The exact handback bytes authenticated in the tag are not a required input to the final bridge

**Evidence:** Every bridge invocation is specified with `--range <base_sha>..HEAD` and no handback/evidence argument (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:107-116`). The bridge tells the reviewer to run only that diff command as “WHAT TO REVIEW” (`scripts/adversarial-review.sh:53-64`). The parent invokes the final bridge against already-existing A and only then hashes the handback (`docs/handoff/CODEX-DISPATCH-enforcement-guards-2026-08-12.md:428`), while the exact handback bytes are first landed later in C (`:432`). Those bytes therefore are not part of `base_sha..A`; at best an earlier or untracked version is present in the worktree. This matters because the handback carries the P1 census and P3 classification/reconciliation tables (`:452-458`), P3 consumes P1's census (`:93-97,362-368`), and P3-M0 authenticates the handback bytes as an input (`docs/handoff/progress/enforcement-p3.progress.yaml:29-39`).

**Failure scenario:** the executor hands over code A plus an untracked or post-A P1 handback whose census omits a real journal creator. The trusted bridge reviews `base_sha..A`; nothing requires it to open or bind the exact post-A handback bytes. It returns ACCEPT on the code. The parent immediately hashes the executor-authored handback and the owner tag correctly authenticates those bytes; C lands them, and P3-M0's digest/blob comparisons pass. P3 then consumes an omitted write path even though the final review never evaluated the exact authenticated census. This needs no later handback rewrite, so R6-H-1's new integrity comparison does not catch it.

**Required repair:** make the exact handback a named, digest-bound input to the parent-invoked final review. Extend the trusted bridge interface with an explicit handback path and parent-computed pre-invocation digest; require the reviewer to inspect that exact file and echo the digest/path in its register. The parent must verify the echoed digest before creating the tag. Alternatively put a reviewable, non-self-referential evidence manifest in A and make C's handback byte-for-byte derivable from it; merely hashing an unreviewed post-A file is integrity, not acceptance.
