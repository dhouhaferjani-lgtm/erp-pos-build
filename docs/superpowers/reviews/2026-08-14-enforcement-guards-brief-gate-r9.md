## Critical findings

### R9-C-1 — The sealed bundle does not seal the review base, so the executor can collapse both preflight and final review to `A..A`

**Evidence:** Each package's `base_sha` is stored in its ordinary candidate progress YAML—for example P1 declares the parent-written pin and then stores it at `enforcement-p1.progress.yaml:10-33`; P2 does the same at `enforcement-p2.progress.yaml:10-14`; P3 at `enforcement-p3.progress.yaml:10-20,70`. The brief calls the YAML the operative package state (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:104,118`) and uses `<base_sha>..A` for the six-path control preflight and final invocation (`:441`). Yet the manifest's package blocks pin only `final_milestone`, `lenses`, and `max_fix_rounds` (`enforcement-control-manifest.yaml:34-46`); they contain no dispatch base or progress-file projection. The shipped bridge accepts `--base` verbatim (`adversarial-review-final.sh:34-50`), never reads or field-checks a progress YAML, verifies only candidate `HEAD == ACCEPTED` (`:100-104`), and puts the unchecked base straight into the reviewer prompt (`:116-120`). It does not require `BASE` to equal an owner-held pin, to be a strict ancestor of A, or even to differ from A.

**Failure scenario:** after implementing an unreviewable or out-of-scope candidate A, the untrusted executor changes its progress YAML `base_sha` to A. The parent follows the package's documented operative state. `git diff --name-only A..A` makes the six-path control preflight empty, and the bridge accepts `--base A` because `HEAD == A`; the final prompt declares the review range `A..A`. Scope proof and implementation-diff review are now empty even though A contains the package changes. The parent and owner can behave honestly throughout; the mutable candidate has selected the lower endpoint of its own review.

**Required repair:** put each package's dispatch `base_sha`, progress path, and immutable progress-control projection in a parent-owned pre-dispatch object. The final bridge must receive an independently held expected manifest hash, verify the manifest first, load the base from that verified object rather than the candidate YAML, require `BASE` to be a strict ancestor of A, and field-check the candidate YAML's `base_sha`, final milestone id/lenses, `max_fix_rounds`, current `fix_rounds`, and `status: review` against the trusted projection. The six-path preflight and final range must use that same trusted base.

## High findings

### R9-H-1 — The final bridge creates a detached snapshot but runs Claude from the caller's checkout and never supplies the pinned brief or harness

**Evidence:** The bridge verifies hashes for the brief and harness (`scripts/adversarial-review-final.sh:81-86`) but only concatenates lens-contract bodies into `LENS_BLOCK` (`:87-95`). Its final prompt contains the snapshot path, range, handback instruction, and lens text, but neither the brief/harness paths nor their contents (`:116-125`). Most importantly, the actual `claude` command is invoked directly at `:128`; there is no `cd "$SNAP"`, `git -C "$SNAP"`, working-directory flag, or isolated project-config setup. The brief nevertheless claims all diff inspection and command execution occurs in the detached tree and that project-local instructions/settings are pinned by the manifest (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:91,441`). The manifest pins no `CLAUDE.md`, `.claude/settings.json`, or hook/config input (`enforcement-control-manifest.yaml:9-46`), while the repository's actual `.claude/settings.json` defines executable project hooks (`.claude/settings.json:2-34`).

**Failure scenario:** the parent launches the trusted script from its control checkout, which is necessarily not the candidate snapshot. A well-intentioned reviewer runs a relative `git diff`, test command, or file read from its inherited working directory and evaluates the parent's control checkout instead of A. It also has no pinned package brief in its prompt, so it can omit package-specific acceptance and scope requirements while still returning ACCEPT. Alternatively, project configuration from the caller's checkout influences the CLI despite being absent from the manifest. The register then falsely says the detached snapshot was reviewed (`scripts/adversarial-review-final.sh:133-140`).

**Required repair:** invoke the reviewer with the process working directory fixed to the detached snapshot and an isolated/pinned CLI configuration; inject or explicitly require the verified brief and harness contents as binding inputs; pin every enabled project instruction/settings/hook input or disable project-local loading. After the run, reassert snapshot `HEAD == A` and a clean tree. Hash verification of files never consumed by the prompt is not a review binding.

### R9-H-2 — The normal post-A handback cannot satisfy the literal copy-then-clean sequence

**Evidence:** The final handback is not part of A; step 5 says its exact step-1 bytes first land in closing commit C (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:445`). Step 1 first tells the parent to **copy** that handback to its workspace and then requires the candidate worktree to be empty under `git status --porcelain` (`:441`); the execution-mode rule repeats that ordering (`:117`). All three final milestone clauses repeat “parent copies the handback out first, then git status --porcelain must be empty” (`enforcement-p1.progress.yaml:176`; `enforcement-p2.progress.yaml:180`; `enforcement-p3.progress.yaml:178`). The shipped bridge enforces an exactly empty status with no allowed-handback exception (`scripts/adversarial-review-final.sh:100-102`). Copying a file does not remove the source file that made the candidate dirty.

**Failure scenario:** the executor correctly prepares the required post-A handback and hands over A plus that one uncommitted file. The parent copies it to the immutable workspace exactly as instructed. The source remains untracked/modified in the candidate, so the bridge exits 3 at the clean-tree check before creating the snapshot. Committing it into A contradicts the required closing topology; silently deleting or moving it after copy is an unstated mutation of the handed-over evidence. Every conforming package can deadlock at its first final invocation.

**Required repair:** specify one exact, verified transfer operation. For example, require the parent to hash and move the one expected handback path out of the candidate, verify no other status entries exist, then invoke the bridge; or have the bridge accept exactly one declared handback status entry, copy/hash it itself, and reject all others before using only the detached A snapshot. State recovery if the source is tracked versus untracked. “Copy” plus an exactly empty source tree is not executable.

### R9-H-3 — The refreshed manifest authenticates its children but has no authenticated identity of its own, and no consumer verifies the claimed control binding

**Evidence:** The brief says the manifest contains a control source ref and that P3/closing verification compare tag `control_sha256` lines with it (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:92`). The shipped manifest contains child paths/hashes and package controls, but no control source ref, base commit, or self/parent identity (`enforcement-control-manifest.yaml:9-46`). The progress files describe a dispatch-time path+manifest hash, e.g. P1 at `enforcement-p1.progress.yaml:117-121` and P3 at `enforcement-p3.progress.yaml:122-126`, but the bridge accepts only a manifest path, never an independently expected manifest digest (`scripts/adversarial-review-final.sh:34-50`). It verifies values obtained from that same manifest (`:76-98`) and emits bridge/brief/harness/lens hashes but no manifest hash or source commit (`:133-140`). P3's actual P1/P2 evidence consumers check A, register digest, handback digest, C, close-tag target, `closing_commit`, and `accepted_sha` (`enforcement-p3.progress.yaml:20-54`); they never parse `control_sha256` or compare it with either package's dispatch manifest.

**Failure scenario:** after the parent refreshes and commits manifest M2, the final invocation accidentally uses a stale parent-workspace manifest M1 together with the matching stale control checkout. All child hash checks are internally consistent and pass. The register and pin tag bind those stale child hashes but never identify M1 itself. P3 later verifies register/handback/C/close-tag integrity and accepts the package because none of its predicates compares the control lines with the package's dispatch-time manifest. No malicious parent is required; the refresh step has no end-to-end verifier against which a wrong-but-self-consistent copy fails.

**Required repair:** give the manifest a parent-held external identity: record its source commit/ref and sha256 in an owner-controlled dispatch receipt, pass the expected sha256 separately to the bridge, verify it before parsing, and emit both manifest digest and source commit in the register/tag. Preserve each package's dispatch manifest identity in C. P3 must load that package-specific identity and compare every expected control name/hash with the pin tag; closing verification must do the same for P3. A manifest cannot establish its own authority merely by agreeing with itself.

### R9-H-4 — The verdict parser treats any verdict containing `ACCEPT` as acceptance

**Evidence:** The prompt asks for exactly `VERDICT: ACCEPT` or `VERDICT: CHANGES-REQUIRED` (`scripts/adversarial-review-final.sh:116-125`). The parser takes the last line beginning `VERDICT:` and tests the wildcard `*ACCEPT*` first (`:146-149`), rather than requiring exact equality. Therefore strings such as `VERDICT: NOT ACCEPT` or `VERDICT: ACCEPT WITH CONDITIONS` exit 0.

**Failure scenario:** the reviewer detects a blocker but emits `VERDICT: NOT ACCEPT`—whether from ordinary model formatting drift or hostile text in the candidate/handback. The trust-producing executable prints `ACCEPT` and exits 0. The parent digests and tags that negative register as the final ACCEPT evidence, and downstream checks only require a parseable ACCEPT token/digest binding. This false pass needs no malicious parent or owner.

**Required repair:** require exactly one verdict line and exact string equality: `VERDICT: ACCEPT` → 0, `VERDICT: CHANGES-REQUIRED` → 2, everything else → 3. Validate before writing/acting on the final register, and add direct negative cases for `NOT ACCEPT`, conditional acceptance, duplicate verdict lines, and trailing text.

## Minor findings

### R9-M-1 — P3 checks close-tag target and two annotation fields but never requires `closing_check: pass`

**Evidence:** The producer schema requires `{closing_commit: <C>, closing_check: pass, accepted_sha: <A>}` and requires the tag to resolve to C (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:445`). P3's P1 consumer requires target C, annotation `closing_commit == C`, and `accepted_sha == p1_landed_sha` (`enforcement-p3.progress.yaml:39-41`); its P2 consumer repeats the same shape (`:50-54`). Neither requires the annotation's `closing_check` key to exist or equal `pass`.

**Failure scenario:** the owner creates a close tag at the correct C with the correct C/A fields but with `closing_check: fail`, a typo, or no field. P3 accepts it. The owner is the trust root and P3 independently repeats the substantive C/diff/blob checks, so this remains Minor, but the advertised attestation conjunction is incomplete.

**Required repair:** add `closing_check == pass` to both P1 and P2 P3-M0 predicates and to the universal producer read-back check. Apply the same complete read-back to P3's own close tag even though no current package consumes it.
