# DN-consolidation spec — delta gate round 4

## 1. Gate verdict: FAIL

The r4 revision correctly adds exact-`N` predicates to both finalisation writes, inventories the `quantity_delivered` mutation, corrects ND-1/ND-4/ND-5, and supplies a sound two-year barrier strategy in prose. It does not pass. Residual 9 is still open because the prescribed fixture evaluates `date('Y')` twice, and residual 1 is internally contradictory about whether `claim()` returns the `DeliveryNoteClaimSet` that carries `N`; merely returning such a value would not make omitted finalisation a PHPStan type error. The short-payload negative test also requires an impossible interleaving under the mandated row locks. The newly inventoried `partners` lock does **not** create a cycle with the four-kind order, for the reasons in §3. Two further inventory/provenance defects are recorded below.

## 3. `partners`-lock lane-ordering ruling

**Ruling: no cycle with the published four-kind order.** On the only production caller, the SO lane creates/numbers the invoice before `transferPrepayments()` (`SalesOrderToInvoiceConverter.php:168-193`; invoice numbering occurs in `CopiesDocumentData.php:52-94`), and only then reaches the partner lock (`SalesOrderToInvoiceConverter.php:398-410` → `GeneralLedgerService.php:1678-1705`). Its effective suffix is therefore:

```
document_sequences[delivery_note] -> own source lines -> sorted DN rows
-> document_sequences[invoice] -> partners -> GL advisory lock
```

The non-auto-created SO lane starts at the sorted DN rows but has the same suffix. The GL method's only application caller is this SO converter; after locking the partner it takes the per-company GL advisory lock and writes journal rows, not any of the four document lock kinds (`GeneralLedgerService.php:1682-1744,4866-4892`).

The repository's other explicit `partners` row-lock holders supply no reverse edge:

- customer-account transition locks the partner and then updates it/emits its fiscal event, with no document numbering or DN claim (`apps/api/app/Modules/Partner/Application/Services/CustomerAccountStatusService.php:39-88`);
- standalone credit-note creation locks the partner and then requests a **credit-note** sequence (`apps/api/app/Modules/Document/Application/Services/CreditNoteService.php:1124-1139`), a different row because document sequences are keyed by `(company_id,type,year)` (`DocumentNumberingService.php:47-51`; `2025_11_30_140002_add_company_id_to_document_sequences.php:23-27`);
- advance-backed payment reversal already reaches partner after its payment/document/instrument locks and then proceeds to GL, not to a delivery-note/invoice sequence or DN claim (`apps/api/app/Modules/Treasury/Domain/Services/PaymentRefundService.php:807-845`).

Guided pre-post delivery merely reads the partner without `FOR UPDATE` before creating its DN (`InvoiceController.php:951-977`). Thus the wait graph contains four-kind→partner edges but no partner→four-kind edge on the same rows; the partner lock can block throughput, but it cannot close an AB/BA cycle with the published chain.
