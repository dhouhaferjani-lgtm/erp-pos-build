# H-2.2 Customer-Advance GL Posting — Opus Adversarial Review

- Item: H-2.2 (post customer advance/prepayment GL entries)
- Commit: `698221bec` ("Phase 0.1.12: Post customer advance GL entries")
- Branch context: reviewed at the merged commit tree; dev HEAD is far ahead (the
  balance-refresh helper was later renamed/reworked in `5d30776ac` "Refresh
  balances from journal posted events" — out of scope here).
- Reviewer lens: money/precision, sign conventions, event immutability, GL
  correctness, transaction/rollback safety, test quality.

## Summary

The claim holds up under refutation. Before this commit
`createCustomerAdvanceJournalEntry()` created the advance entry as **Draft and
never posted it**, then called `refreshPartnerBalance()` — and
`PartnerBalanceService::getPartnerBalance()` counts only `status = 'posted'`
rows (`PartnerBalanceService.php:46`), so customer advance/credit balances were
effectively always 0. The fix wires the entry through a posting step with a
real actor, defers posting + balance refresh to `DB::afterCommit()` when inside
an outer transaction (rollback-safe), and adds a company-currency fallback so
legacy/no-`CompanyContext` callers can still resolve scale.

I verified the three production callers (`PaymentController::store`,
`PaymentController::storeMultiple` x2, `PaymentAllocationService::applyAllocationFromCommand`)
all wrap the call in `DB::transaction`, so deferral is real in production and
none of them read the entry's `status`/`fiscal_hash` immediately after creation
(they only read `->id`). The double-entry shape (Dr Bank / Cr Customer Advance
with `partner_id` on the credit line) is unchanged and correct, sign conventions
in `liabilityMagnitude()` store non-negative magnitudes with a clamp+warn, and
no float casts or `number_format((float)…)` were introduced.

The tests are genuinely meaningful (not false-confidence): I confirmed
Laravel 12's test `DatabaseTransactionsManager` skips the wrapping
`RefreshDatabase` transaction (`afterCommitCallbacksShouldBeExecuted => level === 1`,
`callbackApplicableTransactions` skips connectionsTransacting), so the
happy-path test really posts (callback fires immediately) while the rollback
test really queues the callback under an extra explicit `DB::transaction` and it
never fires on rollback. Red-first is plausible: pre-fix the advance entry was
never posted and the balance refresh ran inside the savepoint, so
`PartnerBalanceUpdated` would have leaked on outer rollback.

Net: no BLOCKER and no money/data-integrity defect. One real HIGH design risk
(silent inconsistency if the deferred post fails after commit) is untested and
unmentioned. Verdict: APPROVE-WITH-MINOR-EDITS.

## BLOCKER

None.

- Money/precision: no `(float)` cast, no `number_format`, scale resolved via
  injected `CurrencyScaleResolverInterface` with explicit currency or
  `currencyCodeForCompany()` fallback; amounts stay numeric strings
  (`GeneralLedgerService.php:65`, `:351-364`).
- Event immutability: `JournalEntryPosted` / `PartnerBalanceUpdated` are
  dispatched, not restructured; the commit touches no event class.
- GL correctness: balanced Dr/Cr, `partner_id` only on the advance (credit)
  line, posted-vs-draft lifecycle preserved, actor recorded as `posted_by`
  (verified by `test_customer_advance_posts_and_refreshes_credit_balance`
  asserting `posted_by === user->id`).

## HIGH

1. **Deferred post failure after commit leaves silent inconsistency (untested).**
   `postEntryAndRefreshPartnerBalanceAfterCommit()` (`GeneralLedgerService.php:71-86`)
   defers `postEntry()` + `refreshPartnerBalance()` to `DB::afterCommit()`. The
   enclosing payment transaction has **already committed** by the time the
   callback runs. If `postEntry()` throws (e.g. unbalanced-entry guard added in
   later `c54a9d6da`, hash computation, a `posted_at`/update failure), the
   `payments` row and its `journal_entry_id` are already persisted pointing at a
   journal entry that stays **Draft** with a stale partner balance — and the
   HTTP request has likely already returned 201. There is no compensating
   action, retry, or audit on afterCommit failure, and no test exercises the
   "post throws after commit" path. This is the inherent cost of choosing
   afterCommit to get rollback-safety; it should at minimum be logged/alerted
   and documented as a known reconciliation gap. [HYPOTHESIS on production
   blast radius — verified that no error handling exists around the deferred
   callback; not verified against a live failing post.]

## MEDIUM

1. **Currency fallback path can diverge from the CompanyContext scale.**
   `currencyCodeForCompany()` returns the company's stored `currency` and passes
   it as an explicit code to `getScale($currency)`, which uses the **static ISO
   4217 map** (`CurrencyScaleResolver::getScale` early return). The
   CompanyContext path instead prefers `country.currency_decimal_places`
   (`CurrencyScaleResolver.php:56-64`). For a company whose country row
   configures a non-ISO-standard decimal count, the no-context fallback and the
   context path would resolve **different scales** for the same advance. Low
   probability for current currencies (TND/EUR/GBP all match ISO), but it is a
   latent precision-contract inconsistency rather than a true equivalence
   fallback. Consider resolving via the same country-aware path or documenting
   that the fallback is ISO-only by design.

2. **No real-Postgres / hash-chain ordering verification for batched afterCommit
   posts.** When `applyAllocationFromCommand` creates both a payment-received and
   an advance entry in one outer transaction, both posts run in afterCommit and
   each `getPreviousHash()` orders by `posted_at DESC`
   (`GeneralLedgerService.php:1625-1633`); `posted_at` is a `timestamp`
   (`2025_11_30_100000_create_journal_entries_table.php:30`). Sequential `now()`
   calls differ by microseconds so ordering is normally deterministic, but this
   is a fiscal hash-chain dependency that the SQLite test suite cannot
   meaningfully validate. Pre-existing concern, not introduced here, but the
   commit increases the number of same-transaction deferred posts.
   [NEEDS-REAL-PG]

## LOW

1. `currencyCodeForCompany()` (`GeneralLedgerService.php:51-57`) silently relies
   on `companies.currency` being `char(3)` NOT NULL (confirmed in
   `2025_11_30_104000_create_companies_table.php:59`) and on the company row
   existing; a missing row would make `value('currency')` return `null` while
   the docblock asserts `string`. Safe in practice (companyId always sourced
   from a loaded entity) but the `@var string` is an unchecked narrowing.

2. The two "review" artifacts shipped with the commit
   (`…-codex-review.md`, `…-opus-fallback-review.md`) explicitly state the true
   Opus pass is still PENDING; this review closes that gap.

## Verdict

APPROVE-WITH-MINOR-EDITS

The implementation is fiscally correct, precision-safe, rollback-safe in the
common path, and the tests genuinely assert the claim. The single HIGH
(unhandled/untested afterCommit-post failure leaving a committed payment bound
to a Draft journal entry with a stale balance) is a design risk worth a
follow-up — add logging/alerting and a reconciliation note, and ideally a test —
but it does not corrupt money or balances in the success path and is not a
launch blocker for this slice.
