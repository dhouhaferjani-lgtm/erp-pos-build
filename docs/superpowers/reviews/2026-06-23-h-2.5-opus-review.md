## Summary

The claim — "customer-advance clearing during SO→invoice conversion posts when an
actor is present; actorless service conversions stay draft" — holds up under
refutation. The actor is threaded from the authenticated controller
(`request->user()->id`) through `SalesOrderToInvoiceConverter::transferPrepayments()`
into `GeneralLedgerService::clearCustomerAdvanceToReceivable()`, which posts via the
canonical `postEntryAndDispatchPostedEventAfterCommit()` path. Money handling is
correct (no float, scaled bcmath, currency forwarded). The new test is genuinely
red-first: disabling the post call leaves the entry `Draft` and the test fails at
`assertSame(JournalEntryStatus::Posted, ...)` (verified live). PHPStan L8 clean on the
three changed app files. The documented verification (6 tests / 22 assertions) passes.

No BLOCKER or HIGH issues. One MEDIUM (a new throw source — `User::findOrFail` — now
falls inside an over-broad `catch (\RuntimeException)` in the converter, masking a
distinct failure as an "accounts not configured" GL-skip) and minor LOW notes.

Verdict: APPROVE-WITH-MINOR-EDITS.

## BLOCKER

None.

- Money/precision: no float cast or `number_format((float)…)` introduced. `transferPrepayments`
  accumulates with `bcadd(..., $this->scale())` and forwards a `numeric-string` amount;
  `clearCustomerAdvanceToReceivable` keeps scaled `bccomp` guards (positive amount,
  available-advance ceiling). Currency forwarded as `(string) $invoice->currency` and
  honored downstream by `postEntry` via `scaleResolver->getScale($currencyCode)`
  (`GeneralLedgerService.php:1258-1260`). `CurrencyScaleResolverInterface` is
  constructor-injected; no `app()` for scale.
- Sign convention: clearing posts Dr CustomerAdvance / Cr CustomerReceivable, both with
  `partner_id` for the subledger (`GeneralLedgerService.php:853-873`), debit==credit so
  `postEntry`'s balance guard (`:1267`) passes. Available-advance magnitude is computed
  as a non-negative magnitude (`availableCustomerAdvanceMagnitude`, `:888-917`). No sign
  confusion.
- Event immutability / hash chain: reuses `JournalEntryPosted` unchanged; no event renamed
  or restructured. Newly-posted clearing entries correctly join the fiscal hash chain
  (`fiscal_hash`/`previous_hash` set in `postEntry`, `:1273-1284`). The hash-chain
  read-then-update without a row lock in `postEntry` is a PRE-EXISTING pattern shared by
  every GL poster (lines 371/446/533/599/670/1134/…); not introduced by this commit.
- Transaction safety: posting is deferred. The converter wraps everything in
  `DB::transaction` (`SalesOrderToInvoiceConverter.php:167`); inside,
  `postEntryAndDispatchPostedEventAfterCommit` sees `transactionLevel() > 0` and registers
  a `DB::afterCommit` callback (`GeneralLedgerService.php:84-90`), so a converter rollback
  leaks no posted-state or `JournalEntryPosted` event. Correct.

  controller passes `request->user()?->id` (`DocumentConversionController.php:71`).

## MEDIUM

1. New `User::findOrFail` throw is swallowed by an over-broad catch (masking).
   `clearCustomerAdvanceToReceivable` now does
   `User::query()->findOrFail($postedByUserId)` (`GeneralLedgerService.php:810-813`).
   `ModelNotFoundException` extends `RuntimeException` (verified via reflection:
   ModelNotFound → RecordsNotFound → RuntimeException). In `transferPrepayments` the call
   is inside `try { ... } catch (\RuntimeException $e)` whose handler logs
   "Could not create GL entry for prepayment transfer" and records
   `gl_entry_skipped`/`gl_skip_reason` framed as account-configuration failure
   (`SalesOrderToInvoiceConverter.php:411-426`). So a bad/stale actor id would silently
   skip the clearing entry under a misleading "accounts not configured" message — AND, since
   payment allocations are moved to the invoice BEFORE the clearing call
   (`:367-371`), the books would show the advance unconsumed with no clearing JE. Production
   path is currently unreachable (authenticated user → valid id), so this is latent, not
   active. Recommend narrowing the catch (or letting `ModelNotFoundException` propagate) so
   an invalid actor surfaces as an error rather than a masked GL-skip. The broad catch is
   pre-existing, but this commit adds a new, semantically-different throw into it.

## LOW

1. No commit-added test for the actorless-draft branch in the CONVERSION path. The
   converter-level "actorless stays draft" assertion is only indirectly covered by the
   direct GL test. A converter test invoking `convert()` WITHOUT `actor_user_id` and
   asserting `Draft` would lock the second half of the claim at the integration layer.
   Low because the GL-level behavior is already asserted.

2. `clearCustomerAdvanceToReceivable` keeps `$user = null` lookup OUTSIDE the inner
   `DB::transaction` (`GeneralLedgerService.php:809-813`) while the converter's outer
   transaction is open. Functionally fine (the lookup is a read), but the actor existence
   check happens before the partner `lockForUpdate`, so it isn't part of the atomic guard.
   Cosmetic.

3. `cross-module` import of `App\Modules\Identity\Domain\User` into the Accounting GL
   service is pre-existing (sibling methods already type-hint `User`); not a regression.
