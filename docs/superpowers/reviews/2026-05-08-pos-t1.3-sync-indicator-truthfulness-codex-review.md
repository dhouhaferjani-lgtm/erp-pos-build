## Detailed Write-Up

### 1. MAJOR - degraded state is not exposed on the actual button accessible name

`SyncButton` still renders the parent button with `aria-label={t('sync.syncNow')}` at `apps/pos/src/components/atoms/SyncButton/SyncButton.tsx:59`. The new degraded span is rendered inside that button at lines 65-71 and has `aria-label={t('sync.degradedTitle')}` and `title={t('sync.degradedTitle')}` at lines 68-69.

That satisfies the visual/tooltip part, but not the button accessibility contract. Because the interactive element itself has an explicit `aria-label`, assistive tech names the button from that label rather than from its children. The user navigating controls hears "Sync Now", not "Last sync had errors - click to retry". This is exactly the state T1.3 is supposed to make truthful.

The test at `apps/pos/src/components/atoms/SyncButton/__tests__/SyncButton.test.tsx:85-95` only checks the child dot's attribute. It would still pass while the actionable button remains misnamed. The regression test should query the button by role/name under a degraded mock state.

Remedy: compute a button label from state, for example:

```tsx
const syncNowLabel = t('sync.syncNow');
const degradedLabel = t('sync.degradedTitle');
...
aria-label={isDegraded ? `${syncNowLabel}. ${degradedLabel}` : syncNowLabel}
```

### 2. MAJOR - startup `lastSyncAt` hydration can clobber a fresh first tick

`seedOfflineHashChain` creates and starts the scheduler at `apps/pos/src/stores/terminalStore.ts:110-113`, then hydrates `last_sync_at` from SQLite at lines 159-168. `SyncScheduler.start()` is not delayed or debounced: it calls `void this.tick()` immediately at `apps/pos/src/lib/sync/syncScheduler.ts:30-31`.

The race is:

1. `scheduler.start()` fires the first tick.
2. The tick completes `runFullSync`, then `completeSync(result)` writes a fresh `Date.now()` to memory at `apps/pos/src/stores/syncStore.ts:59-63`.
3. The boot hydration path has already read an older `last_sync_at` at `apps/pos/src/stores/terminalStore.ts:163`.
4. Hydration then writes that older parsed timestamp at lines 165-167, making the header show an older sync time after a successful startup sync.

This is narrow but real, and the local comment is currently misleading: `terminalStore.ts:134-140` says the badge is hydrated "before the first scheduler tick fires" and that the first tick is "debounced by ~1 s", but the scheduler code starts the tick immediately.

For `pendingReceiptCount`, last-write-wins is tolerable because both writers read the same SQLite truth after receipt statuses settle. For `lastSyncAt`, the stale persisted value and the fresh in-memory tick value are semantically ordered, so the older value must not win.

Remedy: either perform the `last_sync_at` hydration before `scheduler.start()`, or guard the hydration write by comparing against the current in-memory value:

```ts
const current = useSyncStore.getState().lastSyncAt;
if (current === null || parsed > current) {
  useSyncStore.getState().setLastSyncAt(parsed);
}
```
