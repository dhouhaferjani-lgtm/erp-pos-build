## Critical findings

### R5-C-1 — The closing admin commit can fabricate or rewrite ACCEPT evidence; “header quotes A” does not bind it to the bridge run

**Evidence:** The bridge prompt does not pass a separately asserted accepted SHA or require a metadata header; it asks the reviewer to inspect a diff and emit a final verdict line (`scripts/adversarial-review.sh:49-79`). The script copies the reviewer output to the register and parses `VERDICT:` (`scripts/adversarial-review.sh:82-100`). After that run, r10 permits the parent to add the register and handback in a new commit and requires only that their manually supplied headers quote A (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:407,411`). No hash, signature, immutable pre-promotion copy, bridge-run receipt, or exact-byte comparison binds the committed file to what the bridge produced. The path allowlist explicitly admits every enforcement package's register subtree and every enforcement handback (`:411`; `LEDGER.md:56`). P3 M0 then accepts a parseable ACCEPT artifact at the YAML path plus recorded commits/ancestry; it does not authenticate the artifact (`enforcement-p3.progress.yaml:22-36,80-86,102`). The brief simultaneously states that self-certification is not accepted (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:442`).

**Failure scenario:** after the real M4 reviewer returns CHANGES-REQUIRED—or without a bridge run at all—an editable file under `docs/handoff/reviews/enforcement-p2/` is created with a header naming A and a final `VERDICT: ACCEPT`; the P2 YAML is set to M4 passed/complete and points to it. Every path is admin-allowlisted, the claimed header equals A, and the ancestry checks can use real A. P3 M0 accepts a P2 package that never received ACCEPT. A less malicious version is equally concrete: the required header is prepended to the raw bridge output after review, so the landed bytes are no longer the bytes the bridge produced and no check detects further edits.

**Required repair:** make the evidence binding mechanical and pre-promotion. Have the bridge itself receive and emit candidate SHA A plus milestone/round metadata, write a detached digest/attestation over the exact output, and record that digest outside the editable closing payload before merge (for example in the owner dispatch receipt or a signed tag/attestation). Step 5 must verify exact bytes/digest before committing. P3 M0 must verify that binding, not merely parse `ACCEPT`. Narrow the allowlist to the current package's exact final paths and prohibit rewriting previously landed registers/handbacks.

### R5-C-2 — The durable pin-tag lifecycle cannot support the first dispatch and later permits deletion while CI still requires the tag

**Evidence:** The checker is required to read the tag name from the YAML mirror block, run `git fetch origin tag <pin-tag>`, and only then resolve the variable-held blob (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:173`; `enforcement-p1.progress.yaml:49-53`; `enforcement-p2.progress.yaml:38-41`). But P1-M2 and P2-M1 require metadata commit 2 to record only the seed commit and protected blob, not a planned tag (`enforcement-p1.progress.yaml:132`; `enforcement-p2.progress.yaml:121`). The owner does not push the tag until promotion step 3, after final ACCEPT (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:407-409`), while the mirror block is described as parent-updated in the post-promotion admin commit (`enforcement-p1.progress.yaml:54-56`; `enforcement-p2.progress.yaml:42-44`). Therefore accepted A is not required to carry a non-null tag name when the workflow dispatch on A consumes it. The later lifecycle is also contradictory: step 3 allows tag deletion once `origin/dev` or `origin/main` contains the protected commit (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:409`), while the checker remains specified to fetch that tag explicitly on every event (`:173,275`) and the YAML mirror still names it.

**Failure scenario:** on first promotion, A's `*_baseline_pin_tag` remains null under the operative milestone contract. The owner creates a remote tag, but A's workflow cannot discover its name from the null mirror and fails closed. If the executor guesses and records a tag despite the milestone omission, the second failure remains: after the owner legitimately deletes the tag because a permanent branch contains A, the next PR/push/manual run executes the mandated tag fetch, gets “couldn't find remote ref,” and fails closed even though the blob is reachable from the permanent branch.

**Required repair:** allocate the exact immutable tag name before the metadata commit; record it in A and review it before ACCEPT. At step 3 the owner must create that exact tag and verify it resolves to A before changing the variable or dispatching. Either retain each referenced tag for as long as any supported workflow revision names it, or define and test a permanent-ref fallback that fetches the recorded protected commit and verifies the expected blob; update the mirror/checker in a gated revision before deleting a tag. Define collision/version allocation and re-pin ordering explicitly.

### R5-C-3 — Freshness is checked before the long acceptance/dispatch interval and serializes only enforcement packages, so another lane can still invalidate exact-A promotion

**Evidence:** The brief identifies multiple active CI-writing and production lanes and requires P2 announcements to all of them (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:75,78`). The promotion rule serializes only these enforcement packages: one package completes steps 0–5 before another package's step 0 (`:405`; `LEDGER.md:56`). Step 0 checks the current dev tip before step 1's final ACCEPT, owner variable/tag work, remote push, and workflow run (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:406-410`). There is no second ancestry check immediately before fast-forwarding in step 4. The only route back is triggered by a step-0 failure or red dispatch (`:412`), not by dev advancing after step 0 or the fast-forward itself failing.

**Failure scenario:** enforcement P1 passes step 0 against dev tip D. While its final review or remote workflow runs, the country-defaults, UI, OpenAPI, or another parent-managed lane lands D2 on dev. P1's A still descends from D but not D2. Its remote dispatch is green, yet step 4 cannot fast-forward dev to A. A merge commit violates exact-A; resetting loses D2; and the stated “only route back” has no trigger because step 0 already passed and CI was green.

**Required repair:** serialize the critical section against every local-dev writer, not merely the three enforcement packages, or repeat `git merge-base --is-ancestor <current-local-dev-tip> A` atomically/immediately before step 4. Treat any second-check or fast-forward failure as a mandatory re-gate trigger with the same A′ procedure. The durable owner lock/coordination record must cover steps 0–5 and identify who holds it.

## High findings

### R5-H-1 — The dispatch-time trust-model assertion has no field, M0 predicate, or durable receipt

**Evidence:** F-8 requires the owner, “at each package dispatch,” to enumerate repository write principals and assert that none authors the candidate (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:427`). P1 and P2 refer to that assertion only inside baseline re-pin owner-gate prose whose status is `post_acceptance` (`enforcement-p1.progress.yaml:98-101`; `enforcement-p2.progress.yaml:90-93`). Their M0 milestones do not require an assertion or pointer (`enforcement-p1.progress.yaml:115-122`; `enforcement-p2.progress.yaml:112-119`), and neither schema has a `trust_model_ack`-style field. The live premise that this is a private personal repository is true, but it does not fill the missing per-dispatch record.

**Failure scenario:** the parent fills the ordinary base/phase/window fields and dispatches P1 or P2 without enumerating collaborators or recording the required non-authorship assertion. M0 passes and the entire wave/promotional sequence proceeds. The ratchet is then described as valid under a trust-model condition that was never checked or durably attested—breaking the recorded model on its own terms, without assuming a threat actor outside it.

**Required repair:** add a parent-owned `ratchet_trust_model_ack` field containing or pointing to the dated/commit-stamped principal enumeration and non-authorship assertion; make it a non-null P1/P2 M0 precondition. Reconfirm it at promotion if access changed, and land the final assertion/verification result in the closing receipt.

### R5-H-2 — The “only route back” omits failures and partial side effects in variable, announcement, ref, and tag operations

**Evidence:** Steps 2 and 3 mutate external state before merge: update the repository variable, send P2's announcement, push a throwaway ref, push a durable tag, and dispatch (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:408-409`). The re-gate protocol is expressly the only route back but triggers only when step 0 fails or the dispatch is red (`:412`; `LEDGER.md:56`). It does not cover a wrong variable value, variable update succeeding while tag push fails, a tag-name collision or tag pointing at the wrong commit, throwaway-ref push/dispatch API failure, or final-announcement failure/staleness before a run exists. It also says to re-set the variable only “if the seed blob changed,” which does not repair an owner typo when the seed did not change.

**Failure scenario:** the owner updates `DPA_BASELINE_PROTECTED_BLOB`, then the durable tag push fails because the chosen tag already exists at another SHA. No workflow dispatch occurs, so the red-run trigger never fires. The repository variable has already changed globally; concurrent CI sees mirror drift/unfetchability, the package cannot proceed to step 3, and the supposedly exhaustive “only route back” gives no rollback, retry, or re-gate state.

**Required repair:** define fail-closed handling after every external side effect. Preflight tag/ref availability before variable mutation; verify tag→A and variable→expected blob after writes; on any failure stop promotion, restore the last known-good variable/ref state where possible, record the partial state, and either retry the same unchanged A or enter a clearly specified re-gate path. Announcement resend rules must apply whenever A or the implementation contract changes, and all pre-promotion state must be revalidated immediately before dispatch.

### R5-H-3 — The closing allowlist check is unnamed, unrecorded, and too broad to protect previously landed evidence

**Evidence:** Step 5 says “machine check: diff ⊆ allowlist” but supplies neither a command/script nor an actor/receipt for its result (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:411`). The YAMLs repeat only the prose condition (`enforcement-p1.progress.yaml:71-75`; `enforcement-p2.progress.yaml:57-61`; `enforcement-p3.progress.yaml:63-67`). P3 M0 verifies whole-package statuses/verdicts/ancestry but does not verify that the commit(s) between `p1_landed_sha`/`p2_landed_sha` and the evidence-bearing base are exactly one closing commit with an allowlisted diff (`enforcement-p3.progress.yaml:22-50,102`). The allowlist itself covers all progress YAMLs, all three enforcement review trees, all enforcement handbacks, and the entire LEDGER, so a P2 closing commit may alter previously landed P1 evidence while still satisfying the path subset.

**Failure scenario:** while closing P2, the shared worktree also contains an edit to P1's final register or progress YAML. The parent stages the allowed paths and the path-only subset passes; no required command output identifies the extra cross-package mutation. P3 later reads the altered P1 evidence as if it were P1's original closing record.

**Required repair:** provide a checked-in verifier or exact command that compares `A..admin-tip`, requires exactly one closing commit, rejects every path outside the current package's exact progress/register/handback files plus the specific LEDGER row, and records its output/hash in the closing receipt. P3 M0 should verify the landed SHA→closing-admin→base chain and the current package-specific closing attestation. Do not permit a package's closing commit to rewrite another package's evidence.

### R5-H-4 — The evidence-closing sequence is scoped only to workflow-editing packages, leaving an allowed no-workflow package without a promotion contract

**Evidence:** The six-step sequence, including exact-A merge and the sole step that lands final register/handback/YAML completion, is introduced only for “an accepted package that touches `.github/workflows/**`” (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:405-411`). P3's receipt is likewise required only when its accepted branch touches workflows, and its own YAML calls M2 workflow editing merely “likely” (`enforcement-p3.progress.yaml:57-68`). P3 may satisfy “wire into a lane that actually runs” by placing its test in an already whole-directory-selected lane, producing no workflow diff; the brief does not require a workflow edit in every valid implementation (`CODEX-DISPATCH-enforcement-guards-2026-08-12.md:360`). Yet P3 still produces its final register/handback and final YAML status after A and needs a legal closing commit.

**Failure scenario:** P3 adds its completeness test under an existing automatically run directory, so `.github/workflows/**` is untouched. The mandatory remote-dispatch condition correctly does not fire, but the only defined sequence containing fast-forward promotion and the closing admin commit is out of scope. The parent has no operative instruction for landing A and its post-A evidence without either inventing a path or unnecessarily asserting a workflow dispatch requirement.

**Required repair:** make steps 0, 1, 4, 5, serialization, and the freshness/re-gate rules universal for every package. Make variable/tag/announcement work conditional on the relevant package and make remote dispatch conditional only on workflow edits. Define the no-workflow path explicitly, including the same evidence-binding and package-specific closing checks.
