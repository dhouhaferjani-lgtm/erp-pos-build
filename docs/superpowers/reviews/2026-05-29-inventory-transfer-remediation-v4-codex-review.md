## Summary

v4 is directionally better than v3: it drops the false product-row-lock invariant, introduces a single `ProductCostLock` helper, switches costs to pending -> confirmed, fills the v3 DTO/model holes, specifies sorted transfer loops, and acknowledges that SQLite does not prove advisory-lock serialization (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:11`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:22`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:29`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:337`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:391`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:847`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:858`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:943`).

The plan is still not implementation-ready. The central D2 claim is "every divisor-component writer" takes the same `(tenant_id, company_id, product_id)` advisory lock (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:64`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:66`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:1038`). **P1: the deadlock retry wrapper catches the wrong shape for top-level Laravel transactions.** v4's retry helper catches only `\Illuminate\Database\DeadlockException` (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:179`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:184`). In Laravel's transaction manager, a concurrency error in a top-level transaction with attempts=1 is rolled back and rethrows the original exception; `DeadlockException` is wrapped only for nested transactions (`vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:88`, `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:93`, `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:101`, `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:107`, `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:114`). Laravel's own retry mechanism is the `$attempts` argument to `DB::transaction`, and the concurrency detector recognizes PG deadlock text and SQLSTATE 40001 (`vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:26`, `vendor/laravel/framework/src/Illuminate/Database/Concerns/ManagesTransactions.php:109`, `vendor/laravel/framework/src/Illuminate/Database/ConcurrencyErrorDetector.php:20`, `vendor/laravel/framework/src/Illuminate/Database/ConcurrencyErrorDetector.php:26`, `vendor/laravel/framework/src/Illuminate/Database/ConcurrencyErrorDetector.php:28`). As written, the wrapper may not retry the very deadlocks v4 says are belt-and-suspenders.

Two-process scenario: P1 `confirmCostEvent(E)` locks cost event E, then waits for transfer T (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:743`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:745`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:755`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:757`). ## Advisory-lock correctness

The helper is transaction-scoped and no-ops on non-PG drivers (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:144`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:145`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:157`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:165`). A6 and A6b both place `costLock->acquire` inside `DB::transaction` closures, which is the correct placement for `pg_advisory_xact_lock` (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:524`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:527`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:590`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:591`).

The key identity is not correct in A6b when `expectedCompanyId` is present, as shown above (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:591`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:592`). That is enough to reopen the race even if every intended method calls the helper.

The `hashtext` collision claim is acceptable as a correctness argument: if two unrelated product keys collide, the result is over-serialization, not a missed lock, because both transactions block on the same advisory token (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:161`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:165`). It is a performance/contention risk, not a WAC-corruption risk, provided all writers of the same logical product use the same pre-hash string.

The advisory lock serializes the multi-row read only against writers that also take it. v4's own WAC read is plain `sum()` over `stock_levels` and in-transit transfer lines (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:540`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:552`). That is fine only after the uncovered writers are either routed through `ProductCostLock` or formally removed from the same WAC denominator domain.

## Pending/confirmed lifecycle + accounting

The pending -> confirmed lifecycle is internally coherent. `addCostEvent` creates `Pending` and does not call WAC (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:665`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:699`), while `confirmCostEvent` locks the cost event row, rejects reversed events, capitalizes, then marks confirmed (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:743`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:750`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:759`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:761`).

Two concurrent confirms of the same event serialize correctly: P1 locks event E with `lockForUpdate`, capitalizes, and sets `Confirmed`; P2 waits on E, then sees `Confirmed` and returns no-op (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:743`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:748`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:761`). This closes the double-capitalization shape for the same event, assuming the transaction retries are fixed for row-lock deadlocks.

Two concurrent reversals are also conceptually protected: `reverseCostEvent` creates a compensating negative event with `reverses_event_id = original->id`, and the migration adds a partial unique index on `reverses_event_id` (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:265`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:282`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:951`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:954`). P1 inserts the reversal row; P2's insert waits or fails on the unique index and should surface 409. This depends on the plan's catch being implemented around the reversal create, not just the public add endpoint.

Forward-only reversal is not algebraically restorative when the denominator changed between confirm and reverse. v4 explicitly chooses forward-only and says recorded order is the truth (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:73`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:75`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:76`), so a negative reversal over current owned units can leave WAC different from pre-confirm if intervening sales/receipts occurred. The F3 test only covers the no-intervening-sale case (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:962`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:964`). That is acceptable if documented as Decision D3, but the test name "moves_wac_back" should not imply a general invariant.

Treasury is a documented seam, not an atomic accounting guarantee. The event is afterCommit (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:767`), and Batch T says the future listener creates a pending payment and the month-end audit finds confirmed events without payment allocations (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:914`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:920`). If the future Treasury listener fails, Inventory has already capitalized cost; the audit query is the safety net, not a same-transaction guarantee. That is coherent for D4, but the UI toast "a pending payment was created in Treasury" is too strong before Treasury exists (`docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:891`, `docs/superpowers/plans/2026-05-29-inventory-transfer-remediation-v4.md:893`).
