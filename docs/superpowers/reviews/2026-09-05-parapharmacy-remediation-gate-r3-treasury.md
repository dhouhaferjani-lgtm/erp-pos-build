## 2. New findings

### BLOCKER — NEW-1. `non_money_destination` as written removes the leg's revenue+VAT recognition and the store-voucher clearing debit. The shipped seam it should reuse is not named.

**Spec:** line 165 — *"The last class dispatches by typed operation to liability, receivable or instrument-collection accounting; **it does not manufacture a payment-repository movement**. … W2 must add the explicit routing branch **before generic repository resolution**"*, and acceptance line 204 — *"LOYALTY liability … with **zero invented clearing**"*.

**Source, read at HEAD.** The per-leg Treasury entry is the *only* place POS revenue and output VAT are recognised:
- `apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php:3947-3955` — line_order 0 debits `$cashAccountOverrideId ?? $repository->gl_account_id`; `:3957-3965` then writes the revenue and per-rate VAT credit lines from the sealed split.
- `:3885-3893` records what happens when that VAT leg is missing (**W4-9**: "`4457` carried no journal line for any POS receipt … revenue was overstated by exactly the VAT, and the trial balance still closed — so nothing surfaced it").
- `:3904-3906` — *"The cash-account override is deliberately a **debit-only seam**: the revenue and VAT lines remain byte-identical across immediate and deferred POS tender legs."*
- `apps/api/app/Modules/Treasury/Application/Projections/TreasuryReceiptBridge.php:1457-1458` — the maturity leg sets `$cashAccountOverrideId = $result->portfolioAccountId` **and** `$shouldRecordMovement = false`; `:1515-1521` still calls `createPOSPaymentEntry(...)`; `:1556-1558` is the only movement suppression. **This is exactly the shape a non-money class needs, and it keeps the sale's revenue/VAT.**
- `GeneralLedgerService.php:3915-3921` — `createPOSPaymentEntry` throws when `$repository->gl_account_id` is null, i.e. a branch that resolves *no* repository cannot reach the existing writer unchanged.

And the one non-money tender that is actually implemented today books its clearing debit **through a repository movement**:
- `apps/api/app/Modules/POS/Application/Services/ReceiptPaymentService.php:372-385` — *"The receipt payment row + treasury payment + **repository GL entry** above remain … The voucher repository's GL account **should be configured as PosTenderClearing in deployment so the two journals net out** to Dr VoucherLiability / Cr Revenue."*
- `apps/api/app/Modules/POS/Application/Projections/PosCoreReceiptProjection.php:1616-1632` — *"without this guard the clearing credit would never get its offsetting debit — a permanently unmatched PosTenderClearing balance"*; `:1637` keys redemption on `PaymentInstrumentKind::StoreVoucher`.
- `GeneralLedgerService.php:2955` and `apps/api/app/Modules/Voucher/Application/Services/VoucherRedemptionService.php:45,203` — the voucher side is `Dr VoucherLiability / Cr PosTenderClearing`.

**Failure scenario.** An implementer applies line 165 literally: the non-money branch returns before repository resolution and posts only the liability/redemption side. (a) For a store-voucher leg the `Cr PosTenderClearing` posted by `VoucherRedemptionService` loses its offsetting debit — the permanently unmatched clearing balance the code comment names. (b) For **every** non-money leg the sale's `Cr Revenue` + per-rate `Cr VatCollected` lines (`GeneralLedgerService.php:3957-3965`) are never written, because they only exist inside `createPOSPaymentEntry`. A 100.000 TND sale settled 60.000 cash + 40.000 loyalty then books 60.000 of revenue+VAT instead of 100.000 — the W4-9 defect re-created, silent, and the trial balance still closes. "Zero invented clearing" (line 204) reads as a prohibition on the very clearing account the shipped design uses.

**Minimum correction (two sentences plus two census rows).**
1. State that the non-money class **replaces the debit account and suppresses only the movement-port write**, reusing the existing debit-only seam (`TreasuryReceiptBridge.php:1457-1458,1556`; `GeneralLedgerService.php:3904-3906`); the sale's revenue and sealed per-rate VAT lines are recognised exactly once for every leg regardless of class, and the branch must not sit "before generic repository resolution" in a way that skips the GL writer or its `gl_account_id` precondition (`GeneralLedgerService.php:3915-3921`).
2. Add the shipped store-voucher path to the W2 census table: `PaymentInstrumentKind` codes `store_voucher` / `restaurant_voucher` / `gift_card` (`apps/api/app/Modules/POS/Domain/Enums/PaymentInstrumentKind.php:37-42,63-80`), the deployment convention "voucher repository GL = `SystemAccountPurpose::PosTenderClearing`" (`ReceiptPaymentService.php:378-385`), and a statement of whether W2 retains that netting or replaces it — with a migration disposition for companies already configured that way.
3. Name the destination account purposes for the two non-money rows, or scope them out under D2 (see NEW-3).

**Blocks spec.** The requirement text would, applied literally, understate revenue and output VAT.

### MAJOR — NEW-2. `PaymentInstrumentKind` is an existing, code-keyed tender-classification source of truth with a mandated TS mirror; neither the spec nor the glossary declares it.

`PaymentInstrumentKind.php:26-35` calls itself *"the single source of truth that validators (`StoreReceiptPaymentsRequest`) and writers (`ReceiptPaymentService`, POS receipt projections) consult"* for which `payment_methods.code` values are instrument-bearing, and *"The TS counterpart at `apps/pos/src/lib/payment/paymentMethodKind.ts` mirrors the same code list; both must stay in sync."* Five live consumers: `PosCoreReceiptProjection.php:1510`, `ReceiptPaymentService.php:287`, `StoreReceiptPaymentsRequest.php:254`, **`PaymentMethodController.php:345`** (Treasury configuration validation) and the enum itself. `apps/pos/src/lib/payment/paymentMethodKind.ts:22-26` is the mirror.

Spec:163 declares the derivation inputs as three flags plus "the typed tender operation/redemption handler's economic meaning", and the glossary **Tender classification** row repeats that list. Neither names this enum. Convention 11 class: an undeclared second surface for the same concept. Note also that the seeded catalogue and this SoT are **disjoint** — no seeder writes `store_voucher`/`restaurant_voucher`/`gift_card` (grep of `database/seeders/`), while the seeded FR `MEAL_VOUCHER` (`PaymentMethodSeeder.php:338`) is *not* instrument-bearing under `requiresInstrumentForMethodCode()`, so it carries no `instrument_type`/`instrument_serial`. **Minimum correction:** add the enum + its TS mirror to the W2 census and to the glossary row's derivation, and state which of the two code vocabularies the classification keys on.

### MAJOR — NEW-3. The two non-money destinations named in the matrix have no account purpose at HEAD, and the spec does not require one to be defined and country-seeded.

`SystemAccountPurpose` contains `VoucherLiability`, `PosTenderClearing`, `MarketingGoodwillExpense`, `VoucherBreakageIncome` (`app/Modules/Accounting/Domain/Enums/SystemAccountPurpose.php:108-112`) but **no loyalty purpose** (grep for `point|loyal|reward|fideli` returns nothing), and `app/Modules/Loyalty/` references no `SystemAccountPurpose` at all — `RedemptionProcessingService.php:28,105` moves points, not GL. `InstrumentAccountPurpose` has only cheque/effet cases (`app/Modules/Treasury/Domain/Enums/InstrumentAccountPurpose.php:9-17`), and MEAL_VOUCHER's `has_maturity=false` puts it outside `HandlesMaturityTenderLeg::handles()` (`:33-37`), so the "issuer/to-collect portfolio claim" of spec:176 has no existing account. Yet acceptance spec:204 requires "MEAL_VOUCHER portfolio, LOYALTY liability" to be exercised. Purposes are seeded country defaults with a required-purposes manifest (`app/Modules/CountryDefaults/Domain/Services/ProvisioningRequiredPurposesV1.php:57` is the pattern for `PosTenderClearing`). **Minimum correction:** W2 states that any new destination purpose is named, seeded per country and classified in `ProvisioningRequiredPurposesV1` (REQUIRED vs CONDITIONAL), or those two rows are excluded from the launch matrix under D2 and marked untested rather than accepted.
