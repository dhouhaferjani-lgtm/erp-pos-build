# Otospex readiness — 02 · Onboarding + operations journey for a mechanic tenant

**Date:** 2026-08-30 · **Mode:** read-only adversarial audit (no source touched, no suite run, no server started)
**Question:** the owner wants tenant #1 to be an independent garage on **Otospex / `vertical=mechanic`**. All onboarding rehearsal to date (campaign, seeders, manual testing loop) targeted a **Tunisian parapharmacy on IziPOS**. How much of the path is vertical-agnostic and already hardened, and how much is pharmacy-shaped and untested for a mechanic?

**Headline.** The *backend* is in far better shape than the rehearsal history suggests: `mechanic` is a first-class vertical, Vehicle (41 files, 11 endpoints) and Workshop (213 files, ~50 endpoints, 3 providers) are real, fully module-gated modules with FE pages and near-perfect en/fr/ar i18n, and `DemoTenantSeeder` already builds a working garage demo tenant with customers, vehicles, technicians, bundles, work orders and appointments. The gap is **not the product — it is the delivery path**. Three things block a garage today, in order: (1) **there is no Otospex web build deployed anywhere** — `VITE_APP_PRODUCT` is a build-time constant, the only staging target is the IziPOS build, and the previous `otospex.otospex.dev` deployment has been deleted from the repo without trace; (2) **the entire onboarding promotion gate is hard-wired to Parapharmacy** — `journey.ts:325` is an unconditional `expect(parapharmacyOption).toBeVisible()`, so the campaign cannot even *register* a mechanic tenant, and every leg L1–L10 sits downstream of it; (3) **a garage cannot import its book of business** — no vehicle importer exists at all, and no labour/service importer, so day-one data entry is manual.
