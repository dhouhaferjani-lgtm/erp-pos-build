## 0. Executive answer in five sentences

1. A **buyer-initiated multi-supplier RFQ engine is already shipped** in the ERP — fan-out create, per-supplier
   response recording, a side-by-side comparison grid with best-price highlighting, and an ordered-lock
   award-to-PO — but it is **entirely manual at both ends**: "send" writes a timestamp and mails nothing, and
   the supplier's quote is **retyped by the operator**.
2. **Award is winner-takes-all**: one sibling converts to a PO, every other sibling is Cancelled with
   `closed_reason: 'lost'`. **Mix-and-match across suppliers is structurally impossible today**, not merely
   missing a UI.
3. **There is no outbound messaging transport of any kind beyond transactional email**, and no inbound message
   ingestion at all: no WhatsApp, no SMS, no IMAP, no mailbox poller, no message-webhook receiver, anywhere in
   the monorepo. `partners` has exactly two channel columns — `email` and `phone` — and **no `mobile`, no
   `preferred_channel`, no locale**.
4. **PurchaseHub is the opposite flow** — a supplier-push, campaign/group-buy marketplace hard-wired to the
   **parapharmacy** catalog, with the ERP side a stateless proxy with no tables, no FE and no permission gate.
   It shares nothing with the RFQ engine and is not the foundation for a sourcing agent (its supplier registry
   and API-key transport are, though).
5. **The LLM plumbing the agent needs largely exists, in the wrong app**: `apps/data-acquisition` already has a
   real multi-turn **tool-calling loop**, a **tool registry**, an **`Agent` base class with run persistence and
   provenance**, a **cost/budget guard**, and Anthropic vision + web-search + LLM-judge providers. None of it is
   reachable from the ERP, and there is **no MCP server anywhere in the monorepo**.

## 3. What a first vertical slice would actually reuse

Not a plan — an inventory conclusion, so the design session starts from facts:

- **Keep**: `DocumentType::PurchaseQuoteRequest` + the group convention + `createGroup` fan-out + the comparison FE + the award converter + the permission set + the Playwright suite. The RFQ **document model is right**; its two ends and its award grain are wrong.
- **Extend, don't rebuild**: `DocumentIngestion` (add a `supplier_quote` kind + a committer that calls `recordResponse`) is the shortest path from "a PDF quote arrived" to "the RFQ is priced" — it already extracts `description/supplier_ref/quantity/unit_price/tax_rate/line_total` with per-field confidence and a human review screen.
- **Lift from `apps/data-acquisition`**: `run_with_tools`, `ToolRegistry.to_anthropic_schemas()`, `Agent`/`AgentWriter` + `agent_runs`/`validation_log`, `BudgetGuard`, `LLMCandidateJudge`. This is a real agent runtime that today serves one vertical.
- **Reuse from the platform**: `article_cross_references` (one-hop identity, live via `PlatformIntegration/…/routes.php:49`), `supplier_profiles`, `AuthenticateApiKey` + tiered quotas (the API/MCP front door).
- **Build from zero**: G1 outbound transport · G2 channel identity · G3 inbound capture · G4 split award · G5 supplier-SKU/price table · G6 supplier ranking · G7 work-order need origination · G8 MCP.
- **Decide first (owner-gated)**: the WhatsApp provider (open since 2026-04-23), the parts-identity spec sign-off (`…parts-discovery-intake-identity-design.md`, v0.2 pending, 13 blockers cleared once), the `ArticleNumber`→`iam` folding question, and whether the sourcing agent lives on `apps/platform` (per the owner's framing) or in a new service — noting the ERP has **no LLM package in PHP by design** and every AI hop today is HTTP to a Python service.
