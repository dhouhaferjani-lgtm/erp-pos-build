# Research Baseline: HTTP Request Hygiene for a Modern Multi-Tenant ERP

**Scope**: how mature ERPs (Odoo, Frappe/ERPNext, Dolibarr) shape request traffic for form/list pages, Laravel-at-scale best practice, Stancl database-per-tenant specifics, and TanStack Query 5 SPA patterns — as a baseline to audit AutoERP (Otospex/IziPOS: Laravel 12 API + React 19/TanStack Query 5 SPA + Tauri POS + PostgreSQL DB-per-tenant + Redis/Horizon).

This is a research artifact only — no AutoERP code was read or modified to produce it.

## 1. How mature ERPs shape form-page requests

**Odoo.** The web client's ORM service is a thin abstraction over JSON-RPC that batches at two levels:
- **View metadata**: `load_views` (Odoo ≤16) / the newer `get_views` bundles the arch (XML view definition), field defs (`fields_get`), and related sub-view archs (for `one2many`/`many2one` widgets) into **one call**, so opening a form doesn't issue N calls for N widgets.
- **Record data + defaults**: `web_read` (record data) and `onchange` (server-computed derived fields, e.g. tax recompute when a line's product changes) are separate calls but are **triggered by user interaction, not on open** — the initial form open batches `web_read` with a `specification` (nested field spec, replacing the older flat `fields` list) that pulls related `many2one` display names and `one2many` sub-record summaries **in the same round trip**, avoiding a naive "read then N lookups for each FK".
- **Reference/lookup data** (e.g. `res.partner` for a customer picker) uses `name_search`/`web_search_read` **on demand** (as the user types, not preloaded), but static reference data (currencies, UOM, company config) is fetched once via `fields_get`/`ir.model.fields` and cached in the browser ORM layer; writes bust that cache via bus/longpolling invalidation.
- List views use `web_search_read` which folds **search + read + total count** into one call with a `specification` for exactly which fields (including nested `x2many` previews) to fetch — this is the direct analogue of "compound form-init endpoint." Default page size is 80; `search_read`'s underlying `limit` historically defaulted to 100 unless overridden.
- **Target request count to open a form: 1** (metadata is cached after first navigation to that view/model in the session; only `web_read`+`specification` is needed on subsequent opens of the same model).

Sources: [Odoo ORM API — 18.0 docs](https://www.odoo.com/documentation/18.0/developer/reference/backend/orm.html), [Odoo JS reference (odoo-master)](https://odoo-master.readthedocs.io/en/master/reference/javascript.html), [XML-RPC search_read 100-record limit thread](https://www.odoo.com/forum/help-1/xml-rpc-api-search-read-method-100-records-limitation-216563).

**ERPNext/Frappe.** `frappe.call()` is the universal RPC envelope; `frappe.client.get_list`/`get_all` return **batches** (default page length 20, override with `limit_page_length`), never single-row-per-call. Two caching layers keep lookups cheap:
- **Client-side doctype meta cache**: `frappe.get_meta('DocType')` is fetched once per doctype per session (contains field list, `fieldtype`, `options`, required validations, link filters) — every subsequent form render of that doctype reuses it with **zero network calls**, which is exactly the "meta endpoint with client cache" pattern the audit should look for in AutoERP.
- **Server-side doc cache**: `frappe.get_cached_doc()` looks up in Redis before hitting Postgres/MariaDB, claimed **10000x+ read throughput** over `get_doc()` for hot/small documents (settings singletons, UOM, currency).
- Bulk mutation: `frappe.db.bulk_update()` compresses N row updates into a single `UPDATE ... CASE` statement rather than N round trips — the analogue of "don't make the client loop PATCH calls."
- **Target: 1–2 requests to open a form** — 1 for the record (`frappe.client.get` includes linked display values via `__onload` bundling), meta already cached.

Sources: [Frappe Database API docs](https://docs.frappe.io/framework/user/en/api/database), [Frappe Document API — Medium](https://medium.com/@waliullahthebo/frappe-framework-document-api-the-complete-developer-reference-1e5d7bddc9b3), [Tej Pochiraju — ORM cached doc](https://tej.sh/blog/frappe-cached-doc/), [Frappe Developer Cheatsheet — GitHub wiki](https://github.com/frappe/frappe/wiki/Developer-Cheatsheet), [Get doctype Metadata — Frappe Forum](https://discuss.frappe.io/t/get-doctype-metadata-from-rest-api/86083).

**Dolibarr.** Older, PHP-classic architecture: pages are largely server-rendered (not SPA/RPC-driven), so the "request count" metric doesn't translate directly — a form page IS one HTTP request (full page render) with reference data (`html.formclass.php` helpers for dictionaries: countries, VAT rates, units) pulled from **in-process PHP object caches populated once per request from small, rarely-changing dictionary tables**, not from client-side JS caching. The lesson for AutoERP is the *pattern*, not the transport: dictionary tables (countries, VAT codes, payment terms, units) should be loaded once per request/session server-side and never re-queried per form field.

**Common anti-pattern all three avoid — the one AutoERP should be graded against**: a naive SPA/API pairing does `GET /product/:id` then separately `GET /taxes`, `GET /units`, `GET /categories`, `GET /suppliers?search=`, `GET /warehouses`, one per `<select>` on the form — turning a single logical "open form" action into 6–10 physical HTTP requests. All three benchmarks either (a) bundle these into one compound response, or (b) cache them client-side across form opens so only the *first* form of a session pays that cost.

## 2. Laravel API best practices at scale

- **FormRequest for every write.** Validation lives in a `FormRequest` class, not inline `$request->validate()` in controllers — testable in isolation, keeps controllers thin, and is where request-size/regex ceilings belong (per AutoERP's own precision-contract rule 19: money/qty regex ceilings on top of `numeric`).
- **Allow-listed sort/filter/include columns.** `spatie/laravel-query-builder`'s core guarantee: **only parameters explicitly declared via `allowedSorts()`/`allowedFilters()`/`allowedIncludes()` are honored**; anything else throws `InvalidSortQuery`/`InvalidFilterQuery` rather than silently building a query off a client-supplied column name (this is the standard defense against sort-column SQL injection and against a client requesting an unindexed sort that tanks the DB). Field selection (`allowedFields()`) additionally prevents accidental over-fetch of large text/JSON columns on list endpoints. [Spatie docs](https://spatie.be/docs/laravel-query-builder/v7/introduction), [Sorting docs](https://spatie.be/docs/laravel-query-builder/v7/features/sorting).
- **Bounded `per_page`, cursor pagination for big tables.** Offset pagination (`->paginate()`) degrades on large offsets (`OFFSET 50000` still scans+discards 50000 rows in Postgres); cursor pagination (`->cursorPaginate()`, keyset on an indexed column) is the standard fix for tables that can realistically reach tens of thousands of rows per tenant (stock movements, audit log, journal entries, POS receipts). `per_page` must be **clamped server-side** (e.g. `min($request->per_page, 100)`), never trusted verbatim — an unbounded `per_page=100000` is a denial-of-service vector as much as a UX one.
- **API Resources vs `toArray()`.** `JsonResource` classes make the wire shape explicit and decoupled from the Eloquent model's column set; a bare `Model::toArray()` or `$model->toJson()` leaks every column (including ones added later) and can't omit heavy computed/JSON columns per-endpoint. Resources are also the natural place to `whenLoaded()` a relation, which forces callers to be honest about what was eager-loaded.
- **Eager loading + `preventLazyLoading()` in non-prod.** `Model::preventLazyLoading(!app()->isProduction())` throws `LazyLoadingViolationException` whenever code accesses an un-eager-loaded relation — the single highest-leverage guard against N+1 in a codebase with many controllers/resources. `Model::shouldBeStrict()` bundles this with `preventAccessingMissingAttributes()` and `preventSilentlyDiscardingAttributes()`. Recommended posture: **on in local/testing/staging (throw), off-but-logged in production** (log the violation via the `handleLazyLoadingViolationsUsing()` callback instead of crashing a live request). [PlanetScale — Laravel's safety mechanisms](https://planetscale.com/blog/laravels-safety-mechanisms), [Accreditly — preventLazyLoading](https://accreditly.io/articles/laravel-preventlazyloading-prevent-unintended-queries).
- **N+1 detection / query-counting middleware.** A lightweight dev/staging middleware that wraps the request in `DB::listen()` and asserts/logs `count(queries) <= threshold` per route (or fails CI if a feature test exceeds a per-endpoint query budget) turns "don't introduce N+1" from a code-review nicety into an enforced regression gate — same spirit as AutoERP's own `HorizonQueueCoverageTest`/ratchet-test pattern already in the codebase.
- **Response caching / ETag.** `spatie/laravel-responsecache` (full-response cache keyed by URL+headers, tenant-aware if cache is tenant-prefixed) or manual `ETag`/`Last-Modified` + `304 Not Modified` on read-heavy, rarely-changing endpoints (dictionaries, settings, catalog metadata) avoids re-serializing and re-transferring payloads the client already has.
- **Deploy-time caching**: `config:cache`, `route:cache`, `event:cache`, `view:cache` are non-negotiable for a production Laravel deploy — a missing `route:cache` alone can add tens of ms per request from route-file parsing on every boot.
- **Octane/FrankenPHP**: worth evaluating for a request-heavy ERP because it keeps the framework booted in memory between requests (no full bootstrap per request), but requires auditing for state leakage across requests (singletons, static properties, tenant context) — a correctness risk specific to a database-per-tenant app where "forgetting to reset tenant context between requests in the same worker" is catastrophic (cross-tenant data leak). Treat as a later-stage optimization, not a baseline requirement.
- **Redis cache store vs `database` store**: the `database` cache driver adds a Postgres round-trip (and, in a DB-per-tenant setup, potentially hits the *wrong* database depending on tenant context) for every cache read/write; `redis` is the standard choice for a multi-tenant Laravel app and is required outright for tenant-prefixed Redis caching (see §3).
- **Spatie `laravel-permission` cache**: permission/role lookups are cached (default 24h) keyed by a store key; a database-per-tenant app must ensure this cache is **tenant-scoped** (either Redis-prefixed per tenant or flushed/rebuilt on tenant switch) or permission checks can leak across tenants within the same cache store.
- **Rate limiting**: `RateLimiter::for()` named limiters, not raw `throttle:60,1` inline in route files — named limiters let risk-differentiated endpoints (auth/login vs. general API vs. POS sync vs. export) carry different budgets, and can inspect the authenticated user/tenant to vary limits (e.g. unlimited for an internal service token, tight for public auth). Sanctum's default `throttle:api` middleware group is **60 requests/min per authenticated user (or per IP unauthenticated)** unless overridden. [Laravel 13.x rate limiting docs](https://laravel.com/docs/13.x/rate-limiting), [Mohamed Said — custom limiters](https://msaied.com/articles/laravel-api-rate-limiting-custom-limiters-per-route-strategies-and-header-contracts).
- **Sanctum token expiration**: personal access tokens are non-expiring by default unless `expiration` is configured in `config/sanctum.php`; for an ERP handling financial data, a bounded token lifetime (or refresh-token rotation) plus `sanctum.expiration` is the standard hardening step.
- **Idempotency keys for POS/offline sync writes**: an `Idempotency-Key` request header, checked against a cache/table of `(key, request_hash) -> cached_response`, replays the original response byte-for-byte on retry, returns `422` if the same key arrives with a *different* payload (client bug), and `409 Conflict` with `Retry-After` if a second request with the same key arrives while the first is still processing (race). This is the correctness backbone for a Tauri POS client retrying a sale/shift-close after a dropped connection — **without it, retried writes double-post transactions**. [WendellAdriel/laravel-idempotency](https://github.com/WendellAdriel/laravel-idempotency), [conroyp.com — idempotency in Laravel APIs](https://www.conroyp.com/articles/what-is-idempotency-add-to-laravel-apis).
- **Request size limits, LIKE wildcard escaping, JSON depth**: enforce `post_max_size`/Nginx `client_max_body_size` at the edge; any user-supplied search string fed into a `LIKE` clause must escape `%`/`_` (Eloquent's `whereLike` doesn't auto-escape) to avoid both incorrect matches and a DoS via a pathological wildcard pattern; JSON request bodies should have a depth/size ceiling (Laravel's default `json_decode` depth is 512 — fine, but nested attacker-controlled payloads on `jsonb` columns should still be bounded at the FormRequest level).

## 3. Multi-tenant specifics (Stancl, database-per-tenant)

- **Tenant resolution cost per request**: every request pays a "which tenant, which DB" lookup (domain/subdomain/header → tenant row in `synerivia_central`) *before* the tenancy bootstrappers run. This lookup itself should be cached (tenant-by-domain lookups are prime candidates for a short-TTL Redis cache) — otherwise every single request, including cheap ones, does an extra central-DB round trip purely for routing.
- **Cache key prefixing per tenant**: `stancl/tenancy`'s cache tenancy bootstrapper prefixes cache keys with `%tenant%` (tenant key) so the *same Redis instance* safely serves all tenants without key collisions — this requires `tenancy.redis.tenancy = true` **and** `phpredis` (not `predis`) as the Redis client. Any code that bypasses the tenancy-aware `Cache` facade (e.g. raw `Redis::get()` with a hand-built key) silently escapes this prefixing and is a cross-tenant leak vector — a specific thing to grep for in the audit.
- **Cache store location**: central-DB-only data (tenant directory, plans, super-admin) should cache in a store scoped to the `central` context; tenant-scoped data must cache in the tenant-prefixed store. Mixing the two (e.g. caching a tenant's permission list under an unprefixed key while `CompanyContext` is unset, as flagged by AutoERP's own rule 20 for queued jobs) reproduces the exact class of bug the codebase has already hit with fiscal projections running with no `CompanyContext`.
- **Connection pooling (pgbouncer)**: opening a fresh Postgres connection per request is expensive on its own, and multiplies badly when every tenant is a *separate database* — the OS/Postgres has a hard limit on concurrent connections, and N tenants × M app workers can exhaust it fast without pooling. PgBouncer (transaction-pooling mode) in front of Postgres is the standard mitigation, alongside caching resolved tenant *connection config* (host/db name/credentials) so the tenancy bootstrapper doesn't re-derive it from the central DB every request. [Tenancy for Laravel — configuration](https://tenancyforlaravel.com/docs/v1/configuration/), [kokil.com.np — multi-tenant SaaS Laravel 2026](https://kokil.com.np/blog/building-multi-tenant-saas-applications-in-laravel).
- **Per-tenant rate limits**: a single global `RateLimiter` bucket punishes noisy-neighbor scenarios (one tenant's bulk import saturates the API for everyone) unless the limiter key includes the tenant id, not just the user id — `RateLimiter::for('api', fn ($request) => Limit::perMinute(120)->by($request->user()?->id ?: $request->ip()))` should be `->by(tenant_id . ':' . user_id)` in a multi-tenant system, or paired with a separate coarser per-tenant ceiling.
- **Queue worker tenant context**: Horizon workers process jobs from a shared queue across all tenants; every job must **explicitly** re-establish tenant context (`tenancy()->initialize($tenantId)`) rather than inheriting it from whatever request enqueued it — AutoERP's rule 20 already codifies this for fiscal projections/currency scale; the same discipline applies to any job doing cache reads/writes or DB queries, since a worker that forgets to switch tenant DB context will silently operate against the *previous* job's tenant database.

## 4. React 19 / TanStack Query 5 patterns for ERP SPAs

- **`QueryClient` defaults, tiered by data volatility.** A single global `staleTime` is wrong for an ERP — reference data (tax rates, units, currencies, warehouse list, company settings) changes rarely and should default to **`staleTime: 5–30 minutes`** (or `Infinity` + manual invalidation on the rare admin edit), while transactional data (stock levels, open orders, cash drawer state) should stay near TanStack's own default of **stale-immediately** (`staleTime: 0`) so a background refetch is always eligible. A tiered `defaultOptions.queries.staleTime` plus per-query overrides (via a small `queryOptions` factory per domain) is the standard structure.
- **`placeholderData: keepPreviousData`** (the v5 replacement for v4's `keepPreviousData: true`) on every paginated/filterable list query — without it, changing a page number or filter flashes the list to a loading/empty state instead of showing the previous page's rows dimmed while the next page loads. This is a purely additive UX/perceived-perf fix with no correctness downside. [TanStack — Placeholder Query Data](https://mintlify.wiki/tanstack/query/guides/placeholder-query-data), [GitHub discussion #6460 on the v5 migration](https://github.com/TanStack/query/discussions/6460).
- **`enabled` guards**: any query whose key depends on a value that may be temporarily absent (selected company, selected location, a picked customer before a dependent product-list query can run) must use `enabled: !!dependency` — an un-guarded query fires with `undefined` in the key/params, either 404s or (worse) silently queries the wrong/default scope.
- **Debounced search**: a live-typing search box wired straight to a query key fires one request per keystroke; standard fix is a `useDebouncedValue` (150–300ms) between the input and the query key, combined with `keepPreviousData` so the list doesn't blank between keystrokes.
- **Prefetching on hover/route**: `queryClient.prefetchQuery` on row hover (for a detail panel) or in a route loader (React Router/TanStack Router) hides the form's first-load latency behind the user's dwell time on the list — directly analogous to Odoo/Frappe's meta-cache-warm-on-first-visit pattern, but achievable per-navigation instead of per-session.
- **`select` to trim payloads**: when an endpoint necessarily returns more than a given view needs (e.g. a shared "product" endpoint used by both a picker and a full edit form), `select` in `useQuery` derives the trimmed shape client-side while the cache still stores the full response once — cheaper than adding N narrower endpoints.
- **Structural sharing**: on by default in TanStack Query — but only helps if the server returns *stable* object identities for unchanged rows (i.e. the API shouldn't wrap every list response in a fresh timestamp/nonce that busts structural equality); worth checking that list responses don't include a volatile field that defeats memoization in consuming components.
- **Invalidation granularity**: mutations should invalidate the *narrowest* matching query key (e.g. `['products', productId]` and the specific list key it belongs to) rather than a blanket `invalidateQueries({ queryKey: ['products'] })` that refetches every open products query on the page, including unrelated filters/pages — AutoERP's own `tenantScopedKey([...])` convention (rule 14) is the right place to also standardize a **key hierarchy** (`[tenant, company, 'products']` → `[..., 'products', 'list', filters]` → `[..., 'products', 'detail', id]`) so invalidation can target precisely.
- **Request dedup**: automatic within TanStack Query for identical in-flight query keys — but only if two components actually construct the *same* key; ad-hoc key construction (string concatenation vs. a shared factory) is the usual way this silently breaks and produces duplicate in-flight requests.
- **Avoiding waterfalls — parallel `useQueries` vs. a single aggregate endpoint**: when a form needs several independent reference lists (units, taxes, categories) plus the record itself, either (a) fire them in parallel via `useQueries` (client-side parallelism, still N requests but not serialized) or (b) have the backend expose one aggregate "form-init" endpoint bundling record + all needed reference data (server-side compound response, matching Odoo/Frappe's approach). (b) is strictly better for latency (1 round trip vs. N, even parallel N pays N×TLS/HTTP overhead and N×tenant-resolution cost per §3) and should be the default for any form that needs ≥3 reference datasets.
- **Persisting reference caches (`persistQueryClient`) for POS-like clients**: a Tauri POS client benefits enormously from persisting the `QueryClient` cache (IndexedDB/localStorage via `@tanstack/query-persist-client-core`) across app restarts — reference data (products, taxes, units) survives a relaunch without a network round trip, critical for the POS's offline-tolerant design already documented in AutoERP rule 20.
- **Optimistic updates**: for POS-speed interactions (adding a cart line, marking a stock count), `onMutate` optimistic cache writes + rollback on error keep the UI instantaneous while the real write is in flight — but must be paired with the idempotency-key mechanism (§2) so a retried write after a rollback+retry doesn't double-apply server-side.
- **Retry policy**: TanStack's default is 3 retries with exponential backoff for queries; for **mutations**, the default is *no* automatic retry (correct, since a naive auto-retry on a write is unsafe without idempotency keys) — any custom mutation retry logic added on top must be idempotency-key-backed, not bare re-POST.

## 5. Proposed AutoERP budgets (with rationale)

| Metric | Budget | Rationale |
|---|---|---|
| Requests to open a create/edit form (excluding auth/bootstrap) | **≤ 2** | Matches Odoo (1, metadata cached) / Frappe (1–2, meta cached); allows 1 aggregate init call + at most 1 rare/heavy lookup not worth bundling |
| Requests to open a list/grid page | **≤ 2** | List+count in 1 call (spatie query builder + Resource with meta), optional 1 for facets/filters if not embedded |
| `per_page` default / hard cap | **25 / 100** | Matches Frappe's `get_list` default of 20 rounded up for UI density; a 100 cap prevents unbounded payloads and OFFSET blowups on large tenant tables |
| Cursor pagination threshold | **required beyond ~10k rows per tenant table** (stock movements, journal entries, POS receipts, audit log) | Offset pagination cost grows with offset; these are exactly the tables that grow unbounded over a tenant's lifetime |
| DB queries per API request (list endpoint) | **≤ 15**, flat regardless of row count | `preventLazyLoading` + eager loading discipline; growth with N is the N+1 signature to catch |
| DB queries per API request (form-init/aggregate endpoint) | **≤ 25** | Slightly higher ceiling since it deliberately bundles several reference datasets, still must not scale with record count |
| p95 latency, list/search endpoints | **≤ 400ms** | Standard perceived-responsiveness threshold for interactive grids; achievable with proper indexing + eager loading + Redis-cached reference joins |
| p95 latency, cached reference-data endpoints | **≤ 250ms** (ideally < 100ms once Redis-warm) | These should rarely hit Postgres at all in steady state |
| Max serialized payload per grid row | **≤ 2KB** | Forces explicit field selection (API Resources / spatie `allowedFields`) instead of dumping full model + relations per row |
| Rate limit, general authenticated API | **120 req/min per (tenant, user)** | Above Sanctum's raw default (60/min/user) to accommodate a data-dense SPA firing several parallel queries, but still bounded and tenant-isolated |
| Rate limit, POS sync endpoints | **higher/burst-tolerant, keyed by device+tenant**, paired with mandatory idempotency keys | POS retries after connectivity loss are expected traffic, not abuse — must not be throttled into failure, but every retry must be idempotent |
| Rate limit, auth endpoints | **5/min per IP** | Standard brute-force mitigation |
| Reference-data `staleTime` (taxes, units, currencies, company settings) | **5–30 min**, or `Infinity` + explicit invalidation on admin edit | These change on the order of "days," not "seconds" — treating them like transactional data wastes requests |
| Transactional data `staleTime` (stock, open orders, cash session) | **0** (TanStack default), rely on `keepPreviousData` for UX smoothing | Must reflect near-real-time state; caching here risks stale-money bugs |
| Idempotency key coverage | **100% of POS/offline-sync mutation endpoints** | A single unretried duplicate POST is a double-posted sale/duplicated stock movement — a fiscal-integrity issue given AutoERP's hash-chain compliance model |

## Audit checklist

Numbered, yes/no, runnable against the AutoERP codebase.

1. Does opening a create or edit form for a common entity (product, customer, sale, purchase order) fire more than 2 network requests, excluding auth/bootstrap? (Check via Playwright network capture or browser devtools on a cold cache.)
2. Is there a compound "form-init"/"meta" endpoint pattern anywhere in `apps/api` (one controller action returning record + reference lists), or is every reference `<select>` backed by its own `useQuery`/endpoint?
3. Do reference-data hooks (taxes, units, currencies, categories, warehouses, payment terms) set a `staleTime` ≥ 5 minutes, or do they default to `staleTime: 0` like transactional data?
4. Are paginated list queries (products, orders, stock movements, journal entries) using `placeholderData: keepPreviousData` in v5 syntax, or do they flash empty on page/filter change?
5. Do search inputs feeding a `useQuery` key debounce (150–300ms) before firing, or does every keystroke trigger a request?
6. Do dependent queries (e.g. product list scoped to a selected company/location) use `enabled: !!dependency`, or can they fire with an undefined/default scope?
7. Is `Model::preventLazyLoading()` (or `shouldBeStrict()`) enabled in local/testing/staging `AppServiceProvider::boot()`? Is a production violation logged anywhere, or is the guard entirely absent in prod?
8. Pick 3 representative list endpoints (e.g. products index, sales index, stock movements index) and count actual SQL queries executed per request (via `DB::listen()` or Laravel Debugbar/Telescope) at both 10 rows and 200 rows of underlying data — does query count grow with row count (N+1 signature) or stay flat?
9. Do list endpoints use `spatie/laravel-query-builder` (or an equivalent explicit allow-list) for sort/filter/include columns, or do they interpolate request-supplied column names directly into `orderBy()`/`where()`?
10. Is `per_page` clamped server-side (e.g. `min($request->integer('per_page', 25), 100)`) on every paginated endpoint, or can a client request an unbounded page size?
11. Do any tenant tables likely to exceed ~10k rows per tenant (stock movements, journal entries, POS receipts, audit/hash-chain log) use offset (`->paginate()`) pagination instead of cursor (`->cursorPaginate()`)?
12. Do list/detail endpoints return API Resources with explicit field selection, or do any return bare `Model::toArray()`/`toJson()` (checkable by grepping for resources vs. raw model returns in controllers)?
13. Is the Redis cache store used tenant-aware (`tenancy.redis.tenancy = true`, `phpredis` driver), and does a grep for raw `Redis::` facade calls (bypassing the tenancy-prefixed `Cache` facade) turn up any cross-tenant leak risk?
14. Do queued jobs (Horizon) that touch cache or DB explicitly call `tenancy()->initialize($tenantId)` before doing any work, matching the pattern already mandated by rule 20 for fiscal projections?
15. Are named rate limiters (`RateLimiter::for(...)`) defined per traffic class (general API, auth, POS sync, exports), or is everything on Sanctum's default `throttle:api`?
16. Are rate limiter keys scoped to `(tenant, user)` / `(tenant, device)`, or only to `user`/`ip` (risking one tenant's traffic throttling another, or one tenant starving a shared bucket)?
17. Do POS/offline-sync mutation endpoints (sale submission, shift close, stock count submission) require and honor an `Idempotency-Key` header, replaying the cached response on retry rather than re-executing the write?
18. Is `sanctum.expiration` configured (bounded token lifetime), or do issued tokens never expire?
19. Are `LIKE`-based search filters escaping user-supplied `%`/`_` wildcards, or can a client-supplied search string produce a pathological/incorrect match?
20. Are `config:cache`, `route:cache`, `event:cache` run as part of the production deploy pipeline (check the deploy script / Dockerfile / CI workflow), or is route/config parsing happening on every request boot in production?
21. Is there any query-count or N+1 regression test/CI gate (a ratchet test analogous to AutoERP's existing `HorizonQueueCoverageTest`/tenant-uniqueness ratchets) protecting list/form-init endpoints, or is N+1 prevention purely a code-review convention with no automated enforcement?
22. Does the TanStack Query key convention (`tenantScopedKey`) also encode a hierarchy (list vs. detail, filtered vs. unfiltered) sufficient for mutations to invalidate narrowly, or do mutations invalidate broad top-level keys that refetch unrelated open queries?
23. For the Tauri POS client specifically: is `persistQueryClient` (or equivalent) used to persist reference-data caches (products, taxes, units) across app restarts, or does the POS re-fetch full reference data on every cold start?
