# Idempotency Audit — AutoERP (apps/erp)

Read-only audit. 605 POST/PUT/PATCH/DELETE routes found across `apps/api/app/Modules/*/*/routes.php` (+ `POS/routes_{held_orders,tables,orders,kitchen}.php`, `Import/Providers/ImportServiceProvider.php`, `routes/api.php`; `Compliance/Providers/ComplianceServiceProvider.php` registers GET-only routes, no mutations). All citations are `path:line` opened directly; no line number is asserted without having read the file.

Three research agents ran in parallel with the author to cover ground exhaustively: **(1)** mechanism deep-dive (stock transfer, fiscal ingestion, document posting, draft autosave, codebase-wide `idempoten*`/`Idempotency-Key` grep), **(2)** queued `ShouldQueue` job/listener re-run safety, **(3)** frontend double-submit guards on the 10 named forms. Their findings are folded into the sections below with the same evidentiary bar (every claim traceable to a file the agent or the author opened).

## C. Drafts and conversions

- **Two autosaves racing into two drafts: YES, reachable.** `DraftPersistenceService::saveDraft()`'s create branch (no `draftId` yet) has no unique constraint and no lock (`apps/api/app/Modules/Document/Domain/Services/DraftPersistenceService.php:104-119`). On the frontend, `useDraftAutoSave.ts`'s `performSave()` has **no in-flight guard** — `isSaving` is set but never read as a gate before firing a new save (`apps/web/src/hooks/useDraftAutoSave.ts:146-198`), and `saveNow()` does not await or block on an already-in-flight `performSave()` (`:203-213`). Both the debounced tick and an explicit "save now" trigger read `draftId` from the same stale closure/state — if either fires again before the first response updates `draftId`, both requests carry `draft_id: null` and both hit `createNewDraft()`.
- **Submit-from-draft consumes the draft once?** Confirm (`InvoiceController::confirm` etc.) locks the row and re-checks `isDraft()` under the lock before transitioning — correct, single-consumption guaranteed for the *confirm* step (`apps/api/app/Modules/Document/Presentation/Controllers/InvoiceController.php:607-624`).
- **Quote → Order:** NOT rejected reliably on a second conversion. `QuoteToSalesOrderConverter::convert()` checks `payload['converted_to_order_id']` on an **unlocked** `$source` fetched before the transaction opens, and `linkDocuments()` performs an unconditional `update()` with no WHERE guard and no unique index (`apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/QuoteToSalesOrderConverter.php:65-156`; `apps/api/app/Modules/Document/Domain/Services/Conversion/Concerns/CopiesDocumentData.php:202-210`). Two concurrent `convert-to-order` calls on the same quote can both pass and both create a real `SalesOrder` row.
- **Order → Invoice:** correctly rejected — `SalesOrderToInvoiceConverter` re-fetches the order with `lockForUpdate()` **inside** the transaction and re-checks `isOrderFullyInvoiced()` after the lock (`apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/SalesOrderToInvoiceConverter.php:168-197`) — the exact pattern `QuoteToSalesOrderConverter` is missing.
- **PO → Goods Receipt:** NOT reliably rejected under concurrency — `GoodsReceiptService::createDraft()` runs its remaining-quantity guard against the unlocked, controller-supplied `$po`/`$po->lines`, inside a `DB::transaction` that never re-fetches the PO with a lock (`apps/api/app/Modules/Inventory/Application/Services/GoodsReceiptService.php:129-166`). Two concurrent partial-receive requests can both pass and both over-receive.
- **Invoice → Credit Note:** not confirmed protected — `InvoiceToCreditNoteConverter::convert()` has no `lockForUpdate()` in the converter itself (`apps/api/app/Modules/Document/Domain/Services/Conversion/Converters/InvoiceToCreditNoteConverter.php:99-140`); whether `CreditNoteService::createCreditNote` locks internally was not traced this pass (§H).
- **Counting completion → adjustments:** the app-level guards (`replay_audit` marker + `COUNTING:{number}` movement probe in `ApplyStockAdjustmentsOnCountingCompleted`) are both **unlocked read-then-write**, by the migration's own admission, so two concurrent completions of the same counting can each conclude "not applied yet." A DB-level backstop closes the gap: two partial unique indexes on `stock_movements (reference_id, product_id, location_id[, variant_id]) WHERE reference_type='inventory_counting'` (`apps/api/database/migrations/tenant/2026_08_23_120000_unique_stock_movements_counting_apply.php`, docblock + `ApplyStockAdjustmentsOnCountingCompleted.php:88,147-154,206-230`).

## E. Frontend double-submit protection

Axios (`apps/web/src/lib/api.ts`): **no general mutation retry.** The only replay is a one-shot 419/CSRF retry that replays the original request verbatim (`api.ts:291-312`, guarded by `config._csrfRetried`) — safe since nothing persisted on a 419. Timeout 30000ms (`api.ts:240`); on timeout the caller cannot know if the request committed server-side. POS (`apps/pos/src/lib/api.ts`, `fetchWithTimeout.ts`) has no retry either; its own doc comment explicitly flags the "committed server-side, response dropped" hazard (`fetchWithTimeout.ts:8-11,35-39`) and defers to a separate idempotency-key reconciliation, not to this layer.

TanStack Query: `apps/web/src/lib/queryClient.ts:12` explicitly sets `mutations.retry: 0`. POS's `App.tsx:32-38` sets no `mutations` key at all, falling back to TanStack v5's own default of `retry: 0` — functionally identical, just implicit.

- **Fiscal event ingestion** (`OutboxIngestor`) — atomic `ON CONFLICT DO NOTHING RETURNING id` + hash-based payload-mismatch detection routing to quarantine instead of silent accept/duplicate. `apps/api/app/Modules/Fiscal/Application/Services/OutboxIngestor.php:891-923,1064-1156`.

- **Document cancel** — explicitly fixed for the exact TOCTOU class left open in `post()` (I-4), with a code comment naming the bug it closes. `DocumentPostingService.php:363-374`.
- **Fiscal refund compensation** — tenant/company-scoped lookup, "already applied" cash-movement guard, DB unique constraint, catch-and-replay. `RefundCompensationService.php:81-385`.
- **ApplyFiscalEventProjectionJob** — two independent overlap defenses (`WithoutOverlapping` + a DB status machine with a stale-`Running` age guard) on top of retry/backoff. `apps/api/app/Modules/Fiscal/Application/Jobs/ApplyFiscalEventProjectionJob.php:144-288`.

## Summary (for the calling agent)

**Counts by class:** doc-create ~25 routes / 0 confirmed mechanisms. doc-transition ~35 / ~9 correct, ~4 confirmed racy. stock ~45 / ~5 correct, ~2 confirmed racy (over-receipt, transfer-race-uncaught). money/GL ~55 / ~10 correct (one, Payment, has a real double-submit path in production — see I-1). fiscal-chain ~15 / 2 best-in-class + 1 shared racy path (`DocumentPostingService::post`, also money/GL). draft/autosave ~10 / update-branch correct, create-branch racy. external-side-effect ~15 / 2 correct, rest thin or unguarded outbound calls. crud ~405 / a handful of retrofit unique indexes, otherwise unexamined and low individual severity.

**P0s (2):** (I-1) `PaymentForm.tsx` never sends the idempotency key `PaymentController::store()` fully supports, and its own double-submit guard is broken (disables on RHF `isSubmitting`, but `onSubmit` never awaits `.mutate()`) — a fast double-click creates two real payments and moves money twice. (I-2) `GoodsReceiptService::createDraft()`'s over-receipt guard runs against an unlocked, stale purchase-order snapshot inside its own transaction, so two concurrent/retried goods-receipt requests on the same PO can both pass and both over-receive stock and money.

The codebase has two competing idempotency idioms living side by side: a mature "claim-then-catch-unique-violation, compare payload on replay" pattern (fiscal ingestion, `TreasuryMovementService`, POS returns, fiscal refund compensation) and a thinner "check the in-memory object, write unconditionally" pattern (Quote→Order conversion, PO→GoodsReceipt, `DocumentPostingService::post`, draft-autosave create). The fix pattern already exists in the same codebase in every case (e.g. `DocumentPostingService::cancel()` fixes the exact bug `post()` still has) — this is a consistency gap, not a missing-capability gap.
