# RBAC / Permissions Benchmark — Odoo · ERPNext (Frappe) · Dolibarr · Norms

Research date: 2026-09-09. Purpose: baseline for a spec covering roles & permissions in a multi-tenant, multi-company, multi-location Laravel ERP using Spatie `laravel-permission` with teams, React front-ends, and a POS app with PIN operators. Every factual cell cites an official doc/source URL.

---

## G1 — Permission model shape (granularity of actions)

| Odoo | ERPNext (Frappe) | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| Two layers: (1) **Access rights** (`ir.model.access`, usually declared in `ir.model.access.csv`) — model-level CRUD only: `perm_read`, `perm_write`, `perm_create`, `perm_unlink`, scoped per `res.groups`; a model with no ACL row is inaccessible to anyone. (2) **Record rules** (`ir.rule`) — row-level domain filters per operation (read/write/create/unlink), default-allow (if no rule applies, and ACL grants access, access is allowed) [Security in Odoo](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html), [ir.model.access](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.model.access.html), [ir.rule](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.rule.html). Finer actions (post, cancel, approve, refund, discount, export) are **not** part of the core ACL model — they are ad hoc `groups=` checks or `group_*` membership tests inside business logic/views (e.g. POS manager actions, purchase double-validation groups) [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html). | `DocPerm` is model(DocType)-level with a rich, standardized verb set beyond simple CRUD: `read, write, create, delete, submit, cancel, amend, report, export, import, print, email, share, set_user_permissions`, plus **permission levels 0–9** for field-group-level (column-level) restriction — a role can be granted access to only some field groups on the same DocType [Role Based Permissions](https://docs.frappe.io/erpnext/role-based-permissions), [Perm Levels](https://docs.frappe.io/erpnext/perm-levels). Actions like "approve" are modeled via **Workflow** role-gated transitions rather than a DocPerm verb. | Per-module rights defined in the module descriptor as `$this->rights[]` entries, conventionally exposed to end users as **`lire` (read), `creer` (create/write), `supprimer` (delete)**, plus module-specific "specials" (e.g. `user->user->password`, `->export`) [Module_Users (developer)](https://wiki.dolibarr.org/index.php?title=Module_Users_%28developer%29). Rights are registered in `llx_rights_def` and linked to users/groups via `llx_usergroup_rights` / `llx_user_rights` [Configuring User Permissions in Dolibarr](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-user-permissions-in-dolibarr-a-detailed-guide). Coarser-grained than ERPNext; "export", "validate", "send" are usually separate declared rights per module rather than a universal verb set. | NIST/INCITS 359 RBAC reference model defines **permissions as operation×object pairs** assigned to roles, not a fixed verb list — the standard is deliberately silent on which verbs exist, leaving that to the system [INCITS 359 overview](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/), [NIST CSRC RBAC](http://csrc.nist.gov/rbac/). OWASP: enforce access control on every request server-side, deny by default [OWASP Access Control Cheat Sheet source](https://github.com/nokia/OWASP-CheatSheetSeries/blob/master/cheatsheets/Access_Control_Cheat_Sheet.md), [A01:2021 Broken Access Control](https://owasp.org/Top10/2021/A01_2021-Broken_Access_Control/). Filament Shield / Spatie pattern: one permission string per (verb, resource) pair, verbs modeled as Laravel **Policy methods** (`viewAny, view, create, update, delete, deleteAny, restore, forceDelete, replicate, reorder`) [Filament Shield](https://filamentphp.com/plugins/bezhansalleh-shield). | Adopt ERPNext's breadth, not Odoo's minimalism: declare an explicit, closed verb enum per resource — `view_any, view, create, update, delete, restore, export, import, print` PLUS **business-action verbs as first-class permissions** (`post, cancel, approve, refund, void, discount, price_override, close_shift`) rather than burying them in ad hoc code checks. Model row-level scoping (company/location) as a *separate* concern from action verbs (see G5), matching Odoo's two-layer split. |

## G2 — Role structure

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| **Groups** (`res.groups`) are the role primitive; hierarchy is expressed via `implied_ids` — membership in a group automatically grants membership in every implied group ("Manager" implies "User") [implied_ids discussion](https://www.odoo.com/forum/help-1/add-implied-ids-in-group-37846), [Group hierarchy override guide](https://medium.com/cybrosys/how-to-override-existing-security-groups-in-odoo-13-4c5fe6a32d2f). Groups are grouped into `ir.module.category` for UI organization [category_id pattern](https://dev.to/jeevanizm/how-to-create-new-permission-groups-permission-category-7lh). Groups are DB rows editable in the UI (Settings ▸ Users & Companies ▸ Groups, developer mode) — no hard "system vs custom" split, but shipped groups like `base.group_system` (Settings/Administration) are conventionally protected by being required for superuser mode [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html). | **Role** is the primitive (a simple DocType, no built-in hierarchy/implication — composition is done via **Role Profile**, a named bundle of multiple roles assignable in one step) [Role and Role Profile](https://docs.frappe.io/erpnext/user/manual/en/role-and-role-profile) — e.g. a "Sales Supervisor" Role Profile bundles Employee + Sales Manager + Sales User + Sales Master Manager. ERPNext ships default Role Profiles (Inventory, Manufacturing, Accounts, Sales, Purchase) at install [Role and Role Profile](https://docs.frappe.io/erpnext/role-and-role-profile). **Administrator** sits above **System Manager**: System Manager has near-full rights but Administrator is unrestricted and its credentials are withheld from customers on Frappe Cloud [Administrator](https://docs.frappe.io/erpnext/v13/user/manual/en/setting-up/users-and-permissions/administrator), [System Manager permissions](https://discuss.frappe.io/t/system-manager-permissions/119394). | No built-in hierarchy — permissions are granted directly to **users or groups** (`llx_usergroup_rights`), and groups are a flat convenience aggregation, not implying other groups [Configuring User Permissions in Dolibarr](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-user-permissions-in-dolibarr-a-detailed-guide). A user flagged `admin=1` (Superadmin) bypasses rights checks. | NIST RBAC defines optional **role hierarchy** (senior roles inherit junior roles' permissions) as part of the "hierarchical RBAC" component of the reference model [INCITS 359](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/). Spatie: roles and permissions are both first-class models; a role is just a named permission bundle, no native hierarchy — hierarchy, if wanted, must be built by the app (e.g. seeding one role's permission set into another) [Basic Usage](https://spatie.be/docs/laravel-permission/v8/basic-usage/basic-usage). | Use **flat roles + explicit permission bundles per role** (Spatie's native model), and add an ERPNext-style **"role profile"/"role template"** as an *application-level* convenience for onboarding (assign N roles in one click) rather than encoding true implication in the permission engine — simpler to reason about under multi-tenant teams. Reserve one non-deletable, non-editable **System Administrator** role per tenant (protected in code, not just convention) distinct from a **platform/support** role (see G6). |

## G3 — Permission catalogue as code / auto-registration on module install-upgrade

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| Declared as **CSV** `ir.model.access.csv` (columns: `id, name, model_id/id, group_id/id, perm_read, perm_write, perm_create, perm_unlink`) plus XML `res.groups`/`ir.rule` records, shipped inside each module's `security/` folder and loaded via the module's `__manifest__.py` `data` list [Security tutorial](https://www.odoo.com/documentation/19.0/developer/tutorials/server_framework_101/04_securityintro.html), [example CSV](https://github.com/odoo/technical-training-solutions/blob/14.0-core/estate/security/ir.model.access.csv). Data files (including these CSVs) are (re)loaded **every module install AND upgrade** — `-u <module>` re-parses and re-applies them, using external IDs (`noupdate` XML attribute governs whether existing custom rows survive an upgrade) [CSV files loaded on update — issue #23630](https://github.com/odoo/odoo/issues/23630), [Struggling with ir.model.access.csv](https://www.odoo.com/forum/help-1/struggling-with-irmodelaccesscsv-182920). Net effect: **a new module's ACL rows appear automatically in Settings ▸ Technical ▸ Access Rights the moment the module is installed/updated** — no manual re-sync step; but rows with `noupdate="1"` that an admin customized are NOT silently overwritten by later upgrades (XML "no update" semantics), so custom tweaks persist while new module rows still get added. | Declared as **JSON permission blocks (`permissions` array) inside each DocType's `.json` file** in the app's source tree (`doctype_name.json`), version-controlled with the app. Registration is driven by **`bench migrate`**, which runs: before_migrate hooks → app patches → **doctype/schema sync** (DocTypes, therefore DocPerm rows, are synced from JSON to DB) → fixtures → translations [bench migrate reference](https://docs.frappe.io/framework/user/en/bench/reference/migrate), [Database Migrations](https://frappeframework.com/docs/v15/user/en/database-migrations). A `before_migrate` hook is explicitly used to **sync user permissions** as part of the migrate pipeline [bench migrate](https://docs.frappe.io/framework/user/en/bench/reference/migrate). Net effect: a new/changed DocType's permission rows appear automatically after `bench migrate` — but changes an admin made via the Role Permissions Manager UI are stored as **Custom DocPerm** overrides layered on top of the standard/shipped DocPerm, so upgrades add new standard rows without clobbering admin customizations [Custom Docperm overriding default permissions](https://discuss.frappe.io/t/custom-docperm-overriding-default-permissions/84268). | Declared in the module descriptor class (`class modMyModule extends DolibarrModules`) as a PHP `$this->rights[]` array (numero, label, defaultlevel key like `lire`/`creer`/`supprimer`) [Module_Users (developer)](https://wiki.dolibarr.org/index.php?title=Module_Users_%28developer%29); ModuleBuilder scaffolds this structure [Module ModuleBuilder](https://wiki.dolibarr.org/index.php?title=Module_ModuleBuilder). Registration happens **on module activation** (enabling the module in Home ▸ Setup ▸ Modules triggers the descriptor's `init()`, which INSERTs the declared rights into `llx_rights_def`) — i.e., permissions only materialize when a human enables the module, not automatically on code deploy; a code-only upgrade of an already-active module still re-runs `init()` on next activation/version bump to add newly declared rights. | RBAC "administrative functional specification" (INCITS 359 Part 2) formalizes permission/role/assignment as administrable objects with defined add/remove operations, but is silent on deployment/migration mechanics [INCITS 359](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/) — this is a framework-specific concern. Filament Shield generates permissions from **runtime resource/page/widget discovery** (`shield:generate`) rather than static declarations, with an `exclude` list per category, and a `buildPermissionKeyUsing()` hook for custom naming [Filament Shield](https://filamentphp.com/plugins/bezhansalleh-shield). Spatie itself has no built-in "declare in code, auto-sync to DB" mechanism — permissions are rows created imperatively (typically in seeders), and `syncPermissions()`/`syncRoles()` are the supported way to reconcile a role's permission set idempotently [Basic Usage](https://spatie.be/docs/laravel-permission/v8/basic-usage/basic-usage). | **This is the key design decision for a Spatie-based system.** Odoo's CSV-on-upgrade and ERPNext's JSON-on-migrate patterns both converge on the same principle: **permissions are declared as versioned code artifacts colocated with the module, and a migration/deploy step (not a manual UI action) idempotently syncs the DB catalogue from that code** — new permissions for a newly deployed module appear automatically; pre-existing custom role grants are untouched (Odoo `noupdate`, ERPNext `Custom DocPerm` overlay) and **new permissions are NOT auto-granted to non-admin custom roles** — they default to nobody (deny-by-default) except a protected Administrator/System-Manager-equivalent role, which the operator must then explicitly extend to other roles. Implement as: each Laravel module ships a `permissions.php` (or attribute-based discovery, Shield-style) manifest; a `permission:sync` command (wrapping `firstOrCreate` + `syncPermissions` against a Super-Admin-equivalent role only) runs in every deploy/migration; never auto-grant new permissions to tenant-defined custom roles. |

## G4 — Permission management UI capabilities

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| Two UIs: (1) simplified **Access Rights tab** on the user form — per-application dropdowns ("None" / "User: Own Documents" / "User: All Documents" / "Administrator") [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html); (2) **Technical Settings ▸ Groups** (needs developer mode) — full group editor showing "Selected Groups" (explicit) vs "Groups added automatically" (implied), with a "Users" tab and an "Inherited" view [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html). No unified role-permission matrix grid across all models in the base UI (third-party apps add one). | **Role Permission Manager**: a matrix-style page (Setup ▸ Permissions ▸ Role Permissions Manager) to pick a Role + DocType and toggle read/write/create/delete/submit/... per permission level, with "Add a new rule", multiple rules per level, and an explicit "Set User Permissions" delegation button [Role Based Permissions](https://docs.frappe.io/erpnext/role-based-permissions). A separate third-party **Role Permission Manager** app adds a single consolidated view/edit surface across native+custom role permissions [Role Permission Manager (Frappe Cloud Marketplace)](https://cloud.frappe.io/marketplace/apps/role_permission_manager). Per-user overrides exist as **User Permissions** (see G5), layered independently of the role matrix. | Per-user and per-group permission pages under Users & Groups admin; permissions are shown as toggled checkboxes grouped by module, with group-based assignment recommended over per-user to reduce management overhead [Configuring User Permissions in Dolibarr](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-user-permissions-in-dolibarr-a-detailed-guide), [Managing user roles like a pro](https://nextgestion.com/en/blog/how-to-manage-user-roles-and-permissions-like). Per-user overrides ARE first-class (rights checkbox grid is literally rendered per user, not just per group). | Filament Shield's own admin UI is a role-permission checkbox matrix grouped by resource/page/widget, generated from `shield:generate`, with search/filter — the closest OSS Laravel-ecosystem analogue to ERPNext's matrix [Filament Shield](https://filamentphp.com/plugins/bezhansalleh-shield). | Ship a **role×permission matrix editor grouped by module** (Odoo's Technical Groups view + ERPNext's Role Permission Manager combined) as the primary surface; support **per-user permission overrides** as an explicit, audited exception path layered on top of role grants (ERPNext User Permission / Dolibarr per-user checkbox pattern), not as the default workflow. Add a **"show effective permissions for this user"** read-only view (union of role grants + overrides + scoping) — none of the three OSS ERPs make this trivial in their base UI, so build it deliberately rather than copy a gap. |

## G5 — Row-level / data scoping (company, location/warehouse)

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| **Record rules** (`ir.rule`) apply a domain filter per model/group/operation; multi-company scoping is implemented as a **global record rule** referencing `company_id in user.company_ids` shipped on most business models, layered under the same default-allow/OR-combination semantics as any other record rule [Restrict access to data tutorial](https://www.odoo.com/documentation/19.0/developer/tutorials/restrict_data_access.html), [ir.rule](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.rule.html). Global rules AND with each other; rules of the same group OR together; the whole global set ANDs with the whole per-group set — i.e., row visibility = (all global rules pass) AND (at least one applicable group rule passes). Locations/warehouses are just another model with their own optional record rules; no separate warehouse-scoping primitive exists in core. | **User Permissions** — a distinct mechanism from DocPerm: a per-user rule restricting all documents containing a given Link field value (e.g. restrict a user to `Company = "Acme"` or `Warehouse = "WH-1"`), applied automatically across every DocType that links to that value [User Permissions](https://docs.frappe.io/erpnext/user-permissions), [Users and Permissions](https://docs.frappe.io/framework/user/en/basics/users-and-permissions). This is how ERPNext does Company/Warehouse/Cost-Center restriction — layered independently on top of role-based DocPerm (role says "can read Sales Invoice"; User Permission says "...only where Company = Acme"). | **Multicompany module** adds an `entity` column; all business queries must add `WHERE entity IN (getEntity($object->table_name))` — data scoping is enforced by convention in every module's SQL, not by a declarative rule engine [MultiEntity_dev](https://wiki.dolibarr.org/index.php?title=MultiEntity_dev). Users are explicitly linked to one or more entities/companies by a SuperAdmin; a newly added entity starts with only "Multi-company" + "Users & groups" rights for its group [Module MultiCompany](https://wiki.dolibarr.org/index.php/Module_MultiCompany). Dolibarr additionally has classic "see all records of this type" vs "see only records you created/are assigned to" rights on many modules (documented per-module, e.g. `->readall` style rights) [Configuring Permissions for Internal Users](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-permissions-for-internal-users-in-dolibarr). | RBAC core reference model has no native concept of attribute/row scoping — this is squarely "ABAC" territory layered on top of RBAC; NIST's RBAC standard covers only role/permission/user assignment, not data-instance filtering [INCITS 359](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/). In Laravel/Spatie terms, this maps to **Eloquent global scopes** (company/location) composed independently of role/permission checks — Spatie's teams feature scopes *role/permission assignment* to a team, which is adjacent but not the same as row-level data filtering within a team. | Treat **action permission** (can the role do X) and **data scope** (which rows of X) as two orthogonal layers, exactly like Odoo (ACL + record rule) and ERPNext (DocPerm + User Permission) both do. Implement scope as declarative, composable filters (company_id, location_id) attached per-role or per-user — not embedded ad hoc in every query like Dolibarr's convention-based `entity` filter, which is the weakest of the three models for guaranteeing coverage. Provide both **"all locations"** and **"assigned locations only"** grants per role, and support a **"see own records only"** variant (Dolibarr's own/all split) for POS operators. |

## G6 — Super admin / owner / technical admin

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| ORM-level **`sudo()`**/superuser mode bypasses all ACLs and record rules (hard-coded group/user checks may still apply); by convention `uid=1` is always superuser [Security in Odoo](https://www.odoo.com/documentation/19.0/developer/reference/backend/security.html). UI-level **Superuser mode** is gated: only users with Settings ▸ Administration access may enter it, and Odoo's own docs warn it can lock the user out of the database if misused [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html). On Odoo Online/Odoo.sh, the platform separates **database administrator** (tenant-side, via the database manager, sign-in as DB admin) from **Odoo support/platform employees**, and every action taken by Odoo employees OR the DB administrator is written to a queryable **Admin Activity Log** the tenant can view [Odoo Online docs](https://www.odoo.com/documentation/19.0/administration/odoo_online.html). | **Administrator** (username, not a role) is the true super-user, above **System Manager**; Administrator has unrestricted access while System Manager is "near-full but not absolute" [Administrator](https://docs.frappe.io/erpnext/v13/user/manual/en/setting-up/users-and-permissions/administrator), [System Manager permissions](https://discuss.frappe.io/t/system-manager-permissions/119394). On **Frappe Cloud**, tenant customers explicitly cannot log in as Administrator — credentials are withheld by the platform because a shared server may host many tenant sites and admin credential distribution would be a cross-tenant risk; System Manager is the de facto ceiling for cloud-hosted customers [Administrator docs](https://docs.frappe.io/erpnext/v13/user/manual/en/setting-up/users-and-permissions/administrator). Each Frappe Cloud tenant is a fully isolated **site** with its own database [Sites](https://docs.frappe.io/framework/user/en/basics/sites), [Multi-Tenancy](https://prilk.frappe.cloud/docs/frappe-framework/multi-tenancy) — the platform's separation is at the infrastructure layer, not just role layer. | A user flag `admin=1` grants Superadmin status that bypasses standard rights checks; multicompany setups still require a SuperAdmin to assign per-entity rights to a new entity/company [Module MultiCompany](https://wiki.dolibarr.org/index.php/Module_MultiCompany). No documented platform-vs-tenant separation model (Dolibarr is typically self-hosted per instance, not a shared multi-tenant SaaS). | Spatie's own documented pattern is **not** "give super-admin all permission rows" but a **`Gate::before` short-circuit**: `Gate::before(fn($user,$ability) => $user->hasRole('Super Admin') ? true : null)` — must return `null` (not `false`) so it doesn't interfere with normal policy resolution, and only affects checks that go through Laravel's `Gate`/`can()` — direct calls to `->hasPermissionTo()` bypass it [Defining a Super-Admin](https://spatie.be/docs/laravel-permission/v8/basic-usage/super-admin). Filament Shield mirrors this with a dedicated `super_admin` role option plus a `shield:super-admin` command to bootstrap the first super-admin account [Filament Shield](https://filamentphp.com/plugins/bezhansalleh-shield). | Mirror Odoo/ERPNext/Frappe Cloud precisely: (1) a **platform-operator role** (Synerivia staff) that is infrastructure-level, never assignable through tenant UI, and logged on every use; (2) a **tenant System Administrator role**, assignable by the tenant, that is the ceiling *within that tenant's data* — implemented as Spatie's `Gate::before` super-admin pattern scoped additionally by team/tenant so it can never cross tenant boundaries; (3) **last-admin protection**: block removing/demoting the last System-Administrator-equivalent user of a tenant (none of the three OSS ERPs document this explicitly — it is a gap worth closing rather than copying); (4) never let `->hasPermissionTo()`/direct package calls bypass the Gate — audit all authorization call sites go through `can()`/policies per the Spatie caveat. |

## G7 — Least-privilege defaults for a new user

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| A newly invited internal user gets **no application access by default** and must be assigned a role per app via the Access Rights tab; Odoo ships **per-app default role pairs** ("User" / "Manager") so admins pick a sane starting tier per app rather than per individual permission [Access rights](https://www.odoo.com/documentation/19.0/applications/general/users/access_rights.html). Portal and Public are separate, more restricted user types by default. | New users get **no Roles** until explicitly assigned (or a Role Profile is applied); ERPNext ships **standard roles per module** ("Sales User"/"Sales Manager", "Purchase User"/"Purchase Manager", "Accounts User"/"Accounts Manager", "Stock User"/"Stock Manager", etc.) as the out-of-the-box granularity to assign [Role Based Permissions](https://docs.frappe.io/erpnext/role-based-permissions), [Role and Role Profile](https://docs.frappe.io/erpnext/role-and-role-profile). | **Nothing granted until explicitly configured** — a new user/group in Dolibarr has zero rights by default; every permission (per module, per action) must be turned on deliberately [Configuring User Permissions in Dolibarr](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-user-permissions-in-dolibarr-a-detailed-guide). This is the strictest of the three. | OWASP: deny access by default unless explicitly allowed; least privilege = minimal necessary access [Access Control Cheat Sheet](https://github.com/nokia/OWASP-CheatSheetSeries/blob/master/cheatsheets/Access_Control_Cheat_Sheet.md). NIST RBAC's "role assignment" relation is empty by default for a new user in any correct implementation — no user has any role except by explicit assignment [INCITS 359](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/). | Default a newly created user to **zero permissions** (Dolibarr-strict), but ship a curated set of **starter role templates per module/vertical** (Odoo's User/Manager pairs, ERPNext's module role pairs) so onboarding an employee is "pick 1–3 templates," not "toggle 200 checkboxes." Never auto-grant "all current module permissions" to a role as a side effect of creating it. |

## G8 — Separation of duties & approval permissions

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| **Double validation on purchases**: enabled in Purchase settings; when a PO's amount exceeds a configured threshold it is force-routed to a "To Approve" stage; only users in the **"Purchase Order Double Approval"** group (distinct from the ability to create/confirm a PO) can approve/refuse it, with approver, approval date, and refusal reason tracked [How to set up two levels of approval](https://odoo-users.readthedocs.io/en/latest/purchase/purchases/rfq/approvals.html), [Purchase Order Double Approval](https://www.softhealer.com/blog/odoo-2/post/purchase-order-double-approval-369). This is a distinct permission from `purchase.group_purchase_user`/`group_purchase_manager` — creating ≠ approving. | **Workflow** documents define named **Workflow States** and **Transitions**; each transition specifies the triggering action, the resulting state, and **which Role(s) are allowed to perform it**, with optional conditions (e.g., "leave > 5 days requires Role X approval") — so create/approve are cleanly separated by assigning different roles to different transitions [Workflow](https://docs.frappe.io/erpnext/workflow), [Workflow State](https://docs.frappe.io/erpnext/user/manual/en/workflow-state). Multi-level approval chains (manager → senior manager → general manager) are natively expressible as a chain of states/transitions. | No native workflow-transition engine in core; separation of duties is achieved by NOT granting the "validate"/"approve" right on a module to the same group that has "create," relying on the per-module rights list (e.g. an invoice module typically separates create rights from validate/approve rights) — enforcement is per-module convention rather than a generic engine [Configuring Permissions for Internal Users](https://dolimarketplace.com/en-us/blogs/dolibarr/configuring-permissions-for-internal-users-in-dolibarr). | NIST RBAC explicitly includes **Static and Dynamic Separation of Duty (SSD/DSD)** as an advanced RBAC component in INCITS 359 Part 1 — SSD prevents a user from ever holding two conflicting roles simultaneously; DSD prevents exercising both within one session [INCITS 359](https://blog.ansi.org/ansi/role-based-access-control-rbac-incits-359/). This is the most rigorous of all sources reviewed — neither Odoo, ERPNext nor Dolibarr implement generic SSD/DSD; they only implement it ad hoc per document type (PO double approval, workflow roles). | Model approvals as **ERPNext-style workflow transitions gated by role**, not just a binary "approve" permission — this scales to multi-tier approval chains and threshold-based routing (Odoo's double-validation amount) as a special case (a transition condition). Explicitly forbid the same permission granting both "create" and "approve" on financially significant documents (PO, expense, refund) — enforce this as a lint/seed-time check, approaching NIST's SSD concept without building a full SSD engine. |

## G9 — POS operator permissions (PIN / manager override)

## G11 — Permission caching & invalidation

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| `ir.model.access` checks are backed by an in-process/registry cache; changing a group's membership or an ACL/record-rule row triggers Odoo's standard **registry/ormcache invalidation** so the new rules apply on the next request (implementation detail of the ORM registry, not a separately documented "clear ACL cache" command in the sources reviewed here — treat as inferred from Odoo's general ormcache invalidation pattern referenced in ir.model.access/ir.rule docs [ir.model.access](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.model.access.html), [ir.rule](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.rule.html)). | Frappe's caching is **best-effort auto-invalidation**: ORM writes (`doc.save`, `frappe.db.set_value`) clear the affected document's cache automatically, but **raw SQL writes do not**, requiring a manual `frappe.clear_document_cache(doctype, name)` [Caching](https://docs.frappe.io/framework/user/en/guides/caching). For multi-tenant caching, verify the cache **store** is per-request/per-process safe under horizontal scaling (Redis-backed, not `array` driver in production), since a stale worker process cache after a role change is the most likely production incident class in this area. |

## G12 — Frontend/UI gating from the same source of truth

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|---|
| Views/menus/buttons declare a `groups="module.group_x,module.group_y"` XML attribute; the **server** strips elements the current user's groups don't satisfy before serving the view/menu — there is no client-side permission map to keep in sync, because the client only ever receives what it's allowed to see [Hide/View menu based on groups](https://www.cybrosys.com/odoo/odoo-books/odoo-17-development/security/hide-view-menu-based-on-groups/), [How to hide any menu for special groups](https://www.odoo.com/forum/help-1/how-to-hide-any-menu-for-special-groups-113826). For the React/Laravel stack: expose the current user's **effective permission list** (post role+override+scope resolution) in the auth/bootstrap payload (e.g., alongside Sanctum's `/user` or a dedicated `/me/permissions` endpoint) and gate FE menus/buttons from that array — never hardcode a second permission-name-to-feature map in the frontend. Every mutating request must still be independently authorized server-side (policy/middleware) regardless of what the FE rendered. |

## G15 — Testing practices (permission regression coverage)

| Odoo | ERPNext | Dolibarr | Norm / other | Recommended default |
|---|---|---|---|---|
| Access checks are enforced inside the ORM itself (`_check_access`, called by every `read`/`write`/`create`/`unlink`), so any test using the ORM with a non-superuser `env(user=...)` automatically exercises ACL + record-rule enforcement — Odoo's own test suite relies on this "test as a specific user" pattern rather than a separate permission-testing framework [ir.model.access](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.model.access.html), [ir.rule](https://odoo-development.readthedocs.io/en/latest/odoo/models/ir.rule.html). | `@frappe.whitelist()` performs **zero authorization by itself** — it only exposes a function over HTTP; the function must call `frappe.only_for(role)` or `doc.check_permission(ptype)` explicitly, which is a documented footgun (whitelisting ≠ authorizing) [Code Security Guidelines](https://github.com/frappe/erpnext/wiki/Code-Security-Guidelines), and has produced real CVE-class findings — e.g. "Multiple Authorization Bypass Vulnerabilities via `@frappe.whitelist()` Without Permission Checks" in a Frappe-ecosystem app [frappe/insights #890](https://github.com/frappe/insights/issues/890). `frappe.get_list` (permission-aware) vs `frappe.get_all` (bypasses permission filtering) is a similarly documented pitfall. | Not documented as a formalized test-suite pattern in the sources reviewed for this benchmark. | OWASP calls for **centralizing access-control logic** and testing it as a first-class concern rather than scattering ad hoc checks, precisely because scattered checks (like Frappe's opt-in `@frappe.whitelist()`) are exactly the failure mode that produces silent authorization bypasses [Access Control Cheat Sheet](https://github.com/nokia/OWASP-CheatSheetSeries/blob/master/cheatsheets/Access_Control_Cheat_Sheet.md). Add **regression tests per role** (a test matrix asserting role X can/cannot perform action Y) analogous to Odoo's "run the ORM as a specific non-superuser" pattern — i.e., write feature tests that authenticate as a seeded role and assert 200/403 rather than only unit-testing the policy class in isolation. |

## Multi-tenant SaaS specifics

**Odoo Online / Odoo.sh.** Odoo's hosted offerings keep the *tenant* super-admin (the "database administrator," managed through the database manager) distinct from Odoo's own *platform* support staff — both categories of actor are logged identically in a tenant-visible **Admin Activity Log**, so a tenant can audit both self-inflicted admin actions and any action Odoo support performed on their behalf (e.g. in response to a support ticket or maintenance) [Odoo Online docs](https://www.odoo.com/documentation/19.0/administration/odoo_online.html). Odoo.sh additionally exposes infrastructure-level access (web shell, SSH, CI) to the tenant's own developers for self-hosted-like control while still being a managed platform [Odoo.sh docs](https://www.odoo.com/documentation/19.0/administration/odoo_sh.html).

**Frappe Cloud.** Multi-tenancy is enforced primarily at the **infrastructure** layer, not just the role layer: each tenant is a **site** with its own isolated database, files, and installed apps, all hosted on a shared **bench** [Sites](https://docs.frappe.io/framework/user/en/basics/sites), [Multi-Tenancy](https://prilk.frappe.cloud/docs/frappe-framework/multi-tenancy). On top of that infra isolation, Frappe Cloud additionally withholds the **Administrator** account from tenant customers — the Administrator credential is reserved for Frappe's own platform operations (e.g. version upgrades across many hosted sites), and **System Manager** is the highest role a tenant customer can actually hold, which is a deliberate platform/tenant separation enforced by *credential custody*, not just permission scoping [Administrator docs](https://docs.frappe.io/erpnext/v13/user/manual/en/setting-up/users-and-permissions/administrator).

**Common pattern to copy.** Both platforms converge on the same shape: (1) infra/DB-level tenant isolation (a Synerivia-equivalent: database-per-tenant, which this codebase already implements per `apps/erp/CLAUDE.md`'s Stancl `PostgreSQLDatabaseManager` tenancy model); (2) a **tenant-side super-admin role that is real but capped** — it administers everything inside the tenant, never anything about the platform itself; (3) a **platform-operator identity that is categorically different from any tenant role** (not just "a role with more permissions" but a separate credential/account space), with every platform-operator action against a tenant's data logged somewhere the tenant itself can see it — this last point (tenant-visible platform-action audit log) is the one most worth deliberately replicating, since it is the concrete mechanism that makes "we promise we won't look at your data without telling you" enforceable rather than just a policy statement.

## Spatie laravel-permission with teams: documented pitfalls

- **Teams config must be set before the first migration.** `'teams' => true` (and optionally a custom `'team_foreign_key'`) has to be set in `config/permission.php` *before* running the package's initial migration; enabling teams after the fact requires generating and running an additional migration via `php artisan permission:setup-teams` [Teams permissions](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions).
- **Switching the active team requires manually unsetting cached relations.** After calling `setPermissionsTeamId($newTeamId)`, the app must call `$user->unsetRelation('roles')->unsetRelation('permissions')` (or equivalent) before the next permission check — otherwise stale, previously-loaded role/permission relations from the old team are used, silently authorizing against the wrong team's grants [Teams permissions](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions).
- **Global vs team-scoped roles.** A role created with `team_id => null` is a global role, unique across the whole application; a role created with a specific `team_id` is scoped to that team and its **name only needs to be unique within that team** — the same role name (e.g. "Manager") can validly exist in multiple teams as distinct rows [Teams permissions](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions).
- **Middleware ordering matters.** The recommended pattern is a dedicated middleware that calls `setPermissionsTeamId()` early in the request lifecycle, registered in Laravel's `$middlewarePriority` **before** `SubstituteBindings` — getting this wrong produces intermittent false 404s/authorization failures because route-model-bound checks can run before the team context is set [Teams permissions](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions).
- **Multiple guards require an explicit `guard_name`.** If the app uses more than one guard (e.g. a separate guard for POS device sessions vs web sessions), every role/permission needs `guard_name` set explicitly — each guard has its own independent set of roles/permissions [Basic Usage](https://spatie.be/docs/laravel-permission/v8/basic-usage/basic-usage).
- **Cache is only auto-invalidated through the package's own methods.** `syncPermissions()`, `syncRoles()`, `assignRole()`, `givePermissionTo()`, and role/permission `create`/`delete` all auto-reset the cache; **direct database manipulation (raw `DB::table()` writes, bulk imports, multi-DB tenant seeders) does NOT**, and will silently serve stale permissions until `app(PermissionRegistrar::class)->forgetCachedPermissions()` or `php artisan permission:cache-reset` is run [Cache docs](https://spatie.be/docs/laravel-permission/v8/advanced-usage/cache), [Artisan Commands](https://spatie.be/docs/laravel-permission/v8/basic-usage/artisan). This is the sharpest multi-tenant/multi-DB pitfall for this stack: a per-tenant-database architecture (as this project uses) means the cache store must be scoped so tenant A's cached permission set can never bleed into tenant B's request — verify the cache key strategy accounts for the active tenant connection, not just the team_id column within one shared DB.
- **`syncPermissions()` semantics are a full replace, not a merge.** `$role->syncPermissions($permissions)` sets the role's permission set to exactly the given list (removing any not included), which is the correct idempotent tool for a code-declared permission catalogue (G3) but dangerous if called with a partial list during a partial deploy.
- **Super-admin must go through `Gate::before`, returning `null` not `false`, and only protects calls that go through Laravel's `Gate`.** A direct call to `->hasPermissionTo()` (bypassing `can()`/`@can`/policies) will NOT receive the super-admin short-circuit — all authorization call sites in the app must be standardized on `can()`/policies for the super-admin bypass to be reliable [Defining a Super-Admin](https://spatie.be/docs/laravel-permission/v8/basic-usage/super-admin).

## Derived recommended defaults (10–15 bullets, each traceable to the rows above)

1. **Separate action permissions from data scope as two orthogonal layers** — action verbs (G1/G13) resolved independently from company/location row-scoping (G5) — mirroring Odoo's ACL+record-rule split and ERPNext's DocPerm+User-Permission split.
2. **Adopt a closed, explicit verb enum per resource**, CRUD-plus business actions (`post, cancel, approve, refund, void, discount, price_override, close_shift, impersonate`), not Odoo's minimal 4-verb ACL — matching ERPNext's breadth (G1).
3. **Declare permissions as versioned code (per-module manifest), synced to the DB by an idempotent deploy/migration step** — never by manual UI action — reusing Odoo's CSV-on-upgrade and ERPNext's JSON-on-migrate pattern (G3).
4. **New permissions default to nobody except the protected System-Administrator-equivalent role; never auto-grant to existing custom tenant roles on deploy** — deny-by-default at the catalogue-sync layer (G3, G7).
5. **New users get zero permissions by default**, onboarded via curated **role templates** bundling 1–3 starter roles (Odoo User/Manager pairs, ERPNext Role Profiles) rather than per-checkbox setup (G2, G7).
6. **Ship a role×permission matrix editor grouped by module**, plus a **"show effective permissions for this user"** read-only resolved view (role + override + scope) — a deliberate improvement over all three OSS ERPs' base UIs, none of which expose this cleanly (G4).
7. **Support per-user permission overrides as an audited exception path layered on roles**, not the default workflow — ERPNext User Permissions / Dolibarr per-user grid pattern (G4, G5).
8. **Implement a platform-operator role categorically separate from any tenant role** (different credential/account space, never tenant-assignable), with every platform action against tenant data logged to a tenant-visible audit log — Odoo Online / Frappe Cloud pattern (G6, Multi-tenant SaaS).
9. **Add last-admin protection**: block demoting/removing a tenant's last System-Administrator-equivalent user — a gap in all three OSS ERPs reviewed, worth closing proactively (G6).
10. **Model approvals as role-gated workflow transitions** (ERPNext Workflow pattern) with threshold-based auto-routing as a special case (Odoo double-validation) — and forbid the same permission granting both "create" and "approve" on financial documents, approaching NIST SSD without building a full SSD engine (G8).
11. **POS: manager-PIN-gated step-up authorization per action** (discount-over-X%, price override, refund, void, session-close-with-variance), each independently toggleable — Odoo's Manager Approval settings — plus profile-to-location binding (ERPNext POS Profile) (G9).
12. **Make role/permission changes, authorization denials, and impersonation sessions first-class mandatory audit events** (not opt-in field tracking like Odoo's default `tracking=True`) — combining ERPNext's mandatory impersonation logging with OWASP's "log all access-control failures" guidance (G10, G14, OWASP).
13. **Route every permission mutation through Spatie's own methods and run `permission:cache-reset` in every deploy/migration/bulk-import path**; verify the cache store is scoped correctly for a database-per-tenant architecture so no tenant's cache can serve another tenant's permissions (G11, Spatie pitfalls).
14. **Frontend renders exclusively from a server-computed effective-permission payload delivered at auth/bootstrap** (Odoo view-stripping / ERPNext bootinfo / Dolibarr shared rights-object pattern) — no second hardcoded permission map in the React app; every mutating request is still independently authorized server-side regardless of what the UI rendered (G12).
15. **CI must fail if any route/endpoint lacks an explicit permission/policy check** — directly defending against the class of bug Frappe's `@frappe.whitelist()`-without-`has_permission` produced in practice — plus a per-role regression test matrix asserting can/cannot per action (G15).
