There is **no shared/central permission table** — every tenant has its own independent Spatie catalogue.
- **Permission cache is NOT tenant-aware** — see §10 (critical finding: still open at HEAD).

## 4. Roles

- 7 Spatie roles are seeded (§2): `admin`, `manager`, `cashier`, `viewer`, `technician`, `operator`, `accountant`. Role assignment is **per-user, per-tenant** (Spatie team = `tenant_id`, §1) — **not** per-company. A user's Spatie role set is identical across every company they belong to inside a tenant; company-level differentiation is handled entirely outside Spatie by `user_company_memberships.role` (a separate `MembershipRole` PHP enum, see below) and `allowed_location_ids` (§8).
- **"Super admin" is a completely separate, non-Spatie concept.** `App\Models\SuperAdmin` (`app/Models/SuperAdmin.php`) is its own `Authenticatable` model living in the **central** database, authenticated via a dedicated `sanctum-admin` guard (`SuperAdminAuthController.php:18-26,69`), gated by `App\Http\Middleware\EnsureSuperAdmin` (checks `$user instanceof SuperAdmin && $user->role === SuperAdminRole::SuperAdmin->value` plus active status, `EnsureSuperAdmin.php:43-52`) and `RequireCentralAdminRole`/`EnsureCentralAdmin`. There is **no `Gate::before` bypass** anywhere in the codebase (`grep -rn "Gate::before" app` returns nothing) and **no `AuthServiceProvider`** exists at all (policies are registered directly in `AppServiceProvider::boot()`, §6) — super-admin bypass is entirely middleware-based (`EnsureSuperAdmin`/`RequireCentralAdminRole`), not a Gate-level global override. `SuperAdmin` has its own enum `SuperAdminRole` (`super_admin`, plus a `DefaultsEditor` variant referenced in `EnsureCentralAdmin.php:25` and `CountryDefaults/Presentation/Requests/UpdateDefaultsEditorRequest.php:26`).
- **`owner`** is not a Spatie role at all — it only exists as a value of a **different**, unrelated enum: `App\Modules\Company\Domain\Enums\MembershipRole` (`Owner`, `Admin`, `Manager`, `Accountant`, `Cashier`, `Technician`, `Viewer` — `MembershipRole.php:9-15`), used exclusively as the `role` column on `user_company_memberships` (a UI/company-scoping label with an `isAdminRole()` helper, lines 20-23), and is unrelated to the Spatie `Role` model. `DatabaseSeeder.php:346,355` assigns `MembershipRole::Owner` to the company membership row for the demo admin user, while separately assigning the Spatie `admin` role (`DatabaseSeeder.php:362-366`) — two independent "role" systems using overlapping vocabulary (`admin`, `manager`, `cashier`, `accountant`, `technician`, `viewer` are values in BOTH the Spatie `roles` table and the `MembershipRole` enum, by coincidence of naming, not by any shared code path).
- **Protected/system roles**: `RoleController::update`/`destroy` hardcode `$systemRoles = ['super-admin', 'admin', 'owner']` (`RoleController.php:228,277`) to block rename/delete. This array is **stale/inconsistent with reality**: `super-admin` and `owner` are **not** seeded Spatie role names (§ above) — only `admin` is a real, protected role; the other two guard strings are dead code (they can never match any real `Role` row's `name`, since no seeder ever creates a Spatie role named `super-admin` or `owner`).
- **Custom role support**: yes — `RoleController::store`/`update` allow creating/editing arbitrary tenant-custom roles with arbitrary permission subsets (gated by `roles.manage`, §5). No `is_system`/`protected` DB column exists; protection is purely the in-code `$systemRoles` array check (name-based, not id/flag-based) shown above.

## 5. Role & permission management API (`RoleController`, `UserController`)

- Routes registered in `app/Modules/Identity/routes.php:57-81`, all under `Route::prefix('api/v1')->middleware(['api', 'auth:sanctum', SetPermissionsTeam::class, EnforceTokenTenantClaim::class])`. **No `can:` middleware is attached to any of these routes** — a stylistic outlier vs. the rest of the codebase's 608 `can:`-middleware routes (§3). Authorization for these routes is instead implemented inside FormRequest `authorize()` methods and ad-hoc controller checks:
  - `GET /roles` (`RoleController::index`, line 123), `GET /roles/{id}` (`show`, line 162), `GET /permissions` (`permissions`, line 315) take a plain `Request $request` (**not** a FormRequest) and perform **no authorization check at all** — any authenticated tenant user with company context can list every role (with its full permission set) and the entire permission catalogue. This is confirmed **intentional and tested**: `tests/Feature/Identity/RBACTest.php:137-165` (`test_authenticated_user_can_list_roles`, `test_authenticated_user_can_list_permissions`) asserts exactly this open-read behavior.
  - `POST /roles` (`store`) is gated by `StoreRoleRequest::authorize()` → `$this->user()?->can('roles.manage') ?? false` (`StoreRoleRequest.php:19-22`).
  - `PATCH /roles/{id}` (`update`) → `UpdateRoleRequest::authorize()` same `roles.manage` gate (`UpdateRoleRequest.php:18-21`), plus an in-controller system-role rename guard (`RoleController.php:228-236`).
  - `DELETE /roles/{id}` (`destroy`) → `DeleteRoleRequest::authorize()` same `roles.manage` gate (`DeleteRoleRequest.php:20-23`), plus in-controller system-role guard (line 277-285) **and** a "role has users" guard (`countUsersForRole($role) > 0` → 422 `ROLE_HAS_USERS`, lines 288-296) — a role with any assigned users cannot be deleted. There is **no "last admin" / "cannot demote the only admin" check anywhere** in `RoleController`/`UserController` — an admin's own role can be changed via `PATCH /users/{id}` (`UpdateUserRequest`) by any other user holding `users.update` + an assignable role, with no floor on "at least one admin must remain in the tenant".
  - `POST /users/{userId}/roles` (`assignRole`) and `DELETE /users/{userId}/roles` (`removeRole`) are both gated by `AssignRoleRequest::authorize()` → `$this->user()?->can('users.assign-roles') ?? false` (`AssignRoleRequest.php:20-23`), **plus** an escalation guard: `AssignableRole` validation rule (`app/Modules/Identity/Presentation/Rules/AssignableRole.php:28-52`) diffs the target role's permission set against the actor's own `getAllPermissions()` and fails validation ("You cannot assign a role that grants permissions beyond your own") if the target role would grant anything the actor doesn't already hold. The same `AssignableRole` rule is reused in `CreateUserRequest::rules()` (`CreateUserRequest.php:50`) and `UpdateUserRequest::rules()` (`UpdateUserRequest.php:56`) for the `role` field on user create/update, so the escalation guard is applied consistently on all three role-granting surfaces.
- **Privilege escalation — 2026-06-14 go-live "RoleController no authz" finding**: code comments explicitly cite this finding by number and show it **has been remediated** at HEAD: `AssignRoleRequest.php:16-22` ("Go-live audit Finding #1 — without this gate any authenticated tenant member could self-assign `admin`"), `AssignableRole.php:19` ("Go-live security audit 2026-06-14, Finding #2 (privilege escalation)"), `StoreRoleRequest.php:14-21`, `UpdateRoleRequest.php:12-20`, `DeleteRoleRequest.php:11-22` all cite the same finding/TD-015. Tests corroborate: `tests/Feature/Identity/RoleAuthorizationTest.php` (`test_cashier_cannot_self_assign_admin_role`, `test_cashier_cannot_create_role`, `test_cashier_cannot_update_role`, `test_cashier_cannot_delete_role`, `test_admin_can_assign_role`/`create_role`/`delete_role`), `tests/Feature/Identity/UserManagement/UserRoleRankTest.php` (`test_delegated_user_cannot_create_an_admin`, `test_delegated_user_cannot_promote_existing_user_to_admin`, `test_admin_can_still_create_an_admin`). **Residual gap**: the three **read** endpoints (`index`/`show`/`permissions`) remain unauthorized by design (see above) — not privilege *escalation* (no state mutation) but is an information-disclosure asymmetry relative to the write endpoints' hard gating.
- **Tenant isolation**: `resolveTenantUser()` (`RoleController.php:103-117`) constrains user lookups to `where('tenant_id', $this->companyContext->requireCompany()->tenant_id)` and returns the same "User not found" 404 shape for both a genuinely-missing id and a cross-tenant id (comment: "dev-remediation/B.M2.4"). `Role::findOrFail()` calls throughout rely on Spatie's package-level team `global scope` (auto-injected by `SetPermissionsTeam`) rather than an explicit `where`, documented via `#[CrossTenantRoute(reason: ...)]` PHP attributes on every method (lines 122, 161, 186, 222, 271, 314) explaining why the cross-tenant-route static-analysis rule is satisfied. Verified by `tests/Feature/Identity/RoleTenantIsolationTest.php` (`test_assign_role_rejects_cross_tenant_user`, `test_remove_role_rejects_cross_tenant_user`, `test_user_roles_rejects_cross_tenant_user`, `test_same_tenant_*` positive cases).
- **Auditing**: `assignRole`/`removeRole` dispatch `App\Modules\Identity\Domain\Events\RoleAssigned`/`RoleRemoved` (`RoleController.php:365-371`, `404-411`) carrying actor id, target user id, role name, company id, timestamp — described in code comment as "the only record of who granted whom which role" (line 360-362). Verified by `tests/Feature/Identity/RoleAssignmentAuditTest.php` (`test_assign_role_persists_audit_event`, `test_remove_role_persists_audit_event`, `test_failed_assignment_leaves_no_audit_event`). Role **create/update/delete** on `RoleController` itself (`store`/`update`/`destroy`) have **no equivalent audit event** — only the user↔role assignment edge is audited, not mutations to a role's own permission set.
- **Frontend exposure of permissions**: `GET /api/v1/auth/me` (`AuthController::me`, line 616) and the login response both build `App\Modules\Identity\Application\DTOs\AuthUserData::fromUser()` (`AuthUserData.php:34-60`), which calls `setPermissionsTeamId($user->tenant_id)` then `$user->getRoleNames()` and `$user->getAllPermissions()->pluck('name')` — the full **effective** permission list (role-derived) is shipped to the frontend on every login/`/me` call, as `roles: list<string>` and `permissions: list<string>` fields, TypeScript-transformed (`#[TypeScript]` attribute, line 11) into the generated frontend types.

## 7. Module gating (`config/verticals.php`, `RequireModule`)

- `config/verticals.php` defines two verticals: `mechanic` (product `otospex`, `compatible_extras: [Appointments, Fleet]`, `default_modules: [Identity, Tenant, Catalog, Vehicle, Partner, Workshop, Sales, Inventory, Treasury, Accounting, PlatformIntegration]`) and `pharmacy` (product `izipos`, `compatible_extras: [BatchExpiry, Prescription, Ecommerce, PurchaseBonus]`, `requires_batch_tracking: true`, similar core module list plus `BatchExpiry`).
- `App\Http\Middleware\RequireModule` (`app/Http/Middleware/RequireModule.php:38-67`) is applied as `module:<Name>` on routes; it resolves the requesting `User`'s `Tenant`, asks `CompanyConfigService::getConfigForTenant($tenant)->hasModule($module)`, and `abort(403, "Module '{$module}' is not enabled for this business type")` if disabled. It has **no interaction with Spatie permissions at the DB level** — disabling a module does **not** revoke or delete any granted permission row; module gating is a pure **route-reachability** gate layered independently on top of (not integrated with) the permission system.
- The **permission catalogue itself is module-agnostic**: `RolesAndPermissionsSeeder` seeds the full 304-permission/7-role catalogue for **every** tenant regardless of vertical (comment at `RoleController.php:32-34`: "the seeder always creates every group (111 tests depend on that)"). Module-based hiding happens only at **read time** in `RoleController::index`/`permissions` via two private constant maps — `PERMISSION_GROUP_MODULE` (lines 35-46: `vehicles→Vehicle`, `workshop*→Workshop`, `menus/modifier-groups→Menu`, `composite-items→CompositeItems`, `scheduling→Appointments`, `batches→BatchExpiry`, `loyalty→Loyalty`) and `ROLE_MODULE` (lines 53-56: `technician→Workshop`, `operator→Workshop`) — which filter what the **listing** endpoints show, not what's actually grantable/storable. A tenant can still have a user holding e.g. `batches.view` even if `BatchExpiry` is disabled for their vertical; the permission simply won't be *displayed* by `GET /permissions`/`GET /roles`.
- Design inconsistency: `app/Modules/Marketplace/Providers/MarketplaceServiceProvider.php:38-49` documents that `marketplace.admin` is seeded to **every** tenant `admin` (via `Permission::all()`) even though the controller behind it (`MarketplaceSellerController`) is "documented... as SUPER-ADMIN, fleet-wide semantics" — the mismatch between the permission's scope (tenant-admin-grantable) and the feature's intended scope (platform-fleet-wide) is currently papered over by an unrelated `config('marketplace.enabled')` kill-switch defaulting to `false`, not by fixing the permission/role model.

## 8. Location and company scoping vs. Spatie permissions

- **`user_company_memberships`** (`database/migrations/tenant/2025_11_30_106000_create_user_company_memberships_table.php:23-65`): `user_id`, `company_id`, `role` (varchar(50), free-text label documented as one of owner/admin/manager/accountant/cashier/technician/viewer — the `MembershipRole` enum, §4), `allowed_location_ids` (nullable JSON — `NULL` = all locations), `is_primary`, `status`.
- **`LocationContext`** (`app/Modules/Company/Services/LocationContext.php`): `getAllowedLocationIds()` (194-207) returns `null` for "all locations" (unrestricted membership) vs `[]` for "no active membership" (fail-closed) vs an explicit id list; `canAccessLocation()` (224-239) and `validateLocationAccess()` (253-264, throws) implement the row-level check, explicitly documented (lines 22-23, 244-246) as **defense-in-depth** — "Phase 3 middleware will be the primary enforcement point for most HTTP requests."
- **`ValidateLocationAccess` middleware** (`app/Http/Middleware/ValidateLocationAccess.php`) is the primary HTTP-layer enforcement: collects `location_id`/`from_location_id`/`to_location_id`/route param/query param/`lines[].location_id` (lines 96-144) and 403s (`LOCATION_ACCESS_DENIED`) if any collected id fails `LocationContext::canAccessLocation()`. This is a **row-scope** check (which locations' data can this request touch), fully orthogonal to Spatie's **action-scope** check (`can('inventory.transfer')` etc, checked separately, usually by a `can:` route middleware on the same route). The two must both pass — Spatie permissions say nothing about location, and `allowed_location_ids` says nothing about which actions are permitted.
- **`CompanyContext`** (`app/Modules/Company/Services/CompanyContext.php`) is a simple request-scoped holder (`currentCompanyId`/`currentTenantId`, set by `CompanyContextMiddleware`, not audited here in depth) — resolved from the `X-Company-Id` header or the user's first membership per `docs/conventions/03-AUTHORIZATION.md:147-150`.
- **Special-case permission-like flags directly on `users`** (found via migration grep, not part of the Spatie/permissions tables):
  - `can_discount` (boolean, default `false`) and `max_discount_percent` (decimal(5,2), nullable, CHECK 0–100 on PostgreSQL) — added in `database/migrations/tenant/2026_01_10_063755_add_discount_permissions_to_users.php:22-28,33`; further touched by `2026_03_23_200000_fix_discount_permission_defaults.php` and `2026_07_08_130000_add_discount_policy_columns.php`. These are **per-user numeric/boolean overrides**, not Spatie permissions — resolved via `App\Modules\POS\Domain\Services\DiscountPermissionResolver` (used throughout `PosAuthController`, §9) alongside (not instead of) the `admin` role check (`isAdmin($user)` short-circuits to `max_discount_percent = 100.0`, e.g. `PosAuthController.php:100-101`).
  - No `is_super_admin` column exists on `users` — super-admin is entirely the separate `SuperAdmin` model/table (§4), never a flag on the tenant `User` model.

## 9. POS-specific permissions

- **PIN-based operator auth**: `App\Modules\POS\Presentation\Controllers\PosAuthController` (`PosAuthController.php`). All four endpoints (`verifyPin`, `setupPin`, `pinData`, `syncPins`, `hasPins`) are gated by `Gate::authorize('pos.operate_terminal')` (lines 66, 122, 172, 253, 338) at the top of the method — i.e. the caller (the terminal session's authenticated user, not the PIN-verified operator) must already hold `pos.operate_terminal` before any PIN logic runs.
- The **PIN-holder population** is centralized in one private method, `pinHolders()` (lines 46-57), explicitly documented (lines 33-45) as "the single definition of 'an operator PIN this terminal may act on'" shared by `verifyPin`, `pinData`, and `hasPins`, to close three previously-independent, previously-buggy population definitions (comments reference concrete fixed holes: cross-company operator impersonation via a company-A terminal returning a company-B-only manager's full permission set, F-3/F-5/N-5 offboarding-belt gaps). Population = active `UserCompanyMembership` in `CompanyContext`'s company ∩ `UserStatus::Active` user ∩ `pos_pin IS NOT NULL`, all within the caller's tenant.
- **PIN verification (`verifyPin`) returns to the device**: `id`, `name`, `email`, `roles` (`getRoleNames()`), `permissions` (`getAllPermissions()->pluck('name')` — the operator's **full** Spatie permission list), `can_discount`, `max_discount_percent` (lines 93-103) — i.e. the full permission catalogue for the PIN'd operator is pushed to the POS client on every PIN switch, not just POS-specific permissions.
- **`pinData` (offline sync mirror)** additionally computes `approval_scopes` per operator (lines 208-216) by filtering `App\Modules\POS\Domain\Enums\ApprovalScope::cases()` against `$user->hasPermissionTo($scope->permissionName())` — this is the mechanism that maps the `pos.approve_*` permission family (`pos.approve_credit_limit_override`, `pos.approve_account_status_override`, `pos.approve_discount_limit_override`, `pos.approve_tender_tolerance_override`, `pos.approve_void_or_return_override`, `pos.approve_cash_drawer_control`) into a discrete `approval_scopes` list the offline device can check against a manager's PIN for override approvals (void, refund, discount-limit, drawer control, etc.) without a live server round-trip. `pin_hash` (the bcrypt hash itself, not a plaintext PIN) is included in this offline payload (line 223) by design, to let the device verify PINs offline.
- **`syncPins`** is hardened **self-only**: any `user_id` in the `updates` payload other than the authenticated caller's own id is rejected (lines 276-293, comment explains this "closes the same-company authorship gap" — a holder of `pos.operate_terminal` could otherwise overwrite another active member's PIN).
- Beyond PIN plumbing, the seeded `pos.*` permission family (§2) directly encodes POS action-level gates by name: `pos.void_receipts` (dead, §3), `pos.process_returns`, `pos.close_shift_with_variance`, `pos.configure_cash_count`, `pos.tolerance.apply`, `pos.view_cross_location_stock`, plus the refund-flow family (`pos.refund_above_threshold`, `pos.refund_no_receipt` [dead], `pos.refund_extend_daily_cap`, `pos.issue_goodwill_voucher[_high_value]` [high_value dead], `pos.void_voucher`, `pos.extend_voucher_expiry`, `pos.transfer_voucher`, `pos.redeem_voucher` [dead], `pos.refund_destination_override`, `pos.refund_voucher_to_cash` [dead], `pos.search_customer_recent_purchases` [dead]/`_full_history`/`_cross_company` [dead]) — enforced elsewhere via `->can()`/`Gate::authorize()` in the refund/returns controllers (not re-verified line-by-line in this pass beyond the dead-permission census in §3).

## 10. Permission cache — tenant-scoping status (2026-09-03 lane `rh-t1`)

- **Status: NOT fixed at HEAD `e85641a66`.** The Spatie cache key is the single static string `'spatie.permission.cache'` (`config/permission.php`, §1) with **no tenant suffix**. `PermissionRegistrar` obtains its cache store via `CacheManager::store()`, which Stancl's tenancy tagging does not intercept.
- The bug is explicitly documented and dispatched in `docs/handoff/HANDOVER-request-hygiene-T1-permission-cache-2026-09-03.md:5-7`: *"every tenant has its own `permissions` table but they all share the key `spatie.permission.cache`, so tenant A's registry can be served to tenant B and any role edit anywhere flushes everyone. Known since 2026-07-03..., never fixed."* Referenced as finding **S-1** in `docs/superpowers/plans/2026-09-03-request-hygiene-phase-a.md`, "Task 1: Tenant-scoped Spatie permission cache (S-1)" (lines 60-141), with a fully-specified fix: two new listeners (`ScopePermissionCacheToTenant`, `RestoreCentralPermissionCache`) wired into `TenancyServiceProvider`, keying the cache as `spatie.permission.cache.<tenant-id>` for database-per-tenant mode.
- **Verification that it is unmerged**: none of the four planned files exist at HEAD —
  - `apps/api/app/Modules/Identity/Application/Listeners/` contains **only** `SendEnrichmentNotificationListener.php`; `ScopePermissionCacheToTenant.php` / `RestoreCentralPermissionCache.php` are absent.
  - `apps/api/tests/Feature/Identity/PermissionCacheTenantScopingTest.php` does not exist.
  - `App\Providers\TenancyServiceProvider` (`app/Providers/TenancyServiceProvider.php:47-60`) wires **only** `TenancyInitialized → BootstrapTenancy` and `TenancyEnded → RevertToCentralContext`; there is no permission-cache-scoping listener registered.
  - No `docs/handoff/HANDBACK-request-hygiene-T1-*.md` exists (the sibling tasks T10/T10b/T11/T12/T12b/T12c/T13/T14 all have handback docs; T1 does not), and no commit/merge for `lane/rh-t1-permission-cache` appears in `git log --all` (searched for `rh-t1\b`, `lane/rh-t1-permission-cache`, `tenant-scoped.*cache`, `permission.cache` — the closest real, merged fix is a *different*, earlier commit `9a56149cf` "feat(deploy): api entrypoint rolls pending tenant migrations + flushes spatie permission cache at boot" (2026-07-03, `apps/api/docker/entrypoint.sh`), which forces a **`permission:cache-reset` at container boot** — a deploy-time mitigation that clears the (still globally-keyed) cache, not a fix for the cross-tenant key collision itself).
- **Net effect at HEAD**: under `TENANCY_DB_PER_TENANT=true` (the production topology per `.env.example:56`), the permission/role cache is a single process-wide key shared by every tenant's Spatie registry snapshot. A role/permission edit in any one tenant flushes (and the next read repopulates) the shared key from whichever tenant's DB connection is active at that moment — a live cross-tenant data-consistency risk on the read side (a request could observe another tenant's cached role/permission set) that is separate from, and not mitigated by, `SetPermissionsTeam`'s per-request team-id scoping (the team_id filter is applied to whatever the cache returns; if the cache returns tenant B's snapshot the team_id filter still filters correctly for tenant B's team ids, so the practical exposure is serving a **stale/wrong tenant's permission catalogue shape**, most acutely for tenant-custom roles/permission edits made via `RoleController`, not a straightforward "wrong team_id gets wrong permission" bypass — but the go-live audit language quoted above treats it as a hard cross-tenant leak).

## 11. Automation / consistency; new-tenant provisioning; existing-tenant drift
