### 6.2 THE COSTING RULE — one virgin product per WAC-asserting class  [r2, gate BLOCKER G1-C1-01]

> **WAC is a running, company-wide average persisted on `products.cost_price`. No absolute cost or stock figure in the matrix is valid unless its product is used exactly once in the run.**

`companyOwnedQuantity()` sums **every** `stock_level` row for the product in the company — all locations, all variants — plus in-transit (`WeightedAverageCostService.php:100-128` ✔), the blend is `newValue / newCompanyQty` (`:241-253` ✔), and the result is written back to `products.cost_price` (`:291` ✔) as the input to the next receipt. r1 hand-computed every class against a virgin product while reusing `P1`/`P4` across six classes in one serial run, which made `W2-TOT-3`, `W2-PART-2`, `W2-PRICE-1`, `W2-LAND-2`, `W2-LAND-4` and `W2-EDGE-7` unreachable as written.

**r2 takes option (a): a dedicated product per class**, named `P-<CLASS>-<n>`, so every hand-derived figure stays byte-identical to the arithmetic both reviewers verified. The full SKU table is in `02-scenario-matrix.md` §Fixture; the rule for seeding is:

- created in **W2-SETUP-3** in one API loop, each with `unit = pc`, its class's `purchase_price`, and its class's `tax_configuration_id`;
- **omit** `requires_batch_tracking` for a lot-story product (the vertical default makes it `true`); **send `requires_batch_tracking: false` explicitly** for every costing product, or the receipt 422s on "Batch data is required" — the same workaround the money campaign documents at `w4-support.ts:150-173`;
- a product may be reused **only** by rows that assert no absolute `cost_price` or `stock_levels` figure.

### 6.7 The FEFO consumption driver  [r2, pinned in r3]

FEFO is the consumption path for the entire parapharmacy vertical (every product is lot-tracked by default), and r1 built two perfect FEFO fixtures in `W2-PART-4` and consumed neither. The only surface a Playwright run can drive that reaches `FEFOInventoryService::consumeBatchesAtomically` is the **delivery note**: `POST /delivery-notes` (`can:deliveries.create`) then `POST /delivery-notes/{id}/confirm` (`can:deliveries.confirm`) → `DeliveryNoteService::issueStock` (`:297`) → `consumeBatchesAtomically` (`:389`) ✔ (routes `Document/Presentation/routes.php:330-336` ✔). The alternatives are POS device events (not Playwright-drivable) and `POST /batches/{uuid}/write-off`, which targets one named lot and therefore proves nothing about *selection*.

**[r3] Three fixture facts decide whether FEFO runs at all, and every FEFO row must pin them:**
1. **`location_id` is required — and omitting it produces a LOUD refusal, not a silent skip.** **[r4 — this corrects the mechanism r2 asserted and r3 adopted.]** `confirm()` refuses a header-less delivery note before `issueStock` is ever reached: `throw new \DomainException('Delivery note must have a location before confirmation. Document: …')` (`DeliveryNoteService.php:89-93`) ✔, mapped to **422 `INVALID_STATUS_TRANSITION`** (`DeliveryNoteController.php:595-596`) ✔. Because the header location is guaranteed non-null past that guard, `$line->location ?? $deliveryNote->location` cannot resolve to null and the `continue` at `:309-313` is **unreachable from this endpoint**. `location_id` is still `nullable` on the create request (`CreateDocumentRequest.php:93-99`), so the pin stays mandatory — only the justification was wrong, and it is the kind of wrong that costs a triage hour when a tester meets a 422 the spec called impossible.
2. **The line must carry NO `batch_id`.** FEFO is the **`elseif`**: `if ($line->batch_id !== null) { issueBatchStock(…) } elseif ($product->requires_batch_tracking) { consumeBatchesAtomically(…) }` (`DeliveryNoteService.php:380-388`) ✔. A line with a `batch_id` tests the named-lot path and proves nothing about selection.
3. **`partner_id` is required** with no customer-type filter (`CreateDocumentRequest.php:66-70`), so an imported supplier (`SUP-A`) is usable — but it must be named.

**[r3] The scope note is narrowed by one clause.** The delivery note's *lifecycle* and the *amount* of its COGS booking stay out of wave 2, but its **existence** does not: `issueStock` calls `recordSale` (`:316-323`), which writes an `Issue` movement with `reason = MovementReason::Delivery` and a **negative** `quantity` (`WeightedAverageCostService.php:470-489`) — which is also what makes W2-WDIL-1(a)'s Σ-vs-delta identity hold once the FEFO leg runs — then enqueues a `MovementGlContext(kind: Exit)` on the `InventoryGlPostingBuffer` (`DeliveryNoteService.php:399-401`) ✔. Wave 2's own P0 is "stock moved, GL swallowed"; the run's only stock **exit** must therefore assert that **at least one journal entry exists** for the issue movement. Its amount and lifecycle are recorded, not asserted.

**Scope note, stated so a reviewer can hold us to it — [r4] corrected, because r3 left this sentence contradicting the paragraph two lines above it.** The delivery note is a sales-side document and sales is not wave 2. `W2-LOT-9`/`W2-LOT-10` borrow it **purely as a consumption driver** and assert the lot ledger, the aggregate (`inventory_batch_stock` per lot, `stock_levels`, no negative row) **and the EXISTENCE of the exit journal entry** — keyed `source_type = 'inventory_exit'`, `source_id = <issue movement id>`, `status = 'posted'`, an empty result FAILING the row. Only the COGS **amount** and the document lifecycle are **recorded, not asserted** — they belong to a later wave. (r3 said "assert **only** the lot ledger and the aggregate … GL entries are recorded, not asserted", which re-opened exactly the hole the paragraph above closes; a runner reading §6.7 to the end would have taken the later, absolute sentence.)
