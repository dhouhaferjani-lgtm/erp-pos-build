# Adversarial Design Review - Parapharmacy Merchandising (2026-06-28)

## Summary
The parapharmacy merchandising design is directionally useful, but it is not ready to build as written because the POS delta-sync and module-entitlement assumptions leave upgraded devices with stale local state. The highest-risk gap is the missing POS cursor reset after adding merchandising columns: current production code already has a v57 precedent proving that schema-added product fields require a forced full re-fetch. Several backend details also need tightening before implementation: brand uniqueness must be explicitly tenant-scoped, product read paths must actually eager-load and serialize the new brand relation, suitability needs a relation pattern that matches the schema, and SmartPrompts validation must move with the shared enum. The remaining issues are contract precision problems around `pullCustomers()` and equivalence confidence, both small to fix now and expensive to rediscover after implementation.

## Findings

### [CRITICAL] v58 migration does not reset POS sync cursors
**Spec section:** §4 POS offline sync, lines 134-144; §8 testing strategy, lines 180-183.

**Code evidence:** POS product sync is delta-driven by `sync_metadata.products_last_sync`: `pullProductsCore()` reads `products_last_sync` and sends it as `updated_since` when present (`apps/pos/src/lib/sync/syncService.ts:545-553`), then writes the cursor only after a completed pull (`apps/pos/src/lib/sync/syncService.ts:619-620`). Customer sync is also cursor-driven: `pullCustomers()` reads `customers.updated_since`, sends it as `updated_since`, and persists the server `synced_at` cursor on success (`apps/pos/src/lib/customer/customerSyncService.ts:133-169`). The current max POS migration, v57, explicitly documents and implements the required pattern: after adding `products.has_variants`, it deletes `products_last_sync` so the next pull is a full re-fetch (`apps/pos/src/lib/db/migrations.ts:1773-1788`). Its regression test states the failure mode directly: without deleting the cursor, unchanged products stay stuck with the default value because delta sync never re-fetches them (`apps/pos/src/lib/db/__tests__/migrations.v57.test.ts:9-15`, `apps/pos/src/lib/db/__tests__/migrations.v57.test.ts:67-102`).

**Problem:** The spec's v58 adds `products.brand_id`, `products.brand_name`, `products.parapharmacy_metadata`, `customers.skin_type`, and `customers.skin_advice_note` (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:138-143`) but never requires deleting `products_last_sync` or `customers.updated_since`. On upgraded terminals that already have both cursors, the server will only return rows changed after the old cursor. Existing unchanged products and customers keep the new SQLite columns at `NULL` indefinitely, so brand filters, skin suitability, equivalents, complements, routines, and customer skin advice silently remain absent for most of the demo catalog.

**Recommendation:** Make v58 force a full baseline for every affected entity. Delete `sync_metadata` keys `products_last_sync` and `customers.updated_since` in the v58 migration, and add migration tests mirroring v57 that seed the cursors before v58, apply v58, and assert the cursors are gone. If customer sync later gets a secondary cursor key, clear that too. The acceptance criteria should explicitly verify the next sync omits `updated_since` for products and customers after the migration.

### [IMPORTANT] Brand uniqueness needs explicit tenant scoping
**Spec section:** §1.3 Brand entity, lines 47-69; §1.9 Enrichment-accept fix, lines 99-102.

**Code evidence:** The spec says `slug` is "unique per tenant" (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:57`) and says enrichment should upsert a brand by tenant-normalized name (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:99-101`), but the proposed `brands` column list contains no `tenant_id` or `company_id` (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:50-65`). Existing product identity is tenant-scoped: `products` has `tenant_id` and `unique(['tenant_id', 'sku'])` (`apps/api/database/migrations/tenant/2025_11_30_052910_create_products_table.php:16-39`). Existing enrichment data is also written with both `tenant_id` and `company_id` (`apps/api/app/Modules/Product/Application/Services/EnrichmentReviewService.php:38-43`).

**Problem:** Without a `tenant_id` column and a composite unique index, "unique per tenant" is unimplementable. In a tenant database this may look harmless at first, but the codebase still stores `tenant_id` on tenant tables and uses tenant/company scopes as a defense-in-depth convention. A global `slug` unique would prevent two tenants from carrying different brand registries if the table is ever central or shared in tests, while a table without tenant scope cannot support the spec's tenant-normalized enrichment upsert. It also makes `products.brand_id` less defensible because a tenant-scoped product would point at a brand row that does not carry the same partition key.

**Recommendation:** Add `tenant_id` to `brands` and make the uniqueness explicit: `unique(['tenant_id', 'slug'])`. If brand records are intended to be shared across companies inside one tenant database, state that explicitly and keep `company_id` off by design; if brands are company-local, add `company_id` and use `unique(['tenant_id', 'company_id', 'slug'])`. The enrichment accept flow must upsert with the same scope used by the unique index, not an implicit or global name lookup.

### [IMPORTANT] Product brand eager-loading not mapped to ProductController read paths
**Spec section:** §1.3 Brand entity, lines 67-68; §1.8 DTOs & API, lines 91-97; §4 POS offline sync, lines 138-140; §7 build order, lines 168-174.

**Code evidence:** The spec says `products.brand_id` is available to all verticals and "eager-loaded always" (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:67-68`) and says `ProductData` gains `brand: BrandData|null` (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:91-95`). Current `ProductController::index()` builds an explicit `$with = ['category', 'unitOfMeasure']` list and only appends vertical-specific metadata relations (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:72-90`). `show()` loads only `unitOfMeasure` in the base query, then conditionally loads parapharmacy or automotive metadata (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:263-299`). `store()` reloads vertical metadata and then only `unitOfMeasure` before serializing (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:398-417`). Current `ProductData` has no `brand` constructor field and `fromModel()` maps only scalar product fields, media, `parapharmacy_metadata`, and `automotive_metadata` (`apps/api/app/Modules/Product/Application/DTOs/ProductData.php:22-56`, `apps/api/app/Modules/Product/Application/DTOs/ProductData.php:58-98`).

**Problem:** Adding a model relation and a DTO class is insufficient. The existing product response shape is controller-driven and DTO-driven; unless every read path loads `brand` and `ProductData::fromModel()` maps it, the `/products` list, `/products/{id}`, create response, update response, and POS catalog pulls will not carry the new brand consistently. This also intersects with the POS wire shape: §1.8 describes nested `brand`, while §4 wants flat `brand_id` and `brand_name` columns. Without an explicit mapping point, the device repository cannot populate the new SQLite columns.

**Recommendation:** Update all `ProductController` response paths to include `brand` in their base relation loads, independent of vertical. Add `BrandData` and a `public ?BrandData $brand` field to `ProductData`, mapped only when the relation is loaded. Decide and document the POS wire shape: either expose flat `brand_id`/`brand_name` in the POS product payload or flatten nested `brand` before `upsertProducts()`. Add tests for list, detail, create/update response shape, and POS product repository round-trip.

### [IMPORTANT] Product skin suitability contradicts product_ingredient pivot precedent
**Spec section:** §1.5 Product skin suitability, lines 76-79; §1.8 DTOs & API, lines 91-95; §8 testing strategy, lines 180-183.

**Code evidence:** The spec proposes `product_skin_suitability` with `product_id` and an enum string `skin_type`, then says `Product::suitableSkinTypes()` should be modeled on the `product_ingredient` `belongsToMany withPivot` precedent (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:76-79`). The precedent is materially different: `product_ingredient` has `product_id`, `ingredient_id`, pivot fields, FKs to `parapharmacy_product_metadata.product_id` and `ingredients.id`, and a unique pair (`apps/api/database/migrations/tenant/2026_01_08_174850_create_product_ingredient_table.php:14-39`). `ParapharmacyProductMetadata::ingredients()` is a `belongsToMany(Ingredient::class, 'product_ingredient', ...)` with `withPivot([...])` and `orderByPivot('order')` (`apps/api/app/Modules/Product/Domain/ParapharmacyProductMetadata.php:113-124`). `Ingredient::products()` mirrors the same many-to-many relation back to `ParapharmacyProductMetadata` (`apps/api/app/Modules/Product/Domain/Ingredient.php:76-86`).

**Problem:** A `belongsToMany` relation needs a related model/table. The proposed suitability table has no `skin_types` lookup table, only an enum value, so it cannot honestly follow the existing `product_ingredient` relation shape. If implemented as written, developers either create an invalid Eloquent relation or invent a different ad hoc accessor while the spec and tests expect `belongsToMany withPivot`. The anchor is also different: the ingredient precedent hangs off `ParapharmacyProductMetadata` using `product_id` as the parent key, while the merchandising spec says the new relationship lives directly on `Product`.

**Recommendation:** Pick one relation model and specify it precisely. The simplest fit is a small `ProductSkinSuitability` model with `product_id`, `skin_type` cast to the shared enum, and `Product::skinSuitabilities(): HasMany`, while the DTO exposes `suitable_skin_types` by plucking enum values. If the team wants true `belongsToMany withPivot`, add a real `skin_types` lookup table/model and relate through `product_skin_suitability`. Do not cite `product_ingredient` as a direct precedent unless the schema has a real related table and matching relation mechanics.

### [IMPORTANT] Offline Merchandising entitlement is company-config cache, not SQLite sync
**Spec section:** §2 Merchandising module gating, lines 106-115; §5 POS UI, lines 148-157; §9 Risks & open items, lines 187-193.

**Code evidence:** The spec says the offline POS reads "synced module entitlements" and asks the plan to confirm the device entitlement-sync mechanism (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:110-114`, `docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:189-190`). In current POS code, module gating is not a SQLite sync table. `hasModule()` reads `productStore.companyConfig.all_enabled_modules` (`apps/pos/src/stores/productStore.ts:110-120`). The config is fetched from `/company/config` and persisted through `companyConfigCache` (`apps/pos/src/api/productApi.ts:42-56`; `apps/pos/src/lib/companyConfigCache.ts:6-15`). On startup/product fetch, the store hydrates cached company config before attempting a live fetch (`apps/pos/src/stores/productStore.ts:200-223`). `runFullSync()` refreshes company config best-effort near the end of the sync tick (`apps/pos/src/lib/sync/syncService.ts:2038-2042`), and `authStore.refreshCompanyConfig()` writes it back to the product store and offline cache (`apps/pos/src/stores/authStore.ts:418-430`). On the backend, `/company/config` returns `all_enabled_modules` (`apps/api/app/Http/Controllers/Api/CompanyConfigController.php:70-93`), and `CompanyConfigService` builds that list by merging vertical defaults and enabled extras (`apps/api/app/Services/CompanyConfigService.php:48-79`).

**Problem:** The spec describes the entitlement path incorrectly. There is no merchandising entitlement row being synced into SQLite alongside products/customers. Offline module checks depend on a cached `/company/config` payload for the selected company. That means offline rendering can only be correct if the cache has already been hydrated after `Merchandising` is added to `parapharmacy.default_modules`; otherwise `hasModule('Merchandising')` returns false while offline and the POS hides merchandising surfaces despite the local data being present. Conversely, when entitlements change, the cache refresh and invalidation path is the contract to test, not a new device sync table.

**Recommendation:** Rewrite the spec to say "Merchandising entitlement is read from cached `/company/config` (`all_enabled_modules`) via `hasModule()`." Add `Merchandising` to `ModuleName` and `parapharmacy.default_modules` in the same backend change, then test that `/company/config` includes it for parapharmacy tenants. On POS, add tests for online refresh persistence, offline startup hydration from `companyConfigCache`, and `hasModule('Merchandising')` gating. Avoid adding a second entitlement-sync mechanism unless there is a separate product requirement for it.

### [IMPORTANT] pullCustomers() needs a SyncResult contract and error policy
**Spec section:** §4 POS offline sync, lines 141-144; §7 build order, lines 173-175; §8 testing strategy, lines 180-183; §9 Risks & open items, lines 187-193.

**Code evidence:** The spec correctly notes that `pullCustomers()` is orphaned and must be wired into `runFullSync()` (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:141-143`). Current `pullCustomers()` is a strong typed pull: it validates response shape and cursor fields, validates tenant/company scope and account status, upserts each customer, and persists `customers.updated_since` only at the successful terminal page (`apps/pos/src/lib/customer/customerSyncService.ts:39-58`, `apps/pos/src/lib/customer/customerSyncService.ts:80-130`, `apps/pos/src/lib/customer/customerSyncService.ts:133-176`). But `runFullSync()` currently pulls products, payment config, operators, terminal state, tables, menus, vouchers, voucher ledger, receipt QR index, variants, location stock, and company config; it never calls `pullCustomers()` (`apps/pos/src/lib/sync/syncService.ts:2000-2042`). `SyncResult` has fields for many pull surfaces but no `customersPulled` or `customersFailed`/customer error signal (`apps/pos/src/lib/sync/syncService.ts:142-161`), and the returned object likewise has no customer field (`apps/pos/src/lib/sync/syncService.ts:2088-2109`).

**Problem:** Simply "wiring `pullCustomers()`" is under-specified. If customer sync throws on malformed server data, scope mismatch, network failure, or cursor contract drift, the implementation needs to decide whether that failure aborts the whole sync tick, is swallowed and logged like location stock/variants, or contributes to the degraded sync indicator. Without a `SyncResult` field, scheduler/UI/tests cannot tell whether customer merchandising data was pulled, skipped, or failed. That matters because customer `skin_type` drives the POS skin-advice defaults and because the cursor reset in v58 only helps if the customer pull actually runs.

**Recommendation:** Extend the sync contract before implementation: add `customersPulled` and either `customersFailed` or a logged `customer_sync` error path to `SyncResult`. Wire `pullCustomers(db, tenantId, companyId)` in `runFullSync()` using IDs from `authStore`, and define the failure policy explicitly. The pragmatic policy is to catch, log, add an error/degraded signal, and continue selling, matching variant/location-stock behavior, while never advancing `customers.updated_since` on failure. Add tests for a successful call, argument source, result accounting, and each error class that should be swallowed versus propagated.

### [IMPORTANT] SmartPrompts validation should derive from the shared SkinType enum
**Spec section:** §1.1 Canonical SkinType enum, lines 39-42; §7 build order, lines 168-169; §8 testing strategy, lines 180-183; §9 Risks & open items, lines 187-193.

**Code evidence:** The spec moves `SkinType` to `app/Shared/Domain/Enums/SkinType.php` and says SmartPrompts consumers should migrate to it (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:39-42`). Today SmartPrompts has its own enum with the five values `normal`, `oily`, `dry`, `combination`, and `sensitive` (`apps/api/app/Modules/SmartPrompts/Domain/Enums/SkinType.php:5-14`). `RecommendationRequestData` imports that module-local enum (`apps/api/app/Modules/SmartPrompts/Application/DTOs/RecommendationRequestData.php:5-20`). `SmartPromptsController` also imports the module-local enum and hardcodes validation as `in:normal,oily,dry,combination,sensitive` before calling `SkinType::from(...)` (`apps/api/app/Modules/SmartPrompts/Presentation/Controllers/SmartPromptsController.php:10-13`, `apps/api/app/Modules/SmartPrompts/Presentation/Controllers/SmartPromptsController.php:27-67`).

**Problem:** Moving the enum but leaving validation as a hardcoded string preserves today's five values but reintroduces the drift the shared enum is supposed to eliminate. A future enum addition, rename, or value deprecation would update product suitability and partner casts but not the SmartPrompts request validator. The DTO and controller would also keep importing the deleted old namespace unless every consumer is migrated in the same change.

**Recommendation:** Import the shared enum in `RecommendationRequestData` and `SmartPromptsController`, delete the module-local enum, and derive validation from `SkinType::cases()` or Laravel's `Enum` rule against the shared enum. Add a focused SmartPrompts test that proves all shared enum values are accepted and an invalid value is rejected. Regenerate TypeScript types after the enum move.

### [NIT] Equivalence confidence needs explicit precision/range
**Spec section:** §1.7 Equivalents / Complements, lines 85-89; §8 testing strategy, lines 180-183.

**Code evidence:** The spec defines `product_equivalents.confidence` only as "decimal nullable" (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:85-87`). It later acknowledges this is subject to the precision contract and says to use bcmath-safe handling, no float casts (`docs/superpowers/specs/2026-06-28-parapharmacy-merchandising-design.md:180-183`). The codebase treats decimals explicitly: product prices and tax rates declare concrete precision/scale in migrations (`apps/api/database/migrations/tenant/2025_11_30_052910_create_products_table.php:23-25`), ingredient concentration uses `decimal('concentration_numeric', 12, 4)` (`apps/api/database/migrations/tenant/2026_01_08_174850_create_product_ingredient_table.php:18-20`), and `Product` casts decimal fields with explicit scales (`apps/api/app/Modules/Product/Domain/Product.php:143-156`).

**Problem:** `decimal nullable` leaves three implementation choices unstated: whether confidence is a fraction (`0.00` to `1.00`), a percentage (`0.00` to `100.00`), or a whole-score convention like enrichment's `0-100`; what precision/scale the database should enforce; and what request/seed validation should reject. Because this field is not money or quantity, ambiguity is more likely to lead to float casts, inconsistent UI labels, or impossible comparisons across seeded and enriched relations.

**Recommendation:** Define the contract explicitly or drop the field for the demo. If keeping it, use a simple percentage score such as `decimal(5,2)` with range `0.00 <= confidence <= 100.00`, cast to `decimal:2`, validate as a decimal string with min/max, and document whether `null` means "unscored" rather than "0 confidence." Add one test for range enforcement and one serialization test that proves the value remains a string/decimal-safe value.

## Verdict
No-go until the spec is amended. The core product idea is sound, but building from the current text would ship stale POS merchandising data on upgraded devices and leave too many contracts implicit across brand scoping, product payloads, customer sync, and shared enum validation. Fix the v58 cursor reset requirement first, then tighten the schema/API/sync contracts above; after those edits, the design is implementable with focused tests rather than broad rework.
