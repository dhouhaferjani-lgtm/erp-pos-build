### BLOCKER 1 — Pricing intent can be correct on paper and still fail in the real write paths

The §4.5 contract is good, but it has to be implemented before persistence in every product mutation path. Today `ProductController::store()` creates from `$validated` at `apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:400-404`, `ProductController::update()` mass-assigns `$validated` at `:688-689`, and `ProductService::upsert()` maps `sale_price` at `apps/api/app/Modules/Product/Application/Services/ProductService.php:54-63` before `Product::updateOrCreate()` at `:103-110`. The spec says `sale_price` present without `pricing_mode` must mean `manual`, and says explicit `pricing_mode:auto` from the margin editor is authoritative, but it does not name a backend owner that mutates controller/import payloads consistently. Failure path: an import updates an existing `auto` product's `sale_price` without `pricing_mode`; absent a central resolver, the price is stored while mode remains `auto`, and the next WAC event calls `updateSalePrice()` at `apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:288`, `:580`, or `:762` and overwrites it.

### BLOCKER 2 — WAC still has a no-CompanyContext scale trap

The spec's §8 test bullet identifies the right failure mode, but §4.5 and §4.10 do not give an implementation mechanism. `MarginService::scale()` currently calls `$this->scaleResolver->getScale()` with no argument at `apps/api/app/Modules/Product/Application/Services/MarginService.php:42-45`. `CurrencyScaleResolver::getScale()` throws if there is no explicit currency and no bound `CompanyContext` at `apps/api/app/Shared/Infrastructure/CurrencyScaleResolver.php:36-51`. CLAUDE rule 20 says queued jobs and fiscal projections run with no CompanyContext and must pass explicit currency at `CLAUDE.md:78-83`. WAC calls `updateSalePrice($product)` directly at `apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:288`, `:580`, and `:762`, so a purchase/return/adjustment in a worker-like context can fail before pricing mode or resolver hierarchy matters. The spec should require explicit product/company currency threading in the backend design, not only in tests.

### BLOCKER 3 — Correct resolution is useless if the product DTO/editor still consume raw overrides

The spec requires the editor to seed from effective margin and show provenance/clamp state in §5.2, but it does not state that `ProductData` gains an `effective_margins` payload. Current list and show actions return `ProductData::fromModel()` at `apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php:131-135` and `:320-321`. `ProductData` exposes only raw override fields at `apps/api/app/Modules/Product/Application/DTOs/ProductData.php:47-48` and serializes those raw fields at `:86-87`. Current FE pricing code reads `product.target_margin_override` / `product.minimum_margin_override` or defaults at `apps/web/src/features/inventory/components/pricing/ProductPricingCard.tsx:34-38`. Failure path: a product inherits target/minimum from a parent category and the resolver clamps `minimum`, but the editor still sees null overrides and company defaults, so it displays the wrong band, compares a margin edit against the wrong inherited value, and never renders `minimum_clamped`. The spec should make effective margin DTO threading a named acceptance item, not leave it implicit as "new API payload."

## Summary

- The four earlier BLOCKERs are mostly addressed in design intent, but percent-scale output and pricing-mode implementation ownership remain partial.
- The biggest residual blocker is not formula math; it is making §4.5's pricing intent state machine run through the actual controller and import/upsert paths.
- The second blocker is WAC scale resolution: the spec names the no-CompanyContext test but does not require the backend signature/currency threading that makes the test pass.
- The third blocker is DTO/API threading: `EffectiveMargins` must be returned where the product editor/list actually read pricing data, including `minimum_clamped`.
- `resolveMany()` is achievable without N+1 using materialized `path`, but the spec should explicitly prohibit `getAncestors()` in batch resolution and test both loaded and unloaded direct category relations.
