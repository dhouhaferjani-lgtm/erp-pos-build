# [documents] Reverting a confirmed purchase order erases its confirmation evidence and records no actor or reason

**Filed:** 2026-09-09 (owner question on PR #210: "why would confirmed → draft be necessary; is it OK?") · **Severity:** Major (audit) · **Regression:** no, pre-existing.

**Today:** `DocumentPostingService::revertPurchaseOrder()` (`apps/api/app/Modules/Document/Domain/Services/DocumentPostingService.php:587-640`) is well fenced — only a confirmed PO; refused when any goods receipt exists (`PURCHASE_ORDER_HAS_RECEIPTS`), when a supplier invoice references it (`PURCHASE_ORDER_HAS_SUPPLIER_INVOICES`), or when it came from an RFQ (`PURCHASE_ORDER_FROM_RFQ`); the document number is preserved by `DocumentStatusService::transition()` (`DocumentStatusService.php:135-142`, renumbering refused). But the transition writes `confirmed_at = null, confirmed_by = null` (`DocumentPostingService.php:634-637`) and the PO branch receives no `$actorId` (`:517` signature vs `:587` call), so after a revert nobody can tell that the order was ever confirmed, by whom, who reverted it, or why. No domain event is emitted for the transition (no `Document*Status*`/`*Reverted*` event class exists under `Modules/Document/Domain/Events`).

**Benchmark:** Odoo keeps the confirmed order locked and lets only the Purchase Administrator unlock/edit or cancel-then-reset-to-draft, with the chatter recording each step; ERPNext never edits a submitted PO in place — Cancel (only without linked receipts/invoices) then Amend creates revision `PO-0001-1` and the original stays as an immutable cancelled record; Dolibarr allows "Modify" back to draft only before approval. Common ground: editing before any downstream document is allowed; the audit trail of the confirmation and of the reversal is always retained.

**Fix:** (1) pass the actor into the PO branch and require a `reason` (FormRequest, ≥ 3 chars) on `POST /documents/{id}/revert` for confirmed POs; (2) do NOT null `confirmed_at/confirmed_by` — keep them and add `reverted_at`, `reverted_by`, `revert_reason` (nullable columns, additive migration), cleared again on the next confirmation which also bumps a `confirmation_count`; (3) emit a stored `DocumentRevertedToDraftV1` event (document id, type, actor, reason, previous confirmed_at/by) via the DomainEvent base so the fiscal/audit chain sees it; (4) surface the revert in the document's timeline on the web; (5) tests: second company, re-run (revert twice → 422), receipts/invoices/RFQ guards unchanged.

**Acceptance:** after confirm → revert → confirm, the timeline shows both confirmations and the reversal with actor + reason, and the document number is unchanged.
