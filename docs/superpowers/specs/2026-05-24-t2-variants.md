## 1. Purpose

Current `Product` is single-SKU. Verticals depending on size/color/material variants (orthopedic line within parapharma, fashion, footwear, eyewear, cosmetics, sportswear) cannot be properly modeled. There is a deferred TODO at `apps/erp/apps/api/database/migrations/2026_01_05_150000_create_product_batches_table.php:23` (`// TODO: Add when product_variants table exists`).

This module ships a generic product variants capability — `ProductAttribute` / `ProductAttributeValue` / `ProductVariant` + variant-aware stock / movements / reservations / batches / document lines + admin matrix editor — reusable across every retail vertical.

Architectural reference: UnoPim (github.com/unopim/unopim, MIT, Akeneo-inspired) — extract concepts, rebuild natively in our hexagonal stack.

**Naming:** Per Codex review NOTE, the service class is `ProductVariantService` (not `VariantService` — avoids near-collision with existing `ImageVariantService`).

**Patterns to mirror:**

- **Hexagonal split:** Domain (entities + VOs + enums) → Application (services + DTOs) → Infrastructure (Eloquent repositories) → Presentation (controllers + React components)
- **Backward-compat at service layer:** every method taking `product_id` today gets an optional `variant_id`. When `variant_id` is null, behavior identical to today.
- **Stock at variant level when variants exist, product level when they don't:** `stock_levels` rows have nullable `variant_id`. Row with `variant_id=NULL` means product-level stock.
- **Tenant + company + location scoping** preserved everywhere via Stancl context (DB boundary post-T6).

**Constraints:** hexagonal, constructor injection, strict typing, enums, TDD, PHPStan level 8.
**Migration placement:** all T2 migrations → `database/migrations/tenant/` per topology contract.
**Cross-DB FK:** intra-tenant only.

## 3. Domain model

### New entities (all in tenant DB)

**`ProductAttribute`** (reusable across products within a tenant)
- `id`, `code` (snake_case, unique per tenant), `name` (localized), `data_type` enum (`Text`, `Numeric`, `Boolean`, `Date`, `Selection`, `Color`, `Image`), `is_variant_axis` (bool), `display_order`, `is_active`

**`ProductAttributeValue`** (possible values when `data_type=Selection` or `is_variant_axis=true`)
- `id`, `attribute_id` (FK), `code` (snake_case), `label` (localized), `hex_color` (optional, Color type), `display_order`

**`ProductVariant`**
- `id`, `product_id` (FK Product), `variant_code` (string, unique per product), `sku` (string, unique per tenant), `barcode` (nullable, unique when present), `name_suffix` (string, e.g., "39 / Noir"), `is_default` (bool), `is_active` (bool), `display_order`
- `price_override` (decimal, nullable — falls back to parent product price)
- `cost_override` (decimal, nullable)
- `image_url` (nullable — variant-specific image)
- Timestamps + soft deletes

**`ProductVariantAttributeValue`** (junction — which attribute values define this variant)
- `id`, `variant_id` (FK), `attribute_id` (FK), `attribute_value_id` (FK)
- Composite unique: `(variant_id, attribute_id)`

### Schema changes to existing tenant tables (all nullable for backward compat)

- `stock_levels`: ADD `variant_id` (FK, nullable). **Unique constraint strategy (revised per round-2 B-2):**
  - Drop existing `(tenant_id, product_id, location_id)` unique
  - Replace with TWO partial unique indexes that **match the existing key shape** (do NOT add `company_id` — it's still nullable on legacy rows per `2025_11_30_131000`, and adding it would let two `company_id=NULL` rows for same `(tenant_id, product_id, location_id)` coexist, weakening the constraint):
    - `(tenant_id, product_id, location_id)` WHERE `variant_id IS NULL`
    - `(tenant_id, product_id, variant_id, location_id)` WHERE `variant_id IS NOT NULL`
  - This handles PostgreSQL's NULL-distinct semantics correctly AND preserves the pre-migration constraint shape exactly for non-variant rows
  - When a future migration backfills `company_id` and makes it non-nullable, the unique key can be tightened in a separate dedicated migration; that's out of T2 scope
- `stock_movements`: ADD `variant_id` (FK, nullable)
- `stock_reservations`: ADD `variant_id` (FK, nullable)
- `product_batches`: ADD `variant_id` (FK, nullable). Drop existing `(company_id, product_id, batch_number)` unique. Replace with TWO partial unique indexes (`product_batches.company_id` is non-nullable per `2026_01_05_150000:19` so we CAN include it):
    - `(company_id, product_id, batch_number)` WHERE `variant_id IS NULL`
    - `(company_id, product_id, variant_id, batch_number)` WHERE `variant_id IS NOT NULL`
  - **Removes the TODO comment** at `2026_01_05_150000:23`.
- `document_lines` (sales/invoice/PO/etc): ADD `variant_id` (FK, nullable)
- `pos_receipt_lines`: ADD `variant_id` (FK, nullable). **Coexistence with existing XOR constraint** (per round-2 P2-3): the table currently enforces `(product_id IS NOT NULL AND composite_item_id IS NULL) OR (product_id IS NULL AND composite_item_id IS NOT NULL)` per `2026_03_03_100000_add_composite_item_id_to_pos_receipt_lines.php:36-40`. Variants hang off the product side only; add CHECK constraint `(variant_id IS NULL OR product_id IS NOT NULL)` to prevent variant_id being set with a composite item.
- `pos_receipt_line_batch_allocations`: ADD `variant_id` (FK, nullable) — preserves the batch+variant link

## 4. Public contracts

### Application services

```php
AttributeService
  ::create(CreateAttributeCommand): ProductAttribute
  ::addValue(AddAttributeValueCommand): ProductAttributeValue
  ::listForTenant(): Collection<ProductAttribute>  // tenant auto-resolved via Stancl

ProductVariantService
  ::createVariant(CreateVariantCommand): ProductVariant
  ::generateMatrix(UUID $productId, array $attributeIds): Collection<ProductVariant>
  ::resolveBarcode(string $barcode, UUID $companyId): ProductVariant|Product|null  // returns variant if matched, falls back to product
  ::resolveSku(string $sku, UUID $companyId): ProductVariant|Product|null
  ::deactivate(UUID $variantId): ProductVariant
```

### Events

- `ProductVariantCreated`, `ProductVariantUpdated`, `ProductVariantDeactivated`
- `ProductAttributeCreated`, `ProductAttributeValueAdded`

### REST endpoints

- `GET /api/v1/products/{id}/variants`
- `POST /api/v1/products/{id}/variants` — single variant
- `POST /api/v1/products/{id}/variants/matrix` — generate cartesian
- `PUT /api/v1/products/{id}/variants/{variantId}`
- `DELETE /api/v1/products/{id}/variants/{variantId}` (soft delete)
- `GET /api/v1/product-attributes` — list per tenant
- `POST /api/v1/product-attributes`
- `POST /api/v1/product-attributes/{id}/values`
- Existing `GET /api/v1/products/lookup?barcode=...` extended to return variant when matched

## 8. Adversarial review checklist

**Reviewer instruction (mandatory):** *"Verify findings against actual code at cited paths. Read the files. Do not make assumptions. Pay special attention to: (1) backward compat — every existing service method should still work for non-variant products; grep for callsites of every modified method; (2) the partial unique index strategy — verify both indexes exist and behave correctly with NULL variant_id; (3) batch + variant integration — `product_batches` unique constraint update must not break existing batch rows; (4) the spec said `CompositeItemVariant` is style reference only, not full lifecycle pattern — verify implementation doesn't shortcut by copying it."*

- [ ] **Backward compat sweep:** grep callsites of `StockAdjustmentService::receive`, `::issue`, `::transfer`, `::reserve` — verify each works with `variant_id=null`
- [ ] **Partial unique index correctness:** both indexes created (`WHERE variant_id IS NULL` + `WHERE variant_id IS NOT NULL`); insert tests confirm no false duplicates or false uniques
- [ ] **`product_batches` unique constraint:** updated correctly with NULL-handling
- [ ] **Tenant isolation:** every variant query auto-scoped via Stancl tenant context; cannot read variants from another tenant
- [ ] **FEFO correctness:** mixed variant + non-variant products in same receipt — FEFO returns correct batches per product
- [ ] **Migration safety:** runs cleanly on tenant with existing non-variant data; existing rows get `variant_id=NULL`
- [ ] **Document lines:** invoices/POs print variant_id correctly (e.g., "Chaussure X — 39 / Noir" vs. just product name)
- [ ] **Edge case:** soft-deleted variant held in open POS cart — behavior defined + tested
- [ ] **Variant lifecycle:** implementation has full service/controller/repository structure; doesn't shortcut via the thin CompositeItemVariant pattern (per P1-7)
- [ ] **All migrations in `database/migrations/tenant/`** per topology contract; no cross-DB FKs
