## 1. Problem, definitions, scope

**Problem.** A transfer is decremented at source on `store` and incremented at destination by a quantity-less `complete` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:346-383`): the receiver cannot say "11 of 12 arrived, one broken". No receipt document exists, so nothing can be blind; the three in-transit readers derive incoming from `status = in_transit` alone (`apps/api/app/Modules/Inventory/Application/Services/LocationStockQueryService.php:137-164,217-245`, `apps/api/app/Modules/Inventory/Application/Services/StockMatrixQueryService.php:390-408`, `apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:117-127`) and cannot express a partial receipt. Nobody is told a transfer is coming or arrived short.

**Definitions (M2 r1 — two different things).**
- **Open remainder**: per line, `sent − received − damaged − written_off − returned > 0` while the transfer is `in_transit` or `partially_received`. No reason, no alert, `has_discrepancy` false.
- **Confirmed discrepancy**: (a) **damaged** units declared on a receipt — reason required, alert at receipt; (b) **short** units confirmed by a **close** — write-off or return, reason required, alert at close. Shortness is never asked of a receiver (D2). A shortage confirmed at close is a **transfer-level fact**: its event actor is the closer, and it is never attributed to any receiver as that receiver's own report (§4.4, confirmed attribution ruling).

**In scope.** T-2: receipt document (per-line received/damaged, lot grain); remainder stays in transit; close with `disposition: write_off | return_to_source` (OQ-1) under reconcile + close authority; quantity-based in-transit derivation; stored header + per-line events with a real aggregate anchor; `complete` as the zero-discrepancy delegate for non-blind actors only. T-3: `blind_receiving`; receiver view by construction; server-side blind closure over every reachable surface incl. the POS feeds and the replenishment feeds (§5.0, §5.9); advisory `visibility_version` (§4.5); reconciliation; mobile contract. T-4-min: two DB notifications (§7).

**Out of scope** (ticket each): push/Expo; `ReplenishmentRequestedNotification`; mobile screens (M-1); T-3b implementation; inter-company transfers (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:96-101` still refuses); over-receipt tolerance; alert threshold (v1 = any); **receipt `void`/reversal** — an over-reported receipt has no reversal in v1: a supervisor corrects on-hand with a stock-adjustment document (which refuses destructive reasons on every batch-tracked product, `apps/api/app/Modules/Inventory/Application/Services/StockAdjustmentDocumentService.php:520-531` — such products go through the lot write-off path), while receipt rows, counters, reconciliation and terminal state stay as posted; **receiver note** (D2 ticket T-2b); **analytics read model / dashboard** (T-4 or later — this lane guarantees the stored facts and ships the reference query, §4.4); shrinkage account provisioning (exists: `apps/api/app/Modules/Accounting/Application/Services/InventoryVarianceAccountProvisioner.php:162-169`, purpose `InventoryShrinkageExpense`, `apps/api/app/Modules/Accounting/Domain/Enums/SystemAccountPurpose.php:65-68`); a sidebar `permissions` (any-of) prop (§8); a client-side purge guarantee for pre-flip data (§4.5, R4).

**Transactional fact.** `Migrator::runMigration` wraps `up()` in `$connection->transaction($callback)` whenever the schema grammar supports transactions and `$migration->withinTransaction` is true (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:448-451`); `PostgresGrammar::$transactions = true` (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Schema/Grammars/PostgresGrammar.php:18`, base default `false` at `apps/api/vendor/laravel/framework/src/Illuminate/Database/Schema/Grammars/Grammar.php:31`); `Migration::$withinTransaction = true` by default (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migration.php:19`) and none of this lane's migrations overrides it. Tenant migrations run per tenant DB through `tenants:migrate` (`.claude/context/architecture.md:70`, `docs/architecture/database.md:45`). On PostgreSQL a failing statement rolls the whole migration back: **a half-migrated PG schema cannot exist**.

**Logging fact (r4-M2).** `Migrator::run` selects only files absent from the migrations repository (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:124-159`, `pendingMigrations` rejects every logged name at `apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:150-158`), and `runUp` logs a migration only AFTER `runMigration` returned (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:252-258`). Consequences: (a) a rolled-back migration is unlogged, so the next `tenants:migrate` re-selects and re-executes it — that is the ONLY automatic recovery this spec claims; (b) a logged migration is never re-executed, so `tenants:migrate` does NOT repair post-commit drift (a column, constraint or index dropped by hand after the migration committed). The rev-4 S3 "drop one added column, one CHECK, one index, rerun → identical" test is deleted.

**Manual recovery for post-commit drift (documented, not automated).** An operator writes a NEW forward migration using the recipe below (its guards make re-creating the missing object a no-op everywhere else) and runs `tenants:migrate`; `tenants:run migrate:rollback` is never used for this lane's migrations because `down()` drops the receipt tables and their rows. The runbook line goes into `docs/handoff/PROMOTION-CHECKLIST-*` (§11 step 4).

**Recipe (each migration of §11 step 1).** (1) New tables: one `Schema::create` carrying the `uuid('id')->primary()` and every NOT NULL column (precedents `apps/api/database/migrations/tenant/2026_05_28_120000_create_stock_transfers_table.php:29-30`, `apps/api/database/migrations/tenant/2026_07_04_100000_create_goods_receipts_tables.php:14-16,34-36`), guarded by `Schema::hasTable`; no `constrained()`/`unique()` inside the closure. ### 3.1b Model contract — decimal strings end to end (r5-M4)

**Why casts, not the driver.** The precision contract's storage tier requires an Eloquent `decimal:N` cast on every money/quantity model property so reads return canonical strings (`docs/architecture/precision-contract.md:15-20`, cast rule at `docs/architecture/precision-contract.md:19`), and its service tier forbids `(float)$model->decimalProp` and native arithmetic on those values (`docs/architecture/precision-contract.md:22-28`, forbidden list at `docs/architecture/precision-contract.md:28`). PostgreSQL returns `numeric` as a string, but the SQLite test lane returns numeric affinity values, so the cast is the only portable guarantee. The PHPStan guard `ForbidFloatCastOnDecimalProperty` resolves the owning class and fires only on properties carrying a `decimal:*` cast (`apps/api/app/PHPStan/Rules/ForbidFloatCastOnDecimalProperty.php:20-35`, node type `Cast\Double` at `apps/api/app/PHPStan/Rules/ForbidFloatCastOnDecimalProperty.php:46-48`) — an un-cast column is invisible to it. Precedents for the exact shape: `StockTransferLine` declares `@property numeric-string $quantity` (`apps/api/app/Modules/Inventory/Domain/StockTransferLine.php:25-27`) with `'quantity' => 'decimal:4'` (`apps/api/app/Modules/Inventory/Domain/StockTransferLine.php:56-63`); `StockTransferLineBatchAllocation` likewise (`apps/api/app/Modules/Inventory/Domain/StockTransferLineBatchAllocation.php:21,46-52`); `StockTransfer` casts `transfer_cost` (`apps/api/app/Modules/Inventory/Domain/StockTransfer.php:85-96`, `'transfer_cost' => 'decimal:4'` at `apps/api/app/Modules/Inventory/Domain/StockTransfer.php:91`); `CompanyFraudSettings` mixes `'integer'`, `'boolean'` and `'decimal:4'` casts (`apps/api/app/Modules/Compliance/Domain/CompanyFraudSettings.php:131-150`).

### 4.4 Pattern-detection reference query (owner requirement; attribution CONFIRMED — `docs/handoff/OWNER-QUESTIONS-consolidated-2026-09-06.md:106`)
Attribution rules: (1) per-line receipt events record exactly what each receiver posted (received/damaged, their identity, `actorRole = receiver`, blind flag); (2) a shortage discovered at close is a transfer-level fact — its line events carry `actorRole = closer` and are never counted as the closer's "mis-receiving" nor attributed to the last receiver; (3) the query is scoped per company and measures, per receiver, (a) damage reported vs the company baseline and (b) supervisor-confirmed variance on lines that receiver posted (receipt-line events joined to the close outcome on the same `transferLineId`); a line posted by several receivers counts for each of them with `shared_line = true`. Because `event_class` is indexed and `event_properties` is jsonb (`apps/api/database/migrations/tenant/2025_11_30_102448_create_stored_events_table.php:16-17,20`), no new table is needed:
```sql
WITH e AS (SELECT event_properties AS p FROM stored_events
           WHERE event_class = 'App\Modules\Inventory\Domain\Events\StockTransferReceiptLineRecordedV1'
             AND created_at >= now() - interval '90 days'),
postings AS (SELECT p->>'companyId' company_id, p->>'actorUserId' user_id, p->>'transferLineId' line_id,
                    (p->>'quantityDamaged')::numeric damaged FROM e WHERE p->>'actorRole' = 'receiver'),
receipts AS (SELECT company_id, user_id, line_id, COUNT(*) postings, SUM(damaged) damaged
             FROM postings GROUP BY 1, 2, 3),
closes AS (SELECT DISTINCT p->>'transferLineId' line_id
           FROM e WHERE p->>'actorRole' = 'closer' AND (p->>'quantityWrittenOff')::numeric > 0),
baseline AS (SELECT company_id, AVG((damaged > 0)::int) damage_rate FROM receipts GROUP BY 1)
SELECT r.company_id, r.user_id, COUNT(*) lines_posted, SUM(r.postings) postings,
       AVG((r.damaged > 0)::int) damage_rate, b.damage_rate company_damage_rate,
       COUNT(*) FILTER (WHERE c.line_id IS NOT NULL) lines_later_written_off,
       bool_or((SELECT COUNT(*) FROM receipts r2 WHERE r2.line_id = r.line_id) > 1) shared_line
FROM receipts r JOIN baseline b USING (company_id) LEFT JOIN closes c USING (line_id)
WHERE r.company_id = :company_id GROUP BY 1, 2, b.damage_rate ORDER BY lines_later_written_off DESC, damage_rate DESC;
```
**Grain (r5-m2).** The metric is LINE-based, as its column names say: `receipts` collapses every posting by the same receiver on the same transfer line into ONE row (`GROUP BY company_id, user_id, line_id`) before any rate is computed, so `lines_posted`, `damage_rate`, the company baseline and `lines_later_written_off` each count a `(receiver, transfer line)` pair once however many partial receipts that receiver posted on it; `postings` is reported beside it for volume. `damaged` per pair is the SUM over the receiver's postings (a receiver who declares damage on any of their postings for a line has damaged that line). `closes` is `DISTINCT` per line so the left join cannot multiply rows. `shared_line` is true when more than one receiver posted on the line. T16 pins the shape, including a repeated-partial-receipt fixture. A T-4/later lane turns this into a read model + `fraud-alerts` rule.

### 5.1 `POST /stock-transfers/{id}/receive` — `can:inventory.transfers.complete` + `canAccessLocation(destination)`

Request (`ReceiveStockTransferRequest`; rule 19: `numeric` + `regex:/^\d+(\.\d{1,4})?$/`, accepts JSON numbers and numeric strings — ingress contract `docs/architecture/precision-contract.md:30-40`, quantity regex at `docs/architecture/precision-contract.md:35`; clients send strings):
```json
{ "idempotency_key": "uuid (required)", "notes": "string|null",
  "lines": [ { "transfer_line_id": "uuid", "quantity_received": "11.0000", "quantity_damaged": "1.0000",
               "discrepancy_reason": "damaged_in_transit", "discrepancy_note": "box crushed",
               "lots": [ { "batch_id": 812, "quantity_received": "11.0000", "quantity_damaged": "1.0000" } ] } ] }
```
Rules:
1. **Idempotency first.** `DB::transaction(attempts: 3)` → `lockTransfer` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:734-742`) → lookup by `(tenant_id, company_id, idempotency_key)`: same `transfer_id` + equal `payload_hash` → stored receipt, 200, `meta.replayed = true`, regardless of state; different transfer or hash → `IDEMPOTENCY_KEY_REUSED`. Only then `canReceive()` else `TransferStateException`.
2. **Key race across transfers.** Catch `UniqueConstraintViolationException` outside the transaction, re-read the committed winner by key (precedent `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:170-190`), apply rule 1's discriminator.
3. **Canonical payload hash.** `ReceiptPayloadCanonicalizer`: drop `idempotency_key`; `notes`/`discrepancy_note` absent ≡ null; quantities → 4-dp via `bcadd($q,'0',4)`; lines sorted by `transfer_line_id`, lots by `batch_id`; recursive `ksort`; `json_encode(JSON_UNESCAPED_SLASHES|JSON_UNESCAPED_UNICODE|JSON_THROW_ON_ERROR)` (precedent `apps/api/app/Modules/Fiscal/Application/Services/TerminalRegistrySnapshotService.php:540-558`); sha256.
4. **Valuation preflight (M3).** If Σ `quantity_damaged` > 0: `InventoryValuationModeResolver::requirePerpetual(companyId)` (`apps/api/app/Modules/Inventory/Application/Services/InventoryValuationModeResolver.php:79-88`) BEFORE any movement; its `UnsupportedValuationModeException` (`apps/api/app/Modules/Inventory/Domain/Exceptions/UnsupportedValuationModeException.php:22`, no HTTP mapping today) → typed 422 `VALUATION_MODE_UNSUPPORTED`, no rows.
5. **Validation contract (r5-M1) — every payload the schema forbids is refused before any write.** Two layers, both complete before the first row/movement/event; a failure at either layer leaves zero `stock_transfer_receipts`/`_lines`/`_lots` rows, zero movements, zero `stored_events` and unchanged counters (T5 asserts each case). **Layer A — `ReceiveStockTransferRequest`** (structural; runs in the FormRequest before the controller, hence before rule 1; sibling `apps/api/app/Modules/Inventory/Presentation/Requests/StoreStockTransferRequest.php:65-109`; cross-field rules via `withValidator()` → `$validator->after()` exactly as `apps/api/app/Modules/Inventory/Presentation/Requests/StockAdjustmentLineRules.php:85-144` (`withValidator` is invoked by `apps/api/vendor/laravel/framework/src/Illuminate/Foundation/Http/FormRequest.php:94-95`; `after` at `apps/api/vendor/laravel/framework/src/Illuminate/Validation/Validator.php:440`); failures are the framework `VALIDATION_ERROR` 422 (`apps/api/bootstrap/app.php:325-334`) with static field messages). **Layer B — `StockTransferReceiptService`** (data-dependent; inside the transaction after rule 1, the header lock and all line product advisory locks taken in one sorted call as `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:326-339`; evaluated for every line before any write; failure = typed `TransferReceiptFailureReason` 422, `details = {transfer_line_id, batch_id}`). `is_lot_tracked` is NOT a request field: the service derives it as "the transfer line has ≥ 1 batch allocation" (the grain I3 binds the receipt to; §11 step 1e uses the same definition for the backfill) and stores it on the receipt line.

### 6.4 Freight — CONFIRMED default (owner, `docs/handoff/OWNER-QUESTIONS-consolidated-2026-09-06.md:106`; benchmark `docs/superpowers/reviews/2026-09-09-benchmark-owner-decisions-po-revert-freight-attribution.md`; algorithm preserved verbatim from rev 3/4)
**Today.** `capitalizeTransferCost` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:631-707`) weights on shipped `quantity` (`computeAllocationWeights`, `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:714-728`), allocates 100 % of `transfer_cost` with the last line absorbing the 4-dp residual (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:671-707`), and capitalises each share via `recordCostAdjustment` (`apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:745-831`), which writes a quantity-0 `Adjustment` movement (`apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:812-830`) and **no journal**, and no-ops when company-owned quantity is 0 (`apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:771-775`). Transfer freight has no GL leg in this module.

**Confirmed algorithm.** At the terminal transition (`completed` or `closed_*`), once per transfer:
1. `goodTotal = Σ lines.quantity_received`, `sentTotal = Σ lines.quantity` (4-dp strings).
2. Working scale `w = max(ALLOCATION_SCALE, s + 4)` where `ALLOCATION_SCALE = 6` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:65-70`) and `s = CurrencyScaleResolverInterface::getScaleSafe($company->currency_code, 3)` (rule 19; the terminal transition may run without `CompanyContext`).
3. `pool = CurrencyScale::bcformat(bcmul(transfer_cost, bcdiv(goodTotal, sentTotal, w), w), 4)` — one rounding, at the stored scale of `transfer_cost` (truncation, `docs/architecture/precision-contract.md:25-26`).
4. `freight_uncapitalized = bcsub(transfer_cost, pool, 4)` → `stock_transfers.freight_uncapitalized` (`decimal(15,4)`; exact by construction; I7).
5. The existing allocation loop runs on `pool` instead of `transfer_cost`, with **landed weights**: `ProRataQuantity` → `quantity_received`; `ProRataValue` → `quantity_received × unit_cost_snapshot`; `EqualPerLine` → `1` for lines with `quantity_received > 0`, else `0`. Zero-weight lines are skipped (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:661-663`); the last cost-bearing line absorbs the residual so Σ `allocated_transfer_cost = pool` exactly (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:671-707`). `recordCostAdjustment` per line as today.
6. Damaged, written-off and returned units are all outside `goodTotal`, so their freight share is the residual: never capitalised, no journal, surfaced in reconciliation and carried on the header events.

**Worked example** (`transfer_cost = 120.0000`, `pro_rata_quantity`, TND `s = 3`, `w = 7`). Lines: A 8 sent, B 4 sent. Receipt: A 5 good, B 4 good; close `write_off` of A's remaining 3. `goodTotal = 9`, `sentTotal = 12`; `bcdiv('9','12',7) = 0.7500000`; `pool = bcformat(90.0000000, 4) = 90.0000`; `freight_uncapitalized = 120.0000 − 90.0000 = 30.0000`. Allocation on landed weights 5 and 4 (total 9): A `bcmul('90.0000', bcdiv('5','9',7), 7) = 49.9999995` → 4 dp `49.9999`; B (last) = `90.0000 − 49.9999 = 40.0001`. Persisted: `A.allocated_transfer_cost = 49.9999`, `B = 40.0001`, `freight_uncapitalized = 30.0000`; `49.9999 + 40.0001 + 30.0000 = 120.0000` (I7). Single-line T4 (12 sent, 5 good, 7 written off): `pool = 50.0000`, `freight_uncapitalized = 70.0000` = 7/12 of 120. T3 (11 good + 1 damaged of 12): `pool = 110.0000`, residual `10.0000`.

Rejected alternatives (recorded, not open): (a) "expense with shrinkage" — Dr `InventoryShrinkageExpense` / Cr a transfer-freight clearing account; would need a new `SystemAccountPurpose`, provisioning in `InventoryVarianceAccountProvisioner` and every seeded country chart, and would double-hit P&L unless the clearing account is reconciled against the freight invoice; (b) mode-consistent pool ratio — identical to the default under `pro_rata_quantity`.

Precision (rule 19): quantities numeric strings; `bccomp/bcadd/bcsub` at `QTY_SCALE = 4`; no float; `ForbidFloatCastOnDecimalProperty` guards models.
