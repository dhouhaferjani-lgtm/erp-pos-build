## 1. Problem, definitions, scope

**Problem.** A transfer is decremented at source on `store` and incremented at destination by a quantity-less `complete` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:346-383`): the receiver cannot say "11 of 12 arrived, one broken". No receipt document exists, so nothing can be blind; the three in-transit readers derive incoming from `status = in_transit` alone (`apps/api/app/Modules/Inventory/Application/Services/LocationStockQueryService.php:137-164,217-245`, `apps/api/app/Modules/Inventory/Application/Services/StockMatrixQueryService.php:390-408`, `apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:117-127`) and cannot express a partial receipt. Nobody is told a transfer is coming or arrived short.

**Definitions (M2 r1 — two different things).**
- **Open remainder**: per line, `sent − received − damaged − written_off − returned > 0` while the transfer is `in_transit` or `partially_received`. No reason, no alert, `has_discrepancy` false.
- **Confirmed discrepancy**: (a) **damaged** units declared on a receipt — reason required, alert at receipt; (b) **short** units confirmed by a **close** — write-off or return, reason required, alert at close. Shortness is never asked of a receiver (D2). A shortage confirmed at close is a **transfer-level fact**: its event actor is the closer, and it is never attributed to any receiver as that receiver's own report (§4.4).

**In scope.** T-2: receipt document (per-line received/damaged, lot grain); remainder stays in transit; close with `disposition: write_off | return_to_source` (OQ-1) under reconcile authority; quantity-based in-transit derivation; stored header + per-line events with a real aggregate anchor; `complete` as the zero-discrepancy delegate for non-blind actors only. T-3: `blind_receiving`; receiver view by construction; blind closure over every reachable surface incl. the POS clients and the replenishment feeds (§5.0, §5.9, §8b); `visibility_version` contract (§4.5); reconciliation; mobile contract. T-4-min: two DB notifications (§7).

**Out of scope** (ticket each): push/Expo; `ReplenishmentRequestedNotification`; mobile screens (M-1); T-3b implementation; inter-company transfers (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:96-101` still refuses); over-receipt tolerance; alert threshold (v1 = any); **receipt `void`/reversal** — an over-reported receipt has no reversal in v1: a supervisor corrects on-hand with a stock-adjustment document (which refuses destructive reasons on every batch-tracked product, `apps/api/app/Modules/Inventory/Application/Services/StockAdjustmentDocumentService.php:520-531` — such products go through the lot write-off path), while receipt rows, counters, reconciliation and terminal state stay as posted; **receiver note** (D2 ticket T-2b); **analytics read model / dashboard** (T-4 or later — this lane guarantees the stored facts and ships the reference query, §4.4); shrinkage account provisioning (exists: `apps/api/app/Modules/Accounting/Application/Services/InventoryVarianceAccountProvisioner.php:162-169`, purpose `InventoryShrinkageExpense`, `apps/api/app/Modules/Accounting/Domain/Enums/SystemAccountPurpose.php:65-68`); a sidebar `permissions` (any-of) prop (§8 — the receiver's entry points are the bell deep link and the list URL).

## 3. Domain model and schema contract

### 3.1 New columns and the migration guard recipe (r2-M7 / r3-M2 — promise narrowed)

**Transactional fact.** `Migrator::runMigration` wraps `up()` in `$connection->transaction($callback)` whenever the schema grammar supports transactions and `$migration->withinTransaction` is true (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migrator.php:448-451`); `PostgresGrammar::$transactions = true` (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Schema/Grammars/PostgresGrammar.php:18`, base default `false` at `apps/api/vendor/laravel/framework/src/Illuminate/Database/Schema/Grammars/Grammar.php:31`); `Migration::$withinTransaction = true` by default (`apps/api/vendor/laravel/framework/src/Illuminate/Database/Migrations/Migration.php:19`) and none of this lane's migrations overrides it. PostgreSQL DDL is transactional, so on the production/staging lane (`tenants:migrate` per tenant DB, `apps/api/config/database.php:87-120`) a failing statement rolls the whole migration back: **a half-migrated PG schema cannot exist**. The rev-3 "rerun after ANY partial failure repairs exactly what is missing" promise is withdrawn; the r3-M2 counter-examples (a missing primary key, a dropped NOT NULL column on a populated table) describe states the PG lane cannot reach, so no primary-key pass and no nullable/backfill/not-null repair sequence is added (REJECT of the remedy, with this proof).

### 4.4 Pattern-detection reference query (owner requirement; attribution default — orchestrator, owner to confirm, §12 OD-2)

```sql
SELECT r.company_id, r.user_id, COUNT(*) lines_posted,

FROM receipts r JOIN baseline b USING (company_id) LEFT JOIN closes c USING (line_id)
WHERE r.company_id = :company_id GROUP BY 1, 2, b.damage_rate ORDER BY lines_later_written_off DESC, damage_rate DESC;
```

### 5.1 `POST /stock-transfers/{id}/receive` — `can:inventory.transfers.complete` + `canAccessLocation(destination)`

Request (`ReceiveStockTransferRequest`; rule 19: `numeric` + `regex:/^\d+(\.\d{1,4})?$/`, accepts JSON numbers and numeric strings — ingress contract `docs/architecture/precision-contract.md:30-40`, quantity regex `:35`; clients send strings):

```json
  "lines": [ { "transfer_line_id": "uuid", "quantity_received": "11.0000", "quantity_damaged": "1.0000",
               "discrepancy_reason": "damaged_in_transit", "discrepancy_note": "box crushed",
               "lots": [ { "batch_id": 812, "quantity_received": "11.0000", "quantity_damaged": "1.0000" } ] } ] }
```
Rules:
1. **Idempotency first.** `DB::transaction(attempts: 3)` → `lockTransfer` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:734-742`) → lookup by `(tenant_id, company_id, idempotency_key)`: same `transfer_id` + equal `payload_hash` → stored receipt, 200, `meta.replayed = true`, regardless of state; different transfer or hash → `IDEMPOTENCY_KEY_REUSED`. Only then `canReceive()` else `TransferStateException`.
2. **Key race across transfers.** Catch `UniqueConstraintViolationException` outside the transaction, re-read the committed winner by key (precedent `apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:170-190`), apply rule 1's discriminator.
3. **Canonical payload hash.** `ReceiptPayloadCanonicalizer`: drop `idempotency_key`; `notes`/`discrepancy_note` absent ≡ null; quantities → 4-dp via `bcadd($q,'0',4)`; lines sorted by `transfer_line_id`, lots by `batch_id`; recursive `ksort`; `json_encode(JSON_UNESCAPED_SLASHES|JSON_UNESCAPED_UNICODE|JSON_THROW_ON_ERROR)` (precedent `apps/api/app/Modules/Fiscal/Application/Services/TerminalRegistrySnapshotService.php:540-558`); sha256.
4. **Valuation preflight (M3).** If Σ `quantity_damaged` > 0: `InventoryValuationModeResolver::requirePerpetual(companyId)` (`apps/api/app/Modules/Inventory/Application/Services/InventoryValuationModeResolver.php:79-88`) BEFORE any movement; its `UnsupportedValuationModeException` (`apps/api/app/Modules/Inventory/Domain/Exceptions/UnsupportedValuationModeException.php:22`, no HTTP mapping today) → typed 422 `VALUATION_MODE_UNSUPPORTED`, no rows.
5. Locks: after the header lock, all line product advisory locks in one sorted call (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:326-339`); per line: line ∈ transfer else `LINE_NOT_ON_TRANSFER`; `received + damaged ≤ remainder` else `OVER_RECEIPT`; lot rules (I3) else `UNKNOWN_LOT` / `LOT_OVER_RECEIPT` / `LOT_REQUIRED`; Σ(received + damaged) > 0 else `NOTHING_TO_RECEIVE`.
6. **Remainder vs discrepancy (r3-M4).** Omitted lines = open remainder. `discrepancy_reason` required iff `quantity_damaged > 0` (`DISCREPANCY_REASON_REQUIRED`), and must satisfy `allowedFor(Receipt)` = `damaged_in_transit | other` (`DISCREPANCY_REASON_INVALID`); the damage movement reason is always `MovementReason::Damage` whatever the declared reason (§6.1); `has_discrepancy = Σ damaged > 0`.
7. Writes: movements (§6) → counters → receipt rows (`sequence` = count + 1; `is_lot_tracked` from the line's product) → status (`completed` if Σ remainder = 0 else `partially_received`; on `completed`: `completed_by/at`, then §6.4 capitalisation) → stored events via `persist($event, $receiptId)` (§4.0) → GL buffer flush inside the root transaction (§6.2) → `afterCommit`: plain `StockTransferReceiptPosted`, and `StockTransferCompleted` when terminal.
8. Response 201 `{ data: { receipt: StockTransferReceiptData, transfer: <gated builder output> }, meta: { replayed: false } }`.

### 6.4 Freight — exact default pending OQ-4 (M4 r1/r2; orchestrator default, owner to confirm; Preserved verbatim from rev 3)
**Today.** `capitalizeTransferCost` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:631-707`) weights on shipped `quantity` (`computeAllocationWeights`, `:714-728`), allocates 100 % of `transfer_cost` with the last line absorbing the 4-dp residual (`:671-707`), and capitalises each share via `recordCostAdjustment` (`apps/api/app/Modules/Inventory/Application/Services/WeightedAverageCostService.php:745-831`), which writes a quantity-0 `Adjustment` movement (`:812-830`) and **no journal**, and no-ops when company-owned quantity is 0 (`:771-775`). Transfer freight has no GL leg in this module.

**Default algorithm.** At the terminal transition (`completed` or `closed_*`), once per transfer:
1. `goodTotal = Σ lines.quantity_received`, `sentTotal = Σ lines.quantity` (4-dp strings).
2. Working scale `w = max(ALLOCATION_SCALE, s + 4)` where `ALLOCATION_SCALE = 6` (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:65-70`) and `s = CurrencyScaleResolverInterface::getScaleSafe($company->currency_code, 3)` (rule 19; the terminal transition may run without `CompanyContext`).
3. `pool = CurrencyScale::bcformat(bcmul(transfer_cost, bcdiv(goodTotal, sentTotal, w), w), 4)` — one rounding, at the stored scale of `transfer_cost` (truncation, `docs/architecture/precision-contract.md:25-26`).
4. `freight_uncapitalized = bcsub(transfer_cost, pool, 4)` → `stock_transfers.freight_uncapitalized` (exact by construction; I7).
5. The existing allocation loop runs on `pool` instead of `transfer_cost`, with **landed weights**: `ProRataQuantity` → `quantity_received`; `ProRataValue` → `quantity_received × unit_cost_snapshot`; `EqualPerLine` → `1` for lines with `quantity_received > 0`, else `0`. Zero-weight lines are skipped (`apps/api/app/Modules/Inventory/Application/Services/StockTransferService.php:661-663`); the last cost-bearing line absorbs the residual so Σ `allocated_transfer_cost = pool` exactly (`:671-707`). `recordCostAdjustment` per line as today.
6. Damaged, written-off and returned units are all outside `goodTotal`, so their freight share is the residual: never capitalised, no journal, surfaced in reconciliation and carried on the header events.

**Worked example** (`transfer_cost = 120.0000`, `pro_rata_quantity`, TND `s = 3`, `w = 7`). Lines: A 8 sent, B 4 sent. Receipt: A 5 good, B 4 good; close `write_off` of A's remaining 3. `goodTotal = 9`, `sentTotal = 12`; `bcdiv('9','12',7) = 0.7500000`; `pool = bcformat(90.0000000, 4) = 90.0000`; `freight_uncapitalized = 120.0000 − 90.0000 = 30.0000`. Allocation on landed weights 5 and 4 (total 9): A `bcmul('90.0000', bcdiv('5','9',7), 7) = 49.9999995` → 4 dp `49.9999`; B (last) = `90.0000 − 49.9999 = 40.0001`. Persisted: `A.allocated_transfer_cost = 49.9999`, `B = 40.0001`, `freight_uncapitalized = 30.0000`; `49.9999 + 40.0001 + 30.0000 = 120.0000` (I7). Single-line T4 (12 sent, 5 good, 7 written off): `pool = 50.0000`, `freight_uncapitalized = 70.0000` = 7/12 of 120. T3 (11 good + 1 damaged of 12): `pool = 110.0000`, residual `10.0000`.

**Owner alternative (a) "expense with shrinkage"**: post the residual as Dr `InventoryShrinkageExpense` / Cr a transfer-freight clearing account. Requires a new `SystemAccountPurpose`, provisioning in `InventoryVarianceAccountProvisioner` and every seeded country chart, because freight was never debited to Inventory by this module (its invoice sits in Expenses/Purchasing) — a second P&L hit unless the clearing account is reconciled against that invoice. Not the default. Alternative (b) mode-consistent pool ratio (Σ landed weight ÷ Σ shipped weight instead of the quantity ratio) is listed for completeness; identical to the default under `pro_rata_quantity`.

Precision (rule 19): quantities numeric strings; `bccomp/bcadd/bcsub` at `QTY_SCALE = 4`; no float; `ForbidFloatCastOnDecimalProperty` guards models.
