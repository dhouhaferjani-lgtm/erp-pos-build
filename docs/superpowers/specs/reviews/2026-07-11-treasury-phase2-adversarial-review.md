## Part A — treasury-reviewer (full-spec review)

**Spec claims that VERIFIED clean** (no findings): `MovementSourceType::Instrument` already exists (`app/Modules/Treasury/Domain/Enums/MovementSourceType.php:17`); `payments.instrument_id` exists and is written (`database/migrations/tenant/2025_11_30_120000_create_treasury_tables.php:144`, `PaymentController.php:601`); `payment_instruments.payment_id` exists and has no writer (`2025_11_30_120000...php:127`); `payment_instruments.amount` is `decimal(15,3)` post-widen; the register is unpaginated `->get()` (`PaymentInstrumentController.php:52`); bounce piggybacks `instruments.clear` (`Treasury/Presentation/routes.php:111-113`); `instruments.update/bounce/remit` are genuinely new (`RolesAndPermissionsSeeder.php:210-213`); canonical `PaymentDTO` carries `instrumentSerial` (`Fiscal/Domain/DTOs/Canonical/PaymentDTO.php:31`); the bridge loads the full `PaymentMethod` model so it CAN see `has_maturity` (`TreasuryReceiptBridge.php:405`); `JournalCode` has no `EF` and unmapped types fall to `OD` (`JournalCode.php:33-39`); deposit's bank-repo guard exists (`PaymentInstrumentController.php:175`); the FE two-call orchestration is exactly at `PaymentForm.tsx` ~608-658; `createPaymentReceivedJournalEntry` takes `paymentMethodAccountId` as a parameter, so the B2B debit-line swap is a clean seam (`GeneralLedgerService.php:981-991`); the immutability-trigger template exists (`2026_07_08_100200`); partial-unique-index precedent exists (`2026_07_08_150000_add_idempotency_key_to_payments.php`).

**Framing correction to the review mandate:** `treasury:reconcile` check #2 is movement→JE only — it asserts every non-exempt *movement* carries a Posted, amount-matching JE (`ReconcileTreasuryCommand.php:248-303`). There is **no** "every cash/bank journal line has a movement" direction. A JE-without-movement on 5112 (or the bank account) does not freeze anything — it *silently* diverges GL from cash. That makes findings 7 and 12 worse, not better: the failure mode is undetected wrong books, not a loud freeze.

### Findings (T-series)

**T1. [BLOCKER] §12.3 vs §6 — document-lock / GL-advisory-lock inversion (real deadlock).** Spec §6 orders every transition: instrument lock → `postEntryNow` (company advisory lock) → port. §12 then orders bounce: JE first, subledger reopening third. But the existing B2B payment flow locks document rows BEFORE taking the advisory lock: `PaymentController.php:670-674` (`lockForUpdate()->findOrFail($allocationData['document_id'])`) runs before the GL post at `:781/:794`. Concurrent scenario: payment on invoice D holds D's row lock and waits for the company advisory lock; bounce holds the advisory lock and waits for D's row lock. AB/BA deadlock, per company, on a hot path. *Fix:* re-order §12 — acquire all document row locks (sorted) BEFORE `postEntryNow`; state the global lock order explicitly in §6: instrument row(s, sorted) → document row(s, sorted) → GL advisory → repository row.

**T2. [BLOCKER] §8 — the deferred-tender cutover is direction-blind; supplier payments by traite break the books.** `PaymentController::store()` is one endpoint for BOTH directions (`$isSupplierPayment` branch, `PaymentController.php:406/775-806`). §8's swap/no-movement rule is written entirely for customer receipts. Applied naively to a supplier payment by check/traite, either (a) the JE still credits repo cash (`createSupplierPaymentJournalEntry`, `GeneralLedgerService.php:711-721`) with no movement → silent GL↔cash divergence reconcile cannot see, or (b) an inbound receipt account is misused on an outbound payment. §2/D-4 never says what `PaymentController` does with an outbound `has_maturity` payment. *Fix:* scope the cutover to customer-direction; supplier-direction `has_maturity` payments keep Phase-① behavior verbatim this phase, with the instrument registered `direction=outbound`, and a test pinning that.

**T3. [BLOCKER] Refund/reversal of a deferred payment — spec silent; current code pays out cash that never arrived.** `PaymentRefundService::refundPayment()` refunds ANY `Completed` payment (`PaymentRefundService.php:89`, `canRefund()` `:479-481`) and `postRefundGlAndMovement()` unconditionally posts a GL reversal against the repository cash account and records a movement OUT (`:439-473`). Post-cutover, a check/traite payment is `Completed` with NO cash in; refunding it decrements the drawer/bank for money never received — and the pending instrument stays `Received`, later clearing cash IN for an un-allocated invoice. `partialRefund` and `reversePayment` (`:211`, `:523`) share the hole. *Fix:* payments with a linked non-terminal instrument are not refundable via the cash-refund path (422 → route through §12.4 cancel / §12 bounce); refunds of a payment whose instrument already Cleared are a normal cash refund.

**T4. [HIGH] §12.3/§19.1 — the "existing allocation-reversal path" (`DELETE /payments/{id}/allocations`) does not exist.** No such route exists (all module routes grepped; Treasury routes have only smart-payment preview/apply, `Treasury/Presentation/routes.php:192-198`), and `PaymentAllocationService` has no delete/reverse method. The actual machinery: negative-amount `PaymentAllocation` rows (as `PaymentRefundService.php:156-163` writes) + the pgsql trigger `update_document_balance_due()` recomputing `balance_due` from `SUM(payment_allocations.amount)` (`2026_01_08_214145_add_balance_due_cache_trigger.php:28-61`). *Fix:* specify negative allocation rows on a reversal record (never DELETE); note the sqlite test driver has no such trigger (assert via pgsql CI or maintain `balance_due` imperatively as `PaymentController` does).

**T5. [HIGH] §12.3 — reopening `balance_due` leaves the document `status = Paid`; the reopened invoice disappears from every Posted-filtered surface.** `PaymentController` flips fully-paid docs to `DocumentStatus::Paid` (`PaymentController.php:716-718`); the balance trigger never touches status. `UpcomingPaymentsService::openDocuments()` filters `status = Posted` (`UpcomingPaymentsService.php:70`) — a bounced-and-reopened invoice appears in NO échéancier/forecast, defeating §10 for exactly the invoices most at risk. `DocumentFullyPaid` has also already fired (loyalty etc.). *Fix:* revert status Paid→Posted on reopening (verify the document-immutability trigger `2025_12_11_054716` permits it); pin a test that a reopened invoice reappears in `UpcomingPaymentsService`.

**T6. [HIGH] §11 reconcile check #4 contradicts §5.6/§8 — the provenance scope can never see the receipt-side debits.** §5.6: the receipt-side payment JE stays `source_type=payment`. §11: check #4 compares against EF/instrument-sourced lines only. The debit that puts value INTO 5112/413 is payment/pos-sourced — invisible to an EF-scoped sum → permanent false drift on every tenant from day one. *Fix:* define the GL side over all lines on the (dedicated) portfolio accounts with the §18 watermark, or join payment/pos-sourced lines through `payments.instrument_id`; pin in the drift-seeding test.

**T7. [HIGH] §8 — excess/advance path unaddressed for deferred tenders.** For a check exceeding the allocated total, `PaymentController` posts `createCustomerAdvanceJournalEntry` debiting `repository->gl_account_id` (`PaymentController.php:826-865`; builder `GeneralLedgerService.php:330-341`). Post-cutover that debits BANK CASH with no movement — undetectable. And the instrument's amount (full payment) vs allocated-only portfolio debit drifts check #4 by the excess. *Fix:* for deferred tenders the ENTIRE payment amount debits the portfolio account (allocation JE + advance JE both swap their debit line), or reject excess on deferred tenders.

**T8. [HIGH] §8 covers two writers; three more B2B endpoints accept `has_maturity` methods.** `MultiPaymentController::createSplitPayment` validates `splits.*.instrument_id` (`MultiPaymentController.php:123-125`), `recordDeposit` accepts `instrument_id` (`:250-252`) and moves cash through the port, `recordPaymentOnAccount` (`:412`) takes any method; `PaymentController::storeMultiple` takes arbitrary methods per line (`PaymentController.php:995-998`) and records per-line movements (`:1502-1521`). All keep cash-at-receipt for a traite and create no instrument — G7 bypassed through every side door. *Fix:* enumerate ALL web payment writers; implement the cutover or 422 `has_maturity` methods on paths that don't (a defensible Phase-② scope cut, but written down).

**T9. [HIGH] §7 bounce-before-clear fee — "movement out for fee only" vs JE "Cr bank (fee + VAT)" will FREEZE live bank repos.** Reconcile check #2: when the JE books lines on the repo's own `gl_account_id`, the movement amount MUST match those lines (`ReconcileTreasuryCommand.php:405-423`); mismatch → freeze (`:294-302`). The §7 fee JE credits bank for `fee + fee_vat`; a movement of `fee_amount` alone mismatches by the VAT and freezes the repository nightly. *Fix:* fee movement amount = `bcadd(fee_amount, fee_vat_amount, scale)`; pinned test.

**T10. [HIGH] §9 POS refund contre-passation shape wrong — no customer receivable in the POS receipt JE.** The POS receipt-side entry (post-swap) is Dr P / **Cr ProductRevenue** with `partner_id: null` (`GeneralLedgerService.php:2586-2623`); there is no 411 line to reverse. As specced, the refund leaves Revenue overstated and a dangling 411 debit. *Fix:* contre-passation = Dr ProductRevenue / Cr P-or-R; the maturity refund leg SKIPS its Out movement (no cash came in, none goes out).

**T11. [HIGH] §9/§18 pre-cutover replay — instrument creation must be SUPPRESSED for pre-cutover-shaped legs; the watermark can't catch them.** Post-deploy replay of a pre-cutover check event: the leg Payment exists (cash-debit JE + movement) but NO instrument → §9 step 1 as written creates one; pending instrument whose value was already cashed → double-counts échéancier + drifts check #4; `created_at` post-watermark so §18 misses it. *Fix:* shape probe — if the leg's movement exists (port key `fiscal_event:{id}:payment:{index}`), leg is pre-cutover: accept as complete, create NO instrument, post no new JE.

**T12. [HIGH] §8 — deferred payment with no/unledgered repository posts NO portfolio JE while still closing the invoice.** The payment JE is gated on `$repository->gl_account_id` (`PaymentController.php:770-774`); `repository_id` nullable and only conditionally guarded (`:541-559`). A deferred payment with no repository allocates with no Dr-P JE → invoice settled, portfolio empty, check #4 drifts. *Fix:* `repository_id` (custody) REQUIRED for `has_maturity` payments; decouple the portfolio-JE gate from the repo's `gl_account_id`.

**T13. [MED] §6/§8 — instrument-row lock ordering across flows unspecified.** If `PaymentController` writes `payment_instruments.payment_id` after the GL post, that's advisory → instrument, inverting the lifecycle order. *Fix:* pre-validate + `lockForUpdate` the linked instrument BEFORE `postEntryNow`; slips lock line instruments id-sorted; write the total order into §6.

**T14. [MED] §9 — "the drawer repository the bridge already resolves" is not what the bridge resolves.** `resolveDefaultRepository()` returns the FIRST tenant+company repository with a `gl_account_id`, ordered by id — explicitly NOT method/drawer-aware (`TreasuryReceiptBridge.php:575-608`). *Fix:* reword to "the bridge's default-repository resolution (P2-6 deferral)" + note the custody-quality limitation.

**T15. [MED] §5.1 `bank_id uuid FK banks` — the `banks` table does not exist on dev.** `feat/bank-reference-verification` has not merged; a `->constrained('banks')` migration fails on every tenant. *Fix:* plain indexed uuid, no FK (or `hasTable`-gated constraint); say so in §5.1.

**T16. [MED] Instrument endpoints tenant-scoped only — cross-company leak inherited.** `index/show/deposit/clear/bounce/transfer` filter `tenant_id` only (`PaymentInstrumentController.php:33-35, 65-68, 147-149, 214-216, 255-257, 302-304`) though `company_id` exists. *Fix:* add the `company_id` predicate during the Phase-② controller rework.

**T17. [MED] Hardcoded `'TND'` currency defaults vs the §2 currency hard guard.** Instrument store defaults `currency ?? 'TND'` (`PaymentInstrumentController.php:121`); payments same (`PaymentController.php:604, 1143`). *Fix:* default to company/repository currency; spec in §5.1/§8.

**T18. [MED] Withholding (RAS) on deferred payments — silent.** Certificate created at receipt regardless of method (`PaymentController.php:630-661`); nothing in §12.3 touches it — a bounced traite leaves a live RAS certificate. *Fix:* decision point (expert-comptable): block `withholding_enabled` on deferred tenders, or reverse/flag the certificate at bounce.

**T19. [MED] §12.3 × tolerance write-offs.** An invoice closed via `CloseInvoiceWithToleranceService` (`CloseInvoiceWithToleranceService.php:108-118`) then bounced: reversing only the payment's allocations leaves the tolerance allocation + write-off JE → `balance_due` reopens short. *Fix:* reverse tolerance allocations linked to the dishonored payment too + contre-passation of the tolerance JE.

**T20. [LOW] §19.5 — `country_payment_settings` is per-COUNTRY, not per-company-country** (`unique('country_code')`, no company_id, `2025_12_10_100000...php:14-36`). `instrument_alert_days` will be a country-level default.

**T21. [LOW] §9 — "Deposit/AccountPayment siblings share tender iteration" overstates.** `TreasuryDepositBridge` is single-tender by contract (`TreasuryDepositBridge.php:150`, reads `$view->payment`). Align phrasing.

**T22. [LOW] §16 — add reconcile-#2 pins for the clear/dishonor/bounce_fee movement amounts** (movement-vs-bank-line equality, pgsql).

**Verdict: APPROVE-WITH-FIXES** — architecture correct; Rev 1 not dispatch-ready until T1-T12 reconciled.

## Part B — fiscal-pos-reviewer (POS/fiscal perimeter: §9, §8-POS, §16, §17)

**Q1 — Canonical payload reality.** The canonical tender leg carries exactly 6 fields: `amount`, `foreign_currency_amount/code`, `instrument_serial`, `instrument_type`, `method_code` (`Fiscal/Domain/DTOs/Canonical/PaymentDTO.php:27-34`). No method id, no repository id, no transaction reference. The bridge resolves the full `PaymentMethod` tenant-scoped (`TreasuryReceiptBridge.php:391-405` via `EloquentPaymentMethodResolver.php:36-48`), so `has_maturity` + the new `instrument_kind` are resolvable on the worker with no CompanyContext. **`instrument_serial` semantics are voucher-only** (`PaymentInstrumentKind.php:39-42`; `AdvancedPaymentsModal.tsx:452-469`; `SaleReceiptPayload.ts:360-366`). The check number a cashier types lands in `transaction_reference` (`AdvancedPaymentsModal.tsx:452`, shown when `has_maturity` at :522) which is **NOT in the sealed payload** — lost to the server. **Check tenders DO reach the bridge today**: `AdvancedPaymentsModal.tsx:212` lists ALL active methods; only quick-cash and account-payment exclude `has_maturity` (`paymentStore.ts:857, 1231`).

**Q2 — Fiscal-hash safety.** Confirmed safe as designed: bridge reads via `CanonicalPayloadReader::forSaleReceipt()` (`TreasuryReceiptBridge.php:310`) — read-only; nothing touches `fiscal_events`, canonical bytes, or `pos_receipt_payments`. One wording defect (F9).

**Q3 — Idempotency/replay.** Advisory lock `TreasuryReceiptBridge.php:258-263`, per-leg `payments.idempotency_key` `:456-461`, complete-set replay incl. "Payment+GL landed but movement never did → complete it" `:463-469` + `record()` `:548-572`, legacy null-key short-circuit `:292-301`. The spec's movement-existence marker is not deterministic — F5.

**Q4 — Refund/void path.** `invoice_type_code` detection at `:322-323`; today's refund leg posts `createPOSRefundReversalEntry` (Dr Revenue / Cr Cash — `GeneralLedgerService.php:2686-2706`) + movement Out. Job retry contract: throw → attempts++ → backoff → `dead_lettered` after 5 (`ApplyFiscalEventProjectionJob.php:392-401, 428-458`). "Never throw" compatible only if scoped narrowly (F3).

**Q5 — Rule 20.** Queue `fiscal-projections` covered (`horizon.php:209`); no new queue. Explicit currency already the bridge pattern (`:523, :561`). Gap: lifecycle service CompanyContext injection vs worker path (F6).

**Q6 — Split tender / Z-report.** No drift source: device expected_cash counts only `payment_type === 'CASH'` (`apps/pos/src/lib/offline/zReportService.ts:210-243`); per-method expectations from device-local receipts; server expected_cash from `cash_drawer_operations`, never `payment_repositories.balance` (`CashDrawerService.php:387-413`). Skipping the check-leg movement is invisible to X/Z/drawer counts on both layers. Spine reconcile stays coherent because the JE debit swaps off the cash account in the same change (check #2 movement↔JE-line assertion `ReconcileTreasuryCommand.php:248-300`).

### Findings (F-series)

**F1. [BLOCKER] §9 refund bullet — no mechanism to locate the instrument to cancel; no leg↔instrument mapping rule.** The refund is its OWN fiscal event; keys are `fiscal_event:{refund_event_id}:…` — the instrument is keyed under the ORIGINAL event. Original resolvable via `original_receipt_reference.fiscal_event_id` (`OriginalReceiptReferenceDTO`, used by `PosCoreReceiptProjection.php:513-524`) but the spec never says so; index correspondence undefined for partial refunds / split tenders. *Fix:* resolve original event id from the canonical reference; candidates = still-`Received` instruments `idempotency_key LIKE 'fiscal_event:{original_id}:instrument:%'`; match on (method `instrument_kind`, exact amount); 0 or >1 match ⇒ alert path, never guess-cancel.

**F2. [BLOCKER] §9 refund bullet — contre-passation JE shape wrong for POS + unstated interaction with the standard refund reversal (double-reversal risk).** POS receipt JEs have no AR leg — post-swap original is Dr P / Cr Revenue; contre-passation is **Dr Revenue / Cr P**. Booking Dr 411 strands a debit in AR and leaves revenue unreversed. Separately the spec never says the maturity refund leg must SKIP `createPOSRefundReversalEntry` (Cr cash! `GeneralLedgerService.php:2697-2706`) and skip movement-Out — implemented literally the leg gets BOTH. *Fix:* one explicit posting table for the POS maturity refund leg: cancel-JE Dr Revenue / Cr P-or-R IS the leg's entire GL effect; no refund-reversal entry; no movement; ALSO define the remitted/cleared-instrument case (today "do not touch it" posts nothing for that leg — revenue never reversed; standard cash reversal is then correct since the drawer really pays out — decide and write it down).

**F3. [HIGH] §9 "never throw" over-broad — collides with retry/dead-letter contract.** Blanket never-throw marks rows `applied` over swallowed transient DB/GL failures — the silent-skip class the file documents as a fixed BLOCKER (`TreasuryReceiptBridge.php:199-215`). Redelivery: after successful cancel the instrument is `Cancelled` — must be an idempotent no-op, not a repeated audit row. *Fix:* scope never-throw to business outcomes (active/missing/ambiguous instrument ⇒ alert); transient exceptions propagate; `Cancelled` ⇒ silent no-op; alert row keyed per `(refund_event_id, leg_index)`.

**F4. [HIGH] §9/§5.5 — missing portfolio account on the worker path unspecified.** §5.5's pre-transaction 422 is interactive-only; the bridge cannot 422. Missing `checks_to_collect`/`effects_receivable` account must THROW (→ retry → dead-letter → operator seeds chart), matching the `gl_account_id` fail-closed posture (`TreasuryReceiptBridge.php:437-444`). *Fix:* state in §9, pin in §16.

**F5. [HIGH] §9 replay-shape marker not deterministic.** The idempotent-hit branch completes Payment-exists/movement-missing legs by recording the movement (`:463-469, 548`); post-cutover a maturity leg with no movement is ALSO the expected new shape — movement-absence cannot distinguish. *Fix:* probe the existing leg JE's debit-line account — repo `gl_account_id` ⇒ old shape (movement expected/completable, NO instrument backfill); portfolio account ⇒ new shape (instrument expected, movement forbidden); no Payment row ⇒ new shape. Durable-artifact deterministic; §18 watermark then serves only reconcile-#4 exclusion. State whether old-shape legs get instruments backfilled (recommend NO). Pre-Task-20 legacy events short-circuit at `:292-301` and never reach the maturity logic.

**F6. [MED] §6/§9 — `InstrumentLifecycleService` CompanyContext injection vs projection invocation.** On the Horizon worker no context is bound; "where interactive" is not an implementable seam. *Fix:* context-free entrypoint (explicit tenant/company/currency) used by the bridge; §16 cleared-context test for the cancel path.

**F7. [MED] §9 — `instrumentSerial` reference branch is dead for checks; device-typed check number silently lost.** `instrument_serial` populated only by the voucher flow; the check reference travels as `transaction_reference`, not canonical. Every POS check will be `POS-{event}-{index}` + `needs_details`. *Fix:* say the device reference is LOST (not "taken if present"); add guard: 422 when a method is both `has_maturity=true` and instrument-bearing per `requiresInstrumentForMethodCode()` (voucher-kind maturity method would collide with the voucher GL bypass `GeneralLedgerService.php:2258-2285`).

**F8. [MED] §9 — sibling-bridge sharing overstated; §7 credit-line language doesn't fit deposits.** Deposit/AccountPayment bridges are single-leg (`TreasuryDepositBridge.php:176-192`, `TreasuryAccountPaymentBridge.php:163-179`). A deposit's JE credits a liability, not "customer receivable" — state the swap flow-agnostically: swap only the cash-debit line; existing credit line untouched. Custody nuance: the device's repository choice (`AdvancedPaymentsModal.tsx:57-58`) never reaches the server; custody = `resolveDefaultRepository()` (possibly a cash drawer) — say it.

**F9. [LOW] §17 wording — "canonical payload/hash bytes unread-unmodified" is false as written**: the bridge must and does READ the payload (`:310`). Certifiable claim: read-only, never mutated, hash bytes never recomputed/re-authored. Add test pin: new flow writes nothing to `pos_receipt_payments`.

**F10. [LOW] Open questions §19.2 answered in code:** `MovementSourceType::Instrument` exists (`MovementSourceType.php:17`); `payments.instrument_id` exists (`2025_11_30_120000:144`, `Payment.php:80`). §5.1 survey claims verified accurate.

**Verdict: APPROVE-WITH-FIXES** — fix the refund/void sub-spec (resolution, JE shape, throw scope), swap the replay marker to the JE-shape probe, specify fail-closed on missing portfolio accounts — then dispatchable.
