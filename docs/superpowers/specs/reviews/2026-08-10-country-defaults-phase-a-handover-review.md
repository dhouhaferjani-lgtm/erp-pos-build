- **Accepted specification:** `docs/superpowers/specs/2026-08-08-country-defaults-super-admin-design.md` (Rev 14); closure: `docs/superpowers/specs/reviews/2026-08-08-country-defaults-spec-review.md`, Round 14

- **Reviewer effort level:** HIGH — adversarial, repository-grounded, read-only. `HEAD` and local `origin/dev` were both verified at `7d85232cc54abd6a6b2135f476205ab434e71a66`; no fetch was needed.

The accepted design was treated as settled. This review asks only whether the handover faithfully and completely dispatches that design against the current repository.

## Findings

### F-1 — P1 — The D-3 authority recommendation does not define a boundary-clean dependency shape

The handover correctly detects the existing authority: `CountryTaxConfigurationRegistry` owns `supports_stamp_duty` in its private map and returns false for unlisted countries (`apps/api/app/Modules/Taxation/Application/Registries/CountryTaxConfigurationRegistry.php:14-33,48-50`), and both live tax-surface reads call it (`apps/api/app/Modules/Taxation/Presentation/Controllers/TaxConfigurationController.php:245-265`). It also correctly requires one timbre authority (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:37,103-105,118-124`).

The dispatch remains non-implementable, however, because “exposed through `Shared/Contracts`, registry delegates” does not say what is a contract, what is the implementation, where either lives, or how it is bound (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:404-410`). Putting an implementation in `Shared/Contracts` would itself violate the repository rule that this location contains interfaces and cross-module access is only through those interfaces, events, or a module public service (`.claude/context/architecture.md:45-52`). Letting the new Country Defaults module import the Taxation registry would reverse the dependency and make the central provisioning/certification kernel depend on a tenant-tax application class. Leaving the current boolean in `CountryTaxConfigurationRegistry::MAP` while adding a new registry would create the duplicate authority the handover forbids.

**Recommended fix:** settle the direction in the handover. Create `apps/api/app/Shared/Contracts/CountryDefaults/CountryAccountingCapabilities.php` as an interface exposing `supportsStampDuty(string): bool` and `version(): string`; create the sole implementation at `apps/api/app/Modules/CountryDefaults/Application/Services/CountryAccountingCapabilitiesService.php`, with the `{TN}` predicate and version scalar together; bind it in `CountryDefaultsServiceProvider`; constructor-inject the shared contract into `CountryTaxConfigurationRegistry`, remove `supports_stamp_duty` from that registry's `MAP`, and have `supportsStampDuty()` delegate. Keep only the seeder-class map in Taxation. Require a source/architecture test that fails if another production predicate or capability country set appears.

### F-2 — P1 — Module placement and the implementation file map are explicitly unresolved

The handover tells the implementer to decide between a new module, `app/Modules/Admin`, and legacy controllers, and then repeats that decision in VERIFY-AT-DISPATCH (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:362-364,431-432`). This is a hard stop for M1/M2, not a harmless implementation detail. The repository architecture requires Domain/Application/Infrastructure/Presentation separation (`.claude/context/architecture.md:18-43`). The existing Admin module is only a monitoring slice (`apps/api/app/Modules/Admin/Presentation/Controllers/MonitoringController.php:5-20`), while legacy fleet/vertical controllers still sit under `App\Http\Controllers\Api\Admin` (`apps/api/app/Http/Controllers/Api/Admin/SuperAdminController.php:5-32`; `apps/api/app/Http/Controllers/Api/Admin/VerticalConfigController.php:5-32`). The handover introduces a substantial domain-generic template lifecycle, not another method on a fleet controller.

Even after choosing a module, a fresh session must guess locations for `CertificationScope`, the 41-entry manifest, the protected-code registry, serializer, three central models, services, static country provider, command, routes, provider binding, golden artifacts, and frontend feature. M1–M6 name these artifacts but do not give a path map (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:100-116,141-150,178-198,214-233,255-280,301-320`).

**Recommended fix:** prescribe a new module rooted at `apps/api/app/Modules/CountryDefaults/`, with `Domain/ValueObjects/CertificationScope.php`, `Domain/Enums/{TemplateDomain,TemplateStatus}.php`, `Domain/Services/ProvisioningRequiredPurposesV1.php`, `Application/Services/{CountryAccountingCapabilitiesService,TemplatePublishingService,TemplateAssignmentService,CountryTemplateResolver,CanonicalCoaSerializer}.php`, `Infrastructure/Models/{AdminTemplate,AdminTemplateAccount,CountryTemplateAssignment}.php`, `Presentation/Controllers`, `Presentation/Requests`, `Presentation/Resources`, `Presentation/routes.php`, and `Providers/CountryDefaultsServiceProvider.php`. Register the provider in `apps/api/bootstrap/providers.php` and load its routes as `SupportAccessServiceProvider` does (`apps/api/app/Modules/SupportAccess/Providers/SupportAccessServiceProvider.php:27-52`). Keep only central authentication controller/middleware changes in `apps/api/app/Http/...`. Add exact migration, command, fixture, test, config, and `apps/web/src/features/adminCountryDefaults/` paths to each milestone.

### F-3 — P1 — The proposed `admin/auth` change is ambiguous at a security-critical middleware boundary

The handover says the `admin/auth` group “moves to `EnsureCentralAdmin`” (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:186-189,419-422`). The live route has two different boundaries: public, throttled `POST /admin/auth/login` at `apps/api/routes/api.php:37-41`, and only the nested logout/profile group has `auth:sanctum-admin` plus `super_admin` at `apps/api/routes/api.php:43-47`. Moving the whole prefix under `EnsureCentralAdmin` would make login require an already-authenticated administrator. Moving or weakening the outer full-admin group would expose dashboard/fleet/billing/monitoring routes, which currently share `auth:sanctum-admin`, `super_admin`, and `throttle:admin-sensitive` (`apps/api/routes/api.php:56-59`). `EnsureSuperAdmin` also enforces the exact `super_admin` role and active state (`apps/api/app/Http/Middleware/EnsureSuperAdmin.php:42-59`), whereas `RequireCentralAdminRole` already checks active state and exact listed roles (`apps/api/app/Http/Middleware/RequireCentralAdminRole.php:17-30`).

**Recommended fix:** prescribe the minimal edit byte-for-byte: leave `POST /v1/admin/auth/login` public and throttled; replace only the nested logout/`me` group's `'super_admin'` middleware with `EnsureCentralAdmin::class` (or a newly registered `central_admin` alias), retaining `auth:sanctum-admin`; leave the `Route::prefix('admin')` full-admin group unchanged. Add route-inventory assertions for unauthenticated login availability, all three roles on `me`/logout, `defaults_editor` denial on every full-admin route, and the existing full-admin middleware list.

### F-4 — P1 — The Release-2 switch is not an executable two-stage deployment contract

The accepted spec settles the ordering: Release 1 creates schema and draft imports, humans publish and assign, `country-defaults:verify` passes in staging and production, and only then do readers switch; the entrypoint is explicitly not the interlock (`docs/superpowers/specs/2026-08-08-country-defaults-super-admin-design.md:195-203`). The handover proposes a default-legacy config flag and a separate commit, but marks both as needing dispatch confirmation and does not name the config key, environment variable, owning file, the exact two read sites, or how “Release 2” is activated without merging unsafe reader code (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:278-281,423-426`). This leaves a fresh session to choose a rollout mechanism for the riskiest milestone.

**Recommended fix:** settle the mechanism in the brief: add `apps/api/config/country_defaults.php` with `provisioning_enabled => (bool) env('COUNTRY_DEFAULTS_PROVISIONING_ENABLED', false)` and the independently default-off `external_editors_enabled`; branch code may contain both readers, but both company-creation paths select the template reader only from the uncached config value at call time. Release 1 deploys with `COUNTRY_DEFAULTS_PROVISIONING_ENABLED=false`; after authenticated certification, all assignments, and a zero exit from `country-defaults:verify` on staging and production, Release 2 changes deployment configuration to true. Name rollback as restoring false. Require tests for both flag values on both provisioning paths and prove no cache wraps the flag or resolver.

D-1 says the moved numbers are “likely” near zero and VERIFY-AT-DISPATCH asks whether publishing as-is is acceptable (`docs/handoff/CODEX-DISPATCH-country-defaults-phase-a-2026-08-10.md:35,83-90,411-415`). A source inventory of the accepted 27 REQUIRED cases over the complete definition arrays (`apps/api/database/seeders/TunisiaChartOfAccountsSeeder.php:125-350`, `apps/api/database/seeders/FranceChartOfAccountsSeeder.php:124-429`, `apps/api/database/seeders/GenericChartOfAccountsSeeder.php:106-237`) yields no missing REQUIRED purpose in TN, FR, or Generic.

Make M0/M4 report both the 27 REQUIRED result and the scope-dependent result: TN has the required stamp purpose; FR/Generic have none as required for non-timbre; then run the full publish gate, not only “zero REQUIRED.”
