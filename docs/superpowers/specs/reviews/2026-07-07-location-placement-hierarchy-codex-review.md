# Verdict
BLOCK. The model direction is sound, but the spec is not implementation-ready because it leaves the delta cursor contract unresolved while the mobile handover calls it "LOCKED", and it relies on soft-delete behavior that current hard-delete/cascade code does not provide. The biggest risks are missed offline updates, incorrect subtree matching, tombstone/unique-index edge cases, and counting behavior at variant and subtree grain.

## Critical Findings
1. Delta sync is not safe enough to freeze for mobile. Spec §4.3 defines `GET /inventory/placements?location_id=&updated_since=&cursor=` and says pagination is "Provisional" with an `updated_at` watermark plus overlap and secondary `id` sort (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:122`, `docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:124`), while §12 still lists cursor semantics as an open question (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:212`). The handover contradicts that by saying the data model + sync strategy are "LOCKED" (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:6`) and tells mobile to build on `updated_since` + tombstones before page size and cursor semantics are pinned (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:64`, `docs/handoff/HANDOVER-location-hierarchy-mobile.md:92`). This can miss a placement updated exactly at the stored watermark, or drift under concurrent writes during a paginated sync. Fix: make the API return a server-captured high-water mark at sync start, page with `WHERE (updated_at, id) > (:last_updated_at, :last_id) AND updated_at <= :sync_high_watermark`, order by `(updated_at, id)`, and persist the tuple cursor only after all pages complete. Use the same normalized SQLite timestamp discipline the repo requires (`CLAUDE.md:82`, `apps/pos/src/lib/db/sqliteTime.ts:24`).

2. Soft-delete semantics are underspecified and conflict with current cascade behavior. The current migration physically cascades `product_zone_assignments.zone_id` deletes through `cascadeOnDelete()` (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:47`), and the current service hard-deletes a zone by calling `$zone->delete()` with no `SoftDeletes` trait on the model (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:48`, `apps/api/app/Modules/Inventory/Domain/LocationZone.php:35`). The spec says `DELETE /inventory/nodes/{node}` soft-deletes a node and subtree and "cascades placements to tombstone" (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:107`), but an FK cascade does not fire on a soft delete, and a later hard delete would erase placement tombstones needed for delta sync. Fix: require `SoftDeletes` on both models, implement subtree + placement tombstoning explicitly inside one transaction, avoid relying on FK cascade for sync tombstones, and document whether hard deletes are ever allowed after mobile clients may need tombstones.

3. The partial unique placement index is the right primitive, but the spec does not define the write algorithm needed once tombstoned duplicates exist. The current table has a hard unique key on `(product_id, location_id)` (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:51`), and current assignment uses `updateOrCreate(['product_id', 'location_id'], ...)` (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:77`). The spec changes that to partial uniqueness `WHERE deleted_at IS NULL` (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:81`, `docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:183`), which allows multiple tombstoned rows for the same product/location. That means the old `updateOrCreate` lookup becomes ambiguous or misses soft-deleted rows depending on `SoftDeletes` scope. Fix: define move/reassign as "update the live row if present; otherwise insert a new live row" with an `ON CONFLICT` target on the partial unique index, or explicitly restore the latest tombstone after locking by `(product_id, location_id)`. Also spell out the migration sequence: drop the old unique index, add `deleted_at`, then create `CREATE UNIQUE INDEX ... ON product_placements(product_id, location_id) WHERE deleted_at IS NULL`.

4. Path matching is unsafe without a code grammar and a real prefix index. The spec stores a slash-joined code path and says a normal btree index supports `LIKE 'A1/%'` (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:53`), while current code validation accepts any string up to 50 chars for `code` (`apps/api/app/Modules/Inventory/Presentation/Requests/CreateZoneRequest.php:36`, `apps/api/app/Modules/Inventory/Presentation/Requests/CreateZoneRequest.php:40`). The explicit `n.path = 'A1' OR n.path LIKE 'A1/%'` shape in the handover is safe against the `A1` vs `A10` prefix collision (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:74`, `docs/handoff/HANDOVER-location-hierarchy-mobile.md:75`), but codes containing `/`, `%`, or `_` break path parsing or LIKE matching. A plain btree is also not reliably used for LIKE prefix scans unless collation/operator class is chosen correctly. Fix: ban `/`, `%`, and `_` from node codes or escape LIKE patterns everywhere; add `varchar_pattern_ops`/`text_pattern_ops`, `ltree`, or a separate ancestor table; and make all subtree queries use `path = :path OR path LIKE :escaped_path || '/%' ESCAPE '\'`.

## Important Findings
1. Node code uniqueness and soft-delete/reactivation semantics are incomplete. The spec preserves unique `(location_id, code)` unchanged (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:51`) while adding node tombstones (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:57`). The current table really has that hard unique key (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:37`). A deleted node would block code reuse forever unless restored, but the spec does not define restore/reactivation or partial uniqueness for live nodes. Fix: either make node code uniqueness partial on `deleted_at IS NULL` and define path behavior for reused codes, or explicitly prohibit reuse and add a restore endpoint/UX.

2. Subtree moves need a stronger atomicity contract. The spec says `path` and `depth` are recomputed for the whole subtree on create/move (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:64`) and that large subtree moves should use a single prefix-replacement UPDATE (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:213`). Current update behavior is a simple fill/save with no tree state to lock (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:40`). Without a transaction that locks the moving node, new parent, and affected subtree, concurrent moves/code changes can produce split paths or cycles. Fix: require `SELECT ... FOR UPDATE` or an advisory lock per `location_id`, verify the parent is not inside the moving subtree after locks are held, then update parent/path/depth and affected descendants atomically.

3. Variant-grain placement is not decided, but the rest of inventory already is variant-aware. Current product placements have no `variant_id` (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:41`, `apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:47`), while counting items persist `variant_id` from seeds (`apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:150`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:159`) and overlap protection is explicitly `(product_id, location_id, variant_id)` aware (`apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:1103`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:1108`). The spec repeats stock grain as `(product, location[, variant])` (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:17`) but keeps placements unique at `(product_id, location_id)` only (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:81`). Fix: explicitly decide that placement is product-level even for variant products, or add nullable `variant_id` with the same two-part partial unique pattern used elsewhere for null/non-null variants.

4. Zone-scoped counting will break unless every old reference is migrated together. Current validation points to `location_zones` (`apps/api/app/Modules/Inventory/Presentation/Requests/CreateCountingRequest.php:53`), checks selected zones against `location_id` via `LocationZone` (`apps/api/app/Modules/Inventory/Presentation/Requests/CreateCountingRequest.php:166`, `apps/api/app/Modules/Inventory/Presentation/Requests/CreateCountingRequest.php:169`), seeds from `ProductZoneAssignment::whereIn('zone_id', ...)` (`apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:326`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:328`), and POS advisories load `LocationZone` names by location (`apps/api/app/Modules/Inventory/Application/Services/CountingBlockService.php:119`, `apps/api/app/Modules/Inventory/Application/Services/CountingBlockService.php:121`). The spec lists these reference updates (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:184`), but it should make them a single backend phase with tests because any one missed reference is a runtime failure after the table rename. Fix: add a migration checklist/test that `CreateCountingRequest`, `InventoryCountingService::zoneItemSeeds`, `assignCountedItemToZone`, `CountingBlockService::zoneAdvisoriesFor`, draft activation, and DTO transform all run against `location_nodes/product_placements`.

5. Assign-as-you-count is ambiguous for subtree counts. Current behavior auto-assigns only when exactly one zone is scoped (`apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:653`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:657`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:697`, `apps/api/app/Modules/Inventory/Application/Services/InventoryCountingService.php:701`). The spec says assign-as-you-count assigns to the selected node when exactly one node is scoped (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:128`), but later says "selected leaf" (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:169`) even though placements can point to any depth, not necessarily a leaf (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:76`). Fix: define the rule as either "assign to the one explicitly selected node, even if it is an ancestor" or require the counter to choose the actual leaf for unexpected items during subtree counts.

6. Endpoint authorization must not rely on the service as a trust boundary. Current routes are properly under API/auth/team/tenant/module middleware (`apps/api/app/Modules/Inventory/Presentation/routes.php:28`) and reuse `inventory.view`/`inventory.adjust` on zones (`apps/api/app/Modules/Inventory/Presentation/routes.php:282`, `apps/api/app/Modules/Inventory/Presentation/routes.php:304`). Current controller resolution also pins zones to the current company through their location (`apps/api/app/Modules/Inventory/Presentation/Controllers/ZoneController.php:145`, `apps/api/app/Modules/Inventory/Presentation/Controllers/ZoneController.php:150`). But `ZoneService::assignProduct()` itself loads the zone by bare id and does not validate the product's company (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:68`, `apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:86`). Fix: make new node/placement service methods accept tenant/company context and validate product, location, node, parent, and target node consistency inside the transaction, not only in controllers.

7. Scale indexing is not sufficient as written. Current assignment listing is unpaginated (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:105`, `apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:110`) and current FE already notes a future pagination switch would need a different response shape (`apps/web/src/features/settings/zones/api.ts:52`, `apps/web/src/features/settings/zones/api.ts:58`). The spec fixes node products to paginated/searchable (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:112`, `docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:143`) but does not name the required indexes. Fix: require `product_placements(location_id, node_id) WHERE deleted_at IS NULL`, `product_placements(location_id, updated_at, id)`, `product_placements(product_id, location_id) WHERE deleted_at IS NULL`, and a proper path-prefix index on `location_nodes(location_id, path ...)`.

8. The mobile handover repeats the SQLite timestamp warning but still leaves format and boundary rules too loose. The handover says `updated_at TEXT (UTC, sqlite format -- see live-counting sqliteTime note)` (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:34`) and "reuse `toSqliteUtc()` discipline" (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:65`), which avoids the known lexical trap documented in the repo (`apps/pos/src/lib/db/sqliteTime.ts:1`, `apps/pos/src/lib/db/sqliteTime.ts:13`). But it does not say whether API timestamps are ISO strings or SQLite strings, which side normalizes the persisted cursor, or whether comparisons are inclusive/exclusive. Fix: add a concrete client contract: server sends ISO 8601, client stores SQLite `YYYY-MM-DD HH:MM:SS` only for local SQL comparisons, sync cursors are server-issued opaque tuple values or normalized consistently before comparison.

9. The branch sequencing recommendation is correct but should be treated as mandatory. The current worktree contains the tables introduced by the not-yet-merged branch (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:20`, `apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:41`), and the spec recommends waiting for live-inventory-counting to merge before branching fresh from dev (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:188`, `docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:189`). If implemented before that merge, the rename migration may target tables that do not exist on dev and will entangle two review scopes. Fix: mark the sequencing as a hard prerequisite, not just "Recommended."

## Minor Findings
1. The UI/i18n migration is acknowledged but easy to under-scope. Current locations page opens the zone panel as a modal (`apps/web/src/features/settings/LocationsPage.tsx:591`, `apps/web/src/features/settings/LocationsPage.tsx:600`), and the panel plus dialogs are keyed under `inventory:zones.*` (`apps/web/src/features/settings/zones/ZonesPanel.tsx:142`, `apps/web/src/features/settings/zones/ZoneFormDialog.tsx:67`, `apps/web/src/features/settings/zones/BulkAssignDialog.tsx:93`). The spec says migrate `zones.*` to `placement.*` with aliases (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:137`). Fix: add this to acceptance tests or lint/search checklist so renamed terminology does not leave stale labels in the counting wizard and settings page.

2. DTO/type regeneration is correctly mentioned but should be made blocking. Current FE imports generated DTO aliases from `packages/shared/types/generated.d.ts` through `features/settings/zones/api.ts` (`apps/web/src/features/settings/zones/api.ts:4`, `apps/web/src/features/settings/zones/api.ts:10`), and the generated types currently expose `ZoneDto`/`ZoneProductAssignmentDto` only (`packages/shared/types/generated.d.ts:857`, `packages/shared/types/generated.d.ts:876`). The spec notes `php artisan typescript:transform` (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:184`, `docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:202`). Fix: make type generation a required verification step before frontend work compiles.

3. CSV import path matching by name is underdefined. The spec allows `placement_path` segments matched by code or name within a location (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:158`) and later only flags same-name ambiguity as a risk (`docs/superpowers/specs/2026-07-07-location-placement-hierarchy-design.md:215`). Current code uniqueness exists for `code`, not `name` (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:37`). Fix: require code-first imports for production bulk loads, or define deterministic dry-run errors for any non-unique name segment before auto-create.

4. Node full sync is probably fine at hundreds of nodes, but the ceiling should be explicit. The handover says nodes are "small: hundreds of rows/tenant" and replace-all is fine (`docs/handoff/HANDOVER-location-hierarchy-mobile.md:23`, `docs/handoff/HANDOVER-location-hierarchy-mobile.md:61`). That is reasonable, but the feature context includes tens/hundreds of locations and arbitrary depth. Fix: document a practical ceiling, e.g. full-sync nodes remain acceptable up to low tens of thousands of nodes per tenant; beyond that reuse the same delta cursor contract as placements.

5. Table naming is consistent with this app's current tables, but the spec should note why. The root topology doc's generic naming rule is for DB ownership/prefix decisions (`../../claude/database-topology.md:21`, `../../claude/database-topology.md:40`), while this app already has unprefixed tenant inventory tables such as `location_zones` and `product_zone_assignments` (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:20`, `apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:41`). Fix: add one sentence that `location_nodes` and `product_placements` intentionally evolve existing tenant inventory tables and preserve local naming continuity.

## What's Solid
- Keeping stock at `(product, location[, variant])` is supported by the current flat schema: zones and assignments have no quantity columns (`apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:20`, `apps/api/database/migrations/tenant/2026_07_06_200002_create_location_zones_tables.php:49`), and current comments explicitly say zones are labels only (`apps/api/app/Modules/Inventory/Domain/LocationZone.php:18`, `apps/api/app/Modules/Inventory/Domain/LocationZone.php:20`).
- Preserving `CountingScopeType::Zone = 'zone'` is the right backward-compat choice because the current enum value exists as `'zone'` (`apps/api/app/Modules/Inventory/Domain/Enums/CountingScopeType.php:14`) and generated frontend scope types include it (`packages/shared/types/generated.d.ts:882`).
- Replacing the settings modal with a first-class placement page is justified by the current nested modal flow (`apps/web/src/features/settings/LocationsPage.tsx:591`, `apps/web/src/features/settings/LocationsPage.tsx:600`) and current zones panel being a flat list (`apps/web/src/features/settings/zones/ZonesPanel.tsx:164`, `apps/web/src/features/settings/zones/ZonesPanel.tsx:222`).
- The explicit same-location invariant is necessary and aligns with current defenses: `CreateCountingRequest` already re-pins zone ids to the selected location (`apps/api/app/Modules/Inventory/Presentation/Requests/CreateCountingRequest.php:141`, `apps/api/app/Modules/Inventory/Presentation/Requests/CreateCountingRequest.php:143`), and `ZoneService::assignProduct()` rejects a zone/location mismatch (`apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:71`, `apps/api/app/Modules/Inventory/Application/Services/ZoneService.php:74`).
- Making node products paginated/searchable is the right scale correction because the current zone-products endpoint is unpaginated and the FE already documents that limitation (`apps/web/src/features/settings/zones/api.ts:52`, `apps/web/src/features/settings/zones/api.ts:58`).
