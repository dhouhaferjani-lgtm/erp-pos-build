# Treasury-reviewer — Scan-to-Document (Spec B §8b/§8c/§6, Plan Task 8) design review

> Reviewer: treasury-reviewer (adversarial, code-grounded). Date: 2026-07-06.
> Scope: scanned-invoice → supplier-invoice commit path ONLY. Design-stage (no impl exists).
> Verdict: **NEEDS-REVISION** (1 BLOCKER, 4 MAJOR, 1 confirming MINOR).
> Evidence base (branch feat/scan-to-document = origin/dev + docs):
> - CreateSupplierInvoiceService.php, SupplierInvoiceController.php,

## BLOCKER-1 — SI committer payload cannot satisfy CreateSupplierInvoiceService::create (missing per-line `vat_rate`; nullable `unit_price`/`currency`/`issue_date`) → 500 on every invoice commit
`CreateSupplierInvoiceService::create` reads several keys by DIRECT array access (no `?? null`):
- per line `$lineInput['quantity']` (CreateSupplierInvoiceService.php:81), `$lineInput['unit_price']` (:83), **`$lineInput['vat_rate']` (:85)** — all mandatory. A missing `vat_rate` becomes `(string) null = ''`, and `bcmul($qty,'',…)`/`bcdiv('','100',6)` (:92/:96/:99) throws `ValueError` in PHP 8 → HTTP 500.
- header `$validated['currency']` (:54), `$validated['partner_id']` (:123), `$validated['issue_date']` (:130) — all direct access / NOT NULL columns.

The plan's reviewed payload (plan Task 7 interfaces, ReviewedLineData at plan lines 300–305) is:
`productId, ?variantId, quantity, ?unitPrice, ?freeQuantity, ?batch, ?sourceLineId` — **there is no tax-rate field at all**, `unitPrice` is nullable, and header `currency`/`documentDate` are nullable (`public ?string $currency; public ?string $documentDate`). Task 8 (plan:335) only mentions building `source_document_ids[]`, per-line `source_line_id`, `pending_receipt` — it never lists `vat_rate`, `currency`, `issue_date`.
The extraction DTO DOES capture `taxRate` (plan Task 2, ExtractedLineData at plan:119), but the reviewed payload drops it, so the committer physically has no VAT rate to forward.
**Fix:** add a REQUIRED `taxRate` to ReviewedLineData→map to `vat_rate`; make `unitPrice` required for invoice kind; make `currency` and `documentDate` required for invoice kind. Add an explicit "build `$validated` with keys {currency, partner_id, issue_date, [due_date], [supplier_reference], source_document_ids[], lines[{quantity, unit_price, vat_rate, source_line_id, [product_id], [variant_id], [is_bonus_line]}]}" checklist in Task 8, and a committer test that asserts a 3-line invoice with vat_rate actually creates (not just "Draft SI"). `price_entry_mode` and payment fields are NOT required by this service (it computes net subtotal = qty×unit_price directly) — do not add them.

## MAJOR-1 — receipt-line consumption is FIFO by PO line; the user's receipt-line mapping is discarded → wrong PPV/accrual basis for the exact multi-BL month-end case this feature targets
Spec §8b/§10 has the user map each invoice line to a specific suggested *uninvoiced receipt line* (possibly across many BLs). But `CreateSupplierInvoiceService::create` accepts only `source_line_id` = the PO line (CreateSupplierInvoiceService.php:112); it never accepts a receipt_line_id. Consumption/basis is computed by `SupplierInvoiceMatchSnapshotService::forSourceLine` → `ReceiptLineConsumptionPlanner::plan`, which orders receipt lines **FIFO by `created_at,id`** (ReceiptLineConsumptionPlanner.php:33-35) and returns `matched_receipt_line_id = $slices[0]` (SupplierInvoiceMatchSnapshotService.php:65) — i.e. the earliest posted receipt line for that PO line, NOT the one the user mapped. Multiple invoice lines on the same PO line just advance the FIFO cursor via `qtyAlreadyPlanned` (CreateSupplierInvoiceService.php:160-166).
Consequence: when a PO line has several receipts at DIFFERENT accrual costs (exactly the consolidated-monthly-invoice-with-PPV scenario in §0/§8b), the `price_match_basis`/PPV computed at post time reflects FIFO-consumed lines, not the user's chosen BL. The review UI's receipt-line mapping is therefore lossy/advisory — only its PO-line is honored. `consumed_receipts` shown back to the user (SupplierInvoiceController.php:523-564) is also derived from `source_line_id`→all receipts, reinforcing that receipt selection is not truly per-line.
**Fix:** either (a) route precise receipt selection through the shipped `POST /supplier-invoices/{id}/link-receipts` surface (SupplierInvoiceController.php:286-314) after create, or (b) explicitly document in §8b that receipt selection is FIFO-within-PO-line and the UI mapping only determines the PO line + total qty. Do not silently imply the mapped BL is the consumed BL.

## MAJOR-2 — pending fork: the acting-user permission `supplier-invoices.create-pending` is enforced ONLY in the controller the committer bypasses; the service checks the company policy only
`CreateSupplierInvoiceService::create` guards pending with the COMPANY toggle only: `allowsInvoiceFirst()` (CreateSupplierInvoiceService.php:65-67). The USER permission `supplier-invoices.create-pending` is asserted exclusively in `SupplierInvoiceController::store` via `assertInvoiceFirstCreatePermission` (SupplierInvoiceController.php:218, 237-255) — **which the committer does not go through**. So a user holding `document-ingestions.commit` but NOT `supplier-invoices.create-pending` can create a pending SI by committing an ingestion.
Plan Task 8's interface bullet (plan:335) mentions only the policy `allowsInvoiceFirst`; unlike the BL committer (Task 7, plan:314 "Committer asserts `goods-receipt.create-standalone`"), it never states the SI committer must re-assert the user permission. Only test (d) (plan:344) implies a 403 — an assertion with no specified enforcement point.
**Fix:** state explicitly in Task 8 that `SupplierInvoiceCommitter` must `Gate::forUser($actor)->authorize('supplier-invoices.create-pending')` on the pending fork before calling the service (mirroring Task 7's BL path), since the commit-endpoint permission is not a substitute.

## MAJOR-3 — duplicate-reference guard is advisory-only (GET endpoint + non-unique index); committer SELECT-then-create races and there is no DB uniqueness
The shipped "duplicate reference" check is a read-only GET (`SupplierInvoiceController::duplicateReference`, SupplierInvoiceController.php:173-203) that the frontend calls for a warning banner. `CreateSupplierInvoiceService::create` performs NO duplicate check. The only DB artifact on `external_document_number` is a plain **index** `(company_id, external_document_number)` (migration 2025_12_11_100001_add_is_historical_to_tables.php:36) — NOT unique.
Plan Task 8 (plan:335) says the committer will "throw 422 DUPLICATE_SUPPLIER_REFERENCE when (partner_id, supplier_reference) already exists" — a committer-level SELECT-then-INSERT with no unique backstop → TOCTOU race: two DISTINCT ingestions of the same invoice (e.g. a photo and a PDF → different `checksum`, so the §4 checksum-unique guard does NOT catch them) both pass the SELECT and both create a Draft SI → duplicate payable. The checksum guard (§4) and the NeedsReview→Committing state transition only prevent re-commit of the SAME bytes / SAME ingestion, not two ingestions sharing a supplier reference.
**Fix:** note this residual explicitly. Recommend a tenant-scoped partial unique index on `(company_id, partner_id, external_document_number)` for SupplierInvoice type (catch the race at the DB), or at minimum document that the committer check is best-effort and the checksum guard covers only identical-file re-uploads.

## MAJOR-4 — calling the service directly bypasses CreateSupplierInvoiceRequest::withValidator cross-field checks
`SupplierInvoiceController::store` relies on `CreateSupplierInvoiceRequest::withValidator` (CreateSupplierInvoiceRequest.php:151-257) for: source docs are POurchaseOrders (:189), not cancelled (:202), PO partner matches request partner (:214), PO currency matches (:224), and each `source_line_id` belongs to a referenced PO's lines (:250). `CreateSupplierInvoiceService::create` re-runs NONE of these; it trusts `$validated`. A committer calling the service directly with a mismatched/garbage `source_line_id` will still create a Draft SI — the matcher then flags it `Exception` (SupplierInvoiceMatcher.php:341-362), but a bad Draft is persisted and shown as committed.
**Fix:** Task 8 must specify the committer re-validates (scoped `findOrFail` + PO-type/partner/currency/source_line-membership) exactly as `withValidator` does — the plan's generic "tenant/company-scope re-validated in the committer" (plan:308, written for Task 7) is not sufficient detail for the SI cross-field invariants.

## MINOR-1 (confirmation) — no GL at create is correct; but balance_due is NOT persisted at create and only defaults to `total` in display
Confirmed: `create` writes only Document+DocumentLines in Draft (CreateSupplierInvoiceService.php:127-128), no JournalEntry. GL (GR-IR clearing) posts ONLY in `SupplierInvoicePostingService::post` (SupplierInvoicePostingService.php:277). `balance_due` is set to `total` ONLY at post (SupplierInvoicePostingService.php:289); at create it stays NULL and the API merely displays `balance_due ?? total` (SupplierInvoiceController.php:464). The `match()` call at create (CreateSupplierInvoiceService.php:219) is read-only (no quantity_invoiced writes). So the design's "SI left Draft, no GL, no stock movement at create" is verified.
**Note for the design:** a committed-but-unposted (Draft) SI has `balance_due = NULL` in the DB — payables/aged-payables queries that filter on persisted `balance_due` will not see it until it is POSTed from the SI surface. §8b already keeps posting manual, so this is acceptable; just document that scanned invoices land as Draft payables invisible to `PaymentController` (which reads `balance_due`) until posted.

## Verdict
**spec ❌ + quality NEEDS-REVISION.** The SI commit path as specced cannot execute (BLOCKER-1) and has four correctness/authz/idempotency gaps. Resolve BLOCKER-1 and MAJOR-2/3 before implementing Task 8; document MAJOR-1/MAJOR-4/MINOR-1 in §8b.
