## Findings

### 1. [HIGH] Plan Task 3/4 — sub-scale-currency input produces an unbalanced 3-line entry → posting 500s
`ExpenseRequest.php:71` (and the plan's Task 2 `vat_amount` rule) use the FIXED 3dp money regex regardless of company currency — a EUR (2dp) company can legally submit `total: "119.005"`. Task 3's pseudocode keeps `$total` **unnormalized** (`$total = (string)($data['total'] ?? '0.00')`, persisted raw into `documents.total` decimal(15,3)) while `vat_amount` is `bcformatStrict`'d to scale 2 and `subtotal` is derived at scale 2. Task 4 then debits `subtotal + nonDeductible` (2dp) + `deductible` (2dp) against `Cr total` = `119.005` (3dp, off the currency grid). `sealAndPersistEntry` balances at `max(3, scale) = 3` (`GeneralLedgerService.php:2925-2949`): `119.000 ≠ 119.005` → `InvalidArgumentException` → 500 at post, expense stuck Posted-status-flipped-then-rolled-back. Today this input is harmless (both lines = total); the split makes it a hard failure. — **Why it matters:** France/EUR is a core vertical; this is a user-reachable 500 on the money path introduced by W1. — **Fix:** in `assertVatInvariants` (or just before derivation) when `vat_amount` is present, either (a) normalize AND persist `total` via `bcformatStrict($total, $scale)` so all three stored figures share the grid, or (b) throw `DomainException` when `bccomp($total, bcformatStrict($total, $scale), $scale + 1) !== 0`. Pin a EUR + 3dp-total test either way.

### 2. [MEDIUM] Plan Task 1 — the `document_tax_details` widening premise is stale: columns are ALREADY `decimal(15,3)` on dev
`database/migrations/tenant/2026_03_23_100000_widen_missed_monetary_columns_to_scale_3.php:22-25` already widened `tax_base`/`tax_amount` to (15,3) — the plan's (and spec §5.3's) "live (15,2) cast/column mismatch" claim is false on `6e95f309e`; the drift was fixed in March. Consequences: (a) the proposed second migration is a redundant no-op; (b) its `down()` narrowing to (15,2) fights the 2026-03-23 migration's guarantee — a rollback of only the new migration would truncate 3dp data that migration owns; (c) Task 1 Step 2's "expect FAIL (`1.901` truncated to `1.90`)" is impossible **twice over** — PG columns are already 3dp, and the test suite runs on SQLite `:memory:` (`phpunit.xml:41-42`) where decimal scale is unenforced and the widening migrations explicitly no-op (`2026_03_23...php:55-57`). The executor's red step will go green immediately and the TDD gate will read as a broken environment. — **Fix:** delete the second migration + its red expectation from Task 1; keep only the `expense_metadata` VAT-columns migration. Optionally keep a plain (always-green, documented as such) schema-assertion test.

### 3. [MEDIUM] Plan Task 3 pseudocode — `bccomp($vat, $effective['total'], 4)` is a hardcoded literal scale that fails the plan's own CI constraint
`ForbidHardcodedBcmathScale` covers `bccomp` (`app/PHPStan/Rules/ForbidHardcodedBcmathScale.php:42-48`) and fires in `app/Modules/*/Application/Services/` (`:113-121`) — exactly where `assertVatInvariants` lives. The plan's Global Constraints promise PHPStan-clean money code, then the Task 3 snippet violates the rule. — **Fix:** pass the resolved `$scale` (or `$scale + 1`) into `assertVatInvariants` and use it in the `bccomp`; do not paper over with a `precision-ok` comment (the scale genuinely is currency-dependent here).

### 4. [MEDIUM] Plan Tasks 1/3 file lists omit the `ExpenseMetadata` model change — mass assignment silently drops the new VAT fields
`ExpenseMetadata::$fillable` (`app/Modules/Expense/Domain/ExpenseMetadata.php:50-62`) has no `vat_rate`/`vat_deductible_percent`, and `casts()` (`:75-83`) has no entries for them. Task 3's `ExpenseMetadata::create([... 'vat_rate' => ..., 'vat_deductible_percent' => ...])` would silently discard both (Laravel drops non-fillable keys), producing a confusing Task 3 Step 4 failure far from the cause — and if the executor "fixes" it by only asserting the document columns, the GL posting reads `$metadata->vat_deductible_percent ?? '100.00'` and silently treats every partial-deductibility expense as 100% deductible (wrong 4456 amount, wrong declared VAT). — **Fix:** add `apps/api/app/Modules/Expense/Domain/ExpenseMetadata.php` to Task 1 (or 3) Files: fillable + casts (`'vat_rate' => 'decimal:2'`, `'vat_deductible_percent' => 'decimal:2'`), and pin one test asserting the 80% split reads a NON-default percent through the model.

### 5. [MEDIUM] Cross-wave contract baked in W1: `ExpenseService::create()` resolves currency from `CompanyContext` — console callers (Task 10) will throw
`ExpenseService.php:72` — `$companyCurrency = $this->companyContext->requireCompany()->currency` — runs unconditionally in `create()`, and Task 3 keeps this shape (`getScale((string) $companyCurrency)`). Task 10's command claims rule-20 compliance by passing explicit `company_id`, but `create()` itself will `requireCompany()` in a context-less console run. W1 owns this file; if W1 ships the plan's shape unmodified, W2 either breaks or must bind CompanyContext per company in the loop (which the plan never states). Not a W1 runtime defect, but a W1 design decision the plan silently defers. — **Fix (in W1 Task 3):** decide the shape now — accept an optional explicit currency/company in `create()` (resolve `Company::whereKey($data['company_id'])->currency` when context is absent), or add an explicit note to Task 10 that the command must set CompanyContext per company. Flagging for the Opus W2 lane as well. *(The Opus lane independently rated this BLOCKER — see companion review Finding 1.)*

### 6. [LOW] New cross-module edges (rule 6): Accounting → Expense and Expense → Taxation
Task 4 has `GeneralLedgerService` (Accounting) importing `App\Modules\Expense\Domain\Services\ExpenseVatSplit`, and `ExpenseService` (Expense) mass-creating `App\Modules\Taxation\Domain\Entities\DocumentTaxDetail` (a Taxation-module Eloquent model, `app/Modules/Taxation/Domain/Entities/DocumentTaxDetail.php`). Both are new deptrac edges on a codebase mid-SoC-remediation. — **Fix:** put `ExpenseVatSplit` in `App\Shared\Domain` next to `CurrencyScale` (it is a pure bcmath function, not Expense domain logic — this also removes the Accounting→Expense edge entirely); the DocumentTaxDetail write is tolerable as-is (Document module precedent) but worth a one-line note in the task.

### 7. [LOW] Zero-VAT edge unpinned: `vat_amount: "0"` passes validation but breaks the "byte-identical" promise
`min:0` + the regex admit `"0"`/`"0.000"`; the plan's derivation then stores `tax_amount = "0.000"` (non-null) and defaults `vat_deductible_percent = '100.00'` — posting stays 2-line (the `bccomp(..., '0') === 1` gate) and no tax detail is written, but the stored row is no longer byte-identical to a VAT-less expense, and Task 3's backward-compat test (`tax_amount` null) won't cover it. — **Fix:** normalize `vat_amount` of zero to `null` in the service (one `bccomp`) and pin a test, or explicitly pin the "zero stored as 0.000, still 2-line JE" behavior.

### 8. [LOW] Missing high-value money-path tests in Tasks 3/4
(a) `update()` **clearing** VAT (explicit `vat_amount: null` on a draft that had it) → `subtotal` must be re-derived to `total`, `tax_amount` null — and decide whether `vat_rate`/`vat_deductible_percent` are cleared (the plan's merge shape would leave the percent stamped); (b) `update()` changing only `vat_amount` → subtotal re-derived from merged total; (c) the equality edge `vat_amount == total` → 422 (the invariant uses `>= 0` on `bccomp`, so equality throws — pin it, it's one keystroke from a `>` regression that would allow zero-net expenses); (d) per Finding 1, EUR + regex-legal 3dp total. The pinned list is otherwise strong (unpaid/paid, 80%, millime, 0%, VAT-less regression, tax-detail row, EUR variant, supplier balance round-trip, reconcile).
