## 2. Goals

1. Cash-only sale payable Swedish-rounded to the country denomination **inside the signed SALE_RECEIPT bytes**, with the applied denomination itself signed — every receipt verifiable against its authoring policy, offline, forever. Card/mixed exact.
2. In-tolerance cash shortfalls auto-accept without PIN; rounding deltas and tolerance write-offs post to `6580`/`7580` on the live pipeline, v3-gated so brownfield data and replays can never poison the queue.
3. Config syncs to the device, works fully offline, fails **closed** everywhere; greenfield provisioning is self-healing.
4. Aggregates stay explained: receipt-level rounding is signed; Z-level rounding/tolerance lines reconcile `gross = net + vat + rounding` as **derived observability** (per-receipt signatures are the fiscal authority; the Z carries real tolerance values in its existing signed key and an unsigned additive rounding summary — no schema_version bump, no new signed Z key in v1). Drawer == Σ rounded totals − change; revenue/loyalty on exact value.
5. v1/v2 events parse, repair, and replay byte-identically forever; deploy is server-first, two-phase, auto-deploy-safe on Postgres (PG-run tests for every constraint-class change).

**Non-goals (v1):** per-company rounding UI; canonical REFUND/VOID authoring; new SIGNED Z/X payload keys (Z_REPORT v2 — 🎫, unlocks signed Z-level rounding later); wholesale training-GL fix (🎫; new entries guarded); `'CASH'` string-match normalization beyond the invariant below (🎫); policy-revision pinning (🎫); historical GL correction (forward-only + quantification report); custom cash methods beyond code `CASH` (🎫); `ACCOUNT_CHARGE`; X_REPORT changes (same retired-server-path + no-cash-line rationale as Z, stated not inferred); void GL reversal (pre-existing gap, 🎫).

## 3. Approach

Fold rounding into `total` + two signed sibling fields + extended identity; policy-verifiable via signed denomination + static caps + projection reconciliation; v3-gate as the single cutover discriminator for BOTH the projection's new derivations AND the bridge (r2 F-2/F-8 — one rule, both layers); Z surfaces handled without a Z payload version (r2 F1/F-6). Alternatives (sibling-only, synthetic payment line, Z_REPORT v2 now) rejected — history in the review file.

## 4. Design

### 4.1 Semantics

`exact_total` = cart gross after discount; `D` = denomination normalized to currency scale `s` (§4.2); all comparisons bcmath/big.js decimal strings.

- **Cash-ness (ONE predicate, all layers):** `payment_methods.is_cash_tender = true`, with the **invariant `is_cash_tender = true ⇒ UPPER(code) = 'CASH'`** enforced by validation (server store/update + backfill) and documented — this makes the flag provably coincide with the existing literal `'CASH'` matches on the device Z (`zReportService.ts:778`) and server expected-cash (`ReportGenerationService.php:513`), so no drawer/Z divergence is possible (r2 T-F5). Custom cash methods 🎫. The device evaluates cash-only over the **union** of `paymentLines` and `voucherTenders`; voucher legs are payment legs (derivation `SaleReceiptPayload.ts:120`) and never cash. Quick-cash **method selection** (`paymentStore.ts:855-858,1231`) migrates to `is_cash_tender && is_active` with an explicit no-cash-method-configured error (r2 F10).
- **Rounding applies iff:** policy `cash_rounding.enabled` AND `D` valid (normalized, `> 0`, representable at `s` — §4.2) AND every leg cash AND `invoice_type_code ∈ {SALE, TRAINING}`.
- `rounded_total = round_half_up(exact_total / D) × D`; `cash_rounding_adjustment = rounded_total − exact_total` (signed, `|adj| ≤ D/2`, tie up).
- **Payload (v3):** `total = rounded_total`; new REQUIRED fields `cash_rounding_adjustment` (signed) + `cash_rounding_denomination` (non-negative, normalized at `s`; `bcformatStrict('0', s)`-equivalent when rounding did not apply, in which case adjustment is canonical zero and `total = exact_total`).
- **Identity + binds (v3; evaluation ORDER is normative, r2 F5):**
  1. `subtotal + vat_total == (total − adj) + discount` exact (absent fields ⇒ zero ⇒ v1/v2 unchanged).
  2. If `adj ≠ 0`: FIRST assert `bccomp(denomination, '0', s) > 0` (throw `RuntimeException` — never reach bcmod with a zero divisor; `DivisionByZeroError` is an `Error` the quarantine path does not catch); THEN `|adj| ≤ denomination/2` with the half computed at `s+1` (`bcdiv(D,'2',s+1)`, compare at `s+1` — truncation-safe, r2 F6); THEN `bcmod(total, denomination, s) == 0` (both operands already normalized at `s`).
  3. Static history-stable caps on `denomination`: `≤ 1.000` (s=3), `≤ 1.00` (s=2), `≤ 10` (s=0 — JPY 10-yen rounding is real, r2 F6).
  Suppression payloads (`total=5.000, adj=-95.000`) fail (2)+(3) ⇒ quarantine; explicit rejection tests incl. `adj ≠ 0 ∧ denom = 0 ⇒ quarantine (not worker death)`.
- **Refund sign convention (stated now for the immutable future, r2 F14):** on a canonical REFUND/VOID v3 payload, `cash_rounding_adjustment = rounded_refund_total − exact_refund_total` of the refund's own non-negative magnitudes — same orientation as a sale, never re-negated.
- **Change eligibility:** checkout refuses completion when `change > Σ cash-leg amounts` (card-only over-tender rejected pre-sign; dedicated error key).
- **Tolerance:** `shortfall = total − Σ payments` when positive; auto-accept without PIN iff policy enabled AND all-cash AND `shortfall ≤ effective_max = min(pct × total, max_amount)` — §8.1 floor option: `max(min(pct × total, max_amount), D)` when rounding active AND `exact_total > 0`, **with a per-shift auto-accept guard** (device-side counter; beyond N auto-accepts per shift — default 10 — escalate to the PIN path; count surfaced on EOD — r2 F-14). Beyond ⇒ existing PIN path unchanged. Over-tender is change; 758 only from round-up.

### 4.7 Refunds (v1 stance, r2 F-8 honest costing)

Refunding a rounded cash sale via the live `ReceiptReturnService` pays out exact untenderable millimes — real day-1 gap. The Rev 2 "round the payout at the screen" remedy is **not implementable as a sentence**: refund totals are server-computed from lines and CHECK-bound; both cash and prorated non-cash payout paths must be threaded; the service's no-arg `getScale()` is a rule-19 trap; and per-partial-return rounding drifts unboundedly in N. **§8.2 therefore offers two honest options:** (a) fund a properly-designed follow-up (server-side payout rounding + delta booking + partial-return cap) sized as its own small track before/at launch; (b) launch with the gap documented (cashiers hand-round; drawer variance absorbs ≤ D/2 per refund; visible in counts). The v3 validator + bridge reversal remain refund-ready either way.
