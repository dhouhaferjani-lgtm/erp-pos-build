# POS Cash Rounding + Tender Tolerance — Design Spec (Rev 1)

**Date:** 2026-07-27
**Status:** DRAFT — pending adversarial review + owner approval
**Owner decisions (LOCKED 2026-07-27, do not re-litigate):** (1) BOTH mechanisms — cash rounding (Swedish-round the cash-due total to the nearest practical coin at checkout; card/mixed stay exact; adjustment prints on the receipt) AND tolerance write-off (residual differences within the configured tolerance accepted and booked automatically to seeded 658/758). (2) Rounding denomination is a country-seeded default (0.050 TND for Tunisia) extending `country_payment_settings`; no per-company setup UI in v1.
**Branch:** `feat/pos-cash-rounding`, worktree `../erp.cash-rounding`, base `1201ba37d` (origin/dev tip, post-treasury-⑤). All file:line facts below verified against that commit on 2026-07-27 by a 4-agent research pass.

## 1. Problem

Tunisia has no circulating coin below 50 millimes in practice, so a cash total of 9.997 TND is physically untenderable. Today the POS hard-requires full tender to the millime: quick cash throws on any shortfall (`apps/pos/src/stores/paymentStore.ts:874-879`), advanced checkout's only under-tender path is a manager-PIN `tender_tolerance_override` (`paymentStore.ts:1124-1191`). Server tolerance config exists (`country_payment_settings`, TN 0.5% / 0.100 TND) but **no endpoint the POS calls ever serves it** — the device has no rounding or tolerance knowledge at all. This is the last confirmed functional blocker before the first parapharmacy client onboards.

### Verified current state (the spec builds on these facts)

- **Fiscal payload:** SALE_RECEIPT is authored at `event_version=2`; the whole payload nests inside the signed canonical bytes (`apps/pos/src/lib/fiscal/FiscalEventEngine.ts:608-629`, RFC-8785 JCS encoder). Aggregate identity enforced EXACTLY on both sides — `subtotal + vat_total == total + transaction_discount_amount`, `Σ vat_breakdown.{net,vat} == subtotal/vat_total` (`apps/api/.../FiscalPayloadConstraintValidator.php:851-921`; device mirror `apps/pos/src/lib/fiscal/payloads/SaleReceiptPayload.ts:185-230`). Violation ⇒ quarantine. Top-level money fields use a strictly NON-NEGATIVE regex (`FiscalPayloadConstraintValidator.php:2612-2619`). The top-level key set (`PAYLOAD_KEYS['SALE_RECEIPT']`, :225-255) rejects unknown keys and is NOT yet version-branched (only line-item keys are, :1715-1739). Versioning precedent = v1→v2 (`FiscalEventPayloadRegistry.php:53-107`; `LineItemDTO::fromArray()` `array_key_exists` back-compat).
- **No `Σ payments == total` invariant exists** at any layer (validator `validatePayment()` :1845-1885; device builder). `payments[].amount` is contractually the **TENDERED** amount (comment + Bug-2 fix at `paymentStore.ts:920-946`, citing `CashCountToleranceVarianceRegressionTest.php:30-40`), so `Σ payments − total` = change (over) / −shortfall (under).
- **Tolerance half already partially shipped:** manager-PIN override authors `OPERATOR_APPROVAL_GRANTED` + `OVERRIDE_TENDER_TOLERANCE` fiscal events with evidence threaded into `SALE_RECEIPT.approval_references[]` (`posOverrideAuthoring.ts:70-158`, `receiptService.ts:156-187,295`). `pos_receipts.tolerance_writeoff` + `pos_shifts.tolerance_writeoff_total/count` columns exist (migrations 2026_04_25_*), Z-report v2 `tolerance_summary` and a drill-down UI exist (`zReportService.ts:323-338`; `ToleranceDrillDown.tsx`; endpoint `GET /pos/shifts/{id}/tolerance-receipts` **not yet routed** per `toleranceApi.ts:4-17`).
- **BUT all tolerance GL/write-off lives only on the legacy no-new-writers path** (`ReceiptPaymentService.php:183-211,399-406`; carve-out documented at `TreasuryReceiptBridge.php:114-127`). The live device-authored pipeline — `PosCoreReceiptProjection` (priority 50, read model, NO GL) + `TreasuryReceiptBridge` (priority 150, Treasury-gated, GL) — has **zero tolerance or rounding logic**.
- **GL bridge posts per-leg `Dr Cash / Cr ProductRevenue` at the leg amount** (`TreasuryReceiptBridge.php:392-733` → `GeneralLedgerService::createPOSPaymentEntry()` :3313-3376), runs on a Horizon worker with no CompanyContext and already threads `$receipt->currency` explicitly (rule 19).
- **Discovered adjacent defect (pre-existing, latent):** because leg amounts are TENDERED, a canonical-path cash sale with change over-credits ProductRevenue and overstates the drawer movement by the change amount; and `pos_receipts.change_due` is written only by the legacy service (grep: no projection writes it), so `ReportGenerationService`'s expected-cash logic (`:478,514-535`, subtract-change-due) COALESCEs to 0 for canonical receipts. Bridge tests only cover exact-tender sums (`TreasuryReceiptBridgeTest.php:339-345,428`). See §4.6 prerequisite.
- **Config plumbing:** `country_payment_settings` (tenant migration `2025_12_10_100000_...`, TN seeded 0.5%/0.100 in `up()`) has NO rounding column. `PaymentToleranceService::getToleranceSettings()` implements Company → Country → system-default (`:41-66`). Purpose→account = `Account::findByPurposeOrFail` (`Account.php:238-266`); `PaymentToleranceExpense`/`PaymentToleranceIncome` map to seeded `6580`/`7580` in TN/FR/Generic charts (`TunisiaChartOfAccountsSeeder.php:254-255,278-279` etc.).
- **Device config sync:** no bootstrap endpoint; per-domain pulls in `runFullSync` (`syncService.ts:1977-2070`, 60s–5min cadence) + eager refreshes at terminal activation (`terminalStore.ts:470-524`). Template for "always-resolvable cached config" = `FraudSettingsPosController` (`POS/routes.php:188`; resolver always returns a DTO with defaults). SQLite migrations at **v62** (`migrations.ts:1913`); column adds use `isDuplicateColumnError` guard; timestamps `DEFAULT (datetime('now'))` + `toSqliteUtc()` (rule 20). Mid-sale reads are synchronous from Zustand hydrated from SQLite (`paymentStore.ts:792-838`, `PaymentSummary.tsx:54-56`); currency scale via `getActiveCurrencyDecimals()` (`currency.ts:10-42`, TND=3 device-side table).
- **Cash-ness detection:** no enum; checkout convention is `is_physical && !has_maturity` (`paymentStore.ts:856-858,1231`); two legacy string matches on `'CASH'` exist elsewhere (`CashReconciliationSection.tsx:111`, `zReportService.ts:778`).
- **Refunds:** device builder only ever emits `invoice_type_code: 'SALE'|'TRAINING'` (`SaleReceiptPayload.ts:159`); canonical REFUND/VOID is validator/projector-ready but has no authoring UI; legacy `ReceiptReturnService` (server-authored, outside hash chain) is the live refund path.
- **Precision contract:** B2C POS `unit_price` is TTC; fiscal integrity is enforced at the aggregate identity, never per-line (`docs/architecture/precision-contract.md:96-109`). All money = bcmath/big.js decimal strings; device uses big.js `Big.RM = 1` half-up (`apps/pos/src/lib/decimal.ts:42-44`).

## 2. Goals

1. A cash-only sale's payable total is Swedish-rounded to the country-seeded denomination **inside the signed SALE_RECEIPT bytes**, printed on the receipt; card/mixed sales stay exact to the millime.
2. Residual cash shortfalls within the configured tolerance are accepted at checkout **without a manager PIN** and booked automatically; rounding deltas and tolerance write-offs post to `6580` (charge) / `7580` (gain) on the live fiscal-event pipeline.
3. Rounding + tolerance config syncs to the device and works fully offline; absent config fails closed to today's exact behavior.
4. Z-reports, drawer expectations, and GL reconcile exactly: drawer cash == Σ rounded totals − change; revenue == exact pre-round totals; every derivation is bcmath at currency scale.
5. The whole feature is compatible with v1/v2 events forever and deployable server-first with self-guarding migrations (push-to-dev auto-deploys `tenants:migrate`).

**Non-goals (v1):** per-company rounding UI; rounding on the legacy server-authored refund path (`ReceiptReturnService` recomputes exact totals from lines and is outside the hash chain — refunds of rounded sales refund the exact line value; 🎫 follow-up ticket, see §4.7); Z_REPORT payload schema changes (gross already reconciles, §4.5); B2B/AR tolerance behavior changes; normalizing the two legacy `'CASH'` string matches (🎫 ticket); denominations other than one per country; multi-currency tender.

## 3. Approaches considered

- **A (chosen): fold rounding into `total` + signed sibling field, event_version 3.** `total` becomes the rounded payable; a signed `cash_rounding_adjustment` field carries the delta; the aggregate identity is extended to bind it exactly. Z-report `gross_sales` (a plain Σ `receipt.total` on both device `zReportService.ts:742` and server `ReportGenerationService.php:953-955`) then reconciles with the drawer with **zero aggregation changes**; the identity keeps the delta tamper-evident inside the signed bytes.
- **B (rejected): sibling field NOT folded into `total`.** Every consumer of `total` (Z-report, drawer expectation, change math, GL) would need to learn `total + adjustment`; missing one silently un-reconciles the drawer. Strictly worse.
- **C (rejected): rounding as a synthetic payments[] line (e.g. `method_code: 'ROUNDING'`).** Abuses the tender contract; `TreasuryReceiptBridge` would fail-closed on method resolution (`payment_method_not_found`) or need a fake method row; pollutes drawer/variance reporting.

For tolerance, the shortfall stays **derivable** (`total − Σ payments`) rather than getting a new payload field: no new invariant to version, and the device-side enforcement plus server-side config check bound it. Manager-PIN override (beyond tolerance) keeps its existing evidence trail unchanged.

## 4. Design

### 4.1 Semantics (single source of truth)

Let `exact_total` = cart gross after discount (today's `total`), `D` = resolved denomination, scale `s` = currency scale (TND 3).

- **Rounding applies iff:** config `cash_rounding.enabled` AND every tender leg's resolved method is cash (`is_physical && !has_maturity` — the existing checkout convention) AND `invoice_type_code ∈ {SALE, TRAINING}` (training mirrors sale behavior for realistic drills).
- `rounded_total = round_half_up(exact_total / D) × D` (big.js: `Big(exact).div(D).round(0, Big.roundHalfUp).times(D).toFixed(s)`; server verification via bcmath at scale `s+1` intermediates). `cash_rounding_adjustment = rounded_total − exact_total`, **signed**, `|adj| ≤ D/2`. Non-cash / disabled / no-config ⇒ adjustment `= 0` at scale (and `total = exact_total`).
- **Payload:** `total` = `rounded_total` (the payable). `subtotal`, `vat_total`, `vat_breakdown`, line items, `transaction_discount_amount` are all UNTOUCHED — rounding is VAT-neutral by design (standard treatment; aggregate-level per the precision contract, never smuggled into lines).
- **New aggregate identity (v3):** `subtotal + vat_total == (total − cash_rounding_adjustment) + transaction_discount_amount`, exact `bccomp == 0` at `currency_scale`. For v1/v2 (field absent ⇒ treated as zero) this degenerates to the existing identity — one code path, version-safe.
- **Change:** `change = Σ payments − total` when positive (unchanged formula; `total` is now the rounded payable).
- **Tolerance (cash under-tender):** `shortfall = total − Σ payments` when positive. Device auto-accepts without PIN iff `tolerance.enabled` AND `shortfall ≤ min(percentage × total, max_amount)` (mirrors `PaymentToleranceService::check` non-strict semantics). Beyond tolerance ⇒ existing manager-PIN `tender_tolerance_override` path, byte-for-byte unchanged. Over-tender is change, never a 758 gain; 758 arises only from round-up.

### 4.2 Config: columns, resolver, POS endpoint (server)

- **Tenant migration** (self-guarding, auto-deploy safe): add to `country_payment_settings` — `cash_rounding_enabled` boolean default `false`, `cash_rounding_denomination` decimal(15,4) nullable; then idempotent backfill `UPDATE ... SET cash_rounding_enabled = true, cash_rounding_denomination = 0.0500 WHERE country_code = 'TN' AND cash_rounding_denomination IS NULL`. FR (and Generic-country tenants) stay disabled. Model `$fillable`/`$casts` updated (`CountryPaymentSettings.php:18-38`).
- **`PosPaymentPolicyResolver`** (new, `POS/Application/Services/`, constructor-injected): composes `PaymentToleranceService::getToleranceSettings($companyId)` + a rounding lookup over the same Company→Country chain (company override column deferred to v2 — v1 reads country row only, system default = disabled). **Always returns a complete DTO** (fraud-settings pattern) — `{country_code, currency_code, cash_rounding: {enabled, denomination}, tender_tolerance: {enabled, percentage, max_amount}}`; disabled defaults when rows are missing.
- **`GET /api/v1/pos/payment-policy`** — new `PosPaymentPolicyController` in the POS module, same route middleware + terminal-auth stance as `GET /pos/fraud-settings` (`POS/routes.php:188`). PHP DTO with `php artisan typescript:transform` for the shared type (rule 7). No new permissions.

### 4.3 Device: sync, cache, checkout, receipt (apps/pos)

- **SQLite v63** (stacks on owed v60–v62): `payment_policy_cache` table — `company_id TEXT PRIMARY KEY`, discrete typed columns (`cash_rounding_enabled INTEGER`, `cash_rounding_denomination TEXT`, `tolerance_enabled INTEGER`, `tolerance_percentage TEXT`, `tolerance_max_amount TEXT`, `country_code TEXT`, `refreshed_at TEXT NOT NULL DEFAULT (datetime('now'))`). Any JS-side timestamp comparison routes through `toSqliteUtc()`.
- **Sync:** `pullPaymentPolicy(db)` added to `runFullSync` (alongside `pullPaymentConfig`, `syncService.ts:2026`) + eager refresh at terminal activation (next to `refreshFraudSettingsCache`, `terminalStore.ts:524`). Hydrates a `paymentPolicy` slice (in `paymentStore` beside `fetchPaymentConfig`/`refreshFromSQLite`, `paymentStore.ts:792-838,1414-1422`): SQLite → store synchronously first, then live API re-set in background.
- **Synchronous read:** `getActivePaymentPolicy()` accessor (non-hook, `useAuthStore.getState()`-style like `currency.ts:20-32`). **Missing/never-synced ⇒ `{cash_rounding: disabled, tolerance: disabled}`** — the POS behaves exactly as today (fail-closed to full-tender-exact; fraud-settings degrade posture, NOT the payment-config blocking posture — blocking cash checkout on a fresh offline device over an optional convenience feature would be launch-hostile).
- **One pure helper module** `apps/pos/src/lib/payment/cashRounding.ts`: `roundCashTotal(exact, denom, scale)`, `computeRoundingAdjustment(...)`, `isCashOnlyTender(legs, methods)` (per-leg `is_physical && !has_maturity`). Both display paths and the authoritative payload assembly call this one implementation.
- **Checkout integration (three call sites, mirroring the enforcement map):**
  - `CashPaymentScreen` / `computeCashTenderState` (`CashPaymentScreen.tsx:16-30`): amount due displays `rounded_total`; change vs `rounded_total`; a rounding line renders when adjustment ≠ 0. Quick-tender denominations unchanged.
  - `paymentStore.processCashCheckout` (`:874-879`): enforcement becomes `tendered ≥ rounded_total` OR `shortfall ≤ tolerance` (auto-accept, no PIN). Beyond tolerance: existing error (unchanged copy pointing at advanced checkout).
  - `processAdvancedCheckout` (`:1120-1191`) + `AdvancedPaymentsModal.computeTenderState` (`:128-151`) and gates (`:269-273,423-427`): effective due = `rounded_total` while ALL current lines are cash, `exact_total` otherwise (adding a card line reverts to exact live in the UI); within-tolerance shortfall completes without PIN; beyond-tolerance keeps the PIN flow exactly as-is (evidence, events, `approval_references` untouched).
- **Authoritative application** is in `receiptService.ts` payload assembly (`:283-336`): recompute rounding there from the same helper + policy snapshot at the moment of signing (`total` = rounded, `cash_rounding_adjustment` emitted; `changeDue` derived vs rounded total at `:335-336`). The updated device-side `assertSaleReceiptAggregates` then proves store-vs-service consistency before the event is sealed — a mismatch throws before signing, never after.
- **Receipt print:** `ReceiptData` gains `cash_rounding_adjustment`; `buildReceiptData.ts` maps it; templates print the existing-but-unwired `rounding` label (`locales/*/pos.json:834`, `printing.ts:80`) with the signed value when non-zero. Server `FullReceiptResponse` mirrors the column (§4.5).
- **i18n:** new keys (rounding line copy, tolerance-accepted notice) in `en`+`fr` `pos.json` (ar = existing debt, noted not expanded).

### 4.4 Fiscal payload v3 (both sides, mirrored)

- **Registry:** `FiscalEventPayloadRegistry` SALE_RECEIPT authored version 2→3; `SUPPORTED_VERSIONS['SALE_RECEIPT'] = [1, 2, 3]` (`FiscalEventPayloadRegistry.php:53-107`). Events are immutable forever — v1/v2 parse untouched.
- **Key sets:** branch the TOP-LEVEL `PAYLOAD_KEYS['SALE_RECEIPT']` by `$eventVersion` (new mechanism, modeled exactly on the existing line-item v1/v2 branching at `FiscalPayloadConstraintValidator.php:1715-1739`): v3 = v2 keys + `cash_rounding_adjustment` (REQUIRED in v3 — the device always emits it, `"0.000"` when no rounding; required-always beats optional for canonical-bytes determinism). v1/v2 payloads containing the key keep failing `payload_extra_field`. Device mirror: `SALE_RECEIPT` key set + `SaleReceiptPayloadInput` type (`FiscalEventEngine.ts:391-434`), pinned by the existing FiscalPayloadKeyDrift vitest gate.
- **Field validation:** new **signed** money regex `^-?(0|[1-9]\d*)\.\d{s}$` for this field only (documented in the precision contract's negative-allowed exception list, `precision-contract.md:34`). Zero MUST be emitted as canonical `"0.000"` — `"-0.000"` is rejected (regex-side `-0` with all-zero fraction check) so canonical bytes stay deterministic. No static magnitude bound is added — the aggregate identity already binds the value exactly.
- **Aggregate identity:** `validateSaleReceiptAggregateConsistency` (`:851-921`) + device `assertSaleReceiptAggregates` (`SaleReceiptPayload.ts:185-230`) both implement §4.1's identity with absent-field ⇒ zero. Quarantine semantics unchanged.
- **DTO:** `SaleReceiptPayload.php` gains nullable `cashRoundingAdjustment` read via `array_key_exists` (the `LineItemDTO::variant_id` precedent, `LineItemDTO.php:71-79`); `CanonicalPayloadReader` accessor; null ⇒ zero at consumers. Device `buildSaleReceiptPayload` (`SaleReceiptPayload.ts:106-179`) emits it from input; V2→V3 builder delegation preserved.

### 4.5 Server read model (PosCoreReceiptProjection — no GL here)

- **Tenant migration** (additive, nullable, auto-deploy safe): `pos_receipts.cash_rounding_adjustment` decimal(15,3) nullable; `pos_shifts.cash_rounding_total` decimal(15,3) default 0 + `cash_rounding_count` int default 0 (symmetry with the tolerance aggregates).
- Projection writes per receipt (all bcmath at `currency_scale` from the payload — rule 19, no CompanyContext): `cash_rounding_adjustment` (null for v1/v2); **`change_due` = max(0, Σ payments − total)** — closes the canonical-path gap so `ReportGenerationService`'s subtract-change-due expected-cash works (`:478,514-535`); **`tolerance_writeoff` = max(0, total − Σ payments)** when positive (existing column, currently legacy-only). Shift aggregates updated under the existing `lockForUpdate` pattern (`Shift::applyToleranceWriteoff`, `Shift.php:159-168`; new sibling `applyCashRounding`).
- Z-report needs **no** schema/aggregation change: device and server `gross_sales` are Σ `receipt.total`, which now already contains the rounding; per-shift rounding visibility comes from the new `pos_shifts` aggregates; tolerance keeps flowing through the existing `tolerance_summary` machinery.
- **Small in-scope closure:** route the already-built drill-down — `GET /pos/shifts/{shiftId}/tolerance-receipts` backed by `PaymentToleranceQueryService::receiptsWithToleranceForShift` (`PaymentToleranceQueryService.php:43-159`), unlocking the shipped `ToleranceDrillDown.tsx` (`toleranceApi.ts:4-17`). Optional-cut if review deems it creep.

### 4.6 GL (TreasuryReceiptBridge — Horizon worker, Treasury-gated)

**Prerequisite fix (discovered defect, must land first — flagged for owner confirmation):** net change out of cash legs before Payment/GL/movement creation in `projectPaymentLineFromCanonical` (`TreasuryReceiptBridge.php:392-733`). `change = max(0, Σ legs − total)` is subtracted from the last cash leg (cascading backwards if it exceeds one leg; change is only ever returned from cash). Effective leg sums then equal `total − shortfall`. Without this, the new rounding/tolerance entries would sit on a revenue baseline that's wrong by the change amount on most real cash sales. Zero effect on exact-tender sales (all existing tests unchanged); regression-pinned with an over-tender test.

**New entries** (both: created + `postEntryNow($entry, $receipt->cashier, $receipt->currency)` inside the existing per-event `DB::transaction`, explicit currency per rule 19; idempotent via source-type-scoped existence check + NEW partial unique indexes on `journal_entries(source_type, source_id)` for the new source types — the established pattern (`journal_entries` has NO global source uniqueness; index adds ride the §4.5 tenant migration)):

1. **Rounding** — `R = cash_rounding_adjustment` (v3, ≠ 0): `R > 0` ⇒ `Dr ProductRevenue R / Cr 7580 (PaymentToleranceIncome) R`; `R < 0` ⇒ `Dr 6580 (PaymentToleranceExpense) |R| / Cr ProductRevenue |R|`. `source_type = 'pos_cash_rounding'`, `source_id = receipt->id`, new `JournalCode::fromSourceType` mapping. Refund/void events with a non-zero adjustment get the symmetric reversal (legs flipped, `pos_cash_rounding_refund`) — forward-compat for canonical refunds, mirroring `createPOSRefundReversalEntry`'s stance.
2. **Tolerance** — `S = max(0, total − Σ legs)` (> 0): `Dr 6580 S / Cr ProductRevenue S` — the exact shape of the legacy `createPOSPaymentToleranceEntry` (`GeneralLedgerService.php:3246-3300`), reused/adapted; `source_type = 'pos_payment_tolerance'`, `source_id = receipt->id`. Applies whether the shortfall was tolerance-auto-accepted or manager-PIN-approved (evidence already lives in `approval_references` + the OVERRIDE event; the bridge does not re-authorize). If `S` exceeds the resolved config AND no tender-tolerance approval reference exists, still post (the receipt is signed law) + structured warning log `pos.tolerance.shortfall_exceeds_config`.

**Worked check** (TND, exact 9.973, D 0.050 ⇒ rounded 9.950, adj −0.023; tendered 9.900, shortfall 0.050): legs net 9.900 ⇒ `Dr Cash 9.900 / Cr Rev 9.900`; tolerance ⇒ `Dr 6580 0.050 / Cr Rev 0.050`; rounding ⇒ `Dr 6580 0.023 / Cr Rev 0.023`. Net: Cash 9.900, Revenue 9.973 (= exact), 6580 0.073. Drawer, revenue, and write-offs all reconcile to the millime.

**Missing 6580/7580 on brownfield companies** (charts seeded before commit `2c238ce7f` lack them): `findByPurposeOrFail` throws ⇒ projection job retries and surfaces in Horizon (fail-loud, consistent with the bridge's existing stance on missing GL links). Deploy checklist gains a purpose-backfill step (§7).

### 4.7 Refunds (explicit v1 stance)

Live refunds go through legacy `ReceiptReturnService` (server-authored, outside the hash chain, recomputes exact totals from lines) — a refund of a rounded sale refunds the **exact** line value, and no rounding field exists on that path; correct and unchanged. Canonical REFUND/VOID payloads (not yet authorable from any UI) accept `cash_rounding_adjustment` under the same v3 identity, and the bridge posts the symmetric reversal (§4.6) — so when canonical refund authoring lands, rounding is already coherent. 🎫 Follow-up ticket: device refund UX should coin-round cash refund payouts (needs canonical refund authoring first).

## 5. Edge cases

- Denomination ≤ 0 / null with `enabled=true` (corrupt config): helper treats as disabled; server resolver never emits it (validates on read).
- Exact total already a multiple of D: adjustment `0.000`, still emitted (v3 required field), no GL entry, no receipt line.
- Zero-decimal currencies: helper honors `getCurrencyDecimals`; a denomination below scale resolution disables rounding (guard in helper + resolver).
- Config changes mid-sale (sync tick between screen and finalize): payload assembly re-reads the policy once at signing; pre-sign aggregate assert makes any display/payload divergence throw before sealing (never a signed inconsistency; worst case is a re-confirm).
- Voucher/mixed tenders: any non-cash leg (incl. `store_voucher` etc. instrument methods — not `is_physical` cash registers) ⇒ no rounding; tolerance auto-accept still applies only to the cash residual arithmetic (`total − Σ` regardless of mix — matches existing PIN-override scope).
- Offline forever-device: policy cache from last sync applies; never-synced ⇒ disabled (exact behavior, §4.3).
- Old device (v2 author) + new server: valid forever. New device (v3) + old server: quarantine ⇒ **server must deploy first** (§7).
- Training receipts: rounded like sales (§4.1) but excluded from GL/aggregates exactly as training receipts are today (`PaymentToleranceQueryService.php:179-190` stance).

## 7. Compatibility & deploy

- **Order is mandatory: server first** (accepts v2+v3), **then the POS device build** (authors v3 unconditionally). A v3 event hitting a pre-deploy server quarantines. Device v63 stacks on the already-owed v60/v61/v62 — one device update ships all.
- Migrations: all additive + self-guarding (column-adds, nullable/default'd, idempotent TN backfill) — safe for push-to-dev auto-deploy incl. `tenants:migrate`. No new permissions ⇒ no `RolesAndPermissionsSeeder`/`permission:cache-reset` owed by THIS feature (prior treasury owes unchanged).
- **Deploy checklist additions** (folds into the standing staging-owes stack): verify TN backfill row post-migrate; run a 6580/7580 purpose presence check across tenant companies (brownfield charts pre-`2c238ce7f`) and backfill via the chart-purpose path before enabling POS device rollout; Horizon restart (new projector code).
- Rollback stance: device rollback to v62 build reverts authoring to v2 (server keeps accepting); config kill-switch = `UPDATE country_payment_settings SET cash_rounding_enabled = false` (device follows within one sync tick; tolerance likewise).
