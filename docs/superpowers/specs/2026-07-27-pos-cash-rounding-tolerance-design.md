## 1. Problem

Tunisia has no circulating coin below 50 millimes in practice, so a cash total of 9.997 TND is physically untenderable. Today the POS hard-requires full tender to the millime: quick cash throws on any shortfall (`apps/pos/src/stores/paymentStore.ts:874-879`), advanced checkout's only under-tender path is a manager-PIN `tender_tolerance_override` (`paymentStore.ts:1124-1191`). Server tolerance config exists (`country_payment_settings`, TN 0.5% / 0.100 TND) but no endpoint the POS calls ever serves it. Last confirmed functional blocker before the first parapharmacy client onboards.

## 2. Goals

1. Cash-only sale payable is Swedish-rounded to the country-seeded denomination **inside the signed SALE_RECEIPT bytes**, with the denomination itself signed so every receipt is verifiable against the policy that authored it — offline, forever. Card/mixed stay exact.
2. Residual cash shortfalls within configured tolerance auto-accept without a manager PIN; rounding deltas and tolerance write-offs post to `6580`/`7580` on the live fiscal-event pipeline, gated so brownfield data and replays can never poison the projection queue.
3. Config syncs to the device, works fully offline, and fails **closed** (exact behavior) when absent — on every surface, server and device.
4. Every fiscal aggregate stays internally explained: Z/X/grand totals expose `gross = net + vat + rounding`; drawer == Σ rounded totals − change; revenue/loyalty/analytics stay on the exact value (consumer matrix, §4.5).
5. v1/v2 events parse, repair, and replay byte-identically forever; deploy is server-first, two-phase, auto-deploy-safe.

**Non-goals (v1):** per-company rounding UI; canonical REFUND/VOID authoring; wholesale fix of the pre-existing training-GL leak (🎫; new entries are guarded); `'CASH'` string-match normalization (🎫); immutable policy-revision infrastructure with per-shift pinning (signed-denomination field covers v1 verification; 🎫 revision pinning); correcting historical GL drift from pre-existing defects (forward-only + quantification report, §4.6); denominations beyond one per country; multi-currency tender; `ACCOUNT_CHARGE` payloads (separate key set, untouched).

## 3. Approach (reconfirmed post-review)

Fold rounding into `total` + signed sibling fields + extended identity (Approach A of Rev 1; sibling-field-only and synthetic-payment-line rejected for the same reasons — un-reconciled Z/drawer, method-resolution fail-closed). Review-driven changes to the approach: the adjustment is now **policy-verifiable** (signed denomination + hard cap + projection reconciliation — closes the revenue-suppression hole F-B1/C2), the cutover is **payload-versioned** (v3-gated netting/GL — closes replay poisoning T1/C6), and the Z/print/NF525 surfaces are **in scope** (closes B5/M6/C11/C12). Tolerance shortfall stays derivable (`total − Σ payments`) — no new invariant to version; bounded by signed payments + device enforcement + projection-time config check.

## 4. Design

### 4.1 Semantics

Let `exact_total` = cart gross after discount, `D` = resolved denomination, `s` = currency scale.

- **Cash-ness (one rule, both sides):** new boolean `payment_methods.is_cash_tender` (§4.2). A tender leg is cash iff its resolved method has `is_cash_tender = true`. Seeded true only for `CASH` chart variants; custom/unflagged methods (incl. `MEAL_VOUCHER`) are non-cash ⇒ fail-safe exact. Device evaluates over the **union** of `paymentLines` and `voucherTenders` (voucher legs are never cash).
- **Rounding applies iff:** policy `cash_rounding.enabled` AND `D > 0` AND representable at scale `s` AND every leg is cash AND `invoice_type_code ∈ {SALE, TRAINING}` (training mirrors sale for drill realism; GL/aggregates exclude training, §4.5/§4.6).
- `rounded_total = round_half_up(exact_total / D) × D` (device: `Big(exact).div(D).round(0, Big.roundHalfUp).times(D).toFixed(s)`; server verification bcmath at `s+1` intermediates). `cash_rounding_adjustment = rounded_total − exact_total`, signed, `|adj| ≤ D/2` (tie rounds up ⇒ `+D/2` reachable).
- **Payload (v3):** `total = rounded_total`; TWO new required fields — `cash_rounding_adjustment` (signed) and `cash_rounding_denomination` (non-negative; the denomination actually applied, `0` when rounding did not apply). When not applied: adjustment `0`, denomination `0`, `total = exact_total`. `subtotal`/`vat_total`/`vat_breakdown`/lines/discount UNTOUCHED — rounding is VAT-neutral, aggregate-level only.
- **Identity + hard static binds (v3, validator + device pre-sign):**
  1. `subtotal + vat_total == (total − cash_rounding_adjustment) + transaction_discount_amount` (exact; absent fields ⇒ zero ⇒ degenerates to today's identity for v1/v2 — one code path).
  2. If `cash_rounding_adjustment ≠ 0`: `cash_rounding_denomination > 0`, `|adjustment| ≤ denomination/2`, and `total` is an exact multiple of `denomination` (bcmod == 0). If adjustment `= 0`: no constraint on denomination beyond regex (it may be `0` or the applied-but-no-op denomination).
  3. Static cap independent of config: `cash_rounding_denomination ≤ 1.000` at scale 3 / `1.00` at scale 2 / `5` at scale 0 (constants; deterministic, history-stable). Together (2)+(3) cap `|adj|` absolutely — the identity is no longer a free parameter; a suppression payload (`total=5.000, adj=-95.000`) fails (2) and (3) and quarantines. Explicit rejection tests in §6.
- **Change eligibility (new device invariant, closes C5):** `change = Σ payments − total` when positive, and checkout REFUSES to complete when `change > Σ cash-leg amounts` (card/instrument legs never produce change; card-only over-tender is rejected before signing). Server-side the bridge nets change only from cash legs and alerts if the invariant is violated by an old/foreign event (§4.6).
- **Tolerance (cash under-tender):** `shortfall = total − Σ payments` when positive. Device auto-accepts without PIN iff policy `tolerance.enabled` AND every leg is cash AND `shortfall ≤ effective_max`, where `effective_max = min(percentage × total, max_amount)` — **plus the §8-flagged denomination floor option** (recommended: `effective_max = max(min(pct × total, max_amount), D)` when rounding is active, so a customer short exactly one coin auto-accepts on any basket; without the floor, sub-10-TND single-coin shortfalls stay PIN-gated under seeded TN values: `0.005 × 9.950 = 0.0498 < 0.050`). Beyond ⇒ existing manager-PIN path, unchanged. Zero-total sales: no tolerance, no rounding, no GL. Over-tender is change, never a 758 gain; 758 arises only from round-up.

### 4.2 Config: columns, resolver, POS endpoint (server)

- **Tenant migration A (schema + data, self-guarding):**

  2. `country_payment_settings.cash_rounding_enabled` boolean default **false**; `cash_rounding_denomination` decimal(15,4) nullable; model `$fillable` + `$casts` (**`'string'` cast** — rule 19, never float).

SET cash_rounding_denomination = 0.0500 WHERE country_code = 'TN' AND cash_rounding_denomination IS NULL`. **`cash_rounding_enabled` stays false in the migration** — the flip is an ops action (below), decoupling behavior activation from auto-deployed `tenants:migrate`.

### 4.6 GL (TreasuryReceiptBridge — Horizon worker, Treasury-gated)

**Cutover rule (closes T1/C6): ALL new behavior in this section applies to `event_version >= 3` SALE_RECEIPT events only.** v1/v2 events replay byte-identically to today (tendered-amount legs, no netting, no new entries) — payload-derived, deterministic, no config/time dependency. Historical drift from the pre-existing defects (over-tender revenue, training GL, PIN-shortfall never booked) is **forward-only**: 🎫 one-off quantification report (enumerate affected receipts, Σ drift per company) for the owner/accountant; no mutation of posted entries.

**Training guard (C1):** for v3 events with `training_flag = true`, the bridge posts NOTHING new (and the pre-existing leg-posting for training receipts is ticketed, not silently changed here — but the new rounding/tolerance entries check the flag explicitly).

**Change-netting (v3 only):** a pre-pass in `apply()` over `$view->payments` in canonical index order (M18 — the per-leg method cannot see siblings): resolve each leg's method once, classify cash via `is_cash_tender`, compute `change = max(0, Σ legs − total)`, subtract from the LAST cash leg cascading backwards (deterministic under replay — pure function of the sealed payload). Zero-netted legs create **no Payment / no GL / no movement** (T2 — pgsql `CHECK (amount > 0)`; ordinal holes in `fiscal_event:{id}:payment:{i}` documented as legal; Treasury `payments` rows are no longer 1:1 with `pos_receipt_payments`). If `change > Σ cash legs` (foreign/old event violating §4.1's device invariant): net what cash allows, durable alert `pos.change.exceeds_cash_legs`. **Two-semantics rule (M14), documented in code + docs:** Treasury `payments.amount` = amount RETAINED (net of change); `pos_receipt_payments.amount` = amount TENDERED. Consumers pick per the matrix.

**New entries** (each: training-guarded, v3-gated, `hasAccountForPurpose` precheck — missing purpose ⇒ **skip entry + durable structured alert** `pos.gl.tolerance_purpose_missing`, never a whole-receipt projection failure (T3; the receipt's payment legs still post); created + `postEntryNow($entry, $receipt->cashier, $receipt->currency)` inside the existing per-event transaction; idempotent via source-type-scoped existence check + the §4.5 partial unique indexes):

1. **Rounding** — `R = cash_rounding_adjustment ≠ 0`: `R > 0` ⇒ `Dr ProductRevenue R / Cr 7580 R`; `R < 0` ⇒ `Dr 6580 |R| / Cr ProductRevenue |R|`. `source_type = 'pos_cash_rounding'` (JournalCode: explicit decision = default `Misc`/OD, consistent with tolerance today — m18/T16). Canonical REFUND/VOID v3 events (unauthored today) get the symmetric reversal, `source_type = 'pos_cash_rounding_refund'`.
2. **Tolerance** — `S = max(0, total − Σ legs) > 0`: `Dr 6580 S / Cr ProductRevenue S` (legacy `createPOSPaymentToleranceEntry` shape, `GeneralLedgerService.php:3246-3300`, adapted). **`source_type = 'pos_tolerance_bridge'`** — distinct from legacy `pos_payment_tolerance` so the unique index never collides with brownfield rows (T8); disjointness also structural (legacy receipts have no fiscal event; bridge keys on `fiscal_event_id`). Applies to auto-accepted and PIN-approved shortfalls alike; if `S` exceeds the resolved config with no tender-tolerance approval reference ⇒ post + warn `pos.tolerance.shortfall_exceeds_config`.

**Worked check** (self-consistent under the §8 denomination-floor option; TN, D 0.050): exact 9.973 ⇒ rounded 9.950, `adj = −0.023`, denomination 0.050 signed. Tendered 9.900 ⇒ `S = 0.050 ≤ effective_max = max(min(0.005×9.950, 0.100), 0.050) = 0.050` ⇒ auto-accepted. Legs net 9.900 (no change) ⇒ `Dr Cash 9.900 / Cr Rev 9.900`; tolerance ⇒ `Dr 6580 0.050 / Cr Rev 0.050`; rounding ⇒ `Dr 6580 0.023 / Cr Rev 0.023`. Net: Cash 9.900, Revenue 9.973 = exact, 6580 0.073; debits == credits at every entry. (Without the floor this example is PIN-gated — stated in §8.)

### 4.7 Refunds (v1 stance + §8 escalation)

Live refunds ride legacy `ReceiptReturnService` (exact recompute, outside hash chain). Unmitigated, refunding a rounded cash sale pays out untenderable millimes on day 1 (M16) — the failure mode this feature exists to remove. **Minimal v1 remedy (recommended, §8 owner decision):** the refund settlement screen rounds the CASH payout to `D` (same helper/policy) and the server refund path books the delta via the existing 6580/7580 purposes (`source_type = 'pos_refund_rounding'`); refund documents show the same rounding line. Canonical REFUND/VOID authoring stays out of scope; the v3 validator + bridge already handle it symmetrically for when it lands.

## 5. Edge cases

- Corrupt config (`enabled` with `D ≤ 0` / below scale resolution): helper disables; resolver never emits it; validator bind (2) rejects a signed contradiction.
- Exact multiple: adjustment `0`, denomination still signed as applied value, no GL, no receipt line.
- Zero-total / 100%-discount: `total` clamps `'0'` (`receiptService.ts:284`); rounding no-ops; `effective_max = 0` unless floor active — floor applies only when a cash amount is actually due (`exact_total > 0`); no GL.
- Mixed/voucher tenders: union rule (§4.1); voucher-partial sales never round; `MEAL_VOUCHER` non-cash by flag.
- Mid-sale policy sync: CheckoutPolicySnapshot is what signs; a tick cannot alter a signed number (§4.3).
- Offline forever / never-synced: last-synced or disabled policy; signed denomination keeps every receipt verifiable regardless of staleness (§4.5 reconciliation flags drift).
- Old device (v2) + new server: valid forever, no new GL behavior (v3 gate). New device + old server: v3 quarantines ⇒ server-first deploy (§7); post-upgrade repair works because `ParseFailureResolutionService` is version-threaded (§4.4).
- Replay: netting + entries are pure functions of sealed v3 payloads; pre-seeded tendered-amount Payment rows only exist for v1/v2 events, which the new code never touches (T1 test pins this).
- Training: rounded at checkout, signed, excluded from write-offs/GL/tolerance queries (`PaymentToleranceQueryService.php:179-192` filter + new guards).
- Negative totals: unreachable (`total` non-negative regex retained; only the adjustment is signed; `|adj|` bound by (2)+(3)).
