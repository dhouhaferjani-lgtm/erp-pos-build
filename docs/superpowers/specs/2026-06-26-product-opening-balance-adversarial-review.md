# Adversarial Review — Opening Balance Design (2026-06-26)

## Critical (would cause data loss, fiscal failure, or security bypass)

1. **Bundling opening balance into `POST /products` lets product creators post inventory and GL without inventory/accounting authority.**  
   **Spec gap cited:** Section 1 says product create posts stock plus `Dr Inventory / Cr Opening Balance Equity` (lines 10-20), and Section 5 bundles the posting inside `ProductController::store` (lines 104-124). It never adds an authorization requirement beyond the existing product create route. Existing route evidence: `apps/api/app/Modules/Product/routes.php` gates `POST products` with `can:products.create` (lines 57-59), while existing opening-balance import posting is gated by `can:accounts.manage` in `apps/api/app/Modules/Accounting/Presentation/routes.php` (lines 152-154), and stock adjustment is explicitly `can:inventory.adjust` per `AdjustStockRequest` (lines 13-16).  
   **Concrete failure scenario:** A user who can create products but cannot manage accounts or adjust inventory submits `opening_qty=1000` and `opening_unit_cost=10.000`. The spec would create stock, change WAC/cost basis, and post a GL entry under only `products.create`. That is a privilege escalation into accounting and inventory valuation.  
   **Recommended fix:** Require a separate permission for inline opening, at minimum `products.create` plus an inventory/accounting permission such as `inventory.adjust` and/or `accounts.manage`, or move opening posting to a separate endpoint with explicit authorization. The UI must hide/disable the section under the same permission, but the server must enforce it.

2. **Inline non-historical GL entries bypass the GL fiscal hash chain.**  
   **Spec gap cited:** Section 4.1 creates a `JournalEntry` directly with `status=Posted` (lines 80-85). Section 5 sets inline `isHistorical=false` (lines 118-123). Section 9 only says openings are not part of the POS fiscal hash chain (lines 177-179); it does not require the GL hash chain. Existing evidence: `JournalEntry` has `fiscal_hash`, `previous_hash`, and `chain_sequence` fields (`apps/api/app/Modules/Accounting/Domain/JournalEntry.php`, lines 29-31), and `GeneralLedgerService::postEntry` assigns `chain_sequence`, `fiscal_hash`, and `previous_hash` before dispatching `JournalEntryPosted` (`apps/api/app/Modules/Accounting/Domain/Services/GeneralLedgerService.php`, lines 1289-1312).  
   **Concrete failure scenario:** Inline opening creates a today-dated, non-historical posted journal entry with no `fiscal_hash` and no `chain_sequence`. Trial balance includes it, but GL chain verification ignores it because it has no fiscal hash. This creates an unsealed posted accounting entry in production.  
   **Recommended fix:** Decide explicitly whether inline openings are historical or live GL. If live (`is_historical=false`), create the entry through the canonical GL posting/hash path or add equivalent hash-chain assignment inside `OpeningBalancePostingService`. If historical, set `is_historical=true` and document why a create-form opening is treated like cutover history.

3. **The enter-once invariant is only a controller pre-check, not a service or database invariant.**  
   **Spec gap cited:** Section 1 promises “server refuses a second opening” (lines 17-20), but Section 5 only checks `InventoryService->hasMovements($product->id) === false` in `ProductController::store` before calling the posting service (lines 117-123). Section 4.1 makes `OpeningBalancePostingService` reusable for both import and inline paths but does not put any duplicate-opening check or idempotency key inside that service (lines 67-85). Existing database evidence: `stock_movements` has indexes but no unique guard for one opening per product/source (`apps/api/database/migrations/tenant/2025_11_30_110000_create_inventory_tables.php`, lines 32-49); the only later stock-movement partial unique guard is for reversal idempotency, not opening creation (`2026_06_25_120000_add_reverses_movement_id_to_stock_movements.php`, lines 11-23).  
   **Concrete failure scenario:** Any future caller, bulk import adapter, test helper, queue retry, or direct service call can invoke `OpeningBalancePostingService::post()` twice for the same product and source. The service will add quantity twice, replace cost twice, and post two GL entries. The design’s “server invariant” is bypassed because the invariant is outside the reusable use case.  
   **Recommended fix:** Move the enter-once/idempotency rule into `OpeningBalancePostingService` under the same product advisory lock, and back it with a database uniqueness strategy, for example a dedicated opening-balance posting table or a partial unique index keyed by company/product/variant/source where feasible. The product controller should become an adapter, not the only guard.

4. **Wrong opening cost cannot be corrected through the specified adjustment path.**  
   **Spec gap cited:** Section 1 and Section 2 route all post-opening changes to the stock adjustment flow (lines 17-20 and 32-33). Section 3 explicitly says adjustments are “Quantity only — WAC unchanged” (lines 46-50). Existing API evidence: `AdjustStockRequest` accepts only `product_id`, `location_id`, `new_quantity`, and reason fields, with no unit cost or GL correction input (`apps/api/app/Modules/Inventory/Presentation/Requests/AdjustStockRequest.php`, lines 24-33); `StockAdjustmentService::adjust()` updates quantity and records an adjustment movement, but does not change product cost or reverse the opening GL entry (`apps/api/app/Modules/Inventory/Domain/Services/StockAdjustmentService.php`, lines 617-637).  
   **Concrete failure scenario:** User creates a product with `opening_qty=100` and accidentally enters `opening_unit_cost=50.000` instead of `5.000`. The product is immediately locked. The recommended adjustment flow can reduce/increase quantity but cannot fix `products.cost_price` or reverse/restate the `Dr Inventory / Cr Opening Balance Equity` amount. COGS and inventory valuation stay wrong.  
   **Recommended fix:** Define a correction flow before implementation: either reversal plus replacement opening while no downstream movements exist, or a cost adjustment/revaluation flow that posts the required GL correction and updates WAC under lock. The product-page helper must point to the correction flow when the mistake is valuation, not just quantity.

5. **Opening balances can be posted into locations the user is not authorized to access.**  
   **Spec gap cited:** Section 2 says the location is auto-resolved via `LocationContext->resolveLocationId(null, companyId)` (lines 29-31), and Section 5 uses that result without an access check (lines 115-123). Existing evidence: `LocationContext` has an explicit `validateLocationAccess()` method for defense-in-depth (`apps/api/app/Modules/Company/Services/LocationContext.php`, lines 225-235), and the stock adjustment controller calls it before adjustment (`apps/api/app/Modules/Inventory/Presentation/Controllers/StockMovementController.php`, lines 223-229). The spec does not require the same validation.  
   **Concrete failure scenario:** A user restricted to Location A creates a product while the company default/current resolved location is Location B. The opening movement and stock level are created in Location B even though the user could not adjust stock there through the normal stock endpoint.  
   **Recommended fix:** After resolving the location, call `LocationContext->validateLocationAccess($locationId, $companyId, $user)` in the product create adapter, and include a test for a user restricted away from the default location.

## High (would cause wrong data or broken UX at runtime)

1. **The spec says “company default location,” but the cited API resolves current active location first.**  
   **Spec gap cited:** Section 2 says “auto-resolve the company default” using `resolveLocationId(null, companyId)` (lines 29-31), and Section 9 says “No default location configured -> 422” (line 176). Existing evidence: `LocationContext::resolveLocationId()` returns the current active location before the default location (`apps/api/app/Modules/Company/Services/LocationContext.php`, lines 119-144), and `getDefaultLocation()` falls back to the first active location when no default exists (lines 88-116).  
   **Concrete failure scenario:** In a multi-branch company, the opening stock lands in the user’s current active location, not the company default the spec promises. If there is no default but one active location exists, the design’s promised 422 never happens; stock is silently posted to the first active location.  
   **Recommended fix:** If the intended behavior is truly company default only, do not call `resolveLocationId(null, companyId)`. Add a method that returns only an active default location and returns null if none exists. If current-location fallback is intended, change the spec, UI copy, and tests to say so.

2. **The IziPOS scope is not enforced server-side.**  
   **Spec gap cited:** Title and status frame this as “IZI POS editor” work (line 1), but Sections 5-8 modify the shared `ProductController`, `CreateProductRequest`, `ProductData`, and `ProductForm.tsx` without any IziPOS product/vertical gate (lines 104-168). Existing evidence: `Product/routes.php` gates product CRUD only by `module:Inventory` and product permissions (lines 42-67). `Vertical::product()` maps automotive/Otospex verticals separately from IziPOS verticals (`apps/api/app/Enums/Vertical.php`, lines 74-93), and `ProductService::isIziPOS()` exists (`apps/api/app/Services/ProductService.php`, lines 32-38).  
   **Concrete failure scenario:** An Otospex tenant with Inventory enabled receives the inline opening balance fields and can post opening stock/GL through the shared product create endpoint, even though the delivery is scoped to IziPOS.  
   **Recommended fix:** Add an explicit server-side product or vertical gate for inline opening posting, and mirror it in the frontend. Tests should cover at least one Otospex vertical rejecting or ignoring opening fields.

3. **The service does not specify a physical-product guard.**  
   **Spec gap cited:** Sections 5 and 6 validate only quantity and unit cost (lines 114-123 and 134-140); they do not forbid openings for `ProductType::Service` or `is_physical=false`. Existing evidence: `CreateProductRequest` derives `is_physical=false` for services and enforces type/physical coherence (`apps/api/app/Modules/Product/Presentation/Requests/CreateProductRequest.php`, lines 39-55 and 92-134), but the opening-balance rules are independent.  
   **Concrete failure scenario:** A service product is created with `opening_qty=10`. The spec posts stock movement and stock level for a non-physical product. Downstream inventory reports and COGS assumptions treat a service as stocked inventory.  
   **Recommended fix:** Add validation: opening fields are prohibited unless the final product is physical. Put the same guard in the posting adapter/service so a forged API request cannot bypass UI conditions.

4. **Stock movement domain events are missing from the opening path.**  
   **Spec gap cited:** Section 4.1 creates `StockMovement` rows (lines 76-79) but never dispatches `StockMovementRecorded`/V2. Existing evidence: `StockMovement` is a plain model with no observer-dispatched event (`apps/api/app/Modules/Inventory/Domain/StockMovement.php`, lines 54-82). WAC and adjustment paths manually dispatch movement events after creating movements (`WeightedAverageCostService.php`, lines 841-884; `StockAdjustmentService.php`, lines 638-675). Channel sync listens to `StockMovementRecorded` (`apps/api/app/Modules/Channel/Providers/ChannelServiceProvider.php`, lines 24-29).  
   **Concrete failure scenario:** Inline opening creates stock and GL, but external channel stock sync and any audit listeners wired to `StockMovementRecorded` do not see the initial stock change. The product appears in the ERP with inventory but remains out of sync in channels until a later movement or reconciliation job.  
   **Recommended fix:** Dispatch `StockMovementRecorded` and `StockMovementRecordedV2` after commit for every created opening movement, or explicitly document why opening movements are excluded and ensure downstream consumers do not require them.

5. **`ProductCreated` is still fired inside a transaction that may later roll back.**  
   **Spec gap cited:** Section 5 wraps `ProductController::store` in a transaction but keeps “fire ProductCreated” before the opening post (lines 111-123). Existing evidence: current `ProductController::store` dispatches `ProductCreated` immediately after `Product::create()` (`apps/api/app/Modules/Product/Presentation/Controllers/ProductController.php`, lines 348-363). The event is an operational domain event (`apps/api/app/Modules/Product/Domain/Events/ProductCreated.php`, lines 9-18).  
   **Concrete failure scenario:** Product insert succeeds and `ProductCreated` is dispatched, then opening posting fails because no inventory/OBE account exists or the location check fails. The transaction rolls back the product, but listeners may already have recorded or acted on a product that no longer exists.  
   **Recommended fix:** Move product/opening side-effect events to `DB::afterCommit()` or dispatch after the outer transaction has committed. Add a failure test proving no product-created side effect fires when opening posting fails.

6. **Concurrent entry-number generation can fail or collide for openings on different products.**  
   **Spec gap cited:** Section 4.1 moves `generateEntryNumber(companyId)` verbatim into the posting service (lines 74-75). Existing evidence: current `InventoryOpeningService::generateEntryNumber()` reads the last `INV-OB-{year}` entry and increments without locking (`apps/api/app/Modules/Inventory/Application/Services/InventoryOpeningService.php`, lines 447-465). `journal_entries` enforces unique `(tenant_id, entry_number)` (`apps/api/database/migrations/tenant/2025_11_30_100000_create_journal_entries_table.php`, lines 40-41). Product advisory locks are per product (`ProductCostLock.php`, lines 11-17), so openings for different products do not serialize.  
   **Concrete failure scenario:** Two users create different products with opening balances at the same time. Both transactions read the same last `INV-OB` number and generate the same next number. One insert hits the unique constraint and the entire product create fails, even though there is no business conflict.  
   **Recommended fix:** Use a database-backed sequence/table lock for `INV-OB` numbering, or generate source-derived unique entry numbers for inline openings. Add a two-request concurrency test over different products.

7. **Zero or missing unit cost silently creates zero-cost inventory.**  
   **Spec gap cited:** Section 5 says `opening_qty > 0` posts, and `opening_unit_cost=0` leaves `cost_price` untouched (lines 114-128). Section 6 makes `opening_unit_cost` nullable (lines 134-137). Section 9 repeats that zero unit cost posts a movement (lines 173-174).  
   **Concrete failure scenario:** User enters quantity, forgets unit cost, and saves. The system creates stock and a zero-value GL entry/movement, but WAC remains zero. Later sales can post zero COGS until a purchase or cost correction occurs. This is especially dangerous because the design locks the opening fields immediately after the movement.  
   **Recommended fix:** Make `opening_unit_cost` required when `opening_qty > 0`, unless the user explicitly confirms a zero-cost opening with a distinct control and audit note. If zero-cost openings are legitimate, define the accounting behavior and correction path.

## Medium (ambiguity, missing validation, edge case not handled)

1. **The reusable DTO/service boundary lacks canonicalization rules.**  
   **Spec gap cited:** Section 4 defines DTOs with quantity and unit cost “strings” (lines 56-64), and Section 6 says “Strings end-to-end” (line 140), but only `CreateProductRequest` has regex validation (lines 134-137). The precision contract requires bcmath/Big.js and rounding once at the write boundary (`docs/architecture/precision-contract.md`, lines 13, 24-28, and 51-55).  
   **Concrete failure scenario:** The import adapter or a future internal caller passes `"1.23456"` or a float-cast string into `OpeningBalancePostingService`. The service spec does not require DTO constructors or service entry to validate/canonicalize with `QuantityScale`/`CurrencyScale`, so different callers can reach storage with different precision behavior.  
   **Recommended fix:** Make `OpeningBalanceLine` validate/canonicalize quantity to scale 4 and unit cost/value to the intended cost/currency scale, and reject non-string numeric inputs at the service boundary.

2. **The new `hasMovements(productId)` contract omits tenant/company scope.**  
   **Spec gap cited:** Section 7 adds `public function hasMovements(string $productId): bool` (lines 142-154). Existing `InventoryServiceInterface::upsertStockLevel()` requires tenant and company IDs (lines 19-25), and `StockMovement` carries both tenant and company (`apps/api/app/Modules/Inventory/Domain/StockMovement.php`, lines 21-27).  
   **Concrete failure scenario:** The implementation can accidentally query only by product ID, creating a new cross-module method that does not encode tenant/company isolation in its signature. Even if product UUIDs are globally unique today, the interface no longer makes the isolation requirement explicit.  
   **Recommended fix:** Define `hasMovements(string $tenantId, string $companyId, string $productId): bool` and require all implementations to scope on all three fields.

3. **No explicit behavior for `opening_qty=0` with nonzero cost, or cost entered then quantity cleared.**  
   **Spec gap cited:** Section 5 says empty/zero quantity posts nothing (line 127), while Section 6 allows nullable cost independently (lines 134-137). The frontend section in Section 8 does not define conditional clearing, warnings, or dirty-state behavior (lines 161-168).  
   **Concrete failure scenario:** User enters cost first, later clears quantity, and saves. The cost is silently discarded because the backend posts nothing. The UI does not tell the user that their entered cost will be ignored.  
   **Recommended fix:** Add conditional validation or UI behavior: clear/disable cost when quantity is empty/zero, or return a 422 when cost is provided without positive quantity.

4. **Negative opening stock is rejected without an alternate migration path.**  
   **Spec gap cited:** Section 6 uses `min:0` and unsigned regexes for both opening fields (lines 134-137), and Section 9 only covers zero/empty and zero-cost cases (lines 170-176). The precision contract explicitly allows negative regex variants where negatives are legitimate (`docs/architecture/precision-contract.md`, lines 34-35).  
   **Concrete failure scenario:** A tenant migrates from an old POS after selling items before completing stock setup, so the initial counted quantity for a SKU is negative. The inline form cannot represent it and the spec does not say whether to use stock adjustment, import, or a correction workflow.  
   **Recommended fix:** State whether negative openings are prohibited by accounting policy. If prohibited, document the required operational path. If supported, use signed quantity validation and define GL/WAC consequences.

5. **The test plan does not exercise the adversarial concurrency/idempotency cases it claims to cover.**  
   **Spec gap cited:** Section 9 says double submit/retry is guarded by transaction plus `hasMovements` (line 175), but Section 10 lists only simple product create and enter-once tests (lines 181-194).  
   **Concrete failure scenario:** The implementation passes all planned tests while still failing two simultaneous product-opening requests, duplicate service calls, unique entry-number races, or retry-after-timeout idempotency.  
   **Recommended fix:** Add tests for duplicate service calls, simultaneous openings for the same product/source, simultaneous openings for different products, and retry after a forced failure inside posting.

6. **The missing handoff document blocks review of the superseded open questions.**  
   **Spec gap cited:** The spec says it supersedes `docs/handoff/HANDOVER-opening-balance.md` (line 6), and the task explicitly asked to cross-reference that file. The file is absent in this worktree; `find docs -iname '*opening*balance*'` only found archive/spec/testing files and the current design spec.  
   **Concrete failure scenario:** An open question in the handoff may have been silently dropped, and reviewers cannot verify that the design actually supersedes it.  
   **Recommended fix:** Restore the handoff document, update the spec with a replacement link, or copy the superseded questions into an appendix before handoff.

## Low / Nits (minor gaps worth noting)

1. **The UI lock copy points to “Inventory › Stock,” but the exact route/action is not specified.**  
   **Spec gap cited:** Section 8 suggests helper text pointing to “Inventory › Stock” (lines 166-168). Existing frontend stock adjustment lives in `StockLevelsPage` via `POST /stock-movements/adjust` (`apps/web/src/features/inventory/StockLevelsPage.tsx`, lines 95-119 and 625-628).  
   **Concrete failure scenario:** Implementers add generic helper text without a link or route, leaving users locked out of opening fields but unsure where to correct quantity.  
   **Recommended fix:** Specify the route and, if feasible, include product/location query prefill.

2. **`opening_unit_cost` naming hides that the value seeds WAC/cost basis, not purchase price.**  
   **Spec gap cited:** Sections 1 and 8 introduce `opening_unit_cost` as “money” beside opening quantity (lines 10-15 and 161-164), while Section 3 says this directly replaces the cost basis (lines 40-52).  
   **Concrete failure scenario:** UI labels may lead users to enter sale price or supplier list price instead of valuation cost, especially because the existing product form already has purchase and sale price fields nearby.  
   **Recommended fix:** Require label/help text that says this is the inventory valuation cost used for WAC and GL opening value.

## Verdict

The spec is not safe to implement as-is. It needs a revision pass before handoff, mainly to close authorization, GL hash-chain, service-level idempotency, correction, and location-resolution gaps. The design is directionally usable, but the current wording would let an implementation pass the stated tests while still producing unsealed GL entries, unauthorized inventory valuation changes, duplicate openings, and unrecoverable cost mistakes.
