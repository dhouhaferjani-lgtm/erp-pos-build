## Task 1 (P1) — boot must not wipe the persisted company selection
Root cause: `apps/web/src/stores/authStore.ts` persists `user` + `token` but NOT `isAuthenticated` (starts `false`). `AuthProvider` renders children as soon as a persisted `user` exists, so `CompanyProvider.tsx` ~line 126:
```ts
useEffect(() => { if (!isAuthenticated) { reset(); queryClient.removeQueries({ predicate: userCompaniesPredicate }) } }, [...])
```
runs on EVERY page load, and `reset()` does `localStorage.removeItem('autoerp-company-selection')`. When `/auth/me` then resolves and `/user/companies` loads, `resolveCompanySelection` finds no persisted id and picks the primary company, re-persisting it over the user's choice. Reproduced: switch to a non-primary company → reload → back on the primary, key overwritten.
Fix (exactly this): make that effect fire only on a genuine authenticated → unauthenticated transition — track `wasAuthenticated` in a `useRef`, set it true when `isAuthenticated` becomes true, and call `reset()` + `removeQueries` only when `wasAuthenticated.current && !isAuthenticated`. Do NOT start persisting `isAuthenticated` (the comment in `authStore` explains why). Real logout already goes through `clearAllAppState` (`useLogout.ts`, `AuthProvider` 401 path), so nothing is lost.
Tests first: `apps/web/src/features/company/CompanyProvider*.test.tsx` — (a) boot with a persisted `user` and `autoerp-company-selection = B` (non-primary), auth resolves after companies → the store ends on `B` and the key still reads `B`; (b) a real logout (isAuthenticated true → false) still resets the store and removes the key.

## Task 2 (P2) — creating a company must switch to it (row 1e)
`useCompanyStore.setCurrentCompany(id)` refuses ids not in `state.companies`; `AddCompanyModal.tsx:70-74` and `CompanyOnboardingPage.tsx:~66-70` call it with the freshly created id before the list refetches → silent no-op (reproduced: after "Create Company" the header still shows the old company). Add a store action `adoptCreatedCompany(company: Company)` that appends the company if absent, clears any remembered denial, sets `currentCompanyId`, and persists via `persistCompanyId`; map the `POST /companies` response to the store `Company` shape (extend `features/company/api.ts` `CreateCompanyResponse` from what `CompanyController::store` actually returns — do not invent fields); call it from both places; keep the existing `invalidateCompanies()` call. `setCurrentCompany`'s guard stays.
Tests first: store test (adopt selects + persists an unknown id; `setCurrentCompany` with an unknown id still no-ops) and an `AddCompanyModal` test asserting `currentCompanyId` + `localStorage['autoerp-company-selection']` equal the new id after create.

## Task 3 (P3) — no "Access denied" noise when switching company
On a manual switch, `CompanySelector.handleCompanyChange` calls `switchCompany` then a blanket `queryClient.invalidateQueries()`; for one render the old-company location-scoped queries refetch with the previous company's `location_ids[]` and get a 403 (`treasury/cash-position` observed), surfaced as an "Access denied…" error. In `apps/web/src/lib/api.ts` 403 handling (~line 170 where the "Access denied" message is logged/toasted), suppress the user-facing surfacing when the response's request carried an `X-Company-Id` that no longer equals `useCompanyStore.getState().currentCompanyId` (the same "sent vs current" matching `handleCompanyScopeRejection` already uses) — still reject the promise. Test first in the existing `lib/api*.test.ts` suite: a 403 whose request header is a stale company id does not toast/log-as-error; a 403 for the current company still does.
